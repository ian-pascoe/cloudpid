# AGENTS.md

## Design

- **Spec**: before designing or changing architecture, packages, Durable Objects, tools, or the client protocol, read `docs/spec.md`; it records the settled design and milestones.
- **Tool names**: every model-facing tool name is snake_case (`browser_handoff`, `subagent_wait`); wrap and rename library tools that are not.

## Workspace

Layout is in `docs/spec.md` → _Repository layout_. Root `typecheck`, `lint`, `test`, and `build` scripts run through Turborepo (`turbo.json`); `pnpm check` runs all but `build`, then `format:check` (oxfmt runs once at the root). Run one package with `pnpm --filter @cloudpid/protocol test`.

Every workspace package (`apps/*`, `infra`, `packages/*`) is named `@cloudpid/<dir>` and follows the same shape:

- **Just-in-time**: `exports` point at `src/*.ts`; there is no build step to run before dependents see a change. Add the package's own tests as `src/*.test.ts`. Tests that need workerd (Durable Object storage, alarms, eviction) are `src/**/*.workerd.test.ts`, run by the package's `workerd` Vitest project through `@cloudflare/vitest-plugin` (see `apps/server/vitest.config.ts`): `pnpm exec vitest run --project workerd <file>`. The plugin is patched (`patches/@cloudflare__vitest-plugin@1.4.6.patch`) to keep the module snapshot it sends a reused worker under workerd's 32 MiB WebSocket message limit, past which the worker dies with `1009 Message is too large` ([cloudflare/workers-sdk#16349](https://github.com/cloudflare/workers-sdk/issues/16349)). When upgrading the plugin, `pnpm install` fails on the stale patch: drop it if upstream fixed #16349, else port it.
- **`package.json`** has `typecheck` (`tsc`), `lint` (`oxlint`), and `test` (`vitest run`) scripts, and a `workspace:*` devDependency on `@cloudpid/config`.
- **`tsconfig.json`** extends `@cloudpid/config/tsconfig/base.json`; **`vitest.config.ts`** re-exports `@cloudpid/config/vitest`; **`.oxlintrc.json`** extends the root config. Copy these from a sibling package instead of editing the shared bases per package.
- Tooling (`typescript`, `vitest`, `oxlint`, `oxfmt`, `turbo`) is installed once at the root; packages do not list it.
- Runtime dependencies go in the package that imports them (`pnpm --filter @cloudpid/<pkg> add …`); the ones still at the root (`pi-*`, `@cloudflare/*`) move to their first consumer when a ticket starts using them.
- Relative imports end in `.ts` (`allowImportingTsExtensions` is on in the shared tsconfig), so every file also runs under plain Node type stripping.
- Effect's `http` modules are unstable but allowed through `allowedUnstableApis` in the shared tsconfig; add other unstable subtrees (`effect/rpc`, …) there when a ticket adopts them.
- `skills/` is bundled skill content, not a package (see _Skills_ below).

`pnpm install` skips the reference-repository clones when `CI` or `SKIP_REFERENCE_REPOS` is set; the `effect-tsgo` patch still runs.

## Skills

`skills/` holds the headless-safe skills from the owner's local pi config, copied whole (contents, not links). The Workspace DO mounts them read-only with computer's `WorkerBundle` at `/workspace/.agents/skills` (`apps/server/src/workspace/Workspace.ts`), so a write under it through the file tools or the Worker Shell fails with `EROFS` and a deploy that changes them replaces the copy. computer's sync drops a Container write under the mount (the Workspace refuses it) but leaves it on the Container, so the Container's bootstrap (`bootstrapScript` in `apps/sandbox-image/src/toolchains.ts`) bind-mounts the directory over itself read-only on each Container start: a command's write there fails with `EROFS` there too. It is best effort: a Container that cannot mount (`alchemy dev`'s, without FUSE; one running when a deploy replaces the skills) keeps an ordinary directory, where a write succeeds locally, never reaches the Workspace, and is gone at the next start; only the mount is protected, so moving `/workspace/.agents` on the Container takes it along (checked deployed: the writes fail with `EROFS`, and the mount comes back read-only after a restart). What a Workspace had at `/workspace/.agents/skills` before it was mounted (computer clears a mount's root when it first indexes it) is moved to `/workspace/.agents/skills.pre-bundle` first (`keepPriorSkills`, `apps/server/src/workspace/skills.ts`; `-2`, `-3` when that is taken). They ship inside the Workspaces Worker's upload as `?raw` string imports listed in `apps/server/src/workspace/bundled-skills.generated.ts`, so keep them to text and small. Every Workspace therefore has a `.agents/` directory at its root; `find` and `grep` from above the mount skip it, and a search of a path in the mount finds the files.

computer refuses `mkdir -p` of any path above a read-only mount, `/workspace` included, though the directory exists. `ensureDirectory` (`packages/computer-env`) makes that a no-op for the file operations and, through `GuardedFilesystem` (`apps/server/src/workspace/tracked.ts`), for the Worker Shell; a Workspace stub that does not extend `TrackedWorkspaceStub` must return a `GuardedFilesystem` as its `fs`.

To refresh, run `node scripts/sync-skills.mjs` (sources: `~/.pi/agent/skills`, then `~/.agents/skills`; `--source <dir>` overrides). It copies the skills named in `INCLUDED_SKILLS` at the top of the script, each with the upstream it comes from (`SOURCES`; the upstream's licence text is vendored in `skills/LICENSES/`, and a skill whose upstream and licence are unknown is not bundled), drops the paths in `EXCLUDED_PATHS` (including each skill's `agents/` metadata), refuses what `scripts/skills-checks.ts` forbids (binaries, files over 128 KB, a bundle over 1 MB, anything that looks like a credential or a local path), and rewrites `bundled-skills.generated.ts` and `skills/NOTICE.md`; commit all of it. `skills/` is outside oxfmt and oxlint. `bundled-skills.test.ts` fails in CI if the manifest, its `version` (computer copies the mount into a Workspace again only when it changes), the checks or the notices disagree with the directory.

The `skills` prompt section (`@cloudpid/extensions/skills`) asks the conversation's environment for them: `ComputerExecutionEnv.discoverSkills` is one call to the Workspace DO's `skills(cwd)`, which walks next to the files (`discoverSkills` in `@cloudpid/extensions/skills-discovery`, a module of its own so the Workspaces Worker does not load the harness) and reads the bundled skills from the bundle in memory, parsed once per bundle version, so a request is one RPC whatever the number of skills and only the repo's own skills are read. An environment without `discoverSkills` is walked through its file operations instead. The list is the skills in `.agents/skills` of the conversation's `cwd` and of each directory above it up to `/workspace`, nearest first (so a repo's skills beat the bundled ones of the same name; symbolic links to skill directories are followed one level), in the format local pi uses, at most 100 and each description cut to 1024 characters. Skills with `disable-model-invocation: true` are not listed, and the section says they are for the user to name.

Project instructions (`AGENTS.md`, `CLAUDE.md`) are found the same way, next to the files: `@cloudpid/extensions/agents-md` puts those of the conversation's `cwd` in the `project_context` section, frozen per context so the system prompt never changes, and wraps `read`, `edit` and `write` to add those of the touched file's directory to the result (`docs/spec.md` → _Filesystem and tools_ → _Project instructions_). Anything it adds later goes at the end of the context, never into the system prompt: a changed section breaks the provider's prompt cache.

## Infra

The alchemy stack is `infra/alchemy.run.ts`; its scripts run alchemy from `infra/`: `pnpm --filter @cloudpid/infra run dev` serves workerd on `http://localhost:1337`, and `pnpm --filter @cloudpid/infra run deploy --stage dev_$USER` deploys to Cloudflare (use `run`, since bare `pnpm deploy` is pnpm's built-in, and no `--`, which pnpm forwards literally; add `--dry-run` to only plan). It authenticates with the local alchemy profile (`alchemy profile edit --add Cloudflare`) and keeps state with `Cloudflare.state()`. A Worker is declared in its own app with `main: import.meta.url`; the stack imports and `yield*`s it. That makes it an Effect Worker, whose generated entry exports only `default` and its Effect DO classes. A Worker that must export anything else (a plain DO class, a `WorkerEntrypoint` such as `@cloudflare/computer`'s `WorkspaceServiceProxy`) is a plain async Worker instead: its entry module (`main: new URL("./worker.ts", import.meta.url).href`) holds no alchemy code, and a separate resource file declares it, as `apps/server/src/workspace/` does for `Workspaces`.

The browser Worker is a plain Worker too (`apps/browser`, resource `Browsers`): it exports the `BrowserHost` DO and `@cloudflare/codemode`'s `CodemodeRuntime` (the facet `agents/browser`'s tool keeps its runs in), has the Browser Run binding `BROWSER` (alchemy: `Cloudflare.Browser()`) and a Worker Loader `LOADER`, `workersDev: false` and no routes. The Session DOs reach it through their `BROWSER_HOST` binding, declared in `apps/server/src/worker.ts` with its `scriptName` Output. In workerd tests give miniflare the facet class as a Durable Object too (`CODEMODE_RUNTIME`, else `ctx.exports.CodemodeRuntime` is not a class) and `workerLoaders: { LOADER: {} }`.

The codemode sandbox is a plain Worker too (`apps/codemode-sandbox`, resource `CodemodeSandboxes`): it exports pi-codemode's `CodemodeSandboxDurableObject` as `CodemodeSandbox`, has `workersDev: false` and no routes (nothing reaches it but the Session DOs' `CODEMODE_SANDBOX` binding, declared in `apps/server/src/worker.ts` with its `scriptName` Output so it deploys first), and bundles QuickJS's `.wasm` as a compiled module through alchemy's own rolldown rule. In workerd tests that import it, give miniflare `modulesRules: [{ type: "CompiledWasm", include: ["**/*.wasm"] }]`.

**Container.** The Workspace DO's Container (`apps/sandbox-image/image/Dockerfile`, declared in `apps/server/src/workspace/resource.ts`) is a Docker image that every deploy and `alchemy dev` builds, so both need a running Docker with the `buildx` plugin (alchemy fails with `DockerBuildFailed` without it; with colima, `brew install docker-buildx` and point `cliPluginsExtraDirs` in `~/.docker/config.json` at `$(brew --prefix)/lib/docker/cli-plugins`). The image is `linux/amd64`, so on Apple silicon start colima with `--vz-rosetta`. `alchemy dev` runs the Container in local Docker without `/dev/fuse`, where computerd falls back to its userspace shim; the real FUSE mount exists only deployed. alchemy is patched (`patches/alchemy@2.0.0-beta.83.patch`) so that adding a Container to a Durable Object class that is already deployed works: alchemy creates the class's container application before the Worker upload that Container-enables the namespace, and Cloudflare rejects it (`Durable Object namespace is not Container-enabled`); the patch retries the create until that upload lands. When upgrading alchemy, `pnpm install` fails on the stale patch: check whether upstream fixed the ordering before porting it.

**Container Toolchains and git.** On each Container start the Workspace DO runs a bootstrap before the first command (the Environment's Toolchains written as `/workspace/mise.toml` where the Workspace has none or still has the copy written last, `mise install` from the Workspace's `mise.lock`, git's identity and credentials, pnpm's global `config.yaml` (store and virtual store on the Container's disk), then the Setup Scripts that are due (the Environment's own, then each repo's `.cloudpid/setup.sh`), then, after the install snapshot, the Start Scripts that bring up services at every start (the Environment's, then each repo's `.cloudpid/start.sh`; a service must detach; a repo's `.cloudpid/` is its own, committed, unlike the harness's `/workspace/.cloudpid`): `docs/spec.md` → _Container and Toolchains_; code in `apps/sandbox-image/src/toolchains.ts` and `apps/server/src/workspace/toolchains.ts`). `CLOUDPID_GITHUB_TOKEN` is a required deploy-time secret (`Config.Redacted`, bound to the Workspaces Worker, and to the main Worker, whose Session DOs refuse it in a variable the agent saves: `docs/spec.md` → _Agent changes_) that commands get as `GH_TOKEN`/`GITHUB_TOKEN`; `CLOUDPID_GIT_NAME` and `CLOUDPID_GIT_EMAIL` are optional and set the identity of the agent's commits (default `cloudpid` and the owner's email). Under `alchemy dev` the Container has no FUSE, so the stack sets `CONTAINER_FUSE=false` and the `ignore` list is not applied (computerd's shim exits on one). To exercise a Container end to end, deploy your own stage and give the Workspaces Worker a temporary route that runs a command through `ComputerExecutionEnv.onBackend("container")`; `kill 1` in the Container restarts it (PID 1 is the image's supervisor, which stops computerd and sends no exit report), killing computerd makes it log one (`pkill -KILL -x computerd`) (`workspace.container.output` in the Workspaces Worker's logs: `docs/spec.md` → _Exit reports_), and an old Workspace DO instance keeps its old code until it is evicted, so start a Session in a new Workspace after a redeploy. Each Workspace has its own Workspace DO (`ws:<id>`) and Container, with its own clones of its Environment's Repos, made when a Session first works in it, or ahead of it in the Environment's spare Workspace, which a new Session takes (`apps/server/src/workspace/prepare.ts` and `spare.ts`; scripts in `apps/sandbox-image/src/workspaces.ts`; `docs/spec.md` → _Spare Workspace_). The Container's size (a Cloudflare named type or the custom `cpu-1`, the default, `cpu-2`, `cpu-3`, `mem-4`, `mem-8` and `mem-12`; a stored `custom-N`, their old name, reads as `cpu-N` through `currentInstanceName`), its size limit (`maxInstance`, default `cpu-2`, which bounds the agent's `container_resize`: a one-launch size override in the Workspace DO's storage, `resize.ts`, that the idle stop forgets), idle time, extra Container-only paths (`ignore`, added to `TOOLCHAIN_IGNORE`), variables (plain, under `toolchainEnv`'s, in every command's environment; with the variables for every Environment, a Registry document, merged under them when the Registry hands the settings over), the Environment's own Setup and Start Scripts and its Toolchains (`toolchains`, a `mise.toml`; empty: the image's base ones) are per-Environment settings (`ContainerSettings`, `packages/config/src/container-settings.ts`) kept in the Registry. The Workspaces Worker cannot bind the Registry, so a Session hands them to its Workspace DO when it readies the Workspace (`updateContainerSettings`), and the main Worker hands them to a spare's with its set-up (`prepareSpare`); the DO keeps a copy (`apps/server/src/workspace/settings.ts`) and applies it at each launch (`launch.ts`) and, for the variables, scripts and Toolchains, at each bootstrap (`ToolchainBackend`'s `settings`); a disk snapshot is taken after the first successful bootstrap that installed something (a Toolchain, or a Setup Script that succeeded) and on idle stop, and restored at the next launch (`snapshots.ts`; off under `alchemy dev`). Live-checking snapshots needs a deployed stage: give the Workspaces Worker a temporary `workersDev` route that runs a command through `ComputerExecutionEnv.onBackend("container")` and can destroy the Container, since a restore and the idle stop only exist there.

**Worker Shell and `bash` routing.** The Worker Shell's `jq` is an optional computer module (`@cloudflare/computer/shell/jq`) and its `git` needs `createGitClient()`, which loads `@platformatic/vfs`, an optional peer of `@cloudflare/computer`; the Workspace DO passes both (`Workspace.ts`). The Worker Shell itself needs `just-bash`, an optional peer of computer since 0.6.0. Every package that depends on `@cloudflare/computer` (`apps/server`, `packages/computer-env`) lists `@platformatic/vfs` and `just-bash` too, so pnpm resolves one instance of computer (two give mismatched types). `bash` without a `backend` is routed by `packages/extensions/src/bash-routing.ts`: the Container is the costly backend, so a program on neither list is asked of the Worker Shell (`command -v`) before going to the Container, and a command that writes no file reruns on the Container when the Worker Shell says it cannot run it (`docs/spec.md` → _Backends_). When computer or its shell changes what the Worker Shell runs, update `WORKER_SHELL_COMMANDS`, `WORKER_SHELL_BUILTINS`, `CONTAINER_PROGRAMS` and the git subcommands there (`apps/server/src/workspace/bash.workerd.test.ts` runs the lists through the real shell, and checks each git form against real git's output). Only a few read-only `git` forms run on the Worker Shell, because its git (isomorphic-git) is not always git's; anything that writes goes to the Container.

**Container-only paths** (ADR-0018). Every path outside `/workspace`, and inside it every path the launch's patterns name (`TOOLCHAIN_IGNORE`, then the Environment's `ignore`, then `!/.cloudpid` and `!/.cloudpid/**` from `withHarnessKept`), exists only on the Container. The Workspace DO decides with `isContainerOnly` (`packages/computer-env/src/container-paths.ts`). A model tool's request carries `reachContainer` (the Session's `env` and file search set it; `lookupEnv` and everything else must not, so they never start the Container), and the DO then runs the operation as a script on the Container (`ContainerFiles`, `container-files.ts`), moving bytes through stage files in `/workspace/.cloudpid/tmp`. The harness's own files live in `/workspace/.cloudpid`: `tmp/` (temp files, `bash` spills, clone staging) and `uploads/` (Attachments). A `bash` command whose path words name a Container-only path is routed to the Container by `bash-routing.ts`, through `ComputerExecutionEnv.containerOnly`. The scripts are tested in plain bash in `container-files.test.ts`; on a deployed stage they run through computerd's FUSE mount, which the tests do not have.

**Model proxy secrets.** Every deploy and `alchemy dev` needs `MODEL_PROXY_URL`, `MODEL_PROXY_API_KEY` and `CLOUDPID_GITHUB_TOKEN` in the environment: the Session DO and the Workspaces Worker read them with `Config.Redacted`, which binds them to the Worker as secrets (see _CI_ for where they live). `alchemy dev --stage dev_$USER` replaces that stage's deployed Worker with the local one and deletes its Access app; redeploy the stage afterwards.

**Secrets key.** Every deploy and `alchemy dev` also needs `SECRETS_ENCRYPTION_KEY` (at least 32 characters; `openssl rand -base64 32`), the master key the Session DO encrypts the owner's Secrets under, the Registry DO the Secrets kept for Environments and the Workspace DO its copy of them, read and bound the same way (to the main Worker and the Workspaces Worker). CI takes it from the `production` environment's secrets (set by hand: `openssl rand -base64 32 | gh secret set SECRETS_ENCRYPTION_KEY --env production`); locally, keep it in `~/.config/cloudpid/dev.env`. Changing it drops the Secrets held at that moment (they expire within 15 minutes anyway; the agent asks again); messages already scrubbed of a value stay scrubbed, as their index does not depend on the key. It also leaves every Secret kept for an Environment unopenable (the Registry logs each by name and leaves it out, so the owner sets it again), and each Workspace takes no snapshot and makes no Build until a readying hands its copy again. A malformed key fails only what needs it: Environments with no kept Secret work as before, and those with some get none in their Workspaces' set-up (`secretsUnavailable`), no new Build, and Secrets calls that fail saying why.

**VAPID keys.** Every deploy and `alchemy dev` also needs `VAPID_PUBLIC_KEY` (base64url uncompressed P-256 point), `VAPID_PRIVATE_KEY` (base64url 32-byte scalar) and `VAPID_SUBJECT` (a `mailto:` URL), the identity Web Push messages are signed with (RFC 8292): the Registry DO reads them with `Config.Redacted` (`apps/server/src/push/config.ts`), so they are bound as Worker secrets. CI takes them from the `production` environment's secrets; locally, keep them in `~/.config/cloudpid/dev.env`. To make a pair: `node -e "const {publicKey,privateKey}=require('node:crypto').generateKeyPairSync('ec',{namedCurve:'P-256'});const j=privateKey.export({format:'jwk'});console.log(Buffer.concat([Buffer.from([4]),Buffer.from(j.x,'base64url'),Buffer.from(j.y,'base64url')]).toString('base64url'),j.d)"` prints the public key, then the private one. The public key reaches the web app through `getPush`; the private key never leaves the Worker. The layer checks the three at startup (subject, key lengths, and that the two are a pair), so a malformed secret fails a deploy or `alchemy dev` at once. Rotating the pair strands every device's subscription (a push service refuses a subscription made with another key, so each push is logged as a failure); a device replaces its own the next time the app is opened, if it still allows notifications.

**Web app.** `apps/web` (Vite, React 19, Tailwind v4) is built by the Server's deploy (an alchemy `Command.Build` in `apps/server/src/worker.ts`, which runs `pnpm run build` in `apps/web`) and served by the main Worker as static assets: files are answered by the asset layer, a navigation to `/sessions/:id` gets `index.html`, and `/rpc` and the Session socket reach the Worker. Its state lives in Effect Atom over one runtime (`apps/web/src/runtime.ts`; ADR-0011). The app is an installable PWA: `apps/web/public/` holds the manifest (linked with `crossorigin="use-credentials"`, since Access guards it), the icons, and `sw.js`, the service worker that shows pushes and opens the Session on a tap (it caches nothing). For UI work, run `pnpm --filter @cloudpid/web run dev` next to `alchemy dev`: Vite proxies `/rpc` and the Session socket to `localhost:1337`. On a cloudpid Container, start it with `VITE_POLL=1`: `/workspace` is a FUSE mount whose changes made through the Workspace raise no inotify events, so without polling Vite keeps serving a file's old version. `@pierre/diffs` is pinned to an exact version and patched (`patches/@pierre__diffs@1.6.1.patch`: a `FileDiff` re-attached while its first highlight was pending stayed empty, [pierrecomputer/pierre#1233](https://github.com/pierrecomputer/pierre/issues/1233), fixed upstream by [#1219](https://github.com/pierrecomputer/pierre/pull/1219) but not released yet; `docs/spec.md` → _Diffs and review_); when upgrading it, `pnpm install` fails on the stale patch: drop it once the release has #1219, else port it.
**Search keys.** `EXA_API_KEY` and `PARALLEL_API_KEY` are optional deploy-time secrets for `web_search`: the web extension reads them with `Config.Redacted` (`WebConfigLive`), so a key set in the deploying environment is bound to the Worker as a secret. With neither set, `web_search` answers that it is not configured (`web_fetch` needs no key). CI takes both from the `production` environment's secrets; locally, keep them in `~/.config/cloudpid/dev.env`. `WEB_TOOLS_LIVE=1 pnpm --filter @cloudpid/extensions exec vitest run src/web/live.test.ts` checks the tools against the real network and providers.

**Container analytics.** `CLOUDPID_ANALYTICS_TOKEN` is an optional deploy-time secret: an API token with Account Analytics Read that the Workspace DO reads its Containers' usage with, for the cost in the Session header (`docs/spec.md` → _Container cost_). The Workspaces Worker gets it as a secret, with the deploy's account as `CLOUDFLARE_ACCOUNT_ID` (`apps/server/src/workspace/resource.ts`); unset or empty, the cost is estimated. `infra/github.ts` makes one token per GitHub environment (`cloudpid-container-analytics`, `cloudpid-container-analytics-preview`) and writes it into `production` and `preview`, so it is not set by hand there; rerun `ci:setup` after pulling the change. For local deploys, mint one in the dashboard and keep it in `~/.config/cloudpid/dev.env`.

**Telemetry.** Every Worker of the stack sets `observability: WORKER_OBSERVABILITY` (`@cloudpid/telemetry`: logs, invocation logs and traces), which rides on the script upload, so the CI token's Workers Scripts Write covers it and no permission was added. The Session DO makes custom spans through `tracing` from `cloudflare:workers` (compatibility date 2026-07-28 or later; the stack uses 2026-08-31), imported when an object is built, since the stack imports `Session.ts` under Node. Read traces in the dashboard (Workers → Observability → Traces) or through the telemetry query API (`POST /accounts/{id}/workers/observability/telemetry/query`, `view: "traces"`), whose `traces` view lists summaries only: span names and attributes are in the dashboard. To see what a span is made of while debugging, log from inside it: a log line carries the trace and span ID it ran under. The spend limit and usage are in `apps/server/src/session/spend.ts`.

**Images.** The Server Worker has a Cloudflare Images binding, `IMAGES` (`Cloudflare.Images.Images`, declared in `apps/server/src/worker.ts`), which the Session DOs' `read` scales and re-encodes images with (`docs/spec.md` → _Filesystem and tools_). It has no backing resource and rides on the script upload, which Workers Scripts Write covers (the upload API's accepted permission), so the CI tokens need nothing more. Every account is on the Images Free plan by default: 5,000 unique transformations a month, after which the binding answers error 9422 and `read` leaves the image out with a note. `alchemy dev` emulates the binding locally with sharp (size and format, not quality); in workerd tests give miniflare `images: { binding: "IMAGES" }`, as the `workerd-session` project does.

**Stages and Access.** `apps/server/src/deployment.ts` decides per stage where the Worker is served and who may reach it: `prod` is served on `https://pi.ianpascoe.dev` (workers.dev off), every other stage on `workers.dev`, and all of them sit behind an Access application that allows only the owner's email. The Access team domain is `spirit-led-software`. `alchemy dev` runs locally and has no Access.

**CI.** `.github/workflows/ci.yml` runs `pnpm check` on every PR and push to `main` (`check` and `preview` set up through `.github/actions/setup`: pnpm, Node, the pnpm store cached by lockfile with a fallback to the newest store and pruned before it is saved, then the install; `preview`, which holds deploy credentials, only reads the cache, and the `prod` deploy uses none; `check` also caches turbo's `.turbo/cache`, pruned to the entries its tasks used) and, on push to `main`, deploys stage `prod` in the GitHub environment `production` (deployments from `main` only). Each pull request from a branch of this repository (not a fork, which gets no secrets) also gets a preview: once `check` passes, the `preview` job deploys stage `pr-<number>` in the GitHub environment `preview` (any branch), on `workers.dev` behind Access like every non-`prod` stage, and `infra/alchemy.run.ts` posts its URL as one PR comment (`GitHub.Comment`, with the workflow's `GITHUB_TOKEN`) that each push updates; closing or merging the PR runs `alchemy destroy --stage pr-<number>` from the PR's head commit. Deploys and the destroy of one PR never overlap or cancel midway (job concurrency `preview-<number>`), and a destroy evaluates the stack, so it needs the same variables as a deploy. Alchemy records the Worker's absolute `main` path in state, but a deploy from another checkout path plans no change, so CI and local deploys can alternate. CI's credentials are code: `infra/github.ts` (stack `cloudpid-github`, stage `ci`) creates the scoped API token `cloudpid-ci-deploy` (Workers Scripts, Workers Containers, Secrets Store for alchemy's state store, Access apps and policies, and zone/DNS/routes on `ianpascoe.dev`) and writes `CLOUDFLARE_API_TOKEN` (secret) and `CLOUDFLARE_ACCOUNT_ID`, `MODEL_PROXY_URL` (variables) into `production`; it also creates the `preview` environment and its token `cloudpid-ci-preview` (the same account permissions, no zone ones) with the same secret and variables. Any branch can use `preview`'s token, and Workers Scripts Write covers every Worker on the account, `prod`'s included, so whoever can push a branch can reach `prod`. Deploy it from a workstation with the `admin` alchemy profile (the Cloudflare Global API Key and `gh`): `pnpm --filter @cloudpid/infra run ci:setup`; rerun it to change permissions. To rotate the token, run `pnpm --filter @cloudpid/infra exec alchemy destroy --config github.ts --stage ci --profile admin`, then `ci:setup` again: the `production` environment is retained on destroy, so the hand-set `MODEL_PROXY_API_KEY` and the `main` branch policy survive, and only the token, its secret and the variables are replaced. Set `MODEL_PROXY_API_KEY` by hand (the stack does not manage it): a Commissary API key for `https://api.ai.ianpascoe.dev`, which is outside Access, so a service token cannot authenticate to it: `gh secret set MODEL_PROXY_API_KEY --env production`. `CLOUDPID_GITHUB_TOKEN` is set by hand the same way (a GitHub token that can clone, push and open PRs on the repos the agent works on) and the deploy step passes it on. `preview` needs its own copy of every hand-set secret (`MODEL_PROXY_API_KEY`, `SECRETS_ENCRYPTION_KEY`, `CLOUDPID_GITHUB_TOKEN`, `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, `EXA_API_KEY`, `PARALLEL_API_KEY`): set them with `gh secret set <NAME> --env preview`, with an encryption key and VAPID pair of its own (the dev ones from `~/.config/cloudpid/dev.env` will do), since the previews share them. A preview whose secret is missing fails its deploy and its destroy. For local deploys, keep `MODEL_PROXY_URL` and `MODEL_PROXY_API_KEY` in `~/.config/cloudpid/dev.env` (outside the repo) and load them with `set -a; . ~/.config/cloudpid/dev.env; set +a`. `.env*` files are gitignored.

## Git hooks

Husky hooks run on every commit and push:

- **pre-commit**: lint-staged runs `oxlint --fix` and `oxfmt` on staged files.
- **commit-msg**: commitlint requires [Conventional Commits](https://www.conventionalcommits.org/) (`feat: …`, `fix: …`, `chore: …`).
- **pre-push**: `pnpm run typecheck`, `pnpm run lint` (both through Turborepo, cached), and `pnpm run format:check`. Tests run in CI; run `pnpm run check` for everything locally.
- **post-merge / post-checkout**: `pnpm install` when `pnpm-lock.yaml` changed, otherwise a reference-repository sync.
