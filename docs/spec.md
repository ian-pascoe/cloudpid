# cloudpid: Pi on Cloudflare

A personal, always-on coding agent that recreates the local pi harness on Cloudflare. pi-durable runs the agent, `@cloudflare/computer` holds the files and runs commands, alchemy provisions everything, and Effect is the application language.

This spec records the design settled on 2026-10-20. Terms follow [`GLOSSARY.md`](../GLOSSARY.md); the hard-to-reverse choices have ADRs in [`docs/adr/`](adr/).

## Scope

- **Single user**, behind Cloudflare Access. There are no tenants, quotas, or per-user isolation.
- **v1 clients:** an HTTP and WebSocket API and a web UI. A terminal client and GitHub, Slack, or cron triggers come later.
- **Lean on existing packages.** Prefer Earendil (`pi-durable`, `pi-ai`, `pi-codemode`, `pi-mcp`, `pi-telemetry`) and Cloudflare (`@cloudflare/computer`, `agents/browser`) building blocks over writing our own.

## Architecture

```
Browser (web UI, PWA) ──Access──▶ Main Worker ──WS─────▶ Session DO (per Session)
                                       │                    ├─ pi-durable Harness (SQLite, prefix pi_)
                                       │                    ├─ browser tool ─▶ Browser Worker (BrowserHost DO per Session → Browser Run)
                                       │                    └─ RemoteCodemodeSandbox ─▶ Codemode Sandbox Worker (DO per Session)
                                       ├──────────────▶ Registry DO (singleton)
                                       └──────────────▶ Workspace DO (per Workspace)
                                                            ├─ computer Workspace (SQLite VFS)
                                                            ├─ Worker Shell backend (just-bash, Worker Loader)
                                                            └─ Container backend ─▶ Container (computerd + mise)
```

### Durable Objects

| Object                  | Key                           | Holds                                                                                                                             |
| ----------------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **Session DO**          | UUIDv7                        | One pi-durable Harness: the root conversation, its subagent conversations, tasks, documents, usage. It is bound to one Workspace. |
| **Workspace DO**        | `ws:<id>`, the Workspace's id | One `@cloudflare/computer` Workspace and its Container: one Workspace's clones. Its Sessions share it.                            |
| **Registry DO**         | singleton                     | Environments, Workspaces and Session listings (title, timestamps, status), settings overrides, push subscriptions.                |
| **Codemode sandbox DO** | Session DO id                 | QuickJS script execution. It lives in a separately deployed Worker so scripts run in another isolate.                             |
| **Browser host DO**     | Session DO id                 | The Session's one Browser Run browser (`agents/browser`) and the runs of the model's CDP code. It lives in the `Browsers` Worker. |

The Harness and the Workspace live in separate objects ([ADR-0001](adr/0001-session-and-workspace-durable-objects.md)). An Environment's Build is made by a Workspace DO of its own, `build:<environment id>` (`buildObjectName`; see _Container and Toolchains_ → _Builds_). The Workspace DO is hosted by its own plain Worker, `Workspaces` (bound as `WORKSPACES`): the Worker Shell reaches the DO through a `WorkspaceServiceProxy` entrypoint the hosting Worker must export (`ctx.exports`), and an alchemy Effect Worker's generated entry exports only `default` and its Effect DO classes. Session DOs bind it across scripts with `Cloudflare.DurableObject("Workspace", { scriptName: Workspaces.workerName })`, the Output and not a literal, so `Workspaces` deploys first; they call it through the raw `DurableObjectNamespace` stub, which `getWorkspace()` and `ComputerExecutionEnv` need. The two Workers deploy separately, so `ComputerExecutionEnv`'s requests to the DO only ever gain operations, never change existing ones.

### Session host

The Session DO opens the Harness with `openDurableObjectSqliteStorage(ctx.storage, { prefix: "pi_" })` and wakes itself from its alarm. It follows the pattern in pi-durable's `test-workers/worker.ts`, not Cloudflare's `PiHarness` ([ADR-0002](adr/0002-own-session-host.md)).

- Use `HarnessOptions.onWake` and `Harness.wake()` to arm the alarm at the earliest sleep, or as a heartbeat while work is active. They are unreleased on pi main as of 2026-10-20. Until they ship, arm a 60 s heartbeat alarm while any task is live.
- Arm the alarm before admitting work. Call `resume()` from the constructor and the alarm.
- Long model streams are bound by the platform's wall-time limits. pi-durable resumes interrupted work.

### Effect boundary

Effect is the language everywhere except pi-durable's own core ([ADR-0003](adr/0003-effect-around-pi-durable.md)).

- Each DO builds its Layers once and keeps a `ManagedRuntime`. Services (`Context.Service`) include `Harness`, `WorkspaceClient`, `Models`, `Settings`, `Secrets`, `Registry`, and `Telemetry`.
- `packages/effect-durable` provides `defineEffectTool` (Effect `Schema` parameters compiled to TypeBox/JSON Schema), `effectHook`, `effectSection`, and `effectTask`. Chord `Context` cancellation becomes fiber interruption, and typed failures become tool error results (`effectTask`: the task's `failed` outcome; a defect faults it, as a native throw does). A task's phases run as Effects but still commit their checkpoints through `runtime`.
- Harness internals, commits, documents, and task phases stay native. Effect reaches them through thin facades (`Effect.tryPromise`), never a parallel scheduler.

### Models

- Requests go to the existing proxy `api.ai.ianpascoe.dev` with a Commissary API key, sent as each provider's native API key (`x-api-key` for Anthropic). The proxy is Commissary's API host, which sits outside Cloudflare Access and rejects service tokens. Model IDs match `~/.pi/agent/models.json`.
- Default `anthropic/claude-opus-5-5` at `high` thinking.
- Roles: `small` haiku-5-5, `medium` sonnet-5-5, `large` opus-5-5, `xlarge` fable-5-1, with the hints from `~/.pi/agent/settings.json`.

### Settings

- A typed Effect `Schema` with defaults in `packages/config`: every field has a decoding default, so decoding the overrides gives the resolved settings, and the schema's `Encoded` side is the overrides' shape (a deep partial that rejects unknown keys). Invalid overrides fail with one readable line per problem.
- Runtime overrides live in a Registry DO document (the `documents` table, named `settings`), editable in the UI at `/settings` over `getSettings`/`updateSettings`. The document is added by a Registry migration (the `documents` table). A write is strict and keeps only what differs from the defaults, so a setting left alone follows later default changes; a read is lenient: saved overrides that no longer resolve (a model a release dropped) are left out one by one and listed in `problem`, and the rest still apply.
- Each Session reads the overrides from the Registry when a client connects and before it admits input (outside the alarm lock, and not again for 30 s after a failed read), and keeps the last read in its own storage, so a changed default applies to the next request of new and idle Sessions without a redeploy and is what a client first sees, and a Registry that is down never stops one. A default changed during a Run reaches the Run from its next provider request, as a pick does. The Harness's `compaction` is a getter over that copy. The default model and thinking level are written to the root conversation's agent before each request unless the Session picked its own (see `configure`); a pick of a model the settings no longer accept is ignored.
- They cover models, roles, thinking level, compaction, the offered tools (`tools.offered`, see _Tool discovery_), the spend limit (`spendLimit.perSession`, US dollars, off by default; see _Operations_ → Telemetry), whether a move in the Session tree asks about a branch summary (`branchSummary.skipPrompt`, off by default; see _Client and protocol_ → _Session tree_), and extension options. A Workspace's Container size, size limit, idle time, extra Container-only paths, variables and Setup and Start Scripts are not in this document: they are its Environment's settings, kept in the Registry with the Environment (see _Container and Toolchains_ → _Container settings_).

## Workspace and execution

[ADR-0016](adr/0016-environments-and-a-container-per-workspace.md) replaced the Machines of [ADR-0015](adr/0015-workspaces-are-worktrees-on-a-shared-machine.md). An **Environment** (GLOSSARY.md) is what the owner sets up once: a name, its Repos and its Container settings. A **Workspace** is what Sessions work in: a Workspace DO of its own (`ws:<id>`; the DO class and the `WORKSPACES` binding keep their names), its own Container, and its own full clone of each of its Environment's Repos, all on one branch. A new Session gets a new Workspace unless it is started in one that exists. Where this spec says a Workspace's file tree, Container, settings or snapshot, it means that one Workspace's. Machines, their worktrees and their Sessions were not carried over: the Registry's migration 11 reset them (see _Client and protocol_ → Registry migrations).

### Filesystem and tools

- The workspace root is `/workspace`, with one directory per Repo of the Workspace: its clone. A Session's `cwd` defaults to its Workspace's directory (`workspaceDirectory`: `/workspace/<repo>` when the Workspace has exactly one Repo, else `/workspace`). `/workspace/.cloudpid/uploads/<session-id>/` holds the Session's Attachments (see _Client and protocol_ → Attachments); like `.agents`, it is a hidden directory beside the repos.
- `ComputerExecutionEnv` (`packages/computer-env`) implements pi-durable's `ExecutionEnv` over the Workspace DO's RPC stub, and must pass `registerEnvConformance`. Its `listFiles` walks one directory at a time (one `fs.find` of the directory's own entries each) and filters as it goes, so a directory it skips (an excluded name, what git ignores, `.git`) is never walked; a directory holding `.git` below the listed one is a work tree of its own, whose ignore rules apply from there in place of those above it, also when the listed directory is in no work tree.
- `write` and `edit` are pi-durable's own tools, `read` is pi-durable's wrapped so that every image it returns fits the conversation (see _Images `read` returns_ below), and `bash` is pi-durable's tool with one more argument, `backend` (`@cloudpid/extensions/coding-tools`, see _Backends_). `ls`, `find`, and `grep` are thin tools over the Workspace DO's search operations (`readdir`, `find`, `grep` in `@cloudpid/computer-env`'s host, over computer's `fs.readdir`, `fs.find`, and `fs.grep`; `@cloudpid/extensions/files`), so on the Workspace's own paths they never start the container. Their parameters and output follow local pi's; `find` and `grep` skip `node_modules` and `.git` below the searched path, since the Workspace's file system has no `.gitignore` handling, and a search from above `/workspace/.agents/skills` or `/workspace/.cloudpid` skips them too.
- **Container-only paths** ([ADR-0018](adr/0018-file-tools-reach-container-only-paths-through-the-container.md), GLOSSARY.md): a model tool's file operation on a path only the Container has (outside `/workspace`, or matching the launch's Container-only patterns inside it) runs on the Container, starting it if it is stopped. The Session's `env` and file search ask for it (`reachContainer` on each `EnvRequest`; `lookupEnv`, the composer, Skill and Prompt template discovery, Attachments and the readying never do). The Workspace DO decides by pattern alone, never by whether the file exists (`isContainerOnly`, `container-paths.ts`), with the patterns of the launch that runs now or of the next one (`ContainerLaunch.ignore`); every launch's list ends with `!/.cloudpid` and `!/.cloudpid/**` (`withHarnessKept`), so the harness's own directory is always synced. computer reaches a Container only through commands, so each operation is a bash script the Workspace DO runs there as any command (`ContainerFiles`, `container-files.ts`; 5 minutes at most), its failures named as the Container's (`… (on the Container)`). Bytes cross through stage files in `/workspace/.cloudpid/tmp` (`xfer-<uuid>`), which computer pushes before the command and pulls after it. `read` (and a binary reader) copies the whole file over when it opens it and reads the copy as the Workspace DO's own reader, since pi-durable's line scan needs every byte; a file over 32 MB (`MAX_CONTAINER_FILE_BYTES`) is refused with a pointer to `bash`. `edit`'s read records the file's SHA-256, and the write after it replaces the file (a temp file beside it with its mode, moved over it) only while it still has that hash, else fails with "read it again". `find` and `grep` rooted in a Container-only path run `find` (its `-path` as a superset of the glob, filtered exactly in the Workspace DO, at most 20,000 lines) and `rg --json --no-ignore --hidden`. `ls` of a synced directory adds the Container-only entries the Container has there, marked `(container-only)`, only while it runs: a listing does not start it. Operations the tools do not use on such paths (rename, remove, truncate, watch, listings for the composer) fail as `not_supported`, pointing at `bash`. computer's `createPiTools` is not used ([ADR-0008](adr/0008-pi-durable-tools-over-computer-tools.md)). The coding tools' `coding_tools` prompt section (fixed text, one line per tool the request offers) tells the model to read files with `read` rather than `cat`/`sed -n` in `bash`, to change them with `edit`/`write` rather than python, node or `sed -i` scripts, to search with `grep`/`find`/`ls`, and to leave `bash`'s `backend` unset so the Container starts only for what needs it.
  - **Images `read` returns** (`@cloudpid/extensions/images`, [#91](https://github.com/ian-pascoe/cloudpid/issues/91)). A tool result is one conversation entry, one row of the Session DO's SQLite, which Cloudflare caps at 2 MB; a write over it fails the commit and so the Session. So every image `read` returns is at most 750,000 base64 characters (`MAX_IMAGE_CHARACTERS`, about 560 KB, the bound the browser's screenshots keep too), or the model's own `inputLimits.images.resize.maxBytes` when smaller; its width and height stay the model's (2000 × 2000 by default). The Session gives pi-durable's `read` an image processor over the Server Worker's Cloudflare Images binding (`IMAGES`), not Photon, whose WebAssembly memory would grow in the Session DO's 128 MB isolate and never shrink. `read` offers PNG, JPEG, GIF and WebP, the formats every provider takes inline and the binding takes as input; pi-durable's `read` also finds BMP, which the binding does not take, so a BMP is left out with a note to convert it to PNG first. An image that already fits passes through untouched, with no call to the binding: its size comes from its header (PNG's IHDR, GIF's screen, WebP's VP8/VP8L/VP8X chunk, JPEG's SOF segment; ported from pi-durable, `NOTICE.md`), and only an image whose header cannot be read is measured with the binding's `info`, so an outage or a used-up quota never drops an image that fits. Otherwise the binding scales it down to the model's width and height and re-encodes it (JPEG stays JPEG, anything else becomes WebP, which keeps transparency), at quality 80, then 60 when a little over (at least 60% of the output fitting), then smaller, both sides shrinking by the square root of the share that fits with a 10% margin and at least a quarter at a time, at most 6 outputs per image (`MAX_IMAGE_ATTEMPTS`), from one copy of the file's bytes. Images bills each unique transformation (a source and its size: format and quality do not count; `info` is free; 5,000 a month on the Free plan, after which it answers error 9422). The result says what was done: pi-durable's notes say it was converted or resized, with the factor that maps coordinates back; one only re-encoded at its size and format says "Re-encoded at quality 60 to fit…", and an animated GIF or WebP made a still (the output's `anim: false`) says only its first frame is shown. An image that cannot be made to fit, that the binding cannot decode, or that the binding refuses (quota, outage) is left out: the result is an error whose message names the image and why, and the Session goes on. pi-durable reads an image whole into the Session DO before preparing it, so an image file over 20 MB (`MAX_IMAGE_FILE_BYTES`, the Images binding's input limit) is refused before any of it is read, with a note to read a smaller copy. `alchemy dev` and the workerd tests use miniflare's local emulation of the binding (sharp, which honours the size and format but not the quality); the workerd test reads a 3 MB PNG of noise through a Session and checks that the stored image is within the bound and the Session answers on.
  - **Images of one tool result.** The bound is per image, but one result can carry several: a `codemode` script can `image()` many (pi-codemode allows 16 Mi characters of output; a script gets no images from a schema-less tool such as `read`, but can build its own), and a browser run can take several screenshots. So every tool result's images, a call's own and a nested one's, are held to 1,500,000 base64 characters in all (`MAX_RESULT_IMAGE_CHARACTERS`, two images at the bound, leaving room for the result's text and details): they are kept in order until the next would go over, and that one and every image after it become a note saying it was left out and why (`ResultImages`, an `afterTool` hook, which runs before pi-durable stores a result entry or a nested call's result). Code mode stores a script's result in its run's document before the hooks run, so the Session's sandbox holds the script's output to the same budget first (`remoteSandbox`, `apps/server/src/session/codemode.ts`).
- A Session is bound to one Workspace, recorded in the Registry with the Workspace's Environment when the Session is created and never changed. The Session DO asks the Registry for it once and keeps it (`workspace-placement` in its key-value storage); `HarnessOptions.env` builds a `ComputerExecutionEnv` on that Workspace's DO (`workspaceObjectName`: `ws:<id>`) for each call, in the conversation's own `cwd`, else the Workspace's directory. A Session the Registry does not list works at the root of `ws:unlisted`, which is never readied, and is asked about again. A Repo's directory is a name (`REPO_NAME` in `packages/protocol`: letters, digits, `.`, `_`, `-`, never leading with a dot or dash), so a Workspace's directory cannot be a path.
- **Environments from the UI:** the Environments page (`/environments`) lists the Environments (`listEnvironments`), each as a card with its Repos and its Workspaces. An Environment has a fixed id (`EnvironmentId`: `default`, or eight hex digits for one the owner makes) and a **name**, 1 to 80 characters after trimming, unique among Environments whatever the case (the Registry compares names folded with `toLowerCase`, as the web app does; a `COLLATE NOCASE` unique index backs it for ASCII), which can be changed (`renameEnvironment`). `default` (named Default, with no Repos) is made by the migration and cannot be deleted, so a new Session always has an Environment to start in. `createEnvironment` makes one with a name and no Repos. A card's ⋯ menu has _Edit…_ (a dialog with the name, the Container's size, idle time and extra Container-only paths, and the Environment's variables (a `NAME=value` line each, checked as they are typed), Setup Script and Start Script: `getEnvironmentSettings`/`updateEnvironmentSettings`; it says they apply at a Workspace's next Container start, that the variables are plain, and that a service a Start Script starts must detach) and _Delete…_ (`deleteEnvironment`; not offered for `default`, which the Registry also refuses). Deleting asks the owner to type the name, then removes each of the Environment's Workspaces as _Remove_ does, then its spare Workspace (its record, then its Workspace DO: see _Spare Workspace_), then its Build object, then its record and the Secrets kept for it, which the Registry deletes only while no Workspace, spare or not, is made from it: one made meanwhile is removed the same way and the sweep runs again (three rounds at most); a failure partway leaves what is not yet removed listed, to try again. Once the record is gone the Build object is wiped once more, since a Build upkeep that asked it for a Build meanwhile made it anew; an upkeep that asks a spare to prepare or a Build object for a Build after that finds the record gone and wipes the object again itself. Each Workspace row shows its branch and has _New session here_, _Restart container…_ and _Remove…_. **Remove** (`removeWorkspace`) asks the owner to type the branch, then deletes every Session bound to the Workspace, archived ones too, each as `deleteSession` does, then the Workspace DO (`destroy`: its Container, its files with what was not committed or pushed, its settings and snapshot record; the saved disk itself expires on its own), then its record, which the Registry deletes only while no Session is bound to it: a Session started meanwhile is deleted the same way and the sweep runs again (three rounds at most). The branches pushed from it stay on the remotes. **Restart container** (GLOSSARY.md → Container restart) asks for a confirm, then the Workspace DO forgets its Snapshot and stops its Container if it runs (`restartContainer`): the files and Sessions stay, commands running in the Container end, and the next command launches a Container from the Environment's Build when there is a usable one, else from the image, which installs the Toolchains, runs the Setup Scripts and is snapshotted again; what only the Container's disk held (its Container-only paths: dependency directories, build output, caches) is gone. A Workspace the Registry does not list is refused by both. **Secrets** (see _Agent capabilities_ → _Secrets_): each card has a _Secrets_ section, and a section above the cards keeps those for every Environment. Each lists its Secrets by name, with whether each reaches the Build (a switch: `setEnvironmentSecretBuild`), _Replace_ (which puts the name in the form, for the value to be typed again) and a delete that asks for a confirm (`deleteEnvironmentSecret`); a card also names the Secrets it gets from every Environment. The form takes a name and a value of one or more lines, masked where the browser can (`setEnvironmentSecret`; a new Secret's build flag is in the form, and a name the section keeps replaces that value, keeping its flag), checks both as they are typed, and empties once the Registry has the value. A value is never shown again. **Agent changes** (see _Agent capabilities_ → _Agent changes_): each card lists what the agent changed in the Environment, newest first (`listAgentChanges`, asked again every few seconds while the page is visible), each with the setting, its value before and after in full, who made it and when (with a link to the Session that made it while it is listed), the agent's reason, and _Revert_ (`revertAgentChange`) while it is the agent's and not reverted yet; a refused revert says what the field is now.
- **Repos from the UI:** an Environment's card lists its Repos and adds one (`addRepo`) from an address: `parseRepoSource` (`packages/protocol`, which the UI uses as the owner types) accepts `owner/repo` (GitHub) or an `https` URL of a dotted, non-numeric host whose path is plain segments, and refuses credentials, ports, queries, fragments, escapes, `..`, other schemes and private-looking hosts. The directory defaults to the repo's name, and the form has an optional field to name it (`RepoName`'s rule, checked as it is typed); one another Repo of the Environment has is refused, the refusal shows under the form, and the owner names this one. Each Repo row has _Remove_ (`removeRepo`). Both change only the Environment's record, and after the answer its spare Workspace, which no longer has the Environment's Repos and is made again (see _Spare Workspace_): nothing is cloned or deleted in a Workspace a Session has. A Workspace takes the Environment's Repos (name and address) when it is made and keeps them, so a Repo added later reaches new Workspaces only, and one removed stays in the Workspaces that have it.
- **Workspaces** ([ADR-0016](adr/0016-environments-and-a-container-per-workspace.md)): `createSession` with `workspace: "new"` (the default) takes the Environment's spare Workspace when it has a current one (see _Spare Workspace_, below), or else registers a Workspace with the Session, in one transaction: an id of eight hex digits (`WorkspaceId`); its Environment (`environment`, `default` when none is named; one that does not exist is refused) and that Environment's Repos then; its branch, `cloudpid/<id>` or one the owner names (`branch`, a name git takes: `BranchName`, other than `cloudpid/spare`); and the branch it starts from (`base`, else each Repo's default branch). A branch another Workspace of the Environment is on is refused, naming that Workspace, so the owner starts the Session in it instead. `workspace: <id>` starts a Session in one that exists, which brings its Environment (naming another is refused, as are `branch` and `base`). Deleting a Session leaves its Workspace and what the Session did in it, until the owner removes the Workspace; archiving leaves it too. The clones are not made when the Workspace is: the Session DO readies its Workspace when the Session first uses its files or environment (`readyPlacement`, `apps/server/src/session/workspace.ts`),. Readying (`prepareWorkspace`, `apps/server/src/workspace/prepare.ts`) asks the Registry for the Workspace's set-up (`getWorkspaceSetup`: its Repos, branch and base, and its Environment's Container settings), hands the settings to the Workspace DO (`updateContainerSettings`) when they differ from those it holds (the Workspaces Worker cannot bind the Registry), then asks the Workspace's files whether each Repo's `/workspace/<repo>/.git` is there, without the Container. For the Repos that lack one it runs `prepareWorkspaceScript` (`@cloudpid/sandbox-image/workspaces`) on the Container under the Workspace's lock (`flock`), 15 minutes at most: a full clone of each into `/workspace/.cloudpid/tmp/clone-<repo>` (`GIT_ALLOW_PROTOCOL=https`, with git's hooks off and `SKIP_REFERENCE_REPOS=1`, so a Repo's own checkout hooks do not run before its Setup Script does), on the Workspace's branch: tracked from `origin` when the remote has it, else made from `origin/<base>` or the remote's default branch, else an orphan branch in an empty repo; then it is moved into place and runs `mise install` if it declares Toolchains. A Repo that cannot be cloned is reported with git's output, and the others are still made. Each new clone then has its Setup Script run if it is due (`repoSetupScript`; one that fails is only logged, and due again at the next Container start), then its Start Script if it has one (`repoStartScript`), since the Container already runs and its bootstrap did not see the clone: the clone script leaves a flag for each clone it made in `/tmp/cloudpid-start-due/workspace/`, which the run takes under the clone's lock, so of two Sessions that made it at once only one starts its services; one that fails is only logged too. A readying that succeeded holds for 60 s (`WORKSPACE_CHECKED_FOR`); one that failed fails the call and is tried again at the next, so a clone that failed or was deleted is made again from its branch. The composer's lookups (`catalog` and `files`) only read files, so they never ready the Workspace or wait for it (`lookupEnv`): until the clones are there they find only what the Workspace holds, its bundled Skills. Workspaces share nothing but their Repos' remotes: each has its own files, Container, Toolchains, processes and ports.
- **Carried files:** a Fork or Clone in a new Workspace (see _Client and protocol_ → _Session tree_) starts from the source Workspace's files as they are. After the Registry has registered the new Workspace and the new Session is filled, the source's Workspace DO runs `carryWorkspaceScript` (`@cloudpid/sandbox-image/workspaces`) on its Container under the Workspace's lock, 15 minutes at most: for each Repo it has a clone of with a commit, its HEAD (commits not pushed included) is pushed to `origin` as the new branch, and its uncommitted Changes (untracked files that are not ignored included), read through an index of its own so the clone is left as it was, as a commit on HEAD to `refs/cloudpid/carry/<branch>` (`carryRef`). It is refused before anything is pushed when a remote has the branch already, and a push that fails takes back what was pushed. The new Workspace's readying then clones the branch as any, and `prepareWorkspaceScript` applies the carried commit's diff to the work tree, uncommitted still, and deletes the ref; a carry that does not apply fails that Repo's clone (made again at the next readying) and stays on the remote for the owner. The switch of a spare taken for it does the same.
- **Spare Workspace** ([ADR-0016](adr/0016-environments-and-a-container-per-workspace.md); a spare starts its first Container from its Environment's Build as any new Workspace does: see _Container and Toolchains_ → _Builds_): each Environment keeps one Workspace made ahead, so a new Session does not wait for the clones, the Setup Scripts and the first Container start. Its record is marked spare (`spare`, Registry migration 12) and is on the placeholder branch `cloudpid/spare` (`SPARE_BRANCH`, `@cloudpid/protocol`, which a new Workspace's own branch may not be: `ownBranchProblem`), so the Environment-and-branch index allows one per Environment; it records the Environment's Repos when it is made, as any Workspace does, and the Environment's last good Build then (its snapshot id, `spare_build`, Registry migration 15), which it is prepared from. `listWorkspaces` and `getWorkspace` leave it out, so the UI never shows it and no Session can name it (`workspace: <id>`). **Taken:** `createSession` with a new Workspace takes the spare when its Repos (names and addresses, in any order) are the Environment's: in the same transaction it stops being spare and gets the branch (`cloudpid/<its id>` by default, or the owner's, with the usual refusal of a branch another Workspace is on, which leaves the spare) and the base, and is listed from then, made at that time. A spare whose Repos differ is stale: it is not taken, and the Session gets a new Workspace. A spare made from another Build than the Environment's last good one is stale too, but a Session still takes it (its clones are there) until the upkeep removes it. **Replenished:** after a Session is created in a new Workspace (taken or made), after `createEnvironment`, `addRepo` and `removeRepo`, after the Builds' upkeep records a new last good Build (`buildUpkeep`), and behind `listSessions` (every Environment, until a run in that isolate finds nothing to do, so a fresh deploy gets spares too, and again after an upkeep of one Environment failed), the main Worker keeps the Environment's spare current after the answer, in `waitUntil` (`spareUpkeep`, `apps/server/src/registry/rpc.ts`). One Registry call (`upkeepSpares`) says what to do, so an upkeep with nothing to do costs that call: it lists the stale spares and registers a spare, with a fresh id, for each Environment that has none. Each stale spare's record is forgotten (`forgetSpare`, which keeps a record a Session took meanwhile, whose Workspace DO is then left alone), then its Workspace DO is wiped (`destroy`, then `reset`), and a second call registers their replacements; each spare registered is asked to prepare itself (`prepareSpare`), and one whose record was forgotten meanwhile (its Environment deleted, or gone stale) has its Workspace DO wiped again, since the request made it anew. What fails is logged and left: a stale spare not forgotten is removed at a later upkeep, one forgotten whose wipe failed is left to its idle stop, and a spare that was not prepared is readied by the Session that takes it, as any new Workspace. **Prepared:** the main Worker's `waitUntil` lasts about 30 s after the answer, far less than a clone, so the spare's Workspace DO does the work (`apps/server/src/workspace/spare.ts`): `prepareSpare` stores the set-up (Repos, branch, the Environment's Container settings and its last good Build; the Environment's Secrets it carries are kept sealed apart, as a readying's are: see _Agent capabilities_ → _Secrets_) and sets the DO's alarm for now, and answers. The DO has one alarm, which the idle stop uses too: it begins a preparation that waits (without waiting for it to end), then runs the idle stop's check, and the idle stop never sets it later than a preparation that waits. The preparation holds the Container from the idle stop as a command does and runs `prepareWorkspace` over the DO's own files and Container (`preparationHost` with the DO itself as the Workspace stub): the settings are handed over, the Repos cloned on `cloudpid/spare` from each one's default branch, and their Setup and Start Scripts run; then one empty command runs on the Container, so a spare of no Repos has had its bootstrap (Toolchains, the Environment's Setup Script) too. Then the Container is snapshotted and stopped as at an idle stop (`IdleStop.stop`; a command that runs or arrives during the snapshot keeps it), unless the spare was taken meanwhile (see below). A preparation that fails is logged and leaves the spare as it is; one cut off by an eviction is begun again at the DO's next alarm (the idle stop's, which the hold armed), three times at most. **Readied once taken:** the readying (`prepareWorkspace`) reads each clone's `.git/HEAD` from the Workspace's files, without the Container, and gives the clones on `cloudpid/spare` to `prepareWorkspaceScript` with the missing ones. The script switches such a clone under the Workspace's lock, then the clone's own (so a Setup or Start Script of the spare's that still runs is waited for), with git's hooks off and `SKIP_REFERENCE_REPOS=1`: it fetches `origin`, checks out the Workspace's branch as a clone does (tracked from `origin` when the remote has it, else made from `origin/<base>`, else from the remote's default branch, `origin/HEAD`, else unborn in an empty repo), keeping what the spare's Setup Script changed in tracked files unless the checkout cannot (then it is discarded), and deletes `cloudpid/spare`. A switch that moved the commit removes the clone's Setup Script record, so the script is due again, flags the clone for its Start Script and runs `mise install` if it declares Toolchains, as for a new clone; the readying then runs both scripts as for a new clone. A spare taken while it is still being prepared ends on the Workspace's branch: a readying that finds a clone not there yet waits for the spare's clone under the Workspace's lock and then finds it on `cloudpid/spare` and switches it, and the spare's own Setup and Start Scripts take the clone's lock, as the switch does. A spare taken midway is not stopped under its Session: the preparation reaches its own Workspace DO through a handle of its own, and any call of the DO's from outside (a command, a file operation, a readying's `containerSettings` or `updateContainerSettings`, a Skills or Prompt templates lookup: `SparePreparation.noteUse`) marks the spare taken, so the preparation ends without the stop, logs so, and leaves the Container to the idle stop as for any Workspace. The mark is kept in the object's storage (`cloudpid:spare-used`) and never undone: a preparation that has not begun (a request the upkeep sends again after the take, or one an eviction cut off) is dropped, logged, instead of readying, and stopping, a Workspace a Session works in. **Removed:** a stale spare by the upkeep, as above, and an Environment's spare when the Environment is deleted (see _Environments from the UI_). Not verified on a deployed stage: the Workspace DO running commands on its own Container through itself (checked in workerd, which has no Container), the preparation's snapshot and stop, and how much of a new Session's wait a spare takes away.
- Skills: the headless-safe skills from `~/.pi/agent/skills` and `~/.agents/skills` are copied to `skills/` (`node scripts/sync-skills.mjs`, which lists them) and mounted read-only with `WorkerBundle` at `/workspace/.agents/skills` in every Workspace; a write there fails with `EROFS`. The files ship in the Workspaces Worker as `?raw` imports (text only, so nothing that needs a local app, browser or binary is bundled; each skill's upstream licence is kept in `skills/LICENSES/`, and `find` and `grep` from above the mount skip it). Repo-local `.agents/skills` are discovered too: the `skills` prompt section (`@cloudpid/extensions/skills`) lists the skills in `.agents/skills` of the conversation's `cwd` and of each directory above it up to `/workspace`, nearest first, as local pi lists them (name, description, path of `SKILL.md`, which the agent loads with `read`; `disable-model-invocation` skills are left out of the list). Discovery reads files and never starts the Container. Prompt templates in `.agents/prompts` are found the same way, for the composer (see _Client and protocol_ → Slash commands).
  - **Cost per request:** discovery runs on every LLM request, so it runs where the files are: `ComputerExecutionEnv.discoverSkills` is one call to the Workspace DO's `skills(cwd)`, which walks the directories from `cwd` up in process (`discoverSkills`, `@cloudpid/extensions/skills-discovery`) and takes the bundled skills from the bundle in memory, parsed once per bundle version (the mount is read-only and holds exactly the bundle, so it is what a walk of the mount finds; a test compares the two). A request is therefore one RPC whatever the number of skills, with no listing and no read of the bundled ones. The repo's own skills are still listed and read on each request, but next to the storage and capped at 100; they are not cached, since the agent edits them. An environment without `discoverSkills` (a test's) is walked through its file operations, as before.
  - **The Container's copy:** computer's sync refuses a Container write under the mount (it is recorded as skipped) but leaves it on the Container, so the Container's copy would drift until it restarts. The bootstrap (see _Container and Toolchains_) therefore bind-mounts `/workspace/.agents/skills` over itself read-only (only where the Container has a real mount: not under `alchemy dev`, `CONTAINER_FUSE=false`), and a write there fails with `EROFS` on the Container too. It is best effort: where the Container cannot mount (`alchemy dev`'s, without FUSE), or when a deploy replaces the skills in a running Container, the directory stays ordinary and a write there succeeds locally, never reaches the Workspace and is gone when the Container restarts. Only the mount itself is protected: `mv /workspace/.agents …` on the Container takes the mount along, and the Workspace then holds the moved copy as ordinary files next to the real mount. Checked deployed: `touch`, `>>`, `rm -rf` under the mount fail with `EROFS` on the Container, which comes back read-only after a restart (`kill 1`), and the Worker Shell's and the Container's `sha256sum` of a skill agree.
  - **Files already at the mount:** computer clears a mount's root the first time it indexes it, so what a Workspace had at `/workspace/.agents/skills` before the mount existed would be deleted. The Workspace DO moves it to `/workspace/.agents/skills.pre-bundle` (`-2`, `-3` if taken) before the first index and logs a warning; nothing is moved when the directory is absent or empty, nor once the mount has been indexed (computer records it). The bundled skills (#71) are already in `prod`, so any Workspace opened since has indexed the mount and nothing is moved for it: only a Workspace not opened since then can have files set aside. The move is only logged (a warning in the Workspace DO's logs); nothing in the UI or the agent's context says so, but `ls /workspace/.agents` shows the directory. Skills of a Workspace's own belong in a repo's `.agents/skills`, or in `.agents/skills` of the repo directory the agent works in.
- **Project instructions** (`@cloudpid/extensions/agents-md`): the Workspace's `AGENTS.md` files are put in front of the model as local pi and codex put them there. A directory's instructions file is the first of `AGENTS.override.md`, `AGENTS.md`, `AGENTS.MD`, `CLAUDE.md`, `CLAUDE.MD` it holds (pi's list; an empty one counts as none), cut to 64 KiB and 1,000 lines with a note to `read` the rest; the instructions for a directory are those of `/workspace`, of each directory between, and of the directory itself, the farthest first (a directory outside `/workspace` has only its own). Finding them reads files only, next to them: `ComputerExecutionEnv.discoverInstructions(directory)` is one call to the Workspace DO's `instructions(directory)` (`discoverInstructions`, `@cloudpid/extensions/agents-md-discovery`, a module of its own so the Workspaces Worker does not load the harness); an environment without it is walked through `readTextFile`.
  - **The `project_context` section** holds the instructions of the conversation's `cwd`, each as `<project_instructions path="…">` in pi's format. Its text is read once per context and then shown as it was (`PromptInput.shown`), whatever the files say later: pi-durable sends a changed section as a patch, which a provider without mid-conversation system messages (Anthropic's, as the Session's models are configured) folds into the system prompt, the head of the cache prefix. A Handoff starts a context without it, and the next request reads the files again; a compaction that keeps an earlier system entry keeps the text too.
  - **`read`, `edit` and `write`** (wrapped; the extension sits before `secrets`, so a path's Secret references are resolved when it looks) add to their result the instructions for the touched file's directory that the context does not show yet, or shows with other text ("these replace them"), as Claude Code does for the `CLAUDE.md` files below its working directory. A tool result is the end of the context and is committed with the text, so nothing a request sent changes in a later one. An edit or write of an instructions file the context showed gets a one-line note that its new text applies instead of the file again; a `read` of one adds nothing for it. One result gets at most 128 KiB and 2,500 lines of instructions (the rest waits for a later call), and the three tools' output limits are raised by as much, since pi-durable keeps only the head of a result over its limits (`read` bounds its own text to the defaults). A failed call, a script's (nested) call, whose result goes to the script, and a lookup that fails add nothing.
  - **What the context shows** is a conversation document (`cloudpid.agents-md`): each file's path and a hash of the text shown. A `beforeRequest` hook makes it what the request holds (the section's blocks and the `details.agentsMd` of the results), so after a Handoff or a compaction took a result out, its instructions are added again at the next touch; the wraps check and update it in one commit, so parallel calls add a file once.

### Backends

| Backend      | Runs                                                                    | Use                                                                            |
| ------------ | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Worker Shell | just-bash in a Dynamic Worker, with `createGitClient()` providing `git` | Text and file commands: `cat`, `grep`, `sed`, `jq`, and read-only `git status` |
| Container    | Real Linux through computerd and FUSE at `/workspace`                   | Anything needing a real binary: `npm`, `node`, test runners, `gh`              |

`bash` chooses a backend per call: an explicit `backend` argument (`worker` or `container`) always wins, and without one the command decides (`routeCommand`, `packages/extensions/src/bash-routing.ts`). The Worker Shell cannot run ELF binaries, has no network, and has no credentials, so a command that needs any of those goes to the Container; a command that is not understood goes there too, since the Container runs anything and starts only when a command is sent to it. The Container is the costly part of a Session (billed while it runs, seconds to start), so the Worker Shell gets every command it can run: a program the router does not know is asked of the Worker Shell, and a command the Worker Shell turns out not to run is rerun on the Container when running it twice cannot write twice (both below). The tool description tells the model what each backend can do, that routing is automatic, that the Container is costly and that `backend` overrides it; an environment that cannot reach the Container answers a `container` call with an error.

- **Programs the router does not know:** a program in neither `WORKER_SHELL_COMMANDS`/`WORKER_SHELL_BUILTINS` nor `CONTAINER_PROGRAMS` (the real binaries the model runs most, which go straight to the Container) is asked of the Worker Shell before the command runs (`resolveRoute`: one `command -v` script, `probeScript`, for every such program in the command), and the command goes to the Container when one is missing. The script ends with a line of its own, and an answer without it (cut short, or a probe that failed) is not kept: its command goes to the Container this once. The answers are kept for the `bash` tool's life (one per Session DO isolate): every Worker Shell runs computer's shell at the version the Workspaces Worker deployed, and a Workspace DO still on older code that lacks a program fails the command, which then falls back as below.
- **Fallback:** a command routed to the Worker Shell has its output held back until it ends. When its stderr shows the Worker Shell could not run it as the Container would (`workerShellCannot`: `command not found`, an option its version of a program rejects, `not supported`, a syntax error, the git pack limit's message; on stdout, where `2>&1` puts them, only the shell's own `command not found` and syntax error, since a file the command prints may hold any line) and the command writes no file (`BashRoute.writes`: no output redirect but to `/dev/null` or a descriptor, no `rm`/`mkdir`/`cp`/`mv`/`tee` and the like, no `sed -i` (`-i.bak` and clusters included), `sort -o`, `find -delete`, no `awk` program that may redirect or comes from a file, no program the router does not know), it runs again on the Container, the Worker Shell's output is dropped, and an info diagnostic tells the model why. A command that writes is left with the Worker Shell's answer, since running it twice could write twice; so is one whose error a `2>/dev/null` hid, or a pipe changed (`2>&1 | grep x`). A Worker Shell command that never started (`spawn_error`) runs on the Container too, when it writes no file (computer may have started it before failing).

- **Container-only paths:** a command whose path words name a Container-only path goes to the Container up front: before a command routed to the Worker Shell runs, its argument words, redirect targets, `--opt=value` values and the literal start of each glob are resolved against its `cwd` (following a `cd` earlier in the command; `~` is the Container's `/root`) and sent in one call to the Workspace DO (`ComputerExecutionEnv.containerOnly`), which answers by the launch's patterns as for the file tools. False positives (`grep node_modules package.json`) are accepted: they cost a start, not a wrong answer. A Worker Shell run whose error says a Container-only path has no such file reruns on the Container as a fallback does, when it writes no file.
- **Reading the command:** the command is read the way bash reads it (quotes, pipelines and lists, subshells, `$(…)` and backticks, heredocs, `env`/`time`/`timeout`/`xargs`/`find -exec`/`bash -c` wrappers), so a program named in a string or a heredoc body does not count and one inside a substitution does. Every simple command must be one the Worker Shell runs, or the whole call goes to the Container (one call, one backend, except that a fallback runs the whole call again on the Container). `case` is read too: its word, `in` and patterns are not commands, its clauses' commands are. `./script`, `/usr/bin/x`, `bash script.sh`, `source`, a command named by `$VAR`, `select`, `coproc`, process substitution (computer 0.6.0's shell does not parse it, though just-bash 3.6 does), and a command that does not parse go to the Container.
- **Worker Shell commands:** `@cloudflare/computer`'s just-bash core (`cat`, `grep`, `rg`, `sed`, `awk`, `find`, `sort`, `tar`, …, no `curl`, `python`, `node`, `yq`, `sqlite3`), `jq` (an optional computer module the Workspace DO adds), the shell built-ins, and `git`. `WORKER_SHELL_COMMANDS` is that list; a workerd test runs each name through the real Worker Shell.
- **git:** `git` on the Worker Shell is isomorphic-git behind `createGitClient()` (the Workspace DO passes it), not real git, and its output is not always git's. Only a small read-only set stays there, each form checked against real git's output in the workerd test: bare `git status`, `git log --oneline` (with `-n`/`-N`), `git rev-parse` (`HEAD`, `--abbrev-ref HEAD`, `--show-toplevel`), bare `git ls-files`, and `git branch` (bare or `--show-current`). Everything else goes to the Container: every subcommand that writes the index or a ref (`add`, `rm`, `commit`, `tag`, `branch <name>`, `init`, `remote`, …), `diff` and `show` (the client's patches are not git's), plain `log` (another date format), `cat-file` (broken), `clone`, `fetch`, `pull`, `push` (no network or credentials on the Worker Shell), `config`, and what rewrites the working tree (`checkout`, `switch`, `reset`, `merge`, `stash`, `clean`), as does any option or argument not listed (`git status --short`, `git log --graph`). The Worker Shell's git has no default identity (it was removed: a commit there needs `GIT_AUTHOR_*`/`GIT_COMMITTER_*` in the command, and the router sends every commit to the Container, whose identity is `CLOUDPID_GIT_NAME`/`CLOUDPID_GIT_EMAIL`).

The Workspace DO registers both backends on its one Workspace, as `worker-shell` and `container-shell`, so both see the same `/workspace`: computer pushes the DO's changes to the Container before a Container command and pulls its changes back after it. `ComputerExecutionEnv.onBackend()` selects one. computerd runs commands with `/bin/sh -c`, which is dash on Ubuntu, so a Container command is wrapped in `exec bash -c '…'` to keep `bash` bash. The Container starts on the first command sent to it, which waits for it (a message the owner sends starts nothing, so a turn that runs no command costs no Container time): about 2 s after a restore, 10–30 s from the image on Cloudflare (4 s under `alchemy dev`).

The Worker Shell returns a command's output once, when it exits: `onOutput` gets all of stdout, then all of stderr, attributed but not interleaved in arrival order. The Container streams output as it comes, so its tests must check streaming, which the Worker Shell's cannot.

### Container and Toolchains

[ADR-0004](adr/0004-mise-toolchains-with-preinstalled-defaults.md) covers this design.

- **Image:** `ubuntu:24.04` (pinned by digest, as every base image is) plus `fuse3`, the everyday command-line tools agents and scripts expect (`curl`, `wget`, `jq`, `ripgrep`, `fd-find` with `fd` linked to its `fdfind`, `unzip`, `zip`, `xz-utils`, `procps`, `psmisc`, `lsof`, `iproute2`, `dnsutils`, `netcat-openbsd`, `less`, `file`, `tree`, `openssh-client`, `gnupg`, `sudo`, `sqlite3`, `tzdata`, and from exe.dev's exeuntu list `rsync`, `socat`, `net-tools`, `iputils-ping`, `bubblewrap`, `locales` with `en_US.UTF-8`, and `time`), `build-essential` with `pkg-config` and the headers native npm and pip packages build against (`libssl-dev`, `zlib1g-dev`, `libffi-dev`), Docker (see _Docker_, below), `earlyoom` (the memory guard: see _Memory guard_), `computerd` (pinned to match `@cloudflare/computer`, run under the image's supervisor: see _Exit reports_), and `mise` ([#169](https://github.com/ian-pascoe/cloudpid/issues/169), ADR-0004's second revision). Every versioned program a project uses, `git` and `gh` included, is a mise Toolchain, never an apt package (an apt `git` a package pulled in would be behind mise's shims on `PATH` anyway); the image preinstalls the base Toolchains into mise's system directory (next bullet), where they are still found and managed as Toolchains, through the Workspace's mise config. `python3-pip` and `pipx` are left out, since they would bring apt's Python beside mise's. The image must be glibc-based, so no Alpine. exeuntu itself is not the base: it is a VM image with systemd, exe.dev's integrations and a desktop's libraries, 1.8 GB compressed against this image's few hundred MB, which every launch from the image and every Snapshot would pay.
- **Preinstalled Toolchains:** the image holds mise's installs of the base `mise.toml`'s Toolchains, one exact version each of `conda:git`, `gh`, Node (the LTS), pnpm, Python and uv (`BASE_MISE_TOML` in `apps/sandbox-image/src/toolchains.ts`; the image builds from its copy, `apps/sandbox-image/image/mise.toml`, which a test keeps equal). They are in mise's system directory (`mise install --system`, `/usr/local/share/mise/installs`, shims in `/usr/local/share/mise/shims`, on `PATH` after the user shims), which mise searches for a version a config asks for before it downloads one, so they are used by any Workspace or repo whose config asks for exactly those versions, and by none that does not: a project's versions still decide (ADR-0004). `mise ls` labels them `(system)`. The image also makes the base file's `mise.lock` (`BASE_MISE_LOCK`, `/usr/local/share/cloudpid/mise.lock`), because `mise lock` downloads the aqua and Python artifacts it checksums (90 MB for these), which would undo the preinstall. The versions are exact because mise locks a prefix (`node = "24"`) to the newest release, which the image soon would not have. Refreshing them is an image change: a new Workspace then gets the new versions, and an existing one keeps its own, downloaded if the image no longer has them.
- **Persistence:** `mise.toml` and `mise.lock` live in the workspace and are synced; a Workspace with no mise config gets its Environment's Toolchains as its root `mise.toml` on the first Container start (its `toolchains` Container setting), or the base `mise.toml` (the image's preinstalled Toolchains: see above) with the image's `mise.lock` for it beside it when the setting is empty. The bootstrap records the SHA-256 of the copy it wrote, with the lockfile made for it, in `/var/lib/cloudpid/toolchains` (`TOOLCHAINS_STATE_DIRECTORY`, outside `/workspace`, so nothing syncs it and a snapshot carries it), and replaces a root `mise.toml` that still has that hash (or is the base file, which it wrote before it kept a record) when the Environment's Toolchains change, with the recorded lockfile when it is for the same copy; a root `mise.toml` the Workspace changed is its own and stays, and so does a root with a mise config of another name; a root `mise.toml` the Workspace changes later is locked by the bootstrap (`mise lock --global`, to `linux-x64`). The Toolchains themselves (`MISE_DATA_DIR`, `MISE_CACHE_DIR`) stay in mise's default place on the Container's disk, `/root/.local/share/mise` and `/root/.cache/mise`, with `TMPDIR` as `/tmp` on the same disk, so an install never renames across a filesystem or the ignore boundary (no `EXDEV`) and nothing of it reaches the Workspace DO. computer's `ignore` (`TOOLCHAIN_IGNORE` in `apps/sandbox-image/src/toolchains.ts`) lists `**/node_modules`, `**/.venv`, `/target` and `/*/target`, pnpm's store (`**/.pnpm-store`: where an install made before the pnpm configuration below, or by an older pnpm, left it, at the mount's root because the home directory is on another filesystem), caches (`**/.cache`, `**/__pycache__`, …), and build tools' caches and environments by names no source directory has (`**/.turbo`, `**/.next`, `**/.nuxt`, `**/.svelte-kit`, `**/.parcel-cache`, `**/.terraform`, `**/.gradle`, `**/.tox`, `**/.nox`, `**/.direnv`, `**/.wrangler`, `**/.astro`, `**/.angular`, `**/.expo`, `**/.nx`, `**/.docusaurus`, `**/.nyc_output`, `**/.hypothesis`, `**/.dart_tool`, `**/.zig-cache`, `**/.stack-work`): they stay container-local and out of DO SQLite. Names some repos commit (`dist`, `build`, `coverage`, `vendor`, `.yarn`, `_build`, `.output`, `deps`) stay synced, since a tracked file on an ignored path shows as deleted in the Worker Shell's git; so does `.alchemy` (it can hold real deploy state). Ignoring a path only keeps it out of the Workspace DO: computerd still serves every file operation on it through FUSE, which is what made `pnpm install` 3–6× slower than on plain disk (see _Known risks_), so a path that should be fast has to be off `/workspace` as well, which is what the next bullet does for pnpm and Turborepo. An Environment adds its own paths after these (its `ignore` setting, at most 50, each checked against computer's pattern rules when saved, since computer refuses a bad one when it builds the Container's backend): the last pattern that matches a path wins, so a `!` pattern keeps a built-in one synced. Ignoring a path the Workspace already holds does not remove its files from the Workspace DO; they stay until deleted. Under `alchemy dev` no list is applied (see _Infra_ in `AGENTS.md`). The first plan put the Toolchains under `/workspace/.mise` on that list; see _Known risks_ for why they are not.
- **pnpm and Turborepo off the mount** (#151): pnpm's files are on the Container's disk, outside `/workspace`, so `/workspace/<repo>/node_modules` is mostly symlinks (784 in the root's of this repo, with 61 other files) and the install does not go through FUSE. The bootstrap writes pnpm's global configuration, `config.yaml` in `$XDG_CONFIG_HOME/pnpm` or `~/.config/pnpm` (pnpm 11 and later read it, and 11.0–11.22 ignore two of its keys: see below; `PNPM_GLOBAL_CONFIG` in `apps/sandbox-image/src/toolchains.ts`), each key only when the file does not already have it (so a Container's own `pnpm config set --global` stays): `storeDir: "$HOME/.pnpm-store"` (`/root/.pnpm-store`, the content-addressed store in `v11/files`), `virtualStoreType: global` together with `enableGlobalVirtualStore: true` (pnpm's global virtual store under its two names: `virtualStoreType` is read from 11.23, `enableGlobalVirtualStore` from 11.0 and still later, and pnpm 11.0–11.22 would else put the store on the Container's disk and the virtual store on the mount, which copies packages instead of hard-linking them; pnpm 11.20 ignores `virtualStoreType` and `confirmModulesPurge` in the global file with a warning at each install, and 11.28 and 12.15 take both keys without one, and a repo's `virtualStoreType: project` or `enableGlobalVirtualStore: false` wins on them; the store's packages are linked once into `<storeDir>/v11/links`, on the same filesystem as the store, so pnpm still hard-links, and each project's `node_modules` holds symlinks into it plus a small `node_modules/.pnpm` of its lockfile and hoisted links) and `confirmModulesPurge: false` (pnpm's install no longer asks before it purges `node_modules`, which would hang a command: an install made the old way moves to the new layout at the next `pnpm install`). `virtualStoreDir` is not set: set globally it would also be where a repo that chooses the project layout keeps its virtual store, shared with every other repo (the global setting applies to `virtualStoreType: project` too), and unset the global virtual store is under the store. `CI` is not set for commands, since it changes other tools' behaviour. These are in the global file and not in environment variables because pnpm lets `pnpm_config_*` variables override a repo's `pnpm-workspace.yaml` and the global file loses to it: a repo that sets its own `storeDir`, `virtualStoreDir` or `virtualStoreType: project` (or `enableGlobalVirtualStore: false`) keeps it (checked with pnpm 12.15), and gets the old speed. A repo's pnpm older than 11 does not read the file and works as before, with its store at the mount's root. `**/.pnpm-store` and the `node_modules/.pnpm` of the project layout are what the token scan skips (see _Snapshots_). Node resolution under a global virtual store (checked on a deployed Container): a package's declared and peer dependencies resolve from its real path in the virtual store, so vitest, vite and `tsc` find theirs; a dependency a package does not declare resolves through the `NODE_PATH` that pnpm sets for what it starts (`pnpm run`, `pnpm exec`, a `node_modules/.bin` shim), for CommonJS and, since pnpm 11.23, for ESM through an `--import` hook in `NODE_OPTIONS`; a `node` started by hand, without pnpm's environment, finds the dependencies of the project's own `package.json` and what each package declares, and not an undeclared one (`Cannot find module`). TypeScript does not use `NODE_PATH`: a library whose `.d.ts` imports `react` without declaring `@types/react` found it only in the project layout's hoisted directory, so `apps/web`'s `tsc` failed under the global virtual store (`event` implicitly `any`, `use(RegistryContext)` of type `unknown`; `atom-react`, assistant-ui, `lucide-react`, `streamdown` and `react-textarea-autosize` are such libraries) until its `tsconfig.json` mapped `react` and `react-dom` to its own `@types` with `paths`; a repo with the same problem declares the missing dependency with `packageExtensions` or does the same. A repo that chooses the project layout itself (`virtualStoreType: project`, or `enableGlobalVirtualStore: false`) keeps it, but with the store on the Container's disk and `node_modules/.pnpm` on the mount, pnpm copies the packages instead of hard-linking them ("Packages are copied from the content-addressable store"): that repo should set its own `storeDir` too. Turborepo's cache is `TURBO_CACHE_DIR=/root/.cache/turbo` in every command's environment (`toolchainEnv`), instead of `.turbo/cache` in the repo; `**/.turbo` stays ignored for the rest of what Turborepo writes there. The variable beats a repo's `turbo.json` `cacheDir` (checked with turbo 2.11: only `--cache-dir` beats the variable), and turbo has no global configuration file to put the default in, so a repo that sets `cacheDir` gets the variable's directory anyway.
- **Bootstrap:** before the first command of each Container start, `ToolchainBackend` (`apps/server/src/workspace/toolchains.ts`, a wrapper around computer's `ContainerBackend`) runs `apps/sandbox-image`'s `bootstrapScript` through the Container's shell. It writes the Environment's Toolchains as the root's `mise.toml`, or the base `mise.toml` when it has none (with the image's lockfile for it, or the recorded lockfile of that same copy: see _Persistence_), where the root's `mise.toml` is still the copy it wrote last, or the root has no mise config of any kind mise reads (`mise.toml`, `.mise.toml`, `mise.local.toml`, `.config/mise.toml`, `.config/mise/config.toml`, `.mise/config.toml`, `.tool-versions`); locks the root's `mise.toml` (`mise lock --global`, when the lockfile is missing or older than the config); runs `mise install` (from `mise.lock`; a no-op for what is present) in `/workspace` and in each repo directory with a mise config; sets git's identity and credentials; writes pnpm's global `config.yaml` (see _pnpm and Turborepo off the mount_); and, when that succeeded, runs the Setup Scripts that are due (see _Setup Scripts_), then the Start Scripts (see _Start Scripts_). It reads the Workspace's Container settings once, as it begins: their variables are the environment of the bootstrap, its scripts and every command of that Container start (see _Command environment_), their Setup and Start Scripts are the Environment's, and their Toolchains are the `mise.toml` it writes. Before all of that it makes the directories the Workspace holds read-only (`/workspace/.agents/skills`, the bundled skills) read-only on the Container too, with a bind mount remounted `ro`, when the Container can mount; that never fails the bootstrap. Commands that arrive meanwhile wait for it; computer has pushed the Workspace's files to the Container by then. A command killed or timed out while it waits is not run afterwards. A failed bootstrap is logged (never with the token) and does not stop commands: the command that waited for it starts with a note on stderr (the failure's output, redacted), later ones with a pointer to it, and the next attempt comes after a minute, doubling with each failure in a row up to 15 minutes. A new connection to the same Container does not repeat the bootstrap. A cold start takes about 10 seconds on Cloudflare plus the install, which is nothing for the base `mise.toml` (the image has its Toolchains) and about 10 seconds for Node 22 and Python 3.13 when a Workspace asks for those instead; a restart reinstalls from the lockfile. With a snapshot to restore (see _Snapshots_) the Container starts with its Toolchains in place, and the bootstrap finds nothing to install.
- **Setup Scripts:** a repo can prepare itself on the Container (typically installing its dependencies) with a Setup Script, its `.cloudpid/setup.sh` (`SETUP_SCRIPT`; under `.cloudpid/`, not the `.agents/` other agents read, since only cloudpid runs it: [ADR-0020](adr/0020-repo-scripts-live-in-cloudpid.md)), and an Environment can have one of its own (its `setupScript` Container setting, bash, at most 64 KiB of UTF-8), for what its Workspaces need whatever the repo (system packages, a Docker image). Once the Toolchains are installed (not after a failed install, whose retry does it), the bootstrap lists the scripts that are due (`pendingSetupScripts` in `apps/sandbox-image/src/toolchains.ts`): first the Environment's, which that same exec writes to `/var/lib/cloudpid/environment/setup.sh` (base64 in the command, so no quoting or heredoc can meet its text; an empty setting removes the file), then the repos' (directories directly below `/workspace`). A script is due when its SHA-256 differs from the last one that succeeded on this Container's disk, recorded in `/var/lib/cloudpid/setup/<repo>` (the Environment's under `@environment`, a name no Repo can have), outside `/workspace`, so nothing syncs it and a snapshot carries it. It runs each one after the other as an exec of its own (`setupScriptRun`), the Environment's first: with bash, in the repo's directory (the Environment's in `/workspace`), with no input and a command's environment (Toolchains on `PATH`, the GitHub token, the Environment's variables) plus the Environment's Secrets marked for the Build, each as `$PI_SECRET_<NAME>` (from the Workspace DO's copy: see _Secrets_; no other script or command gets them that way), stopped with every process it started after 15 minutes (`timeout`, which signals its process group; computer's exec limit is a minute longer). A script that succeeds records its hash, so it runs again only when its content changes, or on a Container started from the image (a Container restored from a snapshot has the record and what the script installed, its dependency directories being Container-only paths on the disk). Commands wait for them as for the install, and the Container counts as in use meanwhile (the idle stop), whether or not a command still waits. A failed or stopped script does not stop commands and is not retried in that Container: it is logged, the first command that starts after it (the one that waited, unless it was killed meanwhile) gets a note on stderr carrying the end of its output (redacted), and later commands in that Container a one-line pointer to it; it is due again at the next Container start. A script that exits with `timeout`'s status (124) on its own is reported as that exit status: only the run's own last line (`SETUP_TIMED_OUT_MESSAGE`) marks a script stopped for its time. The install snapshot is taken after the scripts, so it keeps what they installed, and their time is not the snapshot's; a script that succeeded counts as an install for it, and one that failed does not (see _Snapshots_). This repo's own script (`.cloudpid/setup.sh`) runs `CI=1 SKIP_REFERENCE_REPOS=1 pnpm install --frozen-lockfile`: `CI` so pnpm asks nothing, and `SKIP_REFERENCE_REPOS` so `prepare` does not clone effect and pi into `.repos/` (about 5,150 files, 355 MB, not ignored, so they would sync into the Workspace DO). A clone that a Workspace's readying makes after the bootstrap gets its script run right after it is made (see _Workspaces_, above).
- **Start Scripts:** what a snapshot cannot hold (running services: a database, `docker compose up`) is started at each Container start by Start Scripts: the Environment's (its `startScript` Container setting, at most 64 KiB) and each repo's `.cloudpid/start.sh` (`START_SCRIPT`). After the Setup Scripts and after the install snapshot (so no service is writing to the disk while it is taken, and none is in it), the bootstrap runs the Environment's in `/workspace` (`environmentStartScriptRun`, which writes it to `/var/lib/cloudpid/environment/start.sh` as the Setup Script is written), then lists the repos that have one (`startScriptDirectories`) and runs each in its repo's directory (`startScriptRun`): each an exec of its own, with bash, no input and a command's environment, stopped with every process it started after 5 minutes (`START_TIMEOUT_SECONDS`; computer's exec limit is a minute longer). Nothing records them: they run at every Container start, a restored one included, and not after a mere reconnect; a new bootstrap on a Container that already runs (after the Workspace DO was evicted) runs them again, so a Start Script should leave a service that is already up alone. An exec ends when the script has and nothing holds its output, so a service a Start Script starts must detach: `setsid nohup cmd >/tmp/cmd.log 2>&1 &` (outside the script's process group, which `timeout` signals, and off its output). Commands wait for them, as part of the bootstrap. One that fails or is stopped is reported as a Setup Script is (logged; a note with the end of its output for the first command that starts after it, a pointer for later ones; a stopped one's note says to detach), stops no command and does not count as an install. A clone that a Workspace's readying makes while the Container runs gets its Start Script run once, after its Setup Script (see _Workspaces_).
- **Global default:** the root's `mise.toml` is also mise's global config (`MISE_GLOBAL_CONFIG_FILE`), so the base Toolchains (git and gh among them) resolve from any directory, not only under `/workspace` (a scratch clone in `/tmp`, the git calls pip and npm make from their own temp directories). The Workspace's own `mise.lock` stays the lockfile; mise locks a global config only through `mise lock --global`, which the bootstrap runs. A root whose config lives elsewhere (`.config/mise.toml`) is installed but is not the global default.
- **Command environment:** computerd starts a command with `PATH` (the image's, with mise's shims first) and `HOME` only, not the image's other variables, so the Workspace DO adds the rest to each command's exec environment (`toolchainEnv`): `MISE_GLOBAL_CONFIG_FILE`, `MISE_TRUSTED_CONFIG_PATHS=/workspace`, `MISE_YES=1`, `GIT_TERMINAL_PROMPT=0`, `TURBO_CACHE_DIR=/root/.cache/turbo` (see _pnpm and Turborepo off the mount_), `BASH_ENV` (the memory guard's note: see _Memory guard_) and the GitHub token (see _Git_), under what the caller passes. The Environment's variables (its `variables` Container setting: at most 50, names a shell can export, values of at most 4096 characters) are under those, so they cannot replace them: the names `toolchainEnv` sets, `PATH`, `HOME`, `PWD`, `SHELL`, `USER` and any `CLOUDPID_` one are refused when saved (`variableNameProblem`). The Workspace DO reads them once per Container start, at its bootstrap, and gives them to the bootstrap, its scripts and every command of that Container start, so a change applies at the next start. They are plain: the agent can read them, and they are not taken out of output (a value to keep from the agent is a Secret kept for the Environment: see _Secrets_). The token, and each Secret kept for the Environment as its Secret Reference, are taken out of what a command prints (`redact.ts`, also when split across output chunks), which stops accidents (`env`, `set -x`) from reaching the Session's history, not a command that encodes one.
- **Under `alchemy dev`:** the local Container has no `/dev/fuse`, and computerd's userspace shim refuses an ignore list (it exits), so the stack sets `CONTAINER_FUSE=false` and the Workspace DO asks for none: `node_modules` and the rest then sync into the local DO like any file. The bootstrap is the same.
- **Container settings:** every Environment has eight Container settings, which its Workspaces' Containers take, the Container's size (`lite`, `basic`, `standard-1`, `custom-1`, `standard-2`, `custom-2`, `standard-3`, `custom-3`, `standard-4`; default `custom-1`: 1 vCPU, 3 GiB memory, 12 GB disk; the image, 1.3 GB on disk on Debian and larger on Ubuntu with Docker, is unchecked on `lite`'s 2 GB disk: see _Known risks_), its size limit (`maxInstance`, one of the same names, default `custom-2`: the largest the size may be and the largest the agent's `container_resize` may start a Container on, see _Resize by the agent_; a Limit, GLOSSARY.md, which the agent changes only with the owner's Approval, ADR-0019; sizes are ordered by memory, then vCPU, `compareInstances` in `packages/config/src/container-settings.ts`, so `custom-1` is below `standard-1`, `standard-2` below `custom-2` and `custom-3` between `standard-3` and `standard-4`; a save of a size above the limit is refused with a message naming both, `instanceLimitProblem`, checked by the Registry's `updateEnvironmentSettings` and by the Edit dialog before it, and a read raises a saved limit below the saved size to the size, so an Environment saved larger than `custom-2` before the limit existed keeps its size as its limit), its idle time in minutes (1 to 1440; default 2), extra Container-only paths (`ignore`, none by default; see _Persistence_), variables (none by default; see _Command environment_), its own Setup and Start Scripts (`setupScript`, `startScript`, none by default; see _Setup Scripts_ and _Start Scripts_), and its Toolchains (`toolchains`: the text of a `mise.toml`, at most 16 KiB of UTF-8 with no NUL, which mise reads and the save does not; empty by default, the image's base Toolchains; see _Persistence_ and _Bootstrap_). `ContainerSettings` (`packages/config/src/container-settings.ts`) is a Schema with decoding defaults like the global settings (writes strict, reads lenient, only what differs from the defaults is kept). They are kept in the Registry with the Environment (`environments.settings`), and the UI reads and writes them through `getEnvironmentSettings`/`updateEnvironmentSettings` (the Environments page's _Edit…_ dialog, where the size limit is next to the size). The Workspace DO cannot bind the Registry (its Worker deploys before the main Worker that hosts it), so each Workspace DO keeps a copy in its own storage (`apps/server/src/workspace/settings.ts`), which a Session's readying replaces when the Environment's differ (`updateContainerSettings`, see _Workspaces_), and reads that copy when it launches its Container (the size, idle time and paths) and when the Container's bootstrap begins (the variables, scripts and Toolchains): a change reaches a Workspace when one of its Sessions next readies it, at most a minute later while it works. **They apply at the next Container launch**: `ContainerLaunch` (`launch.ts`) captures the size, idle time and Container-only paths when it launches and keeps them while that Container runs, because computer relaunches a running Container whose launch differs from the one asked for, so a saved change must not reach a reconnect to the running one. computer's `ContainerBackend` takes its `ignore` list when it is built, so the Workspace DO builds one per list (`PerLaunchContainerBackend`, `per-launch-backend.ts`), asking `ContainerLaunch` before each connection which list the Container it reaches has.
- **Size per launch:** under `schedulingPolicy: "durable_object"` the Workspace DO chooses the size in `ctx.container.start({ instance })` at each launch (the Container application on Cloudflare declares none; alchemy's `instanceType` is not valid for this policy), so one Container class serves every size and the deploy, prod included, is unchanged. `ContainerLaunch.wrap` decorates the Container API computer's `ContainerBackend` launches through, adding `instance` and `containerSnapshot` to its `start` and `restart`. A launch takes the size the agent's resize recorded (see _Resize by the agent_) instead of the settings' size, while it is within their size limit; the launch record keeps the size each Container launched with, whichever it was. The sizes are stored by name in the Workspace's settings (`INSTANCE_TYPES`): Cloudflare's named types (`lite` to `standard-4`) under their own names, and the custom sizes `custom-1`, 1 vCPU, 3 GiB (3072 MiB) memory and 12 GB disk (`{ vcpu: 1, memoryMib: 3072, diskMb: 12000 }`), `custom-2`, 2 vCPU, 6 GiB (6144 MiB) memory and 12 GB disk (`{ vcpu: 2, memoryMib: 6144, diskMb: 12000 }`), and `custom-3`, 3 vCPU, 9 GiB (9216 MiB) memory and 12 GB disk (`{ vcpu: 3, memoryMib: 9216, diskMb: 12000 }`, about $0.084 a running hour with its disk, $0.216 a fully busy CPU hour; above the default size limit, so an owner raises the limit to `custom-3` or larger before the size or the agent's resize can use it). A custom size needs 1 to 4 vCPU, at most 12 GiB memory and 20 GB disk, and at least 3 GiB memory per vCPU ([limits](https://developers.cloudflare.com/containers/platform-details/limits/)); every custom size keeps the same 12 GB disk, so a snapshot or Build taken on one restores on the others. `containerInstance` `containerInstance` (`packages/config/src/container-settings.ts`) maps the custom sizes to those resources at each launch. A stored name never changes meaning (a future custom size gets a new name), and the launch record keeps the name, not the resources.
  - **Why these defaults:** Cloudflare bills a Container's CPU only for active use, and its memory and disk for as long as it runs ([pricing](https://developers.cloudflare.com/containers/pricing/)), so memory is most of what a running Container costs: on `custom-2` (the default until #189) $0.054 of its $0.057 a running hour, with CPU at $0.144 a fully busy hour. `custom-1` halves the memory (about $0.030 a running hour with its disk, $0.072 a fully busy CPU hour), keeping `standard-2`'s vCPU and disk; the disk costs little, and keeping it means a snapshot or Build taken on `custom-2` (or `standard-2`) still fits on `custom-1`. Every idle minute costs the Container's full memory, against about 2 s for a small restore (a Workspace with a large `pnpm` store has measured about 27 s, and its idle stop's snapshot 45–60 s): hence the 2-minute idle default, which an Environment whose Workspaces restore slowly can raise. A repo whose checks need more than about 2.5 GB at once (this repo's `turbo run typecheck lint test` reached 5.9 GB: see _Memory guard_) should set its Environment to `custom-2` or larger, or run its tools with less concurrency.
  - **Changing a default:** a Workspace with no saved size or idle time follows the default at its next launch; one that saved a value keeps it (saving a value equal to the default stores no override, and one equal to a former default, such as `standard-2`, `custom-2` or 5 minutes, is stored; an Environment that left the size or idle time at the default before #189 follows the new one). A Container that runs is never relaunched for it: `ContainerLaunch` keeps the launch it recorded (a running Container found with no record, at `start` or `restart`, is taken to be on `standard-2`, the default when launches were first recorded).
  - A snapshot is a disk image labelled with its image and Container-only paths, not a size, so one taken on `standard-2` restores on `custom-2` and the reverse, and one taken on any custom size restores on the others (all have 12 GB of disk).
- **Snapshots:** `snapshotContainer()` captures the Container's root file system (not memory, processes or separate mounts) and `start({ containerSnapshot })` restores it, on the `durable_object` policy only, under a 30-day lifetime that each restore refreshes. `ContainerSnapshots` (`snapshots.ts`) takes one **after the first successful bootstrap of a Container that started from the image, when that bootstrap installed something** (inline, after its Setup Scripts and before the commands that waited for the bootstrap are sent, so nothing else writes) and **on idle stop** (before the Container is destroyed; a spare Workspace's Container is stopped this way once the spare is prepared: see _Workspace and execution_ → _Spare Workspace_), keeps only the latest handle in the Workspace DO's storage, and the next launch restores it. A bootstrap installed something when its install ended its stdout with `BOOTSTRAP_CHANGED` (`apps/sandbox-image/src/toolchains.ts`: each step of the script that changes the disk in a way worth a snapshot sets its `changed=1`, which `mise install` does when mise's installs directory differs from before it) or when a Setup Script succeeded (`ToolchainBackend`, which runs them as execs of their own). A Setup Script that failed does not count by itself: it runs again at the next Container start, from the image or from a snapshot, whose record does not have it; with mise's installs or another script's success the snapshot is still taken, and keeps what the failed one left. A bootstrap that installed nothing (the base `mise.toml` on the image, all preinstalled, and no Setup Script due) is not snapshotted, so its first command does not wait for one (logged at info); its Container is snapshotted at its idle stop. When the install snapshot is not taken (failed, or given up on), a later bootstrap in the same Container (after the Workspace DO was evicted) tries again though it installs nothing itself (`installPending` in the launch record). The handle is labelled with the image the Container runs, recorded per launch (the deployed image for a launch from the image, the snapshot's for a restore), not the image a launch would run now: Containers outlive a deploy, so one still on the old image is not snapshotted (and an adopted Container with no launch record gets none). A snapshot is not portable to another image, so a deploy that changes the image discards it. One close to the 30-day lifetime (counted from its creation or latest restore) is not restored, and neither is one taken with other Container-only paths than the launch has (computerd's store and the disk's copies of those paths are laid out for the old ones): the snapshot record keeps the list (built-in paths included), and a Workspace whose paths changed starts its next Container from the image. So does every Workspace after a deploy that changes `TOOLCHAIN_IGNORE`, and a Container still running from before such a deploy is relaunched by computer at its next connection, as for any change to its launch; a snapshot recorded before lists were (2026-10-22) is not restored either. A Container restored from a snapshot is not snapshotted again after its bootstrap: its idle stop does. A launch with no restorable snapshot of its own starts from the Environment's Build when there is a usable one, and is snapshotted after its bootstrap as a launch from the image is (see _Builds_, next). Snapshots are off under `alchemy dev` (`CONTAINER_FUSE=false`: no real mount).
- **Builds** ([ADR-0016](adr/0016-environments-and-a-container-per-workspace.md), GLOSSARY.md → Build): each Environment has a Build, a Snapshot of a Container with its Toolchains installed and what its Setup Scripts download cached outside `/workspace`, which a new Workspace (a spare included) starts its first Container from. **Made** by the Environment's Build object, a Workspace DO named `build:<environment id>` (`BuildRunner`, `apps/server/src/workspace/build.ts`), on its alarm, since a Build outlasts the main Worker's `waitUntil` (as a spare's preparation does; the idle stop shares the alarm and holds the Container meanwhile): it hands itself the Environment's Container settings without the Setup and Start Scripts (`buildContainerSettings`; no service runs in a Build), starts its Container (whose bootstrap installs the Environment's Toolchains, or the base ones, and records the copy it wrote and its lockfile, so a Workspace started from the Build writes the same `mise.toml` with that lockfile and installs nothing), then runs, each a script of its own (`@cloudpid/sandbox-image/builds`) that must exit 0: a full clone of each Repo's default branch into `/var/tmp/cloudpid-build` (`BUILD_ROOT`, outside `/workspace`, so nothing syncs it; git's hooks off, `SKIP_REFERENCE_REPOS=1`, `mise install` where a clone declares Toolchains, with the scratch root in `MISE_TRUSTED_CONFIG_PATHS`), the Environment's Setup Script in that root, then each Repo's `.cloudpid/setup.sh` in its clone, each as the bootstrap runs one (15 minutes at most, a command's environment); it reads each clone's commit, stops every process the scripts left running (each script's environment carries `CLOUDPID_BUILD_RUN=<request id>`, which the clean-up finds in `/proc/*/environ`: `dockerd` then `containerd` get 30 s after `SIGTERM`, the rest 5 s, then `SIGKILL`), deletes the clones and the Setup Scripts' records, so a Workspace started from the Build runs its own scripts once (fast, with the downloads cached), snapshots the Container (`ContainerSnapshots.capture`, with the scan for the token and the Environment's Secrets, labelled `build`) and stops it. A step that fails ends the Build with its reason (the end of its output, redacted of the GitHub token and the Environment's Secrets), and the last good Build stays in use; a Build cut off by an eviction is begun again at the next alarm, three times at most. The Build object takes no snapshots of its own. **Kept current** by the main Worker after an answer, as the spares are (`buildUpkeep`, `apps/server/src/registry/builds.ts`): after `createEnvironment`, `addRepo`, `removeRepo`, `updateEnvironmentSettings`, a change to the Environment's Secrets (to every Environment's, for one kept for every Environment), a Session created in a new Workspace, and behind `listSessions` and `listBuilds` (every Environment; once a run finds nothing to do or under way, that isolate asks nothing for an hour). One Registry call (`buildWork`) gives each Environment's Repos and overrides; each Build object answers what it holds and the image a launch runs now (`buildState`), and is asked for a Build (`startBuild`) when the key of the one wanted (`buildKey`, `apps/server/src/workspace/build-record.ts`: a SHA-256 of the Repos' names and addresses, the variables, the Setup Script, the Toolchains (only when there are some, so the keys of Builds without stay what they were), the Container-only paths and the image, and, where the Environment has Secrets marked for the Build, an HMAC-SHA256 of their names and values under a key the Registry derives from `SECRETS_ENCRYPTION_KEY` (`buildSecretsDigest`, carried by `buildWork`), so a value is never in a key in the clear; not the size, idle time or Start Script) is neither the last good one's nor under way: so a deploy that changes the image makes every Environment's Build again. A failed Build of the wanted key is tried again a day after its attempt. Once a day the Build object is asked for a look instead (`check`): it asks each Repo's remote for its default branch (`git ls-remote`) and builds only when one moved from the Build's commits, or the Build is older than 20 days (`BUILD_REFRESH_MS`, well within a snapshot's 30). An Environment with no Repo, no Setup Script and no Toolchains has no Build. What the object answers (its last good Build, and the one under way or the last failure) is recorded in the Registry (`recordBuild`, Registry migration 13), which hands the last good Build with each Workspace's set-up (`getWorkspaceSetup`, `upkeepSpares`), and the readying gives it to the Workspace DO when it differs from the one it holds (`updateEnvironmentBuild`). Deleting an Environment destroys its Build object. **Used:** `ContainerLaunch` starts a Container from the Workspace's own snapshot when it has a restorable one, and otherwise from the Build it holds when that Build is of the image a launch runs now, has the launch's Container-only paths, is younger than a snapshot's lifetime and has not failed in this Workspace. The launch then sets `CLOUDPID_RESET_STORE=1` in the Container's environment, which has the image's supervisor delete computerd's store (`COMPUTERD_DB`, with its `-wal` and `-shm`) before computerd starts, since the Build's store holds another Workspace's sync positions; the variable is asked for again on a reconnect to that Container, so computer adopts it rather than relaunching. A Workspace started from a Build takes its own install snapshot after its bootstrap. A Build that the Container did not start from (refused, or the health probe failed and computer restarted it) is remembered as failed in that Workspace (the last ten), which starts from the image, and the Workspace's own snapshot is never forgotten for it. A Workspace that has a snapshot of its own never uses a Build, so a Workspace made before a Build reaches it only after _Restart container_. **Secrets:** the main Worker asks the Registry for the Environment's Secrets (`environmentSecrets`) only when it asks for a Build, and hands them with the request (`startBuild`), apart from the request the Build object stores; the object keeps them sealed as any Workspace DO does (see _Secrets_). The Environment's Setup Script and each Repo's get those marked for the Build, each as `$PI_SECRET_<NAME>` (the variable a Session's commands get it as), in their environment only (`buildSecretEnvironment`): not the clone, the clean-up or any other step, not the settings the object hands itself (`buildContainerSettings`, stored in the clear), and never in a script's text. Every Workspace made from the Build shares its Snapshot, so the others never reach it. Since the clean-up deletes the Setup Scripts' records, a Workspace made from the Build runs its Setup Scripts again: they get the same marked Secrets there, from the Workspace DO's copy (see _Setup Scripts_). The scan before its snapshot searches for every one of the Environment's Secrets, marked or not, and a Build object that cannot open its copy fails the Build with that reason. **Shown** on each Environment's card on the Environments page (`listBuilds`: none, building since, built at, or failed with its reason, and what new Workspaces start from meanwhile), with _Rebuild_ (`rebuildEnvironment`), which asks for a Build now even when the last good one is current. Builds are off under `alchemy dev`: a request fails at once, saying so. Not verified on a deployed stage: a Container restored from another Durable Object's snapshot, the store reset reaching the supervisor through the launch's environment (computer's `ContainerBackend` passes `env` through `ContainerLaunchSpec`), the clean-up stopping a Docker daemon a Setup Script started before the snapshot, how large a Build's snapshot gets and how long it takes, and how much of a new Workspace's first start it saves.
  - **What is in it:** the Container's disk only. `/workspace` is a FUSE mount the snapshot does not hold, but computerd's store behind it is on the disk (`COMPUTERD_DB=/var/lib/computerd/state.db` in the image), with the synced files' contents and its sync positions, so the Workspace's files are in the snapshot through it and a restored Container is sent only what changed since the snapshot. computer resends every file when the store is behind the Workspace DO's push position (`reconcileWatermarks`), as for a Container that died after its install snapshot; with computerd's default in-memory store every launch was that resend, which for a Workspace of ~96k files held the Workspace DO for minutes (prod, 2026-10-22). computer's `ignore` paths are held by computerd on the Container's disk (`/tmp/workspace/...`), so `node_modules`, `.venv` and caches are in the snapshot and come back with it, while the Worker Shell and the Workspace DO still never see them.
  - **No secrets:** the bootstrap writes no token (git's credential helper reads `$GITHUB_TOKEN` from the environment, and `~/.gitconfig` holds only that helper), and a command that does write one (`~/.netrc`, a copied `.env`) must not reach a snapshot: before each snapshot a process of the Container's own (`ctx.container.exec`, so no connection to computerd is needed in the idle alarm) searches every top-level directory but `/proc`, `/sys`, `/dev`, `/run` and `/workspace` (the mount; the Workspace's files are searched in computerd's store) for `CLOUDPID_GITHUB_TOKEN` as it is and as base64 of it and of `x-access-token:<token>`, and for each Secret kept for the Environment as it is and as base64 of its UTF-8 (`scanPatterns`: of a value of several lines, its longest line, a key's body rather than a header any file holds; of a long one, 256 characters from its middle; a value under 8 characters is not searched for, as it would be found by chance). The patterns go in its environment, split over variables of 64 KiB at most, never its command line. It skips directories named `.pnpm-store` or `.pnpm` (pnpm's store, `/root/.pnpm-store`, with the global virtual store in it, `v11/links`, and the project virtual store in `node_modules`), which hold only the packages pnpm installed and are most of the disk after an install (see _Known risks_); the rest of `node_modules`, such as `.cache`, is searched, and a token a command or an install script writes into those two is not found. A hit skips the snapshot (the earlier one stays, and the warning names the file, never the value), a token in a file of the Workspace included, since computerd's store holds it; a scan that cannot run or finish in 30 s skips it too. A value written in another encoding is not found. The Workspace DO searches for the copy of the Environment's Secrets it holds (see _Secrets_), and takes no snapshot while it cannot open that copy. `secret_ask` values are not searched for (the idle alarm has no access to a Session's held Secrets): one a command wrote to the Container's disk stays in a snapshot for up to 30 days (see _Secrets_).
  - **Time:** a snapshot, its scan included, is given up on after 120 s (`SNAPSHOT_TIMEOUT_MS`), after the install and on idle stop alike. The commands that waited for the bootstrap are held for the install's meanwhile (the Setup Scripts before it do not count), so a snapshot that takes long delays the first command by as long, up to 120 s; that is kept so that nothing else writes while it is taken (a command could write the token after the scan, or a file the snapshot half holds). It was 60 s for the install (#156), which lost snapshots that needed longer: `snapshotContainer` runs on after the limit, with its handle dropped. Past 120 s the snapshot is given up on and not recorded, the commands run, and `installPending` stays set, so the idle stop's snapshot or the next bootstrap's tries again.
  - **A restore that does not come up** falls back to the image. A start the platform rejects outright for the snapshot (an expired or unknown handle) is retried once from the image, and the snapshot is forgotten. A Container that fails its health probe (computer's budget is 60 s in all, 30 s for each of the launch and its one restart) falls to computer's restart, which `ContainerLaunch` turns into a launch from the image; the snapshot is forgotten when the Container died, and kept when it was merely slow (the new Container's own snapshot replaces it once it is taken). A snapshot larger than the disk of a smaller size cannot be restored there, and takes the same way out.
  - **Measured** (see _Known risks_; on `standard-2`, the default size then): a cold Container with the base `mise.toml` (all preinstalled, so no install snapshot) answers its first command in about 2.5 s on a host with the image (17 s on one without), a restored one in under 2.5 s; with versions the image does not have (Node 22 and Python 3.13), about 28–30 s with the install snapshot against 2 s.
- **Idle stop:** computer never stops the Container it starts (its WebSocket, heartbeat timer and container monitor keep the Workspace DO alive, and the platform's inactivity timeout never fires), so the Workspace DO stops it: every connect, push and pull on the Container records a use, and a Durable Object alarm snapshots the Container's disk and destroys it once the Workspace's idle time has passed without one (`apps/server/src/workspace/idle.ts`). A command still running on the Container counts as use: the Workspace stub the DO hands out (`tracked.ts`) holds the command until its client disposes the exec handle, and the alarm waits again while any is held. A bootstrap also holds the Container itself while it runs (`ToolchainBackend`'s `activity`), Setup Scripts included, whether or not a command still waits for it: a Setup Script can run for 15 minutes, past the idle time, after the command that waited was killed. The idle stop counts holds, so the command's and the bootstrap's own nest and each ends its own. The idle time is the one the Container was launched with. The first use of a Container comes before its launch is recorded, so the alarm is armed with the default (2 minutes) and brought forward once the real time is known; a Workspace whose own idle time is longer finds at that first alarm that the Container is not yet due and waits again for the rest (`IdleStop.alarm`). A snapshot takes seconds and the alarm holds no input gate, so a command may arrive during it and connect to the Container: after the snapshot the alarm checks that the Container is still idle (no use and no running command since it decided), and keeps the Container if not, leaving the alarm the use re-armed to take over. An idle stop that stops a running Container forgets the size the agent's resize recorded (`ContainerResizes.stopIdle`, `apps/server/src/workspace/resize.ts`), so the launch after it is on the Environment's size again; an alarm that finds no Container running (one a resize or `container_restart` stopped since its last use) keeps it for the Container the next command starts. The alarm is the Workspace DO's only one, which a spare Workspace's preparation shares (see _Workspace and execution_ → _Spare Workspace_).
- **Exit reports:** the platform keeps a Container's own output (computerd's stdout and stderr) where no API reads it, and computer logs only `workspace.container.exited` with the exit status, so a Container that dies mid-command left nothing in the Workers logs to say why (prod saw two `exit code: 1` deaths on 2026-10-21/22, each after commands hung for minutes). The image's entrypoint is therefore a supervisor (`apps/sandbox-image/image/supervise`, bash): it runs computerd, passes its output through to the Container's log as before, keeps its last 200 lines (at most 32 KB) in memory, never on the disk a snapshot captures, replacing the payload of each `data:<mime>;base64,<payload>` run of 64 characters or more with `[base64 dropped]` in that kept copy (computerd's log lines carried file contents that way, hundreds of KB a line, which filled the 32 KB and pushed out the crash `uncaughtException: Error: log <id>: append after exit` and its stack; a line-buffered `sed -u -E` between `tee` and `tail` does it, so a line of any size is handled as it comes, one cut off by the end of its line included, and the Container's own log keeps the full output), and forwards SIGTERM and SIGINT to it. When computerd exits without having been signalled through the supervisor, the supervisor posts its status (128 + the signal for one a signal killed), how long it ran and those lines to `http://cloudpid.internal/container-exit` (bash's `/dev/tcp`, so it needs no HTTP client; five seconds at most) and then exits with computerd's status. The Workspace DO intercepts that host for each Container it launches, right after computer intercepts `computer.internal` and again after a restart (`withExitReports`, `exit-report.ts`); `ContainerExitReports` (`worker.ts`) logs the report as `workspace.container.output` with the Workspace DO's id (also the Container instance's id in the dashboard), with the GitHub token taken out, then the Environment's kept Secrets: it asks the Workspace DO the report names (`redactExitReport`, through the Workspaces Worker's own `WORKSPACES` binding), which takes each out of the lines as its Secret Reference with the copy it keeps sealed (see _Agent capabilities_ → _Secrets_). When that copy does not open or the DO cannot be reached, the report is logged with its status and uptime only, and `withheld` says why its lines are not. Anything in the Container can post a report, so it is only ever logged. computer's own `computer.internal` proxy forwards only its `/api` and `/health`, which is why the report has a host of its own. A Container the platform kills outright (out of memory, a host lost) takes the supervisor with it and sends none; the exit status then still says how it ended. The memory guard's lines are among computerd's (next).
- **Memory guard:** the Container has no swap, and when its commands use up the memory (this repo's `turbo run typecheck lint test` at Turborepo's default concurrency: from 0.3 GB to 5.9 GB of `custom-2`'s 6 GiB in 100 s, 2026-10-23) the kernel evicts the pages of computerd's own program long before its OOM killer acts. computerd, which serves `/workspace` and runs every command, then stalls on the disk, and every command hangs, `echo` included, until the Container is restarted. The image's supervisor therefore runs a memory guard beside computerd (`apps/sandbox-image/image/cloudpid-memory-guard`): earlyoom (Ubuntu's 1.7), which stops the process with the highest OOM score (in effect the largest) with SIGTERM once the memory available is below the lower of 15% and 1 GiB, and with SIGKILL below the lower of 8% and 512 MiB (`MEMORY_GUARD_PERCENT` and `MEMORY_GUARD_KIB` in `apps/sandbox-image/src/memory-guard.ts`; on `custom-2` about 950 MB and 510 MB, against about 400 MB where computerd's pages were being evicted; on the default `custom-1` about 480 MB and 260 MB, not yet measured there, so a SIGKILL may come after computerd has started to stall). It never stops computerd, the supervisor or the guard (`--avoid`, by the 15 characters of a name the kernel keeps); a service a Start Script started, Docker's daemon included, is stopped like any process. Its lines go where computerd's do: the Container's log, and the lines of an exit report. **The note:** a command whose process was stopped would only show the process dying (status 143 or 137, or a tool's own error), so the guard reads earlyoom's announcement of each stop (`sending SIGTERM to process <pid> uid <uid> "<name>": badness <n>, VmRSS <n> MiB`, printed before the signal; earlyoom's own hook, `-N`, runs only once the process has exited, by when its command has often ended) and leaves a note for it in `/run/cloudpid-memory-guard` (`MEMORY_NOTES_DIRECTORY`): a file named by the time in microseconds, written beside its name and renamed into place. A process sent SIGTERM and then SIGKILL gets one note. Every command's environment carries `BASH_ENV` (`toolchainEnv`, so an Environment's variable may not have the name), which the command's `exec bash -c` reads before the command: `/usr/local/share/cloudpid/command.bash` (`image/command.bash`) sets an EXIT trap that prints on stderr, when the command ends, each note left since it started, and unsets `BASH_ENV`, so a bash the command starts prints none again. The command's text is unchanged, so its line numbers are its own. The value is `$([ -r <file> ] && echo <file>)`, which bash expands, so a Container still running an older image after a deploy reads nothing instead of printing at each command that the file is missing. The note names the process, its pid and its memory, says when, and suggests running less at once (Turborepo's `--concurrency`, Vitest's `--maxWorkers`) or restarting the Container at a larger size with `container_resize` (see _Resize by the agent_). Every command running when a process is stopped gets the note, not only the one the process belonged to. Not covered: a command that sets its own EXIT trap or `exec`s another program gets no note, one that ends within milliseconds of the stop may miss it, and bash skips `BASH_ENV` when its stdin is a socket and `SHLVL` is unset (it takes itself for a command rshd started), which computerd's `/dev/null` stdin never is. The supervisor removes the notes before it starts the guard and computerd, since a snapshot may keep `/run`. **Measured** (2026-10-23, `custom-2`, a Container with the guard and `command.bash` installed by hand): this repo's `turbo run typecheck lint test --force`, which had frozen the Container without the guard (and, another time, ended only because a test timed out under the load and Turborepo stopped the run), brought the memory available down to 692 MB; the guard stopped two `tsc` processes (1.16 GB and 0.93 GB), the run failed with `@cloudpid/server#typecheck` exiting 137 and both notes in its output, and the Container answered throughout. A Python process growing by 500 MB/s was stopped at 5.1 GB with 855 MB still available, and its command ended with the note.
- **Restart by the agent:** a Container can stop answering while the Workspace DO still does (computerd starved of memory the memory guard did not free in time, or wedged): every command then hangs until its timeout, `echo` included, and no command can fix it. `container_restart` (formerly `restart_container`, renamed with no alias under ADR-0019's `container_*` naming; a saved `tools.offered` entry that names the old name is read and saved as the new one, and is not reported as a problem: `withRenamedTools`, `packages/config/src/settings.ts`; the `container` extension, `packages/extensions/src/container.ts`; deferred, so the model finds it with `tool_search`, and the `bash` tool's description points to it) stops the Session's Workspace's Container at once through its Workspace DO (`stopContainer`, which has the platform destroy the Container, so it works whatever computerd is doing, and runs no command), without a snapshot of its own. It takes a `reason` (1 to 500 characters), which the transcript shows as the call's summary, and asks no one: the agent restarts when it judges the Container hung. By default the Workspace keeps its Snapshot, so the next command starts a Container from it, as after an idle stop, with the Start Scripts run again, on the size the agent's resize recorded if there is one (with `fresh` too; the owner's _Restart container_ forgets it, so the owner's restart starts on the Environment's size); with `fresh` the Snapshot is forgotten first, as the owner's _Restart container_ does (GLOSSARY.md → Container restart), for when a restart from the Snapshot did not help. Commands running in the Container end, other Sessions' in the Workspace too. The tool is `replay: "unsafe"` (a rerun after an eviction would stop the Container the next command started) and sequential. It does not ready the Workspace, and starts no Container.
- **Resize by the agent** (GLOSSARY.md → Container resize, ADR-0019): `container_resize({ size, reason })` (the `container` extension; deferred) restarts the Session's Workspace's Container at another size, for that Container alone, until its idle stop: the agent's way to more memory when the memory guard stops its processes, and back to a smaller size once that work is done. `size` is an `INSTANCE_TYPES` name (the description lists each with its resources, by memory), `reason` is 1 to 500 characters, shown as the call's summary as `container_restart`'s is, and it asks no one. Through the Workspace DO's `resizeContainer` (`ContainerResizes`, `apps/server/src/workspace/resize.ts`), which holds the Container from the idle stop meanwhile: a `size` above the Environment's size limit (`maxInstance`, as the Workspace DO's copy of the settings has it) is refused, naming the limit and that the owner can raise it, and nothing is stopped. Otherwise a running Container is snapshotted as at the idle stop (`ContainerLaunch.snapshot`, labelled `resize`; the scan for the token and the Environment's Secrets included) and destroyed, whatever runs on it: commands running there end, other Sessions' in the Workspace too, and the result says so. A snapshot that could not be taken does not stop the resize, and the result says the next Container starts from the last one. The size is recorded in the Workspace DO's storage (`cloudpid:container-resize`) before the stop, as a one-launch override, so the next launch, whichever command starts it, is on that size and restores the snapshot, `node_modules` and the other Container-only paths included. With no Container running the size is only recorded. A resize to the Environment's own size records nothing (it forgets the override), and one to the size the running Container already has does not stop it and says so. The idle stop forgets the override (see _Idle stop_; it is forgotten just before the Container is destroyed, so a resize that lands during the stop is kept), and so does the owner's _Restart container_; `container_restart` keeps it. A snapshot that cannot be restored on the target size (larger than its disk) takes the fallback to the image (see _Snapshots_), and the result warns of that when the target's disk is smaller than the current size's. The Session's Container cost already prices each launch at its own size, so a resize needs nothing there. The tool is `replay: "unsafe"` and sequential, as `container_restart` is, and subagents have it too. It does not ready the Workspace: the settings are the Environment's as the Workspace DO last had them, handed over at each readying (at most a minute old while the Session works). Not yet verified on a deployed stage: a resize of a running Container, then a command that launches on the new size from that snapshot with `node_modules` restored.
- **Egress:** unrestricted direct egress in v1, and not logged. A per-Workspace allowlist, and logging with it, come later.
- **Docker** (measured in [#170](https://github.com/ian-pascoe/cloudpid/issues/170) on a deployed Container): the image has `docker.io`, `docker-compose-v2` and `docker-buildx`, which run there with the overlay2 driver and cgroup v2, for a Start Script to bring up services (databases, dev dependencies) that a Snapshot cannot hold. Nothing runs systemd, so nothing starts the daemon on its own: `cloudpid-dockerd` (`apps/sandbox-image/image/cloudpid-dockerd`) does nothing when `docker info` answers, and otherwise starts `dockerd` detached (`setsid nohup`, its output in `/var/log/dockerd.log`) and waits up to 60 s for it to answer, under a lock so two calls at once start one daemon; arguments go on to `dockerd`. The Container's `/proc/sys` is read-only, so a default `dockerd` fails while it enables IP forwarding: the image's `/etc/docker/daemon.json` turns off `iptables`, `ip6tables` and `ip-forward`, and the helper sets `DOCKER_ALLOW_IPV6_ON_IPV4_INTERFACE=1`. Default compose files then work: bridge networks, with published ports reachable on the Workspace's localhost through Docker's userland proxy. Bridge-networked containers get no internet, since nothing forwards their packets; `network_mode: host` does. Images and volumes are in `/var/lib/docker`, on the Container's disk, so a Snapshot carries them. Postgres through compose was ready 10 s after `up`, the image pull included. Custom images for the Container itself are not offered ([ADR-0016](adr/0016-environments-and-a-container-per-workspace.md)).

### Concurrency

Sessions in one Workspace share its file tree, Container, processes and ports, as local pi sessions share a directory. Each new Session gets a new Workspace by default, with clones, a branch and a Container of its own ([ADR-0016](adr/0016-environments-and-a-container-per-workspace.md), which supersedes [ADR-0015](adr/0015-workspaces-are-worktrees-on-a-shared-machine.md)); starting a Session in an existing Workspace shares it. Subagents share their parent's Workspace.

### Git

- Clone and push with mise-installed `git` and `gh` in the Container (`conda:git` from conda-forge, since mise has no git in its registry otherwise; `gh` from aqua).
- Authentication comes from a GitHub token, the deploy-time secret `CLOUDPID_GITHUB_TOKEN` (`Config.Redacted`, bound to the Workspaces Worker as a secret and read by the Workspace DO). Each Container command gets it as `GH_TOKEN` and `GITHUB_TOKEN`, which is all `gh` needs. The bootstrap also points git's credential helper for `https://github.com` at `$GITHUB_TOKEN`, read when git asks, so no host but github.com is offered it and no file holds it (the helper is in the Container's `~/.gitconfig`, not in `/workspace`). It is not logged.
- Commits are by `CLOUDPID_GIT_NAME` / `CLOUDPID_GIT_EMAIL` (deploy-time variables; defaults `cloudpid` and the owner's email), set as the Container's global git identity unless one is already set. A repo's own `user.name` and `user.email` win.

### Tool discovery

The model is offered a small set of tools; every other tool is _deferred_ (`GLOSSARY.md` → Offered tool, Deferred tool), the exposure of the owner's local pi (codemode first, a small offered set).

- **`tool_search`** is pi-durable's tool (`@earendil-works/pi-durable/tool-search`): BM25 over the names, descriptions, and parameters of the conversation's deferred tools, whose matches are loaded with `control.addTools`. That writes the conversation's `modelTools`, so loaded tools stay offered on that branch, also after a compaction. It is not callable from scripts, which have `searchTools()`.
- **The offered set** is the settings' `tools.offered`: tool names or patterns (`*` matches any run of characters), snake_case, edited on the settings page (an entry that is not one is refused, and a saved list with a bad entry is dropped whole, with the other overrides kept). The default is `read`, `write`, `edit`, `bash`, `ls`, `find`, `grep`, `codemode`, `tool_search`, the context tools (`context_notes`, `context_history`, `context_rollover`), and `secret_ask`. The first nine are the owner's local default tools (pi's own `read`, `bash`, `edit`, `write`, and `defaultTools`: `codemode`, `find`, `grep`, `ls`, `tool_search`; `fffind` and `ffgrep` are not ported). The context tools stay offered because Rollover depends on them (the Rollover request tells the model to call `context_rollover`). `secret_ask` stays offered because the `secrets` prompt section, which tells the model to call it instead of asking the owner to paste a credential, is gated on the secret tools; that section is also rendered while they are all deferred (with a line to load them), so the guidance never depends on a search. `tool_search` and `context_rollover` are offered whatever the settings say: without the first the model cannot reach a deferred tool, and without the second the compaction hook finds no `context_rollover` and silently falls back to pi-durable's own compaction. The order of `tools.offered` does not matter: the tools keep registry order, followed by the ones loaded.
- **Deferred by default:** `web_search`, `web_fetch`, `browser`, `browser_handoff`, `secret_list`, `secret_forget`, `todo`, `container_restart`, `container_resize`, the six subagent tools (`subagent`, `agent_message`, `subagent_wait`, `subagent_status`, `subagent_cancel`, `subagent_delete`), and the `environment_*` tools, and so any tool a later extension adds. A prompt section gated on its tool being offered is hidden until the tool is loaded: `subagent_roles` (the role hints, shown once `subagent` is loaded) and `todo`'s guideline; the `deferred_tools` section names the tools, so the model knows to search.
- **Mechanism:** the `tool-search` extension (`@cloudpid/extensions/tool-search`) wraps every tool of the other extensions (`wraps`) and sets `deferred` when its offered set does not name the tool. Wraps are pure, as pi-durable requires, so the extension is built from one offered set, and when the Session reads settings that changed it (`SessionHostOptions.reload`) it installs the extension again over the earlier one ("an extension is the unit of reload"): pi-durable applies that to the next phase it starts, never to one under way. A model's tool call spans two phases (the generation, then the call), so a read that lands between them can defer a tool the request offered: that call fails as unavailable, which is rare, and the model can load the tool with `tool_search` and call it again. A change reaches the next request of every conversation, new and idle ones as the other settings do, and a tool that was loaded stays offered. The `deferred_tools` prompt section names every tool the settings defer, in name order, loaded or not, so loading a tool does not change it and the provider's prompt cache keeps hitting; it is left out for an agent that has no `tool_search`. Up to 40 are named on one line; past that, a line per family of two or more tools of one prefix (`- environment_*: environment_get, …`, the prefix being the name up to its first `_`), then the tools alone in theirs on a last line (`- others: …`).
- **Scripts:** a deferred tool is still enabled, so nested calls resolve it and `codemode` scripts call it without loading it; its `tools.<name>` declaration is not in the `codemode` section's inline list, and scripts find it with `searchTools()`, `describeTool()`, and `describeNamespace()`.

### Subagents

The tool surface and semantics stay as they are today:

- Canonical IDs such as `agent-1` and `agent-1.reviewer` (a leading `root.` is accepted; `root` and `parent` are reserved), plus tombstones and a depth cap.
- Model roles.
- `read`/`modify` toolset presets under a capability ceiling.
- `session_context`: `omit`, `inherit` (the parent's conversation quoted before the task), or `compact` (a summary of it, made by the `small` role's model, or the child's own when no `small` role is configured).
- Wait events: `turn`, `message`, `timeout`, and `steered`. One open wait per caller and child; a second is refused.

They are rebuilt on pi-durable primitives, following its example 23 (`@cloudpid/extensions/subagents`):

- Children are conversations owned by a background anchor task.
- Each input to a child is a turn, carried by a background reporter task in its parent's conversation. A Session document records the agents, their recent turns, tombstones, and open waits, and one commit decides each delivery.
- A settled turn's answer goes to a `subagent_wait` blocked on it. Otherwise it is held (`delivery: "pending"`) until the parent is idle, so a later `subagent_wait` in the parent's run can still claim it, and then reported as a follow-up, deduplicated by `requestId`. The rule is the same for every parent: the root gets the report as follow-up input, and a parent that is itself a subagent gets it as a new turn, whose answer is reported further up. Inputs steered into one run end in one answer, which is delivered once; the other turns are `duplicate`.
- **Stop.** Stop aborts one conversation, never the agents below it: a subagent's work is background work (its anchor is a background task), so the root's Stop leaves it running, and it reports as usual. **Stop all** (`abort` with `subagents: true`, offered beside Stop while a subagent or background task is live, or while the run goes on with any subagent below it (an idle one can have a report held for that run), and in the Tasks Pane) aborts the conversation and every subagent below it with `background: true`, which also aborts their reporters, so the reports held for the parent are dropped (`delivery: "none"`) and nothing starts a new run. A report that is already held when a plain Stop lands is still delivered once the root is idle, which starts a new run: pi-minimal-subagents holds it until the next run, but a reporter that waits for a run that may never come would stay live (and keep the Session's alarm armed) indefinitely, so the rule stays one for every parent, and Stop all is how the owner silences everything.
- **The owner and a subagent.** The owner may submit to and abort a live subagent's conversation from its thread. The Session checks that the conversation is the root's or a live subagent's (the Subagents document maps it; a deleted agent's conversation, or any other, is refused). Input to a subagent is a plain user message: `whenBusy: "steer"` joins its run at the next boundary, `"followUp"` waits for its next run, as for the root. It is not a turn: nothing waits on its answer, so the answer is not reported to the parent, and the parent's `subagent_wait` and reports are untouched. An input the owner steers into a run that also carries a turn of the parent ends in one answer, which the turn reports as usual. Aborting a subagent ends its running turn `aborted` (nothing reported), and keeps the agent for more input.
- `subagent_wait` is a durable task that sleeps until its deadline (`TaskRuntime.sleep`); a rerun of the call after an eviction finds it.
- A child's tools are exactly its grant (`AgentState.tools`): ordinary tools within its caller's, never `context_rollover` (a Handoff would end the child's run without the turn's answer), plus all six coordinator tools when it was launched with `delegation: "fanout"` below the depth cap, or only `agent_message` otherwise.
- The roles come from the settings' `roles`; the depth cap and toolsets from `extensions.subagents` (`maxSubagentDepth`, default 2; `baseToolset`, `readToolset`, `modifyToolset`).
- **A child's offered tools** (what its model is offered; the rest of its grant is deferred) are not the root's loaded set. A child given a preset or an exact list is offered every tool of it, deferred or not, because the spawner or the owner's toolset settings named them (`todo`, in the default `baseToolset`, is offered to every such child); its coordinator tools are always offered. A child that inherits its caller's tools (`tools` omitted) is offered what the settings offer every conversation among them and has `tool_search`, which it inherits, for the rest; when the grant has no `tool_search` (the caller is a preset child), nothing could load a deferred tool, so the whole grant is offered and the `deferred_tools` section is left out. Tools loaded by the parent do not carry over.

### Context management

pi-context-management's `context_notes`, `context_history`, and `context_rollover` (`@cloudpid/extensions/context`), with its parameters and limits:

- **Notes** are a conversation document (`defineDoc`, `fork: "current"`), which also keeps the last saved Handoff. A Handoff does not touch documents, so Notes outlive it.
- **History** reads entries from storage, also those before a Handoff or compaction; Context Windows start at each head marker (`pi.reset`, `pi.compaction`). Lineage scope covers the conversations of the agent's ancestors and descendants in the Session's subagents document; references are `context:<conversationId>:<entryId>` and `context:<conversationId>:note:<name>`.
- `context_rollover` must be the only call of its round and is not callable from scripts. It returns `control: { handoff }` with the Handoff and a Note Index; pi-durable applies it after the whole round, so the Handoff never splits a tool batch. It also queues a follow-up, so the task continues in the new context, unless the run's only inputs are Rollover requests, as when one is placed after the task's final answer: then the run stops at the Handoff.
- A `CompactionTask` `beforeCompact` hook, in conversations that offer `context_rollover`, turns a background threshold compaction (`backgroundTokens` below the blocking threshold) into a prepare-then-rollover turn: it declines, which blocks nothing, and while a run is live steers a Rollover request into it, once per Context Window. A blocking threshold compaction and an overflow compaction are the Emergency Rollover, because declining a blocking one would send a request without pi-durable's overflow recovery: the summary is the last saved Handoff and the Note Index, on pi-durable's cut, which keeps tool calls with their results. With `backgroundTokens: 0` every Rollover is an Emergency Rollover. A manual compaction keeps pi-durable's summary.
- The transcript shows Handoffs, compaction summaries, and Rollover requests as notices; an extension's input entry asks for a notice with a `notice` title in its data. A Rollover or a compaction does not take the earlier Context Windows off the transcript: what a client watched stays above the notice, and a snapshot that starts with a head marker leaves out the History before the marker's head, which the top of the thread offers as "Show earlier messages", a `history` page at a time (see _Client and protocol_).
- The owner's `/rollover [focus]` steers the Rollover request into the conversation, with the focus (at most 2,000 characters) appended as Handoff-only instructions, as local pi-context-management's command does; its request ID marks it as a Rollover request, so one made while idle stops at the Handoff. `/compact [focus]` is pi-durable's manual compaction, the focus as the summary's additional focus. Both are Session Slash commands (see _Client and protocol_ → Slash commands).
- Not ported: Idle Rollover, the `/context` command, and the Rollover Tail (`tailTokens`): a Handoff starts the context from the Handoff alone.

### Todo

pi-todo's `todo` tool (`@cloudpid/extensions/todo`): `list`, `add`, `update`, `remove`, `clear`, its parameters, and its structured output (`structuredOutputSchema`, so a script's `todo` call returns `{ action, tasks | task | id | cleared }`). The owner's `/todo clear` is a Session Slash command (see _Client and protocol_ → Slash commands) that clears the list as the tool's `clear` does. Not ported: the TUI widget and renderers, and the troubleshooting Skill.

- The list is a conversation document (`defineDoc`, `fork: "current"`): `nextId`, a `rev` that counts its changes, and the Todo Items (the tool, the document and the socket call them "Tasks", as pi-todo does; background tasks are another thing). Every conversation has its own, a subagent's included (`todo` is in the default `baseToolset`, so a child has it whatever preset it was given), and a Handoff or compaction does not touch it. A call reads and changes it in one commit, so a batch `add` or `update` with one bad entry (an empty title, an unknown or repeated ID) changes nothing and spends no ID. The list holds at most 200 Todo Items, 300 characters of title and 2,000 of description each, and 20,000 characters and 500 lines in all as the model reads it, because every result shows the whole list (pi-durable keeps at most 50 KB and 2,000 lines of a result) and every watching client is sent it whole. The tool accepts `null` for a field the model leaves out, as pi-todo's `acceptNullForOptionalArguments` does.
- Each result's text ends with the whole list, and its `details.todoRev` is the `rev` it shows. pi-todo keeps hidden snapshots among the messages, each at a fixed place with fixed text, so the provider's prompt cache (a breakpoint on the last message) keeps hitting; here the context needs the list back in three cases, each handled at a place that does not move or, for the last, at the end of the request:
  - A script's nested `todo` calls leave no result in the context. The document remembers the call (`changedBy`) and a `ToolTask` `afterTool` hook appends the list to that call's result, with `details.todoRev`, so it is committed with the result. It does so only when the result and the list fit pi-durable's limits (which keep the head of a result, after the hook); a result too long to show the list whole does not claim to, and the third case applies.
  - A Handoff or compaction took the `todo` results out. A `GenerationTask` `beforeRequest` hook finds that the Context Window holds no `todo` result and puts the list at the end of the window's first message (the Handoff or summary, which is a user message, so no user message follows another), after a header saying it is the extension's note. The window is told by that message's timestamp, and the text is recorded in the document (`shown`) at the window's first request, so every later request of the window sends the same bytes however the list changes in between. A recorded text is never rewritten, and a window that holds a `todo` result gets none. It asks the agent to reconcile unfinished Todo Items when the context holds no `todo` result at all, and sends nothing for a list that was never used.
  - The list changed and no result in the window shows it (the last `todoRev` in the request, or the recorded text's, is not the document's `rev`): a Stop during a script after its nested call, an interrupted call, parallel scripts whose results finish out of order, a result too long for the list. Rare, so the request gets a short note at the end of its last message, asking the model to call `todo` with `action: "list"`; nothing before it changes, so the prompt cache keeps its prefix, and the note goes when the model calls `todo`, as that result shows the list.
    Known limitation: `fork: "current"` gives a fork the source's latest list, not the list as of the fork point as pi-todo's branch-following snapshots do. A fork's context may then be behind the list or ahead of it; the note above covers the first case. A Session branch is such a fork (see _Client and protocol_ → _Session tree_), and so is what a Fork or Clone copies: both take the list as it is when they are made.
    A `todo` section holds the tool's guideline.
- The web app shows the list live: `watch` of a conversation also streams `todos` messages (see _Client and protocol_), which the Tasks Pane shows for the root and a subagent's thread for that subagent.

### Secrets

| Kind        | Holds                                                                                                                                            | Storage and use                                                                                                                                                                                                                                                                                        |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Deploy-time | Commissary API key for the model proxy, 1Password service-account token (v2), VAPID keys. In v1 also the GitHub token and the Exa/Parallel keys. | Read with `Config.Redacted` in `infra/` and bound as Worker secrets                                                                                                                                                                                                                                    |
| Runtime     | Values entered through `secret_ask`, which opens a masked form in the UI                                                                         | Encrypted with AES-GCM in the Session DO under a key held as a Worker secret. Referenced by pi-secret's double-brace `secret:NAME` placeholder or `$PI_SECRET_*`. Injected into exec env only at call time. Redacted by an `afterTool` hook and at the Session's model seam. Expires after 15 minutes. |
| Environment | Values the owner keeps for one Environment or for every Environment on the Environments page                                                     | Sealed with AES-GCM in the Registry DO (migration 14), bound to their scope and name. Used, injected and redacted as runtime ones are, in every Session of the Environment, and never expire. One marked for the Build also reaches every Setup Script of the Environment as `$PI_SECRET_*`.           |

`packages/extensions/src/secrets` ports pi-secret (`NOTICE.md`). The key is `SECRETS_ENCRYPTION_KEY`, from which HKDF derives one AES-GCM key per Session; each record is bound to its name and expiry. A `secret_ask` waits on a durable request: the Session sends the waiting requests to every client (`secret_requests`), the owner answers in a masked form (`secret_answer`), and the request and answer survive eviction, so a call cut off by one finds its answer when it reruns. Values never enter durable state: pi-durable records the arguments a `beforeTool` hook returns, so that hook only blocks calls naming a Secret the Session does not hold, and wraps of the tools that use Secrets (coding tools, Files, `web_fetch`; never `web_search`, whose queries leave for a search provider) resolve placeholders, inject `$PI_SECRET_*` into their commands' environment, and redact streamed output and the command's Result Spill (raw output in the Workspace's `/workspace/.cloudpid/tmp`, which both backends see) inside `execute`. Every held Secret is in every wrapped command's environment, so a process left running in the background keeps it past expiry and `secret_forget`. Provider requests are scrubbed at the Session's `Models` (`scrubbingModels`), so generations, compaction summaries, and a subagent's `compact` summary are all covered; a message is indexed by an unkeyed SHA-256 of its JSON, so its scrubbed form survives eviction, expiry, and a key change. Tools whose arguments become conversation content (code mode, subagents, Notes, Handoffs) are not wrapped; the calls they lead to resolve their own references. Redaction covers each value's common encodings. `secret_ask` and `secret_forget` are parent-only; children read and use the parent's Secrets. An alarm deletes each Secret when it expires, and a request whose call is gone (abandoned while the object was evicted) is withdrawn once the Session is idle. A value a command writes to a file outlives that expiry: under `/workspace` it is in the Workspace DO's storage, and on the Container's disk it is in the next snapshot, kept up to 30 days (the scan before a snapshot searches for the GitHub token and the Environment's Secrets, not for these: see _Container and Toolchains_ → _Snapshots_).

**Environment Secrets** ([ADR-0016](adr/0016-environments-and-a-container-per-workspace.md)) are kept by the owner for one Environment or for every Environment (`listEnvironmentSecrets`, `setEnvironmentSecret`, `setEnvironmentSecretBuild`, `deleteEnvironmentSecret`; see _Workspace and execution_ → _Environments from the UI_). A name is one `secret_ask` takes (`SECRET_NAME`, at most 128 characters); a value is not empty, holds no NUL and is at most 32 KiB of UTF-8; a scope keeps at most 100. The main Worker passes the value to the Registry DO, which seals it (AES-GCM under a key HKDF derives from `SECRETS_ENCRYPTION_KEY` for the Registry, bound to the scope, an Environment's id or `*`, and the name, so a row moved to another scope or name does not open) and stores only the ciphertext (`environment_secrets`). No RPC answers a value, an error names the problem and never the value, and nothing logs one. An Environment's own Secret wins over one of the same name kept for every Environment. Values leave the Registry DO only over Durable Object RPC within the deployment, opened for:

- **A Session** (`sessionSecrets`, by the Session's Environment), which holds them in memory only, never in its storage, and asks again at its first use of Secrets 30 s after the last answer (5 s after a failure, keeping what it held meanwhile). It uses them as held `secret_ask` ones: Secret References, `$PI_SECRET_*` in its wrapped commands, redaction of output and of provider requests. They never expire; `secret_list` shows each as kept for this Environment or for every Environment, `secret_forget` refuses them (the owner deletes one on the Environments page), and a `secret_ask` value of the same name wins while it is held. A value deleted or replaced is still redacted by the Session until the object is evicted. Before using a set, the Session hands it to its Workspace DO (`updateEnvironmentSecrets`), and keeps the set it held when that fails, so no value reaches a command before the Workspace searches for it.
- **A Workspace's set-up** (`getWorkspaceSetup`, `upkeepSpares`): the readying hands them to the Workspace DO, and a spare's request carries them (`prepareSpare` keeps them apart from the set-up it stores).
- **A Build** (`environmentSecrets`): see _Container and Toolchains_ → _Builds_.

The Workspace DO keeps its copy sealed in its storage (AES-GCM, HKDF purpose `workspace`, bound to the object's id and the name; `SECRETS_ENCRYPTION_KEY` is bound to the Workspaces Worker too), not in memory only, because what needs it runs on the DO's alarm after an eviction or a deploy, when nothing hands it again: the idle stop's snapshot, a spare's preparation and snapshot, a Build. It searches the Container's disk for each before every snapshot and takes each out of what a command prints as its Secret Reference. A copy that does not open (the key changed or is missing) is a set of values the DO cannot show to be absent from the disk, so its snapshots are skipped and its Builds fail until the next handover replaces it. So is the copy a handover leaves when the Registry could not open the Environment's Secrets (the set-up then carries `secretsUnavailable`, a fixed reason, in place of `secrets`: `environmentSecretsUnavailable`, which keeps the values it held before for redaction). The Setup Scripts of the Workspace's Container, and of a clone its readying makes, get those marked for the Build from the copy, each as `$PI_SECRET_<NAME>`, as a Build's do (`buildSecretEnvironment`): a Workspace made from a Build runs its Setup Scripts again, and a script that needs one would fail there without it. No other script or command gets them that way. A copy is replaced whole: a Secret deleted is no longer searched for, and what a command wrote with it stays where it is.

An Environment no Secret reaches never needs the Registry's key. While `SECRETS_ENCRYPTION_KEY` is malformed, the Registry DO answers everything else: the set-up of a Workspace whose Environment has Secrets carries none and says why (`secretsUnavailable`, `secrets unavailable: …`), so the Workspace takes no snapshot that would need them; that Environment's Build is left as it is (logged); and `setEnvironmentSecret`, `sessionSecrets` and `environmentSecrets` fail, saying the Secrets cannot be kept or opened.

From v2, secret references may name 1Password items. Credentials then move into a single dedicated vault, and deploy-time secrets shrink to the model proxy key, the 1Password token, and VAPID.

### Web

`packages/extensions/src/web` ports pi-web-tools (`NOTICE.md`): `web_search` over Exa or Parallel (keys are optional deploy-time secrets; a Session with both picks one by a stable hash of its conversation ID) and `web_fetch` (Markdown, text, or HTML; JSON re-indented; `offset`/`limit` line paging). A Worker has no temp file the model can read, so a result over 50 KiB or 2,000 lines is cut to whole lines and ends with a note naming the `offset` that reads on, instead of spilling to disk. HTML converts without a DOM in one linear pass; a page nested more than 1,024 levels deep (browsers stop at 512) or converting to more than 20 MiB of Markdown fails with a note to use `format: html`, so a hostile page cannot stall the Session.

**SSRF guard.** `web_fetch` reaches the network only through `guardedFetch`, which follows redirects itself and, for the URL and every hop, refuses non-HTTP(S) schemes, URLs with credentials, and any host that is or resolves to a loopback, private, link-local, CGNAT, unique-local, multicast, reserved, or cloud-metadata address (`169.254.169.254`, `fd00:ec2::254`, `metadata.google.internal`, `*.internal`, `*.local`, single-label names). Numeric hosts are decoded as a resolver would (decimal, hex, octal, short forms) and IPv6 forms that carry an IPv4 address (mapped, compatible, NAT64, 6to4) are judged by it.

A Worker cannot resolve a name before `fetch`, so a public-looking name that resolves to a private address is caught by a DNS-over-HTTPS lookup of its A and AAAA records through Cloudflare's resolver before each hop; a lookup that fails refuses the hop. The residual risk is DNS rebinding: the platform's own lookup at `fetch` time is separate from ours, so a name that answers differently to two queries in quick succession can pass. Both lookups share Cloudflare's caching resolver, which holds an answer for its TTL, and Cloudflare's edge also refuses Worker subrequests to private and internal addresses (the guard does not rely on that), so what is left is a narrow race for an attacker who controls a name's records and wants the Session to reach a public address of their choosing, which the guard does not try to prevent.

### Browser

[ADR-0007](adr/0007-browser-and-credentials.md) covers this design.

- **Tool:** `agents/browser` `Browser` with `browserRun(env.BROWSER, { keepAliveMs: 10 min })` in a browser host DO (`BrowserHost`), one per Session, in the plain `Browsers` Worker (`apps/browser`). `agents/browser/pi`'s `browserTool()` there runs the model's CDP code in a Worker Loader isolate (`LOADER`). The Session DO cannot host it: `browserTool` keeps its runs in a `CodemodeRuntime` facet the hosting Worker must export, and the Server Worker, an alchemy Effect Worker, exports only its Effect DO classes. The Session DO's `browser` tool (`packages/extensions/src/browser`) reaches the browser host DO over RPC, takes its description from it, and passes the calling conversation's ID. `Browser` keeps its record through an explicit `DurableBrowserSessionStore`, so no `Lifecycle` is installed: it would take over the object's `fetch`, `alarm`, and WebSocket handlers.
- **Session:** one shared Browser Run session per Session, with a tab per conversation (the root and each subagent: `conversation:<id>` scope) and shared cookies. Logins last as long as the Browser Run session.
- **Keep-alive:** Browser Run reclaims a browser after `keep_alive` without a CDP command (10 minutes here, so a long gap in the middle of a turn does not lose it; its maximum is 20). The Session closes it sooner, through the browser host DO, once the Session has been idle 5 minutes after the browser's last use, so an abandoned browser is not billed for the rest of the `keep_alive`: the time of the last use is kept in the Session DO's storage (noted before a run and after it), joins the Secret expiry as a wake time of the host's alarm (`wakeAt`), and the close runs when the host settles idle (`onIdle`) under a 5-second timeout, so a slow host cannot stall admission. A Session that is never idle is not closed by it; Browser Run's own timeout still applies.
- **Results:** a screenshot is returned as an image part and shown in the tool's card. It is kept in the transcript, so one over about 560 KB (750,000 base64 characters, the bound `read`'s images are held to: see _Filesystem and tools_) is replaced by a note to retake it as a smaller JPEG, and only PNG, JPEG, and WebP are kept. Only the latest 3 screenshots go to the model in a request (older ones read `[screenshot omitted]`, at the model seam next to Secret scrubbing), and the transcript snapshot a client gets carries the latest 10, so neither a provider's image limits nor a socket message's size limit grows with a long browsing Session. A screenshot is pixels: it cannot be redacted of a Secret the page shows. Results are redacted of held Secrets by the secrets extension's `afterTool` hook; `browser` is not one of the tools that resolve Secret references, since its code is stored with the run.
- **`browser_handoff({ instructions })`** (`packages/extensions/src/browser/handoff.ts`, host side `apps/browser/src/handoff.ts`): Browser Run's structured handoff (Human in the Loop), taken over in our own Live View ([ADR-0013](adr/0013-own-live-view-with-links-minted-on-open.md)). The browser host attaches to the conversation's active tab over a CDP connection of its own (`agents/browser`'s `CdpConnection` hands its caller no events), notes the tab's viewport (`innerWidth`, `innerHeight`, `devicePixelRatio`), sends `Cloudflare.handoff` with the instructions and `timeout` of 30 minutes (Browser Run's maximum), and hears the owner press Done or Failed as the `Cloudflare.handoffComplete` event on that connection (`success`, `reason`); Browser Run fires it on its own timeout too. It mints no link at the start. A conversation with no open tab gets an error telling the model to open the page with `browser` first.
  - **Link:** no Live View link is minted until the owner opens a Live View, and none is stored, sent to every client, or pushed. The Session keeps the request (instructions, conversation, deadline) in its key-value storage and sends the waiting requests to every client (`browser_handoff_requests`, sent after `hello` on every connect, an empty list too, so a client can tell "none waits" from "not heard yet", and to every client whenever the list changes), and pushes a `notice` with the instructions whose `url` is the Session's page with the handoff's Live View Pane open (`/sessions/:id?pane=live-view:<requestId>`: the extension sends the query, `liveViewPaneQuery` of `@cloudpid/protocol`, and the push puts it on the Session's page; the Pane's key is `liveViewPaneKey`). The UI shows a card with the instructions beside the Secret form, naming the subagent (ID and role) when the tab is not the root agent's; its **Take over** opens the Live View Pane, and a small **Open in Cloudflare** beside it mints a link the same way and opens Browser Run's hosted Live View (a fallback). The Pane never opens on its own. To connect, the client sends `live_view { id, requestId }` (a socket command shaped like `catalog` and `files`, ADR-0009), which the Session passes to the browser host's `liveView(requestId)` over `BROWSER_HOST` and answers to the asking client alone with `LiveViewLinks`: `{ tab: { targetId, link }, windows: [{ targetId, openerId, title, link }] }`. Each `link` is a fresh `Cloudflare.getLiveView` (`mode: "tab"`) with `expiresInMs: 60000` (Browser Run's minimum) and an explicit `targetId` (without one, Browser Run picks the newest page of the browser, not the handed-over tab), given as its `webSocketDebuggerUrl`, a `wss` URL the client opens straight from our origin (Browser Run checks the JWT, not the `Origin`). The windows are the page targets of `Target.getTargets` on the host's browser-level connection whose `openerId` leads back to the handed-over tab, directly or through another window (every pop-up and new tab carries one, `noopener` ones included: the spike, #152; a page with no opener, such as a tab the agent made, is not a window), breadth first. The client asks again when the Pane opens, on every reconnect, when the tab hears `Page.windowOpen`, and when a window's connection closes. Once the handoff has ended (or for a request the Session does not have) `live_view` fails with "the handoff is over" (`LIVE_VIEW_HANDOFF_OVER`). A link is in no socket message but that answer, no push, no storage of the Session or the host, and no tool argument, result, `details`, transcript entry, snapshot, or model request; a workerd test asserts that on every other socket message to every client, the pushes, the Session's key-value storage, the Harness's tables, the snapshot, and the model's requests. What a link exposes is set out in _Risks_ → Exposure of the shared browser session.
  - **Completion:** the owner's Done or Failed (with an optional reason) in the Live View Pane is the signal; there is no client command. The Pane sends `Cloudflare.handoffComplete { success, reason }` on the handed-over tab's own connection, as the hosted page does, and the host hears the event; the Pane also hears it on its connection and closes when another device finishes. The Pane closes when the handoff ends (Done, Failed, Stop, timeout); closing it does not end the handoff. The tool's result says how it ended: the user finished, the user could not (with their reason), timed out after 30 minutes, or ended without a word (Browser Run no longer had the handoff); and how many windows the tab opened are still open, each by its origin only (never the URL: an OAuth redirect carries a code), read when the handoff is ended (`endHandoff`'s `windowOrigins`); when the host could not read them in the five seconds a cleanup gets, the result says it is not known whether windows are open, never that there are none. It names no link. Stop withdraws the request and ends the handoff in Browser Run, over a new connection when the browser host restarted since it started.
  - **Cleanup:** there is no link to purge: the Session drops the request from its storage when the call ends, and the host deletes its record when the Session ends the handoff. **The agent's viewport:** the Pane sets the tab's size (`Emulation.setDeviceMetricsOverride`), one override shared by every connection, which closing a connection does not undo and a clear from another connection undid unreliably (the spike). So at every ending (Done, Failed, Browser Run's timeout, a handoff Browser Run lost, Stop) the host sets the size it noted at the start explicitly (`setDeviceMetricsOverride { width, height, deviceScaleFactor, mobile: false }`, Browser Run's default 780×493 at DPR 1 when it could not be read), checks `innerWidth` and `innerHeight` and sets it once more if they differ; then, on every window of the handoff that is still open (which never had an agent override), it clears the Pane's override in the window's own session and, if the window does not show the size the host read when `liveView` first listed it (before the Pane had a link to it), sets that size explicitly. All this before `waitHandoff` answers the ending and before `endHandoff` forgets the handoff. The Pane also clears its override before Done and Failed, on close and on `pagehide`, best effort; a size the agent had set itself before the handoff is the one put back, though not its `mobile` flag, which the page cannot tell. A record the Session never ended (it was deleted, or the call was cut off for good) carries its deadline and is pruned by the host's alarm five minutes past it, and the Session does not show or push a request past its deadline plus the grace it gives the host. A request that was ended leaves a one-hour tombstone in the host, so a start that arrives late is refused instead of opening a handoff nobody ends; a second start of the same request while the first is in flight joins it. The host reads the conversation's tab from `agents/browser`'s stored records without resolving a browser: a conversation with no browser or tab of its own gets the no-open-tab error, and no browser is started for it. When the host cannot reopen its connection, only Browser Run saying the browser or tab is gone ends the handoff (`ended`); any other failure is retried by the Session's rounds.
  - **Durability:** the tool is `replay: "safe"` and waits in rounds of 25 s on the host's `waitHandoff`, so no call outlives an eviction; the request and its deadline are in the Session's storage, and the rerun after an eviction waits for the same handoff (`startHandoff` is idempotent by the call's task ID, and the host keeps its record in its own storage). A host that restarted reconnects and asks `Cloudflare.getHandoffState`: a handoff that is over with no end event heard ends as "ended". A request whose call is gone is ended once the Session is idle, as an abandoned Secret request is.
  - **Keep-alive:** each round also notes the browser as used, so the Session's 5-minute idle close never runs under a pending handoff (a live tool call means the Session is not idle anyway), and the host's quiet-round `getHandoffState` poll is a CDP command, which keeps Browser Run's own `keep_alive` from reclaiming the browser while the owner works.
- **v2, `fill_credential({ item, fields, submit? })`:**
  - The host resolves 1Password items, checks that the active tab's origin matches the item's URLs, types the values with CDP `Input.insertText`, and computes TOTP itself.
  - It returns only `{ ok, filled, origin }`.
  - The first use of each item in a Workspace asks the user: once, or always for this Workspace.
- **1Password access (v2):**
  - First a time-boxed spike running `@1password/sdk` in the Worker, with its WASM loader aliased to a Workers module import.
  - Fallback: a minimal Node container with the SDK behind its own DO, exposing only `resolve`.
  - The token never reaches the Workspace container.

### Agent changes

[ADR-0019](adr/0019-the-agent-manages-its-environments-and-settings.md) lets the agent manage its Environments; an **Agent change** (GLOSSARY.md) is one change it makes, recorded with its reason. The `environment` extension (`@cloudpid/extensions/environment`) has the first tools, deferred as any later extension's are.

- **`environment_list()`:** each Environment's id, name, Repos and Build, marking the Session's own. **`environment_get({ id? })`:** the Environment's name and Repos, every Container setting (size, size limit `maxInstance`, idle time, Container-only paths, variables, Setup and Start Scripts, Toolchains), the names of the Secrets kept for it and of those kept for every Environment that it does not override, each with whether it reaches the Build (never a value), and its Build, with the last 1,000 characters of the last failed Build's reason. `id` defaults to the Session's Environment (its Workspace's); an unknown one is refused, pointing to `environment_list`.
- **`environment_variable_set({ id?, name, value, reason })`, `environment_variable_unset({ id?, name, reason })`:** one variable, by the owner's save's rules (`variableNameProblem`, at most 50 variables, values of at most 4,096 characters); a refusal says why and saves nothing. The `reason` (1 to 500 characters) is required. Unsetting a variable that is not set, or setting the value it has, says so and records nothing. Each result says the change applies at each Workspace's next Container start, adds for the Session's own Environment that `container_restart` applies it now, and says when the change asked for a new Build. Both run alone (sequential), and are not replayed: a rerun after an eviction would record the change again (`replay: unsafe`).
- **Values are plain.** A value that holds the value of a Secret the Session holds (`secret_ask`'s or the Environment's), or the GitHub token (`CLOUDPID_GITHUB_TOKEN`, which the main Worker is bound to for this), as written or in any encoding the Session's redaction knows, is refused, and nothing is saved or recorded (checked once the Session's Secrets are refreshed, so one the owner has just kept counts); so is a `reason` that holds one, since it is kept as written. The refusal points to keeping it as a Secret for the Environment. The tools are not wrapped to resolve Secret References, and the secrets extension's `beforeTool` hook lets their calls through: a reference in `value` is saved as that text, held or not, as the description says.
- **Root only.** The `environment_*` tools are the root conversation's, as `secret_ask` is: `PARENT_ONLY_TOOL_PREFIXES` keeps every tool whose name starts with `environment_` out of a child's grant, named or inherited.
- **Applied** as the owner's save is: the Session calls the Registry DO's `changeEnvironment` (the Environment, the change as a field, `variables.<NAME>` or a setting's name, with its new value or null, and the author: Session, conversation, tool, reason), which checks and writes the settings as `updateEnvironmentSettings` does and records the change in the same transaction, answering the values before and after and whether the Build key changed (`buildKey`, with the image left out). Then, as after the owner's save, the Session runs the Builds' upkeep for that Environment (`buildUpkeep`, which keeps its spare current once a new Build is good), and, for the Session's own Environment, hands the new overrides to its own Workspace DO at once (`updateContainerSettings`; a failure is logged, and the next readying hands them). Other Environments' Workspaces get the change at their next readying, as they get the owner's.
- **Kept** (Registry migration 17, `agent_changes`): each change with its time, actor (`agent`, or `owner` for a revert), Session, conversation, tool, reason, scope (the Environment's id), field, and the values before and after (JSON, null for not set). A scope keeps its last 200; deleting an Environment deletes its own. `listAgentChanges { environment }` lists them newest first, each with the revert that undid it (`revertedBy`). `revertAgentChange { environment, change }` writes the value before back and records that as the owner's change (`reverts`); it is refused, saying what the field is now, when the field no longer has the value the change gave it, for a change reverted already (the agent may have given the field that value again since), and for an owner's change (a revert is not undone). The main Worker then runs the Builds' upkeep, as after the owner's save. The Environments page lists them (see _Workspace and execution_ → _Environments from the UI_).
- **Transcript and Notification:** each change's result carries `details.agentChange` (the change's id, the Environment, the field, the values before and after), which its card shows in full. The Session keeps the Run's changes (tool, Environment name, field) in its key-value storage, and when the owner's Run that made at least one ends it sends one `notice` listing them, besides the usual `finished` or `failed` (see _Client and protocol_ → _Notifications_).

## Client and protocol

- **Wire:** the contract lives in `packages/protocol`, shared by server and web ([ADR-0009](adr/0009-session-socket-messages-over-alchemy-rpc.md)).
  - **Session socket:** `GET /sessions/:id/socket` on the main Worker, forwarded to the Session DO, which accepts it as a hibernatable WebSocket. A Session the Registry does not know answers 404. Messages are JSON in the Cloudflare pi example's shapes, as Effect `Schema`. The Session greets a client with `hello` and its active branch's conversation (as `root`, its name from before Session branches; see _Session tree_), with `copying` while it is still being filled as a Fork or Clone. Commands carry an optional `id`, which a `result` or an `error` answers, also when the command cannot be read. Keys a command does not define are an error.
  - Commands: `submit` (with `whenBusy` and a `requestId` that deduplicates), `abort`, and `watch`/`unwatch`. `configure` picks the root agent's model and thinking level (the active branch's) (`null` follows the default in the settings again); the Session says which fields it picked (`picked`, after `hello` and to every client after a `configure`); it is a socket command, not Registry RPC, because the pick belongs to one Session, is applied by that Session's Harness, and reaches every watching client as an `agent_changed` event. `submit` and `abort` take an optional `conversationId` of a live subagent, and `abort` an optional `subagents` flag that also stops everything below it (see _Subagents_: Stop). `watch_task_graph`/`unwatch_task_graph` start and stop `task_graph` messages: a summary of the Session's live work (`agents`: ID, parent, conversation, role, model, `working` or `idle`; `background`: live background tasks other than the subagents' own bookkeeping), made from pi-durable's `watchTaskGraph()` and the Subagents document, at most one every 250 ms, and only when it changed. The watch is kept in the socket's attachment and restarts on wake, like a conversation's. Watching a conversation also streams its Todo List: after the snapshot, a `todos` message (`conversationId`, `tasks`) with the whole list, and another each time it changes; each replaces the last of that conversation, and `unwatch` stops them. `secret_answer` answers a Secret request with the values entered in a masked form (or `null` to cancel); the Session sends the waiting requests (`secret_requests`) after `hello` and to every client when they change, and the values never reach a client again. The Session likewise sends the Browser Handoffs waiting for the owner (`browser_handoff_requests`, with no Live View link) after `hello` on every connect, an empty list too, and to every client when they change; `live_view { requestId }` mints links to one of them for the asking client alone (see _Browser_), and there is no answer command, as the owner finishes in the Live View. `catalog` and `command` serve the composer's Slash commands, and `files` its `@` mentions (below). `history { before, conversationId? }` answers a `HistoryPage` of the active branch's or a live subagent's History before entry `before`, read newest first and sent oldest first: at most 200 entries read (`MAX_HISTORY_ENTRIES`) and the ones a transcript shows kept (no system prompts or bookkeeping) until they pass about 4 MiB of JSON (`MAX_HISTORY_BYTES`, well under workerd's 32 MiB message cap), the entry that passes it included, with the `before` to ask for next (`null` when nothing is left; `apps/server/src/session/history.ts`). `tree`, `navigate` and `switch_branch` serve the Session tree, and `active_branch` follows it (see _Session tree_, below). Still to come: `reset` and approval responses.
  - `whenBusy: "steer"` joins the running Run at its next boundary, after the tool calls in progress. A steer that finds the Run giving its final answer starts the next Run, as `followUp` does.
  - `watch(conversationId)` streams `events`: a batch holding a `snapshot`, then pi `AgentEvent` batches unchanged. The socket's attachment names its watches. A Session woken from hibernation restarts them, each with a fresh snapshot, on the same socket. A watch that ends, or cannot restart, is dropped with an `error` naming its `conversationId`. A client whose socket closed (an eviction, a deploy) reconnects and watches again.
  - `watch_usage`/`unwatch_usage` start and stop `usage` messages: what the Session has spent (input, output, cache read and cache write tokens, total tokens, and `cost` in US dollars) and its spend `limit` (`null` for none), each replacing the last, at most one every 500 ms and only when it changed. One read of the ledgers is in flight per watch, and changes that come meanwhile ask for one more; a limit changed in the settings is sent when the Session next reads them (a connect, a prompt, a `configure`). The totals are pi-durable's session total (`harness.usage()`, every conversation's `pi.usage` summed, subagents included) plus the title calls'. Each message also carries `container`, what the Session's Workspace's Containers have cost (see _Operations_ → Telemetry → Container cost), read from the Workspace DO (`containerUsage`, which starts nothing) with the ledgers; it is left out when no Container ran, the Session has no Workspace, or the read failed. Each message also carries `context`, how full the active branch's Context Window is (`apps/server/src/session/context-usage.ts`): `tokens`, the size of its next request as pi-durable reckons it before compacting (pi-ai's `estimateContextTokens` over the branch's model context: the newest answer's usage plus estimates of the messages after it), out of its model's `contextWindow` (from the model catalog, with the proxy's caps), `compactAt`, where automatic compaction starts (the background threshold, or the blocking one without background compaction; null when it is off), and `parts`, `tokens` split in proportion to estimates of the system prompt and tool definitions, the owner's messages, the answers and the tool results. It is read again only when the branch, its newest entry, its model's window or the compaction settings changed, and left out when the model's window is not known or the read failed. A move to another branch and a `configure` send a message at once. Like the task graph, the watch is read when the task graph changes (a response's usage is committed with it), kept in the socket's attachment, and restarted on wake. The composer's toolbar shows a ring filled to the share of the context window used (in Ink once the context is within 85% of where it compacts); hovering, focusing or tapping it shows the breakdown: a bar of the window with each part and the compaction point marked, each part's tokens and the room left, then the spend (the models' cost plus the Containers', ticking each second while a Container runs, from the rates the message carries up to the idle stop it names), the spend limit, input, output, cache read and cache write tokens, and the Container's run time, CPU time, and memory, CPU, disk and egress cost. Near the spend limit the ring takes the warning border, and at it the error colour and "Limit reached" (the limit holds the models' cost only).
  - The runtime answers the client's `ping` heartbeat with `pong` without waking the Session.
  - **Attachments:** `PUT /sessions/:id/attachments/:name` on the main Worker (behind Access, beside the socket) takes a file's raw bytes as the body and writes them into the Session's Workspace at `/workspace/.cloudpid/uploads/<session-id>/<name>`, answering 201 with `{ name, path }` (`StoredAttachment`); `DELETE` of the same path removes one that was not sent (204, also when it is gone). A Session the Registry does not know answers 404, and neither touches a Workspace. The name is one escaped path segment, sanitised (`sanitizeAttachmentName` in `@cloudpid/protocol`): letters, digits, `.`, `_` and `-` kept, every other run of characters one dash, never starting or ending with a dot or dash (so never `.`, `..`, hidden or an option), at most 100 code points and 200 UTF-8 bytes (Linux allows 255) with its extension kept, `attachment` when nothing is left; one that is taken gets `-2`, `-3`, … before its extension. Every path is built from the Session's ID and that name, so nothing a client sends reaches outside the Session's directory. A body over 25 MB (`MAX_ATTACHMENT_BYTES`, by its length header or as it is read) answers 413 and writes nothing, and one cut off (shorter or longer than its length header, or stopped by the client) answers 400: the Workspace DO holds the whole file in memory to write it (its storage keeps it in 512 KiB chunks), in 128 MB that runs the rest of the Workspace. A body with a length header is read into one buffer of that size, and the Workspace writes it without copying it again. The write goes through the file operations a Session's environment uses, which make the directory with `ensureDirectory`. Two uploads of one name at the same moment could both find it free, the later write winning; the web app names its own uploads apart, so only two pages uploading one name at once meet that. `DELETE` removes any file of that name in the Session's directory, sent or not: the route cannot tell them apart, and the owner is the only one who reaches it. Uploaded files stay in the Workspace after sending, as a Deleted Session's files do.
  - **Registry:** `RegistryRpcs`, an Effect `RpcGroup` over HTTP (`POST /rpc`, JSON), lists, creates, renames, archives, unarchives and deletes Sessions (each in a new Workspace of an Environment or in one that exists), lists, creates, renames and deletes Environments, adds and removes an Environment's Repos (`addRepo`, `removeRepo`), reads and saves an Environment's Container settings (`getEnvironmentSettings`, `updateEnvironmentSettings`), lists, keeps, flags and deletes Secrets kept for an Environment or for every Environment, never answering a value (`listEnvironmentSecrets`, `setEnvironmentSecret`, `setEnvironmentSecretBuild`, `deleteEnvironmentSecret`: see _Agent capabilities_ → _Secrets_), lists the Environments' Builds and makes one again (`listBuilds`, `rebuildEnvironment`: see _Container and Toolchains_ → _Builds_), lists an Environment's Agent changes and reverts one (`listAgentChanges`, `revertAgentChange`: see _Agent capabilities_ → _Agent changes_), lists and removes Workspaces (`listWorkspaces`, `removeWorkspace`), restarts a Workspace's Container (`restartContainer`, answered by its Workspace DO; a Workspace the Registry does not list is refused), makes a Fork or Clone of a Session (`forkSession`: see _Session tree_), and reads and replaces the settings overrides. After it answers, `listSessions` also wipes some of what was left from before Environments (see _Registry migrations_) and keeps the Environments' spare Workspaces (see _Workspace and execution_ → _Spare Workspace_) and their Builds.
- **Reducer:** `view.ts` and `transcript.ts` from Cloudflare's `agents` example `examples/next/harnesses/pi` (MIT, attributed). They are extended for `nestedTools`, compactions, subagents, and earlier Context Windows: a head marker (a Handoff's reset, a compaction) moves what is before its head from `messages` to `earlier` rather than dropping it, a snapshot keeps a view's `earlier` when the view saw the snapshot's marker (a woken Session's fresh snapshot loses nothing) and otherwise starts it empty with `before` at the marker's head, and `withEarlier` puts a `history` page in front. The thread shows `earlier` then `messages`, so a turn a page boundary splits is whole again. This reducer is the only code that interprets `AgentEvent`s.
- **UI:**
  - Vite and React 19 in `apps/web`, served as static assets by the main Worker.
  - assistant-ui `ExternalStoreRuntime`: steers map to `steerItems`, follow-ups to `items`, and `onCancel` to abort.
  - `streamdown` for Markdown, with Tailwind v4 and shadcn.
  - **Composer:** one box with the input and a toolbar: the root conversation's model and thinking level (one `model:level` chip whose menu lists the models, each with a submenu of the thinking levels; picking a level sends `configure` with both) on the left, the context ring (see `watch_usage` above), Attach, then Send, or Steer, Queue and Stop while a Run is in progress, on the right; Attachment tiles sit above the input. A `/` at the start of the message opens a menu of Slash commands; those the web app runs itself are `/model [model]` and `/thinking [level]` (`configure`, or open the picker without an argument, on the models or on the levels of the model in effect), `/name <title>` (`renameSession`), `/new` (`createSession` in a new Workspace of the shown Session's Environment), `/archive`, `/settings`, `/tree`, `/fork` and `/clone` (see _Session tree_), `/stop`, `/stop-all` and `/copy` (the last answer to the clipboard); a subagent's composer has only the last three. The Session's own commands, Prompt templates and Skills come from `catalog`, asked for when the menu first opens and again once the answer is 30 s old: the `/` menu lists Commands (the web app's and the Session's), then Prompt templates, then Skills as `/skill:name`, and a `$` at the start of a word opens a menu of the Skills alone (none when nothing matches, so `$HOME` is left alone). An `@` at the start of a word (not in an email address or inside backticks) opens a menu of the conversation's files and folders (`files`, below). A subagent's composer offers the Session's commands, addressed to its conversation, and its directory's templates, Skills and files. A `/name` the web app does not know is sent as written, for the Session to expand. An owner's message the Session expanded shows as typed, with a closed "Skill · name" disclosure for the Skill a `/skill:` embedded (a `$name` link has none).
  - **Slash commands** (`docs/adr/0001-expand-skills-and-prompt-templates-at-submit.md`). `catalog` (optional `conversationId`) answers `{ commands, templates, skills }` for the conversation's directory (its `cwd`, else its Workspace's directory): the Session's commands (name, description, argument hint, whether the argument is `none`, `optional` or `required`, and its `choices`; `/rollover` only where the conversation's agent has `context_rollover`), and the Prompt templates and Skills found from that directory up to `/workspace`, nearest first, each with its name, description and argument hint; Skills include the `disable-model-invocation` ones, which exist for the owner to name. A Workspace that cannot be asked leaves the templates or Skills out (logged), not the commands. The commands are also `SESSION_COMMANDS` in `@cloudpid/protocol` (`sessionCommandsFor`), so the web app runs one typed before the catalog arrives, or after it could not be had, instead of sending it to the model; it offers `/rollover` in the root's composer only. `command { name, args, conversationId? }` runs one on the root conversation or a live subagent's and answers `{ notice?, file? }`; a command that cannot run fails with why, shown under the composer:
    - `/compact [focus]`: pi-durable's manual compaction (`Conversation.compact`), the focus at most 2,000 characters, as a Rollover's. While a Run is in progress it waits for the conversation to be idle, the request kept in the Session's storage so an eviction does not lose it, and runs then.
    - `/rollover [focus]`: the Rollover request, steered (see _Context management_). Not offered, and refused, in a conversation without `context_rollover`: a subagent is never granted it, so a subagent's composer has no `/rollover`. A client whose socket closes before a command's answer is told that it may have run.
    - `/todo clear`: clears the conversation's Todo List, moving its revision, so watching clients are sent the empty list.
    - `/export`: the conversation's whole History, every Context Window, as Markdown (`file`: name, MIME type, content), which the web app downloads. Each page of entries is rendered as it is read and counted in UTF-8 bytes of the JSON string it travels as, and an export over 8 MiB is refused as soon as it passes that: the file is one `result` message, which workerd caps at 32 MiB, and while it is built the Session holds the Markdown, the message and a page of entries at once in an isolate of 128 MB that runs the Session's work too, so a quarter of the message limit leaves room for them.
  - **`@` mentions.** `files { query, conversationId? }` answers `{ paths }`: at most 50 paths relative to the conversation's directory (as for `catalog`) that match `query` (what follows the `@`, at most 1,024 characters), best first, a folder's ending in `/`. They come from one `ExecutionEnv.listFiles` walk of the directory (above): what git ignores is left out (the `.gitignore` files of the directory, below and above it in its work tree, and `.git/info/exclude`; below a directory in no work tree, each repository's own), and so are `.git` and `node_modules`, at most 50,000 entries, the walk cut off after 8 s (a cut-off listing is logged); a folder above a listed path that the listing lacks is added. Also left out: a path holding whitespace, which a mention cannot hold (it ends at the first space, and the agent reads no quoting), every Session's Attachments (`/workspace/.cloudpid/uploads`) and the bundled Skills' mount (`/workspace/.agents/skills`). Paths are ranked by `rank` in `@cloudpid/protocol`, the function the composer's menu ranks with (exact, prefix, word start, substring, letters in order; a match in the last segment, a folder's name, before one elsewhere), shallower paths first among equals, so an empty query lists the top level first; each listing is lower-cased and split once, and a request keeps only its best 50 as it ranks. The Session holds each directory's listing for 30 s (`apps/server/src/session/file-search.ts`), at most 4 directories and 100,000 paths, the least recently asked settled one dropped first (one being made is never dropped); requests made while a directory is listed share that listing, at most 2 listings run at once, and one that fails or has not ended within 10 s is not held, so the next request lists again. A conversation without an environment has no files; a Workspace that cannot list, or does not answer in time, fails the request. The web app sends the query 120 ms after the owner stops typing and narrows the last answer with the same ranking meanwhile; an answer serves while the menu stays open and for 30 s, so opening the menu again asks afresh. With no rows, the menu shows "Searching files…" until the first answer, "No matching files or folders." when there is none, and "Could not search the files." when the request failed (cleared when the menu closes), in a live region announced as it changes. A row shows the name (a folder's with its `/`) and, muted, the folder it is in, cut from its start on a narrow screen. A pick inserts `@path` and a space at the caret, in place of what was typed after the `@`; a folder inserts `@dir/` with no space, so the menu stays open and typing on narrows into it. The message keeps the mention as plain text: nothing is inlined, and the agent opens the path with its own tools.
  - **Prompt templates** are `.agents/prompts/*.md` (not below), found by the Workspace DO's `prompts(cwd)` next to the files, as skills are (`ComputerExecutionEnv.discoverPrompts`; `@cloudpid/extensions/prompt-templates`), the nearest winning a name, at most 100. Parsing follows local pi: the name is the file's, the description its `description` frontmatter or its body's first line cut to 60 characters, and `argument-hint` its hint. The listing carries no bodies (a template's file is read when a message uses it), and leaves out a file over 256 KiB (by its size, before reading it) and one whose name holds whitespace, which a Slash command could not name.
  - **Expansion at submit.** Before the Session admits the owner's message it asks the conversation's Workspace for its Skills and templates when the text may name one (it starts with `/` or holds a `$` that may start a name): `/skill:name [args]` at the start becomes local pi's `<skill name location>` block (`SKILL.md` without its frontmatter, "References are relative to" its directory), then the arguments; `$name` naming a known Skill (exactly, case-sensitively), in the prose of the message or of a `/skill:`'s arguments, becomes in place a Markdown link to its `SKILL.md`, `[$name](/path/to/SKILL.md)` (the path URI-encoded, and `?`, `#`, `(` and `)` too; only an absolute, well-formed path is linked), every occurrence, in order, as the owner's pi extension pi-skills-selector makes it: no file is read for it, and the model reads the Skill when it needs it; `/name args` naming a template becomes the template with local pi's substitution (`$1`…, `$@`, `$ARGUMENTS`, `${N:-default}`, `${@:N}`, `${@:N:L}`, bash-style quoting, no re-substitution). A name nothing knows is left as typed, as are `$HOME` and other expressions, an escaped `\$name`, a `$name` glued to a word (a letter, digit, `_`, `$`, `/`, `+` or `-` before or after it, or `.` and a word after it), and one in code or in an existing link (inline, reference or automatic) or link definition. A `/skill:` or template whose file cannot be read or is over 256 KiB is left as typed too (a `/skill:` so left keeps its references linked), and so is the whole message when the expansion and the typed text together would be over 1 MiB (an entry is one SQLite row, at most 2 MB); what was left so is logged. A Workspace that cannot be asked, or does not answer within 5 s, leaves the message as typed. Messages are admitted in the order they arrive (a lock separate from the alarm's), so one sent while the message before it waits on its Workspace is not admitted first. The prose is found with marked's lexer, as pi-skills-selector finds it (`apps/server/src/session/skill-references.ts`, ported from its `skill-references.ts` with its tests). An expanded message is placed as a `cloudpid.user` entry whose model message is the expansion and whose data is `{ display, skills: [{ name, location }] }`, `skills` naming only the Skill a `/skill:` embedded: the transcript projection and the title show `display`, and the queue lanes show the text the client sent.
  - **Attachments** (GLOSSARY.md → Messages). The composer's Attach button (a file picker, any files), a paste of files, or a drop anywhere on the thread (a subagent's thread for its own composer) attach files, which upload over the route above one at a time, in the order they came (an `XMLHttpRequest`, for its upload progress), each named apart from the composer's others (a file over 25 MB fails at once, without an upload); removing one before sending stops its upload or deletes the stored file, also when the upload ended as it was removed. Files uploaded but not sent stay in the Workspace when the composer goes (the subagent's card closes, the page changes or reloads), as sent ones do; a removed one is the only one deleted. A subagent's composer uploads to the same Session's `.cloudpid/uploads/<session-id>/`. A message with Attachments is sent by the composer itself (assistant-ui sends text only), as a steer while a Run is in progress (Enter, Ctrl/Cmd+Shift+Enter) or a follow-up (Alt+Enter, Queue): its input is the typed text as one text part, then a text part of each Attachment's `@/workspace/.cloudpid/uploads/<session-id>/<name>` on a line of its own (a part of its own, so a Prompt template or Skill the Session expands from the first part takes no path for an argument and drops none), then each picture inline as an image part. The text and Attachments leave the composer when it is sent and come back, with the Session's reason under the box, when the Session refuses it. A picture is decoded in the browser once, drawn at a 1568 px long edge (kept until it is sent or removed), and encoded from that drawing as JPEG, or WebP (PNG where the browser cannot encode WebP) when it has transparency; all of a message's pictures take one quality, the best of 0.85, 0.72, 0.6, 0.48 and 0.36 at which they share 1.5 M base64 characters (`INLINE_IMAGE_BUDGET`), and when even the lowest is over, the largest goes as a file only and the rest are fitted again (`apps/web/src/chat/image-budget.ts`, with the encoder injected). A GIF goes unchanged, still animated, at the best quality when it fits the budget alone; at the others it is a still like any picture, and its tile says so. One that does not fit, or that the browser cannot decode (some HEIC, a corrupt file) or encode, is attached as a file only, and its tile says why (a picture over 25 MB fails instead, as any file does). The fitting runs as Attachments are added or removed, so the tiles say it before sending; Send is disabled, saying why under the box, until every upload is done and every picture fitted, and a failed upload must be removed first. The lanes show the typed text and the Attachments' names. The transcript shows a message's images (an expanded message keeps them: `display` replaces only its first text part).
  - **What a submit may hold.** An owner's message is one entry, a single SQLite row that Cloudflare caps at 2 MB, and a queued one is also copied into the conversation's inbox document (`pi.inbox`), one row for every message waiting; a write over the cap fails the commit, which fails the Session. So before admitting a submit, in arrival order and after its expansion (what is measured is what would be written), the Session refuses one whose content and entry data are over 1.9 MB (`MAX_STORED_INPUT_BYTES`) as UTF-8 JSON, one that would take the inbox over it beside the messages already waiting, and an image part whose `mimeType` is not PNG, JPEG, WebP or GIF, answering the client with an `error` that says why and keeps running (`apps/server/src/session/input-guard.ts`). This holds for any client, not only the web app's budget. miniflare's SQLite does not enforce the 2 MB cap, so the workerd test shows the refusal and the Session going on, not the failure it prevents.
- **Subagents in the UI:** a `subagent` tool call that started an agent (its result's `details.conversation_id`) is a card with the agent's ID, role, model and status (from the task graph). Opening it is a second `watch` on that conversation, released when closed; the thread inside is its own assistant-ui runtime, with a composer that steers or queues input and a Stop button (and Stop all, on the same terms). The **Tasks Pane** (below), fed by `watch_task_graph`, lists the agents (each openable into the same thread, with its own Stop) and the background work, and has Stop all.
- **Session tree** ([ADR-0017](adr/0017-session-tree-in-session-forks-and-clones-as-sessions.md); GLOSSARY.md → Session tree, Session branch, Fork, Clone): local pi's `/tree`, `/fork` and `/clone`. Labels on the tree's nodes are not done yet (#180).
  - **Session branches** are pi-durable forks (`fork(at)`) of the root conversation inside the Session DO, and the Session keeps which one is the active branch in a session document (`cloudpid.session-tree`, `apps/server/src/session/tree.ts`: the active one, and when each was last active). Everything that took the root conversation follows the active branch: `hello`, `submit` and `abort` without a `conversationId`, `configure` and the default model, the task graph's root, and the Subagents document's root agent (`activeBranch`, and `branches`, every branch's conversation), so a subagent the root agent starts belongs to the branch it was started from, keeps running when the owner moves, and reports and sends its `agent_message`s to that branch (`reportConversationOf`). A `conversationId` that names the active branch is the active branch, following the settings and the owner's pick as one left out does; one that names another Session branch is refused, as that branch is reached by making it active. `hello` still calls the active branch `root`, the name it had when the root conversation was the only one, so a client open across a deploy reads it as before. The transcript is the active branch's whole path, as pi-durable's fork-aware history reads it.
  - **`tree`** answers a `SessionTree`: one node per entry a transcript shows (ID, parent, branch, `user`, `input`, `assistant`, `tool` or `notice`, its text cut to one line of 200 characters, whether an answer ends its Run, its time), parents before children and siblings oldest first, with the active branch, its last node (`leaf`) and every branch's last activity. A branch with no entry of its own is left out. Clients compute the rest: siblings are nodes with one parent.
  - **`navigate { entryId, position, summary? }`** (a `TreePoint` and the summary asked for) moves the active branch to just before an owner's message (`before`, which answers its text for the composer) or just after an entry (`at`), and answers `Navigated` (the branch, the text). Where an existing branch's last entry is the point, that branch becomes active (the one active last, when several); otherwise a new branch is forked there (`planNavigation`), and before the Session's first message it is a fresh conversation, with the agent of the branch left. It is refused while the active branch is busy: a Run in progress, a compaction, messages waiting to be placed, or a `/compact` waiting. `summary { instructions? }` (at most 2,000 characters) has the active branch's model summarize the entries of the branch left that the branch entered does not share (pi's `collectEntriesForBranchSummary` and its prompt, `apps/server/src/session/branch-summary.ts`, at most about 100k tokens of the branch, newest kept), on the Session's spend as a title call is; the summary is placed in the branch entered as a `cloudpid.branch-summary` entry the context reads with pi's framing and the transcript shows as a "Branch summary" notice. `switch_branch { conversationId }` makes a branch active as it stands, refused likewise. Either announces `active_branch { conversationId }` to every client, which stops watching the branch it watched, watches the new one, and asks for the tree again.
  - **Fork and Clone** (`forkSession { source, point?, workspace?, branch? }`, answering the new Session and the text for its composer): a Fork is a new Session from a point of the source's active branch (just before an owner's message, whose text goes into the new Session's composer, or after an answer); a Clone, with no point, is one from its latest entry, refused while the active branch is busy (as `navigate` is). Either is refused while the source is itself still being filled. The source answers what to copy (`forkSource`, `apps/server/src/session/fork-host.ts`, with what is copied in `fork.ts`: the branch, the last entry, `pi.agent` as of the point (pi-durable's default before the Session's first message, so the Fork takes the settings in force), the fields of model and thinking level it picked itself, each as the branch ran with it at the point (the others follow the default in the Fork too), the Notes and the Todo List as they are now), and the Registry registers the new Session (titled `<source's title> (fork)` or `(clone)`, `Untitled session` standing for a source with none, cut to the longest title (`forkTitle`), with its `origin`: the source's ID and `fork` or `clone`), then fills it with the branch's path through the point (every Context Window), a page at a time (at most 200 entries and about 8 MiB of JSON: `exportEntries`, `importEntries`, in the loop `fillSession` that the tests drive too), into the new Session's root conversation, renumbered, its heads and edits pointing at the entries it was given, then hands it the rest (`importFinish`). Other branches, held Secrets and Usage are not copied: the new Session starts at none. Until it is filled the new Session refuses messages and moves, saying it is still being made, and greets with `copying` (the Registry answers once it is filled, so the source's page says the new Session is being made meanwhile, and makes one Fork or Clone at a time); once filled it closes its sockets with 1012, so the clients connect again and are greeted afresh. `workspace` is the source's Workspace by default (`same`); `new` makes one of the source's Environment on `branch` (or `cloudpid/<id>`, refused as `createSession` refuses one), refused while anything of the source works (any branch's Run or queued messages, any subagent, a `/compact` waiting: the Harness's live tasks that are not background work, and its unsettled submissions); from then until the files are carried (`releaseFork`, or 30 minutes at most) the source takes no message, so nothing changes them meanwhile. Once the Session is filled the source's Workspace DO carries its files there (see _Workspace and execution_ → _Carried files_). A Fork that fails leaves nothing: its Session is deleted, or its new Workspace removed with it, and the source takes messages again.
  - **In the web app:** under each owner's message and each answer that ends a Run on the active branch, a bar has a Branch button (`navigate`: to just before the message, its text put back in the composer, or just after the answer) and Fork, a split button (the main part in this Workspace, its menu "Fork in a new workspace…", which asks for the new Workspace's optional git branch); under the answer the active branch ends with (past any notices), Fork reads Clone and Branch, with nowhere to go, is disabled. - **Notifications:** Web Push when a Run ends, fails, or needs input.
  - **Keys:** `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT` are deploy-time secrets read by the Registry DO (`Config.Redacted`). The public key reaches the web app through `getPush`; the private key never leaves the Worker.
  - **Subscriptions:** a device's `PushSubscription` (endpoint and keys) is a row of the Registry DO's `push_subscriptions` table, over `getPush`/`subscribePush`/`unsubscribePush`. The settings page turns notifications on (permission, subscribe, `subscribePush`) and off (`unsubscribePush`, unsubscribe) per device. `getPush` says whether the Registry holds the asked endpoint, and the page gives it back a subscription the browser holds but the Registry lost.
  - **Sending:** the Registry DO's `notify(sessionId, event)` (`apps/server/src/push`) encrypts one message per subscription (RFC 8291 `aes128gcm`) and signs it with VAPID (RFC 8292), both on WebCrypto. The body is a title (the Session's title), one line, the Session's page and a tag, a few hundred bytes. Each push is given up on after 5 s, 16 at a time, so the Session's 20 s wait holds for up to 64 browsers (a Session that gave up sooner would send it again). A 404 or 410 from the push service deletes the subscription; any other failure is logged and the subscription kept. Only endpoints at known push services (FCM, Mozilla, Apple, Windows) over https are accepted. A Session DO reaches it through `SessionRegistry.notify`, and extensions through the `OwnerNotifications` service in `@cloudpid/extensions/notify`, which takes a `notice` event (title, body, url; the title, body and url are bounded so a push fits one message).
  - **Triggers:** the Session host keeps the submissions the owner made until their Run's end is notified (in its key-value storage, so an eviction does not lose it), and notifies once they settle: `finished` when one was answered, `failed` (with the error's text) when one went unanswered for any reason but the owner stopping it (`aborted`, `reset`). A notification the Registry could not take stays pending and goes out with the next settle. A Secret request notifies when it is first asked, in the background so the request neither waits for the push nor is held past an abort (`input`, naming the Secrets and the agent's reason, never a value). A Browser Handoff notifies the same way (a `notice` with the instructions as its body and, as its `url`, the query `?pane=live-view:<requestId>`, which the push puts on the Session's page so a tap opens the handoff's Live View Pane; never a link). A Run that made Agent changes ends with one more `notice`, listing each (tool, Environment name, field) and opening the Session; the changes wait for the next settle when it could not go out (see _Agent capabilities_ → _Agent changes_).

  - **Archive** (`archiveSession`) stops everything the Session runs (its root and every subagent, background work included, through the Session DO's `stopAll`), then sets the record's `archivedAt`. An archived Session leaves the list for a collapsed _Archived (n)_ section, grouped by Environment; its page shows a banner with _Unarchive_ (`unarchiveSession`) in place of the composer. Read-only is the UI's rule only: the Session itself is untouched and kept whole. A Session that could not be stopped is not archived (`SessionActionError`).
  - **Delete** (`deleteSession`, after a confirm dialog) asks the Session DO to `destroy` itself (`apps/server/src/session/lifecycle.ts`): stop everything it runs, close its browser, close its clients' sockets with `SESSION_DELETED_CLOSE_CODE` (4404), close the Harness, and wipe its storage and alarm, after which the object resets; then the Registry forgets the record. The files it wrote in its Workspace stay, its Attachments in `.cloudpid/uploads/<session-id>/` too, and so does the Workspace, while another Session (archived ones too) is bound to it. The last Session's delete removes the Workspace with it, as **Remove** does once its Sessions are gone: the Workspace DO (`destroy`), with what was not committed or pushed, then its record, which the Registry deletes only while no Session is bound to it. The Session is gone by then, so the delete succeeds whatever happens to the Workspace: an object that cannot be wiped is logged and leaves the Workspace listed with no Session, for the owner to remove, and a Session started in it meanwhile keeps the record, its object made again as the Session first works there. The confirm dialog says which of the two the delete does. A client whose socket closes with that code does not reconnect and leaves for `/` with a notice. Once a run finds none left, that isolate does no more. - **Titles:** a background task asks the `small` role for a 3–6 word title (from the first message as the owner typed it, not its expansion), stored in the Registry DO and shown in the Session list. The owner renames a Session from its ⋯ menu or with `/name` (`renameSession`); its header shows the title only.
  - **Source:** a Session's record has a `titleSource`: `owner` (named at creation or renamed), `generated`, or null while it has no title. The Registry enforces the rules, not the Session: `setGeneratedTitle` sets a title only while `titleSource` is null, so a generation never replaces an owner's title (set before or while the model worked) and happens at most once; `renameSession` always wins. There is no way to clear a title.
  - **Task:** the Session host (`apps/server/src/session/titles.ts`) runs it beside the Run, never inside it. Once per answer to a submission to the root conversation (and, in an instance that only resumed work after an eviction, when the Session settles idle), it asks the Registry whether a title is wanted, reads the root's first message and first answer (each cut to 2,000 characters), asks the `small` role's model (the Session's own model, its pick or else the default, if there is no `small` role) for a title through the Session's models, so the request is scrubbed of held Secrets like any other, and offers the sanitized reply to the Registry (first line, no `Title:` label, quotes, markdown, control, zero-width or bidi characters, or ending punctuation, at most 80 characters). Subagent conversations are never named: only the root's messages are read.
  - **Durability:** what it keeps in the Session's storage is whether it is done and how often it failed. An attempt counts when it starts, so an eviction mid-request uses one; a failed request, an empty reply or an unreachable Registry leaves the task open for the next answer or wake, and it gives up after 6 attempts. A Session the owner named is marked done on the first check. The call's tokens and cost are logged (`Session title request`) and added to the Session's spend, kept in the Session's storage because no conversation's `pi.usage` holds them; the call is not held to the spend limit (see _Operations_ → Telemetry).

## Operations

- **Infra:** alchemy `2.0.0-beta.83` with `@effect/platform-node`. Workers and DOs are written in alchemy's Effect form, or as plain classes through Worker `bindings` where a mixin such as `withWorkspace` requires it. Containers use `schedulingPolicy: "durable_object"`.
- **Stages:** `alchemy dev` (workerd and local Docker, stage `dev_$USER`) and a single `prod` stage with `Cloudflare.state()`. GitHub Actions runs `pnpm check` and deploys `prod` on push to `main`. Each pull request from this repository gets a preview stage `pr-<number>` once `check` passes, with its URL in a PR comment, destroyed when the pull request is closed.
- **Access:** every stage's main Worker sits behind a Cloudflare Access application (declared on the Worker's `access` prop) with one policy, allow the owner's email. `prod` is served on `pi.ianpascoe.dev` (`ianpascoe.dev` zone, Access team `spirit-led-software`) and not on `workers.dev`; other stages stay on `workers.dev`.
- **CI credentials:** a second stack, `infra/github.ts` (`cloudpid-github`, stage `ci`), creates the scoped deploy API tokens and the GitHub environments `production` (deployments from `main` only) and `preview` (pull request previews, any branch) with their secrets and variables. See `AGENTS.md` → _Infra_.
- **Telemetry:**
  - **Traces.** `@cloudpid/telemetry` adapts pi-telemetry's `TelemetryContext` to an Effect `Tracer` (`effectTelemetry`), and that tracer to Workers' custom spans (`tracing` from `cloudflare:workers`, `workersTracer`), so every Effect span and every pi span is a span in the Worker's trace, among the runtime's own for fetches, bindings and RPC. Every Worker of the stack sets `observability: { enabled, logs, traces }` (`WORKER_OBSERVABILITY`; head sampling left at the default of 1, as this is one owner's agent). Workers has no way to name a span's parent, only the async context, so a span keeps the context it started in and its descendants run in it. alchemy's `Cloudflare.Telemetry()` makes a tracer per event and cannot serve the Session DO's long-lived runtime, so the Session builds its own once per object; OTLP export to a third party was not needed, since Workers Observability keeps traces (7 days) and is queryable without a new secret. Billing for traces starts on 1 December 2026.
  - **Spans.** `session.connect`, `session.message`, `session.close` and `session.alarm` are the object's invocations; `session.run` runs from a submission's admission to its settling, with the Run's requests and tool calls started under it, so they join the trace of the invocation that submitted it (the Run goes on after the message's reply, and the trace shows it); `session.resume` covers resuming interrupted work after an eviction, so a resumed Run's spans are in the alarm's or the first message's trace instead, and a Run an eviction cut off has no `session.run` end. `pi.ai.request` (provider, API, model, reasoning level, stop reason, token counts, cost, first chunk) is made at the `Models` seam, so it covers generations, compaction summaries, subagents and the title call; `pi.tool.<name>` (conversation, task and call IDs, whether it errored) wraps every tool, including a `codemode` script's nested calls. A failed request records how it failed (`retryable`, `context_overflow` or `other`, by pi-ai's own classifiers), not the provider's text, and a span carries only the events pi raises (a short dotted name): Effect's logger turns every log made inside a span into an event named by its message, which the Workers tracer leaves out. Prompts, tool arguments and results are never recorded. The pi-durable 1.3.0 Harness emits no spans of its own (it has no `telemetry` option; pi-ai only passes a `telemetryContext` through), so these are made at the seams the Session owns; `effectTelemetry` is the adapter to pass as `HarnessOptions.telemetry` once a release has one, and the wrappers are then taken out.
  - **Usage.** `pi.usage` is pi-durable's ledger per conversation; the Session's total is shown in its header (`watch_usage`, see _Client and protocol_). The title calls have no conversation, so their usage is kept in the Session's storage (`title-usage`) and added to the total.
  - **Container cost.** Each Workspace DO keeps what its Containers have cost (`ContainerUsageLedger`, `apps/server/src/workspace/container-usage.ts`; storage key `cloudpid:container-usage`), shown in the header of every Session in the Workspace (Sessions that share one each show all of it), at Cloudflare's list prices (`CONTAINER_PRICES`, `@cloudpid/config`; the plan's monthly allowance is the account's and is not taken off). The figures are Cloudflare's usage analytics (the GraphQL Analytics API's `containersUsageAdaptiveGroups`, the dataset behind the dashboard's estimate, which counts real CPU time, the micro VM and egress), filtered by the label every launch carries (`cloudpid-ws=<object id>`, set by `ContainerLaunch`; workerd allows label names of at most 16 bytes and values of at most 64; computer does not compare labels, so adding them relaunches nothing). They trail by minutes, so they are asked up to 5 minutes ago, at most once a minute, in the background of a read (the read answers with what it holds); usage over an hour old is settled (asked once and added to a kept sum, in windows of at most a day, back at most 30 days) and the hour since is asked again at each refresh. After what they cover, and throughout when the deployment has no analytics token (`CLOUDPID_ANALYTICS_TOKEN`, with `CLOUDFLARE_ACCOUNT_ID`; `alchemy dev`, local deploys without it) or they fail (one warning per run of failures), the cost is estimated from what the Workspace saw: each launch is a run from its launch record's `launchedAt` to its stop (the idle stop, a restart, a Build's stop, the removal) or, for a Container gone on its own, its last sighting (a use, written at most every 30 s); memory and disk are priced for every second of a run on its size (`INSTANCE_RESOURCES`), and CPU as every vCPU at full use while a command ran (the idle stop's `begin`/`end`), as the Workspace cannot see a Container's CPU. The run time shown is the Workspace's own count. A Container that was running when the labels were introduced is unlabelled until its next launch, so the analytics miss it. The cost is not held to the spend limit.
  - **Spend limit** ([ADR-0010](adr/0010-telemetry-at-the-seams-the-session-owns.md)). `spendLimit.perSession` (USD; off by default, because what a Session is worth depends on the work and the proxy's own key limits bound a runaway) is enforced at the Session's `Models`, as secret scrubbing and the image limit are: a request made when the Session has spent the limit is refused before it reaches the proxy, and ends as an error message ("This Session is out of budget: …") that the Harness ends the Run with, `unanswered` for `model_error` with that text, which the owner's failed-Run push carries. This replaces the `beforeRequest` hook the plan named: pi-durable 1.3.0's hook can only rewrite messages, and one that throws is reported and skipped, so it cannot stop a request; the seam also covers compaction and summaries, which the hook would not. The check runs at each request: those under way when the limit is crossed finish, so a Session overshoots by what they cost (one request per live conversation), and a refused request costs nothing. Subagents share the Session's limit: their requests go through the same `Models` and are held to it (a child's turn ends `failed` for `model_error`, and so does the root's next request), and the total they are held to is the Session's. The text avoids pi-ai's retry markers (`out of budget` is its own non-retryable marker). The title call counts toward the spend but is not refused: it costs a few tokens, and a refused one would leave the Session unnamed. A limit raised or cleared in the settings applies to the next request and a Run continues with a new prompt. If the ledger cannot be read, the request goes through and a warning is logged.

## Known risks and spikes

- **Worker Shell `git status` is not git's.** `git status` stays on the Worker Shell because a cheap status is what the model runs most, but `@cloudflare/computer` 0.5.1's client prints `1 XY path` and `? path` lines (not git's long format), sorts them by path, lists untracked files one by one (git collapses a directory to `dir/`), and gets the staged column wrong whenever the index holds staged entries: a staged, otherwise clean modification prints `MM` (git: `M `), a staged new file `AM` (git: `A `), and a staged new file modified again `A ` (git: `AM`). Unstaged changes, deletions, and untracked files match git, and `.gitignore` is honored. Staged entries come from `git add`, which runs in the Container and reaches the Worker Shell through sync, so `git add` then `git status` is the case that is wrong; if that proves a problem in practice, route `status` to the Container too (one entry in `GIT_ON_WORKER`, at the cost of #22's acceptance example). A tracked file under `TOOLCHAIN_IGNORE` shows as deleted, since the Worker Shell's tree does not hold ignored paths. The Worker Shell and the Container have two different git implementations over one tree, so a repository one wrote is read by the other; the Workspace DO builds the Worker Shell's git client anew for every call (`workerShellGit`, `git.ts`), because one long-lived client caches the index and, having read a repository before its first `git add` (no `.git/index`), kept reporting every committed file as deleted after the Container committed (seen deployed; the workerd test replays it with files real git wrote).
- **Worker Shell git memory.** isomorphic-git reads a whole packfile into memory, and the Workspace DO has 128 MB for everything it hosts, so `git status` or `git log` in a clone with a big pack could take the Workspace down. The Worker Shell's git client (`apps/server/src/workspace/git.ts`) is built anew for every call, so a pack is read again each time, and it refuses any command in a repository whose `.git/objects/pack/*.pack` files total more than 16 MB (`MAX_PACK_BYTES`): the command fails with a message to rerun with `backend: "container"`. Loose objects are not counted, and 16 MB is a conservative guess, not a measurement of where the DO runs out.
- **Preview packages.** `@cloudflare/computer` is a preview: its container backend, the Worker Shell, and computerd are experimental. Pin versions and keep the image and package in lockstep.
- **Unreleased pi-durable features.** `onWake` is not in pi-durable 1.3.0, so the heartbeat fallback is needed until the next release.

- **Exposure of the shared browser session.** Raw CDP in the shared browser session can read cookies and filled values, so prompt injection from pages is the main threat. Mitigations are host-side fills, origin checks, and per-item approval. A Browser Handoff's Live View link is part of this exposure. A link opens **every page of the browser session**, not only the tab it names (putting another page's target ID in its path connects to that page), and connects any number of times until its deadline, 60 s after it was minted; Browser Run cannot revoke it, and its `expiresInMs` only bounds when a connection may _start_: a connection opened in time outlives it (the spike kept two open for 15 minutes), and Done, Failed, or Stop does not close it. Anyone holding a link within its minute, or a connection opened with one, controls the shared, logged-in browser and can watch later work in it. So links are minted only when the owner's Live View Pane asks (`live_view`, or **Open in Cloudflare**), one per open or reconnect, and go to that client alone: none is stored in the Session or the browser host, sent to other clients, put in a push, or shown to the agent ([ADR-0013](adr/0013-own-live-view-with-links-minted-on-open.md)). The Pane's own connections are the owner's to close; the Pane closes when the handoff ends.
