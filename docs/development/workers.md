# Workers, bindings and workerd tests

The rules the platform imposes on the stack's Workers, which the code cannot show. The Workers and Durable Objects themselves are described in [`../architecture/overview.md`](../architecture/overview.md).

## Effect Workers and plain Workers

A Worker is declared in its own app with `main: import.meta.url`; the stack (`infra/alchemy.run.ts`) imports and `yield*`s it. That makes it an Effect Worker, whose generated entry exports only `default` and its Effect DO classes.

A Worker that must export anything else (a plain DO class, a `WorkerEntrypoint` such as `@cloudflare/computer`'s `WorkspaceServiceProxy`) is a plain async Worker instead: its entry module (`main: new URL("./worker.ts", import.meta.url).href`) holds no alchemy code, and a separate resource file declares it, as `apps/server/src/workspace/` does for `Workspaces`. A Worker that exports only a `default { fetch }` and has nothing of alchemy's to run is declared plain too, to keep the Effect runtime and alchemy's generated entry out of a public, cold-started Worker (the App sandbox). The plain Workers are:

- **`Workspaces`** (`apps/server/src/workspace/`): the Workspace DO, `WorkspaceServiceProxy`, `WorkspaceProxy` and `ContainerExitReports`, and two entrypoints that each reach one call of the DO, only for a Workspace's object (`ws:<id>`, never a Build's): `WorkspaceContainerPreviews` (bound by `Browsers`, below) and `WorkspaceMcpBridge`, `mcpBridge(workspace, request, { start, use })`, which `McpWorker` is to bind as `MCP_BRIDGE` (#460; `Cloudflare.WorkerEntrypoint(workspaces, "WorkspaceMcpBridge")`, so `Workspaces` deploys first) to reach a Workspace's Container MCP bridge ([_The stdio bridge_](../architecture/mcp-connections.md#the-stdio-bridge)). Its refusals (404 `no_workspace`, 503 `stopped`, 502 `start_failed` and `bridge_unreachable`) have a fallback member, `bridge_failed`, which a caller reads an unknown code as; its codes and options are `@cloudpid/sandbox-image/mcp-bridge`'s, which the engine imports. The entrypoint's methods only gain.
- **`Browsers`** (`apps/browser`): the `BrowserHost` DO, `@cloudflare/codemode`'s `CodemodeRuntime` (the facet `agents/browser`'s tool keeps its runs in) and `ContainerPreviews`, the entrypoint Browser Run's outbound Workers send the Container previews' hosts to (ADR-0023; the host makes it with `ctx.exports`). Its bindings are `BROWSER` (Browser Run, `Cloudflare.Browser()`), a Worker Loader `LOADER`, and `CONTAINER_PREVIEWS`, a service binding to the Workspaces Worker's `WorkspaceContainerPreviews` entrypoint (`Cloudflare.WorkerEntrypoint(workspaces, "WorkspaceContainerPreviews")`; `Browsers({ workspaces })` takes that Worker's resource, so it deploys first). `apps/browser` cannot import `@cloudpid/server`, which imports it.
- **`AppSandbox`** (`apps/app-sandbox`): the public App sandbox. It serves the MCP App proxy page and `/proxy.js` on the route `*.ianpascoe.app/*` (ADR-0031; [_The App sandbox_](../architecture/mcp-apps.md#the-app-sandbox)), with its proxied wildcard record `*.ianpascoe.app AAAA 100::` declared beside it (`resource.ts`; the zone's id is `APP_ZONE_ID` in `view-host.ts`, which `infra/github.ts` shares). It is **public and prod-only**: no Access, no secret, no binding, no cookie read or set, `workersDev: false`; `infra/alchemy.run.ts` declares it only when `stage === "prod"`, so every other stage frames prod's. Its entry (`worker.ts`) imports its own modules, the pure `@cloudpid/server/deployment` and `@cloudpid/server/view-host`, and `effect` (`Schema` and `Option`, for the `?csp=` JSON). `apps/app-sandbox` is a dependency of `infra` only: nothing imports it into `Server`, so the package graph has no cycle. Its tests are node tests for the pure modules and the proxy script, and `worker.workerd.test.ts`, which needs no bindings (`bun --cwd apps/app-sandbox vitest run --project workerd`).
- **`CodemodeSandboxes`** (`apps/codemode-sandbox`): pi-codemode's `CodemodeSandboxDurableObject`, exported as `CodemodeSandbox`. It bundles QuickJS's `.wasm` as a compiled module through alchemy's own rolldown rule.
- **`McpWorker`** (`apps/mcp-worker`): `McpEngine`, the stateless `WorkerEntrypoint` that runs the MCP SDK for `McpHost`; `McpServer`, the MCP endpoint's `WorkerEntrypoint` (`serve(request, api)`, over `serveMcp` from `@cloudpid/mcp/server`; `Server` binds it as `MCP_SERVER` and routes `/mcp` to it after its guard); and a `default` that answers 404. It runs without `nodejs_compat`: the SDK client, Effect and TypeBox need none, and its workerd tests run its own bundle without the flag. Its only binding is `CF_VERSION_METADATA` (`Cloudflare.Workers.VersionMetadata()`), the version it names itself by in `clientInfo` and, for `McpServer`, in `serverInfo`.

The App sandbox has `workersDev: false` and the one route above and no one calls it. The browser, codemode sandbox and MCP Workers have `workersDev: false` and no routes: nothing reaches them but the Session DOs' `BROWSER_HOST` and `CODEMODE_SANDBOX` bindings and `Server`'s `MCP_ENGINE`, declared in `apps/server/src/worker.ts` with each Worker's Output (its `scriptName`, or the Worker itself for `Cloudflare.WorkerEntrypoint(mcpWorker, "McpEngine")`), not a literal, so they deploy first: Workspaces, then Browsers, CodemodeSandboxes and `McpWorker`, then `Server`.

- **A stateless Worker's isolate is shared by its calls.** Each RPC call to an entrypoint is an invocation of its own, and a timer belongs to the invocation that set it: one that ends (as an `McpEngine` call does once its result stream is read) takes its pending timers with it. So isolate-wide state one call waits on and another releases (`McpEngine`'s byte budget) wakes its waiters synchronously at the release, never through a timer such as Effect's `Semaphore` schedules (`apps/mcp-worker/src/budget.ts`).

## Bindings

- **Call an RPC binding's methods directly** (`binding.acquire(options)`). Reading anything else off one, such as `binding.acquire.bind`, is itself an RPC call to the binding, which fails.
- **Every RPC edge only ever gains**, Durable Object ↔ Durable Object and Worker → Durable Object inside one Worker included. Workers deploy separately, and inside one Worker a busy Durable Object keeps its old code for up to `max_delay` (see _Deploys and Durable Object code updates_), so either end of an edge may run older code than the other. An RPC surface only gains methods, operations, tags and trailing optional arguments or fields, never changes existing ones:
  - A change of meaning is a new method or operation, never an optional field: an old callee's Effect Schema drops keys it does not know.
  - An unknown method or operation fails loudly (`Unsupported`), never as a decode error.
  - Unions the other end may extend (failure tags, states) have a fallback member that reads as a generic failure, in RPC and in storage alike.
  - A removal merges at least 24 h after the change that stopped using it reached prod, or after the retention of any stored payload that can hold it.
  - Where a caller would offer something on its callee's behalf, the callee lists its features and the caller uses a new one only once it is listed.
- **A `fetch` through a service binding into `Server` is refused.** The main Worker verifies the Access assertion on every request (`apps/server/src/access.ts`), and a service binding carries none, so it gets a 403. Internal callers use an RPC entrypoint of the Worker, never its `fetch`. Nothing calls `Server` through a binding today.
- **`MCP_SERVER`** (`McpWorker`'s `McpServer` entrypoint, bound like `MCP_ENGINE`): `serve(request, api)` gets the caller's `Request` (no identity header, cookie or `Authorization`, and no `AbortSignal`, which RPC cannot carry) and an `RpcTarget` the main Worker builds per request. A stub that lasts past the call is `dup()`ed and released when the SSE body ends. The `api` target loads `cloudflare:workers`' `RpcTarget` with a dynamic import, since the stack imports `worker.ts` under Node. A failed call is a `503` with `Retry-After` from `Server`.
- **`MCP_CALLS`** (`Cloudflare.RateLimit`, 120 per 60 s per identity; absent under `alchemy dev`, which means no limit): counted per `tools/call` through the `api` target's `limited` getter. Its namespace id is a hash of the stage, so a preview stage does not count in prod's.
- **`MCP_ENGINE`** (`McpWorker`'s `McpEngine` entrypoint, bound by `Server` through `McpWorker`'s Output, so `McpWorker` deploys first): `McpHost` calls `discover` and `request` with its hooks (`untilAborted`, `auth`, `opened`) as function stubs, which live only as long as the calling invocation, so the caller awaits the call for its whole length. Values cross by structured clone, so each result is encoded with `@cloudpid/mcp/types`' Schemas, failures through `McpErrorWire`, and decoded by the caller; a result over 1 MiB is a native `ReadableStream` inside it, which RPC passes without cloning. `McpEngine` holds each call under `ctx.waitUntil`, or a caller's death would cancel it silently instead of rejecting `untilAborted()`.
- **`IMAGES`** (`Cloudflare.Images.Images`, declared in `apps/server/src/worker.ts`) has no backing resource and rides on the script upload. `alchemy dev` emulates it locally with sharp (size and format, not quality).
- **Custom spans**: the Session DO imports `tracing` from `cloudflare:workers` when an object is built, not at module load, since the stack imports `Session.ts` under Node. It needs compatibility date 2026-07-28 or later (the stack uses 2026-08-31). The spend limit and usage are in `apps/server/src/session/spend.ts`.

## Deploys and Durable Object code updates

- **Durable Objects defer code updates.** The stack keeps the platform's default strategy, `deferred` with a `max_delay` of 300 s ([Durable Objects code updates](https://developers.cloudflare.com/durable-objects/deployments/durable-objects-code-updates/)); it is set per Worker, for every Durable Object class in it, and alchemy cannot declare another. An idle object starts on the new code at its next request. A busy one keeps its old code, and keeps taking new requests on it, until it hibernates or `max_delay` passes. `immediate` would not close the skew either: code updates reach every location eventually.
- **A replaced instance finishes its calls without storage.** When `max_delay` passes, new requests reach a new instance. The old one keeps running the calls it has, its callbacks still answer and it still returns results, but every storage operation fails. Nothing tells it; a failed storage operation is how it learns.
- **Stateless invocations keep their version until they end.** A plain Worker's call in flight, an entrypoint's included, finishes on the version it started on, however many deploys follow (15 min observed).
- **Reverts.** A rollback is a revert merged to `main`, deployed by the normal pipeline. Reverting the latest change is safe, since removals take two steps; reverting past a removal is not. A revert never drops a migration that reached prod: `migrate` (`@cloudpid/effect-durable/sqlite`) numbers migrations by their position, so a reused number never runs on objects that ran the reverted one. Keep the migration and add one that undoes it. A manifest of each shipped migration's digest guards this (the Registry's is `apps/server/src/registry/migrations.manifest.ts` and McpHost's is `apps/server/src/mcp/migrations.manifest.ts`, each checked by its test): the test fails a migration at a shipped position that changed or went missing, and one not recorded yet, so append the digest it prints in the PR that adds the migration, and never edit or remove a line. The manifest is append-only, and CI enforces it: a pull request's `Migration manifests` job (`scripts/check-migration-manifests.sh`, over the PR's base commit) fails when a digest that is in the base is not still at the same position, so a plain `git revert` of the change that added a migration, which removes its manifest line too, fails until the line is restored; the manifest test then fails the migration that went missing. Keep the migration and its line, and add one that undoes it. Two branches that add a migration conflict on the manifest's last line. A new object with migrations adds its own manifest and test (`shippedMigrationProblems`, `@cloudpid/effect-durable/sqlite/testing`). An old reader that rewrites a row drops keys it does not know, so new fields stay optional.

## The Workspace DO

- **Peers of `@cloudflare/computer`.** The Worker Shell's `jq` is an optional computer module (`@cloudflare/computer/shell/jq`), its `git` needs `createGitClient()`, which loads `@platformatic/vfs`, and the Worker Shell itself needs `just-bash`; the Workspace DO passes them (`Workspace.ts`). Every package that depends on `@cloudflare/computer` (`apps/server`, `packages/computer-env`) lists `@platformatic/vfs` and `just-bash` too, so pnpm resolves one instance of computer (two give mismatched types).
- **`mkdir -p` above a read-only mount.** computer refuses `mkdir -p` of any path above a read-only mount (the Skill set's, at `/workspace/.agents/skills`), `/workspace` included, though the directory exists. `ensureDirectory` (`packages/computer-env`) makes that a no-op for the file operations and, through `GuardedFilesystem` (`apps/server/src/workspace/tracked.ts`), for the Worker Shell. A Workspace stub that does not extend `TrackedWorkspaceStub` must return a `GuardedFilesystem` as its `fs`.
- **`bash` routing lists.** When computer or its shell changes what the Worker Shell runs, update `WORKER_SHELL_COMMANDS`, `WORKER_SHELL_BUILTINS`, `CONTAINER_PROGRAMS` and the git subcommands in `packages/extensions/src/bash-routing.ts`. `apps/server/src/workspace/bash.workerd.test.ts` runs the lists through the real shell and checks each git form against real git's output. Only read-only `git` forms run on the Worker Shell, because its git (isomorphic-git) is not always git's.
- **Container-only paths' scripts** (`container-files.ts`) are tested in plain bash in `container-files.test.ts`; deployed, they run through computerd's FUSE mount, which the tests do not have. They need the Container's GNU coreutils and findutils, as the Container's other scripts need its Linux tools (`apps/sandbox-image/src/host.fixture.ts`): on a host without them, such as macOS, those tests skip, and under `CI` they never do. The two grep tests skip wherever `rg` is missing, CI included.

## workerd tests

Tests that need workerd (Durable Object storage, alarms, eviction) are `src/**/*.workerd.test.ts`, run by the package's `workerd` Vitest project through `@cloudflare/vitest-plugin` (see `apps/server/vitest.config.ts`): `bun --cwd <package dir> vitest run --project workerd <file>`. Give miniflare what the code under test binds:

- **Browser host:** the facet class as a Durable Object too (`CODEMODE_RUNTIME`, else `ctx.exports.CodemodeRuntime` is not a class), `workerLoaders: { LOADER: {} }`, and a stand-in Workspaces Worker for `CONTAINER_PREVIEWS` (an auxiliary `workers` entry; see `apps/browser/vitest.config.ts`).
- **Workspace DO** (`workspaceOnly` in `apps/server/vitest.config.ts`): `workerd.fixture.ts`'s `TestWorkspace` stands in for the Container and what runs on it: `fakeContainer`, `fakeDevServer` (the Container previews) and `fakeBridge` (the MCP bridge: its health, its answers, a stream the test writes to, and the launch record's token from `seedLaunchRecord`), and counts the idle stop's uses and holds (`mcpBridgeUses`, `mcpBridgeHolds`). `WorkspaceMcpBridge`'s tests call the entrypoint (`exports.WorkspaceMcpBridge`) and the DO's `mcpBridge` directly.
- **Codemode sandbox:** `modulesRules: [{ type: "CompiledWasm", include: ["**/*.wasm"] }]`.
- **MCP engine** (`apps/mcp-worker/vitest.config.ts`): the test Worker needs `nodejs_compat`, and `McpWorker` must run without it, so `McpWorker` is an auxiliary Worker: the config bundles `src/worker.ts` as alchemy deploys it (rolldown with `@alchemy.run/cloudflare-runtime/rolldown`) and binds its `McpEngine` as `MCP_ENGINE`. Its `outboundService` is a second auxiliary Worker of fake MCP servers (`src/fakes.fixture.ts`, over `@cloudpid/mcp/testing`, which `apps/*` may import where they may not import the SDK), so every `fetch` the engine makes reaches a fake. A host that dies mid-call is a `Caller` Durable Object of the test Worker that calls the engine and then `ctx.abort()`s itself. The same auxiliary Worker's `McpServer` is bound as `MCP_SERVER`, and `src/server.workerd.test.ts` drives it with pi-mcp's `McpClient` over a `StreamableHttpTransport` whose `fetch` is the binding's `serve`, given an `RpcTarget` fake of the main Worker's `api`.
- **Web assets:** the `workerd-assets` project binds the real asset layer (`assets: { directory, binding: "ASSETS", assetConfig: { not_found_handling: WEB_NOT_FOUND_HANDLING } }`, the directory a fixture app in `apps/server/src/assets.fixture/`), and `src/assets.workerd.test.ts` runs only there (`bun --cwd apps/server vitest run --project workerd-assets src/assets.workerd.test.ts`); the `workerd` project excludes it. The asset layer's answer for a missing path is the point of the test, so the config must be the deploy's.
- **Images:** `images: { binding: "IMAGES" }`, as the `workerd-session` project does.
- **A replaced instance:** `refusingStorage(storage)` (`@cloudpid/effect-durable/sqlite/testing`) wraps the storage `runInDurableObject` gives (`state.storage`) and returns `{ storage, trip }`. Give the code under test `storage`, run its call, and `trip()` where the code update would reach it: from then on `sql.exec`, `transactionSync` and the other synchronous members throw, and `get`, `put` and the other Promise-returning ones return a rejected Promise, as the platform's do, while the calls in flight, their callbacks and their results carry on, as on a replaced instance (_Deploys and Durable Object code updates_). The real storage is untouched, so the test reads it through a new instance afterwards. The pattern: open the object's store over `storage`, call, `trip()`, assert the refused writes left no trace and the call still returned its result (best-effort writes) or failed as designed, then check what a new instance sees (`apps/server/src/registry/store.workerd.test.ts`). `ctx.abort()` is not a substitute: it rejects the calls in flight, the opposite of a replaced instance.
