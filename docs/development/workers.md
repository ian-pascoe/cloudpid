# Workers, bindings and workerd tests

The rules the platform imposes on the stack's Workers, which the code cannot show. The Workers and Durable Objects themselves are described in [`../architecture/overview.md`](../architecture/overview.md).

## Effect Workers and plain Workers

A Worker is declared in its own app with `main: import.meta.url`; the stack (`infra/alchemy.run.ts`) imports and `yield*`s it. That makes it an Effect Worker, whose generated entry exports only `default` and its Effect DO classes.

A Worker that must export anything else (a plain DO class, a `WorkerEntrypoint` such as `@cloudflare/computer`'s `WorkspaceServiceProxy`) is a plain async Worker instead: its entry module (`main: new URL("./worker.ts", import.meta.url).href`) holds no alchemy code, and a separate resource file declares it, as `apps/server/src/workspace/` does for `Workspaces`. A Worker that exports only a `default { fetch }` and has nothing of alchemy's to run is declared plain too, to keep the Effect runtime and alchemy's generated entry out of a public, cold-started Worker (the App sandbox). The plain Workers are:

- **`Workspaces`** (`apps/server/src/workspace/`): the Workspace DO, `WorkspaceServiceProxy`, `WorkspaceProxy` and `ContainerExitReports`, and two entrypoints that each reach one call of the DO, only for a Workspace's object (`ws:<id>`, never a Build's): `WorkspaceContainerPreviews` (bound by `Browsers`, below) and `WorkspaceMcpBridge`, `mcpBridge(workspace, request, { start, use })`, which `McpWorker` binds as `MCP_BRIDGE` (`McpWorker({ workspaces })` in `apps/mcp-worker/src/resource.ts`, `Cloudflare.WorkerEntrypoint(workspaces, "WorkspaceMcpBridge")`, so `Workspaces` deploys first) to reach a Workspace's Container MCP bridge ([_The stdio bridge_](../architecture/mcp-connections.md#the-stdio-bridge)). Its refusals (404 `no_workspace`, 503 `stopped`, 502 `start_failed` and `bridge_unreachable`) have a fallback member, `bridge_failed`, which a caller reads an unknown code as; its codes and options are `@cloudpid/sandbox-image/mcp-bridge`'s, which the engine imports. The entrypoint's methods only gain.
- **`Browsers`** (`apps/browser`): the `BrowserHost` DO, `@cloudflare/codemode`'s `CodemodeRuntime` (the facet `agents/browser`'s tool keeps its runs in) and `ContainerPreviews`, the entrypoint Browser Run's outbound Workers send the Container previews' hosts to (ADR-0023; the host makes it with `ctx.exports`). Its bindings are `BROWSER` (Browser Run, `Cloudflare.Browser()`), a Worker Loader `LOADER`, and `CONTAINER_PREVIEWS`, a service binding to the Workspaces Worker's `WorkspaceContainerPreviews` entrypoint (`Cloudflare.WorkerEntrypoint(workspaces, "WorkspaceContainerPreviews")`; `Browsers({ workspaces })` takes that Worker's resource, so it deploys first). `apps/browser` cannot import `@cloudpid/server`, which imports it.
- **`AppSandbox`** (`apps/app-sandbox`): the public App sandbox. It serves the MCP App proxy page and `/proxy.js` on the route `*.ianpascoe.app/*` (ADR-0031; [_The App sandbox_](../architecture/mcp-apps.md#the-app-sandbox)), with its proxied wildcard record `*.ianpascoe.app AAAA 100::` declared beside it (`resource.ts`; the zone's id is `APP_ZONE_ID` in `view-host.ts`, which `infra/github.ts` shares). It is **public and prod-only**: no Access, no secret, no binding, no cookie read or set, `workersDev: false`; `infra/alchemy.run.ts` declares it only when `stage === "prod"`, so every other stage frames prod's. Under `alchemy dev` the stack declares **`LocalAppSandbox`** (same entry, `dev: { port: 1338, strictPort: true }`, `CLOUDPID_APP_SANDBOX_LOCAL=true`, no route) instead, which serves every View at `http://127.0.0.1:1338` and takes the app origin from `?host=` when it is `http://localhost:1337` or `:5173`. Its entry (`worker.ts`) imports its own modules, the pure `@cloudpid/server/deployment` and `@cloudpid/server/view-host`, and `effect` (`Schema` and `Option`, for the `?csp=` JSON). `apps/app-sandbox` is a dependency of `infra` only: nothing imports it into `Server`, so the package graph has no cycle. Its tests are node tests for the pure modules and the proxy script, and `worker.workerd.test.ts`, which needs no bindings (`bun --cwd apps/app-sandbox vitest run --project workerd`).
- **`CodemodeSandboxes`** (`apps/codemode-sandbox`): pi-codemode's `CodemodeSandboxDurableObject`, exported as `CodemodeSandbox`. It bundles QuickJS's `.wasm` as a compiled module through alchemy's own rolldown rule.
- **`McpWorker`** (`apps/mcp-worker`): `McpEngine`, the stateless `WorkerEntrypoint` that runs the MCP SDK for `McpHost`; `McpServer`, the MCP endpoint's `WorkerEntrypoint` (`serve(request, api)`, over `serveMcp` from `@cloudpid/mcp/server`; `Server` binds it as `MCP_SERVER` and routes `/mcp` to it after its guard); and a `default` that answers 404. It binds the Workspaces Worker's `WorkspaceMcpBridge` as `MCP_BRIDGE`, through which `McpEngine` reaches a stdio server in a Workspace's Container (`src/bridge.ts`). It runs without `nodejs_compat`: the SDK client, Effect and TypeBox need none, and its workerd tests run its own bundle without the flag. It runs with `global_fetch_strictly_public` (`src/compatibility.ts`, which its deploy and its workerd tests share): without it, a Worker's `fetch` to a Worker on the same zone fails with error 1042 (a `workers.dev` host of the account included), and one to the Worker's own zone goes to the origin past Cloudflare's security settings, Access among them; with it, the engine's `fetch` goes through the front door as the Internet's would, so an MCP server on one of cloudpid's own hosts (Self-use, [`mcp-endpoint.md` → _Self-use_](../architecture/mcp-endpoint.md#self-use)) or on another Worker of the account is reached through its Access. It changes nothing else the engine reaches: a public host is reached as before, and `MCP_BRIDGE` is a service binding. `McpEngine` also answers `fetchPublic`, the Registry's sign-in read on one of cloudpid's own hosts, for the same reason ([`mcp-sign-in.md` → _Code_](../architecture/mcp-sign-in.md#tokens-reach-the-host-object)). The Server Worker has no such flag: its `fetch` to a same-zone host (prod's model proxy, `api.ai.ianpascoe.dev`) stays as it is. Its other binding is `CF_VERSION_METADATA` (`Cloudflare.Workers.VersionMetadata()`), the version it names itself by in `clientInfo` and, for `McpServer`, in `serverInfo`.

The App sandbox has `workersDev: false` and the one route above and no one calls it. The browser, codemode sandbox and MCP Workers have `workersDev: false` and no routes: nothing reaches them but the Session DOs' `BROWSER_HOST` and `CODEMODE_SANDBOX` bindings and `Server`'s `MCP_ENGINE`, declared in `apps/server/src/worker.ts` with each Worker's Output (its `scriptName`, or the Worker itself for `Cloudflare.WorkerEntrypoint(mcpWorker, "McpEngine")`), not a literal, so they deploy first: Workspaces, then Browsers, CodemodeSandboxes and `McpWorker`, then `Server`.

- **A stateless Worker's isolate is shared by its calls.** Each RPC call to an entrypoint is an invocation of its own, and a timer belongs to the invocation that set it: one that ends (as an `McpEngine` call does once its result stream is read) takes its pending timers with it. So isolate-wide state one call waits on and another releases (`McpEngine`'s byte budget) wakes its waiters synchronously at the release, never through a timer such as Effect's `Semaphore` schedules (`apps/mcp-worker/src/budget.ts`).

## Bindings

- **Call an RPC binding's methods directly** (`binding.acquire(options)`). Reading anything else off one, such as `binding.acquire.bind`, is itself an RPC call to the binding, which fails.
- **Every RPC edge only ever gains**, Durable Object ↔ Durable Object and Worker → Durable Object inside one Worker included. Workers deploy separately, and inside one Worker a busy Durable Object keeps its old code for up to `max_delay` (see _Deploys and Durable Object code updates_), so either end of an edge may run older code than the other. An RPC surface only gains methods, operations, tags and trailing optional arguments or fields, never changes existing ones:
  - A change of meaning is a new method or operation, never an optional field: an old callee's Effect Schema drops keys it does not know.
  - An unknown method or operation fails loudly (`Unsupported`), never as a decode error.
  - Unions the other end may extend (failure tags, states) have a fallback member that reads as a generic failure, in RPC and in storage alike. The fallback may be an existing neutral member, where adding one (`unknown`) would change a client protocol, and the field then says what its fallback means for each reader: a stored Session status falls back to `idle` in a record, and the running cap counts it as running all the same.
  - A result union, statuses and refusals alike, gains a member only for a caller that asks for it, through a new method or an argument that brings it, as `createSession`'s `maxRunning` brings `too-many-running`; its readers switch on the members they know, and one that would otherwise take an unknown member as a success refuses it.
  - A removal merges at least 24 h after the change that stopped using it reached prod, or after the retention of any stored payload that can hold it.
  - Where a caller would offer something on its callee's behalf, the callee lists its features and the caller uses a new one only once it is listed.
- **A `fetch` through a service binding into `Server` is refused.** The main Worker verifies the Access assertion on every request (`apps/server/src/access.ts`), and a service binding carries none, so it gets a 403. Internal callers use an RPC entrypoint of the Worker, never its `fetch`. Nothing calls `Server` through a binding today.
- **`MCP_SERVER`** (`McpWorker`'s `McpServer` entrypoint, bound like `MCP_ENGINE`): `serve(request, api)` gets the caller's `Request` (no identity header, cookie or `Authorization`, and no `AbortSignal`, which RPC cannot carry) and an `RpcTarget` the main Worker builds per request. A stub that lasts past the call is `dup()`ed and released when the SSE body ends. The `api` target loads `cloudflare:workers`' `RpcTarget` with a dynamic import, since the stack imports `worker.ts` under Node. A failed call is a `503` with `Retry-After` from `Server`.
- **`MCP_CALLS`** (`Cloudflare.RateLimit`, 120 per 60 s per identity; absent under `alchemy dev`, which means no limit): counted per `tools/call` through the `api` target's `limited` getter. Its namespace id is a hash of the stage, so a preview stage does not count in prod's.
- **`MCP_ENGINE`** (`McpWorker`'s `McpEngine` entrypoint, bound by `Server` through `McpWorker`'s Output, so `McpWorker` deploys first): the Registry calls `fetchPublic` for a sign-in hop to one of cloudpid's own hosts (a `McpWorker` without it is read past: the hop is sent from `Server`); `McpHost` calls `discover` and `request` with its hooks (`untilAborted`, `onProgress`, `auth`, `opened`) as function stubs, which live only as long as the calling invocation, so the caller awaits the call for its whole length (a Session's `tools/call` passes its own `untilAborted` and `onProgress` through `McpHost.request` to the engine). Values cross by structured clone, so each result is encoded with `@cloudpid/mcp/types`' Schemas, failures through `McpErrorWire`, and decoded by the caller; a result over 1 MiB is a native `ReadableStream` inside it, which RPC passes without cloning. `McpEngine` holds each call under `ctx.waitUntil`, or a caller's death would cancel it silently instead of rejecting `untilAborted()`.
- **`IMAGES`** (`Cloudflare.Images.Images`, declared in `apps/server/src/worker.ts`) has no backing resource and rides on the script upload. `alchemy dev` emulates it locally with sharp (size and format, not quality).
- **Custom spans**: the Session DO imports `tracing` from `cloudflare:workers` when an object is built, not at module load, since the stack imports `Session.ts` under Node. It needs compatibility date 2026-07-28 or later (the stack uses 2026-08-31). The spend limit and usage are in `apps/server/src/session/spend.ts`.

## Deploys and Durable Object code updates

- **Durable Objects defer code updates.** The stack keeps the platform's default strategy, `deferred` with a `max_delay` of 300 s ([Durable Objects code updates](https://developers.cloudflare.com/durable-objects/deployments/durable-objects-code-updates/)); it is set per Worker, for every Durable Object class in it, and alchemy cannot declare another. An idle object starts on the new code at its next request. A busy one keeps its old code, and keeps taking new requests on it, until it hibernates or `max_delay` passes. `immediate` would not close the skew either: code updates reach every location eventually. A deploy that uploads `Server` resets each of its objects still busy 300 s after it, and a Session's tool call in flight settles as one that may have partially run (a wait that is safe to rerun is rerun, but counts toward pi-durable's restart limit). A merge that changes nothing `Server` is built from (its bundle, its assets, its bindings and props), such as one that changes only tests, fixtures or CI, plans `[Server] noop` and resets nothing ([`infra.md` → _CI_](infra.md#ci)).
- **`max_delay` stays at 300 s** (owner's decision on [#626](https://github.com/ian-pascoe/cloudpid/issues/626), 2026-11-04). Every deploy used to upload `Server`, so every merge reset the Sessions busy past it; the first fix was to stop deploys that change nothing at runtime from uploading it (above), not to wait longer. A longer `max_delay` (1800 s was proposed) would let most Runs finish before a reset, but it reverses #423 D2, widens the version skew from 5 to 30 minutes, needs an alchemy patch to send `code_update_strategy` and an `immediate` override for urgent fixes, and the web ↔ Session socket protocol rejects fields it does not know (`onExcessProperty: "error"`, `packages/protocol/src/session.ts`), so a newer web app would fail loudly against a busy older Session for up to 30 minutes. Batching deploys (a cron or a debounce) was rejected too: it delays every merge's feedback and still cuts long Runs at each batch, and a 15-minute debounce removes only about a third of deploys. Revisit a longer `max_delay` only once the socket protocol tolerates extra fields.
- **A replaced instance finishes its calls without storage.** When `max_delay` passes, new requests reach a new instance. The old one keeps running the calls it has, its callbacks still answer and it still returns results, but every storage operation fails. Nothing tells it; a failed storage operation is how it learns.
- **Stateless invocations keep their version until they end.** A plain Worker's call in flight, an entrypoint's included, finishes on the version it started on, however many deploys follow (15 min observed).
- **Reverts.** A rollback is a revert merged to `main`, deployed by the normal pipeline. Reverting the latest change is safe, since removals take two steps; reverting past a removal is not. A revert never drops a migration that reached prod: `migrate` (`@cloudpid/effect-durable/sqlite`) numbers migrations by their position, so a reused number never runs on objects that ran the reverted one. Keep the migration and add one that undoes it. A manifest of each shipped migration's digest guards this (the Registry's is `apps/server/src/registry/migrations.manifest.ts`, McpHost's is `apps/server/src/mcp/migrations.manifest.ts` and the Session's, for its own `import_*` tables, is `apps/server/src/session/migrations.manifest.ts`, each checked by its test) (the Session runs its migrations at the first import and, once its tables exist, at every read and write of them, so a later migration, an undo included, reaches an object that has them): the test fails a migration at a shipped position that changed or went missing, and one not recorded yet, so append the digest it prints in the PR that adds the migration, and never edit or remove a line. The manifest is append-only, and CI enforces it: a pull request's `Migration manifests` job (`scripts/check-migration-manifests.sh`, over the PR's base commit) fails when a digest that is in the base is not still at the same position, so a plain `git revert` of the change that added a migration, which removes its manifest line too, fails until the line is restored; the manifest test then fails the migration that went missing. Keep the migration and its line, and add one that undoes it. Two branches that add a migration conflict on the manifest's last line. A new object with migrations adds its own manifest and test (`shippedMigrationProblems`, `@cloudpid/effect-durable/sqlite/testing`). An old reader that rewrites a row drops keys it does not know, so new fields stay optional.
- **Server's edges outside MCP** (audited in [#426](https://github.com/ian-pascoe/cloudpid/issues/426) against `git log -p` of each surface; the MCP edges are in [`mcp.md` → _Deploys_](../architecture/mcp.md#deploys)). Before this rule existed (2026-11-02), the Registry's methods were renamed and reshaped in step with their callers (#171, #354, #356, #357), the Session's `prompt` was removed (#46) and `redactExitReport` added (#171); each of those reached prod long before, so no instance of either side is left. Since then every edge only gained, and each is gain-only-safe:
  - **Session → Registry** (`RegistryMethods`: status, subagents, MCP task count, title and pushes; settings, Overrides and the Settings changes; the agent's Environment, Repo, Secret, Skill and MCP changes, and their previews; Subagent Workspaces; a Workspace's setup and Skill set; the end of an import; MCP sign-in asks). Arguments gain optional fields only, but two of them changed what a call means, and a Registry from before them ignores them: `AgentChangeAuthor.actor: "owner"` (#591), so an older Registry records the owner's _Always allow_ or _Never_ on a Sampling card as the agent's change, with a revert offered; and `changeSettings`' `guard` (#586), so an older Registry writes an agent's MCP change without checking again, in its transaction, that it widens nothing and that its `${NAME}`s resolve. Both have reached prod and healed; they matter again only on a revert past them. A failure is a defect (`RpcCallError`, or what the Registry threw): there is no typed failure to extend, and an unknown method fails loudly. The answers are result unions (above); `session/environments.ts`' `change` refuses a status it does not know rather than hand the Workspace a change and keep its Build current. **Stored** (`registry/store.ts`), each with its fallback, which threw before and failed every listing: a Session status a later build wrote falls back to `idle` in a record, the MCP endpoint's and the web app's listings and the endpoint's running counts per Environment, while the running cap (`maxRunning`) counts every status but `idle`, so a start never passes it on a Session that may run; a title source to the owner's, which a generated title never replaces; a subagent's status to `idle` (`SessionAgent`, `open`), the others still read; an origin of a kind it does not know to none.
  - **main Worker → Registry** (the rest of `RegistryMethods`: the owner's `RegistryRpcs`, the endpoint's starts, imports and listings, the Builds' and spares' upkeep, sign-in pages, Web Push). The main Worker is the newer side for up to `max_delay` after a deploy while the Registry is busy: a method it does not have fails loudly and heals, and an optional field it does not know (`marks`, `requestId`, `maxRunning`, `maxOpenImports`) is ignored, so the start is not marked as the endpoint's, deduplicated or capped for those minutes. `recordBuild`'s answer is read as optional, since one from before #468 answers nothing (`builds.ts`).
  - **main Worker → Session** (`SessionMethods`: `stopAll`, `destroy` and `reset`; the Fork and Clone calls, `forkSource`, `exportEntries`, `importStart`, `importEntries`, `importFinish`, `releaseFork`; `deleteSubagent`; the `McpApi` calls and `mcpSignInsResolved`/`Failed`; the socket upgrade's `fetch`, whose messages are the client protocol's). Methods only gained; `importEntries` gained trailing optional `apps`, `questions` and `visuals`, and `ForkPlan` and `ExportPage` optional fields only, so a source older than its copy carries no App records, questions or Visuals. Failures are `SessionError` (one tag, its `operation` free text) or an `ApiResult`, whose `ApiErrorCode` reads a code it does not know as `unavailable`.
  - **Workspaces entrypoints → Workspace DO** (`containerPreview(request, port)`, unchanged since #276; `mcpBridge(request, options)`, whose refusals read an unknown code as `bridge_failed`; `redactExitReport(text)`, whose failure withholds the report's lines; and computer's `WorkspaceProxy` and `WorkspaceServiceProxy`, which reach the DO's `fetch` and `__getWorkspaceStub()`). The two proxies and the DO are one library's, so an upgrade of `@cloudflare/computer` changes both ends of that edge at once: check that its proxy still reaches a DO of the version before.

## Startup

- **The platform refuses a version whose global scope takes too long.** A Worker's top-level code (every module its entry imports statically, evaluated before any handler) gets 1 s of CPU; past it, the upload fails with `ScriptStartupError: Script startup exceeded CPU time limit` (code 10021) and the deploy with it. What it costs grows with the code evaluated, mostly parse and compile, so the bytes the global scope reaches are what to watch.
- **The Server Worker's init is a module of its own.** `apps/server/src/worker.ts` holds the props (deploy time) and the Worker class; its init, the routes and the Session, Registry and McpHost Layers, is `worker-init.ts`, which the init Effect loads with `import()`. Alchemy runs the init at the isolate's first event (and at plan time, under Node), so the bundler puts its graph in chunks the global scope never evaluates, and a Durable Object that grows does not move the startup. Before this (#614) the global scope evaluated 3.6 MiB of the 3.9 MiB bundle and the prod deploy failed twice on the limit.
- **`worker.ts` imports only light modules.** A value the props need (a binding name, a constant) lives in a module that imports none of the routes: `MCP_CALLS_LIMIT` is in `mcp-access.ts`, not the endpoint's `mcp/api.ts`; the sign-in paths and the DCR redirect URI (which `mcp-access.ts` lists for Self-use) are in `mcp/sign-in-origin.ts`, not the router or `mcp/sign-in-client.ts`, and its hash is `@cloudpid/config/sha256`, not the package's root, whose graph the init shares. One static import that reaches the init's graph is enough to undo it: the chunk the two share then imports the init's chunk, and the whole graph is parsed at startup again.
- **The startup budget** (`bun run --cwd apps/server startup`, `scripts/startup.mjs`; CI's static part runs it on every change): it bundles the Server as alchemy deploys it, with the compatibility and Durable Objects of `worker-shape.ts` (`worker.ts` deploys with the compatibility; the typecheck holds the keys of `worker-init.ts`'s `durableObjects`, which the init takes its objects from, to exactly the list, and a Durable Object is added in both by convention), profiles its startup in workerd as `wrangler check startup` does (an entry that `import()`s the Worker's, under the CPU profiler, median of 5 cold isolates), and fails over either budget: **1 MiB** of startup modules (deterministic: 526 KiB now, 3.6 MiB before) and **120 ms** of startup CPU (machines differ: 45–65 ms on an M-series laptop now, 205–250 ms before). The bytes are the guard to trust; a CPU failure with one slow run among fast ones is a busy machine, and its runs are printed. It writes the bundle and the last profile (`startup.cpuprofile`, for Chrome DevTools or VS Code) to `apps/server/node_modules/.cache/startup/`. A change that needs a budget raised says why, with the numbers, in its PR.

## The Workspace DO

- **Peers of `@cloudflare/computer`.** The Worker Shell's `jq` is an optional computer module (`@cloudflare/computer/shell/jq`), its `git` needs `createGitClient()`, which loads `@platformatic/vfs`, and the Worker Shell itself needs `just-bash`; the Workspace DO passes them (`Workspace.ts`). Every package that depends on `@cloudflare/computer` (`apps/server`, `packages/computer-env`) lists `@platformatic/vfs` and `just-bash` too, so pnpm resolves one instance of computer (two give mismatched types).
- **`mkdir -p` above a read-only mount.** computer refuses `mkdir -p` of any path above a read-only mount (the Skill set's, at `/workspace/.agents/skills`), `/workspace` included, though the directory exists. `ensureDirectory` (`packages/computer-env`) makes that a no-op for the file operations and, through `GuardedFilesystem` (`apps/server/src/workspace/tracked.ts`), for the Worker Shell. A Workspace stub that does not extend `TrackedWorkspaceStub` must return a `GuardedFilesystem` as its `fs`.
- **`bash` routing lists.** When computer or its shell changes what the Worker Shell runs, update `WORKER_SHELL_COMMANDS`, `WORKER_SHELL_BUILTINS`, `CONTAINER_PROGRAMS` and the git subcommands in `packages/extensions/src/bash-routing.ts`. `apps/server/src/workspace/bash.workerd.test.ts` runs the lists through the real shell and checks each git form against real git's output. Only read-only `git` forms run on the Worker Shell, because its git (isomorphic-git) is not always git's.
- **Container-only paths' scripts** (`container-files.ts`) are tested in plain bash in `container-files.test.ts`; deployed, they run through computerd's FUSE mount, which the tests do not have. They need the Container's GNU coreutils and findutils, as the Container's other scripts need its Linux tools (`apps/sandbox-image/src/host.fixture.ts`): on a host without them, such as macOS, those tests skip, and under `CI` they never do. The two grep tests skip wherever `rg` is missing, CI included.

## workerd tests

Tests that need workerd (Durable Object storage, alarms, eviction) are `src/**/*.workerd.test.ts`, run by the package's `workerd` Vitest project through `@cloudflare/vitest-plugin` (see `apps/server/vitest.config.ts`): `bun --cwd <package dir> vitest run --project workerd <file>`. Give miniflare what the code under test binds:

- **Browser host:** the facet class as a Durable Object too (`CODEMODE_RUNTIME`, else `ctx.exports.CodemodeRuntime` is not a class), `workerLoaders: { LOADER: {} }`, and a stand-in Workspaces Worker for `CONTAINER_PREVIEWS` (an auxiliary `workers` entry; see `apps/browser/vitest.config.ts`).
- **Workspace DO** (`workspaceOnly` in `apps/server/vitest.config.ts`): `workerd.fixture.ts`'s `TestWorkspace` stands in for the Container and what runs on it: `fakeContainer`, `fakeDevServer` (the Container previews) and `fakeBridge` (the MCP bridge: its health, its answers, a stream the test writes to, and the launch record's token from `seedLaunchRecord`), and counts the idle stop's uses and holds (`mcpBridgeUses`, `mcpBridgeHolds`). `WorkspaceMcpBridge`'s tests call the entrypoint (`exports.WorkspaceMcpBridge`) and the DO's `mcpBridge` directly. A Workspace named with `GITHUB_APP_WORKSPACE` gets a test GitHub App from the `TEST_GITHUB_APP_*` bindings (keyed in `vitest.config.ts`), for tests that mint GitHub tokens.
- **Codemode sandbox:** `modulesRules: [{ type: "CompiledWasm", include: ["**/*.wasm"] }]`.
- **MCP engine** (`apps/mcp-worker/vitest.config.ts`): the test Worker needs `nodejs_compat`, and `McpWorker` must run without it, so `McpWorker` is an auxiliary Worker: the config bundles `src/worker.ts` as alchemy deploys it (rolldown with `@alchemy.run/cloudflare-runtime/rolldown`) and binds its `McpEngine` as `MCP_ENGINE`. Its `MCP_BRIDGE` is a stand-in Workspaces Worker, a third auxiliary Worker (`src/workspaces.fixture.ts`: a `WorkspaceMcpBridge` over a fake MCP server, bundled like the others; the test Worker reaches it as `WORKSPACES` to control a Workspace's Container and read what reached it), and its `outboundService` is a second auxiliary Worker of fake MCP servers (`src/fakes.fixture.ts`, over `@cloudpid/mcp/testing`, which `apps/*` may import where they may not import the SDK), so every `fetch` the engine makes reaches a fake. A host that dies mid-call is a `Caller` Durable Object of the test Worker that calls the engine and then `ctx.abort()`s itself. The same auxiliary Worker's `McpServer` is bound as `MCP_SERVER`, and `src/server.workerd.test.ts` drives it with pi-mcp's `McpClient` over a `StreamableHttpTransport` whose `fetch` is the binding's `serve`, given an `RpcTarget` fake of the main Worker's `api`.
- **Web assets:** the `workerd-assets` project binds the real asset layer (`assets: { directory, binding: "ASSETS", assetConfig: { not_found_handling: WEB_NOT_FOUND_HANDLING } }`, the directory a fixture app in `apps/server/src/assets.fixture/`), and `src/assets.workerd.test.ts` runs only there (`bun --cwd apps/server vitest run --project workerd-assets src/assets.workerd.test.ts`); the `workerd` project excludes it. The asset layer's answer for a missing path is the point of the test, so the config must be the deploy's.
- **Images:** `images: { binding: "IMAGES" }`, as the `workerd-session` project does.
- **A replaced instance:** `refusingStorage(storage)` (`@cloudpid/effect-durable/sqlite/testing`) wraps the storage `runInDurableObject` gives (`state.storage`) and returns `{ storage, trip }`. Give the code under test `storage`, run its call, and `trip()` where the code update would reach it: from then on `sql.exec`, `transactionSync`, the synchronous key-value store's members (`kv.get`, `kv.put`: a `kv` kept before the trip refuses too) and the other synchronous members throw, and `get`, `put` and the other Promise-returning ones return a rejected Promise, as the platform's do, while the calls in flight, their callbacks and their results carry on, as on a replaced instance (_Deploys and Durable Object code updates_). The real storage is untouched, so the test reads it through a new instance afterwards. The pattern: open the object's store over `storage`, call, `trip()`, assert the refused writes left no trace and the call still returned its result (best-effort writes) or failed as designed, then check what a new instance sees (`apps/server/src/registry/store.workerd.test.ts`). For an object whose store is opened in its constructor, gate its storage there and trip it from a method the test calls: `TestMcpHost.replace()` (`apps/server/src/mcp/host.fixture.ts`, with `replaced.workerd.test.ts`), and, for the Session's whole storage, a `TestSession` named `mcp-replaced-*` (`session/host.fixture.ts` replaces its `ctx.storage` with the gate; `session/mcp-replaced.workerd.test.ts`). `ctx.abort()` is not a substitute: it rejects the calls in flight, the opposite of a replaced instance.

A test waits for what the code under test does in its own time with `poll(check, failure)` (`apps/server/src/poll.fixture.ts`), never with a count of polls: every wait in a test shares one deadline, 2 s before the test's timeout, so a slow answer on a loaded CI runner still passes, and the wait that is never met fails with its own message rather than the timeout's. Wait for the message or state the assertion is about, not for any N messages, nor for an exact count that a message soon after can pass: CI's runners poll late. `pollFor(find, failure)` answers what `find` found, and `idle(stub)` and `eventually(stub, check)` (`apps/server/src/durable-waits.fixture.ts`) wait on a Durable Object's state, read inside it. A test that needs the code under test caught midway (a message being prepared, a listing under way) holds it there with a gate the test opens, and waits for it to get there (`holdPreparing`, `holdOwnerTabReads`, a `held` Changes fixture), rather than sleeping for less than a delay the fixture adds: a loaded runner wakes the test late. The `apps/server` tests no longer poll by count. A sleep is left where a test shows that something does not happen, or where nothing signals the state it waits for (a message waiting for the Session's lock); a few older tests still sleep where a gate could signal, and get one when touched.
