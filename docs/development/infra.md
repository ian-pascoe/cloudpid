# Infra: running, deploying and CI

How to run the stack locally, deploy it, and keep its secrets and CI credentials. The design behind it is in [`../architecture/operations.md`](../architecture/operations.md).

## The stack

The alchemy stack is `infra/alchemy.run.ts`; its scripts run alchemy from `infra/`:

- `bun --cwd infra run dev` serves workerd on `http://localhost:1337`.
- `bun --cwd infra run deploy --stage dev_$USER` deploys to Cloudflare; add `--dry-run` to only plan. Arguments after the script's name reach alchemy as they are, with no `--`.

It authenticates with the local alchemy profile (`alchemy profile edit --add Cloudflare`) and keeps state with `Cloudflare.state()`. Alchemy records the Worker's absolute `main` path in state, but a deploy from another checkout path plans no change, so CI and local deploys can alternate.

`alchemy dev --stage dev_$USER` replaces that stage's deployed Worker with the local one and deletes its Access apps (the MCP endpoint's too) and its Local agent service token, so redeploy the stage afterwards and read the new token with `local-agent-token`.

## Stages and Access

`apps/server/src/deployment.ts` decides per stage what the main Worker is called, where it is served and who may reach it: `prod` is served on `https://pi.ianpascoe.dev` (workers.dev off) and keeps its alchemy name, and every other stage is named `cloudpid-server-<label>` and served on `workers.dev`. All of them sit behind an Access application that allows only the owner's email. The Access team domain is `spirit-led-software`. `alchemy dev` runs locally and has no Access.

**The Worker verifies the assertion itself** (`apps/server/src/access.ts`; [_The Access guard_](../architecture/mcp-sign-in.md#the-client-document-and-the-callback-outside-access)): Access in front is not trusted to have run. Every request that reaches the Worker needs a `Cf-Access-Jwt-Assertion` signed by the team's keys (`https://spirit-led-software.cloudflareaccess.com/cdn-cgi/access/certs`, kept an hour per isolate) with that issuer, a live `exp` and `nbf`, an `aud` equal to the main application's, `email == OWNER_EMAIL` and no `common_name`; anything else gets a bare 403, and the reason goes only to the Worker's log. The audience is the Worker's var `CLOUDPID_ACCESS_AUD`, the `aud` of the `Server/Access` application (`apps/server/src/access-props.ts`, `accessProps`, declared in `apps/server/src/worker.ts`). The application is declared there, not by the Worker's `access: { policies }` form, so that its `aud` can be a var; it keeps the same logical id, so a deploy updates it in place. That makes a cycle in alchemy's graph (the application's destinations are the Worker's id, the Worker's var is the application's `aud`), which the engine settles through the Worker's precreate stub; a deployed Worker without the var refuses every route. The web app's static assets run the Worker first (`runWorkerFirst`), so the guard covers them too: the Worker serves them after it from the `ASSETS` binding (`apps/server/src/assets.ts`), and every asset request is a Worker request and is billed as one. The assets 404 a path that is no file (`notFoundHandling: "none"`), since through the binding `"single-page-application"` would answer the page to a missing chunk too; the Worker gives the app to a page load itself and a 404 to a missing `/assets/…` file. A cold page load makes several concurrent requests, and each one that finds no kept team keys reads `/cdn-cgi/access/certs` for itself (a read is never shared across requests), so a cold isolate makes a few of those fetches at once. Under `alchemy dev` there is no Access: the stack sets `CLOUDPID_LOCAL_MODE` (only `guardVars(undefined)` does, and `deployment()` and every deployed stage lack it), and the Worker reads both guard vars from its raw environment, not through `Config` (a `Config` read would fail on the boolean alchemy's runtime makes of `"true"`, and at plan time would bind a same-named value of the deploying shell onto the Worker as a secret). A request counts as the owner then only when every host it names is loopback (`localhost`, `127.0.0.1`, `[::1]`; `localhost:1337` and Vite's `localhost:5173`).

The label is the stage lowercased with `_` → `-` (`pr-430` → `cloudpid-server-pr-430`; `dev_ian` → `cloudpid-server-dev-ian`). A stage whose label is empty, longer than 35 characters, starts or ends with `-`, or has characters outside `[A-Za-z0-9_-]` fails its deploy: it is refused, never truncated. The name fixes the stage's **app origin**, `appOrigin(stage)`: `https://cloudpid-server-<label>.ian-g-pascoe.workers.dev` (the account's subdomain is the constant `WORKERS_DEV_SUBDOMAIN`; prod's is `https://pi.ianpascoe.dev`), which the App sandbox derives from a View's hostname ([_The App sandbox_](../architecture/mcp-apps.md#the-app-sandbox)). **Every deploy checks that the main Worker's URL is `appOrigin(stage)`** and fails otherwise (`infra/alchemy.run.ts`, `checkedAppOrigin`), so if the account's `workers.dev` subdomain is ever renamed, every non-prod deploy fails until a pull request changes the constant. The label of a non-prod stage is also a var of its Worker (`CLOUDPID_STAGE_LABEL`); `prod` has none, as its Views have no suffix.

A stage deployed before the fixed names keeps its old random Worker name, and its next deploy does not rename it: the WebBuild step's outputs (`assets.directory` and `hash`) are unresolved at plan time on a fresh checkout, so alchemy's `WorkerProvider.diff` returns early, before its name check, and the engine updates the Worker under its old name, after which `checkedAppOrigin` fails the deploy. (Locally a deploy replaces the Worker, deleting the old script and its Durable Object storage, only when `dist` exists and nothing the build hashes changed.) Such a stage must be destroyed and redeployed: `dev_$USER` with `bun --cwd infra alchemy destroy --stage dev_$USER`, then `bun --cwd infra run deploy --stage dev_$USER`, so the Workspaces Worker doesn't keep Workspaces that the wiped Registry no longer names; an open pull request's preview by closing and reopening the pull request, since `ci.yml` destroys on closed and deploys on reopened. `prod` has no explicit name and needs nothing. The Worker's Access application (`Server/Access`) is bound to the Worker's id, so it follows the replacement and leaves no application on the old host.

**`ianpascoe.app` hosts nothing but the App sandbox**: a View's origin is a subdomain of it, so whatever else the zone served would be same-site with untrusted Views ([ADR-0031](../adr/0031-app-views-run-in-a-secretless-sandbox-on-a-domain-of-their-own.md)). Once the sandbox is deployed its only record is the wildcard `*.ianpascoe.app AAAA 100::` (proxied), which the `prod` deploy creates; until then, and always, the apex and `www` parking records stay removed, so the zone holds no records at all before the first `prod` deploy of the sandbox. Its injection and challenge settings stay **off**: Web Analytics automatic setup (`auto_install`), email obfuscation, server-side excludes, automatic HTTPS rewrites and browser check, with `security_level` lowered (`essentially_off`), since an injected beacon or a challenge page inside the iframe breaks the View. Nothing in the stack manages these (the token has no zone-settings permission), so they are the owner's, set once in the dashboard; check them again if the zone is ever recreated or its plan changes. To check, after the sandbox's first `prod` deploy (nothing answers on the zone before it): a `GET` of a well-formed sandbox host such as `https://aaaaaaaaaaaaaaaaaaaaaaaaaa.ianpascoe.app/` (a 26-character lowercase base32 hash; any other name gets a 404, which carries no HTML to inject into) with a browser's `User-Agent` returns the sandbox's own HTML with no `static.cloudflareinsights.com` script and no challenge.

## Docker for the Container image

Every deploy and `alchemy dev` builds the Container's image (`apps/sandbox-image/image/Dockerfile`), so both need a running Docker with the `buildx` plugin; without it alchemy fails with `DockerBuildFailed`. With colima, `brew install docker-buildx` and point `cliPluginsExtraDirs` in `~/.docker/config.json` at `$(brew --prefix)/lib/docker/cli-plugins`. The image is `linux/amd64`, so on Apple silicon start colima with `--vz-rosetta`.

`alchemy dev` runs the Container in local Docker without `/dev/fuse`, where computerd falls back to its userspace shim: the real FUSE mount exists only deployed. The stack sets `CONTAINER_FUSE=false` there, and the `ignore` list is not applied (computerd's shim exits on one). Snapshots are off under `alchemy dev` too.

## Web UI development

Run `bun --cwd apps/web run dev` next to `alchemy dev`: Vite proxies `/rpc` and the Session socket to `localhost:1337`. On a cloudpid Container its watcher needs no polling: the Workspace DO gives the Container's watchers a file-change signal for the agent's edits ([_File-change signals_](../architecture/container.md)).

## Secrets and variables

Every deploy, `alchemy dev` and a preview's destroy (which evaluates the stack) read these from the environment. Workers read them with `Config.Redacted`, which binds them to the Worker as secrets. Locally, keep them in `~/.config/cloudpid/dev.env` (outside the repo; `.env*` files are gitignored) and load them with `set -a; . ~/.config/cloudpid/dev.env; set +a`.

| Name                                                        | Required | What it is                                                                                                                                                                                         |
| ----------------------------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MODEL_PROXY_URL`, `MODEL_PROXY_API_KEY`                    | yes      | The model proxy and a Commissary API key for `https://api.ai.ianpascoe.dev`, which is outside Access, so a service token cannot authenticate to it. Read by the Session DO.                        |
| `CLOUDPID_GITHUB_APP_ID`, `CLOUDPID_GITHUB_APP_PRIVATE_KEY` | yes      | cloudpid's GitHub App (ADR-0025), bound to the Workspaces Worker and the main Worker. `apps/server/src/github/config.ts` fails on a key that is not an RSA PEM. The key never reaches a Container. |
| `SECRETS_ENCRYPTION_KEY`                                    | yes      | The master key the owner's Secrets are encrypted under (Session, Registry and Workspace DOs); at least 32 characters.                                                                              |
| `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`    | yes      | The Web Push identity (RFC 8292), read by the Registry DO (`apps/server/src/push/config.ts`).                                                                                                      |
| `CLOUDPID_GIT_NAME`, `CLOUDPID_GIT_EMAIL`                   | no       | The identity of the agent's commits (default `cloudpid` and the owner's email).                                                                                                                    |
| `EXA_API_KEY`, `PARALLEL_API_KEY`                           | no       | `web_search`'s providers (`WebConfigLive`); with neither, `web_search` answers that it is not configured (`web_fetch` needs no key).                                                               |
| `CLOUDPID_ANALYTICS_TOKEN`                                  | no       | An API token with Account Analytics Read, for the Container cost in the Session header; unset or empty, the cost is estimated.                                                                     |

### Making and rotating them

- **`SECRETS_ENCRYPTION_KEY`**: `openssl rand -base64 32`. Changing it drops the Secrets held at that moment (they expire within 15 minutes anyway; the agent asks again); messages already scrubbed of a value stay scrubbed. It also leaves every Secret kept for an Environment unopenable (the Registry logs each by name and leaves it out, so the owner sets it again), and each Workspace takes no snapshot and makes no Build until a readying hands its copy again. A malformed key fails only what needs it: Environments with no kept Secret work as before, and those with some get none in their Workspaces' set-up (`secretsUnavailable`), no new Build, and Secrets calls that fail saying why.
- **VAPID pair**: the public key is a base64url uncompressed P-256 point, the private key a base64url 32-byte scalar, the subject a `mailto:` URL. This prints the public key, then the private one:

  ```sh
  node -e "const {publicKey,privateKey}=require('node:crypto').generateKeyPairSync('ec',{namedCurve:'P-256'});const j=privateKey.export({format:'jwk'});console.log(Buffer.concat([Buffer.from([4]),Buffer.from(j.x,'base64url'),Buffer.from(j.y,'base64url')]).toString('base64url'),j.d)"
  ```

  The layer checks the three at startup (subject, key lengths, and that the two are a pair), so a malformed secret fails a deploy or `alchemy dev` at once. Rotating the pair strands every device's subscription (a push service refuses a subscription made with another key, so each push is logged as a failure); a device replaces its own the next time the app is opened, if it still allows notifications.

- **GitHub App**: `bun --cwd infra run github-app:setup` (`infra/github-app-setup.ts`) creates the app through GitHub's manifest flow (one confirmation in the browser), writes the ID and key into `production`, `preview` and `~/.config/cloudpid/dev.env` with `gh secret set`, sends the owner to install the app (All repositories) on their account and each organization, and checks each installation by minting a GitHub token. GitHub shows the key only then: to rotate or replace it, generate one in the app's settings and set it by hand in both environments.
- **`CLOUDPID_ANALYTICS_TOKEN`**: CI's tokens are made by `infra/github.ts` (below); for local deploys, mint one in the dashboard.

## CI

`.github/workflows/ci.yml` runs what `bun run check` runs on every PR and push to `main`, split over parallel jobs (`checks`: typecheck, lint, format and the web build; the tests of every package but the server; the server's tests in three `vitest --shard`s), a `Migration manifests` job (pull requests only), and a `Check` job that passes only when all of them did, the status the `main` ruleset requires.

- **Docs-only changes:** a `changes` job lists the changed files first (a PR's diff from its merge base, or a push's compare with `before`, through the GitHub API). When every one is under `docs/` or a Markdown file (no task reads them: `turbo.json` leaves `*.md` out of every task's inputs), `checks` is skipped, a `docs` job runs only `oxfmt --check` (at `bun.lock`'s version, without an install), and `Check` passes on it; neither `prod` nor a preview deploys. A list that fails or is at the API's cap counts as code.
- **Migration manifests:** a pull request's `Migration manifests` job runs `scripts/check-migration-manifests.sh` over its base commit (it fetches only that commit) when the change touches code, and fails if a digest in a `migrations.manifest.ts` at the base is no longer at the same position: the manifests are append-only, so a plain `git revert` of the change that added a migration cannot drop its line (`docs/development/workers.md` → Deploys and Durable Object code updates → Reverts). `Check` passes when it succeeded or was skipped (a push, or a docs-only change, has no manifest to guard).

- **Caches:** `checks` and `preview` set up through `.github/actions/setup`: Bun, Node, the lockfile's packages cached by lockfile with a fallback to the newest cache (one `bun pm cache pack` file, so it holds only the packages of the lockfile it was saved with), then the install. `preview`, which holds deploy credentials, only reads the cache, and the `prod` deploy uses none. Each part of `checks` also caches turbo's `.turbo/cache` under its own key, pruned to the entries its tasks used.
- **`prod`:** on push to `main`, CI deploys stage `prod` in the GitHub environment `production` (deployments from `main` only).
- **Previews:** each pull request from a branch of this repository (not a fork, which gets no secrets) gets stage `pr-<number>` (Worker `cloudpid-server-pr-<number>`) once `check` passes, deployed by the `preview` job in the GitHub environment `preview` (any branch). `infra/alchemy.run.ts` posts its URL as one PR comment (`GitHub.Comment`, with the workflow's `GITHUB_TOKEN`) that each push updates; closing or merging the PR runs `alchemy destroy --stage pr-<number>` from the PR's head commit, unless the `preview` environment has no deployment for the PR's branch (every `preview` run records one before its first step, so a PR that never started a preview, such as a docs-only one, destroys nothing). Deploys and the destroy of one PR never overlap or cancel midway (job concurrency `preview-<number>`). A preview whose secret is missing fails its deploy and its destroy.
  - **Container application:** the stage's Container application (`cloudpid-<…>-pr-<number>`, the Workspace DO's, which Cloudflare keeps with no instances if nothing deletes it) is part of the teardown. A deploy asks GitHub whether the PR is still open before it starts, and does nothing if it was closed meanwhile: the deploy of the last push waits for `check`, the destroy does not, so a PR closed within those minutes was destroyed while still empty and then deployed, leaving its stage behind (#328). After the destroy, the job lists the account's Container applications and **fails** if one named for this stage is left, so a leftover shows as a red Preview job. Never delete by hand an application outside `pr-<number>` (`prod`, a dev stage or another project's).

### CI credentials

They are code: `infra/github.ts` (stack `cloudpid-github`, stage `ci`) creates the scoped API token `cloudpid-ci-deploy` (Workers Scripts, Workers Containers, Secrets Store for alchemy's state store, Access apps and policies, Access service tokens, and zone/DNS/routes on `ianpascoe.dev` and on `ianpascoe.app`: Zone Read, DNS Write and Workers Routes Write on each) and writes `CLOUDFLARE_API_TOKEN` (secret) and `CLOUDFLARE_ACCOUNT_ID`, `MODEL_PROXY_URL` (variables) into `production`. It also creates the `preview` environment and its token `cloudpid-ci-preview` (the same account permissions, no zone ones: nothing on `ianpascoe.dev`, because previews are served on `workers.dev`, and nothing on `ianpascoe.app`, because only `prod` deploys the App sandbox's Worker, route and record) with the same secret and variables, and one analytics token per environment (`cloudpid-container-analytics`, `cloudpid-container-analytics-preview`) written as `CLOUDPID_ANALYTICS_TOKEN`.

Any branch can use `preview`'s token, and Workers Scripts Write covers every Worker on the account, `prod`'s included, so whoever can push a branch can reach `prod`.

- **Deploy or change permissions:** from a workstation with the `admin` alchemy profile (the Cloudflare Global API Key and `gh`): `bun --cwd infra run ci:setup`. Rerun it after pulling a change to `infra/github.ts`.
- **Before a change that deploys onto a zone:** the deploy token must already hold the permission, or `prod`'s deploy fails. Merge the permission first and rerun `ci:setup` from the merged `main`, then merge the change that uses it (the App sandbox's route and record on `ianpascoe.app` were the first).
- **Before a change that declares an Access service token:** Access: Service Tokens Write (`ACCESS_SERVICE_TOKENS_WRITE` in `infra/github.ts`) is in both tokens' permissions, which "Apps and Policies Write" does not cover (`POST /access/service_tokens` fails `1010 auth.forbidden`). A deploy that declares a service token fails without it, a pull request's preview and `prod` alike, so merge the permission alone and rerun `ci:setup` from the merged `main` **before** the change that declares the token (the Local agent's, `apps/server/src/mcp-access.ts`) previews or merges.
- **Rotate the token:** `bun --cwd infra alchemy destroy --config github.ts --stage ci --profile admin`, then `ci:setup` again. The `production` environment is retained on destroy, so the hand-set secrets and the `main` branch policy survive; only the token, its secret and the variables are replaced.
- **Hand-set secrets:** the stack does not manage `MODEL_PROXY_API_KEY`, `SECRETS_ENCRYPTION_KEY`, the VAPID three, `EXA_API_KEY` or `PARALLEL_API_KEY`. Set each in both environments with `gh secret set <NAME> --env production` and `--env preview`, giving `preview` an encryption key and VAPID pair of its own (the dev ones from `~/.config/cloudpid/dev.env` will do), since the previews share them.

Workers Scripts Write also covers what rides on the script upload: observability (`WORKER_OBSERVABILITY`) and the Images binding need no extra permission.

## The MCP endpoint's Access application

[_Access and identity_](../architecture/mcp-endpoint.md#access-and-identity) is the design; this is how it is deployed. Every deployed stage has **three Access applications** on its host, all in the stack (the third once #444 lands):

1. **The Worker's own** (`Server/Access`), owner-only, which covers every path (`deployment(stage)`, above). Managed OAuth is never turned on for it.
2. **The MCP endpoint's** (`Server/McpAccess`, `apps/server/src/mcp-access.ts`): `self_hosted` with the `public` destination `<host>/mcp` (`pi.ianpascoe.dev/mcp` on `prod`, `cloudpid-server-<label>.ian-g-pascoe.workers.dev/mcp` elsewhere, which is `appOrigin(stage)`'s host and covers sub-paths), managed OAuth (`oauthConfiguration`: access tokens 5 minutes, grant 14 days, dynamic client registration for loopback and localhost), the owner-email Allow, and Service Auth for the Local agent's token **by id** (never `anyValidServiceToken`). A hostname destination beats the Worker's, so only `/mcp` gets managed OAuth: the OAuth token and the service token pass `/mcp` and get a 302 to the Access login on `/` and `/rpc`.
3. **The Bypass application** of [ADR-0035](../adr/0035-cloudpid-identifies-itself-with-a-public-client-document-and-takes-authorization-responses-outside-access.md) for the two public paths under `/oauth/mcp/`, which arrives with #444: until then a stage has two.

- **The token:** `Server/LocalAgentToken`, an `Access.ServiceToken` of a year (`8760h`), named `cloudpid-local-agent` on `prod` and `cloudpid-local-agent-<label>` elsewhere: alchemy finds a token again by its name, and a name two stages shared would make one's destroy delete the other's. It needs the deploy token's Access: Service Tokens Write ([_CI credentials_](#ci-credentials)).
- **The Worker's vars:** `CLOUDPID_MCP_ACCESS_AUD` (the `/mcp` application's `aud`, which is not the main application's) and `MCP_SERVICE_TOKEN_CLIENT_ID` (the token's client ID, public). The secret never reaches the Worker. `alchemy dev` declares neither and sets neither var.
- **Reading the token:** `bun --cwd infra run local-agent-token --stage <stage> [--profile <profile>]` prints `CLOUDPID_ACCESS_CLIENT_ID=…` and `CLOUDPID_ACCESS_CLIENT_SECRET=…` (what `/cloudpid` reads) and the expiry, from alchemy's state (`alchemy state read cloudpid/<stage>/Server/LocalAgentToken`), where the provider keeps the secret redacted: Cloudflare shows it only on create and rotate. It uses the alchemy profile the deploys use. CI never runs it and the stack never prints the secret.
- **A preview's destroy** deletes the `/mcp` application and the token with the rest of the stage; nothing is left behind.
- **After a deploy,** managed OAuth takes 1–2 minutes to take effect: until then `/mcp` answers `1042` or a 302.
- **No WAF rule that requires a User-Agent may sit on `/.well-known/*`** (or Access's own OAuth endpoints): Claude Code's discovery and registration requests send an empty one, and a rule that blocks it breaks sign-in.
- **Renewing and rotating:** the provider has no refresh, so a token that is a year old is renewed in the dashboard (Refresh) or replaced. To rotate the secret, bump `clientSecretVersion` of `Server/LocalAgentToken`, deploy, and rerun `local-agent-token`; the old secret lasts until `previousClientSecretExpiresAt`.

## Checking a deployed stage

- **A Container end to end:** deploy your own stage and give the Workspaces Worker a temporary `workersDev` route that runs a command through `ComputerExecutionEnv.onBackend("container")` (and can destroy the Container, to check snapshots: a restore and the idle stop only exist deployed). `kill 1` in the Container restarts it (PID 1 is the image's supervisor, which stops computerd and sends no exit report); `pkill -KILL -x computerd` makes it log one (`workspace.container.output` in the Workspaces Worker's logs). An old Workspace DO instance keeps its old code until it is evicted, so start a Session in a new Workspace after a redeploy.
- **Traces:** in the dashboard (Workers → Observability → Traces) or through the telemetry query API (`POST /accounts/{id}/workers/observability/telemetry/query`, `view: "traces"`), whose `traces` view lists summaries only: span names and attributes are in the dashboard. To see what a span is made of while debugging, log from inside it: a log line carries the trace and span ID it ran under.
- **Web tools:** `WEB_TOOLS_LIVE=1 bun --cwd packages/extensions vitest run src/web/live.test.ts` checks `web_search` and `web_fetch` against the real network and providers.
- **Images quota:** every account is on the Images Free plan by default: 5,000 unique transformations a month, after which the binding answers error 9422 and `read` leaves the image out with a note.
