# How does `@pierre/diffs` fit the web app?

Research for [#101](https://github.com/ian-pascoe/cloudpid/issues/101) (map [#99](https://github.com/ian-pascoe/cloudpid/issues/99)). Version studied: `@pierre/diffs` **1.6.0** (npm, published 2026-10-20; source `pierrecomputer/pierre` at `0a74026`, `packages/diffs`). Docs: <https://diffs.com/docs>, read through its plain-text twin <https://diffs.com/llms-full.txt> (the HTML page is 13 MB).

Sources are cited as **[docs]** (llms-full.txt / diffs.com/docs, section named), **[src]** (repo path, `packages/diffs/src/…`, v1.6.0), **[pkg]** (the npm tarball, `package.json` or `dist/`), or **[measured]** (a throwaway Vite 8.3.5 + React 19 build I ran for this ticket, `/tmp/sz`, not committed).

## Answer and recommendation

It fits. The library is React 19 compatible, Apache-2.0, renders in Shadow DOM, takes everything we need to hand it (old/new strings, a unified patch, parsed metadata), reports line-range selection per side, and has a built-in "+" gutter button plus slot-based annotation rendering that is a direct match for the draft-Annotation flow. Nothing in the settled design (#99) conflicts with it. Recommended use per surface:

| Surface | Component | Input |
| --- | --- | --- |
| Per-call diff on an `edit`/`write` card | `MultiFileDiff` (or `FileDiff` over `parseDiffFromFile`) | old/new `FileContents`; `oldFile={null}` for a `write` that creates a file. The diff is computed **in the browser**. |
| Changes, Comparison, PR (many files) | `CodeView` (virtualized, one scroll region) with `type: 'diff'` items | `parsePatchFiles(gitDiffOutput)` → `FileDiffMetadata[]`; add `loadDiffFiles` to fetch full contents lazily for hunk expansion |
| Never | `PatchDiff` for a multi-file patch | it **throws** unless the patch holds exactly one file |

Three things to design around, all with the library's own mechanisms:

1. **Theming is the real work.** The built-in themes are Pierre Light/Dark; matching `DESIGN.md` (blue-slate hue 250, OKLCH tokens, system light/dark) means registering a CSS-variables theme (`registerCustomCSSVariableTheme`) and setting `--diffs-*` variables in `styles.css`, plus the `--diffs-*-override` variables for backgrounds. It follows `prefers-color-scheme` with the default `themeType: 'system'`, which is how the app already works. The CSS-variables theme is only one paragraph in the docs, so prototype it first.
2. **Weight.** About **+324 kB minified / +83 kB gzip** on the entry chunk (React included in neither number: the baseline React app is 219/69 kB, with diffs 543/152 kB) **[measured]**, plus a 46 kB (16 kB gzip) worker, plus one lazy chunk per language and theme (e.g. TypeScript 181 kB / 16 kB gzip). Lazy-load the whole diff module (`React.lazy`) so the chat does not pay for it.
3. **Stability is mixed.** Core diff/file/CodeView APIs are not flagged experimental; the worker pool, render cache, token hooks, `UnresolvedFile`, and Highlights are, and `unsafeCSS` carries no backwards-compatibility promise even in patches **[docs: Worker Pool, Token Hooks, Styling]**. Pin an exact version and avoid the experimental pieces on the MVP path, except possibly the worker pool (below).

## Findings

### 1. React 19 API

- Entry points: `@pierre/diffs` (vanilla + utilities), `/react`, `/edit`, `/ssr`, `/worker` **[docs: Installation → Package Exports; pkg `exports`]**. `react`/`react-dom` are optional peers, `^18.3.1 || ^19.0.0` **[pkg package.json]**. ESM only, no CJS.
- Six React components **[docs: React API → Components]**:
  - `CodeView`: mixed virtualized list of `file` and `diff` items in one scroll container.
  - `MultiFileDiff`: `oldFile` / `newFile` as `FileContents` (`{ name, contents, lang?, cacheKey? }`); `null` for the missing side of an added/deleted file. An omitted side is not `null`; empty contents are `contents: ''`.
  - `PatchDiff`: `patch` string.
  - `FileDiff`: a pre-parsed `FileDiffMetadata`.
  - `File`: one file, no diff.
  - `UnresolvedFile`: merge-conflict UI (beta; out of scope per #99, #112).
- **A diff of two contents is computed in the browser, on the main thread**: `parseDiffFromFile` calls `createTwoFilesPatch` from the `diff` (jsdiff) package, then parses it **[src: utils/parseDiffFromFile.ts; pkg dependencies `diff 9.0.0`]**. The worker pool only moves *highlighting* off-thread, not diffing. For a very large pair of files, compute the patch server-side (`git diff`) and send the patch.
- **Patch input is "partial".** `parsePatchFiles` yields metadata holding only the patch's lines (`isPartial: true`); expanding collapsed context (`expandUnchanged`, `expandHunk`, the "N unmodified lines" separators) needs full contents, supplied through the `loadDiffFiles` option (returns `{ oldFile, newFile }`, `{ oldFile: null, newFile }` for pure renames). Keep the same `fileDiff` object across renders or hydration is lost **[docs: Core Types → FileDiffMetadata; React API → Partial Diff Hydration]**. `MultiFileDiff` and `parseDiffFromFile` always have full contents.
- **`PatchDiff` is single-file only**: `getSingularPatch` throws `"PatchDiff: Provided patch must include only 1 patch, with 1 diff"` / `"…exactly 1 file diff"` **[src: utils/getSingularPatch.ts, used by react/PatchDiff.tsx; identical in pkg dist/utils/getSingularPatch.js]**. The docs describe it only as "renders from a patch string". Use `parsePatchFiles` (handles multi-file and multi-commit patches, returns `ParsedPatch[]` with `files`) then `FileDiff` per file or `CodeView` items **[docs: Utilities → parsePatchFiles]**.
- Props must be referentially stable (`useMemo` for `options`, annotations, callbacks) or the instance re-renders **[docs: React API → Components]**.
- `CodeView`: items need a stable unique `id`; if content, annotations, or `collapsed` change under the same id, bump `version`. `items` (controlled) or `initialItems` + ref (imperative). `stickyHeaders`, `layout`, header/footer regions inside the scroll container ("ideal for PR summary cards and approval bars"), `scrollTo` by item/line/range **[docs: CodeView → Core Model, Usage Notes, Header/Footer]**. A live demo, <https://diffshub.com>, is linked from the docs.

### 2. Annotations and line selection

- **Selection model.** `SelectedLineRange = { start: number; end: number; side?: 'deletions' | 'additions'; endSide?: … }` **[src: types.ts:509-516]**. Line numbers are one-based on the chosen *file side* (old = `deletions`, new = `additions`), not row positions **[docs: Core Types → LineAnnotation and DiffLineAnnotation]**. This is exactly the Annotation shape in #99 (file, side, line range). `endSide` is emitted only when it differs from `side`, so a range may span both sides; decide how a Review renders that (open question 1).
- **Reporting.** Option `enableLineSelection: true` makes line-number clicks/drags select; callbacks `onLineSelectionStart` (pointer down), `onLineSelectionChange` (while dragging), `onLineSelectionEnd`, and `onLineSelected` (pointer up, final range or `null`) **[docs: React API → Shared Diff Options]**. A built-in hover "+" button: `enableGutterUtility: true` + `onGutterUtilityClick(range)` (fires on pointer up; click = one line, drag from the button = range) **[docs: same]**. `onLineClick`/`onLineNumberClick`/`onLineEnter`/`onLineLeave` give `{ lineNumber, side }`. `renderGutterUtility(getHoveredLine)` is the custom variant (do not combine with `onGutterUtilityClick`).
- **Control.** Prop `selectedLines` (same `SelectedLineRange`) sets the selection from state; "works with both split and unified" **[docs: Shared Diff Render Props]**. In `CodeView`, selection is viewer-wide (one selection across all items; payload `{ id, range }`), controlled with `selectedLines` / `onSelectedLinesChange` or the ref (`setSelectedLines`, `getSelectedLines`, `clearSelectedLines`) **[docs: CodeView → Core Model, Usage Notes]**. So only one range is *selected* at a time; the many draft Annotations are separate `lineAnnotations`, not selections.
- **Custom content at a line.** `lineAnnotations: DiffLineAnnotation<T>[]` (`{ side, lineNumber, metadata }`, `lineNumber: 0` = above the first row) plus `renderAnnotation(annotation, fileDiff)` returning a React node. Although the diff is in Shadow DOM, annotations are **light-DOM children assigned to named slots**, so normal page CSS and React state/context apply (a textarea, a Tailwind-styled card) **[docs: Shared Diff Render Props; src: react/utils/renderDiffChildren.tsx, utils/getLineAnnotationName.ts]**. Several annotations may share a side/line. In `CodeView`, `renderAnnotation(annotation, fileOrDiff, item)` also gets the item (`id`, `version`).
- **Split/stacked switching.** Annotations and selections are in file-side coordinates, and the slot name is `annotation-<side>-<line>`, independent of `diffStyle` **[src: utils/getLineAnnotationName.ts]**, so both survive a `diffStyle` change by construction; the docs do not state this, so verify an in-progress textarea keeps focus and text when toggling. One trap: React children are keyed by **array index** (`key={index}` in `renderDiffChildren.tsx`), so inserting or removing an annotation earlier in the array remounts the ones after it and can lose draft text. Keep draft Annotations in a stable order (append-only, or sort by creation) or wrap content in a component keyed by Annotation id with its draft text in the Session DO state (already the design).
- **Outdated drafts.** The library has nothing for outdated detection; annotations are positions only. Recompute against the new `FileDiffMetadata` ourselves. (Edit mode remaps annotation lines while editing, but that is the out-of-scope #111.)
- **Quoted code.** Selected lines' text is not in the callback payload; read it from `fileDiff.additionLines` / `deletionLines` (these hold the file lines, or only the patch's lines when partial **[docs: FileDiffMetadata type]**), indexed by the one-based line number minus one when full, or via the hunks when partial.

### 3. Theming and styling

- **Shadow DOM.** All diff/file components render into Shadow DOM with CSS grid; CSS variables set on `:root`, a parent, or the component's `style` pass through **[docs: Overview, Styling]**. Tailwind utility classes do not reach inside, but `className`/`style` on the host and everything in annotation slots do. Tailwind v4's `@source`/`@theme` are irrelevant inside the shadow root.
- **Variables** **[docs: Styling → Global CSS Variables; src: style.css]**: `--diffs-font-family`, `--diffs-font-size`, `--diffs-line-height`, `--diffs-tab-size`, `--diffs-header-font-family`, `--diffs-font-features`, `--diffs-min-number-column-width`, `--diffs-gap-inline/-block`, `--diffs-addition-color-override`, `--diffs-deletion-color-override`, `--diffs-modified-color-override`, `--diffs-selection-color-override`, `--diffs-bg-selection-override`, `--diffs-bg-selection-number-override`, and (in `style.css`, not on the docs page) `--diffs-bg-{context,context-gutter,buffer,separator,hover,addition,deletion,addition-emphasis,deletion-emphasis,addition-number,deletion-number}-override`, `--diffs-fg-number(-addition/-deletion)-override`. All derive from `--diffs-bg`/`--diffs-fg` via `light-dark()` and `color-mix(in lab, …)`.
- **Fonts.** `--diffs-font-family` ← `ui-monospace, "SF Mono", "JetBrains Mono", Menlo, Consolas, monospace` (`--font-mono` in `styles.css`), `--diffs-header-font-family` ← the system UI stack; `--diffs-font-size: 13px` is the DESIGN.md Mono size (library default is 13px too, line-height default 20px; DESIGN wants 1.5).
- **Light/dark.** `theme: { dark, light }` with `themeType: 'system'` (default) follows `prefers-color-scheme`; `'light'`/`'dark'` force it, and `instance.setThemeType()` switches at runtime **[docs: Shared Diff Options; src: utils/cssWrappers.ts, components/FileDiff.ts]**. With `'system'` the library adds no `color-scheme` and relies on the host's computed one, and `styles.css` sets `color-scheme: light|dark` on `:root` already, so the app's system-follow behaviour carries over (`@custom-variant dark` is a media query, not a class, so there is no class toggling to wire).
- **Shiki themes.** Any bundled Shiki theme name or the built-in `pierre-light`/`pierre-dark` (also `-soft`, `-vibrant`, colour-blind variants in the package) **[docs: Themes; pkg dist chunks]**. Custom: `registerCustomTheme(name, loader, 'textmate' | 'zed' | 'diffs')`. Editor colours (`editor.background`, `editor.foreground`) drive `--diffs-bg`/`--diffs-fg`, so a theme with OKLCH-derived hex colours would match.
- **Best fit for DESIGN.md: a CSS-variables theme.** `registerCustomCSSVariableTheme(name, variableDefaults, fontStyle)` / `createCSSVariablesTheme()` make a theme whose colours are `var(--diffs-background)`, `var(--diffs-foreground)`, `var(--diffs-token-keyword)`, `--diffs-token-string-expression`, `--diffs-token-function`, `--diffs-token-constant`, `--diffs-token-comment`, `--diffs-token-parameter`, `--diffs-token-punctuation`, `--diffs-token-link`, `--diffs-token-inserted/-deleted`, `--diffs-ansi-*` **[docs: Utilities → registerCustomTheme (one paragraph); src: highlighter/themes/createCSSVariablesTheme.ts]**. Define those in `:root` and in the `prefers-color-scheme: dark` block of `styles.css`, next to the existing tokens, so one stylesheet owns both modes, and map `--diffs-background` to `var(--background)`/`var(--muted)` and the ruled lines via the `--diffs-bg-*-override` set. It works with both Shiki and Highlights backends **[src]**. Caveats: it is lightly documented, and I did not check it renders correctly end to end; the signal rule in DESIGN.md (green = running, red = failed) means diff additions/deletions in green/red need a call (open question 3).
- **Escape hatch:** `options.unsafeCSS` injects into the shadow root at `@layer unsafe` and is documented as having no backwards-compatibility guarantee **[docs: Styling → Unsafe CSS]**. Use data-attribute selectors only, and sparingly.
- **Worker-pool caveat:** with a pool, `theme`, `lineDiffType`, `tokenizeMaxLineLength`, `useTokenTransformer` are set on the pool (`highlighterOptions` / `setRenderOptions`), and component-level values are ignored; changing them re-renders everything and clears the cache **[docs: Worker Pool → Usage]**.

### 4. Weight and performance

- **Dependencies** **[pkg package.json]**: `shiki ^3 || ^4` (not currently in the lockfile of `origin/main`; Streamdown is there without it), `diff 9.0.0`, `hast-util-to-html`, `lru_map`, `@pierre/theme`, `@pierre/highlights`, `@pierre/theming`. Package size 14 MB unpacked (`dist`, mostly source maps and `.d.ts`), tree-shaken in practice.
- **Measured bundle** (Vite 8.3.5, React 19, `MultiFileDiff` + `PatchDiff` + `WorkerPoolContextProvider`, default `shiki-js` engine) **[measured]**: entry chunk 543 kB / 152 kB gzip vs 219 / 69 kB for a React-only entry, so diffs ≈ +324 kB / +83 kB gzip; worker chunk 46 kB / 16 kB gzip; Highlights (WASM lexers) 265 kB / 116 kB gzip, loaded only when `preferredHighlighter: 'highlights'`; 505 files in `dist/assets` in total because each of Shiki's ~200 languages and ~60 themes is its own dynamic-import chunk (e.g. TypeScript 181 kB, JavaScript 175 kB, C++ 786 kB, Emacs Lisp 790 kB, `pierre-dark`/`pierre-light` one chunk each), fetched only when a file of that language renders. Note the Worker and the main thread each carry their own copy of a language chunk (the worker's are bundled by the same build), so a language may be fetched twice. The service worker (`apps/web/public/sw.js`) caches nothing, so these are plain HTTP-cache fetches behind Access.
- **Languages and lazy loading.** Language is detected from the file extension (`getFiletypeFromFileName`), overridable with `lang` / `setLanguageOverride`; `registerCustomLanguage` for others **[docs: Utilities]**. Grammars load on demand; `preloadHighlighter` and the pool's `langs` preload. Unknown languages render as plain text.
- **Highlighter backends** **[docs: Highlighters]**: `shiki-js` (default, JS regex engine, no WASM), `shiki-wasm`, `highlights` (beta, 80 WAT lexers, needs WASM + SIMD; "usually performs best without a pool"). Only one backend per page. `shiki-js` needs no CSP allowance; the others need WebAssembly (check `canUseWASM()`). Cloudpid sets no CSP today (`git grep` over `apps/` for `content-security-policy` / `worker-src` finds nothing on `origin/main`).
- **Worker pool (experimental)** **[docs: Worker Pool]**: `WorkerPoolContextProvider poolOptions={{ workerFactory }} highlighterOptions={{ theme }}`; default 8 workers, LRU AST caches of 100 files + 100 diffs, `mainThreadMaxCharacters` keeps small diffs on the main thread, plain text paints first and highlighted output swaps in, and a pool that fails to start falls back to main-thread highlighting. Without a pool, highlighting runs on the main thread with the JS engine.
- **Under Vite 8**: the docs' Vite recipe is `import WorkerUrl from '@pierre/diffs/worker/worker.js?worker&url'; new Worker(WorkerUrl, { type: 'module' })`, noting you may need `worker.format: 'es'`; "only the Vite and NextJS examples have been tested by us" **[docs: Worker Pool → Setup]**; the repo's demo app uses the same import and `vite: catalog:` **[src: apps/demo/src/utils/createWorkerAPI.ts, apps/demo/package.json]**, and the package's own devDependency is `vite 8.1.0` **[pkg]**. **I confirmed** that Vite 8.3.5 builds it: the worker is emitted as one `worker-*.js` chunk (46 kB) with `worker: { format: "es" }` **[measured]**. I did not run it in a browser. Worker is same-origin static asset served by the main Worker's asset layer, so no special route is needed; under `vite dev` the proxy list in `vite.config.ts` does not need to change. Alternative with no bundler step: copy `dist/worker/worker-portable.js` into `apps/web/public/` and `new Worker('/…/worker-portable.js')` (one self-contained script, bundles all backends) **[docs]**.
- **Virtualization.** `CodeView` has "built-in per-line virtualization that should scale to nearly any file or diff that can fit in memory", only renders the visible window, reconciles measured heights (wrapped lines, annotations), and recycles item DOM shells on scroll (`onPostRender` `unmount` phase fires then) **[docs: CodeView]**. The lower-level `Virtualizer` keeps every top-level file container mounted and "more likely to blank during fast scroll"; use only when code shares a scroller with other DOM **[docs: Virtualization]**. Docs recommend a Worker Pool with virtualization for large diffs. `CodeView` reads the pool from React context unless `disableWorkerPool` **[src: react/CodeView.tsx]**.
- **Documented limits/defaults** (no hard size cap is documented): `tokenizeMaxLineLength` 1000 (lines longer are not highlighted), `maxLineDiffLength` 1000 (no word-level highlight beyond it), `expansionLineCount` 100, `collapsedContextThreshold` 1, pool size 8 **[docs: Shared Diff Options, Worker Pool → API Reference]**. Note: `src/constants.ts` has `DEFAULT_TOKENIZE_MAX_LENGTH = 100_000` read as `options.tokenizeMaxLength` in `File.ts`/`FileDiff.ts`, which does not match the documented option name or value; check which really applies. There is no built-in collapse of lockfiles/generated/binary files; that stays our job (`options.collapsed` per item hides the body, header stays) **[docs: Shared Props; CodeView]**. Binary files do not appear in a text patch as hunks anyway.
- **SSR** (`@pierre/diffs/ssr`, `preloadFileDiff`, …) exists but cloudpid's web app is a client-only SPA on static assets; not needed.

### 5. Mobile/touch, accessibility, licence, cadence

- **Touch.** Pointer events throughout. Mouse hover is ignored for touch/pen (`pointerType !== 'mouse'`), and on touch, tapping the gutter reveals the "+" utility before selection starts; line-number cells and the gutter utility have `touch-action: none` so a drag from them selects instead of scrolling **[src: managers/InteractionManager.ts ~455-470, 785-805; style.css `[data-interactive-line-numbers] [data-column-number]` and `touch-action: none` rules]**. `CodeView` disables pointer events on content while scrolling (opt out with `pointerEventsOnScroll`) and clears pending programmatic scrolls on `touchstart`. Not documented anywhere as a mobile feature: **no mobile-specific docs, no mention of long-press, and the line-number column is the only selection handle**, a small target on a phone. A WebKit/Safari 26 bug causes scroll jumping with a custom `renderGutterUtility` plus `hunkSeparators: 'line-info'` (<https://bugs.webkit.org/show_bug.cgi?id=308027>); use the built-in `enableGutterUtility` button or `line-info-basic` **[docs: Shared Diff Options]**.
- **Accessibility.** The docs have no accessibility section. In the source, ARIA is minimal: hunk separators have `role="button"`, the SVG sprite is `aria-hidden`, the gutter "+" is a real `<button type="button">` **[src: utils/createSeparator.ts, sprite.ts, utils/createGutterUtilityElement.ts]**; line selection is pointer-only (no keyboard path found in `InteractionManager`; keyboard handling exists only in edit mode). Plan on our own accessible route for adding an Annotation (e.g. a per-file "Add note" control that takes a line range in a form) if keyboard/screen-reader use matters; the annotation content itself is our React DOM, so it is as accessible as we make it.
- **Licence.** Apache-2.0 for `@pierre/diffs`, `@pierre/theme`, `@pierre/highlights`, `@pierre/theming` **[pkg package.json `license: apache-2.0`; LICENSE.md; repo licence API field `Apache-2.0`]**. Shiki is MIT (not checked from source here). Apache-2.0 needs the NOTICE/licence carried in redistribution; cloudpid is a private deploy, so low impact.
- **Cadence and stability** **[npm registry `time`; GitHub releases `diffs-v*`]**: 1.2.x (May–June 2026) → 1.3.0 (2026-07-31) → 1.4.0 (09-04) → 1.5.0 (09-24) → 1.6.0 (10-20): a minor roughly every 3–5 weeks, patches in between, `1.6.0-beta.1` ten days before 1.6.0; the repo had a push the day before I read it, ~6.3k stars, ~80 open issues. Semver minors have added API surface (CodeView, edit mode, Highlights) rather than removing it, but I did not audit the changelog for breaking changes between minors. Pin the exact version (`"@pierre/diffs": "1.6.0"`), as the monorepo's other fast-moving deps are, and gate upgrades on a visual check. Flagged experimental/beta in the docs: Worker Pool, render cache, token hooks, `UnresolvedFile`, Highlights, `unsafeCSS` (see above). Core types (`FileContents`, `FileDiffMetadata`, annotations), `MultiFileDiff`/`FileDiff`/`File`/`CodeView`, selection, and `parseDiffFromFile`/`parsePatchFiles` are not flagged.

## Open questions

1. **Cross-side ranges.** `SelectedLineRange` can start on one side and end on the other (`endSide`). Does a Review Annotation allow that, or do we clamp the selection to one side (the library has an `activeLineSide` write option, but I found no public prop to limit user drags)? A prototype should drag across a change in split view.
2. **Does the `edit` tool give us full file contents?** `MultiFileDiff` needs old/new contents; a per-call diff built only from an edit's old/new snippets would show snippet-relative line numbers, so a per-call Annotation could not be anchored to file lines. Depends on what the Session stores for `edit`/`write` calls (not read here); may need the Workspace file at call time, or a hunk-based patch.
3. **Theme mapping.** Does the CSS-variables theme (`registerCustomCSSVariableTheme`) render the `DESIGN.md` palette correctly in both modes, and does `light-dark()` pick up `:root`'s `color-scheme` in the shadow root as the source suggests? Which colours do additions/deletions use, given "green means running, red means failed" in DESIGN.md? Needs a prototype.
4. **Worker pool: worth it?** Pool is experimental; Highlights guidance says main-thread is often faster. Measure on a representative Changes diff (many files, one 5k-line file) with and without a pool and with `mainThreadMaxCharacters`; also confirm in a browser that the Vite `?worker&url` worker starts and a language chunk is not fetched twice.
5. **Annotation remount.** Verify in a browser that toggling split/stacked keeps a draft textarea's text and focus, and that keyed-by-index children behave as read from source when drafts are added or removed.
6. **Docs vs source on tokenize limit** (`tokenizeMaxLineLength` 1000 in docs vs `tokenizeMaxLength` 100 000 in `File.ts`/`FileDiff.ts`) and how an over-long line looks in the diff.
7. **Large-file ceiling.** No documented cap; `parseDiffFromFile` runs jsdiff on the main thread. Find where a pair of files (say 2 MB each) stalls the UI, to set the "big diffs" threshold in #99's not-yet-specified list, and whether server-side `git diff` + `loadDiffFiles` should be the only path for Changes.
8. **Accessibility target.** Decide whether a keyboard-only way to create an Annotation is required, since the library provides none for diffs.
