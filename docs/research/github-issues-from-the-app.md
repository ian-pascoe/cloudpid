# Creating issues from the GitHub App: labels, permissions, token scoping

Research date: 2026-11-09. Sources are primary only (docs.github.com, GitHub's REST OpenAPI description `github/rest-api-description`, GitHub changelog). Where the sources do not say something, the section says "Unconfirmed" or "Silent" and names what was checked. Quotes are short; the URL under each claim is the source. Nothing here was tested against GitHub: no write call was made.

Setup in question: an installation access token minted with only `issues: write` (plus `metadata: read`) calls `POST /repos/ian-pascoe/cloudpid/issues` with `labels: ["cloudpid-report", "needs-triage"]`. The repo is public and owned by a user account the App is installed on (ADR-0025).

Spec version read: OpenAPI 2022-11-28 description, `info.version` 1.1.4, from `main` at commit `2f8f80e` (2026-11-07). https://github.com/github/rest-api-description/blob/main/descriptions/api.github.com/api.github.com.2022-11-28.json . The docs pages show `X-GitHub-Api-Version: 2026-03-10` in their examples; the endpoint text quoted below is the same in both.

## 1. A label name that does not exist in the repo

- **Unconfirmed.** No primary source says whether `POST /repos/{owner}/{repo}/issues` creates a missing label, rejects the request, or drops it. Checked: the "Create an issue" page (https://docs.github.com/en/rest/issues/issues#create-an-issue), the endpoint's `post` operation in the OpenAPI description (above), the "Add labels to an issue" page (https://docs.github.com/en/rest/issues/labels#add-labels-to-an-issue), and the docs search for the changelog. The `labels` parameter text is only: "Labels to associate with this issue. NOTE: Only users with push access can set labels for new issues. Labels are silently dropped otherwise."
- **What the docs do say about errors.** The response codes are 201, 400, 403, 404, 410, 422, 503. 422 is described as "Validation failed, or the endpoint has been spammed." Nothing ties 422 to a missing label. https://docs.github.com/en/rest/issues/issues#create-an-issue
- **Same silence on the second call.** "Add labels to an issue" lists 200, 301, 404, 410 and 422 and does not say what a missing label does. Only "Remove a label from an issue" states a missing-label result: "returns a `404 Not Found` status if the label does not exist." https://docs.github.com/en/rest/issues/labels#remove-a-label-from-an-issue
- **Search results I did not rely on.** Third-party issue threads claim a 422 when a label is missing. They are not primary sources, so they are not evidence here.
- **Consequence.** Do not assume either outcome. Create the two labels first with `POST /repos/{owner}/{repo}/labels` (Issues write; see section 2), or run one test issue and read the response's `labels`. The 201 response's `labels` array shows which labels were kept.

## 2. Does "push access" apply to an installation token with `issues: write` and no `contents: write`?

- **The note applies to the labels parameter as written.** "Only users with push access can set labels for new issues. Labels are silently dropped otherwise." The same wording is on `assignees`, `assignee`, `milestone` and `type`. https://docs.github.com/en/rest/issues/issues#create-an-issue ; the OpenAPI `labels` and `assignees` descriptions repeat it.
- **Which fine-grained permission governs the endpoint.** Create an issue works with "GitHub App installation access tokens" and "The fine-grained token must have the following permission set: 'Issues' repository permissions (write)". https://docs.github.com/en/rest/issues/issues#create-an-issue . The permissions table lists `POST /repos/{owner}/{repo}/issues` under "Repository permissions for 'Issues'" at `write`, for UAT and IAT, with no "Additional permissions" note. https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps#repository-permissions-for-issues . The OpenAPI operation has `enabledForGitHubApps: true`.
- **No separate permission for labels or assignees at creation.** Neither page names one. The App permission schema describes `issues` as "issues and related comments, assignees, labels, and milestones". https://github.com/github/rest-api-description (`components.schemas.app-permissions.properties.issues`, in the file above). "Contents" is described as "repository contents, commits, branches, downloads, releases, and merges", with no mention of issues.
- **Whether "push access" means `contents: write` for an installation token: Silent.** Checked: the Create an issue page, the permissions-required page, the "Choosing permissions for a GitHub App" page, and the troubleshooting page. None says how the push-access check maps onto an App token. The closest statement is general: "The success of an API request with an installation access token only depends on the app's permissions." https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app . It does not mention the push-access note.
- **Reading, stated as inference.** The docs list only Issues write for this endpoint and say an installation token's success depends only on the App's permissions, so an `issues: write` token is the documented fit, and nothing in the docs says it needs `contents: write`. The docs do not say the labels are kept. The answer is therefore **undecided by the docs**. The 201 response's `labels` array is the check: if it is empty, the labels were dropped.
- **Public repo.** "Any user with pull access to a repository can create an issue." https://docs.github.com/en/rest/issues/issues#create-an-issue . This is the access rule for creating the issue itself, not for labels.
- **`X-Accepted-GitHub-Permissions`.** Responses carry this header with the permissions the endpoint accepts, as `name=level` lists separated by commas, and alternatives separated by semicolons. https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api#resource-not-accessible . It would show what the create call accepts. It was not read here, because the endpoint is a POST.
- **A second call: `POST /repos/{owner}/{repo}/issues/{issue_number}/labels`.** "The fine-grained token must have at least one of the following permission sets: 'Issues' repository permissions (write); 'Pull requests' repository permissions (write)". It works with installation access tokens. https://docs.github.com/en/rest/issues/labels#add-labels-to-an-issue . So `issues: write` alone is enough for this call, and `contents` is not listed. The permissions table lists it under both "Issues" and "Pull requests" with the note "Multiple permissions are required, or a different permission may be used." https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps
- **What the second call does not settle.** The page does not say whether the push-access rule applies to it, or what happens to a label that does not exist (section 1). Body: `{"labels": ["a", "b"]}`; the OpenAPI body also accepts an array of strings directly, and objects with `name` (plus `rationale`, `suggest`, `confidence`). It returns 200 with the issue's labels. `POST /repos/{owner}/{repo}/labels` ("Create a label") is listed at Issues write with the same "Multiple permissions" note. https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps
- **Metadata.** `GET /repos/{owner}/{repo}` is listed under "Repository permissions for 'Metadata'" at `read`. https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps#repository-permissions-for-metadata . That "metadata: read" is added implicitly to every token: **unconfirmed**; no page I read states it.

## 3. Narrowing the token: `POST /app/installations/{installation_id}/access_tokens`

- **Both parameters exist, alongside `permissions`.** The body has `repositories` (array of strings, "List of repository names that the token should have access to"), `repository_ids` (array of integers, "List of repository IDs that the token should have access to") and `permissions` (object). https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app ; OpenAPI path `/app/installations/{installation_id}/access_tokens`, `post`.
- **Example from the docs.** `{"repositories":["Hello-World"],"permissions":{"issues":"write","contents":"read"}}` returns 201 with `repository_selection: "selected"`, the `repositories` list and the granted `permissions`. https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app
- **Names are bare repository names.** The schema's example is `rails` and the doc example is `Hello-World`, with no owner. The installation is on one account, so the names resolve within it (inference; the page does not say so).
- **Limits.**
  - "Up to 500 repositories can be listed in this manner." https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app ; also "You can list up to 500 repositories." https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app
  - "The installation access token cannot be granted access to repositories that the installation was not granted access to."
  - Without either parameter, the token has access to "all repositories that the installation was granted access to".
  - `permissions` omitted gives "all of the permissions that were granted to the app"; the token "cannot be granted permissions that the app was not granted." The `issues` values are `read` and `write` (OpenAPI `app-permissions`).
  - Needs a JWT, "Bearer" only; installation tokens and user tokens are not accepted. Tokens expire after one hour.
  - Response codes: 201, 401, 403, 404, 422 (422 is "Validation failed, or the endpoint has been spammed.").
- **Unconfirmed:**
  - Whether `repositories` and `repository_ids` may be sent in the same request, and which wins. The docs say "the `repositories` or `repository_ids` body parameters" and give no rule. Send one.
  - What status a name that does not exist, or that the installation cannot reach, returns. 404 and 422 are both listed and neither is tied to this case.
  - Whether `metadata: read` has to be listed in `permissions`.
- **Fit.** `{"repositories":["cloudpid"],"permissions":{"issues":"write"}}` is the documented shape for a one-repo, issues-only token. The Workspace DO today mints with full permissions (ADR-0025); this would be a separate, narrower mint.
- **Token format.** New installation tokens are moving to a stateless `ghs_APPID_JWT` format, so a token is no longer exactly 40 characters. Starting April 27, 2026, in a staged rollout. https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app ; https://github.blog/changelog/2026-05-15-github-app-installation-tokens-per-request-override-header (linked from that page; not fetched). Relevant to the ADR's masking, which matches minted tokens exactly and keeps the `ghs_` shape for refusals.

## 4. Rate limits that matter for an automated poster

- **Create an issue's own warning.** "Creating content too quickly using this endpoint may result in secondary rate limiting." It "triggers notifications." https://docs.github.com/en/rest/issues/issues#create-an-issue
- **Content creation.** "In general, no more than 80 content-generating requests per minute and no more than 500 content-generating requests per hour are allowed. Some endpoints have lower content creation limits." The limit counts actions on the web interface as well as REST and GraphQL. https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#about-secondary-rate-limits . **Silent** on whether issue creation has a lower limit, and on whether the limit is per token, per user, per installation or per repository.
- **Concurrency.** "No more than 100 concurrent requests are allowed", shared by REST and GraphQL. Same page.
- **Points per endpoint per minute.** "No more than 900 points per minute are allowed for REST API endpoints"; most REST `POST` requests cost 5 points, "Some REST API endpoints have a different point cost that is not shared publicly." Same page. So 180 POSTs a minute at the default cost, above the 80/minute content limit. The cost of this endpoint is unconfirmed.
- **CPU time.** "No more than 90 seconds of CPU time per 60 seconds of real time." Same page.
- **Pacing.** "Make requests serially instead of concurrently" and "wait at least one second between each request" for `POST`, `PATCH`, `PUT` and `DELETE`. https://docs.github.com/en/rest/guides/best-practices-for-using-the-rest-api
- **On a limit error.** 403 or 429. If `retry-after` is present, wait that many seconds; if `x-ratelimit-remaining` is `0`, wait until `x-ratelimit-reset` (epoch seconds); otherwise wait at least a minute, then back off exponentially and give up after some retries. "Continuing to make requests while you are rate limited may result in the banning of your integration." https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#exceeding-the-rate-limit ; https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api#rate-limit-errors
- **No way to read the secondary limit.** "There is not a way to check the status of your secondary rate limit." Same rate-limits page. The limits "are subject to change without notice."
- **Primary limit for the installation.** A minimum of 5,000 requests per hour per installation (15,000 on a Cloud organization); for non-Cloud installations it grows by 50 per hour for each repository beyond 20 and each organization user beyond 20, capped at 12,500. https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#primary-rate-limit-for-github-app-installations . This matches the ADR's note that the limit is shared by every Workspace and the main Worker.
- **Abuse language.** "Repeatedly requesting a missing resource wastes your rate limit and can trigger a secondary rate limit", and "Intentionally ignoring repeated validation errors may result in the suspension of your app for abuse." https://docs.github.com/en/rest/guides/best-practices-for-using-the-rest-api . A poster that retries a 422 in a loop is the case this describes.
- **Other API-level outcomes.** Issues disabled on the repo gives `410 Gone`. https://docs.github.com/en/rest/issues/issues#create-an-issue

_Bears on:_ for a poster that files a few reports an hour, the documented limits are far away; the risk is a retry loop or a burst. Serialise the posts, keep at least a second between them, honour `retry-after`, and cap retries. Because the docs cannot say what a missing label does or whether `issues: write` alone keeps the labels, create the two labels once and check the labels on the first 201 response before relying on them.
