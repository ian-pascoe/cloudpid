# cloudpid's own MCP server: streaming, client support, prior art, tool design (2026-11-01)

Question (issue #392): what can cloudpid's stateless `/mcp` (SDK v2 `createMcpHandler`, `legacy: "stateless"`, both eras, no elicitation/sampling/roots, no MCP tasks) rely on from its clients (pi, Claude Code), and how do comparable products expose remote coding agents? Access/managed OAuth, spec revisions, the SDK client libraries and tasks are already covered in `research-mcp-server-behind-access.md`, `research-mcp-spec-revisions.md`, `research-mcp-core-client-libraries.md` and `research-mcp-tasks.md`; they are not repeated here.

Tags: **[V]** verified in a primary source read today; **[I]** inference from verified facts; **[U]** not found or not checkable. Versions read: `@modelcontextprotocol/server` and `/client` **2.4.0** (npm `latest`, source extracted from the published source maps), pi at `.repos/pi` commit `6291b9bc`, Claude Code docs at `code.claude.com/docs/en/mcp` (read 2026-11-01), spec `2025-11-25` and `2026-07-28` pages at modelcontextprotocol.io.

## 1. Answers in brief

1. **Streaming without a session works on both lanes.** Both spec revisions let the server answer a `tools/call` POST with an SSE stream carrying request-related `notifications/progress` and `notifications/message` before the result; no session id is needed. In SDK 2.4.0 **Legacy always answers with SSE** (the legacy transport's `enableJsonResponse` is not reachable through `createMcpHandler`); **Modern defaults to `auto`** (JSON unless the handler emits a related message first; then it upgrades to SSE) and can be forced with `responseMode: 'sse'` or `'json'` (`'json'` silently drops progress and logs).
2. **A handler sends progress with `ctx.mcpReq.notify({method:'notifications/progress', params:{progressToken, progress, total?, message?}})`**, taking `progressToken` from `ctx.mcpReq._meta?.progressToken`; there is no progress helper. `ctx.mcpReq.log(...)` sends `notifications/message`, but only if the server declared `logging`; on Modern only if the request carried `io.modelcontextprotocol/logLevel`.
3. **Timeouts.** pi: default **60 s** per request (`timeout` in `mcp.json`, seconds), **every progress notification re-arms it** (no total cap), and pi always sends a `progressToken` (the JSON-RPC id) and shows progress text as the tool's live update. TS SDK client: default 60 s, `resetTimeoutOnProgress` default `false`. Claude Code: `MCP_TOOL_TIMEOUT` default ≈ 28 h, a **hard wall-clock limit progress does not extend**; a separate 5-minute idle timeout (HTTP) that progress or any response **does** reset; a per-request timer on the first response byte of at least 60 s; main-conversation calls over **2 min move to a background task**.
4. **Primitives clients surface.** Both surface tools (pi: `codemode`/`deferred`/`direct` exposure) and resources. pi has no prompts or completion support at all, drops `_meta`, shows annotations only to extensions, feeds the model `content` (not `structuredContent`, except as a fallback when `content` is empty) and only the first line of `instructions`. Claude Code surfaces prompts as slash commands, resources via `@` mentions, server instructions (cut at 4,096 chars) and annotations (`readOnlyHint`, `idempotentHint` change behaviour); its docs say nothing on `structuredContent`/`outputSchema` **[U]**. Result limits: pi truncates the middle of text over **20 KB** and saves the rest to a temp file; Claude Code warns at **10,000 tokens**, caps at **25,000** (`MAX_MCP_OUTPUT_TOKENS`), and saves text over **50,000 chars** to a file unless the tool sets `_meta["anthropic/maxResultSizeChars"]` (ceiling 500,000).
5. **Prior art converges on:** a durable agent/session handle, a _Run_ per prompt (Cursor), `create` returning at once, a separate send-input call, cursor-paged event/message history, status enums, and an explicit wait/gather call only where the transport has one (Devin `devin_session_gather`, A2A blocking `SendMessage`, Factory's optional wait). Nobody confirms destructive actions by asking the client: they gate by plan approval (Jules `requirePlanApproval` + `:approvePlan`), by a pending "suggestion" (GitHub `is_suggestion`), by separate archive/delete endpoints (Cursor), or leave it to the client (`claude mcp serve`). OpenAI **removed** `codex mcp-server`; the Codex integration surface is now a JSON-RPC app-server.
6. **Cancellation.** Modern: closing the response stream is the cancel signal and the server MUST treat it as cancellation. Legacy: spec says disconnect SHOULD NOT be read as cancel and the client SHOULD send `notifications/cancelled`; but the SDK's stateless legacy fallback **tears down the per-request server on request abort**, which aborts `ctx.mcpReq.signal`, and a `notifications/cancelled` POST reaches a fresh instance and does nothing. On Workers `Request.signal` needs the `enable_request_signal` compatibility flag. A Run must never be tied to that signal.

## 2. Progress and streaming in a stateless server

### 2.1 Spec

- **Legacy `2025-11-25`**, Streamable HTTP: if the POST body is a request the server MUST return either `text/event-stream` or `application/json`, and the client MUST support both. A session id is optional ("MAY assign a session ID"). — `…/2025-11-25/basic/transports` §Sending Messages, §Session Management. **[V]** The stream "SHOULD eventually include a JSON-RPC response"; notifications on it relate to the request. Progress: any `progressToken` in `_meta`, notifications MUST only reference active tokens, `progress` MUST increase, receivers SHOULD rate-limit. — `…/2025-11-25/basic/utilities/progress`. **[V]**
- **Modern `2026-07-28`**: each request is its own POST; the server answers with a single JSON object or an SSE stream "scoped to that request, carrying request-related notifications followed by the final response"; it "MAY send JSON-RPC notifications — for example `notifications/progress` or `notifications/message` — before the final response", which "MUST relate to the originating client request"; no server→client requests on the stream; the final response SHOULD terminate it; servers SHOULD send `X-Accel-Buffering: no`. `progress` and `message` "flow only on the response stream of the request they relate to", never on `subscriptions/listen`. — `…/2026-07-28/basic/transports/streamable-http` §Receiving Messages. **[V]**
- **Modern `notifications/message` is deprecated** (SEP-2577, ≥ 12 months window; new implementations SHOULD NOT adopt it) and the server MUST NOT send it for a request that lacks `_meta["io.modelcontextprotocol/logLevel"]`. — `…/2026-07-28/server/utilities/logging`. **[V]** Progress is **not** deprecated. — `research-mcp-spec-revisions.md`.
- **Tasks and progress** are mutually exclusive in the Modern extension; cloudpid returns no tasks, so plain progress on the call is available. — `research-mcp-tasks.md`.

### 2.2 `createMcpHandler` (SDK 2.4.0, `packages/server/src/server/{createMcpHandler,streamableHttp,perRequestTransport}.ts`)

- **Options** (`CreateMcpHandlerOptions`): `legacy: 'stateless' | 'reject'`, `onerror`, `responseMode: 'auto' | 'sse' | 'json'`, `bus`, `maxSubscriptions` (1024), `keepAliveMs` (15,000; 0 disables), `maxRequestBodySize` (4 MiB, `413` beyond it). **No `enableJsonResponse`.** **[V]**
- **Legacy (`legacy: 'stateless'`)**: per POST it calls the factory with `{era:'legacy'}`, connects a fresh `WebStandardStreamableHTTPServerTransport({ sessionIdGenerator: undefined, keepAliveMs, maxRequestBodySize })` and calls `handleRequest`. The transport's `enableJsonResponse` defaults to `false`, so every request-bearing POST is answered with `Content-Type: text/event-stream` (`Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no`) and the `Response` is returned as soon as the stream object exists, so the **first byte is not delayed by handler time**. GET and DELETE → `405`; a notification POST → `202`. The pair is closed when the stream ends or the consumer abandons it. **[V]** To get JSON-only legacy you must route `isLegacyRequest(request)` yourself to a transport built with `enableJsonResponse: true` in front of a `legacy: 'reject'` handler (documented hand-wiring pattern); this loses progress on Legacy. **[V]**
- **Modern**: `PerRequestHTTPServerTransport`. `auto` (default): no headers are sent until the handler emits a related message (then it upgrades to SSE and starts keepalive comment frames) or returns the result. A handler that works 90 s without progress produces **no bytes for 90 s**. `sse`: always SSE, opened after the pre-dispatch checks, so ladder errors keep their HTTP status. `json`: never streams; related messages are dropped (the handler warns at construction). `subscriptions/listen` is always SSE. **[V]** Keepalive is a comment frame every `keepAliveMs`. **[V]**
- **How the handler sends progress/log**: `ServerContext.mcpReq` has `notify(notification)` ("sends a notification that relates to the current request"), `log(level, data, logger?)`, `signal`, `_meta`, `send`, plus deprecated `elicitInput`/`requestSampling`. Source comment: related notifications ride the in-flight exchange, and "without the related-request stamp, per-request hosting (`createMcpHandler`, either era) silently drops the message". There is no `ctx.mcpReq.progress()` helper, and the source does not check that `progress` increases or that a token was supplied; the handler must do both. **[V]**
- **`log` gating** (`server.ts` ≈ l.413): returns without sending unless the server declared `capabilities.logging`; on a Modern request, unless `_meta["io.modelcontextprotocol/logLevel"]` is present (an absent key suppresses); on Legacy, the session level from `logging/setLevel`, which in a stateless server is lost between requests, so Legacy logs go out **unfiltered**. **[V]**
- Verified earlier to run in workerd (`research-mcp-core-client-libraries.md` §6, §9).

**Consequences for cloudpid [I]**: (a) keep any wait/poll call well under 60 s (pi default, SDK default, Claude Code's first-byte floor) and emit a progress notification or SSE bytes early; (b) on Modern use `responseMode: 'sse'` (or send an immediate progress notification) so a call that waits does not hold back headers; (c) do not rely on progress to extend Claude Code's wall-clock timeout; its default is ≈ 28 h, so the real ceiling is cloudpid's own wait cap and the 2-minute auto-background; (d) a Worker has no HTTP duration limit while the client stays connected, but a deploy drains old isolates after a grace period and "crashes, resource pressure, and shutdowns can interrupt work earlier" (Workers limits page), another reason for short waits. **[V]** for the Workers text.

So both lanes will see real traffic.

## 4. Prior art: servers/APIs that drive remote coding agents

None of the other products' _MCP_ surfaces is both public and complete; several are REST/JSON-RPC and are included because they define the same operations.

### 4.1 Cursor Cloud Agents API v1 (public beta, REST, not MCP) — `cursor.com/docs/cloud-agent/api/endpoints`

The closest match to cloudpid's Session/Run split. **[V]**

- Durable **agent** + per-prompt **run**. `POST /v1/agents` creates an agent and "immediately enqueues its initial run" (response has `agent` and `run`). `GET /v1/agents` (`limit` default 20, max 100, `cursor`, `prUrl` filter), `GET /v1/agents/{id}`.
- **Send input**: `POST /v1/agents/{id}/runs` `{prompt:{text,images?}, mode?, mcpServers?}`; "only one run can be active per agent" (`409 agent_busy` otherwise). `delivery: "steer"` injects into the running turn (`202`, `delivery: steered|queued`, `runId` when steered); a failed steer "may still have reached the agent… retrying can deliver the prompt twice".
- **Follow a run**: `GET …/runs` (cursor-paged), `GET …/runs/{runId}` (`status` `CREATING|RUNNING|WAITING_FOR_BACKGROUND_WORK|FINISHED|ERROR|CANCELLED|EXPIRED`, `durationMs`, `result` final text, `git.branches[{repoUrl,branch,prUrl}]`), `GET …/runs/{runId}/stream` SSE (`status`, `assistant`, `thinking`, `tool_call{callId,name,status,args?,result?,truncated?}`, `heartbeat`, `result`, `error`, `done`; opaque event `id`s, `Last-Event-ID` resume; `X-Cursor-Stream-Retention-Seconds`; after retention `410 stream_expired` → read the run instead). `POST …/cancel`.
- **Destructive**: archive, unarchive and **permanent delete** are three separate endpoints; no confirmation step. Artifacts listed/downloaded separately.

### 4.2 Google Jules API v1alpha (REST) — `developers.google.com/jules/api`

**[V]** `GET /sources`; `POST /sessions {prompt, sourceContext{source, githubRepoContext{startingBranch}}, automationMode (e.g. AUTO_CREATE_PR), requirePlanApproval, title}` returns at once with `name`/`id`; "you can poll the latest session information using GetSession or ListSessions" (`outputs[].pullRequest`); `GET /sessions?pageSize=` ; `POST /sessions/{id}:approvePlan`; `POST /sessions/{id}:sendMessage {prompt}` returns **empty**: "the agent will send its response in the next activity"; `GET /sessions/{id}/activities?pageSize&pageToken` (default 50, max 100, `nextPageToken`; activities have `originator`, `createTime`, and one of `planGenerated|planApproved|progressUpdated|…` plus `artifacts` like `bashOutput`, `changeSet`, `media`). API-created sessions auto-approve plans by default; `requirePlanApproval: true` makes the approval a separate explicit call.

### 4.3 Devin MCP server (`https://mcp.devin.ai/mcp`, Streamable HTTP) — `docs.devin.ai/work-with-devin/devin-mcp`

**[V]** (tool names and descriptions); argument schemas are not published **[U]**. Bearer `cog_` service-user key (+ `X-Org-Id` for enterprise). Tools: `devin_session_create` (one or more sessions; prompt, title, playbook, tags, ACU limit), `devin_session_search` (filters), **`devin_session_interact`** (one tool: "get status, send messages, sleep, terminate, archive, read messages and attachments, or manage tags"), **`devin_session_events`** ("list summaries, fetch full event details, or search event contents by text"), **`devin_session_gather`** ("wait for multiple sessions to reach a settled state (finished, errored, sleeping, or waiting) before returning… instead of polling in a loop"), plus `devin_playbook_manage`, `devin_knowledge_manage`, `devin_schedule_manage` (CRUD multiplexed by an action argument), `devin_list_integrations`. REST v3 session `status` is `new|claimed|running|exit|error|suspended|resuming` with `status_detail` `working|waiting_for_user|waiting_for_approval|finished|…` (`docs.devin.ai/api-reference/v3/sessions/enterprise-sessions-insights`). Lessons: one `*_manage`/`*_interact` tool per resource keeps the tool count low but mixes read-only and destructive actions under one annotation set; a server-side **wait** tool exists precisely because MCP has no push for results.

### 4.4 GitHub MCP server (Copilot coding agent) — `github/github-mcp-server` README (read today)

**[V]** `create_pull_request_with_copilot` (`owner`, `repo`, `problem_statement`, `title`, `base_ref?`; descriptions say to "confirm [owner/repo] with the user before proceeding"), `assign_copilot_to_issue` (`issue_number`, `base_ref?`, `custom_instructions?`), opt-in `assign_copilot_to_issue_with_intent` with **`is_suggestion: true` "records a pending Copilot assignment intent rather than launching the agent. Approval later supplies the launch context"** plus `rationale`/`confidence`, and `request_copilot_review`. No job-status tool in the README at this commit; progress is followed through the PR and issue tools. List tools use `perPage` (max 100) with `page` or `after` cursors; tools are grouped in toolsets (`copilot`, `copilot_issue_intents`, …) and have a read-only mode. The pending-intent pattern is the only documented way a server splits "propose" from "launch" without elicitation.

### 4.5 OpenAI Codex

- **`codex mcp-server` has been removed** ("the `codex mcp-server` command and the standalone `codex-mcp-server` binary have been removed"; migrate to the app server, "not an MCP server") — `developers.openai.com/codex/guides/agents-sdk`. **[V]**
- What it was (tag `rust-v0.50.0`, `codex-rs/mcp-server/src/codex_tool_config.rs`): two tools, **`codex`** (`prompt`, `model`, `profile`, `cwd`, `approval-policy` `untrusted|on-failure|on-request|never`, `sandbox` `read-only|workspace-write|danger-full-access`, `config`, `base-instructions`) and **`codex-reply`** (`conversationId`, `prompt`). One `tools/call` spanned the whole turn and streamed agent events as notifications while it ran; approvals used server→client elicitation. **[V]** That is the shape cloudpid has ruled out (no server requests; a Run outlives a call).
- Its replacement, the **app server** (`developers.openai.com/codex/app-server`, JSON-RPC over stdio, experimental): `thread/start`, `thread/resume`, `turn/start` (streams `item/*` and `turn/*` notifications), `turn/steer`, `turn/interrupt`, `thread/list` (cursor), `thread/read` (metadata only), `thread/turns/list` (`nextCursor` + `backwardsCursor`, newest-first by default, `itemsView`), approvals as server requests (`item/permissions/requestApproval`). **[V]**
- Codex Cloud tasks (ChatGPT web/mobile/desktop, `developers.openai.com/codex/cloud`): documented only as a UI; no public task API or MCP surface found **[U]**.

### 4.6 Claude Code `claude mcp serve` — `code.claude.com/docs/en/mcp` §Use Claude Code as an MCP server

**[V]** stdio only; exposes Claude Code's _tools_ (Bash, Read, Edit, …), **not** an agent-run/session API. "Your own client is responsible for implementing user confirmation for individual tool calls." For long work it is a pull pattern: `run_in_background: true` on a Bash call returns `backgroundOutputPath`; the client reads the file (via `Read` with `offset`/`limit`) and detects completion by appending `; echo DONE`; "Claude Code adds no closing line… and doesn't notify your client".

### 4.7 Factory (REST) — `docs.factory.ai/docs/api-reference/sessions`

**[V]** `/api/v0/sessions`: `GET` (limit 1–100, cursor; `nextCursor` and a has-more flag), `POST`, `GET/PATCH/DELETE /{id}`, `GET /{id}/children`, `POST /{id}/interrupt` (idempotent when idle; returns `status` `idle|pending|running`), `GET /{id}/messages` (limit 1–100, `cursor`, `role` filter), `POST /{id}/messages` ("adds a user message and **optionally waits for agent completion**"; returns `messageId`, `status`, `recipientDroidStatus` — `idle` means the message starts a turn now, `running` means it is queued behind the current turn), `GET /{id}/messages/{messageId}`. No Factory MCP server found **[U]**. Amp: no public remote-agent MCP server or API found **[U]**.

### 4.8 Agent-to-agent: A2A (`a2a-protocol.org/latest/specification`)

**[V]** `SendMessage` is **blocking by default**: it "MUST wait until the task reaches a terminal… or interrupted (INPUT_REQUIRED, AUTH_REQUIRED) state"; `returnImmediately: true` returns the task "even if processing is still in progress… the caller's responsibility to poll". `GetTask` takes `historyLength` ("the maximum number of most recent messages"; `0` = none). `ListTasks` is cursor-paged (`pageToken`/`nextPageToken`, `""` on the last page, filters `contextId`/`status`). `SubscribeToTask`'s first event is the current Task, "preventing a potential loss of information between a call to GetTask and calling SubscribeToTask".

## 5. Tool design guidance

**Anthropic, "Writing effective tools for agents"** (`anthropic.com/engineering/writing-tools-for-agents`, read today) **[V]**:

- _Count and consolidation_: "More tools don't always lead to better outcomes"; avoid thin wrappers of endpoints; build a few tools for high-impact workflows (`schedule_event` instead of `list_users`+`list_events`+`create_event`; `search_logs` instead of `read_logs`); "too many tools or overlapping tools can also distract agents". No numeric limit given.
- _Naming_: namespace by service and resource (`asana_search`, `asana_projects_search`); prefix vs suffix has "non-trivial effects" that vary by model, so test.
- _Returned context_: high-signal fields, natural-language names over UUIDs ("resolving arbitrary alphanumeric UUIDs to more semantically meaningful… significantly improves precision"); offer a **`response_format` enum (`concise` | `detailed`)**, the example shows 72 vs 206 tokens.
- _Size_: "some combination of pagination, range selection, filtering, and/or truncation with sensible default parameter values"; Claude Code caps responses at 25,000 tokens; when truncating, steer the agent ("make many small and targeted searches") and write errors as "specific and actionable improvements, rather than opaque error codes or tracebacks".
- _Descriptions_: write them "like to a new hire", unambiguous parameter names (`user_id` not `user`), measure with evals; tool annotations "help disclose which tools require open-world access or make destructive changes".
- _Long-running or polling tools_: **not addressed**; no "wait up to N seconds" guidance exists in this article or in the MCP spec/docs I read. **[U]**

**MCP spec, tools (`2026-07-28/server/tools`)** **[V]**: names SHOULD be 1–128 chars from `A-Za-z0-9_-.`, case-sensitive, unique per server (AGENTS.md's snake_case fits); `title`, `description`, `inputSchema`, optional `outputSchema` (JSON Schema 2020-12 default), `annotations`; "clients MUST consider tool annotations to be untrusted unless they come from trusted servers"; `structuredContent` any JSON value; errors are two kinds: **protocol errors** (unknown tool, malformed request, server errors) as JSON-RPC errors such as `-32602`, and **tool execution errors** (API failures, input validation such as a bad date, business-logic errors) as a result with `isError: true` and "actionable feedback that language models can use to self-correct". "Clients **MAY** provide protocol errors to language models, though these are less likely to result in successful recovery. Clients **SHOULD** provide tool execution errors to language models." Security: servers MUST validate input, access-control, **rate limit tool invocations**, sanitize output; clients SHOULD confirm sensitive operations, show inputs, implement timeouts. pi follows this (an `isError` result is shown as an error for direct calls and resolved inside scripts, `docs/mcp.md`).

**Client-side tool-count mechanics**: pi defaults MCP tools to `codemode` exposure (not declared to the model) and `deferred` via `tool_search`; Claude Code defers MCP tools behind tool search, only names and server instructions load upfront, "no fixed per-server tool cap; the practical limit is your context window budget", `auto` mode defers once definitions exceed 10% of the context. So a larger, well-named tool set costs little in either client, but **server instructions and the first 4,096 chars of each description are what the model searches on**. **[V]**

## 6. Pagination, cancellation and limits in the spec

- **Pagination**: opaque cursors on `tools/list`, `resources/list`, `resources/templates/list`, `prompts/list` only; the server fixes page size, clients MUST NOT assume one; `nextCursor` absent = end; invalid cursors SHOULD be `-32602`; "clients MUST treat cursors as opaque… don't persist cursors across sessions" (`2025-11-25/server/utilities/pagination`; the `2026-07-28` page has the same model). **[V]** There is **no spec cursor for a tool result**: transcript/event paging has to be tool arguments (`cursor`/`limit`) and a `nextCursor` field in the result, as in §4. Cursor lifetime is therefore cloudpid's to define; a transcript cursor that survives across calls is not covered by the "don't persist" rule, which is about list cursors. **[I]**
- **Rate limits**: only "servers MUST rate limit tool invocations" (tools, Security Considerations) and "SHOULD implement rate limiting" for progress and log messages; no numbers, no `Retry-After`/`429` convention in these pages. **[V]**
- **Result size**: the spec sets none; limits are client-side (§3). The SDK bounds the **request** body (`maxRequestBodySize`, 4 MiB, `413`). **[V]**
- **Cancellation**:
  - Modern: closing the SSE response stream is the cancel signal; "the server MUST treat a client disconnect as cancellation… SHOULD stop work as soon as practical and MUST NOT send any further messages"; `notifications/cancelled` is stdio-only and a server MUST NOT send it except for `subscriptions/listen`; timeouts SHOULD close the stream; progress MAY reset a timeout but a maximum SHOULD always apply. — `2026-07-28/basic/patterns/cancellation`, `…/transports/streamable-http`. **[V]**
  - Legacy `2025-11-25`: disconnection "SHOULD NOT be interpreted as the client cancelling its request; to cancel, the client SHOULD explicitly send `CancelledNotification`" (§Streamable HTTP). **[V]**
  - SDK 2.4.0 (`createMcpHandler`): **Modern** `PerRequestHTTPServerTransport` listens to `request.signal` (and to the SSE stream's `cancel`), calls `close()`, and the server's close chain runs `controller.abort(SdkError ConnectionClosed)` on every in-flight handler, i.e. `ctx.mcpReq.signal` (documented in `BaseContext`: "an abort signal used to communicate if the request was cancelled from the sender's side") fires. **Legacy fallback**: `request.signal.addEventListener('abort', teardown)` closes transport and server the same way. A `notifications/cancelled` POST on the stateless legacy lane is answered `202` by a fresh instance that has no such request; it cannot cancel anything. **[V]** for the source; the last sentence is **[I]** from the per-request design.
  - pi sends both: it aborts the fetch (closing the stream, which is what works) and POSTs `notifications/cancelled`. Claude Code: closes/aborts on user stop or timeout (details [U]).
  - **Workers**: `Request.signal` fires on client cancel only "when you use the `enable_request_signal` compatibility flag" (compat-flags page; no default date listed) **[V]**. Whether the signal survives the `McpWorker.serve(request, api)` RPC hop from the main Worker is **[U]** and must be tested.
  - **Design consequence [I]**: treat the abort as "stop waiting", never "stop the Run". A Run outlives the call by design; only an explicit stop tool should stop it.

## 7. Implications for cloudpid's `/mcp` (suggestions, not decisions)

1. **Shape**: durable handles + short calls, as Cursor/Jules/Factory/A2A: `start` returns `{session_id, run_id, status}` immediately; `send_input` returns a `{run_id, delivery: started|queued|steered}`-style acknowledgement (Cursor's `409`/`steer` and Factory's `recipientDroidStatus` show the cases to distinguish); `get_run`/`wait_run` return status + `next_cursor`; transcript/event paging by cursor with `limit` and a `concise|detailed` `response_format`.
2. **Wait tool**: a "wait up to N seconds" call is the only in-protocol push substitute; cap `N` at roughly 20–30 s (below pi's 60 s default, the SDK's 60 s default and Claude Code's 60 s first-byte floor; Claude Code backgrounds after 2 min anyway), return early on a Run state change or new events, always return the cursor to resume from, and emit one progress notification at start so the stream has bytes. Make it idempotent and read-only (`readOnlyHint: true`) so Claude Code can run it in parallel and retry it.
3. **Progress**: send `notifications/progress` from long handlers when a token is present (pi always sends one, so pi's TUI gets a live line and its timeout resets); do not depend on it for correctness (Claude Code's progress display is [U], `notifications/message` is only a log file in pi and deprecated on Modern).
4. **Modern lane**: `responseMode: 'sse'` if any handler can run longer than a few seconds without a notification; otherwise `auto` is fine for instant calls.
5. **`content` must carry the answer**: pi's model sees `content` (not `structuredContent` unless `content` is empty); put a compact text/JSON rendering in `content` and the typed object in `structuredContent` with `outputSchema` (pi scripts and Modern clients get typing from it); keep text under ~20 KB for pi and well under 25k tokens for Claude Code, paginate beyond it. Resource links are shown by pi as text pointers and read through `read_mcp_resource`; they only help if the server also serves `resources/read`, and Claude Code's handling is [U], so don't make the transcript depend on them.
6. **No prompts/completions**: pi ignores them; Claude Code would turn prompts into slash commands, optional. **`instructions`**: first line is what pi puts in the system prompt; Claude Code keeps 4,096 chars; put the one-sentence purpose first and the Run/poll protocol after.
7. **Annotations**: set them honestly (`readOnlyHint` on list/get/wait/read tools, `destructiveHint: true` on stop/delete/hand-off, `idempotentHint` where true); pi forwards them to permission extensions, Claude Code uses `readOnlyHint`/`idempotentHint` for parallelism/retry. Treat them as hints (the spec calls them untrusted).
8. **Confirmation without elicitation**: follow the prior art, i.e. split dangerous actions into a separate named tool or a `confirm`-style second step the owner performs in cloudpid's UI (Jules `approvePlan`, GitHub `is_suggestion`), and/or set `_meta["anthropic/requiresUserInteraction"]: true` on the tools that must always prompt in Claude Code. pi has no equivalent: its gates are extension `tool_call` handlers.
9. **Errors**: unknown tool, bad envelope → JSON-RPC (SDK does this); unknown/foreign `session_id`, busy Run, invalid cursor, validation → `isError: true` with an actionable sentence naming the next tool to call (spec §Error Handling; Anthropic article).
10. **Cancellation**: do not tie a Run to `ctx.mcpReq.signal`; test `enable_request_signal` and the RPC hop; accept that Legacy `notifications/cancelled` is a no-op and offer an explicit stop tool.

Tags as above. Primary sources for Cloudflare, SDK and pi; for Claude Code behaviour that its docs do not state, the only evidence is **user-reported measurements in `anthropics/claude-code` issues** (tagged **[R]**, reported, not vendor-documented).

### F1. What the Worker sees behind Access (managed OAuth and service tokens)

- **Managed OAuth is invisible to the origin.** Access issues opaque tokens (`oauth:…`); "Cloudflare resolves the token into the user's identity on the backend and forwards a signed assertion to your origin. From your origin's perspective, the request looks the same as a browser-authenticated request." The MCP server "must validate the Access JWT sent in the `Cf-Access-Jwt-Assertion` header." — Cloudflare One docs, _Managed OAuth_ §Token format. **[V]** So a managed-OAuth bearer request has the same claims as a browser request: `aud` (AUD tag), `email` (verified by the IdP), `exp`, `iat`, `nbf`, `iss` (`https://<team>.cloudflareaccess.com`), `type: "app"`, `identity_nonce`, `sub` (user id, unique per email per account), `country`, plus custom IdP claims. — _Application token_ page, §Identity-based authentication. **[V]** The `email` is therefore present for an owner request (it is the identity-based case); the docs have no separate OAuth shape.
- **The OAuth client (DCR `client_id`, `client_name`) is not documented as visible to the origin anywhere**: not in the claims table, not in a header, not in the managed-OAuth page ("the OAuth flow gives clients the ability to make requests on a user's behalf without exposing identity information to the client" describes only the reverse direction). **[U]** To confirm, log all headers and the decoded JWT from a real pi/Claude Code request; until then, do not design anything that needs to tell pi from Claude Code at the Worker by token. (Client identity from `clientInfo`/`User-Agent` below is self-declared and untrusted.)
- **`ctx.access`**: "when Cloudflare Access authenticates a request that directly invokes your Worker", `ctx.access` has `aud` and `getIdentity()` ("email, groups, device posture, and more identity fields"); it is `undefined` if Access did not authenticate the request. — Workers docs, _Cloudflare Access_ §Read authenticated user identity with `ctx.access`; changelog 2026-08-14. **[V]** `getIdentity()` fields in alchemy's typing: `email?`, `name?`, `user_uuid?`, `account_id?`, `iat`, `ip`, `amr`, `idp`, `geo`, `groups`, `devicePosture`, `is_warp`, `is_gateway`, `service_token_id?`, `service_token_status?` (all optional; "resolves `undefined` when Access has no identity for the request (e.g. some service-token flows)") — `@alchemy.run/cloudflare@2.0.0-beta.84` `src/Workers/WorkerAccess.ts`. That typing is alchemy's, not workerd's; the wire fields are **[U]** beyond `email`/`groups`/device posture named in the Cloudflare docs. Effect accessor: `yield* Cloudflare.Access.Context` then `access.getIdentity()` (`src/Access/Context.ts`).
- **Not propagated across Service Bindings or RPC**: "Cloudflare Access does not propagate `ctx.access` through Service Binding HTTP requests or remote procedure call (RPC) invocations. The downstream Worker does not receive the caller's Access context." Workers with Static Assets run behind an internal router Worker that does not pass `ctx.access` to the user Worker. — same page, §`ctx.access` limitations. **[V]** Consequence for ADR-0038's `MCP_SERVER.serve(request, api)`: `McpWorker` will see `ctx.access === undefined`; the main Worker must read the identity (and AUD) and put it into the `api` `RpcTarget` or into the forwarded request. A forwarded `Request` that still carries `Cf-Access-Jwt-Assertion` would let `McpWorker` verify the JWT itself (JWKS from the team domain), but the docs do not say whether Access strips or re-injects that header across a service binding. **[U]**
- **Service token** (Client ID + Secret in `CF-Access-Client-Id`/`CF-Access-Client-Secret`, needs a _Service Auth_ policy): the JWT payload is `{ type: "app", aud: [...], exp, iss, common_name: "<Client ID>.access", iat, sub: "" }` — i.e. **`common_name` = the service token's Client ID, no `email`, empty `sub`**. — _Application token_ §Service token authentication (JWT example and field table: "common_name: The Client ID of the service token (`CF-Access-Client-Id`)"). **[V]** (The same table also lists `common_name` as the mTLS client-certificate common name for certificate auth.) A third-party validator reports "Service-token requests include `common_name` and usually have no `email`" (cloudflare-experiments.com, not authoritative). Through `ctx.access.getIdentity()`, alchemy types `service_token_id` (client id) and `service_token_status: true`, with the identity possibly `undefined`; what workerd returns for a service token is **[U]**. Distinguish owner vs token in the Worker with `email` present vs `common_name` present in the verified JWT, or `service_token_id` from `getIdentity()` if it resolves.
- Token lifetime context (Access settings): access-token lifetime default 15 min with a longer grant session; policies are re-evaluated at each refresh. — _Managed OAuth_ §OAuth settings. **[V]** Dynamic client registration is limited by `oauth_configuration.dynamic_client_registration` (`allow_any_on_localhost`, `allow_any_on_loopback`, `allowed_uris`). **[V]**

### F2. Long-lived responses on Workers behind Access

- **Workers**: "Incoming HTTP request: wall time **Unlimited** — no hard limit while the client remains connected… A Worker that is still streaming a response body remains active"; subject to the runtime-update grace period; `waitUntil()` extends 30 s after the response or disconnect. — Durable Objects _Limits_ §Wall time limits by invocation type; Workers _Limits_ §Duration. **[V]** So a 300 s SSE response with 10–15 s keepalives is permitted by the documented platform limits; **I found no documented Workers idle-stream timeout** and no figure for Access. **[U]** for an empirical run; the earlier note of an ≈ 5-minute idle watchdog is from the Agents docs (`research-mcp-server-behind-access.md`), not a Cloudflare limit page.
- **524 does not apply to a Worker as such**: Error 524 is "Cloudflare successfully connected to the origin web server, but the origin did not provide an HTTP response before the default **125 seconds** Proxy Read Timeout" (not 100 s; 100 s was the older figure). _Connection limits_ lists Proxy Read Timeout 125 s (configurable on Enterprise zones), Proxy Write Timeout 30 s, Proxy Idle Timeout 900 s (520), HTTP/2 connection idle 900 s, in the context of origin connections. — _Error 524_, _Connection limits_. **[V]** The pages do not say whether a Worker-generated response is exempt; the Worker is the thing that answers, there is no origin hop, so the origin timers should not apply **[I]**, but a Worker that `fetch()`es an external origin is subject to them for that subrequest. Regardless, keepalive bytes every 10–15 s sit far below 125 s, so the question only matters for a silent response (Modern `auto` mode with no progress; §2.2).
- **Access**: no Access page I read documents a limit on response duration. Session management pages describe application-token lifetime ("the window in which a user can initiate a new connection or refresh an existing one"); an in-flight stream is not stated to be cut at token expiry, except for infrastructure (SSH) apps ("when the session duration elapses, any active SSH connections… are closed"). — _Session management_. **[U]** for HTTP apps; test with a bearer token near expiry.
- **Durable Object RPC pending ~300 s**: "Durable Objects (RPC / HTTP): **Unlimited** — no hard limit while the caller stays connected to the Durable Object. Durable Objects remain active while a request, RPC call, response stream, WebSocket, or pending I/O is in flight." CPU is the separate limit (30 s default per invocation, active CPU only; waiting does not count; up to 5 min configurable). — DO _Limits_. **[V]** A pending RPC from a Worker therefore has no wall-clock cap while the caller is connected. Two caveats: "Crashes, resource pressure, and shutdowns can interrupt work earlier" and deploys drain old isolates after a grace period (Workers _Limits_ §Runtime updates); and RPC stubs/targets are disposed when the originating event ends (client disconnect ends the execution context early: _RPC lifecycle_ §Automatic disposal), so an `api` `RpcTarget` passed to `McpWorker` must be `dup()`ed (as ADR-0038 already says) and is lost if the main Worker's request ends. **[V]**

### F3. Workers Rate Limiting binding and alchemy

- **GA**: "Rate Limiting in Workers is now GA. The `ratelimit` binding is now stable and recommended for all production workloads. Existing deployments using the `unsafe` binding will continue to function." — Cloudflare changelog 2025-09-19. **[V]**
- **Config**: `ratelimits: [{ name, namespace_id (integer, unique per account), simple: { limit, period } }]`, **`period` must be 10 or 60 seconds**; call `await env.X.limit({ key })` → `{ success }`. Limits are **per Cloudflare location, approximate and eventually consistent** ("requests can exceed the configured threshold"; a strict global limit needs a Durable Object); bindings that share a `namespace_id` share counters within a location, including across Workers; do not key on IP/region; needs Wrangler ≥ 4.36.0. — Workers docs _Rate Limiting_ (updated 2026-10-21). **[V]**
- **alchemy 2.0.0-beta.84 exposes it**: `@alchemy.run/cloudflare` `src/Workers/RateLimit.ts` + `RateLimitBinding.ts`, exported from `Workers/index.ts`, added to `WorkerBinding`, `InferEnv` (maps to native `cf.RateLimit`) and `RuntimeBindings` (has a `RateLimit.local` implementation for `alchemy dev`). It lowers to `{ type: "ratelimit", name, namespaceId, simple }`. **[V]** API (from the file's own JSDoc):

  ```ts
  // async Worker: declare on env
  export const Worker = Cloudflare.Worker("Worker", {
    main: "./src/worker.ts",
    env: {
      THROTTLE: Cloudflare.RateLimit("THROTTLE", {
        namespaceId: 1001,
        simple: { limit: 10, period: 60 },
      }),
    },
  });
  type WorkerEnv = Cloudflare.InferEnv<typeof Worker>; // { THROTTLE: RateLimit }
  const { success } = await env.THROTTLE.limit({ key: "owner" });

  // Effect-native Worker: yield* attaches the binding and returns an Effect client
  const throttle =
    yield *
    Cloudflare.RateLimit("THROTTLE", { namespaceId: 1001, simple: { limit: 10, period: 60 } });
  const { success } = yield * throttle.limit({ key: "owner" }); // RateLimitError on failure
  // provide: Effect.provide(Cloudflare.Workers.RateLimitBinding)
  ```

  `RateLimitProps = { namespaceId: number | string; simple: { limit: number; period: 10 | 60 } }`; the client exposes `raw` (the native binding) and `limit(options)`. The binding has no backing cloud resource. Names above are quoted from the beta.84 sources; the exact top-level re-export path (`Cloudflare.RateLimit`) follows the JSDoc and was not type-checked here. **[I]** for that path.

### F4. Client identification on the wire

- **pi**: `initialize.clientInfo = { name: "pi", version: <pi VERSION> }` (no `title`; `runtime.ts` passes only `name`/`version`; `client.ts` builds `clientInfo`), `capabilities = { roots: {} }`, `protocolVersion` = pi's latest Legacy (`2025-11-25`). **[V]** The MCP transport sets only `accept: application/json, text/event-stream`, `content-type`, `Authorization: Bearer`, `Mcp-Session-Id` (if any), `MCP-Protocol-Version`, plus user-configured `headers`; **no `User-Agent`** is set in `packages/mcp` or the MCP extension (the `getPiUserAgent` helper is used only for the catalog and interactive-mode requests), so the request carries the runtime's default `fetch` UA (Node/undici: `node`; Bun: `Bun/<version>`). **[V]** for the absence in source; the exact default string is **[I]** (not observed). OAuth DCR `client_name` defaults to `pi` (`docs/mcp.md`: "Pi registers as `pi`"; configurable via `oauth.clientName`).
- **Claude Code**: **[R]** HTTP transport `User-Agent: claude-code/<version> (cli)` (issues #34982, #47390 report `claude-code/2.1.76 (cli)`), and `claude-code/2.1.128 (claude-desktop, agent-sdk/0.2.128)` under the desktop/SDK host (issue #41836); the **OAuth discovery/DCR requests had an empty `User-Agent`** (issue #47390, closed not planned, 2026-04), which WAF rules in front of Access/Cloudflare may block, so do not add a UA-required bot rule on `/.well-known/*` and the OAuth endpoints. `clientInfo.name`: the same issue reports `{"name":"claude-ai","version":"0.1.0"}` for the claude.ai connector; for Claude Code CLI **[U]** (not shown in any source read; do not key on it). Other measured facts (issue #41836, Claude Code 2.1.280, both eras): `tools/call` carries `_meta: { "claudecode/toolUseId": "…", "progressToken": N }`, and on `2026-07-28` every request carries `io.modelcontextprotocol/{protocolVersion,clientInfo,clientCapabilities}` in `_meta`; no session id appears anywhere on the wire. **[R]** This answers the §2.3 `[U]`: **Claude Code does send a `progressToken` on `tools/call`.** All of these are self-declared client values and must not be used for authorization.

### F5. Claude Code: `content` vs `structuredContent` (reverses a §7 suggestion)

- Claude Code's docs do not say, but multiple independent reports show it **forwards `structuredContent` to the model, serialized as JSON, and drops all-text `content` when both are present**, with or without an `outputSchema`; structured-only results work; non-text blocks in `content` are kept and the structured JSON is appended. **[R]** — `anthropics/claude-code` #79944 (open, label `area:mcp`, 2026-07; reproduced on 2.1.222 and 2.1.280 incl. an extraction of the converter order: "if structuredContent exists, serialize it; if content contains non-text blocks, preserve only those and append serialized metadata; otherwise return serialized metadata; map the complete content array only when structuredContent is absent"), #59480, #45575, #55677, #54450, #15412; and a Cursor-forum probe of Claude Code 2.1.220, the Claude desktop app and the ChatGPT/Codex desktop app: "All three forward `structuredContent` to the model, preferring it over `content` when both are present" (while Cursor sends only `content`). No vendor statement that this is intended or will change.
- **pi is the opposite**: the model sees `content`, and `structuredContent` only if `content` is empty (§3). **[V]** (source)
- **Design rule [I]**: the two channels must carry the **same payload**: `structuredContent` the full typed result (not a metadata wrapper), `content` a text rendering of that same result (for pi, Cursor and older clients). Never put the answer in only one of them and metadata in the other. In the SDK the handler may return both; with an `outputSchema` the SDK validates `structuredContent` against it (§F6). Size-wise, the Claude Code token cap applies to whichever form it forwards, so paginate the structured payload itself.

### F6. SDK 2.4.0 server behaviours

- **Invalid tool arguments are an `isError` result, not `-32602`.** In `McpServer`'s `tools/call` handler, `validateToolInput` (which throws `ProtocolError(InvalidParams, "Input validation error: Invalid arguments for tool X: …")`), the handler call and `validateToolOutput` all sit inside one `try`; the `catch` returns `createToolError(message)` = `{ content: [{type:'text', text}], isError: true }` for every error **except** `UrlElicitationRequired`, which is rethrown. Only an **unknown tool** (`Tool X not found`) or a **disabled tool** (`Tool X disabled`) is a JSON-RPC `-32602`, because that check runs before the `try`. A handler `throw` also becomes `isError: true`. Output-schema mismatch (`structuredContent` not matching `outputSchema`) is likewise an `isError` result. — `packages/server/src/server/mcp.ts` ≈ l.296–345. **[V]** (Matches the spec's advice that validation errors be tool execution errors; to return a custom JSON-RPC error for a handler problem you must use the low-level `Server`.) The optional `maxToolInputElements` (unset by default = no limit) also reports as `Invalid arguments…` in the same way.
- **Default `maxRequestBodySize` = 4,194,304 bytes (4 MiB)** (`createMcpHandler` option; a larger POST gets `413` before parsing and before any instance is built; not applied when you pass `parsedBody`). **[V]** (`createMcpHandler.ts`, JSDoc `@default 4194304`.)
- **Per-request tool lists work, and the factory may be async.** `McpServerFactory = (ctx: McpRequestContext) => McpServer | Server | Promise<McpServer | Server>`; `createMcpHandler` awaits it once per HTTP request (both eras; plus one probe instance for `server/discover` and one for `subscriptions/listen`, discarded). `ctx` carries `era`, `authInfo?` and `requestInfo` (the `Request`). `tools/list` is computed from the tools registered on that instance (`registerTool`; `tool.disable()`/`enabled` filters; `enabled=false` tools are omitted from the list and answer `-32602 … disabled` on call). So a tool can be hidden by not registering it, or disabling it, based on an awaited RPC answer inside the factory. **[V]** Costs/caveats: **every** request (each `tools/call`, `tools/list`, `server/discover`) pays the factory, so keep the RPC in the factory cheap or cache it per isolate; list and call can disagree if the RPC answer changes between them (a hidden tool simply answers "not found" at call time, which is acceptable); no `listChanged` is useful on a stateless server, and **`McpServer` advertises `tools: { listChanged: true }` by default** when tools are registered (`registerCapabilities({ tools: { listChanged: getCapabilities().tools?.listChanged ?? true } })`), so construct it with `capabilities: { tools: { listChanged: false } }` to match "no listChanged". **[V]**
- `tools/list` in `McpServer` returns **all enabled tools in one response, with no cursor**; there is no `nextCursor` handling in `mcp.ts`. Fine for tens of tools. **[V]**
