# How does a hosted harness sign in to OAuth MCP servers? (ticket #377)

Research date: 2026-10-29. Question: how can cloudpid (Workers and Durable Objects, web UI behind Cloudflare Access) act as an MCP OAuth client? Which parts of pi-mcp's `oauth` module run outside Node, what redirect URI does a hosted client use and may it sit behind Access, Dynamic Client Registration (DCR) vs Client ID Metadata Documents (CIMD) for a hosted client, token refresh and step-up, and what do Sentry, GitHub, Linear and Figma accept?

Labels: **[V]** verified against a primary source (cited), **[E]** verified by an experiment I ran (see [Experiments](#experiments)), **[I]** inference, **[?]** unknown.

## Answer in brief

1. **pi-mcp's `./oauth` module runs in workerd unchanged, except that `OAuthCallbackServer` (`callback.ts`, `node:http`) is useless there.** [E] Every other file is `fetch`/WebCrypto/`Buffer` only. The whole flow (discovery → CIMD client id → authorization URL → code exchange → refresh) ran in workerd (`nodejs_compat`, compat date 2026-08-31, the repo's test setting) against the live servers' real metadata.
2. **A hosted client's redirect URI is an `https` route of the main Worker** (e.g. `https://pi.ianpascoe.dev/oauth/mcp/callback`), registered with the authorization server (AS). Loopback is neither needed nor sensible. The spec requires redirect URIs to be `localhost` or HTTPS ([2025-11-25 §Communication Security](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)).
3. **The callback route may stay behind Access** [V+I]: the owner's browser makes a top-level GET navigation and carries its `CF_Authorization` cookie (SameSite defaults to None; Strict breaks it). **The CIMD document may not**: the AS (not the owner's browser) fetches it, so it needs an Access Bypass policy on exactly that path. Sentry fetches it at authorize, code exchange and refresh.
4. **Both Sentry and Linear accept either way, and both accept an `https` redirect on cloudpid's domain with DCR** [E]. GitHub supports neither (pre-registered GitHub App/OAuth App with a client secret). Figma only serves catalog clients (DCR returned 403 to an unknown client).
5. **CIMD is the spec's preferred, non-deprecated path** (DCR is "deprecated" in 2026-07-28), is stateless for the client, and suits a single hosted origin well. Keep DCR as the fallback, pre-registration as the third path.
6. **Refresh and step-up are in pi-mcp's `authorizeMcp`/`adaptOAuthProvider`; proactive refresh before expiry, locking and "who stores what" are not** (they live in `coding-agent`, Node-only). A DO must supply: durable `McpOAuthStateStore`, an in-flight refresh guard (a DO's input gate opens on `fetch`), a pending-sign-in record that maps the callback's `state` to the right owner, and a way to surface the authorization URL to the owner.

Note `provider.state()` returns the existing `oauthState` if one is stored, so a hosted "start sign-in" must clear it first as coding-agent does (`oauth.ts:503`).

## 2. Redirect URI for a hosted client, and Access

**Requirements** [V]:

- MCP 2025-11-25: "All redirect URIs MUST be either `localhost` or use HTTPS"; clients MUST have redirect URIs registered; the AS validates them by exact match; clients SHOULD use and verify `state` ([§Communication Security, §Open Redirection](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)). Same text in 2026-07-28.
- MCP 2026-07-28 / SEP-837: DCR clients must send `application_type`; "served from a non-local host" clients SHOULD use `web` ([client-registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)). pi-mcp already derives it: `web` for non-loopback `https` URIs (`flow.ts:114-120`).
- MCP 2026-07-28 / SEP-2468 (RFC 9207): the client records the AS issuer before redirecting and, on the response, compares a present `iss` to it before redeeming the code ([2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog), [authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). pi-mcp implements it: `authorizeMcp({ authorizationCode, iss })` throws `OAuthIssuerMismatchError` (`flow.ts:388-392`). **The hosted callback route must read `iss` from the query and pass it through.**

**Choice** [I]: one fixed route on the main Worker, e.g. `https://<stage host>/oauth/mcp/callback`; all four live AS's advertise `authorization_response_iss_parameter_supported: true` [E], so pi's fallback of a per-server redirect path for servers without `iss` (`oauth.ts:262-270`) is not needed for them (keep it as an option for servers that do not).

Cloudflare's own hosted client is a precedent: the Agents SDK builds `https://{host}/{agentsPrefix}/{agent-name}/{instance-name}/callback`, with an optional `callbackPath` so the callback does not expose the instance name ([Agents `McpClient` docs](https://developers.cloudflare.com/agents/api-reference/mcp-client-api/)). The route resolves the state to its object; for cloudpid the `state` value (or a Registry lookup of it) can do that. [I]

**Behind Access?**

- Access guards _inbound_ requests only; the Worker's outbound `fetch` to AS endpoints is unaffected. [I: standard Access semantics; docs describe Access checking "every HTTP request bound for that site" for a `CF_Authorization` cookie ([authorization cookie](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/))].
- **Callback route behind Access works for the owner's browser** [V+I]: the AS redirects the browser (top-level GET, `response_mode=query`; Sentry/Linear advertise `response_modes_supported: ["query"]` [E]). The application `CF_Authorization` cookie's SameSite is "Admin choice (Default: None)" and Lax is also fine, because Lax cookies are sent with top-level navigations; **Strict "can result in too many redirects"** ([cookie settings](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/)). Whether cloudpid's Access app sets SameSite is not in the repo (grep of `infra/`, `apps/server/src/worker.ts` found no setting; alchemy's `access` prop defaults not checked). [?]
- If the Access session expired while the owner was on the AS's consent page, Access sends them through login first. Cloudflare's changelog confirms Access redirects "users back to an application after login" and preserves the URL ([2026-07-01 entry](https://developers.cloudflare.com/changelog/post/2026-07-01-spa-redirect-fragment-fix)); that the **query string** (`code`, `state`, `iss`) survives that round trip is not stated anywhere I found. [?] Worst case the owner signs in again; the code is single-use anyway.
- The Access bypass the owner may want is only for the **CIMD document path** (next section), not for the callback. A bypass is path-scoped through an Access application on `host/path` with a Bypass/Everyone policy; more specific paths take precedence ([Bypass](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/), [app paths](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/app-paths/)). Bypass requests are not logged. cloudpid's ADR-0025 already anticipates a bypass for a webhook path, but nothing exists yet.
- Which stage: `prod` is `pi.ianpascoe.dev`; other stages are on `workers.dev` hosts (docs/architecture/operations.md). Redirect URIs and the CIMD URL are per stage host. DCR and CIMD cope with that by construction (each stage registers/identifies itself); pre-registered clients (GitHub) list callback URLs explicitly (a GitHub App takes up to 10, exact match unless wildcard is enabled: [callback URL docs](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/about-the-user-authorization-callback-url)), so practically `prod` only.

**No pasted-URL fallback needed**: pi's `promptForRedirectUrl` exists because a browser on another machine cannot reach the loopback callback (`oauth.ts:376-441`). A hosted callback is reachable from any device that has the Access cookie, and the pending sign-in lives in DO storage, not in the browser that started it. [I]

## 3. DCR vs Client ID Metadata Documents for a hosted client

Spec priority (2025-11-25 and 2026-07-28 agree): pre-registered → CIMD if the AS advertises `client_id_metadata_document_supported` → DCR if `registration_endpoint` → ask the user. In **2026-07-28 DCR carries a deprecation warning** ("New implementations should use Client ID Metadata Documents instead") [V: [2026-07-28 client-registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration), [authorization §Client registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)].

CIMD ([draft-ietf-oauth-client-id-metadata-document-00](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-00); the IETF datatracker lists -01 and -02 as newer, not read):

- `client_id` is an `https` URL with a path; the document must contain `client_id` (string-equal to the URL), `client_name`, `redirect_uris`; MCP says "MUST include at least `client_id`, `client_name`, `redirect_uris`" and requires `https` + path ([MCP client registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)).
- No shared-secret auth (`client_secret_*` forbidden); `private_key_jwt` via `jwks_uri` allowed (CIMD §4.1, §6.2). So a CIMD client is public (`token_endpoint_auth_method: none`) unless it publishes a key.
- The AS fetches the document, SHOULD cache per HTTP headers, SHOULD cap size (5 KB) and avoid private addresses (§4.4, §6.5, §6.6); redirect URIs must exactly match the document (§4.5); an AS MAY require redirect URIs to be same-origin with the `client_id` (§6.1).

**Why CIMD fits a hosted single-owner client** [I]:

- Redirect and `client_id` share an origin, which is the shape an AS's same-origin policy accepts, and `https` redirect URIs avoid MCP's "localhost impersonation" warning for CIMD ([security](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)). A hosted client is the case CIMD was designed for ("no prior relationship").
- No client state to persist or lose: pi-mcp does not store the CIMD identity (`flow.ts:358-360`, the document is "not stored"), whereas DCR output (`client_id`, secret) must survive in the DO, or the client re-registers and leaves an orphan client at the AS each time. pi-mcp discards stored client information on `invalid_client` and re-runs (`flow.ts:437-440`).
- Cost: an always-reachable, public route `GET /oauth/client.json` (Access bypass; must not be blocked by a WAF/bot rule). Sentry's own docs warn that its provider "fetches and validates the document during authorization, code exchange, and refresh. A failed fetch can block these operations", and pins one client's metadata server-side so that "an upstream `403` cannot block this client's OAuth flow" ([sentry-mcp oauth-architecture](https://raw.githubusercontent.com/getsentry/sentry-mcp/main/docs/cloudflare/oauth-architecture.md)). So a bypassed document path is a hard availability dependency of refresh as well as sign-in at CIMD-only servers.

**DCR remains necessary as a fallback** for AS's that support DCR but not CIMD, and pi-mcp implements it (`registerClient`, `flow.ts:249`; it sends `application_type`, `grant_types`, `response_types`, `token_endpoint_auth_method: none` by default: `provider.ts` constructor). Hosted specifics [V+I]: SEP-2352 (2026-07-28) says persisted client credentials are bound to the issuer that issued them and must be re-registered when the AS changes; pi-mcp keys state by server URL only (`provider.ts:165`) and caches discovery, so cloudpid's store should key by server name + URL (the map's decision) and drop `clientInformation` when the discovered issuer changes. I did not find pi-mcp handling `client_secret_expires_at` (parsed, never used) [?].

pi-mcp already supports both in one provider: `clientMetadataDocument(metadata)` returns `{url, redirectUrl}` or `undefined` to fall back to DCR (`flow.ts:50-57,358-374`); `clientId`/`clientSecret` options pre-register (`provider.ts:77-80`). pi's `clientMetadataDocument()` in coding-agent additionally _throws_ unless the AS advertises CIMD and `none` auth (`oauth.ts:251-263`); a hosted client would instead choose per AS: pre-registered → CIMD (flag true and `none` supported) → DCR.

## 4. Token refresh and step-up in a hosted client

What pi-mcp does (verified in `flow.ts`):

- **Refresh**: `runFlow` tries `refreshAuthorization` when a refresh token exists and `skipRefresh` is not set; a refresh response without `scope` keeps the old scope (`withScope`, `flow.ts:404-413`), and the old `refresh_token` is kept if the response has none (`flow.ts:296-306`). OAuth errors other than `server_error` abort the refresh (no silent fallback to a new authorization) except that `invalid_client`/`unauthorized_client` drops all credentials and `invalid_grant` drops tokens, then reruns (`flow.ts:433-448`), which yields a `REDIRECT` (sign-in needed).
- **401 handling**: `adaptOAuthProvider` shares one in-flight refresh among concurrent 401s and retries requests whose token was already replaced, because "with rotating refresh tokens, a second refresh with the old refresh token would fail and discard the new grant" (`flow.ts:455-483`). `REDIRECT` becomes `McpOAuthAuthorizationRequiredError` (user interaction needed).
- **Step-up**: a 403 with `error="insufficient_scope"` → `authorizeMcp` with `skipRefresh: true` and scope = granted ∪ challenged (`stepUpScope`, `flow.ts:317-322`; MCP 2025-11-25 §Scope Challenge Handling says the client SHOULD attempt step-up and retry "no more than a few times"). It needs the browser again.
- **Resource indicator**: `resource` (from PRM, validated against the server URL by `selectResource`, `discovery.ts:202-215`) is on authorize and token requests, as MCP requires ([2025-11-25 §Resource Parameter](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)).
- **`offline_access`**: MCP 2026-07-28 lets a client add it only if the AS lists it in `scopes_supported`, and tells servers not to put it in challenges; pi-mcp adds `prompt=consent` when the scope list contains it (`flow.ts` `startAuthorization`).

What a Durable Object changes [I unless cited]:

- **Serialisation**: a DO is single-threaded, but `await fetch()` opens the input gate so other requests interleave ([Rules of Durable Objects](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects)). Rotating refresh tokens therefore need an explicit in-flight promise (as pi's `refreshing`) in the one object that owns that server's tokens, and refresh must be reachable only through it. If more than one object could refresh the same server (e.g. an Environment's MCP object and a Global one), serialise through a single owner (the map's note: credentials are kept per server name and URL at Global).
- **Proactive refresh**: needed because `adaptOAuthProvider.token()` never refreshes (`flow.ts:458`); copy coding-agent's skew logic using `tokensExpireAt` (already saved by `McpOAuthProvider.saveTokens`, `provider.ts:104-111`). Refresh runs lazily on use in a `fetch` context; a DO needs no timer, matching ADR-0025's "nothing runs on a timer" token pattern.
- **Refresh outcomes the model/owner must see**: `McpOAuthAuthorizationRequiredError` means a human is needed. A turn that calls an `mcp__*` tool mid-run is durable (pi-durable); the sign-in becomes a durable request to the owner, like `secret_ask`/elicitation in the map's notes. `redirectToAuthorization(url)` (`flow.ts:62,429`) is the seam that hands the URL to that request.
- **Pending sign-in record**: `codeVerifier` and `oauthState` are saved by pi-mcp's provider; the hosted route needs, in addition, a way from `state` to the owning store and a TTL (GitHub codes live 10 minutes: [authorizing OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)).
- **Secrets at rest**: tokens are credentials; the repo already seals Environment Secrets with a master key in the Workspace DO (`SECRETS_ENCRYPTION_KEY` in `apps/server/vitest.config.ts`); whether MCP tokens get the same sealing is a design choice, not a research fact. MCP 2025-11-25 requires secure token storage ("MUST implement secure token storage").
- **SSRF**: PRM and AS URLs come from the remote server. pi-mcp takes an injectable `fetch` (`OAuthFlowOptions.fetch`, `UnauthorizedContext.fetch`), and rejects non-http(s) URLs in parsed metadata (`types.ts` `safeUrl`) and non-HTTPS token endpoints except loopback (`flow.ts:123-127`), so cloudpid can route OAuth traffic through its `guardedFetch` (agent-capabilities.md "SSRF guard").

Notes per server:

- **Sentry**: DCR and CIMD both on; "All connections use OAuth" ([Sentry MCP docs](https://docs.sentry.io/ai/mcp/)). Its MCP tokens are its own (an MCP access token minted over a stored Sentry token; the upstream refresh token is held server-side; MCP access tokens last up to 1 hour in the reference implementation) [sentry-mcp oauth-architecture]. Fetches the CIMD document at authorize, token exchange and refresh (see §3). Scope-challenge behaviour not tested [?].
- **GitHub**: "Dynamic Client Registration is NOT supported by Remote GitHub MCP Server at this time"; hosts must use a registered **GitHub App or OAuth App** and pass a client secret; GitHub recommends a dedicated app per client and says to honour `WWW-Authenticate` rather than hard-code endpoints ([github-mcp-server `docs/host-integration.md`](https://raw.githubusercontent.com/github/github-mcp-server/main/docs/host-integration.md)). A GitHub App user token expires after 8 h with a single-use rotating refresh token valid 6 months ([refreshing user access tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens)); OAuth App tokens do not expire unless expiry is enabled ([authorizing OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)); both support PKCE S256 and require the `redirect_uri` to match a registered callback. Organizations may block unapproved apps (same host-integration doc). pi-mcp covers this with `clientId`/`clientSecret` on `McpOAuthProvider` (`provider.ts:77-80`); the secret must be kept server-side (a confidential client is natural for a hosted Worker). The existing cloudpid GitHub App (ADR-0025) is a separate matter: that ADR chose installation tokens and listed user-to-server tokens as a rejected option; the MCP sign-in would be another OAuth client (a second app, or the same app with user authorization enabled and callback URLs added). Not decided here.
- **Linear**: "OAuth 2.1 with dynamic client registration"; direct `Authorization: Bearer` with an OAuth token or API key also works ([Linear MCP docs](https://linear.app/docs/mcp)). `read` scope gives read-only; Linear's OAuth app docs say access tokens last 24 h and refresh tokens rotate, with a 30-minute replay grace period for a lost refresh response ([Linear OAuth 2.0](https://linear.app/developers/oauth-2-0-authentication); that page describes Linear's API OAuth, and I did not confirm the MCP AS behaves identically [I]). Each workspace needs its own sign-in (Linear MCP docs).
- **Figma**: "Only clients listed in the Figma MCP catalog … can connect"; others "join the waitlist" ([Figma remote server docs](https://developers.figma.com/docs/figma-mcp-server/remote-server-installation/)). My DCR probe, from an unknown client name, got a bare 403. pi's docs work around this with `oauth.clientName: "Claude Code"` (`packages/coding-agent/docs/mcp.md`), i.e. by presenting as an approved client; I did not test that and do not recommend relying on it. Figma's AS does not advertise `none` auth or CIMD, so even if registration worked the client would be confidential (secret issued at DCR).

I created two throwaway DCR clients (Sentry, Linear; name `cloudpid-research-probe`, redirect `https://pi.ianpascoe.dev/oauth/mcp/callback`, no tokens issued). Neither server's metadata advertises RFC 7592 deletion; they are inert.

## 6. Implications and options for cloudpid (not a design)

- **Reuse**: import `@earendil-works/pi-mcp/oauth` in the Worker/DO; do **not** use `OAuthCallbackServer`. Everything else runs [E]. Write: a DO-backed `McpOAuthStateStore`, the pre-expiry refresh wrapper around `adaptOAuthProvider`/`authorizeMcp` (port of coding-agent's `createMcpAuthProvider` minus the file lock), the sign-in start/complete pair, the callback route and a CIMD document route.
- **Routes the main Worker needs**: `GET /oauth/mcp/callback` (behind Access; reads `code`, `state`, `iss`, `error`, `error_description`), and a public `GET /oauth/client.json` (Access bypass, `Content-Type: application/json`, tiny, cacheable) if CIMD is used.
- **Client identity order** (spec order, per AS metadata): configured `clientId` (GitHub, Figma-if-ever) → CIMD (Sentry, Linear) → DCR → fail with a message naming what the owner must register. All four tested servers are covered by this ladder except Figma (blocked by Figma's policy, not by the flow) and GitHub (needs a registered app).
- **Per-server config** in the `mcp_servers` shape mirrors pi's `oauth` block (`clientId`, `clientSecret` as `${SECRET}`, `scope`, `clientName`, `clientRegistration: "cimd"|"dcr"`, `authServerMetadataUrl`) so entries stay pi-compatible; `callbackPort`/`callbackUrl` are loopback-only and have no meaning here.
- **UI**: pi's `/mcp login` becomes "Sign in" in the MCP status UI (a not-yet-specified item on the map): the authorization URL goes to the owner's client as a link/new tab; completion arrives via the callback route, not via the page that opened the link.
- **Step-up** reuses the same sign-in with `stepUpScope`; the retry bound the spec suggests ("no more than a few times") has to be tracked by cloudpid (pi-mcp does not track attempts).
