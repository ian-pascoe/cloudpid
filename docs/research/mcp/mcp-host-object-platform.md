# MCP host object: what the Workers platform allows (RPC stubs, script cycles, lazy modules, eval, streaming)

Research for the per-Environment "MCP host object" design. Fetched 2026-10-31. Question: can a Durable Object that loads the MCP TypeScript SDK (~9–10 MiB cold heap) live in its own Worker script, called by Session DOs (in `Server`) and itself calling the Registry DO (`Server`) and the Workspace DO (`Workspaces`) without a deploy cycle; or how else to keep the library's heap out of Session isolates.

Conventions: **[V]** verified in a primary source (cited), **[I]** inference from cited sources, **UNCONFIRMED** = could not confirm from a primary source. Sources: `developers.cloudflare.com` pages (the `index.md` form, last-updated dates noted), `cloudflare/workerd` at commit [`dfded0e`][wd-tree] (2026-10-31), `alchemy-run/alchemy` at [`55e34d0`][al-tree] (HEAD, 2026-10-31) and the **installed** `@alchemy.run/cloudflare@2.0.0-beta.84` / `alchemy@2.0.0-beta.84` sources in `node_modules/.bun/` (cloudpid pins beta.84; alchemy HEAD is ahead of it even though its `package.json` also says beta.84, so each alchemy claim says which one it comes from). Reference-style links are listed at the end.

## 1. Answers

1. **Passing stubs over RPC.** **Yes** for all four: a DO stub and a service binding (both are `Fetcher`s, serialised as a channel token), an `RpcTarget`, and a plain function (becomes a callback stub) can be arguments of a DO RPC call, and callbacks work while the call is in flight. **[V]** Lifetime: an `RpcTarget`/function/`RpcStub` param is disposed **when the call returns** unless the callee `dup()`s it; a dup'd callback stays callable until disposed, until the caller's execution context ends, or (for a caller DO) until it is evicted/aborted, after which calls fail with `The execution context which hosts this callback is no longer running.` Whether a received `Fetcher`/DO stub may be stored past the call is **UNCONFIRMED** (code: it is an independent channel token with "limited lifetime but otherwise irrevocable", bound to the callee actor's one-per-actor `IoContext`). If the caller is reset mid-call the callee gets **no AbortSignal**: its JS keeps running (workerd cannot cancel it), its pending callbacks into the caller reject with the abort reason, and later ones fail as above; `AbortSignal`-over-RPC exists only behind the experimental flag `enable_abortsignal_rpc` (**UNCONFIRMED** for production). Size limit: **32 MiB** serialised per argument/result message; `ReadableStream` bytes are not counted.
2. **Cycles between scripts.** Cloudflare's docs say nothing about mutual bindings, but they are **not forbidden**: alchemy's live integration test deploys two Workers that bind each other and call each other **[V]**. Uploading a script whose service binding / DO binding targets a script or class that does not exist is **rejected** (error `10144 ServiceBindingNotFound`, `10061 DurableObjectClassNotFound`), not a warning and not a runtime failure **[V]**. alchemy beta.84 binds by literal `scriptName` (`Input<string>`), but a literal creates no dependency edge, so the target must already exist; it breaks A↔B cycles by **pre-creating a placeholder script** that exports the DO classes, then uploading the real scripts (installed beta.84 supports this for the Tag/`.make()` pattern; the fix for two plain async Workers whose `env` yield each other, #2672, is in alchemy HEAD and **not** in beta.84).
3. **Lazy modules & isolates.** A module reached only through `import()` is evaluated (and its module-level heap allocated) **only when imported** **[V]** (ES semantics; workerd's `dynamicImportModuleCallback`). Whether it is a separate upload module depends on the bundler: **wrangler/esbuild inlines it into the entry file** (no `splitting`; module still evaluates lazily, but its source is in the entry), unless `find_additional_modules` + `rules` is used; **alchemy's rolldown keeps dynamic imports as separate chunks and uploads every chunk**. All DO classes and the stateless handler of one script run in the **same compiled Worker, i.e. one isolate per Worker instance** in workerd **[V]**; Cloudflare's docs say an isolate "can host multiple Durable Objects" and the 128 MB is per isolate. Cross-class isolate co-location in production is **UNCONFIRMED** (closed-source edge), so a lazy `import()` inside `Server` does **not** guarantee the heap stays out of isolates that host Session DOs.
4. **`allow_eval_during_startup`** is **on by default for compatibility dates ≥ 2025-06-01**, so it is on at `2026-08-31` **[V]**. It lets `eval()`/`new Function(text)` (and WebAssembly compile, which is gated on the same switch) run **only during worker startup** (top-level module evaluation); at request time they still throw. Consequence: a library that compiles code from strings lazily at first use (e.g. Ajv) fails; a module first reached through a request-time `import()` is evaluated **outside** the startup window, so top-level `eval` there fails too. **[V]** (workerd `io/worker.c++:2401-2407`).
5. **Outbound streaming fetch from a DO.** **Yes**: an open outbound `fetch()`/connection is pending I/O that keeps the DO in memory (no eviction, no hibernation) for **up to 15 minutes per operation**, and the DO "continues to incur duration charges" meanwhile **[V]**. The limit is "up to six connections simultaneously **waiting for response headers**" per invocation; once headers arrive a connection stops counting, so open SSE bodies do **not** count against it **[V]** (wording in §6). Whether DO RPC calls count toward the six is **UNCONFIRMED**.

## 2. Passing stubs, functions and `RpcTarget`s over Workers RPC

### 2.1 What can be sent

- Docs: RPC "allows … public methods on Durable Objects that can be called by other workers on the same Cloudflare account that declare a binding to it"; supported non-structured-clone types are "Functions, which are replaced by stubs that call back to the sender", `RpcTarget` subclasses, `ReadableStream`/`WritableStream`, `Request`/`Response`, and "RPC stubs themselves, even if the stub was received from a third Worker". **[V]** [rpc docs][doc-rpc] (updated 2026-10-12).
- "You can also send a function in the parameters of an RPC. This enables the 'server' to call back to the 'client' … The 'server' is a Durable Object or WorkerEntrypoint" **[V]** [rpc docs › Send functions as parameters][doc-rpc].
- A DO stub is a `Fetcher` subclass: `class DurableObject final: public Fetcher` ([actor.h:87][wd-actor-h87]). `Fetcher` is `JSG_SERIALIZABLE(rpc::SerializationTag::SERVICE_STUB)` ([http.h:542][wd-http-h542]) and `Fetcher::serialize` writes the subrequest channel's **token** (`getTokenMaybeSync(ChannelTokenUsage::RPC)`), after `requireAllowsTransfer()` ([http.c++:2525-2565][wd-http-cc2525]); `deserialize` rebuilds a `Fetcher` from the token in the receiving isolate ([http.c++:2597-2648][wd-http-cc2597]). So a service binding or DO stub passed as an argument is **not proxied through the caller**; the callee gets its own channel to the target. **[V]** `requireAllowsTransfer` only refuses channels that cannot be reconstructed from a token, "in particular, dynamically-loaded workers" ([io-channels.h:268-282][wd-iochan]).
- workerd's own test sends a DO stub as an argument of an entrypoint RPC and has the callee call it: `env.MyService.incrementCounter(actor, 5)` ([js-rpc-test.js:1128-1133][wd-jsrpc-test1128]); and returns one: `getMyActor` ([js-rpc-test.js:1151-1155][wd-jsrpc-test1151]). That test runs in one workerd config; a stub to a DO in a _different_ script takes the same token path, but no cross-**script** DO→DO test was found. **[I]**
- Forwarding: "A stub received over RPC from one Worker can be forwarded over RPC to another Worker … this proxying only lasts until the end of the Workers' execution contexts. A proxy connection cannot be persisted for later use." **[V]** [rpc docs › Forwarding RPC stubs][doc-rpc]. This is the `RpcStub` (function/`RpcTarget`) case, which _is_ proxied through the introducer ([worker-rpc.c++:1760-1830][wd-rpc-cc1760]), unlike `Fetcher`.

**Design consequence [I]:** rather than rely on a received stub outliving the call, the callee can use its own bindings: a host DO in its own script that has its own cross-script DO bindings to Registry (`Server`) and Workspace (`Workspaces`) needs no stub passing (but see §3 for the cycle this creates).

### 2.3 Callbacks during a long call

Yes. A function passed as an argument can be called by the callee while the call is in flight; workerd tests it, including from inside a DO's `blockConcurrencyWhile()` ("Check that we can receive RPC callbacks during blockConcurrencyWhile(), if they are from an RPC running inside the block", [js-rpc-test.js:636-646][wd-jsrpc-test636]). Docs: stubs passed in params remain until the call returns, and "RPCs can flow both ways between the two" ([rpc docs][doc-rpc]). **[V]**

### 2.4 Caller DO evicted or reset mid-call

- **Idle eviction cannot be the trigger while the call is open.** "Pending I/O and open outbound connections prevent a Durable Object from being evicted. Examples include service binding requests, Durable Object remote procedure call (RPC) calls, outbound `fetch()` requests …"; "Each operation prevents eviction until it completes or for up to 15 minutes from when it starts" ([DO lifecycle][doc-do-lifecycle], updated 2026-10-30). **[V]** After 15 minutes, or on a code update / runtime update / crash, the caller can go away mid-call. "When the Worker runtime system is being updated, in-flight requests have up to 30 seconds to complete"; "HTTP & RPC requests: In-flight requests are allowed to finish if they do not access a Durable Object's storage. If a request attempts to access a Durable Object's storage, it will be stopped immediately" ([DO lifecycle › Shutdown behavior][doc-do-lifecycle]). **[V]**
- **What the callee sees.** When the caller's RPC session is dropped, "the `customEvent()` promise is canceled, thus canceling the session" ([worker-rpc.c++:3592-3598][wd-rpc-cc3592]); in-flight capability calls fail (`DISCONNECTED`, "JS-RPC session canceled", [worker-rpc.c++:3511-3524][wd-rpc-cc3514]). The lifecycle doc's rule "if the client disconnects, the server's execution context is canceled immediately" applies ([lifecycle][doc-lifecycle]). But **callee JS is not interrupted**: "we have no ability to actually cancel execution if a cancellation arrives over RPC" ([worker-rpc.c++:2185-2190][wd-rpc-cc2185]); JS promises "are not RAII-cancelable" ([worker-rpc.c++:2263-2266][wd-rpc-cc2185]). `waitUntil()` "should allow extending execution on the server side even when the client disconnects" ([worker-rpc.c++:3451-3452][wd-rpc-cc3440]). **[V]**
- **Callee calling into a reset caller.** If the caller DO aborts, calls queued or hung through its callback stubs reject with the abort reason and later calls fail with `The execution context which hosts this callback is no longer running.` (a test comment: "TODO(bug): This should propagate the abort reason") ([js-rpc-test.js:2253-2320][wd-jsrpc-test2253]). **[V]** So the callee's way to notice the caller died is a failing callback, not a signal.
- **AbortSignal.** `AbortSignal` is serialisable over RPC in the source (`JSG_SERIALIZABLE(rpc::SerializationTag::ABORT_SIGNAL)`, [basics.h:807][wd-basics-h807]), but `serialize` throws `"AbortSignal serialization is not enabled."` unless `abortSignalRpc` is on ([basics.c++:1171-1173][wd-basics-cc1171]), and that flag (`enable_abortsignal_rpc`) is `$experimental` ([compatibility-date.capnp:783-786][wd-compat783]) and absent from the [public flag list][doc-compat]. **UNCONFIRMED** for production; do not design on it. The related `enable_request_signal` flag only concerns `Request.signal` for incoming `fetch` ([flags page][doc-compat]).

### 2.5 Size limits

"The maximum serialized RPC limit is 32 MiB. Consider using `ReadableStream` when returning more data" ([rpc docs › Limitations][doc-rpc]) **[V]**. In code `MAX_JS_RPC_MESSAGE_SIZE = 1u << 25` ([worker-rpc.h:38][wd-rpc-h38]) and the error is "Serialized RPC arguments or return values are limited to 32MiB" ([worker-rpc.c++:246-248][wd-rpc-cc246]). Byte-oriented `ReadableStream`/`WritableStream`/`Request`/`Response` bodies "are automatically streamed with appropriate flow control" and exceed 32 MiB ([rpc docs][doc-rpc]) **[V]**. Also relevant: each RPC arg/return object gets a disposer, so store results in `using` ([lifecycle][doc-lifecycle]).

## 3. Mutual bindings and cycles between Worker scripts

### 3.1 Is a cycle allowed?

- Cloudflare's docs describe only one-way bindings and a deploy order ("the target Worker … must be deployed first, before Worker A. Otherwise, when you attempt to deploy Worker A, deployment will fail, because Worker A declares a binding to Worker B, which does not yet exist.") ([service bindings › Deployment][doc-sb], updated per page; `index.md` fetched 2026-10-31). **[V]** Nothing there forbids or describes a cycle. A cycle is impossible by upload order alone, because each script must exist before another can bind it.
- alchemy handles it by **creating a placeholder script first**. In installed beta.84 `precreate` uploads a stub whose only content is the DO classes the Worker hosts (`makePlaceholderScript`, a `fetch` returning 503 plus `export class X extends AlchemyPlaceholderDurableObject {}`), so the namespaces and classes exist; real uploads then run later in the same deploy ([WorkerProvider.ts:4670-4860][al-wp-precreate], [WorkerProvider.ts:5725-5775][al-wp-placeholder]; comment at [:705-710][al-wp-705]: "a pre-created stub (which exports the Durable Object classes) for circular Worker↔Worker references"). **[V]**
- It is exercised live: `async circular bindings` — "Two plain async Workers that bind each other … A binds B's default entrypoint, and B binds A's named `Callbacks` entrypoint" — deploys and the test calls A → B.start → A's Callbacks.done, "both edges of the cycle" ([alchemy integration test][al-it-cycle], fixture [`stack.ts`][al-fx-cycle]; HEAD only). There is also a `circular-bindings` fixture with a Durable Object (`Counter`) and Workers A/B ([fixtures/circular-bindings][al-fx-do]). **[V]** I found no test of a _DO-binding_ cycle specifically (only service-binding entrypoint cycles in the async fixture, DO class in the Effect fixture). **[I]** the DO case works the same way, since the stub exports the classes.
- Documented Effect-Worker pattern (what `Server` is): import only the Tag across the cycle, attach each runtime with `.make()`, and alchemy plans "precreate → create with deferred Outputs → update to wire bindings" ([Circular Bindings docs][al-doc-circ]). **[V]**
- **beta.84 vs HEAD:** HEAD's `Platform.ts` guards `onCreate` so "two Workers whose `env` entries yield each other recurse forever (#2672)" ([HEAD Platform.ts:394-405][al-platform]); the installed beta.84 `Platform.ts` has no such guard (`diff` against HEAD shows it was added later). So for two **async** Workers (the shape of `Workspaces`/`Browsers`) with `env` entries that `yield*` each other, beta.84 may overflow while declaring the stack; the Tag/`.make()` pattern or an `Effect.suspend` deferred reference (as in the HEAD fixture) is the documented route. **UNCONFIRMED** that beta.84 actually overflows (inferred from the missing guard).

### 3.2 Binding to a script or class that doesn't exist

- API behaviour: the script upload (`PUT .../workers/scripts/{name}`) **fails** with a typed validation error; it does not warn and does not defer to runtime. Error codes in the Cloudflare API SDK that alchemy uses (`@distilled.cloud/cloudflare@1.0.0-rc.17`, generated from Cloudflare's API): `DurableObjectClassNotFound` = code **10061**, `ServiceBindingNotFound` = code **10144**, both members of `PutScriptError` ([workers.ts:187-193][dc-do], [workers.ts:474-481][dc-sb], [workers.ts:17035-17071][dc-err]). **[V]** (code mapping; Cloudflare's published upload-error table lists a generic `10056` "Binding not found" and `10021` validation errors but not 10061/10144, see [errors docs][doc-errors]: the specific codes are **UNCONFIRMED** on Cloudflare's own docs, **[V]** on the SDK and the live test).
- alchemy's live test: "Deploy-time binding validation rejects a script upload whose bindings reference a resource that doesn't exist. The Durable Object cross-script binding is the one deterministic engine-level trigger: `scriptName` is a plain string, so a stack can name a script that was never deployed." The deploy "must fail with the resource-specific typed error after the bounded retry exhausts — not … a success"; the test asserts `_tag == "DurableObjectClassNotFound"` ([BindingTargetNotFound.test.ts][al-it-nf]). **[V]** (HEAD).
- alchemy retries these as propagation lag: `Schedule.max([fixed("2 seconds"), recurs(10)])` over `ServiceBindingNotFound`, `DurableObjectClassNotFound`, and other not-found tags ([WorkerProvider.ts:714-735][al-wp-714], installed beta.84). **[V]** A DO binding to an existing script that does **not export** the class fails the same way; alchemy's own doc: "Deploy the host first so Cloudflare can verify that the target script exports the requested class" ([DurableObject.ts:1080-1090][al-do-1085], beta.84). **[V]**

### 3.3 alchemy: literal script name?

- `Cloudflare.DurableObject("Name", { scriptName })` takes `scriptName?: Input<string>`, i.e. a literal string **or** a Worker's `workerName` Output ([DurableObject.ts:61, 224, 1358][al-do-61], beta.84). Cross-script async bindings "are references only: the consumer uploads the binding metadata, but Alchemy does not drive class migrations for the foreign class" ([DurableObject.ts:1080-1090][al-do-1085]). cloudpid currently passes Outputs (`workspaces.workerName`, `sandboxes.workerName`, `browsers.workerName`, `apps/server/src/worker.ts:93,110,129`), which gives alchemy the ordering edge.
- A **literal** name gives no graph edge, so alchemy will not order the deploys: the host script must already exist (and export the class) at upload time, or the upload fails after the ~20 s retry. A literal name therefore breaks the first deploy of a fresh stage (bootstrapping) unless the target has been created earlier. **[I]** (from the retry code plus the test above).
- Practical options for the host object, given the above **[I]**: (a) host in its own script, bound from `Server` and binding `Server` back, via the Tag/`.make()` cycle pattern with the precreate stub; (b) host in its own script with a **one-way** edge only (`Server` → host) and let the host reach Registry and Workspace through callbacks/stubs passed by the caller (§2), which needs no cycle but needs stub lifetime to be solved (§2.2, **UNCONFIRMED** for `Fetcher`); (c) keep it in `Server` behind a lazy `import()`, with the isolate caveats in §4.3.

## 4. Lazy module evaluation and isolate sharing

### 4.1 Is a dynamically imported module evaluated only when imported?

- ES semantics: a static `import` graph is instantiated and evaluated before the entry; an `import()` expression loads and evaluates its target when executed. workerd implements `import()` through `HostImportModuleDynamicallyCallback`: the new-registry path "resolves dynamic imports synchronously within the V8 callback … the new registry's lazy compilation model means dynamic imports do not trigger eager compilation of all transitive dependencies" ([modules-new.c++:1443-1452][wd-mod-new1443]); the original registry pops out of the `IoContext` to compile/evaluate on demand (`configureDynamicImports`, [io/worker.c++:965-1025][wd-worker965]). **[V]** (the "only evaluated when imported" statement itself is language semantics, not stated in a workerd/Cloudflare page; **[I]** from the callbacks above.) `new_module_registry` has no default-on date in this workerd commit ([compatibility-date.capnp:514-516][wd-compat514]), so the legacy registry is the default unless the flag is set. **[V]**
- The memory that matters is **evaluated** module state (top-level allocations, class/closure creation, schema compilation). A module that is only bundled but never imported is, at most, source text that V8 must parse (see 4.2). It is not evaluated.

### 4.2 Do bundlers keep dynamic imports separate?

| Bundler                | Result                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Source  |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- |
| **wrangler (esbuild)** | **Inlined.** Wrangler calls `esbuild` with `bundle`, `format: "esm"`, a single `entryPoints`, and no `splitting` option ([bundle.ts:379-420][wr-bundle]); esbuild: "Without code splitting enabled, an `import()` expression becomes `Promise.resolve().then(() => require())` … the imported code is included in the same bundle instead of being split off into a separate file" ([esbuild API › splitting][esb]). Wrangler docs: "Normally, a large lazy-imported file (for example, `await import("./large-dep.mjs")`) would be bundled directly into your entrypoint, reducing the effectiveness of the lazy loading", with `find_additional_modules` + a matching `rules` entry as the opt-out ([bundling docs][doc-bundling]). The wrapped module still _evaluates_ lazily, but its source is parsed with the entry.                                                                                                                                                                                                                   | **[V]** |
| **alchemy (rolldown)** | **Separate chunks, all uploaded.** Alchemy's Worker bundle options are `format: "esm"`, `minify`, `strictExecutionOrder: true` and no `codeSplitting`/`inlineDynamicImports` override ([Rolldown.ts:207-222][al-rd], beta.84); rolldown's default is `codeSplitting: true` ("automatic code splitting"; `false` = "Inline all dynamic imports into a single bundle") ([rolldown docs][rd-cs]). Every output chunk is uploaded (`files: bundle.files` at [WorkerProvider.ts:2736, 3120][al-wp-files]; `bundleOutputFromRolldownOutputBundle` keeps `Object.values(bundle)`, [Bundle.ts:537-548][al-bundle]); an alchemy plugin drops chunks "no entry reaches" so unreachable dynamic chunks are not uploaded ([UnreachableChunksPlugin.ts][al-unreach], installed `alchemy@2.0.0-beta.84`). Users can set `build.output.codeSplitting` to change it ([Rolldown.ts:24-37][al-rd-opts]). The nested `?worker` (dynamic-worker) builds do the opposite and inline everything (`inlineDynamicImports: true`, [WorkerModulePlugin.ts:49][al-wmp]). | **[V]** |

Not verified: that `@alchemy.run/cloudflare`'s uploaded chunk modules are in fact loaded lazily by workerd (they are separate `EsModule` parts of the upload, so by the workerd semantics in 4.1 they are not evaluated until imported) **[I]**; and `strictExecutionOrder: true` ("wraps modules so their bodies run in source order, at a bundle-size cost", [rolldown docs][rd-seo]) wraps cross-chunk modules; it does not change _when_ a dynamically imported chunk evaluates **[I]**.

### 4.3 Do DOs of one script share isolates with each other and with the stateless handler?

- **In workerd, yes: one compiled Worker (one isolate) serves every entrypoint and every DO class of a script.** `ActorClassImpl { worker: Rc<WorkerService>, class_name, … }` builds actors with `ffi::worker_new_actor(&self.worker.worker, &self.class_name, …)` and starts requests with `self.worker.start_request(Some(&self.class_name), None, Some(actor), …)` ([server/worker.rs:885-917][wd-worker-rs885]); stateless entrypoints use the same `self.worker.start_request(self.entrypoint…)` ([worker.rs:831-841][wd-worker-rs885]); `worker_new_actor(const CompiledWorker& worker, …)` ([worker-factory-actor.c++:629][wd-wfa629]). "A worker service owns one namespace per class its config gives storage to" ([server/actor.rs:1-5][wd-actor-rs]). So module-level state (the evaluated MCP SDK, the module registry) is **one copy per isolate**, shared by every DO instance and class that runs in that isolate. **[V]** for workerd; **[I]** for production, whose edge runtime is closed-source.
- Cloudflare's docs: "Durable Objects may run in the same isolate on the same physical machine and share the 128 MB of memory" (stated for "many instances of a single Durable Object class") ([DO pricing footnote 5][doc-do-pricing], same text in [Workers pricing][doc-w-pricing]); "Memory is measured per isolate (which can host multiple Durable Objects), not per object" ([in-memory state][doc-inmem]). **[V]** Neither page says whether _different classes_ of one script share an isolate. **UNCONFIRMED** in production (the workerd evidence above says they do).
- **Memory limit:** "Memory per isolate | 128 MB … including the JavaScript heap and WebAssembly allocations. This limit is per-isolate, not per-invocation. A single isolate can handle many concurrent requests"; on exceeding it "the Workers runtime lets in-flight requests complete and creates a new isolate for subsequent requests" ([Workers limits › Memory][doc-limits], updated 2026). **[V]** Billing charges "for the 128 MB of memory your Durable Object is allocated, regardless of actual usage" ([DO pricing][doc-do-pricing]).
- **So:** a lazy `import()` of the MCP SDK from a class that lives in `Server` would pay the heap only in isolates that actually run the host DO, but nothing documented prevents the host DO and Session DOs from sharing one isolate, in which case the ~10 MiB sits next to Session heaps. Placing the host in a **separate script** is the only configuration the docs support for separate isolates (different script = different Worker = different isolate in workerd, [worker.rs:885][wd-worker-rs885]). **[I]**
- Also noted in workerd: "multiple Workers share an isolate (same script, different zones)" ([io/worker.c++:2411-2418][wd-worker2406]), i.e. one isolate may host several instances of the same script.

## 5. `allow_eval_during_startup`

- **Default:** "Default as of 2025-06-01 | Flag to enable `allow_eval_during_startup` | Flag to disable `disallow_eval_during_startup`" ([compat flags page][doc-compat], updated 2026) and `$compatEnableDate("2025-06-01")` ([compatibility-date.capnp:788-792][wd-compat788]). So at `2026-08-31` it is on by default. **[V]**
- **What it allows:** "Workers can use `eval()` and `new Function(text)` during the startup phase of a Worker script"; with `disallow_eval_during_startup` they throw ([compat flags page][doc-compat]). Everywhere else the base rule holds: "For security reasons, the following are not allowed: `eval()`, `new Function`, `WebAssembly.compile` …" ([web standards][doc-ws], updated 2026-04-23). **[V]**
- **How it works in workerd:** `js.setAllowEval(FeatureFlags::get(js).getAllowEvalDuringStartup())` immediately before top-level execution, reset by `KJ_DEFER(js.setAllowEval(false))` ([io/worker.c++:2401-2407][wd-worker2406]); rationale in the source: "We allow eval and new Function() during startup, because startup time is entirely deterministic, so we can easily reproduce the input to eval() by just running the worker again. We do not allow eval() at runtime because we need to have a record of all code that executes in production". V8's code-generation callback returns `codegen_allowed = base.evalAllowed` ([jsg/setup.c++:741-756][wd-setup741]); `WebAssembly` compilation is gated on the same switch (`allowWasmCallback`, [setup.c++:752-756][wd-setup741]); a no-argument `new Function()` is always allowed ([setup.c++:~735-740][wd-setup741]). **[V]**
- **Consequence for lazy loading [I]:** startup = the worker's top-level module evaluation (including `await import()` at top level, which runs inside it). A module first imported from a request handler runs **outside** that window (the legacy dynamic-import path runs the handler under a separate lock/`enterDynamicImportJs` with no `setAllowEval`, [io/worker.c++:965-1015][wd-worker965]), so top-level `eval`/`new Function` in it throws. **UNCONFIRMED** by an executed test; derived from the single `setAllowEval(true)` site.
- **Relevance to the MCP SDK [I]:** the SDK has two JSON-Schema validators, an Ajv one and a `@cfworker/json-schema` one, and its docs say the default is chosen per runtime ("AJV on Node.js, CfWorker on edge runtimes") ([`fromJsonSchema.ts:12-16`][sdk-fjs], [`cfWorkerProvider.ts:1-8`][sdk-cfw], `modelcontextprotocol/typescript-sdk@39ae8e6`). Ajv compiles validators with `new Function`, which only works at startup. Which provider is picked on workerd was not verified: **UNCONFIRMED**.

## 6. Outbound streaming `fetch` from a DO

- **Stays in memory / blocks eviction:** "Pending I/O and open outbound connections prevent a Durable Object from being evicted. Examples include service binding requests, Durable Object remote procedure call (RPC) calls, outbound `fetch()` requests, … promises passed to `this.ctx.waitUntil()` … TCP sockets and outbound WebSockets also prevent eviction. Each operation prevents eviction until it completes or for up to 15 minutes from when it starts, whichever comes first. Operations started together do not combine their windows. Starting another operation later can extend the Durable Object's time in memory." Hibernation additionally requires "No I/O operation or promise passed to `this.ctx.waitUntil()` remains unfinished, and no outbound connection remains open" ([DO lifecycle][doc-do-lifecycle]). **[V]** Whether an _open response body being read_ after headers counts as the `fetch()` operation (rather than only the pre-header phase) is not spelled out; "open outbound connections" is the closest wording. **[I]** it counts.
- **Billing:** "While an operation prevents eviction, the Durable Object continues to incur duration charges" ([DO lifecycle][doc-do-lifecycle]); "A Durable Object incurs duration charges when it is actively executing JavaScript … or when it is idle but does not meet the conditions for hibernation" and "Pending I/O operations keep an object in memory for up to 15 minutes each. The object incurs duration charges during that time" ([DO pricing][doc-do-pricing]); duration is "billed in wall-clock time as long as the Object is active and not eligible for hibernation, but is shared across all requests active on an Object at once", at the full 128 MB regardless of use ([pricing footnotes 4–5][doc-do-pricing]). **[V]**
- **No hard duration cap while connected:** "Durable Objects (RPC / HTTP) | Unlimited | No hard limit while the caller stays connected to the Durable Object. Durable Objects remain active while a request, RPC call, response stream, WebSocket, or pending I/O is in flight." ([DO limits][doc-do-limits], line 182). **[V]**
- **Simultaneous connections, exact wording:** "Each Worker invocation can have up to six connections simultaneously waiting for response headers. The following API calls count toward this limit while the initial connection is being established and the server has not yet responded: `fetch()` …, Workers KV …, Cache …, R2 …, Queues `send()`/`sendBatch()`, `connect()` TCP sockets. Outbound WebSocket connections also count toward this limit. **Once response headers arrive for a connection, it no longer counts toward the six-connection limit.** This means a Worker can have many connections open simultaneously, as long as no more than six are in the initial 'waiting for headers' phase at the same time. If a seventh connection is attempted while six are already waiting for headers, it is queued until one of the existing connections receives its response headers." and "The runtime measures simultaneous open connections from the top-level request. Workers triggered via Service bindings share the same connection limit." ([Workers limits › Simultaneous open connections][doc-limits]). **[V]** The DO limits table repeats it: "Simultaneous outgoing connections/request | 6 (same as Workers)" ([DO limits][doc-do-limits]). **[V]**
- **Do open streams count?** By that wording, **no**: an SSE response whose headers have arrived is not "waiting for response headers". **[I]** (the page says so for `fetch()`); outbound **WebSocket** connections are listed as counting but it is not stated whether that is pre- or post-upgrade. DO RPC calls and DO `fetch()` are not in the listed APIs, so whether a pending DO RPC counts is **UNCONFIRMED**. The per-top-level-request scoping means a DO held open by many long-lived SSE streams (one per MCP server) is limited only by the pre-header phase, not by stream count [I]. The limit is not implemented in the open-source workerd tree (grep for "simultaneous"/"waiting for headers" finds nothing relevant), so there is no source to confirm the exact semantics. **UNCONFIRMED** beyond the docs.
- Subrequest _count_ also applies: "10,000 (up to 10M)" per invocation on paid, "There is no set time limit on individual subrequests" ([Workers limits › Subrequests][doc-limits]).
