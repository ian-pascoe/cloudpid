# What does a local pi Session hold, and how could pi-durable take it in?

Research ticket [#379](https://github.com/ian-pascoe/cloudpid/issues/379) of the MCP map ([#373](https://github.com/ian-pascoe/cloudpid/issues/373)).

**Question.** For handing a local Session off to cloudpid: what a local pi Session file holds (the JSONL entry types), how it maps onto pi-durable's conversation storage, whether pi-durable can import or seed a conversation's history, and what of a local Session has no cloudpid counterpart.

**Terminology.** The ticket says "hand off". In cloudpid's GLOSSARY a **Handoff** is the agent-written note that starts a new Context Window, and pi-durable also has a `handoff` tool control that writes a `pi.reset` entry. This note calls the thing under study a **Session import** to avoid the clash.

**Sources.** `.repos/pi` at `f09d01b` (`packages/coding-agent` and `packages/durable`, both 1.4.0, the version cloudpid pins in `apps/server/package.json`), the pi docs `packages/coding-agent/docs/session-format.md`, and cloudpid's own `apps/server/src/session/`. "Observed" figures come from the author's own `~/.pi/agent/sessions` (1,778 files, all `version: 3`), as illustration only; they are not a spec.

## Short answer

- A local Session is one JSONL file: a header line, then a **tree** of entries linked by `id`/`parentId`. The "current branch" is not stored; it is the path ending at the **last line of the file**.
- The message payloads are **the same pi-ai `Message` types** pi-durable stores (`UserMessage`, `AssistantMessage`, `ToolResultMessage`, `SystemMessage`). So the conversation content maps almost one-to-one, with no content translation.
- pi-durable has **no importer for pi session files** and no pi-coding-agent dependency. It does have the primitives an importer needs, and cloudpid already runs one for Fork/Clone: it appends entries to a new Session's root conversation in paged commits, renumbering the IDs.
- What does not map one-to-one: the entry tree (durable has linear conversations plus `fork(at)`), model/thinking changes (a rewindable document, not entries), compaction (a `head` marker), context edits, per-entry timestamps, labels, and every extension's custom entry.
- Real hazards are size (the 8 MiB SQLite row cap fails the whole Session), system messages (must not be imported as they are), and context size on the first request.

## 1. What a local Session file holds

### 1.1 Location and file

- Path: `~/.pi/agent/sessions/--<cwd with separators and ":" replaced by "-">--/<ISO timestamp with : and . → ->_<session id>.jsonl`. Override: `--session-dir`, `PI_CODING_AGENT_SESSION_DIR`, or the `sessionDir` setting. Sources: `packages/coding-agent/docs/session-format.md` (File Location); `docs/sessions.md:50`; `src/core/session-manager.ts:589-594` (directory name), `:1079-1080` (file name), `src/config.ts:649`.
- The directory name is lossy (`/` and `-` collapse). The header's `cwd` is the authoritative working directory.
- Loading: JSON per line, malformed lines skipped; the first parsed line must be `type: "session"` with a string `id`, otherwise the file is "not a pi session" (`session-manager.ts:627-675`, `:695-710`).
- A file is only created once the session holds a user or assistant message (`session-manager.ts:1166-1180`).
- Versions: v1 (linear), v2 (`id`/`parentId` tree), v3 (`hookMessage` role → `custom`); the manager migrates in place on load (`:337-352`, migrations at `:289-335`). Current is `CURRENT_SESSION_VERSION = 3` (`:41`). An importer must accept v1/v2 or require the local side to migrate first (opening with `SessionManager` does).

### 1.2 Header (line 1, not part of the tree)

`{type:"session", version?, id, timestamp, cwd, parentSession?}` (`session-manager.ts:43-50`). `id` is a UUIDv7 unless the caller chose one; `parentSession` is the file path of the source session of a `/fork` or `/clone`.

### 1.3 Entries (every later line)

All extend `{type, id, parentId: string|null, timestamp: ISO string}` (`session-manager.ts:57-62`). IDs are 8 hex characters (full UUID on collision) (`:279-286`). Types (`:64-197`, documented in `session-format.md` "Entry Types"):

| `type`                  | Fields beyond the base                                                                                                              | In the model's context?                                                                                    |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `message`               | `message: AgentMessage`: roles `user`, `assistant`, `toolResult`, `system`, plus `bashExecution` and `custom` (`messages.ts:21-62`) | yes, as stored (`bashExecution` and `custom` are converted to user text, `messages.ts:82-100`, `:148-190`) |
| `thinking_level_change` | `thinkingLevel`                                                                                                                     | no (state)                                                                                                 |
| `model_change`          | `provider`, `modelId`                                                                                                               | no (state)                                                                                                 |
| `usage`                 | `kind`, `provider`, `model`, `usage`, `note?` (e.g. cache warming)                                                                  | no                                                                                                         |
| `compaction`            | `summary`, `firstKeptEntryId`, `tokensBefore`, `details?`, `usage?`, `fromHook?`, `systemMessage?`                                  | yes: summary (+ `systemMessage` checkpoint) then the kept range                                            |
| `branch_summary`        | `fromId`, `summary`, `details?`, `usage?`, `fromHook?`                                                                              | yes, as a `branchSummary` user message                                                                     |
| `custom`                | `customType`, `data?` (extension state)                                                                                             | **no**                                                                                                     |
| `custom_message`        | `customType`, `content` (string or text/image blocks), `details?`, `display`                                                        | **yes**, as a user message                                                                                 |
| `context_edit`          | `targetId`, `replacement: {content} \| null`                                                                                        | no itself; changes the target's contribution                                                               |
| `label`                 | `targetId`, `label`                                                                                                                 | no                                                                                                         |
| `session_info`          | `name?`                                                                                                                             | no                                                                                                         |

Message payloads (all pi-ai types, `packages/ai/src/types.ts`):

- `UserMessage` `{role, content: string | (Text|Image)[], timestamp}` (`:579-583`).
- `AssistantMessage` `{content: (text|thinking|toolCall)[], api, provider, model, responseId?, thinkingLevel?, usage, stopReason, errorMessage?, timestamp, durationMs?…}` (`:585-615`). Thinking blocks carry provider signatures; images are inline base64 (`:438-442`).
- `ToolResultMessage` `{toolCallId, toolName, content, details?, usage?, nestedCalls?, isError, timestamp, durationMs?}` (`:629-657`).
- `SystemMessage` `{content: "", sections?, toolsAdded?, toolsRemoved?, timestamp}` (`:561-577`). The session file stores the prompt and tool declarations as system messages in the path, the first request writing one with every section and tool and later changes as patches (`session-format.md`, SessionMessageEntry). In the observed data only 66 of the entries are system messages; older sessions have none.

Observed on the author's machine (112,285 lines): message roles `toolResult` and `assistant` dominate; `user` messages are rare by comparison (149 in the 60 most recent files); also seen `message:system`, `message:bashExecution` (15 across all files), `compaction` (all `fromHook: true`, with `systemMessage`), `context_edit` (all `replacement: null`), `session_info`, `usage`, and a large share of `custom` entries from extensions (`pi-git-checkpoints.*`, `minimal-subagents.*`, `pi-lsp-post-edit-diagnostics`, `pi-todo-state`, `pi-context-note`, `pi-context-handoff`, `plannotator`, …) and `custom_message`s (`minimal-subagents.result/message`, `pi-termctrl.exit`, `intercom_message`, `codex-native-compaction-display`, `pi-context-prepare`, …). No `label` or `branch_summary` entries exist in that corpus. 27 of 1,778 files branch (an entry with more than one child). 378 inline images. The largest file is 39.7 MB; the largest single line is 4.58 MB; 18 lines exceed 1.9 MB; none exceeds 8 MiB.

### 1.4 Tree, leaf and branches

- Entries form a tree through `parentId`. `branch(id)` only moves an in-memory `leafId`; the next append becomes a child of it (`session-manager.ts:1589-1596`). **The leaf is never written**: on load `_buildIndex` sets `leafId` to the last non-header line in file order (`:1103-1118`, `:1111`). So the active branch of a file is the path from that last entry to the root.
- Multiple roots are possible: `resetLeaf()` and `branchWithSummary(null, …)` let a later entry have `parentId: null` (`:1601`, `session-format.md` "Tree Structure").
- `/fork` and `/clone` write a **new file** holding one root-to-leaf path with `parentSession` set (`createBranchedSession`, `:1642-1740`); labels on that path are re-created.
- `/tree` navigation stays in one file; abandoned branches remain as siblings.

### 1.5 Building the model's context from the file

`buildContextEntries` / `buildSessionProjection` (`session-manager.ts:476-570`, `session-format.md` "Context Building"):

1. Take the path leaf → root.
2. If the path holds compaction entries, use the **latest**: the compaction entry, then the non-system entries from `firstKeptEntryId` up to (not including) it, then everything after it. `firstKeptEntryId` equal to the compaction's own id means "retain none".
3. Apply the latest `context_edit` per target (null omits; non-null replaces only `content`, a string becoming one text block for assistant/toolResult).
4. Convert: `message` as stored; `compaction` → optional `systemMessage` + `compactionSummary` user message; `branch_summary` → `branchSummary` user message; `custom_message` → `custom` user message; `custom`, `usage`, `label`, `session_info`, `model_change`, `thinking_level_change` → nothing (`:439-473`).
5. Model and thinking level come from the **last** `model_change`/`thinking_level_change`/assistant message on the path (`:418-436`).

Summary framing is identical in both runtimes: pi's `COMPACTION_SUMMARY_PREFIX` ("The conversation history before this point was compacted into the following summary:\n\n<summary>\n" … "\n</summary>", `messages.ts:12-18`) equals pi-durable's `SUMMARY_PREFIX`/`SUFFIX` (`packages/durable/src/harness/compaction.ts:68-70`).

## 2. What pi-durable stores

### 2.1 Records

- A **Session** holds conversations; the root has the reserved id `1`. A conversation is a **linear, append-only list of entries** with Session-global, ever-growing numeric ids (`docs/spec.md:95-160`, `:298-350`).
- `EntryRecord = {id, conversationId, kind, model?: Message[], data?: JsonValue, head?: EntryId, edits?: ContextEdit[], byTaskId?}` (`docs/spec.md` §2; `src/types.ts`). There is **no entry timestamp**: time lives in the messages' own `timestamp`.
- Built-in kinds (`src/entries.ts:11-34`): `pi.user` (`model: [UserMessage]`), `pi.assistant` (`[AssistantMessage]`), `pi.system` (`[SystemMessage]`, `content: ""`), `pi.tool-result` (`[ToolResultMessage]`, `data: {diagnostics}`), `pi.reset` (`head: "self"`, optional handoff text), `pi.compaction` (`[UserMessage]` summary, `head` = first kept entry, `data: {reason}`).
- Context derivation (`docs/spec.md:298-350`; `src/harness/context.ts:125-155`): H = newest entry with a `head`; the range runs from `H.head` to the tail; the newest edit per target wins (`omit` or `replace` with full `messages`); context entries are H followed by the range's non-head entries; tool results are moved after their call and orphan calls get a synthesized error result; model-less entries and assistant messages with stop reason `aborted`, `error` or `deferred` are excluded (`context.ts:10`).
- **No tree inside a conversation.** The only branching primitive is `fork(at)`: a new conversation whose history is the parent's entries through `at` (`docs/spec.md:1767-1816`; `Tx.forkConversation`, `src/types.ts:1011-1015`). cloudpid's ADR-0017 builds the Session tree on exactly this: each Session branch is a conversation, the Session keeps the active one in `cloudpid.session-tree` (`apps/server/src/session/tree.ts:36-46`).
- **Agent state, including model and thinking level, is a rewindable document** (`pi.agent`, `AgentState`), not entries (`docs/spec.md:540-560`). "Model and thinking level are request options, not prompt state" (`docs/spec.md:4191`). Document state at entry E is the final state of the commit containing E; different states need separate commits (`docs/spec.md:1775-1777`).
- **Usage** is a document (`pi.usage`) updated by `recordUsage` when pi-durable's own writers append an assistant or tool result (`src/harness/generation.ts:1121-1132`, `src/harness/tool.ts:1075`, `src/harness/usage.ts:25`), not derived from entries.
- Notes, Todo, subagent state, Settings and the rest are documents, not entries.

### 2.2 Writing entries from outside a run

Three paths exist; none is specific to pi session files.

1. **`Tx.appendEntry(conversationId, draft)`** inside any `harness.commit` (`src/types.ts:1017-1025`, `src/session/transaction.ts:393-430`). It accepts any `kind`, `model`, `data`, `head` (including `"self"`) and `edits`. The `pi.` prefix restriction applies only to the optional entry on an _input_ submission (`src/harness/submissions.ts:205-212`), not to `appendEntry`. It does not touch `pi.usage`.
2. **`Conversation.submit({type: "write", entry})`**: admits an entry at the next boundary (or at once when idle); a write with only `kind` and `data` is display-only and changes no context (`docs/spec.md:2796-2830`, `src/harness/submissions.ts:246-252`). A write whose `head` points before the active range is rejected `stale`; a raw `tx.appendEntry` head into the past is **not** checked and "changes model context in ways a queued write would not" (`docs/spec.md:6257-6260`).
3. **`createConversation({ownership, agent, init})` / `root(context, {agent, init})`**: `init(tx, id)` runs in the creating commit with the full `Tx`, so a conversation can be created and seeded in one atomic commit (`docs/spec.md:842-870`).

`pi-durable` has no import or export of the pi session format, and `coding-agent` does not depend on it (`packages/coding-agent/package.json` lists no `pi-durable`; `grep` for `durable` in `coding-agent/src` finds only two comments in `utils/shell.ts`). Its "JSONL" backend (`docs/spec.md:6164-6215`) is its own storage log (`main.jsonl`, sidecars), not the pi session format.

### 2.3 cloudpid already seeds a Session from entries

Fork and Clone (ADR-0017; `docs/architecture/client-and-protocol.md:39`) create a new Session DO and fill it by copying:

- `fillSession(source, target, plan)` (`apps/server/src/session/fork.ts:109-140`): `importStart`, then pages of entries (≤200 entries, ≤8 MiB of JSON each, `:22-25`), then `importFinish(plan)`.
- `importEntries` appends each page to `ROOT_CONVERSATION_ID` in one `harness.commit` with `tx.appendEntry`, keeping an old-id → new-id map so a `head` and `edits[].target` are renumbered (`apps/server/src/session/fork-host.ts:238-264`; `copiedDraft`, `fork.ts:145-178`); an unmapped head or edit is dropped.
- `importFinish` copies `pi.agent`, the Notes and the Todo List (`fork-host.ts:266-300`). Until it runs the Session refuses messages (`refusal`, `:302-309`). Usage and Secrets are not copied.

So the missing part of a Session import is **only the translation** from the pi file's tree of entries to `EntryDraft`s (and forks of the root conversation); the filling protocol, paging, renumbering and the "being made" guard exist. This is observation of cloudpid's code, not a claim that the fill API is already exposed outside the Registry/Session pair.

### 3.1 The tree

- A **linear** local path (the common case; 1,751 of the observed 1,778 files are unbranched) is one append sequence into the root conversation.
- A **branching** file needs conversations: append the trunk up to a fork point, `forkConversation(parent, at, {ownership: ownerless})` (the same call cloudpid's `navigate` uses, `branches.ts:274-281`), then append that branch's own entries to the child. A fork sees only its parent's entries through `at` (`docs/spec.md:1767-1816`), so appends after a fork do not leak into it, and a branch off a non-active branch is a fork of that branch's conversation. cloudpid's tree reconstruction (`tree.ts`: each branch's entries linked to the one before, its first to the entry it forked at) then yields pi's tree. The Session keeps which branch is active in `cloudpid.session-tree`; the importer would activate the branch holding the file's last line.
- **Multiple roots** (`parentId: null` more than once) have no counterpart inside one Session branch structure: a second root is a conversation with no parent, which ADR-0017's tree has only as "a branch started before the first entry". Not verified for import; rare (not seen in the corpus).
- Entries on **abandoned branches** can be dropped without loss of the active context, if the owner only wants the current path (cf. Fork/Clone, which copy only the active branch's path, `client-and-protocol.md:39`).

## 4. What has no cloudpid counterpart

- **Extension `custom` entries** (no LLM context): extension state (`pi-git-checkpoints`, `minimal-subagents.registry/identity`, `pi-lsp-post-edit-diagnostics`, `plannotator`, `pi-context-origin`, `pi-agent-lineage`, `codemode-store` …). cloudpid has none of these extensions; dropping them changes nothing the model saw. Exceptions where cloudpid has its own feature with a similar shape, to be mapped deliberately, not assumed: `pi-todo-state` (`{nextId, tasks:[{id,title,status}]}` observed) ↔ `cloudpid.todo`; `pi-context-note` / `pi-context-handoff` ↔ `cloudpid.context` Notes and Handoff (`packages/extensions/src/todo/doc.ts:47`, `context/notes.ts:38`). Those extensions' sources are not in `.repos`, so their formats are only what the observed files show.
- **Extension `custom_message`s** are the opposite: they **are context** (`minimal-subagents.result`, `pi-termctrl.exit`, `intercom_message`, `pi-context-prepare`, …). They must travel as user messages even though their extension is absent, or the imported history would lose what the model was told.
- **Local-only tools.** Assistant `toolCall`s and `toolResult`s name tools of the laptop's pi: extension tools (subagents, termctrl, lsp, plannotator, git checkpoints …), local MCP tools, `todo` and context tools from pi extensions. cloudpid's set differs (`docs/architecture/agent-capabilities.md:8-30`): the base `read`, `write`, `edit`, `bash`, `ls`, `find`, `grep` and `codemode` and `tool_search` overlap by name, others do not. Whether the history is replayable when a named tool is absent from the request's tool list is provider behavior this note did not verify (open).
- **Local paths and files.** Tool results quote laptop paths, and `fullOutputPath` temp files, and `bashExecution` outputs reference them; none exist in the Workspace.
- **Subagents.** pi's subagent extension (as observed) uses separate session files linked by `custom` identity entries; cloudpid's Subagents are conversations in the same Session (GLOSSARY). A local subagent file is a separate import, with no mapped link.
- **Header fields** (`parentSession`, `version`), **labels**, **entry timestamps**, **usage entries**, **`details`/`usage`/`fromHook` of compaction and branch summaries**, **`tokensBefore`**: no field (see table).
- **The local prompt and tool declarations** (system messages and `compaction.systemMessage`): intentionally not carried.
- **Virtual-model router state** (`custom` `pi.virtual-model-state`, `session-format.md`): no counterpart.

## 5. Constraints an import must meet

1. **Row size.** One entry is one SQLite row; workerd caps it at 8 MiB and a write over it fails the commit and therefore the Session (`docs/architecture/client-and-protocol.md:33`, `workspace.md:11-13`; pi-durable stores inline base64 images in `model`). cloudpid bounds its own writers (`MAX_STORED_INPUT_BYTES` 1.9 MB for inputs; images ≤ 750,000 base64 characters; result parts capped, #91/#97). Local files have no such bounds (observed: 18 lines above 1.9 MB, max 4.58 MB, files to 39.7 MB), so an import must measure and cut or reject before appending. A fill page is already limited to 8 MiB of JSON (`fork.ts:22`).
2. **Strict JSON.** Values must be strict JSON, copied by value (`docs/spec.md` invariant 6, `transaction.ts:86`). A parsed JSONL line satisfies it; `undefined` fields are omitted.
3. **Context size.** A local branch can be larger than the cloudpid model's window (observed compactions at 220–390k tokens). Per-model compaction settings apply on the first request; the first run may start with a blocking compaction. Last-assistant `usage` figures from another provider may misjudge `estimateContextTokens` (inference; the Harness estimate uses entry order, `docs/spec.md:6253-6256`).
4. **Heads written raw.** The compaction `head` must name an already appended entry of the same conversation, written before it (always true when appending in path order) because raw heads into the past are unchecked (`docs/spec.md:6257-6260`).
5. **Atomicity and guard.** Fork's guard (the Session takes no message until `importFinish`) and the page protocol are the model to reuse; a failed Fork deletes the new Session (`client-and-protocol.md:39`).
6. **Cache.** The first request after import cannot reuse the laptop's provider prompt cache (different prompt, tools, provider session id); `pi.provider` mints a fresh provider-facing id per conversation (`docs/spec.md:859`, `src/harness/provider.ts:26`).

## 7. Implications for the map (not a design)

- The import payload can be the pi file's entries as-is (documented, versioned format, with a v3 target); the server side does the mapping. Alternatively the local agent maps and sends `EntryDraft`-shaped data; the first keeps pi-format knowledge in one place and works for `pi --export … .jsonl` files too (`/export` and `/import` exist locally, `slash-commands.ts:25-26`).
- Reuse Fork/Clone's `importStart` / paged `importEntries` / `importFinish` (and its refusal guard) rather than a new path; the translation step sits in front of `copiedDraft`.
- A transport over MCP needs paging: one tool call per page of at most 8 MiB of entries (fill already pages at 200 entries / 8 MiB), or an upload by reference. The 1.9 MB `submit` cap is for owner messages, not fill pages.
- Choices the map can fix next: active-path-only versus whole tree; whether model/thinking history is positional or final-only; what to do with extension `custom` entries (drop, or keep as display-only data); how to treat oversized entries; whether to seed Notes/Todo from `pi-context-*` and `pi-todo-state`; Workspace choice and the path rewrite problem.
