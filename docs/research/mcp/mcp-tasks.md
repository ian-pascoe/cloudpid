# MCP Tasks extension (`io.modelcontextprotocol/tasks`): wire semantics, auth, push, host precedents, `@modelcontextprotocol/ext-tasks`

Research for the cloudpid MCP design (wayfinder map #373, tickets in the #389 family). Fetched 2026-11-01. Builds on `research-mcp-spec-revisions.md` §4 and `research-mcp-core-client-libraries.md` §1.5; those are not repeated, but every load-bearing claim here was re-checked against source.

Conventions: **[V]** verified in a primary source (cited), **[I]** inference, **[U]** unknown / not specified. "Spec" = `modelcontextprotocol/ext-tasks` `specification/2026-07-28/tasks.md` @ `b3d28ac` (2026-10-21); `specification/draft/tasks.md` differs from it only in two MRTR link URLs **[V]** (`diff`). cloudpid scope: **Modern (`2026-07-28`) only**.

## 1. Headline findings

1. **Task creation is server-directed and per-request; the only client lever is declaring the extension on that request.** The client puts `extensions["io.modelcontextprotocol/tasks"]: {}` in `_meta["io.modelcontextprotocol/clientCapabilities"]`; a server MUST NOT return `resultType: "task"` to a request that omits it, "regardless of prior declarations". There is no `task` request param, no TTL request, no `tools/list` hint. If a server can't serve a non-declaring client without a task, it MUST answer `-32021` (Missing Required Client Capability). **[V]** So "decline per request" = omit the declaration on that `tools/call` (Claude Code does exactly this). **[V]**
2. **Every `tools/call` must be treated as possibly returning `CreateTaskResult`** (`resultType: "task"`, a flat `Task`: `taskId, status, statusMessage?, createdAt, lastUpdatedAt, ttlMs|null, pollIntervalMs?`). Nothing in the Modern `Tool` shape (no `execution`, no `taskSupport`; `annotations` has only the four hints) predicts it. **[V]** (`schema/2026-07-28/schema.ts` core `Tool`.) The legacy `execution.taskSupport` is gone.
3. **`tasks/get` is the source of truth; it inlines the terminal payload.** `completed` ⇒ `result` is the full original `CallToolResult` (including `isError: true`, `_meta`, `structuredContent`, resource links; it is "exactly what the underlying request would have returned"); `failed` ⇒ `error` is a JSON-RPC error object (only for JSON-RPC faults); `cancelled` ⇒ nothing; `input_required` ⇒ `inputRequests`. Result object itself carries `resultType: "complete"`. **[V]**
4. **Errors are thin.** Unknown **or expired** `taskId` ⇒ `-32602` (MUST for `tasks/get`, SHOULD for `update`/`cancel`); expiry is indistinguishable from "never existed" (only the message text differs, non-normative). Non-declaring client on `tasks/*` or `subscriptions/listen{taskIds}` ⇒ `-32021` (MUST). **No error is defined** for cancel-of-terminal, update-to-non-`input_required`, or authorization denial. **[V]/[U]** (§3.4)
5. **`ttlMs` is a server retention backstop measured from creation, server-chosen, may change per poll, `null` = unlimited; there is no retention guarantee.** After it elapses the server MAY mark the task `failed` and MAY delete it at any time; "not required to retain tasks indefinitely" (even after `completed`). A client cannot request a TTL in Modern. Claude Code does not drop a task because `ttlMs` passed. **[V]** ⇒ cloudpid must treat `-32602` on a known task as "outcome unknown" and surface the last snapshot it has (Claude Code's `outcome unknown.` is the precedent). **[I]**
6. **`pollIntervalMs` is a SHOULD-honour hint that may change on every response; servers MAY rate-limit faster polling.** **[V]** `@modelcontextprotocol/ext-tasks` uses `max(10 ms, hints)`, default 1000 ms when absent. Claude Code clamps to 250 ms–30 s, default 2000 ms, re-reads each poll. **[V]**
7. **Auth: the spec says only that servers MUST authenticate and authorize every task request** ("Auth binding"); how a task binds to a principal is server-defined. Task IDs may be bearer tokens ("MAY"), so a leaked ID can be the only protection. Core authorization says `Authorization` MUST be on every HTTP request, so `tasks/*` carry the normal token. Credential rotation is **not addressed**; the safe reading is a task survives only if the server's binding survives. **[V]/[U]/[I]** (§4)
8. **Push is optional, best-effort, and has a known gap.** `subscriptions/listen` with `notifications.taskIds`; ack lists the IDs the server agreed to; each `notifications/tasks` carries a full `DetailedTask`. `progress`/`message` notifications on tasks are forbidden. **After a dropped stream nothing replays and nothing is re-sent on resubscribe** (ext-tasks issue #24, open); clients must `tasks/get` after (re)subscribing. **[V]** SEP-2694 (resumable task event streams) is an open draft. **[V]**
9. **Modern Tasks cover `tools/call` only; a client is never a task receiver.** SEP-2663 removed client-hosted sampling/elicitation tasks because SEP-2260 makes unsolicited server→client requests invalid; `inputRequests`/`tasks/update` replace them. The extension is **not defined under `2025-11-25`** (a server must treat the declaration as absent there). The `ext-tasks` package's `/receiver` entry is `2025-11-25`-only (task-augmented `sampling/createMessage` and `elicitation/create`). **[V]**
10. **`@modelcontextprotocol/ext-tasks` 0.2.2 (2026-09-30) can be the cloudpid client driver, but V2 needs a host-supplied `rawDispatch` + `v2RequestFraming`, and always declares the extension.** Its `SerializedTaskReference` is only `{endpointId, generation:"v2", taskId, originalOperation:"tools/call"}`: no URL, auth, headers, tool name/args, result codec; cloudpid must persist those itself. Test fixtures (`FakePort`) are **not published**. The package is 0.x (0.1.0 2026-09-17, 0.2.2 2026-09-30); no server side yet (issue #30). **[V]**
11. **Host precedent is thin and fresh.** Only **Claude Code ≥ v2.1.304** (CLI/SDK/Actions, flag-gated; not VS Code ext/desktop) implements the Modern extension (background, `/tasks`, cancel, elicitation, resume). **MCP Inspector** implements both eras (2026-10). **Goose** has an open issue for Modern Tasks (#11208, 2026-08-19) and explicitly refuses the `2025-11-25` form. **VS Code** implements the `2025-11-25` form and *blocks* the turn on it (open issue #308961, WIP backgrounding branch). The MCP website's client matrix has an **empty Tasks column for every client** (checked 2026-11-01; stale, since Claude Code and Inspector do support it). Cursor, fast-agent: no evidence found **[U]**. **[V]**
12. **Stability: Beta ("to Core"), "any change, breaking changes expected to be rare".** The Tasks & Events WG owns stabilization/promotion; open work that would touch the shape: SEP-2694 (resumable event stream), SEP-2848 (async tool approval via tasks), issue #3237 (partial output), ext-tasks PR #26 (`relatedTaskIds` `_meta`), PR #32 (preserve extension fields), issue #24 (missed notifications). Next core release is **late March 2027** (SEP-3398, last Tuesday of March ⇒ 2027-03-30 **[I]**). Real server adoption is near zero outside reference/third-party kits. **[V]/[I]** (§8)

## 2. Wire semantics (Modern)

### 2.1 Negotiation and creation **[V]** (Spec §Capability Negotiation, §Task Creation)

- Client → server, on **every** request that should be eligible (and on every `tasks/*`): `params._meta["io.modelcontextprotocol/clientCapabilities"].extensions["io.modelcontextprotocol/tasks"] = {}`. No settings are defined.
- Server → client: `server/discover` `capabilities.extensions["io.modelcontextprotocol/tasks"] = {}`.
- The declaration "does not suggest that [the client] requires a `CreateTaskResult`". A server that never creates a task is compliant. A client that receives `CreateTaskResult` for an unsupported request type MUST treat it as an invalid response.
- `CreateTaskResult` = `Result & Task` with `resultType: "task"`, flat (no nested `task` object; the spec text still says "the embedded `task`", ignore it; the example and schema are flat). Typically `status: "working"`, "not necessarily".
- Server MUST NOT respond until `tasks/get` for the `taskId` would resolve (strongly consistent creation). Servers SHOULD resolve any MRTR `input_required` rounds *before* returning the task (the MRTR phase and the task phase have independent `inputRequests` key spaces, so no cross-dedupe).
- Wrong-era notes: SEP-2663's table: under `2025-11-25` the extension does not apply; `tasks/result` ⇒ `-32601` under Modern; a `task` param on `CallToolRequest` is ignored; legacy `tasks.requests.*`/`tasks.list` capabilities MUST NOT be advertised alongside it.
- The SEP text calls the revision `2026-06-30` in places; the shipped revision is `2026-07-28`. **[V]**

### 2.2 `Task` fields **[V]**

| Field | Semantics |
|---|---|
| `taskId` | Opaque, server-generated, stable. Must be unguessable (MUST). Format otherwise unconstrained (Claude Code rejects >128 printable ASCII or spaces: host-specific). |
| `status` | `working` · `input_required` · `completed` · `failed` · `cancelled`. Last three terminal and immutable. Transitions: `working ↔ input_required`, either → terminal. |
| `statusMessage?` | Free text for any status; "MAY be exposed to the end-user or model". `failed` SHOULD carry one. Claude Code shows the *latest* poll's value; a response that omits it clears it. |
| `createdAt` / `lastUpdatedAt` | ISO 8601. `lastUpdatedAt` is not given further semantics (what bumps it is unspecified; spec examples reuse one value across states, so don't depend on it). Issue #24 proposes using it to drop stale snapshots **[I]**. |
| `ttlMs` | `number \| null`, from **creation**; server-chosen; "MAY change over the lifetime of a task". See §2.4. |
| `pollIntervalMs?` | Suggested interval; "MAY change over the lifetime". |

`GetTaskResult = Result & DetailedTask`: `WorkingTask | InputRequiredTask{inputRequests} | CompletedTask{result} | FailedTask{error} | CancelledTask`. `resultType` MUST be `"complete"` on it (spec examples were fixed in ext-tasks PR #25 / issue #23). `notifications/tasks` params are the same `DetailedTask` (no `resultType` in the example). `Result._meta` is available on `CreateTaskResult` and `GetTaskResult` (core `Result` type). **[V]** ext-tasks PR #32 (open) fixes the package's Zod schemas stripping unknown top-level fields on those two results, so `ext-tasks` 0.2.2 may drop vendor fields on them **[V]** (`PR #32` body).

### 2.3 Methods

| Method | Params | Success result | Errors |
|---|---|---|---|
| `tasks/get` | `{taskId}` | `GetTaskResult` (above) | unknown/expired ⇒ `-32602` MUST; `-32603`; non-declaring ⇒ `-32021` |
| `tasks/update` | `{taskId, inputResponses}` (keys MUST match currently outstanding `inputRequests` keys) | empty ack, `resultType: "complete"`, **eventually consistent** (status may not reflect it yet) | unknown ⇒ JSON-RPC error SHOULD (`-32602`); `-32021` |
| `tasks/cancel` | `{taskId}` | empty ack, `resultType: "complete"`, eventually consistent | unknown ⇒ SHOULD error; `-32021` |

All three on Streamable HTTP: `Mcp-Method: tasks/…` and **`Mcp-Name` MUST = `params.taskId`** (routing). `ext-tasks` sets it on V2 task requests (tests assert it); Inspector issue #1917 was a bug where it was omitted. `tasks/result` and `tasks/list` do not exist (Method not found). `notifications/cancelled` MUST NOT be used for tasks. **[V]**

### 2.4 TTL, retention, expiry **[V]** unless noted

- Who: the server (in `CreateTaskResult`, may revise on any later response). Modern has no way for a client to request one. (`ext-tasks` `task.retentionMs` maps only to the legacy V1 `task: {ttl}` param.)
- From when: "duration from creation" (`ttlMs` doc comment; ext-tasks `receiver.md` repeats "expires from task creation" for V1). The `tasks/get` paragraph ("if the task's observable status has not reflected the update after `createdAt` plus `ttlMs`…") is garbled; read it as: a non-null TTL lets the client treat the task as unusable after `createdAt + ttlMs`. Not "from last update". **[I]** for the garbled sentence.
- After expiry: server MAY flip the task to `failed` and MAY delete it "at any time"; a purged task answers `-32602` ("Task not found" / "Task has expired" are both example messages). Whether a result is discarded after `completed` + TTL: yes if the server wants; **no minimum retention after completion is promised**. `null` = server keeps it indefinitely (server's operational burden; maintainer comment on issue #11, 2026-08-20).
- Stopping work vs. retention are separate: TTL expiry does not oblige the server to stop the computation (issue #11, maintainer-confirmed intentional).
- Client side: persist IDs (SHOULD) and "MAY delete all state" once it has sent `tasks/cancel`.

### 2.5 `inputRequests` / `tasks/update` **[V]**

- `inputRequests` is `{[key]: {method, params}}` (same shape as MRTR: `elicitation/create`, `sampling/createMessage`, `roots/list` — ext-tasks' input handler routes all three), a **point-in-time snapshot of every outstanding request**. Polling again before answering returns the same keys again (spec example shows exactly this); clients SHOULD dedupe by key.
- Keys are unique over the task's whole life, never reused after a response is delivered; so `inputResponses` keyed by `k` always refer to the request first seen under `k`.
- Server SHOULD ignore responses to keys that are not outstanding (never issued, already answered, superseded). May accept a strict subset (task stays `input_required` until the rest arrive).
- After `tasks/update` the ack is eventually consistent: the next `tasks/get` may still show `input_required` with the same key. The client SHOULD track answered keys and not answer twice, and keep observing until terminal. Claude Code caps at 16 keys per task and answers each key once.
- Trust: "A task is not a higher-trust channel": same trust model as standalone elicitation/sampling (MUST). Relevant to cloudpid's elicitation (owner-only, credential forms declined) and sampling (Approval/Usage) positions: they apply unchanged to task `inputRequests`. **[V]** for the MUST, **[I]** for the mapping.
- Update to a task that is **not** `input_required` (or terminal): the spec defines nothing beyond "ignore keys not outstanding" and "SHOULD error for unknown task"; so expect an empty ack (ignored), or `-32602` if the server purged it. **[U]** (exact behaviour), **[I]** (expectation).

### 2.6 Cancellation **[V]**

Cooperative and ack-only. The ack means "recorded", not "stopping". The task MAY stay `working`, MAY finish `completed`/`failed` instead, and "eventual transition to `cancelled` is not guaranteed". Clients "need not poll again" and may drop task state immediately. Cancel of an already-terminal task: **[U]** (no error defined; since success is "MUST ack" and the task may legitimately already be done, an empty ack is the compatible behaviour **[I]**). Idempotency: not stated **[U]**; ack-only + eventual consistency make repeats harmless **[I]**. Claude Code sends `tasks/cancel` on user stop/Esc-while-waiting/unservable input, not on exit; the server may still finish the work (its docs say so).

### 2.7 `_meta`, MCP Apps and task results

- The terminal `result` is a normal `CallToolResult` (`result: JSONObject`), so `_meta`, `structuredContent`, `resource_link` and embedded-resource content are unrestricted **[V]**. `tasks/get`/`CreateTaskResult` also carry top-level `Result._meta` **[V]**.
- MCP Apps links a UI to a **tool definition** (`Tool._meta.ui.resourceUri`, legacy flat `_meta["ui/resourceUri"]`), not to a result **[V]** (`ext-apps` spec `2026-01-26` §Resource Discovery); the Apps spec never mentions tasks (grep: zero hits). So an App for a task-returning tool is rendered from the tool's `_meta`; the View gets the *final* `CallToolResult` when the task completes **[I]**. Whether a host shows the View early (with the `CreateTaskResult`) or at completion is unspecified **[U]**; there is no Apps "partial/task progress" contract beyond Apps' own partial-input notifications.
- No standard channel for partial output exists (issue #3237 open, 2026-08-14). `notifications/progress` is not supported on tasks.

## 3. Push: `subscriptions/listen` + `notifications/tasks` **[V]**

- Request: `subscriptions/listen` `params.notifications.taskIds: string[]` (plus the usual per-request `_meta`, including the tasks declaration; without it ⇒ `-32021`).
- Server MUST send `notifications/subscriptions/acknowledged` first (core), whose `notifications.taskIds` lists the IDs it **agreed** to push for. IDs omitted from the ack get no pushes; poll those.
- Each push = `notifications/tasks` with a complete `DetailedTask` identical to what `tasks/get` would return then (including `result`/`error`/`inputRequests`). Clients MAY also keep polling.
- `notifications/progress` and `notifications/message` MUST NOT be sent on the stream for a task; "not supported on tasks in general".
- Reconnect/missed notifications: core says an abrupt transport drop ends the subscription (client MAY reconnect; stdio MUST re-send `subscriptions/listen`; server keeps no state), and SSE resumability was removed. **Nothing in the spec replays missed transitions or re-sends state on resubscribe.** Ext-tasks issue #24 (2026-09-26, open) describes the stall (task goes terminal while disconnected; no notification ever; for `input_required` the task stalls server-side) and proposes (a) server snapshot-on-subscribe SHOULD or (b) client MUST `tasks/get` once per acked ID after (re)subscribing. A server implementer there says notifications should be declared best-effort with `tasks/get` as truth. **[V]** (issue), **[I]** (cloudpid should do (b) regardless). SEP-2694 `tasks/stream` (sequenced, resumable events, `events_gone`) is a draft, open since 2026-05-06, updated 2026-08-10, no reference impl. **[V]**
- `ext-tasks` 0.2.2 consumes `notifications/tasks` fed through the port's `onNotification`, but does **not** open `subscriptions/listen` itself (no `subscriptions/listen` reference in `src/client`); the host must open the subscription and forward notifications. **[V]** (grep; SDK may auto-route, unverified **[U]**).
- Claude Code uses polling only (`notifications/tasks` "not used") **[V]**.

## 4. Authorization and identity

- **Binding is mandated, mechanism unspecified.** Security Considerations: "Servers **MUST** perform authentication and authorization checks on each task-related request to ensure that the client has permission to access a task." Task IDs "MAY" be bearer tokens for stored state and MUST be unguessable. No `tasks/list` precisely so a server can't leak one caller's IDs. **[V]** SEP-2663 Motivation: binding to "some sort of authorization context" is bespoke to each server, "in many cases not possible", in which case "the task ID becomes the only line of defense"; sessions are gone (SEP-2567). SEP-1686's "document the limitation if you don't bind" SHOULD was **not** ported (ext-tasks issue #20 / PR #33, closed unmerged 2026-10-15). **[V]** ⇒ a given server may or may not tie a task to the creating principal; cloudpid cannot assume either. **[I]**
- **What the client must send:** the same per-request metadata as any Modern request (`_meta` protocolVersion/clientInfo/clientCapabilities **with the tasks extension**), `Mcp-Method`, `Mcp-Name = taskId`, and `Authorization` (core: "MUST be included in every HTTP request"). No task-specific header or token. **[V]** (`authorization/index.md`; `tasks.md`). A different token for the same user/server is not forbidden by the text; whether it is *accepted* is server policy. **[I]**
- **Denial vs unknown:** no code for "exists but forbidden"; a server will in practice return `-32602`, indistinguishable from unknown/expired (issue #20 point 1 withdrawn 2026-09-09 as a protocol-wide question; maintainer: AuthN/AuthZ rejection codes aren't defined for MCP in general; HTTP 401/403 + `WWW-Authenticate` apply to OAuth HTTP deployments). SEP-2643 (Structured Authorization Denials) is an open proposal. **[V]**
- **Credential rotation:** not addressed anywhere in the spec, SEP, issues. Refreshing an access token for the *same* principal is invisible to the protocol; changing principal (re-sign-in as another account, different tenant, rotated client credentials with a new subject) may make the task unreachable (`-32602`) or, with ID-only servers, still reachable. **[U]**, with the behaviours above **[I]**. Claude Code's guidance for server authors: "Keep the ID answerable across connections, because after a resume Claude Code asks about it on a new connection", and it refuses to follow a task if the server was "reconfigured to a different transport since this task was created" (URL/command/args/env/headers/timeout changed) **[V]** (Claude Code docs). A 401 mid-task is an ordinary OAuth refresh/step-up event on the poll request **[I]**.
- **Design consequence [I]:** key a persisted task reference by (MCP server identity incl. URL, MCP sign-in/principal, `taskId`); on `401/403` refresh as usual; on `-32602` after a credential *change*, report "task not reachable under the current sign-in; outcome unknown" rather than "expired".

## 5. Server-side guidance relevant to a client

- **May a server return a task for any `tools/call`?** Yes, at its discretion, per request, if the client declared the extension; no tool-level opt-in. **[V]** Spec: "in response to any supported request at its own discretion and on a per-request basis". Supported methods today: `tools/call` only; "implementations SHOULD be designed to accommodate additional request types in future revisions".
- **Tool-level hint?** None in Modern. Core `Tool` has `annotations` (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`, `title`) and `_meta`; no `execution`. **[V]** The legacy `execution.taskSupport` (`forbidden|optional|required`) is `2025-11-25` only. `ext-tasks`' `toolDeclaration({taskSupport})` is a *neutral* projection to the legacy shape and is irrelevant to V2. **[V]**
- **May the client decline?** Yes by omission of the declaration on that request (spec: "MUST NOT return CreateTaskResult to a client that did not include the extension capability on its request"). Then a server that *cannot* serve it synchronously MUST error `-32021` with `data.requiredCapabilities`. **[V]** The package, however, cannot decline: `frameV2TaskRequest` force-adds the declaration to every V2 `tools/call` and `tasks/*` it frames; `task.preference: "forbid"` only throws *after* a task came back (and best-effort cancels it). **[V]** (`sdk-client-adapter.ts:177-205`, `session.ts:545-565`). A host that wants a real "decline" must frame its own request (e.g. a sync-only call) or not route that call through the package.
- **Non-declaring client:** server returns the plain result or `-32021`; must not return a task or accept `tasks/*` / `taskIds` subscriptions (MUST `-32021`). **[V]**
- **Required handling:** a declaring client MUST handle either result shape for `tools/call`; MUST NOT use `tasks/result`/`tasks/list`.
- **Server-side recommendations that matter to a host:** answer the `tools/call` quickly with the handle (Claude Code: HTTP task answer must start within the per-request timer); durable creation; `statusMessage` for progress; keep `taskId` answerable across connections. **[V]** (spec; Claude Code docs.)

## 6. Is a client ever a task receiver?

- **Modern extension: no.** Only `tools/call` is task-augmentable, and the requester is always the client. SEP-2663: "Client-hosted tasks are no longer expressible" (SEP-2260 forbids unsolicited server→client requests); `inputRequests`/`tasks/update` carry elicitation/sampling/roots instead. **[V]**
- **`2025-11-25` binding of the extension: none.** The extension "is not defined under the `2025-11-25` protocol version"; Legacy servers use the core experimental `tasks.*` capability, which is out of scope here. The `ext-tasks` package nonetheless ships a V1 requester + `bindTaskReceiver` for task-augmented sampling/elicitation (legacy peers). **[V]** (SEP-2663 compat table; `typescript/receiver.md`.)
- **Planned expansion:** spec text only says other request types may follow. No open SEP found that adds a task-augmented method beyond `tools/call` (searched `modelcontextprotocol/modelcontextprotocol` and `ext-tasks`). Open/related, all additive and unaccepted: SEP-2694 resumable event streams (open, 2026-05-06); SEP-2848 asynchronous tool-call approval returning a task (`io.modelcontextprotocol/tool-approval`, open, updated 2026-10-20); issue #3237 partial output (open, 2026-08-14); ext-tasks PR #26 `io.modelcontextprotocol/relatedTaskIds` `_meta` on `tools/call` (open, 2026-09-29); steer/pause/resume SEP-2669 **closed** 2026-06-13 ("tracked separately" in the extension track), `paused` status not in the spec. Roadmap (updated 2026-08-22): "continued work on Tasks (SEP-2663) toward eventual inclusion of the extension in the core protocol"; Tasks & Events WG (leads Liguori, Alexander, Chang, McCaffrey) owns stabilization, webhook/callback events, and a Tasks/Triggers composition review. **[V]**

## 7. `@modelcontextprotocol/ext-tasks` client API (0.2.2, published 2026-09-30; repo `b3d28ac`/tag `v0.2.2`)

- Package: Apache-2.0, ESM, no root export; entries `/client`, `/receiver`, `/core`, `/core/v1`, `/core/v2`; optional peer `@modelcontextprotocol/client ^2.0.0`; versions on npm: `0.1.0` (2026-09-17), `0.2.2` (2026-09-30). Reshaped from the MCP Inspector's tasks code (ext-tasks #21 merged 2026-09-23). **[V]**
- Entry: `createTaskSessionFromClient(client, {endpointId, onInputRequest?, onError?, tools?, rawDispatch?, v2RequestFraming?})` — create it **after** `client.connect()`; one active session per SDK `Client`; make a new one on reconnect. Generation detected from the connected client (modern + server advertises the extension ⇒ V2). `withTasks(port)` takes any `ConnectedMcpSessionPort {endpointId, taskCapabilities, dispatch(request, {signal, context:{headers, requestTimeoutMs, resetTimeoutOnProgress}}), onServerRequest, onNotification, onInvalidated, invalidated}`: cloudpid can implement this port over its own transport and skip the SDK-client adapter entirely. **[V]**
- Calling: `session.callTool(name, args, {applicationContext, signal, headers, requestTimeoutMs, metadata, resultCodec, task:{preference:'allow'|'prefer'|'require'|'forbid', retentionMs?, retention?}})` ⇒ `ToolExecution` (`kind: 'immediate' | 'task'`). `execution.settle({onEvent})`, `.result()` (terminal outcomes `completed|failed|cancelled` returned, not thrown), `.updates()` (single consumer), `.handle.taskId`, `.cancel()` (remote cancel + release), `.detach()` (release, remote keeps running), `.close()` (release + best-effort cancel). `session.task(taskId, {headers, requestTimeoutMs})` ⇒ manual controller (`snapshot()`, `result()`, `cancel()`). `execution.handoff(persist)` saves a reference **before** detaching; if `persist` throws the execution stays active and can retry. `session.resumeTask(reference, options)` ⇒ new `ToolExecution`, after checking `endpointId` and `generation` match and doing an initial `tasks/get` (an unknown task = expired/removed; `TaskRecoveryOwnershipError` if a live local owner exists). **[V]**
- Reference: `{endpointId, generation: 'v2', taskId, originalOperation: 'tools/call'}` **[V]** (`api.ts:570-582`). Not included: server URL/identity beyond the opaque `endpointId`, auth, headers, `requestTimeoutMs`, `applicationContext`, tool name/args, result codec. `createTaskSessionEndpointId(label, descriptor)` hashes a descriptor (e.g. `{transport, url, tenantId}`) into a stable `endpointId`. Callers must re-pass `headers`/`requestTimeoutMs`/`resultCodec`/`applicationContext` to `resumeTask` (docs: "pass the original call's `headers` and `requestTimeoutMs`"). **[V]**
- V2 request path: `rawDispatch: (request: JsonValue, options?: DispatchOptions) => Promise<{kind:'result', result} | {kind:'error', error:{code,message,data?}}>` — must be "the host coordinator that owns request IDs and response matching" (the SDK `Client` cannot send/decode `resultType:"task"`; it throws `UnsupportedResultType`). `v2RequestFraming: {protocolVersion, clientInfo, clientCapabilities}` (non-empty; JSON objects; deep-frozen) are merged by the package into each V2 `tools/call` and `tasks/*` request as `_meta["io.modelcontextprotocol/protocolVersion" | "/clientInfo" | "/clientCapabilities"]` with `extensions["io.modelcontextprotocol/tasks"]: {}` forced on. Caller `_meta` is preserved. So `rawDispatch` receives a complete JSON-RPC request object (no `jsonrpc`/`id` assumptions stated: the coordinator assigns them) and must set `Mcp-Method`/`Mcp-Name`/auth headers from `options.context.headers` + the body. Rejecting with `DispatchError(message, retryable)` is the transient-failure channel. **[V]** (`sdk-client-adapter.ts`, `port.ts`). Fewer requirements if cloudpid implements `ConnectedMcpSessionPort` itself **[I]**.
- Polling: `max(10 ms, pollIntervalMs hints)`, default 1000 ms; consumes `notifications/tasks` when the port forwards them (it does not open `subscriptions/listen` itself). **[V]**
- Input: `createApplicationInputHandler({elicitation, sampling, roots})`; callback context has `scope: 'request' | 'task'`, `taskId`, `inputId`, `signal`, `applicationContext`; conservative protocol response + `onError` on routing ambiguity/handler failure. **[V]**
- Fixtures: `packages/ext-tasks/test-support/client/{fake-port.ts,semantic.ts}` (`FakePort` records `requests`/`dispatchOptions`, scriptable `dispatchHandler`, simulates server requests/notifications/invalidation) are in the repo but **`files: ["dist","README.md","LICENSE"]` ⇒ not published**; no fake server in the package. Copy the pattern, or depend on the git repo for tests. **[V]**
- Gaps/caveats: no server impl (issue #30, open); the SDK itself has no Tasks (typescript-sdk #2189 open; PR #2782 "Tasks extension for server and client (`ext/tasks` subpaths)" open since 2026-09-10); PR #32 open (field-stripping); 0.x ⇒ API may break. **[V]**

## 8. Host UX precedents

Spec's own client guidance: polling + persist IDs + dedupe `inputRequests`; "A task is not a higher-trust channel"; backward-compat note: a fixed-return `callTool()` "can transparently drive the polling flow internally and surface only the final, completed result", new surfaces can expose the lifecycle. The spec has **no** "model-visible" vs "host-managed" guidance; `statusMessage` MAY be shown to user or model. That choice is the host's. **[V]**

## 9. Adoption and stability outlook

- **Servers returning tasks today:** none verified in production for Modern. Known: the `ext-tasks` repo itself has no server (issue #30); `panyam/mcpkit` Go reference implementation of SEP-2663 (named in the SEP); `AndresSaa/mcp-durable-tasks` (independent engine: state machine, TTL, input rounds, memory/WAL store, conformance kit, 2026-10); an implementer building a computer-use server by hand (modelcontextprotocol#3237, 2026-08-14); typescript-sdk PR #2782 (server+client `ext/tasks`, open) and #2189 (open); the Python SDK `2025-11-25` experimental tasks (python-sdk issue #1853, 2026-01-14, shows VS Code Copilot consuming a legacy Python-SDK task server). Claude Code's docs have a "MCP tasks for server authors" section, i.e. it is the first mainstream consumer. **[V]** for existence; "no known production Modern task-returning server" is **[I]** (absence in searches of GitHub/web 2026-11-01).
- **Legacy `2025-11-25` servers returning tasks:** real but experimental (Python SDK, VS Code-targeted); out of scope.
- **Stage:** extensions page lists "MCP Tasks — Beta, to Core". SEP-3392 (Final 2026-09-25): Beta = "any change, with breaking changes expected to be rare", Extension-Maintainer approval, "real usage welcome"; Stable changes only with a new core revision; Beta → Core by Standards Track SEP. The ext-tasks repo labels its `2026-07-28` schema "Stable" and `draft` "Development" and is dated-snapshot structured (not `beta/` dirs). **[V]**
- **Release:** SEP-3398 (Accepted 2026-10-14) moves the December 2026 target to late March 2027 and sets the cadence "last Tuesday of March and September" ⇒ 2027-03-30 **[I]**. Nothing is in the `draft` changelog yet; the `draft` Tasks spec only differs by link paths from `2026-07-28`. Whether Tasks is promoted into the March 2027 core revision is unannounced **[U]**.
- **Churn risks to plan for [I]:** (a) missed-notification fix (issue #24, either side's rule would change client behaviour); (b) `relatedTaskIds` `_meta` (additive); (c) SEP-2848 tasks that stay `working` while awaiting out-of-band approval (additive, but surfaces long `working` periods); (d) possible `tasks/stream`/event channel (SEP-2694); (e) auth-denial error codes (SEP-2643) and the unported "unbound task" disclosure (issue #20); (f) promotion to core could rename/regroup the capability (the SEP says Tasks "are expected to be supported in future protocol versions"). Mitigation: implement against the `2026-07-28` schema snapshot, keep the task driver behind one module, feature-detect via `server/discover`.
