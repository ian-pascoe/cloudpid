# MCP resources: caching, subscriptions, legacy notification delivery, and Cloudflare limits

Research for the MCP Resources design (a host Durable Object serving many conversations of one owner). Fetched 2026-10-30. Questions: (1) what `cacheScope` allows for sharing resource results across conversations; (2) whether a `subscriptions/listen` filter can change in place, and how listens are cancelled; (3) how `notifications/resources/updated` reaches a `2025-11-25` client when the server refuses the GET stream; (4) Cloudflare memory, size, billing and lifetime limits for a Durable Object that holds an outbound SSE stream.

Conventions: **[V]** verified in a primary source (cited, normative sentence quoted), **[I]** inference (reasoned from sources, not stated by them), **[U]** the source is silent.

Sources are the MCP specification pages (`2026-07-28` and `2025-11-25`), SEP-2575, the `schema/2026-07-28/schema.ts` and `schema/2025-11-25/schema.ts` files in `modelcontextprotocol/modelcontextprotocol`, and Cloudflare's developer docs (pages dated Oct 2026).

## 1. Answers

1. **`cacheScope`** has exactly two values, `"public"` and `"private"`. `public`: "Any client, shared gateway, or caching proxy MAY store and serve the cached response to any user." `private`: "Cached responses MAY be reused for the same authorization context. Caches MUST NOT be shared across authorization contexts (e.g. a different access token requires a different cache)." So one client host serving many conversations of one owner, all presenting the same authorization, **MAY share** `resources/list`, `resources/templates/list` and `resources/read` results across those conversations under **both** values; the conversation is not part of the cache key and the spec says these results must not vary per connection. The key is "the request method together with the request parameters that affect the result (for example, the `uri` for `resources/read`, or the `cursor` for paginated list requests)"; the spec adds the authorization-context partition for `private`. The spec does not define "authorization context" beyond the access-token example **[U]**, so a rotated token is literally a different context.
2. **Filter changes: no in-place change exists.** `subscriptions/listen` takes its filter as request params; there is no update/replace message, and the spec is silent on mutating an open listen **[U]**. The only defined way to change a filter is to open a new listen and close the old one. A client **MAY** hold several concurrent listens: "A client **MAY** have multiple active subscriptions concurrently", each identified by its request ID and tagged in `_meta["io.modelcontextprotocol/subscriptionId"]`. Cancellation on Streamable HTTP: close the SSE response stream ("close the SSE stream (HTTP)"); `notifications/cancelled` is for stdio only ("No `notifications/cancelled` message is required or expected" on HTTP). Whether the server may dedupe overlapping filters across concurrent listens is **[U]**.
3. **`2025-11-25` with GET answered 405:** the spec lets the server do that ("or else return HTTP 405 Method Not Allowed, indicating that the server does not offer an SSE stream at this endpoint"), and defines no other channel for notifications unrelated to a request. The only other stream is a POST response stream, where server messages "**SHOULD** relate to the originating client request". That is a SHOULD, not a MUST, so a server can in principle push `resources/updated` on the SSE stream of a still-open POST, but only while some request's stream is open, and the spec offers no guarantee **[I]**. With no GET and no open POST stream, `resources/updated` cannot be delivered; the client must poll (`resources/read`). **stdio has no equivalent limitation**: the server "sends messages to its `stdout`", which may be "requests, notifications, or responses", with no per-stream rule.
4. **Cloudflare:** (a) **128 MB per isolate** (Workers; Durable Objects are Workers), shared by every DO in that isolate; duration is billed as 128 MB regardless of use. (b) **32 MiB** maximum serialized RPC (the page does not split arguments from return value; streams are exempt), and **32 MiB** for a received WebSocket message (outgoing is not limited by that row). (c) **Yes**: an open outbound `fetch()` keeps the DO in memory and blocks hibernation ("no outbound connection remains open" is a hibernation condition), and it is billed as duration wall-clock at 128 MB × time, at **$12.50 per million GB-s** on Workers Paid with **400,000 GB-s/month included** (Free: 13,000 GB-s/day). One DO held 24/7 = **324,000 GB-s per 30-day month = $0 duration**, inside the allowance (about $4.05 if the allowance did not exist); the account's $5/month Workers Paid minimum and request charges are separate. The allowance is account-wide: two always-held DOs exceed it. (d) **No wall-clock limit on the fetch itself, but the "keeps the DO alive" effect is capped at 15 minutes per operation**, after which "standard eviction rules resume" (idle non-hibernateable DOs are evicted after 70–140 s). Code deploys, runtime updates and host moves also shut DOs down (in-flight HTTP/RPC get up to 30 s during runtime updates), so a long-lived outbound SSE stream **will** be cut and must be re-opened.

## 2. `cacheScope` and the cache key (question 1)

### 2.1 Values and meaning

- Two values: `cacheScope: "public" | "private"`, a required field on every `CacheableResult`. **[V]** [schema.ts `CacheableResult`](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/schema/2026-07-28/schema.ts) (`cacheScope: "public" | "private";`).
- Caching hints are mandatory on `resultType: "complete"` results of `server/discover`, `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list` and `resources/read`: "Servers MUST include caching hints on results with `resultType: "complete"` returned by the following operations". **[V]** [caching › Cacheable Results](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching.md)
- `public`: "The response does not contain user-specific data. Any client, shared gateway, or caching proxy **MAY** store and serve the cached response to any user." **[V]** [caching › Cache Scope Field](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching.md)
- `private`: "The response contains private data that is not meant to be shared between callers. Cached responses **MAY** be reused for the same authorization context. Caches **MUST NOT** be shared across authorization contexts (e.g. a different access token requires a different cache)." **[V]** same section; the schema comment says "The response MAY be cached and reused only within the same authorization context."
- The field "controls who may cache a response, analogous to HTTP `Cache-Control: public` vs `Cache-Control: private`". **[V]** same section.
- Guidance on choosing: "`public` is appropriate for lists of tools, prompts, and resource templates when they are identical for all users. `private` is appropriate for `resources/read` results that depend on the authenticated user, or for filtered list results that vary per user." **[V]** caching › Choosing a Cache Scope. The resources page's examples return `resources/list` and `resources/templates/list` as `public` (`ttlMs` 300000) and `resources/read` as `private` (`ttlMs` 60000). **[V]** [resources](https://modelcontextprotocol.io/specification/2026-07-28/server/resources.md)
- Security: "`public` ... may be shared between callers even if the Result is coming from an authenticated endpoint ... (i.e. different access tokens can leverage the same cache)", and servers "MUST apply appropriate per-primitive access controls, and MUST NOT rely on `cacheScope` alone to prevent unauthorized access". **[V]** caching › Security Considerations.
- Every page of a paginated list is cached separately, and "Servers **MUST** apply the same `cacheScope` to all response pages for a given list request." **[V]** caching › Interaction with Pagination.

### 2.2 Cache key

- "A cached response is identified by the request method together with the request parameters that affect the result (for example, the `uri` for `resources/read`, or the `cursor` for paginated list requests). Clients **MUST NOT** serve a cached response for a request whose method or parameters differ from the request that produced it." **[V]** [caching › Cache Key](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching.md)
- "Results produced by retrying a request through the multi round-trip requests mechanism — that is, requests carrying `inputResponses` or `requestState` — **MUST NOT** be cached, as they depend on inputs that are not part of the cache key." `input_required` results "are not cacheable and carry no caching hints". **[V]** same page.
- The spec does not list the per-request `_meta` (`protocolVersion`, `clientCapabilities`, `clientInfo`) as key members or non-members. Whether a change in declared capabilities between requests invalidates the entry is **[U]**.
- Server side: `resources/list` "**MUST NOT** vary per-connection or as a side effect of other requests on the connection. The set **MAY** vary by the authorization presented on the request — for example, returning only the resources the caller's granted scopes permit — since credentials are per-request input, not connection state." **[V]** [resources › Capabilities](https://modelcontextprotocol.io/specification/2026-07-28/server/resources.md)

### 2.3 Sharing across conversations of one owner

- Under `public`, any caller may be served the entry, so conversation boundaries are irrelevant. **[V]**
- Under `private`, reuse is allowed "for the same authorization context", and the only stated boundary is a different access token. A host object that serves several conversations of one owner with the same access token is inside one authorization context, so one cache can serve all of them. Because the server must not vary results per connection, a conversation (a host-level construct; a "connection" in MCP terms) is not a cache dimension. **[I]** (follows from the two quoted sentences; the spec never mentions conversations or hosts).
- Conservative reading: "a different access token requires a different cache" taken literally means a refreshed or re-issued token for the same principal starts a new cache; the spec does not say whether the same principal under a new token is the "same authorization context" **[U]**.
- Suggested key, **[I]**: `(server endpoint, authorization-context id, method, cursor | uri | uriTemplate-expansion)`; for `public` entries the authorization-context component may be dropped. This is a design choice; the spec fixes only method + result-affecting params and the `private` partition.
- Freshness: valid while `now < t_received + ttlMs`; a relevant notification "invalidates the cached response and it should be considered immediately stale". **[V]** caching › Freshness Calculation, Interaction with Notifications.

## 3. `subscriptions/listen`: filter changes, concurrency, cancellation (question 2)

- Opening: the client sends a request whose params carry the filter; "The server **MUST NOT** send notification types the client has not explicitly requested." Filter fields: `toolsListChanged`, `promptsListChanged`, `resourcesListChanged` (booleans) and `resourceSubscriptions` (`string[]`, "Receive `notifications/resources/updated` for these resource URIs"). **[V]** [subscriptions › Opening a Stream](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions.md); schema `SubscriptionFilter`, `SubscriptionsListenRequestParams.notifications`.
- The server answers with `notifications/subscriptions/acknowledged` first; its `notifications` "reflects the subset the server agreed to honor. Notification types the server does not support are omitted." **[V]** subscriptions › Acknowledgment. The client "SHOULD check the acknowledged filter against what it requested".
- **In-place filter change: not defined.** The spec has no `subscriptions/update`, no amend or replace semantics, and nothing that says an open listen's filter is mutable or immutable. The request is a JSON-RPC request whose params are fixed at send time, its response is the long-lived stream, and SEP-2575 lists only open, multiple-concurrent, stop, graceful-complete, and (stdio) re-send after reconnect. **[U]** for an explicit statement; the absence of any update message is **[V]** in [schema.ts](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/schema/2026-07-28/schema.ts) and [SEP-2575](https://modelcontextprotocol.io/seps/2575-stateless-mcp.md). It follows that adding a URI means opening a new listen (carrying the union or only the new URI) and cancelling the old one, or keeping both. **[I]**
- **Concurrent listens: allowed.** "A client **MAY** have multiple active subscriptions concurrently — for example, one listening for tools-list changes and another for resource updates. Each subscription is identified by the JSON-RPC request ID of its `subscriptions/listen` request, and every notification on the stream carries that ID in `io.modelcontextprotocol/subscriptionId` so clients can demultiplex them." **[V]** [subscriptions › Multiple Concurrent Subscriptions](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions.md); SEP-2575 §"Multiple Concurrent Subscriptions". No limit on the number is stated **[U]**; a server could return an error or trim the acknowledged filter (the acknowledgment is how it says so).
- Duplicate URIs across concurrent listens: whether the server sends one `resources/updated` per listen (each tagged with its own `subscriptionId`) or dedupes is **[U]**. Each listen is a separate stream, so a per-listen notification is the natural reading. **[I]**
- **Cancellation:**
  - Streamable HTTP: "The **client** cancels it — close the SSE stream (HTTP) or send `notifications/cancelled` referencing the `subscriptions/listen` request ID (stdio)." **[V]** subscriptions › Cancellation. And: "**Streamable HTTP**: Closing the SSE response stream is the cancellation signal. The server **MUST** treat a client disconnect as cancellation of that request. No `notifications/cancelled` message is required or expected." **[V]** [cancellation › Transport-Specific Cancellation](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/cancellation.md); also [streamable-http › Cancellation](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http.md): "Closing the SSE response stream **MUST** be treated by the server as cancellation of that request."
  - The transport page adds that this revision "defines no client-to-server _notifications_ over Streamable HTTP". **[V]** streamable-http › Sending Messages.
  - stdio: "The client **MUST** send a `notifications/cancelled` notification referencing the request ID." **[V]** cancellation page. SEP-2575: "The server **MUST** stop sending notifications for that subscription."
  - Server-initiated end: "it **SHOULD** send a successful `subscriptions/listen` response to signal a graceful end ... then close the stream"; on stdio the server instead sends `notifications/cancelled` referencing the listen ID. A close without that result "indicates an unexpected disconnect, which the client **MAY** treat as a trigger to reconnect". **[V]** subscriptions › Graceful Closure; cancellation page.
- No resumption: "Resumable SSE streams via `Last-Event-ID` are not supported." So after a drop the client re-opens a listen and should re-read the resources it cares about, because notifications during the gap are lost. **[V]** streamable-http › Receiving Messages; the "re-read" step is **[I]**.
- Keep-alive: "servers are encouraged to periodically emit an SSE comment line ... as a keep-alive"; "clients must ignore such lines". **[V]** streamable-http note.
- Capability gate: `subscribe` means "whether the server supports resource-specific update notifications for resources requested through subscriptions/listen using the resourceSubscriptions filter." **[V]** [resources › Capabilities](https://modelcontextprotocol.io/specification/2026-07-28/server/resources.md)

## 4. `2025-11-25` Streamable HTTP and `notifications/resources/updated` (question 3)

- Subscribing is `resources/subscribe`; the notification is `notifications/resources/updated`, and the schema says "This should only be sent if the client previously sent a resources/subscribe request." **[V]** [resources (2025-11-25) › Subscriptions](https://modelcontextprotocol.io/specification/2025-11-25/server/resources.md); [schema.ts 2025-11-25](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/schema/2025-11-25/schema.ts) `ResourceUpdatedNotification`. The `resources` page does not say which stream carries it **[U]**.
- The standalone GET stream, verbatim from [transports (2025-11-25) › Listening for Messages from the Server](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports.md):
  1. "The client **MAY** issue an HTTP GET to the MCP endpoint. This can be used to open an SSE stream, allowing the server to communicate to the client, without the client first sending data via HTTP POST."
  2. "The server **MUST** either return `Content-Type: text/event-stream` in response to this HTTP GET, or else return HTTP 405 Method Not Allowed, indicating that the server does not offer an SSE stream at this endpoint."
  3. "If the server initiates an SSE stream: The server **MAY** send JSON-RPC _requests_ and _notifications_ on the stream. These messages **SHOULD** be unrelated to any concurrently-running JSON-RPC _request_ from the client."
- The POST response stream, same page, Sending Messages to the Server: "The server **MAY** send JSON-RPC _requests_ and _notifications_ before sending the JSON-RPC _response_. These messages **SHOULD** relate to the originating client _request_." "After the JSON-RPC _response_ has been sent, the server **SHOULD** terminate the SSE stream."
- One stream per message: "The server **MUST** send each of its JSON-RPC messages on only one of the connected streams; that is, it **MUST NOT** broadcast the same message across multiple streams." **[V]** same page, Multiple Connections.
- **Answer to 405.** With 405 the server has declared "that the server does not offer an SSE stream at this endpoint". The spec then names no other place for notifications unrelated to a request. A `resources/updated` would only fit on the response stream of a still-open POST, where the text is "SHOULD relate to the originating client request" (SHOULD, not MUST; the spec has no sentence that forbids an unrelated notification there, nor one that endorses it). So: delivery is possible only opportunistically, only while a POST stream is open, and on the server's discretion **[I]**; whether a client may rely on it is **[U]**, and a robust client must treat 405 as "no push" and poll. Resumability does not help: it replays only "on the stream that was disconnected" and "MUST NOT replay messages that would have been delivered on a different stream". **[V]** same page, Resumability and Redelivery.
- The client side of the GET is optional ("MAY"), so a client that never opens it also gets no unrelated notifications; this is symmetric with the server 405. **[V]**
- **stdio (2025-11-25):** "The server reads JSON-RPC messages from its standard input (`stdin`) and sends messages to its standard output (`stdout`). Messages are individual JSON-RPC requests, notifications, or responses." There is one bidirectional channel, no per-request stream, and no rule limiting which notifications may be sent or when. **[V]** [transports (2025-11-25) › stdio](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports.md). So stdio has no equivalent limitation; the only prerequisite is that the client previously sent `resources/subscribe`.
- For contrast, `2026-07-28` removes the GET endpoint ("Removal of the GET stream endpoint", "Removal of protocol-level sessions") and delivers `resources/updated` only on a `subscriptions/listen` stream: "Long-lived change notifications (such as list changes and resource updates) are delivered on the response stream of a `subscriptions/listen` request." **[V]** [streamable-http (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http.md). The schema comment: "This is only sent for resources the client opted in to via the `resourceSubscriptions` field of a subscriptions/listen request."

## 5. Cloudflare limits (question 4)

All from developers.cloudflare.com; page "Last updated" dates are Oct 2026.

### 5.1 (a) Memory

- "Each isolate can consume up to 128 MB of memory, including the JavaScript heap and WebAssembly allocations. This limit is per-isolate, not per-invocation. A single isolate can handle many concurrent requests." The Workers limits table lists Memory as 128 MB on both Free and Paid. **[V]** [Workers limits › Memory](https://developers.cloudflare.com/workers/platform/limits/)
- "When an isolate exceeds 128 MB, the Workers runtime lets in-flight requests complete and creates a new isolate for subsequent requests." **[V]** same.
- Durable Objects: "Durable Objects are a special kind of Worker, so Workers limits also apply." **[V]** [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/). Pricing: "If your account creates many instances of a single Durable Object class, Durable Objects may run in the same isolate on the same physical machine and share the 128 MB of memory." **[V]** [DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/) footnote 5. So 128 MB is a per-isolate ceiling that several DOs may share, not a per-DO reservation.

### 5.2 (b) Message sizes

- RPC: "The maximum serialized RPC limit is 32 MiB. Consider using `ReadableStream` when returning more data." **[V]** [Workers RPC › Limitations](https://developers.cloudflare.com/workers/runtime-apis/rpc/). The sentence does not distinguish arguments from return values; both are serialized messages **[U]**/**[I]**. Streams are exempt: "bytes in the body are automatically streamed with appropriate flow control. This allows you to send messages over RPC which are larger than the typical 32 MiB limit" (byte streams only).
- WebSocket: "WebSocket message size | 32 MiB (only for received messages)", for both SQLite- and key-value-backed DOs. **[V]** [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/). Hibernation attachments are smaller: "Maximum serialized size is 16,384 bytes" for `serializeAttachment`. **[V]** [DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)
- Other sizes that matter for caching resource contents: SQLite "Maximum string, `BLOB` or table row size | 2 MB"; key-value backend value size 128 KiB; outbound request body from a DO via `fetch()` "100 MiB by default". **[V]** DO limits.

### 5.3 (c) Does an open outbound fetch keep a DO in memory, and what does it cost

- Hibernation conditions, all required: "No I/O operation or promise passed to `this.ctx.waitUntil()` remains unfinished, and no outbound connection remains open." A DO that is idle but fails them is "idle, in-memory non-hibernateable". **[V]** [DO lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)
- "Pending I/O and open outbound connections prevent a Durable Object from being evicted. Examples include service binding requests, Durable Object remote procedure call (RPC) calls, outbound `fetch()` requests, ... TCP sockets and outbound WebSockets also prevent eviction." **[V]** same page.
- "Durable Objects remain active while a request, RPC call, response stream, WebSocket, or pending I/O is in flight." **[V]** [DO limits › Wall time limits by invocation type](https://developers.cloudflare.com/durable-objects/platform/limits/)
- Billing: "Durable Objects are billed for compute duration (wall-clock time) while the Durable Object is actively running or is idle in memory but unable to hibernate." "While an operation prevents eviction, the Durable Object continues to incur duration charges." **[V]** [DO pricing › Compute billing](https://developers.cloudflare.com/durable-objects/platform/pricing/); lifecycle page. Caveat, a Cloudflare docs inconsistency: the DO limits FAQ says "CPU time is active processing time: not time spent waiting on network requests, storage calls, or other general I/O, which don't count towards your CPU time or Durable Objects compute consumption." Read alone that suggests waiting on I/O is free, but the pricing page and lifecycle page bill wall-clock duration while pending I/O keeps the object non-hibernateable. The pricing and lifecycle pages are specific to duration billing, so this doc follows them. **[V]** for each quote, **[I]** for the reconciliation.
- "Duration is billed in wall-clock time as long as the Object is active and not eligible for hibernation, but is shared across all requests active on an Object at once." **[V]** pricing footnote 4. So N concurrent streams in one DO cost the same duration as one.
- "Duration billing charges for the 128 MB of memory your Durable Object is allocated, regardless of actual usage." **[V]** pricing footnote 5. Example 1: "1,000,000 seconds * 128 MB / 1 GB = 128,000 GB-s."
- Rates: Workers Paid: "Duration | 400,000 GB-s / month, + $12.50/million GB-s", requests "1 million / month, + $0.15/million". Workers Free: "13,000 GB-s / day" and 100,000 requests/day; on Free, exceeding a limit makes further operations of that type fail, and daily limits reset at 00:00 UTC. **[V]** DO pricing. Billing rounds up: "billable usage is rounded up to the next billable unit ... 500,000 GB-s of billable compute duration is rounded up to 1,000,000 GB-s". The pricing examples add "minimum $5/mo usage". **[V]**
- The first-party WebSocket page confirms hibernation is server-side only: "Hibernation is only supported when a Durable Object acts as a WebSocket server. Outgoing WebSockets do not hibernate." **[V]** [DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/) (this is about WebSockets; the same lifecycle rule covers outbound `fetch`).
- Connection-count limit: "Each Worker invocation can have up to six connections simultaneously waiting for response headers ... Once response headers arrive for a connection, it no longer counts toward the six-connection limit." So many open SSE streams are fine once their headers arrive; only the 6 in the header-wait phase are limited. **[V]** [Workers limits › Simultaneous open connections](https://developers.cloudflare.com/workers/platform/limits/). The DO table repeats "Simultaneous outgoing connections/request | 6".

**Cost of one DO held in memory 24/7 at 128 MB** (0.125 GB × seconds; **[I]** arithmetic from the quoted rates):

| Month length | Seconds   | GB-s    | vs 400,000 GB-s allowance | Duration cost (Workers Paid) | Cost with no allowance |
| ------------ | --------- | ------- | ------------------------- | ---------------------------- | ---------------------- |
| 30 days      | 2,592,000 | 324,000 | inside (76,000 left)      | **$0.00**                    | $4.05                  |
| 31 days      | 2,678,400 | 334,800 | inside                    | $0.00                        | $4.19                  |
| 730 h (avg)  | 2,628,000 | 328,500 | inside                    | $0.00                        | $4.11                  |

- On Workers Free, one DO is 86,400 s × 0.125 = 10,800 GB-s/day, under the 13,000 GB-s/day allowance. **[I]** (the Free plan allows SQLite-backed DOs only).
- The allowance is per account and shared by all DOs. 400,000 / 324,000 ≈ 1.23 DO-months, so the second always-on DO pays. Applying the page's rounding rule (billable overage rounded up to the next 1,000,000 GB-s): 2 DOs = 248,000 GB-s over → billed 1,000,000 → **$12.50** (unrounded $3.10); 4 DOs = 896,000 over → $12.50 (unrounded $11.20); 10 DOs = 2,840,000 over → 3,000,000 → $37.50 (unrounded $35.50). The rounding applies at the account level to the "billable usage". **[I]** (reading of the rounding sentence with the Example 2 pattern, where 10,659,200 → "11,000,000 GB-s x $12.50 / 1,000,000 = $137.50").
- Because the duration charge is wall-clock for the whole object, several held streams in one DO do not multiply it, but one DO per conversation would. **[V]** footnote 4; the design consequence is **[I]**.

### 5.4 (d) Lifetime of an outbound fetch and forced restarts

- No fetch-specific wall limit: "There is no set time limit on individual subrequests. As long as the client remains connected, the Worker can continue making subrequests." **[V]** [Workers limits › Subrequests](https://developers.cloudflare.com/workers/platform/limits/). For DOs: "Durable Objects (RPC / HTTP) | Unlimited | No hard limit while the caller stays connected to the Durable Object." **[V]** DO limits. Alarm handlers have 15 minutes of wall time. **[V]**
- **The 15-minute window:** "Each operation prevents eviction until it completes or for up to 15 minutes from when it starts, whichever comes first. Operations started together do not combine their windows. Starting another operation later can extend the Durable Object's time in memory. The limit applies to each operation, not to the total time in memory." "When no operation prevents eviction, the standard eviction rules resume." **[V]** [DO lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/). For outbound WebSockets: "an open outbound WebSocket connection prevents eviction for up to 15 minutes. The connection itself may remain open after that." **[V]** DO WebSockets. So an SSE stream read through one `fetch()` stops protecting the DO after 15 minutes. If nothing else is in flight, the DO is idle and non-hibernateable and is "evicted entirely from memory ... after 70-140 seconds of inactivity", which tears down the stream. The docs do not say outright that the open `fetch` is cut at that moment; that follows from eviction removing the object from memory **[I]**. Whether billing continues between minute 15 and eviction is **[U]**; the idle non-hibernateable state is a billed state **[V]**.
- Keeping the stream alive past 15 minutes therefore requires something else to keep extending the window, e.g. starting another operation, a timer or alarm, or incoming events (each new request or event resets the idle clock). The docs give the extension mechanism ("Starting another operation later can extend the Durable Object's time in memory") but do not describe it as a supported keep-alive pattern. **[I]**
- **Shutdowns that cut a stream:** "Durable Objects will occasionally shut down and objects are restarted ... This can happen for various reasons, including: New Worker deployments with code updates; Lack of requests to an object following the state transitions documented above; Cloudflare updates to the Workers runtime system; Workers runtime decisions on where to host objects." **[V]** [DO lifecycle › Shutdown behavior](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)
  - "HTTP & RPC requests: In-flight requests are allowed to finish if they do not access a Durable Object's storage. If a request attempts to access a Durable Object's storage, it will be stopped immediately and return an error ... When the Worker runtime system is being updated, in-flight requests have up to 30 seconds to complete." "WebSocket connections: WebSocket requests are terminated automatically during shutdown." **[V]** same.
  - "Shutdown hooks or lifecycle callbacks that run before shutdown are not provided"; design to "write state incrementally". **[V]** same.
  - Code updates roll out globally "in an eventually consistent manner", and "This will cause a Durable Object to shut down". **[V]** same; [known issues](https://developers.cloudflare.com/durable-objects/platform/known-issues/).
  - Outside DOs, "processes running the previous version of the Workers runtime give existing Workers requests and connections up to 20 minutes to finish. This includes streaming HTTP responses and WebSocket connections ... Crashes, resource pressure, and shutdowns can interrupt work earlier." **[V]** [Workers limits › Runtime updates](https://developers.cloudflare.com/workers/platform/limits/). The 20-minute grace is stated for Workers requests; the DO page gives 30 seconds for in-flight DO requests, so a DO's outbound stream should assume the shorter figure **[I]**.
  - Cloudflare gives no periodic (e.g. daily) restart schedule for DOs; the listed causes are deploys, inactivity, runtime updates and placement. **[U]** for any other cadence.

## 6. What this means for the Resources design

Marked **[I]**: inferences, not source claims.

- Treat any held upstream stream as best-effort. Expect it to be cut by deploys, runtime updates, host moves, and the 15-minute eviction window; on cut, re-open the listen with the union filter and re-read the subscribed resources, since there is no resumption and missed notifications are lost.
- A host-level cache keyed `(server, auth context, method, cursor|uri)` is spec-conformant for both scopes; use the owner's access token (or a stable principal id the server honours) as the auth-context component and drop it only for `public`.
- Prefer one listen per (server, auth context) whose filter is the union of conversations' subscriptions, and open a replacement listen when the union changes, as there is no in-place edit. Fan out `resources/updated` to conversations inside the host, de-duplicating by URI.
- For legacy `2025-11-25` servers answering GET with 405, push is unavailable; fall back to TTL-less polling of subscribed URIs, or only refresh on use.
- A DO that must hold a stream 24/7 costs duration within the free allowance at one object, and about $12.50 per additional million GB-s above 400,000 GB-s per account; this is small compared to the correctness cost of designing as if the stream never breaks.
