# What must an MCP Apps host implement?

Research ticket [#375](https://github.com/ian-pascoe/cloudpid/issues/375) of the MCP wayfinder map (#373).

**Question.** What does a host need to render MCP Apps (`ui://` resources, `text/html;profile=mcp-app`), how does a tool declare its UI, what is the host↔app message protocol, what are the sandbox/CSP and sizing requirements, what do reference hosts do, and what constraints does that put on a web UI behind Cloudflare Access?

## Short answer

An MCP Apps host is, for each rendered tool result, (1) an MCP **client** that negotiates the `io.modelcontextprotocol/ui` extension and reads `ui://` HTML through `resources/read`; (2) a **double-iframe sandbox** on a second origin that loads that HTML under a host-built CSP; and (3) an MCP-flavoured JSON-RPC **server over `postMessage`** that answers the View's `ui/initialize`, pushes `tool-input`/`tool-result`, proxies `tools/call` and `resources/read` to the real server, and handles `ui/message`, `ui/update-model-context`, `ui/open-link`, display mode and size changes. For cloudpid the hard parts are not the protocol but (a) a **second, secretless origin that is not behind Access** (or is carefully same-site), with per-load HTTP-header CSP, and (b) routing the View's calls through the Session socket to an MCP connection that lives in a Durable Object, not in the browser.

## 1. Negotiation and discovery

**Facts**

- Extension id `io.modelcontextprotocol/ui`; `ui://` prefix and the label are reserved by MCP (SPEC §Extension Identifier, §Reservations). Stage "Stable", Extensions repo `ext-apps` (EXT).
- The client advertises support in `initialize` as `capabilities.extensions["io.modelcontextprotocol/ui"] = { mimeTypes: ["text/html;profile=mcp-app"] }`; `mimeTypes` is REQUIRED (SPEC §Client<>Server Capability Negotiation). EXT says that for `2025-11-25` and earlier this travels in `initialize`'s `params.capabilities.extensions`; the field "is not part of the published schemas for these protocol versions" and supporting it is not required for conformance. For protocol `2026-07-28` and later the client instead sends it per request in `_meta["io.modelcontextprotocol/clientCapabilities"]` and the server answers in `server/discover` (EXT §Negotiation).
- Servers SHOULD check the client capability before registering UI tools and SHOULD offer text-only fallbacks; tools MUST return a meaningful `content` array even when a UI exists (SPEC §Server Behavior, §Graceful Degradation). So advertising changes what `tools/list` returns for some servers.
- A tool declares its UI with `_meta.ui.resourceUri` (a `ui://` URI) and optional `_meta.ui.visibility: ("model"|"app")[]` (default both). The flat `_meta["ui/resourceUri"]` is deprecated; SDK hosts check both and the nested one wins (SPEC §Resource Discovery; SDK `getToolUiResourceUri`, `src/app-bridge.ts:127`). A `resourceUri` not starting with `ui://` is an error (SDK, same function).
- Host MUST use `resources/read` to fetch the URI; MAY prefetch/cache; servers MAY omit UI-only resources from `resources/list` and `list_changed`, so the host cannot rely on listing to find them (SPEC §Behavior).
- The resource: `mimeType` MUST be `text/html;profile=mcp-app`; content in `text` or base64 `blob`; a valid HTML5 document; one `contents[]` item (BASIC-HOST rejects anything else, `implementation.ts` `getUiResource`).
- `_meta.ui` of the resource (`csp`, `permissions`, `domain`, `prefersBorder`) may sit on the content item of `resources/read` **and/or** the `resources/list` entry; hosts MUST check both, content item wins (DRAFT §Metadata Location; not yet in the stable text, which shows it on the content item only). BASIC-HOST implements the fallback.
- Visibility: the host MUST NOT list in the agent's tool list a tool without `"model"`; MUST reject an app's `tools/call` for a tool without `"app"`; app-only tools are never callable cross-server (SPEC §Visibility).

**Gap in pi (verified).** `pi-mcp`'s `ClientCapabilities` type has no `extensions` (`.repos/pi/packages/mcp/src/protocol/types.ts:23-28`), but `connect()` spreads `this.options.capabilities` into the `initialize` params unchanged (`client.ts:217`), so it passes at runtime and needs only a type widening in the planned `packages/mcp`. pi's MCP layer drops `_meta` from resource listings and reads (`coding-agent/src/extensions/mcp/resources.ts:53-54,325`), omits `ui://`/`mcp-app` resources entirely ("pi does not render them", `docs/mcp.md:246`, `resources.ts:49`), and omits `_meta` from the tool result it hands to scripts (`tools.ts:7-9`). A cloudpid host must keep the raw `CallToolResult` (with `_meta`, `structuredContent`) and raw resource `_meta` for the View.

## 2. UI resource and CSP

**Facts**

- Declared CSP inputs (`_meta.ui.csp`): `connectDomains` → `connect-src`; `resourceDomains` → `script/style/img/font/media-src`; `frameDomains` → `frame-src`; `baseUriDomains` → `base-uri`. Empty/omitted = none (SPEC §UI Resource Format).
- Host MUST build CSP from the declared domains; MUST NOT allow undeclared domains (may restrict further); SHOULD log CSP configs. With no `ui.csp` it MUST use `default-src 'none'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; media-src 'self' data:; connect-src 'none'` (SPEC §Host Behavior).
- The reference CSP construction adds `object-src 'none'`, `frame-src 'none'` unless `frameDomains`, `base-uri 'self'` unless `baseUriDomains`, and `connect-src 'self' <connectDomains>` (SPEC §Security Implications). Note the stable text is internally inconsistent: the default block says `connect-src 'none'`, the construction example says `'self' …`. (Inference: in a `document.write`/inner-iframe load `'self'` is the sandbox origin, so `'none'` is the stricter, safer choice.)
- BASIC-HOST's real policy (`serve.ts`) is looser than the spec's: `default-src 'self' 'unsafe-inline'`, `script-src … 'unsafe-eval' blob: data:`, `worker-src 'self' blob:`, `base-uri 'none'`. It also **sanitises** domain entries, rejecting `;`, newlines, quotes and spaces, to stop CSP injection (`sanitizeCspDomains`). Any cloudpid builder of CSP strings from server-supplied origins needs the same validation.
- `permissions` (`camera`, `microphone`, `geolocation`, `clipboardWrite`) map to the inner iframe's `allow` attribute; hosts MAY honour them; apps must feature-detect (SPEC; `buildAllowAttribute`, `app-bridge.ts:189`). Host advertises what it granted in `hostCapabilities.sandbox.permissions/csp`.
- `domain` is "host-dependent" format, a stable per-view origin for CORS/OAuth allowlists. Claude requires `sha256(serverUrl)[:32] + ".claudemcpcontent.com"` and validates it (CLAUDE; `docs/csp-cors.md` in SDK). Optional; omitted → host default ("typically per-conversation", SPEC).
- `prefersBorder` is a hint (SPEC).
- Recommended extras: review UI templates at connection time, hash resources, warn on external domains, allow/blocklists (SPEC §Mitigations 3-4).

## 3. Sandbox: the double iframe

**Facts (SPEC §Sandbox proxy)**

- "If the Host is a web page, it MUST wrap the View and communicate with it through an intermediate Sandbox proxy." Host and Sandbox MUST have **different origins**; the proxy's iframe MUST have `allow-scripts` and `allow-same-origin`.
- Handshake: proxy → host `ui/notifications/sandbox-proxy-ready`; host → proxy `ui/notifications/sandbox-resource-ready { html, sandbox?, csp?, permissions? }`; proxy renders the raw HTML in an inner iframe under CSP (`frame-src 'none'`, `object-src 'none'`, `base-uri 'self'` unless declared). (The ready/resource-ready notifications are SHOULD in DRAFT, MUST in the stable text.)
- The proxy MUST relay every message between host and View except methods starting `ui/notifications/sandbox-`, including `ui/initialize`. The host MUST NOT send anything to the View before it receives `ui/notifications/initialized`. The proxy SHOULD NOT originate requests. The host MAY forward any View message not starting `ui/` to the MCP server, but SHOULD keep it spec-compliant and MAY block it or ask the user (SPEC items 6-8).
- Desktop/native hosts may render the View directly in an iframe (SPEC §Lifecycle step 2).

**BASIC-HOST implementation (the one reference host, `examples/basic-host`)**

- Two servers on two ports: host on `:8080`, sandbox on `:8081`, "ensur[ing] proper origin isolation" (`serve.ts`); the host server answers 404 for `/sandbox.html`.
- The sandbox page is loaded as `iframe.src = http://…:8081/sandbox.html?csp=<json>` with `sandbox="allow-scripts allow-same-origin allow-forms"`; the sandbox server **sets CSP as an HTTP header from the `?csp=` query param** because that is "tamper-proof unlike meta tags" and `Cache-Control: no-store` (`serve.ts`, `implementation.ts` `loadSandboxProxy`).
- `sandbox.ts` checks `window.self !== window.top`, requires and validates `document.referrer` against an allowlist (hard-coded to localhost; "consider updating the validation logic to allow your domain"), derives `EXPECTED_HOST_ORIGIN` from it, runs a **self-test that `window.top.alert()` throws a SecurityError**, creates the inner iframe (`allow-scripts allow-same-origin allow-forms`, plus `allow` from permissions), loads the HTML with `document.write` (srcdoc breaks some libs, e.g. CesiumJS), relays messages after **checking `event.origin`** each way, and posts to the host with an explicit target origin, not `*`.
- The host side connects `AppBridge` with `new PostMessageTransport(iframe.contentWindow, iframe.contentWindow)` ("pass … as BOTH target and source" so only that iframe is heard), sends `sendSandboxResourceReady`, waits for `oninitialized`, then `sendToolInput` and, when the call settles, `sendToolResult` or `sendToolCancelled`. Its `onopenlink` calls `window.open(url, "_blank", "noopener,noreferrer")` **without validating the URL scheme** (a policy decision the spec leaves to the host).
- Fact: the inner iframe is **same-origin with the proxy** (`allow-same-origin`), and all Views the proxy serves share the proxy's origin. Isolation between Views from different servers therefore needs a separate sandbox origin per server/view (Claude's hash subdomain is exactly this; CLAUDE, SPEC `domain`). One shared sandbox origin lets one View read another's `localStorage`/cookies for that origin (inference from same-origin policy; SPEC says only "typically per-conversation").
- Claude additionally asks the user to Allow / Always allow before it displays an app (CLAUDE).
- Other hosts known to implement MCP Apps: Claude, ChatGPT, VS Code Insiders/Stable, Goose, Postman, MCPJam, mcp-use, Alpic (ext-apps `README.md` §Supported Clients; EXT client matrix lists more). I read only Claude's and VS Code's first-party pages, not their sandbox code.

## 4. The host↔View protocol (JSON-RPC 2.0 over `postMessage`)

**Handshake (SPEC §Lifecycle, SDK `spec.types.ts:554-584`).**

1. View → `ui/initialize { appInfo, appCapabilities, protocolVersion }`. Host → `{ protocolVersion, hostInfo, hostCapabilities, hostContext }`. SDK constant `LATEST_PROTOCOL_VERSION = "2026-01-26"`.
2. View → `ui/notifications/initialized`. The host sends nothing before this (SPEC §Sandbox 6; the SDK enforces it, `app-bridge.ts:395-409`).
3. Host → `ui/notifications/tool-input-partial` (0..n, optional) then `ui/notifications/tool-input { arguments }` (**MUST**, at most once, required before `tool-result`), then `ui/notifications/tool-result` (the full `CallToolResult`) when the tool completes, or `ui/notifications/tool-cancelled { reason }` for any cancellation.
4. Teardown: host → `ui/resource-teardown { reason }` (a request) before it removes the iframe for _any_ reason, and SHOULD wait for the reply. DRAFT adds `ui/notifications/request-teardown` (View → host) for View-initiated close.

**View → host requests (host MUST implement, or answer with an error).**

| Method                                                   | Meaning                                          | Host behaviour in spec                                                                                                                        |
| -------------------------------------------------------- | ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `tools/call`                                             | Call a tool on the View's own server             | Only tools whose visibility includes `"app"`; host MAY block or ask the user; the tool result returns as the RPC reply                        |
| `resources/read`                                         | Read a resource of that server                   | Proxy                                                                                                                                         |
| `ping`                                                   | Health                                           | Reply                                                                                                                                         |
| `notifications/message`                                  | Logging to host                                  | Record for debugging/telemetry                                                                                                                |
| `ui/open-link {url}`                                     | Open an external URL                             | SHOULD open in the user's browser/new tab; may deny (`-32000`)                                                                                |
| `ui/message {role:"user", content}`                      | Add a message to the chat                        | SHOULD add to the conversation with that role; MAY ask consent                                                                                |
| `ui/update-model-context {content?, structuredContent?}` | Replace the model-visible context from this View | SHOULD give to the model on future turns; each call **overwrites** the previous; MAY defer to the next user message, dedupe, show to the user |
| `ui/request-display-mode {mode}`                         | `inline`/`fullscreen`/`pip`                      | Reply with the resulting mode; MUST NOT switch to a mode the View did not declare in `appCapabilities.availableDisplayModes`                  |
| `ui/notifications/size-changed {width,height}`           | View's content size                              | See §5                                                                                                                                        |

DRAFT (post-stable, not yet versioned) adds: `ui/download-file` (host mediates downloads because the sandbox lacks `allow-downloads`; confirm dialog, sanitise names), `sampling/createMessage` from the View (gated on `hostCapabilities.sampling`), `tools/list` and `tools/call` **host → View** (app-registered tools, gated on `appCapabilities.tools`), `hostCapabilities.updateModelContext`/`message` content-modality objects, `experimental` keyed by id.

**Host capabilities object (`HostCapabilities`).** `openLinks`, `serverTools{listChanged}`, `serverResources{listChanged}`, `logging`, `sandbox{permissions,csp}`; DRAFT adds `downloadFile`, `updateModelContext`, `message`, `sampling`. A host advertises only what it implements; SDK `AppBridge` wires `serverTools`/`serverResources` from a real `Client` if one is passed. **`AppBridge`'s client argument may be `null`**, in which case the host supplies `oncalltool`, `onreadresource`, `onlistresources`, … handlers itself (SDK `app-bridge.ts:530-535`, doc comment ~503). That is the hook for forwarding to a remote MCP object.

**`hostContext` (SHOULD be provided).** `toolInfo{id,tool}`, `theme`, `styles.variables` (a fixed set of ~85 CSS custom properties, e.g. `--color-background-primary`, `--font-sans`, spacing intentionally excluded; use `light-dark()`), `styles.css.fonts`, `displayMode`, `availableDisplayModes`, `containerDimensions`, `locale`, `timeZone`, `userAgent`, `platform` (`web|desktop|mobile`), `deviceCapabilities{touch,hover}`, `safeAreaInsets`. Changes are pushed with `ui/notifications/host-context-changed` (partial; View merges). Views must carry their own fallbacks.

**Data contract.** `content` is the model-facing text; `structuredContent` is "optimized for UI rendering (not added to model context)"; `_meta` is not for the model (SPEC §Data Passing best practices).

## 5. Sizing

**Facts (SPEC §Container Dimensions).** `containerDimensions` is, independently per axis, **fixed** (`height`/`width`: host controls, View fills), **flexible** (`maxHeight`/`maxWidth`: View sizes itself up to the max) or **unbounded** (omitted). With a flexible axis the host MUST listen to `ui/notifications/size-changed` and resize the iframe; the SDK `App` sends it automatically from a `ResizeObserver` (debounced) when `autoResize` is on. The host SHOULD notify the View when container size changes (`host-context-changed`). BASIC-HOST gives `{ maxHeight: 6000 }` plus a measured `width`, uses `min-width: min(Wpx, 100%)`, accounts for `box-sizing: border-box` borders to avoid a resize feedback loop, and animates height changes 300 ms. Display modes (`inline` default; `fullscreen`, `pip`) are negotiated as above.

## 6. What this asks of a host, as a checklist

1. Advertise `capabilities.extensions["io.modelcontextprotocol/ui"].mimeTypes` (or the per-request `_meta` form on `2026-07-28`+) on every MCP connection; handle servers returning UI tools only when advertised.
2. From `tools/list` keep each tool's raw `_meta.ui`; hide `["app"]`-only tools from the model and enforce `"app"` on View-initiated calls (server-scoped).
3. On a UI-tool call: `resources/read` the `ui://` URI (prefetch/cache by URI; validate mime, single content, size), read `_meta.ui` from content item then listing, build CSP and `allow`.
4. Run the double-iframe sandbox on a distinct origin, CSP delivered as an HTTP header, origin checks both ways, explicit `postMessage` target origins, referrer/origin allowlist, no host secrets on that origin.
5. Serve `ui/initialize` with host info, capabilities and context; gate all other traffic on `initialized`; send `tool-input`, then `tool-result`/`tool-cancelled`; send `ui/resource-teardown` before removal.
6. Proxy `tools/call` / `resources/read` (and `ping`, logging); implement `ui/message`, `ui/update-model-context`, `ui/open-link` (validate scheme), `ui/request-display-mode`, size changes; optionally partial input, theming variables, `host-context-changed`.
7. Log View-initiated RPCs (SPEC §Mitigations 2) and CSP configs; limit resource use.

## 7. Constraints for a UI behind Cloudflare Access

Cloudpid facts first: the main Worker serves `apps/web` as static assets and sits behind one Access application with an allow-owner policy; `prod` on `pi.ianpascoe.dev`, other stages on `workers.dev` (cloudpid `operations.md` §Access; `client-and-protocol.md`: web app static assets, manifest fetched with `crossorigin="use-credentials"` because "Access guards it"). The repo sets no CSP, `X-Frame-Options` or `frame-ancestors` today (grep of `apps/`, `packages/`, `infra/` found none, so no existing header conflicts with adding `frame-src`).

**Facts from Cloudflare**

- Access checks every request for a valid `CF_Authorization` cookie, one **application token per protected domain** plus a team-domain session token (CF-COOKIE). Application-cookie `SameSite` is admin-chosen, default None; HttpOnly default on; Binding Cookie optional.
- A multi-domain Access application can issue cookies for each domain; "Eager redirect cookie" preselects them but "wildcarded subdomains … cannot receive preemptive cookies" (CF-COOKIE).
- Browsers may block third-party cookies "including the `CF_Authorization` cookie" in private modes; cross-origin XHR to Access needs a valid cookie; **preflighted CORS requests (`OPTIONS`) get 403** from Access because browsers send no cookies on them, unless "Bypass options requests" or Access-answered preflight is configured (CF-COOKIE, CF-CORS).
- **Bypass** disables Access enforcement for matching traffic, and is "not recommended" for internal apps; requests are not logged (CF-POLICY). Access can also cover a path or a hostname, including `workers.dev` and custom domains, or all Workers in the account (CF-WORKERS).
- The Access application settings API has `allow_iframe` ("Enables loading application content in an iFrame", CF-API). The public docs I could reach do not say what Access does for framing when it is off (see unknowns).
- Workers routes accept `*.example.com/*` (CF-WORKERS routes) and static-asset `_headers` rules apply only to asset responses, not to responses a Worker generates (CF-WORKERS headers).

**Implications (inference, the part to verify)**

1. **The sandbox needs its own origin, so it needs its own hostname**, and every hostname Access covers needs a cookie. Three shapes, none verified in cloudpid:
   a. _A public (non-Access) sandbox hostname_ serving only a static, secretless proxy page. Nothing on it can authenticate to cloudpid, because all View traffic goes via `postMessage` to the host page, then over the Session socket (which already carries the owner's Access cookie). A Bypass or "no Access application" for that hostname exposes only code that is public in the ext-apps repo. The CSP-per-load, however, must be computed by a Worker on that hostname, so it is not a plain static asset. Constraint to note: it must not be a hostname an "all Workers" Access application covers (CF-WORKERS).
   b. _A same-site sibling subdomain inside the same Access application_ (e.g. `sbx.pi.ianpascoe.dev` beside `pi.ianpascoe.dev`; same site, different origin). The iframe request carries that domain's own `CF_Authorization`, which Access must have issued for it (eager redirect, not for wildcards). Fine on `prod`, awkward on `workers.dev` stages where the sibling would be a different site (`workers.dev` is a public suffix), so the iframe load becomes third-party and Access cookies may be dropped (Safari/Firefox, private windows), and Access would redirect the framed navigation to its login page.
   c. _No separate origin_: the spec requires different origins and `allow-same-origin`; an opaque-origin `sandbox="allow-scripts"` iframe with `srcdoc` would run with a `null` origin and only a `<meta>` CSP. This deviates from the MUSTs and weakens the CSP (meta, not header). It is an option to decide, not a conforming design.
2. **Per-server View isolation.** A wildcard sandbox host (`*.sandbox.<domain>`) allows one origin per MCP server (the Claude pattern). Workers routes can match `*.sandbox.example.com/*`; wildcard Access apps exist, but wildcard hostnames cannot be preselected with cookies, which favours option a (no Access on the sandbox zone) for per-server origins. Cost: DNS/route work per stage (preview stages are `workers.dev` with no wildcard).
3. **CSP must be per load, from an HTTP header** (BASIC-HOST rationale: the inner document is same-origin with the proxy, so it can edit a `<meta>` in the parent but not an HTTP header). Static `_headers` cannot vary by the View's `csp`, so the sandbox hostname needs Worker code (CF-WORKERS headers: headers on Worker-generated responses are set in the Worker). The `?csp=` JSON must be validated against `;`, quotes, spaces and newlines (BASIC-HOST). The host page needs `frame-src https://<sandbox>` if cloudpid later adds a CSP.
4. **Views must not reach the Access origin.** A View whose `connectDomains` names the cloudpid origin would get a 403 on preflight and no cookie. The spec's model has Views reach only declared third parties and the host through `postMessage`, so nothing in the protocol needs the View to call cloudpid directly. A host policy that refuses `connectDomains` entries for its own origins is a cheap guard (inference).
5. **Everything the View does goes through the owner's authenticated channel.** `tools/call`, `resources/read`, `ui/message` and `ui/update-model-context` become socket commands from the browser to the Session; the Access cookie authenticates the socket, not the View. The proxy page therefore holds no Access token and no cloudpid credential. Do not put Access JWTs, Session IDs or secrets in the sandbox URL or `hostContext` (the sandbox origin sees `document.referrer` and any query string).
6. **No Access service token is involved on this side.** Streamable HTTP servers are reached from the DO, not the browser, so the Access/CORS preflight issue (CF-CORS) does not hit MCP traffic. It only bites if a View calls an Access-protected API cross-origin.
7. **Service worker/PWA:** the app's service worker (`apps/web/public/sw.js`, registered from `apps/web/src/push.ts:330`) exists only for Web Push and caches nothing; its scope is its own origin, so it does not see a cross-origin sandbox iframe's loads (inference from service-worker scoping). Nothing in it needs changing for MCP Apps.

## 8. Implications for cloudpid's design (not decisions)

- **Where the MCP client lives vs where the View lives.** The MCP object is per-Environment in a DO (map Notes); the View is in a browser tab. `AppBridge(null, …)` with `oncalltool`/`onreadresource` handlers fits: browser-side bridge, DO-side MCP. Reads (`resources/read` for the HTML) can also be done DO-side and the HTML sent over the socket, which keeps `_meta.ui.csp` intact and never lets the browser talk to MCP servers.
- **Durability.** A View is ephemeral browser state, the tool call is durable. On reload, reconnect or a second device the host must replay `tool-input` and `tool-result` from stored data; a View's only persistence channel back is `ui/update-model-context` (overwrite semantics, per View) and tool calls. Whether replays re-run `tools/call` or reuse the stored result is open.
- **Raw results.** The transcript/session store needs the unsanitised `CallToolResult` (incl. `_meta`, `structuredContent`) and `_meta.ui` resource metadata; pi's adapter currently drops `_meta` (see §1).
- **Advertising.** The extension capability is per connection, but rendering is per attached client. A headless Run (no browser attached, e.g. a scheduled or pushed one) cannot render, yet a server that sees the capability returns UI-variant tools. Options: always advertise and render on next attach, or advertise only per attached client (needs a reconnect/`tools/list` refresh). Text fallbacks make either safe.
- **Prompt injection.** `ui/message` and `ui/update-model-context` are inputs from server-supplied HTML into the model's context. The spec allows consent (`ui/message` MAY, context MAY show the user); an untrusted-source labelling and an owner gate (first-time per server, like Claude's Allow/Always allow) are policy choices cloudpid will want to make, alongside the map's Approval model.
- **Tools and visibility.** `visibility: ["app"]` tools must never reach the model's tool list (SPEC: host MUST NOT include them), while a View must still be able to call them. The map defines exposure `hidden` as "unreachable"; app-visibility is a separate channel from `toolExposure`, so how the two compose (does `hidden` also block a View's call?) is a map decision (inference).
- **Stdio servers in the Container.** A View's refresh button wakes the Container through `tools/call`; the map's "server never keeps the Container awake" rule means View-driven polling has idle-stop/cost consequences (inference).
- **Spec movement.** DRAFT already adds sampling from Views, host→View tool calls, downloads, listing-level `_meta.ui`, view-initiated teardown; the map's "from 2025-11-25 to the present" scope and MCP `2026-07-28` per-request capabilities (EXT) both touch the negotiation step.
- **Interop target.** `@modelcontextprotocol/ext-apps` is MIT, Node 20+, and peer-depends on `@modelcontextprotocol/client@^2` (its `Protocol` base class), `core`, and `zod@^4.2` (SDK `package.json`, `docs/migrate-to-2.md`); the host entry point is `@modelcontextprotocol/ext-apps/app-bridge`. Using it in the browser brings MCP SDK 2.x classes next to cloudpid's own pi-mcp client (inference: they are independent codebases). A small bridge written against the wire types (`src/spec.types.ts`, `schema.json`) is the alternative; `docs/migrate-to-2.md` says the `ui/*` messages are byte-identical between ext-apps 1.x and 2.x.
