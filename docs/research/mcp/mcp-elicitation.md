## 1. Form mode ([11-25] and [07-28])

### Request params

[11-25] "All elicitation requests **MUST** include the following parameters: `mode` (`form`, `url`; "Optional for form mode (defaults to `"form"` if omitted)"), `message` ("A human-readable message explaining why the interaction is needed")." Form mode additionally requires `requestedSchema` ("A JSON Schema defining the structure of the expected response"). "Clients **MUST** treat requests without a `mode` field as form mode." Identical text in [07-28]. [06-18] has no `mode` at all (`message` + `requestedSchema`).

[07-28] difference: the request is no longer a JSON-RPC request; it is an entry in `InputRequiredResult.inputRequests` (`{ method: "elicitation/create", params: {...} }`) and the answer is an `ElicitResult` in `inputResponses` (see §5).

### Restricted schema ("flat objects with primitive properties only")

Authoritative TS: [11-25 schema.ts] `ElicitRequestFormParams.requestedSchema = { $schema?: string; type: "object"; properties: {[k]: PrimitiveSchemaDefinition}; required?: string[] }`; `PrimitiveSchemaDefinition = StringSchema | NumberSchema | BooleanSchema | EnumSchema`. [07-28 schema.ts] is the same shape (minus `TaskAugmentedRequestParams`).

| Type                                  | Keywords in schema.ts (both [11-25], [07-28])                                                                                      |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| string                                | `title, description, minLength, maxLength, format ("email"\|"uri"\|"date"\|"date-time"), default`                                  |
| number / integer                      | `title, description, minimum, maximum, default`                                                                                    |
| boolean                               | `title, description, default`                                                                                                      |
| single-select enum (untitled)         | `type:"string", enum:[…], default`                                                                                                 |
| single-select enum (titled, SEP-1330) | `type:"string", oneOf:[{const,title}], default`                                                                                    |
| multi-select enum (untitled)          | `type:"array", minItems, maxItems, items:{type:"string", enum:[…]}, default:string[]`                                              |
| multi-select enum (titled)            | `type:"array", minItems, maxItems, items:{anyOf:[{const,title}]}, default:string[]`                                                |
| legacy titled enum                    | `enum` + non-standard `enumNames`; "Use TitledSingleSelectEnumSchema instead. This interface will be removed in a future version." |

- Defaults: SEP-1034 / [11-25] changelog item 9 "Add support for default values in all primitive types (string, number, enum)". Spec: "Clients that support defaults SHOULD pre-populate form fields with these values."
- Enums: SEP-1330 / [11-25] changelog item 5 "Update `ElicitResult` and `EnumSchema` to use a more standards-based approach and support titled, untitled, single-select, and multi-select enums".
- Prose: "Note that complex nested structures, arrays of objects (beyond enums), and other advanced JSON Schema features are intentionally not supported to simplify client user experience."
- **Spec-text vs schema.ts mismatch:** the [11-25] prose example for String Schema includes `"pattern": "^[A-Za-z]+$"`, but `StringSchema` in [11-25] schema.ts has no `pattern`. [07-28] prose drops `pattern` from the example (schema.ts unchanged). Treat `pattern` as **unsupported** — a client should not rely on it, a server must not depend on it.
- `required` is the only object-level constraint; per-property `required` is not a thing. Nothing says how a client must render unrecognised keywords: **gap**.
- Result `content` type: `{ [key: string]: string | number | boolean | string[] }`.

### Result shape

[11-25 schema.ts] `ElicitResult { action: "accept"|"decline"|"cancel"; content?: {…} }` — "The submitted form data, only present when action is "accept" and mode was "form". … Omitted for out-of-band mode responses." Same in [07-28] (no longer extends `Result` with JSON-RPC envelope; it is the value in `inputResponses`).

### Decline vs cancel (verbatim, [11-25] and [07-28] identical)

1. **Accept** — "User explicitly approved and submitted with data"; form: `content` holds data matching the schema; URL: `content` omitted. Example: "User clicked 'Submit', 'OK', 'Confirm'".
2. **Decline** — "User explicitly declined the request"; `content` "typically omitted". Example: "User clicked 'Reject', 'Decline', 'No', etc."
3. **Cancel** — "User dismissed without making an explicit choice"; `content` "typically omitted". Example: "User closed the dialog, clicked outside, pressed Escape, browser failed to load, etc."

Server handling guidance: "**Decline**: Handle explicit decline (e.g., offer alternatives)"; "**Cancel**: Handle dismissal (e.g., prompt again later)". [07-28] adds under Error Handling: "Servers **SHOULD NOT** assume that elicitation requests will always succeed, and **MUST** handle cases where the user declines or cancels the elicitation, or where the client fails to process the request."

Implication: decline = durable "no" (don't re-ask the same thing); cancel = "not now / no answer" (may re-ask). Spec does not define what a **timeout / user-away** maps to — **gap**. Observed hosts: VS Code → `cancel` on dismissal (see §8); Goose → JSON-RPC internal error on its 300 s timeout; Claude Code (non-interactive) → tool call times out.

### Validation duties

- [11-25] and [07-28] "Form Mode Security": "Clients **SHOULD** validate all responses against the provided schema"; "Servers **SHOULD** validate received data matches the requested schema". [06-18]: "Both parties **SHOULD** validate elicitation content against the provided schema".
- Client may validate user input before sending ("Clients can use this schema to: 1. Generate appropriate input forms 2. Validate user input before sending 3. Provide better guidance"). Both duties are SHOULD, not MUST.
- Server must also treat `content` as untrusted user input (TS SDK docs say so explicitly, §7).

## 2. Security / sensitive data (exact normative text)

[11-25] and [07-28] "User Interaction Model" WARNING box (verbatim, identical in both):

> Servers **MUST NOT** use form mode elicitation to request sensitive information such as passwords, API keys, access tokens, or payment credentials
> Servers **MUST** use [URL mode] for interactions involving such sensitive information
> "Sensitive information" in this context refers to secrets and credentials that grant access or authorize transactions. General contact or profile information (such as a name, email address, or username) is not categorically prohibited; whether to request such data via form mode is at the discretion of the server and subject to the user's ability to review and decline.
> MCP clients **MUST**:
>
> - Provide UI that makes it clear which server is requesting information
> - Respect user privacy and provide clear decline and cancel options
> - For form mode, allow users to review and modify their responses before sending
> - For URL mode, clearly display the target domain/host and gather user consent before navigation to the target URL

"Form Mode Security" (both): "1. Servers **MUST NOT** request sensitive information (passwords, API keys, etc.) via form mode".

"Security Considerations" list:

- [11-25]: "1. Servers MUST bind elicitation requests to the client and user identity 2. Clients **MUST** provide clear indication of which server is requesting information 3. Clients **SHOULD** implement user approval controls 4. Clients **SHOULD** allow users to decline elicitation requests at any time 5. Clients **SHOULD** implement rate limiting 6. Clients **SHOULD** present elicitation requests in a way that makes it clear what information is being requested and why".
- [07-28]: same minus rate limiting (item 5 becomes the "what and why" SHOULD).
- [06-18] was weaker: "Applications **SHOULD**: Provide UI that makes it clear which server is requesting information; Allow users to review and modify …; Respect user privacy and provide clear decline and cancel options", and "Servers **MUST NOT** use elicitation to request sensitive information."

Notes / gaps:

- **"Never auto-accept" is not stated** for form mode. The nearest text is the MUST to "allow users to review and modify their responses before sending" and "Clients SHOULD implement user approval controls". For URL mode, auto-open is explicitly forbidden (§3). A host that answers elicitations programmatically (Claude Code `Elicitation` hook, §8) is a host-level policy choice, not spec-sanctioned or -prohibited.
- The spec gives the server-side MUST NOT but **no client-side detection duty**: clients are not told to refuse or mask fields that look like secrets (e.g. `password`, `api_key`, `format: password` doesn't exist in the format list). Masking `writeOnly`/password-style input is not specified.
- "Safe URL Handling" server rules apply to form mode too: "**SHOULD NOT** include URLs intended to be clickable in any field of a form mode elicitation request"; client: "**SHOULD NOT** render URLs as clickable in any field of an elicitation request, except for the `url` field in a URL elicitation request".
- Server must "bind elicitation requests to the client and user identity"; "Servers **MUST NOT** rely on client-provided user identification without server verification".
- [11-25] Statefulness: "State **MUST NOT** be associated with session IDs alone". [07-28]: "Elicitations do not require that the server maintain state about users with the multi round-trip requests mechanism. However, if state is stored, servers … **MUST** securely associate this state with individual users".

## 3. URL mode (SEP-1036; [11-25] and [07-28])

### Params

[11-25]: "URL mode elicitation requests **MUST** specify `mode: "url"`, a `message`, and include these additional parameters: `url` (The URL that the user should navigate to) and `elicitationId` (A unique identifier for the elicitation)." schema.ts: `elicitationId` "must be unique within the context of the server. The client MUST treat this ID as an opaque value." `url` is `@format uri`.
[07-28]: **`elicitationId` removed**; params are `mode:"url"`, `message`, `url` only. Changelog minor item 11: "Remove the `notifications/elicitation/complete` notification and the `elicitationId` field of URL mode elicitation requests, both introduced in `2025-11-25`. Under the Multi Round-Trip Requests pattern, the client learns the outcome of an out-of-band interaction by retrying the original request … Servers needing to correlate an elicitation across retries encode their own identifier in `requestState`."

### What "accept" means

[11-25]: "The response with `action: "accept"` indicates that the user has consented to the interaction. It does not mean that the interaction is complete. The interaction occurs out of band and the client is not aware of the outcome until and unless the server sends a notification indicating completion."
[07-28]: "…the client is not directly informed of the outcome. When the client retries the original request, the server determines from the echoed `requestState` (or its own stored state) whether the out-of-band interaction has completed, and either returns the final result or responds with another `InputRequiredResult`. Clients **SHOULD** provide manual controls that let the user retry or cancel the original request".
Cancel in URL mode includes "browser failed to load". `content` omitted on accept.

### Completion notification ([11-25] only)

`notifications/elicitation/complete { elicitationId }`. Servers "**MAY** send"; "**MUST** only send the notification to the client that initiated the elicitation request"; "**MUST** include the `elicitationId`". Clients "**MUST** ignore notifications referencing unknown or already-completed IDs"; "**MAY** wait for this notification to automatically retry requests that received a URLElicitationRequiredError"; "**SHOULD** still provide manual controls that let the user retry or cancel the original request … if the notification never arrives".

### `URLElicitationRequiredError` ([11-25] only)

"When a request cannot be processed until an elicitation is completed, the server **MAY** return a `URLElicitationRequiredError` (code `-32042`) … The server **MUST NOT** return this error except when URL mode elicitation is required. The error **MUST** include a list of elicitations that are required to complete before the original can be retried. Any elicitations returned in the error **MUST** be URL mode elicitations and have an `elicitationId` property."
Shape (schema.ts `URLElicitationRequiredError`): `error: { code: -32042, message, data: { elicitations: ElicitRequestURLParams[]; [k]: unknown } }`.
[07-28] schema.ts comment: codes "`-32042` (URL elicitation required, 2025-11-25 only)" stay reserved and are never reused; replaced by an `InputRequiredResult` containing a URL `ElicitRequest`.
Also [11-25] error handling: clients "**MUST** return … `-32602` (Invalid params)" when a server sends a mode not declared in client capabilities.

### Client duties (verbatim, [11-25] = [07-28])

"Clients implementing URL mode elicitation **MUST** handle URLs carefully to prevent users from unknowingly clicking malicious links. When handling URL mode elicitation requests, MCP clients:

1. **MUST NOT** automatically pre-fetch the URL or any of its metadata.
2. **MUST NOT** open the URL without explicit consent from the user.
3. **MUST** show the full URL to the user for examination before consent.
4. **MUST** open the URL provided by the server in a secure manner that does not enable the client or LLM to inspect the content or user inputs. For example, on iOS, SFSafariViewController is good, but WkWebView is not.
5. **SHOULD** highlight the domain of the URL to mitigate subdomain spoofing.
6. **SHOULD** have warnings for ambiguous/suspicious URIs (i.e., containing Punycode).
7. **SHOULD NOT** render URLs as clickable in any field of an elicitation request, except for the `url` field …"
   → Answer to "embedded webview?": yes, forbidden if it lets client/LLM inspect content/input; use the system browser / SFSafariViewController-class surface. (For a hosted headless agent: the _user's_ browser must open it, not a server-side/headless browser the agent controls.)

Server rules: "**MUST NOT** include sensitive information about the end-user, including credentials, personal[ly] identifiable information, etc., in the URL"; "**MUST NOT** provide a URL which is pre-authenticated to access a protected resource"; "**SHOULD** use HTTPS URLs for non-development environments". "The `url` parameter **MUST** contain a valid URL."

### Phishing / identity binding (verbatim)

"The MCP Server **MUST** verify the identity of the user who opens the URL before accepting information." … "the server **MUST** ensure that the user who started the elicitation request … is the same user who completes the authorization flow." … "the server **MUST** ensure that the mechanism to determine the user's identity is resilient to attacks where an attacker can modify the elicitation URL." Non-normative example: elicit to `https://mcp.example.com/connect?…` (server's own connect URL that checks session cookie `sub` against the MCP authorization server's `sub`) rather than the third-party authorize endpoint.
URL mode is "_not_ for authorizing the MCP client's access to the MCP server"; "MCP servers **MUST NOT** rely on URL mode elicitation to authorize users for themselves"; third-party credentials "**MUST NOT** transit through the MCP client"; "The MCP server **MUST NOT** transmit credentials obtained through URL mode elicitation to the MCP client."
Relevance for cloudpid: a single-user host has no multi-user phishing problem, but the identity-binding burden is on the _server_; the host's duties are the consent/display/secure-open items above.

## 4. Capability declaration

[11-25] verbatim: "Clients that support elicitation **MUST** declare the `elicitation` capability during initialization: `{"capabilities":{"elicitation":{"form":{},"url":{}}}}`. For backwards compatibility, an empty capabilities object is equivalent to declaring support for `form` mode only: `"elicitation": {}, // Equivalent to { "form": {} }`. Clients declaring the `elicitation` capability **MUST** support at least one mode (`form` or `url`). Servers **MUST NOT** send elicitation requests with modes that are not supported by the client." SEP-1036: "Previously, clients only declared `"elicitation": {}` without mode specification."; "Servers SHOULD check client capabilities before sending mode-specific requests"; "Clients MAY initially support only form mode". schema.ts [11-25]: `elicitation?: { form?: object; url?: object }`; also `tasks.requests.elicitation.create` for task-augmented elicitation.
[06-18]: bare `elicitation: {}` (form only, no modes).

[07-28] (no `initialize`): "Clients that support elicitation **MUST** declare the `elicitation` capability in `_meta.io.modelcontextprotocol/clientCapabilities` on each request" with the same `{form:{},url:{}}` / `{}`≡`{form:{}}` rules. Basic page: `io.modelcontextprotocol/clientCapabilities` is **required** on every request ("A request missing any required field is malformed … `-32602` … HTTP `400`"); "A server **MUST NOT** rely on capabilities the client has not declared. If processing a request requires a capability the client did not include …, the server **MUST** return a `MissingRequiredClientCapabilityError` (`-32021`) whose `data.requiredCapabilities` lists the missing capabilities." MRTR: "Servers **MUST NOT** send an `inputRequests` that the client has not declared support for in its capabilities."
Changelog (renumbering): `MissingRequiredClientCapability` was `-32003`, now `-32021`; `-32020…-32099` reserved for the spec.

**Deprecation status:** Elicitation is **not** deprecated in [07-28]. The Deprecated registry lists Roots, Sampling, Logging (SEP-2577), Dynamic Client Registration, `includeContext: thisServer/allServers`, HTTP+SSE. SEP-2577 does not mention elicitation. Elicitation instead becomes the _primary_ surviving server→client interaction (MRTR vocabulary: `ElicitRequest`, `CreateMessageRequest` (deprecated), `ListRootsRequest` (deprecated)).

## 5. [07-28] MRTR (SEP-2322)

Source: MRTR page [07-28]. Banner: "Servers **MUST** send server-to-client requests (such as `roots/list`, `sampling/createMessage`, or `elicitation/create`) using the MRTR pattern. The previous pattern of server-initiated requests is no longer supported. This is a breaking change."

Wire shape:

- Initial request (`tools/call`, `prompts/get`, or `resources/read` — "Servers **MUST NOT** send `InputRequiredResult` responses on any other client requests"; the table lists exactly those three with "Yes") returns a result with `"resultType": "input_required"`, `inputRequests` (map: server-chosen key → `{method:"elicitation/create", params:{mode, message, requestedSchema | url}}`), and/or `requestState` (opaque string). "Servers **MUST** include at least one of `inputRequests` or `requestState` in every `InputRequiredResult`."
- Retry: a new request (JSON-RPC `id` "**MUST** be different") with the original params plus `inputResponses` (same keys → `ElicitResult` `{action, content?}`) and echoed `requestState`. schema.ts `InputResponseRequestParams { inputResponses?: InputResponses; requestState?: string }`.
- Client duties: MUST construct requested inputs before retry if `inputRequests` present; "MUST echo back the exact value" of `requestState`; "MUST NOT inspect, parse, modify"; if none was given "MUST NOT include one"; fields "affect only the client's retry of the original request".
- Server duties on `requestState`: "MUST treat `requestState` as an attacker-controlled input"; protect integrity (HMAC/AEAD) when it influences authz/logic; "**SHOULD** include … inside the integrity-protected payload": authenticated principal, "a short expiry (TTL)", an identifier for the originating request; TTL/principal binding "do not by themselves guarantee single-use" (enforce one-shot server-side if needed). **No numeric TTL is specified** — gap.
- "Servers **MUST NOT** assume that clients will fulfill the `inputRequests` or retry the original request. Servers **MAY** choose to return an `InputRequiredResult` on multiple attempts…". If client sends incomplete `inputResponses` the server "**SHOULD** respond with a new `InputRequiredResult` requesting the missing information again, rather than returning an error."
- Elicitation during `resources/read` / `prompts/get`: **yes** in [07-28] (MRTR table). In [11-25] the elicitation page says only that requests "occur _nested_ inside other MCP server features" (no method list) — any in-flight request worked in practice, and `-32042` could be returned by any request.

URL mode completion without notification: client retries (manually or after user action) → server checks `requestState`/its own stored state. Spec text: "Clients **SHOULD** provide manual controls that let the user retry or cancel the original request". Server may "block until the request is fulfilled" per [07-28] flow diagram note ("It may need to block until the request is fulfilled."). So the host cannot learn "done" from the protocol; it must offer a "I've finished — retry" affordance (or retry-on-focus heuristics — an implementation choice, spec is silent).

Tasks extension (`io.modelcontextprotocol/tasks`, SEP-2663; moved out of core in [07-28]): a task in `input_required` status exposes an `inputRequests` map in `tasks/get`; "The client responds via `tasks/update` — no second connection or unsolicited …". This is the spec's long-wait path for elicitation that must outlive a single HTTP request.

## 6. Timeouts and cancellation

- [11-25] Lifecycle > Timeouts (verbatim): "Implementations **SHOULD** establish timeouts for all sent requests, to prevent hung connections and resource exhaustion. When the request has not received a success or error response within the timeout period, the sender **SHOULD** issue a cancellation notification for that request and stop waiting for a response. SDKs and other middleware **SHOULD** allow these timeouts to be configured on a per-request basis. Implementations **MAY** choose to reset the timeout clock when receiving a progress notification corresponding to the request, as this implies that work is actually happening. However, implementations **SHOULD** always enforce a maximum timeout, regardless of progress notifications …". Same section in [06-18].
- The spec **gives no number** for how long an elicitation may remain pending, and nothing elicitation-specific about timeouts: **gap**. Nothing says a client must answer within N seconds; nothing says a server must wait.
- `notifications/cancelled { requestId, reason? }` ([11-25]): MUST reference in-progress requests issued in the same direction; receivers "SHOULD stop processing … not send a response"; receivers MAY ignore unknown/completed requests; senders "SHOULD ignore any response … that arrives afterward". A server that times out waiting on `elicitation/create` therefore cancels the _server→client_ request; the client should dismiss the dialog (host-level behaviour not specified).
- [07-28] cancellation page: on Streamable HTTP "Closing the SSE response stream is the cancellation signal. The server **MUST** treat a client disconnect as cancellation of that request"; on stdio the client "**MUST** send a `notifications/cancelled`". Servers MUST NOT send `notifications/cancelled` except to tear down `subscriptions/listen`. Timeouts text now says the sender "SHOULD cancel the request" (close stream / send notification). Progress-resets-timeout wording unchanged (MAY reset; SHOULD keep a maximum).
- **Why [07-28] fixes the "human answers hours later" problem:** the original request ends the moment the server returns `input_required`; the user's think time sits _between_ two independent requests, outside any request timeout. The only server-side clock left is the `requestState` TTL the server chooses (and any server-side session/state it keeps).
- In the [11-25] push model the server holds the originating `tools/call` open while it waits, so human latency is bounded by the _server's_ outbound-request timeout and the _client's_ `tools/call` timeout (both default 60 s in the TS SDK — see §7).

## 7. TypeScript SDK v2 (2.4.0)

Docs read from the repo tag (paths under `docs/`): `clients/server-requests.md`, `servers/elicitation.md`, `servers/input-required.md`, `protocol-versions.md`, `migration/support-2026-07-28.md`. Code: `packages/client/src/client/client.ts`, `packages/server/src/server/server.ts`, `packages/core-internal/src/{shared,types}/…`.

### Client side

- Declare capability in constructor: `new Client(info, { capabilities: { elicitation: { form: {}, url: {} } } })`. "An empty `elicitation: {}` declares form mode only — `url` must be listed explicitly. `getSupportedElicitationModes`, exported from `@modelcontextprotocol/client`, turns any `elicitation` capability object into `{ supportsFormMode, supportsUrlMode }`."
- Handler: `client.setRequestHandler('elicitation/create', async (request, ctx) => …)`. Docs: "Branch on `request.params.mode`: `'url'` carries a URL to open in the user's browser, and anything else is a form your client builds from `request.params.requestedSchema`" — "branch on `'url'` and treat everything else as a form, never on `mode === 'form'`". Return `{ action:'accept', content }` / `{ action:'decline' }` / `{ action:'cancel' }`. `ctx.mcpReq.signal` is aborted if the server cancels.
- The same handler serves both eras: on [07-28] connections the client "fulfils the embedded requests through the same handlers registered with `setRequestHandler('elicitation/create' | …)` and retries (fresh request id, `inputResponses`, byte-exact `requestState` echo) up to `inputRequired.maxRounds` rounds (default 10)". `ClientOptions.inputRequired = { maxRounds, autoFulfill }`; `autoFulfill: false` → call rejects on first `input_required` and "the round trips are yours to drive" (`allowInputRequired: true` + `withInputRequired()`); exhausting rounds → `SdkError(InputRequiredRoundsExceeded)` (`INPUT_REQUIRED_ROUNDS_EXCEEDED`).
- Era choice: default is 2025 `initialize`; opt in with `versionNegotiation: { mode: 'auto' | { pin: '2026-07-28' } }` ([protocol-versions.md](https://github.com/modelcontextprotocol/typescript-sdk/blob/v2.4.0/docs/protocol-versions.md)).
- Built-in client-side validation (`_wrapHandler`, client.ts): validates the _request_ and the handler's _result_ against the era's wire schema (`ElicitResult` shape), rejects with `-32602` if the mode isn't declared ("Client does not support form-mode / URL-mode elicitation requests"). It does **not** validate `content` against `requestedSchema` on the client. Optional `elicitation: { form: { applyDefaults: true } }` ("an SDK flag, not a protocol capability") fills `default`s for fields the user left out before the accept is returned.
- Notification handler for 2025-era: `client.setNotificationHandler('notifications/elicitation/complete', …)`.
- `UrlElicitationRequiredError` (exported; `core-internal/src/types/errors.ts`): `class UrlElicitationRequiredError extends ProtocolError` with code `ProtocolErrorCode.UrlElicitationRequired = -32042`, `elicitations: ElicitRequestURLParams[]` getter; `ProtocolError.fromError` rebuilds it from `-32042` + `data.elicitations`. Default message `URL elicitation(s) required`. It is a 2025-era construct: on [07-28] throwing it from a handler fails with an error steering to `inputRequired.elicitUrl(...)`; "the `-32042` error never reaches the 2026-07-28 wire".
- Request timeout defaults: `DEFAULT_REQUEST_TIMEOUT_MSEC = 60_000` (`core-internal/src/shared/protocol.ts`). `RequestOptions`: `timeout`, `resetTimeoutOnProgress` (default `false`), `maxTotalTimeout` (default none). For auto-fulfilled MRTR, `timeout` "applies to every wire leg unchanged" and `maxTotalTimeout` "bounds the WHOLE flow: every retry leg is given only the time remaining" — i.e. user think-time in the handler counts only against `maxTotalTimeout`, if set.

### Server side

- 2025 era: `ctx.mcpReq.elicitInput(params, options?)` (also `server.elicitInput`). Throws `SdkError(CapabilityNotSupported, 'Client does not support form|url elicitation.')` before sending if the capability is missing (form requires `elicitation.form` for the public API; the legacy shim treats bare `{}` as form). For form mode it validates accepted `content` against `requestedSchema` using `ServerOptions.jsonSchemaValidator` — default "Runtime-selected validator (AJV-backed on Node.js, `@cfworker/json-schema`-backed on browser/workerd runtimes)" — and throws `ProtocolError(InvalidParams, 'Elicitation response content does not match requested schema: …')` on mismatch. URL mode: no content to validate.
- Timeouts (docs, `servers/elicitation.md`): "Raise the request `timeout` too — the default is 60 seconds, and a person is on the other end of this one — and forward `ctx.mcpReq.signal` so a cancelled tool call also cancels the parked elicitation." Example uses `{ timeout: 10 * 60_000, signal: ctx.mcpReq.signal }`, and "The host's own `tools/call` has the same 60-second default, so the caller raises it as well" (`callTool(..., { timeout: 10*60_000 })`).
- `server.server.createElicitationCompletionNotifier(elicitationId, { relatedRequestId })` sends `notifications/elicitation/complete` (2025-era only; "no `elicitationId` and no completion signal" on 2026-07-28; sending it there is rejected).
- 2026 era: `ctx.mcpReq.elicitInput` "throws — a handler returns the request instead". Handler returns `inputRequired({ inputRequests: { key: inputRequired.elicit({message, requestedSchema}) | inputRequired.elicitUrl({message, url}) }, requestState? })`; on re-entry reads `ctx.mcpReq.inputResponses` via `acceptedContent(responses, key, zodSchema)` (validates untrusted answer; returns `undefined` for missing/declined/cancelled alike) or `inputResponse(...)` (discriminated view: `missing | elicit | sampling | roots`). `requestedSchema` may be a Standard Schema (zod): converted to the restricted wire grammar; `.regex()` patterns / nested objects throw `TypeError` at build time. Missing client capability → `-32021` before wire. `createRequestStateCodec({ key, ttlSeconds })` gives HMAC-SHA256 `{mint, verify}`; "The codec is signed, not encrypted"; tampered/expired → `-32602 Invalid or expired requestState`. A default-on _legacy shim_ serves the same `inputRequired` handler to 2025-era connections by issuing real `elicitation/create` requests (`ServerOptions.inputRequired.legacyShim: false` to disable); the shim passes accepted content through _unvalidated_ ("handlers validate via the schema-aware `acceptedContent` overload and can re-ask").
- SDK docs on secrets: "Never collect sensitive information — passwords, API keys, payment details — through form elicitation. Use URL mode or an out-of-band flow instead." and "Form answers travel back through the client and land in the model's context like any other tool result."
- Not found in the SDK: any built-in host UI, URL-opening, or secret-field detection; those are the host's job.

## 10. Decision-relevant takeaways for cloudpid (a hosted MCP client/host)

1. Two eras coexist: implement both [11-25] push (`elicitation/create` request) and [07-28] MRTR (`input_required`); the TS SDK 2.4.0 `Client` handler is era-agnostic (same `setRequestHandler('elicitation/create')`).
2. Declare `elicitation: { form: {}, url: {} }` only if URL-mode consent + system-browser opening are really implemented; otherwise `{ form: {} }` (explicit) — a bare `{}` also means form-only.
3. Under [11-25] the server holds its `tools/call` open and the SDK default 60 s timeout (both directions) will kill a slow human; under [07-28] the wait is free (between legs) but `maxTotalTimeout` and `requestState` TTL (server-chosen) apply.
4. Decline = explicit refusal; cancel = dismissed/no choice. The spec has no "timed out / user away" outcome — pick and document one (cancel is closest; Goose returns an error).
5. URL mode: accept = consent to open, not completion. [11-25] may send `notifications/elicitation/complete`; [07-28] has no completion signal, so the host needs a manual "retry" control.
6. A hosted agent must open URLs on the **user's** device/browser, show full URL + highlighted domain first, never pre-fetch, never open in an agent-controlled/headless browser (client/LLM must not be able to inspect the page).
7. Form mode: flat primitives only; honour `default`; support titled and multi-select enums; ignore/never trust `pattern`; validate user input against the schema before replying (SHOULD) — the TS client SDK does not do this for you.
8. Spec forbids servers from asking for secrets in forms but doesn't require clients to detect them; hosts in the wild don't refuse. Consider a host-side policy (surface "server X asks for a password-like field" warning) — an extension beyond the spec.
9. Never auto-accept is not a spec statement for form mode, but users must be able to review/modify before send (MUST) and decline at any time (SHOULD). Programmatic answering (as Claude Code's hooks allow) is a host policy decision.
10. Must show which server is asking (MUST in [11-25] and [07-28]); rate limiting is SHOULD in [11-25] only.
11. Elicitation is not deprecated in [07-28]; roots/sampling/logging are (≥12-month window, earliest removal "First revision released on or after 2027-07-28").
