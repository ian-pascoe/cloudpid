## 1. MCP `2025-11-25` sampling

Primary sources: [client/sampling page](https://modelcontextprotocol.io/specification/2025-11-25/client/sampling.md), schema `S25` (`CreateMessageRequestParams` at [S25:1578](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/0aab7058fe6471f3d7b0301e13965f10ad9cb198/schema/2025-11-25/schema.ts#L1578)).

### 1.1 Capability declaration

- A client that supports sampling **MUST** declare `sampling` at `initialize`. Sub-capabilities: `sampling.tools: {}` (tool use via `tools`/`toolChoice`) and `sampling.context: {}` (`includeContext` values `thisServer`/`allServers`). **[V]** sampling page › Capabilities; [S25:327-338](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/0aab7058fe6471f3d7b0301e13965f10ad9cb198/schema/2025-11-25/schema.ts#L327).
- `sampling.context` is labelled "soft-deprecated". Servers **SHOULD** avoid `thisServer`/`allServers` and **SHOULD NOT** use them unless the client declares `sampling.context`. **[V]** page › Capabilities note; S25:1595.
- Clients **MUST** declare `sampling.tools` to receive tool-enabled requests; servers **MUST NOT** send tool-enabled requests to a client that has not. **[V]** page › Tools in Sampling.
- Task-augmented sampling exists in this revision only: `ClientCapabilities.tasks.requests.sampling.createMessage`, and `CreateMessageRequestParams extends TaskAugmentedRequestParams` (a `task` field in params). **[V]** S25:360-368, S25:1578. (Removed from the core in `2026-07-28`; see §2.)

### 1.3 Result

`CreateMessageResult extends Result, SamplingMessage` (S25:1656-1675):

- `role`: `"user" | "assistant"` (in practice `assistant`).
- `content`: one block or an **array** of blocks. Blocks: text, image, audio, `tool_use` (and, by the type, `tool_result`).
- `model`: string, the name of the model that generated the message (required).
- `stopReason`: optional open string. Standard values: `"endTurn"`, `"stopSequence"`, `"maxTokens"`, `"toolUse"`; "an open string to allow for provider-specific stop reasons".
- `_meta`: optional. Clients **SHOULD** preserve `_meta` on `tool_use`/`tool_result` blocks when they are included in later requests (cache optimisation). S25:1855-1858, S25:1902-1905.

### 1.4 Content types and limits

- Allowed in messages and results: `text` (`text`, `annotations?`, `_meta?`), `image` (`data` base64, `mimeType`), `audio` (`data` base64, `mimeType`), plus `tool_use` and `tool_result`. **[V]** S25:1693-1698, S25:1748-1832; page › Data Types.
- **No size limits, no MIME allow-list, no count limits** are specified. The schema says only "Different providers may support different image types" / "audio types". **[V]** (searched the page and schema for limits; only `maxTokens` and iteration limits appear). The server-side limit on what to send is thus implicit in the model/provider.
- A `tool_result` block carries `content: ContentBlock[]` ("same format as `CallToolResult.content`: text, images, audio, resource links, and embedded resources"), optional `structuredContent`, `isError`, `_meta`. **[V]** S25:1868-1907. So tool results can contain `resource_link` and embedded resources, which are not valid top-level sampling content blocks.

### 1.5 Sampling with tools: who does what

- **The client never executes the tools.** The client forwards `tools` to its model; when the model wants a tool, the client returns `stopReason: "toolUse"` with `tool_use` blocks. **The server executes the tools and loops**: it sends a new `sampling/createMessage` whose `messages` hold the history plus a user message of `tool_result` blocks. The server may cap iterations, and may send `toolChoice: {mode:"none"}` on the last iteration to force a final text answer. **[V]** page › Multi-turn Tool Loop and message-flow diagram.
- The tool definitions are the server's own and need not exist anywhere in the client (explicit in the `2026-07-28` page only: "scoped to the sampling request — they don't need to correspond to registered tools"). **[V]** 2026 page; **[I]** that this holds for 2025-11-25 too (the 2025 page never says the client may run them, and its flow diagram has the server run them).
- Pairing rules (all **[V]**, page › Message Content Constraints, Tool Use and Result Balance, Security 6):
  - A user message containing `tool_result` blocks **MUST contain only** `tool_result` blocks (no text/image/audio mixed in). Rationale given: provider APIs with dedicated roles for results (OpenAI `tool`, Gemini `function`).
  - Every assistant message containing `tool_use` **MUST be followed by a user message consisting entirely of `tool_result` blocks**, one per `tool_use`, each `toolUseId` matching a `tool_use.id`, before any other message. Parallel tool use (an array of `tool_use`) is allowed.
  - These are obligations on the **server** (Security 6: "Servers MUST ensure…"). The client's duty is to reject violations with `-32602` (see 1.7).
- "Both parties **SHOULD** implement iteration limits for tool loops" (Security 7). **[V]**
- `tool_use` content: `{ type, id, name, input: object, _meta? }`. `tool_result`: `{ type, toolUseId, content, structuredContent?, isError?, _meta? }`. **[V]** S25:1834-1907.

### 1.6 What a server gets when it uses an undeclared capability

- **Undeclared `sampling.tools` with `tools`/`toolChoice`:** the schema says the client "**MUST return an error**". **No error code is specified** anywhere in the page or schema. The page's Error Handling lists only `-1` and `-32602` (below). **[V]** (absence); **[I]** `-32602` (Invalid params) is the natural code; the TypeScript SDK client does not implement this check at all (§3.4).
- **Undeclared `sampling.context` with `includeContext: thisServer|allServers`:** only a server-side SHOULD NOT; the client **MAY ignore** the field. **No error is mandated.** **[V]** S25:1595.
- The TypeScript SDK's **server** refuses locally before sending (`SdkError CapabilityNotSupported`, "Client does not support sampling tools capability."), so the wire error never arises with it (§3.4).

### 1.7 Human in the loop, validation, rate limiting, error codes

All from page › User Interaction Model, Message Flow, Error Handling, Security Considerations **[V]**:

- "For trust & safety and security, there **SHOULD** always be a human in the loop with the ability to deny sampling requests."
- Applications **SHOULD**: provide UI that makes it easy to review sampling requests; allow users to **view and edit prompts before sending**; **present generated responses for review before delivery**. The flow diagram also shows the user reviewing the request, **the returned `tool_use` calls** ("Present tool calls for review"), each continuation request, and the final response. `CreateMessageResult` JSDoc: the client "should inform the user before returning the sampled message, to allow them to inspect the response (human in the loop) and decide whether to allow the server to see it" (S25:1650-1655); the request JSDoc says the client "should also inform the user before beginning sampling" (S25:1640).
- Security considerations: (1) clients **SHOULD** implement user approval controls; (2) both parties **SHOULD** validate message content; (3) clients **SHOULD** respect model preference hints; (4) clients **SHOULD** implement **rate limiting**; (5) both parties **MUST** handle sensitive data appropriately. The spec gives no rate-limit numbers or mechanism.
- No MUST for human approval anywhere: it is SHOULD throughout. **[V]**
- **Error codes** ("Clients SHOULD return errors for common failure cases"): user rejected the request `-1`; tool result missing in the request `-32602`; tool results mixed with other content `-32602`. Example: `{"error":{"code":-1,"message":"User rejected sampling request"}}`. **[V]** page › Error Handling. `-1` appears only in the page's prose: `schema.ts` defines just the five JSON-RPC codes and `-32042` as code constants (S25:174-181). **[V]**
- Task-augmented sampling (the `task` param) is the other 2025-11-25 delivery mode for a request that needs a long human review. **[V]** S25:1578; the 2025-11-25 tasks page. Not read in depth here.

## 2. MCP `2026-07-28`

Primary sources: [sampling page](https://modelcontextprotocol.io/specification/2026-07-28/client/sampling.md), [MRTR page](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr.md), [deprecated registry](https://modelcontextprotocol.io/specification/2026-07-28/deprecated.md), [SEP-2577](https://modelcontextprotocol.io/seps/2577-deprecate-roots-sampling-and-logging.md), schema `S26`, [ext-tasks spec](https://github.com/modelcontextprotocol/ext-tasks/blob/b3d28aceaa6d49f5f92258e3d06b61ad6f111e84/specification/2026-07-28/tasks.md).

### 2.1 How sampling appears

- **No more server-initiated requests.** "Servers **MUST** send server-to-client requests (`roots/list`, `sampling/createMessage`, `elicitation/create`) using the MRTR pattern. The previous pattern… is no longer supported." **[V]** MRTR page, top note.
- A server answers a **client request** with `{ "resultType": "input_required", "inputRequests": { "<key>": { "method": "sampling/createMessage", "params": {…} } }, "requestState"?: "<opaque>" }`. The client builds the answers, then **retries the original request** (new JSON-RPC id) with `inputResponses: { "<key>": <CreateMessageResult> }` and the exact `requestState` echoed. **[V]** MRTR page › Core Types, Client Requirements 1-4; [S26:537-606](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/0aab7058fe6471f3d7b0301e13965f10ad9cb198/schema/2026-07-28/schema.ts#L537).
- **Only three client requests may return `input_required`**: `tools/call`, `prompts/get`, `resources/read`. "Servers MUST NOT send `InputRequiredResult` on any other client requests." **[V]** MRTR page › Supported Requests. (This is the context of the #386 and #387 inputs about `prompts/get`.)
- `InputRequest = CreateMessageRequest | ListRootsRequest | ElicitRequest`; `InputResponse = CreateMessageResult | ListRootsResult | ElicitResult`. **There is no error variant** in `InputResponse`, so a refusal cannot be a `-1` on the wire. **[V]** S26:537-542. The sampling page: "If an error occurs or the user declines the sampling request, the client does not need to replay the initial call with an error message, as the server is not waiting for a response". **[V]** page › Error Handling. MRTR rule: servers MUST NOT assume clients will fulfil `inputRequests` or retry; if information is missing, the server **SHOULD** respond with a new `InputRequiredResult` rather than an error. **[V]** MRTR › Server Requirements 8, Error Handling. **[I]** a host that refuses can simply not retry (or retry without that key).
- **Capabilities are per request**: `_meta["io.modelcontextprotocol/clientCapabilities"]` on every request carries `sampling`, `sampling.tools`, `sampling.context`. Servers **MUST NOT** send `inputRequests` the client has not declared support for. **[V]** sampling page › Capabilities; MRTR › Server Requirements 7. If a server needs a client capability the request lacks, it answers **`-32021` `MissingRequiredClientCapability`** with `data.requiredCapabilities` (HTTP 400): this is a **server → client** error on the client's request, not a client error to the server. **[V]** S26:437-442, S26:513-530.
- **Shape changes** against 2025-11-25 (all **[V]**, S26:2087-2260 vs S25:1574-1700):
  - `CreateMessageRequestParams` and `CreateMessageRequest` no longer extend `RequestParams`/`JSONRPCRequest`/`TaskAugmentedRequestParams`: no `task`, no `_meta` on params, no JSON-RPC envelope (`{method, params}` only).
  - `CreateMessageResult extends SamplingMessage` and no longer extends `Result`: the embedded result has no `resultType` and no result `_meta`. The SDK still accepts `_meta` on messages.
  - All fields (`messages`, `modelPreferences`, `systemPrompt`, `includeContext`, `temperature`, `maxTokens`, `stopSequences`, `metadata`, `tools`, `toolChoice`) and all value sets are unchanged. `ClientCapabilities.tasks` is gone from the core (it moved to the tasks extension).
  - `ClientCapabilities.sampling`, every sampling type and `ModelPreferences`/`ModelHint`/`ToolChoice`/`ToolUseContent`/`ToolResultContent` carry `@deprecated` JSDoc. `includeContext` additionally "deprecated as of protocol version 2025-11-25 (SEP-2596)".
- **Text added to the 2026-07-28 page** (not on the 2025-11-25 page; **[V]** by diff):
  - "The list of messages in a sampling request **SHOULD NOT** be retained between separate requests."
  - `systemPrompt`: "The client **MAY modify or ignore** this field **without communicating this to the server**."
  - `includeContext`: "The client **MAY modify or ignore** this field without communicating this to the server. For example, a client could determine that respecting this field in a particular request would require sharing sensitive information with a server, and constrain its response accordingly."
  - "The client **MUST respect the `maxTokens` parameter**. The client **MAY modify or ignore `temperature`, `stopSequences` and `metadata`**" (for example because the model does not support them).
  - `stopReason` described as non-exhaustive; "implementations MAY provide their own arbitrary values".
  - Result `content`: a single block for one block, an array "when the response contains one or more content blocks, such as multiple tool uses or mixed content".
  - The tool definitions "are scoped to the sampling request — they don't need to correspond to registered tools".
  - The security considerations (approval SHOULD, validation SHOULD, rate limiting SHOULD, iteration limits SHOULD, tool_result pairing MUST on servers) and the HITL warning are unchanged.
  - The page's own first example still shows `"includeContext": "thisServer"`. **[V]**

### 2.2 Deprecation (SEP-2577) and its advice

- Deprecated in `2026-07-28` (status Final). Stays "at least twelve months" and is eligible for removal in "the first revision released on or after **2027-07-28**". **[V]** deprecated registry; sampling page banner. Migration path: "**integrate directly with LLM provider APIs**".
- The page banner: "New implementations **SHOULD NOT** adopt it; existing implementations **SHOULD** migrate to integrating directly with LLM provider APIs." **[V]**
- SEP-2577, Capability negotiation (**[V]**): during deprecation wire behaviour is unchanged; "Clients and servers that support deprecated features SHOULD continue to declare the corresponding capabilities"; "Implementations that encounter deprecated capabilities MUST still handle them correctly"; implementations **SHOULD emit a warning** (logs or developer tooling) **when deprecated capabilities are negotiated**; "**New implementations SHOULD NOT add support for deprecated features unless needed for backward compatibility with existing counterparts.**"
- Rationale text in the SEP (**[V]**): sampling "is the most security-sensitive of the three. It allows servers to request LLM completions through the client, which creates attack surface for prompt injection and data exfiltration"; correct implementation "requires human-in-the-loop approval, model selection logic, security considerations, and (since SEP-1577) tool loop support"; adoption is low.
- The SEP also deprecates `ClientCapabilities.tasks.requests.sampling` (the 2025-11-25 task-augmented sampling). **[V]**
- `includeContext: "thisServer" | "allServers"`: Deprecated since `2025-11-25` (SEP-2596), "will be removed no later than the Sampling feature itself"; migration "omit the field or use `none`". **[V]** registry.

### 2.3 Sampling inside the tasks extension

- The extension is `io.modelcontextprotocol/tasks` (EXT-TASKS spec `2026-07-28`). When a task is `input_required`, `tasks/get` returns a `Task` with `inputRequests` (same `InputRequests` map as MRTR, so it may hold `sampling/createMessage`); the client answers with one or more `tasks/update { taskId, inputResponses }`. **[V]** EXT-TASKS:156, 182, 329, 344-346.
- **"Clients MUST treat each entry in `inputRequests` as they would the equivalent standalone server-to-client request"** (same trust model and user-facing behaviour). Security section: "Hosts **MUST** apply the same trust model to these payloads as they would to standard elicitation/sampling requests. **A task is not a higher-trust channel.**" **[V]** EXT-TASKS:348, EXT-TASKS:905.
- Clients **SHOULD deduplicate** `inputRequests` keys across consecutive polls so the user or model sees a request once. Keys are **unique for the life of a task**; a server must not reuse a key. A server **SHOULD ignore** `inputResponses` for keys that are unknown, already answered or superseded, and **MAY accept a partial set**. The `tasks/update` ack is **eventually consistent**. **[V]** EXT-TASKS:346-377.
- Distinction: input needed **before** a `CreateTaskResult` uses ordinary MRTR on the original request; input needed **during** execution uses the task's `inputRequests`/`inputResponses`: "a distinct mechanism: task `inputRequests` are surfaced via `tasks/get` and fulfilled via `tasks/update`, not via retries of the original method". **[V]** EXT-TASKS:591.
- Client-hosted sampling tasks (the client returning a task handle for a sampling request) no longer exist: SEP-2663 removed them "in compliance with SEP-2260" (every unsolicited server→client request is invalid). **[V]** [SEP-2663](https://modelcontextprotocol.io/seps/2663-tasks-extension.md) Motivation.
- Evidence from a shipping host: Claude Code's tasks support serves **only `elicitation/create` (interactive sessions) and `roots/list`** in `inputRequests`; "when Claude Code can't serve a request, it asks the server to cancel the task", and it answers at most 16 keys per task. Sampling is not served. **[V]** [Claude Code MCP docs](https://code.claude.com/docs/en/mcp.md) (tasks › "Methods in `inputRequests`").

## 3. TypeScript SDK v2 (`@modelcontextprotocol/client` 2.4.0)

Everything below is at tag `v2.4.0`. The v2 line is the packages `@modelcontextprotocol/{client,server,core}`; the `@modelcontextprotocol/sdk` name is the v1 line. **[V]** (`npm view`.)

### 3.1 Types

- Zod schemas in `SDK:packages/core/src/schemas.ts`; TS types in `SDK:packages/core-internal/src/types/types.ts`. All carry `@deprecated … SEP-2577`.
  - `ModelHintSchema { name?: string }` (:1582); `ModelPreferencesSchema { hints?, costPriority?, speedPriority?, intelligencePriority? }` with `min(0).max(1)` (:1596); `ToolChoiceSchema { mode?: "auto"|"required"|"none" }` (:1622).
  - `ToolResultContentSchema` (:1640): `structuredContent` is `z.unknown()` (any JSON; SEP-2106) on the 2026 wire, object-only on the frozen 2025 wire schema.
  - `SamplingContentSchema = text | image | audio` (:1666); `SamplingMessageContentBlockSchema = text | image | audio | tool_use | tool_result` (:1676).
  - `CreateMessageRequestParamsSchema = TaskAugmentedRequestParamsSchema.extend({ messages, modelPreferences?, systemPrompt?, includeContext?, temperature?, maxTokens: z.number().int(), stopSequences?, metadata?, tools?, toolChoice? })` (:1708-1759). `maxTokens` is required and **must be an integer** (the spec says `number`).
  - **`CreateMessageResultSchema`** (:1775): `model: string`, `stopReason?: open string`, `role`, **`content: SamplingContentSchema` (a single text|image|audio block, no array, no tool_use)**.
  - **`CreateMessageResultWithToolsSchema`** (:1806): same, but `content` is one block or an array of any `SamplingMessageContentBlock`. `stopReason` enum includes `toolUse`.
  - Types: `CreateMessageResult`, `CreateMessageResultWithTools` (`types.ts:514, 520`); overload helpers `CreateMessageRequestParamsBase` (no `tools`/`toolChoice`) and `CreateMessageRequestParamsWithTools` (`types.ts:951, 960`).
  - The typed result map for the handler: `'sampling/createMessage': CreateMessageResult | CreateMessageResultWithTools` (`types.ts:702`).

### 3.2 Handler registration and signature

```ts
const client = new Client(info, { capabilities: { sampling: { tools: {} } } });
client.setRequestHandler("sampling/createMessage", async (request, ctx) => {
  // request.params: CreateMessageRequestParams
  return { model, role: "assistant", content: { type: "text", text }, stopReason: "endTurn" };
});
```

- Registering the handler throws `SdkError(CapabilityNotSupported, "Client does not support sampling capability…")` unless `capabilities.sampling` was declared in the constructor. **[V]** `SDK:packages/client/src/client/client.ts:1528-1534`.
- Capabilities are **connection-wide, set before `connect()`**: `registerCapabilities` throws after connecting (client.ts:811-817). On the modern era the SDK attaches those capabilities to every request's `_meta` envelope (`_outboundMetaEnvelope`, client.ts:~716-733), and "User-supplied `_meta` keys take precedence over the auto-attached ones" (docstring), so a host can override the envelope per request. **[V]** docstring; **[I]** that a per-request capability override is therefore feasible (not tested).
- The same handler serves both delivery paths: a pushed request on legacy, and an embedded input request fulfilled inside `callTool()`/`getPrompt()`/`readResource()` on modern. Docs: "Register each handler once… your code never sees the difference." **[V]** `SDK:docs/clients/server-requests.md` › "Register each handler once".
- The context: `ctx: ClientContext`. For embedded requests the SDK synthesizes `ctx` with `mcpReq.id = <inputRequests key>`, the call's abort signal, no `send`/`notify`. **[V]** `SDK:packages/core-internal/src/shared/inputRequiredEngine.ts:63-84`.
- A handler may throw `ProtocolError(code: number, message, data?)`, which becomes a JSON-RPC error with that code; arbitrary numeric codes are accepted (`-1` works) though `ProtocolErrorCode` has no `-1` member. **[V]** `SDK:packages/core-internal/src/types/errors.ts:45-49`, `types/enums.ts:5-40`. On modern, a handler failure **rejects the whole call** and aborts the sibling input requests (they are fulfilled concurrently with `Promise.all`). **[V]** `SDK:packages/core-internal/src/shared/inputRequiredDriver.ts:240-262`.

### 3.3 Modern-era round driver

- `inputRequired: { autoFulfill?: boolean (default true), maxRounds?: number (default 10) }`. Past `maxRounds`: `SdkError(INPUT_REQUIRED_ROUNDS_EXCEEDED)`. `autoFulfill: false`: a call needing input rejects on its first round with a typed error unless the call passes `allowInputRequired: true` (manual mode: the caller drives `inputResponses`/`requestState`). **[V]** `SDK:docs/clients/server-requests.md` › "Cap or disable automatic fulfilment"; `inputRequiredDriver.ts:30-81`.
- No handler registered for an embedded method: `SdkError(CapabilityNotSupported, "Cannot fulfil input request '<key>': no handler is registered…")`. An embedded method that is not `elicitation/create | sampling/createMessage | roots/list`: `SdkError(InvalidResult)`. **[V]** `inputRequiredEngine.ts:129-151`.
- The driver echoes `requestState` byte-for-byte on a fresh request id and, with `maxTotalTimeout`, bounds the whole flow. **[V]** `inputRequiredDriver.ts:1-20`. It holds the loop in memory: there is no durable continuation in the SDK (prior research: the Cloudflare `agents` wrapper documents this as intentionally absent). **[V]** (prior note); cloudpid's ADR-0037 plan to persist `ResumeState` therefore goes through manual mode. **[I]**

### 3.4 What the SDK validates, and what it does not

All in `SDK:packages/client/src/client/client.ts:916-965` (`_wrapHandler` for `sampling/createMessage`) unless noted. **[V]**

- **Request:** validated against the era's schema (2025: wire request schema; 2026: embedded `validateInputRequest`). Failure → `ProtocolError(InvalidParams -32602, "Invalid sampling request: …")`. Zod-level constraints: `messages` entries need `role` and `content` of the five block types; `maxTokens` int; priorities in [0,1]; `metadata` a JSON object.
- **Result:** `hasTools = Boolean(params.tools || params.toolChoice)`; the result must match **`CreateMessageResultWithToolsSchema` when the request carried `tools` or `toolChoice`, otherwise the plain `CreateMessageResultSchema`**. So an array `content` or a `tool_use` block returned for a request without `tools`/`toolChoice` is rejected with `ProtocolError(InvalidParams, "Invalid sampling result: …")`. On the 2026 era the embedded response validator covers both. (`client.ts:948-958`.)
- **Not checked by the client** (grep of `client/src` and `core-internal/src/shared`): that `sampling.tools` was declared when `tools`/`toolChoice` arrive; anything about `includeContext` or `sampling.context`; `tool_use`/`tool_result` pairing; the "tool_result-only user message" rule; model-hint matching (no code touches `hints`/`costPriority`); approval, rate limiting, token budgets, image/audio MIME or size. The registration-time check is only `capabilities.sampling` present.
- The **server side** of the SDK does enforce them, which shows the intended behaviour: `Server.createMessage` throws `SdkError(CapabilityNotSupported, "Client does not support sampling tools capability.")` if `tools`/`toolChoice` are present and the client did not declare `sampling.tools`; and validates the last message (only `tool_result` content; each `tool_result` needs a matching previous `tool_use`; the id sets must be equal) with `ProtocolError(InvalidParams, …)` (`SDK:packages/server/src/server/server.ts:1107-1152`). The SDK server also computes the capabilities an embedded input request requires (`sampling: {tools:{}}` when `tools` or `toolChoice` is present, else `sampling: {}`; `SDK:packages/core-internal/src/shared/clientCapabilityRequirements.ts:94-100`). Its `createMcpHandler` comments describe a "handler-time `-32021` (the input_required gate)" on the modern era (`createMcpHandler.ts:765-772`), and its shim for serving a modern-style handler to a 2025-era client fails the call (a `tools/call` `isError` result, otherwise a JSON-RPC error) when the declared capabilities do not cover the embedded request (`legacyInputRequiredShim.ts:195-215`).
- The server's `createMessage`/`ctx.mcpReq.requestSampling` **throws on a 2026-07-28 connection** (push API unavailable). **[V]** `server.ts:1085-1106`.
- Net for cloudpid: capability checks, pairing rules, hint matching, Approval, Usage and spend are all the host's job; the SDK validates only structure and the content-array-vs-tools shape. **[I]**

### 4.1 VS Code (GitHub Copilot)

Primary sources: `microsoft/vscode` at `c198526d8e64ba6f9944e9f7bcc079ed1f6d7fcc`, `src/vs/workbench/contrib/mcp/`; the [VS Code MCP dev guide](https://code.visualstudio.com/api/extension-guides/ai/mcp.md) › Sampling. Cited `VSC:<file>:<line>`.

  - Unset → a **modal dialog** (during a tool call) or a **notification** (outside chat), titled "Allow MCP tools from "X" to make LLM requests?" / "Allow MCP server "X" to make LLM requests?", with buttons **Allow in this Session / Always / Not Now / Never**. `Always` and `Never` persist to the `chat.mcp.serverSampling` setting; `Not Now` stores `false` in a per-session map (but the gate tests `Map.has`, so by reading the code a later request in the same session passes the gate without a prompt **[I]**). **[V]** `mcpSamplingService.ts:129-200`.

- **What is sent to the model:** text parts as text; **image and audio parts both mapped to an `image_url` part** with the given MIME type (audio is sent as an image); `systemPrompt` as a leading system message; messages as user/assistant. `sendChatRequest(model, undefined, messages, {}, token)`: **`maxTokens`, `temperature`, `stopSequences`, `metadata`, `tools`, `toolChoice`, `includeContext` are all dropped**. Messages whose parts are all `tool_use`/`tool_result` are dropped (no parts). **[V]** `mcpSamplingService.ts:59-82`.
- **What is returned:** **text only** ("MCP doesn't have a notion of a multi-part sampling response, so we only preserve text"), `role: 'assistant'`, `model` = the VS Code model id; **no `stopReason`**. Errors → `McpError.unknown` (`-32603`). Requests are serialized through a `Sequencer` while the model is picked. **[V]** `mcpSamplingService.ts:81-120`.
- **Log / transcript display:** per server, a stored log (`mcp.sampling.logs`): requests per day for 7 days and the **last 30 requests/responses** (request messages, response text, timestamp, model). Shown by **MCP: List Servers › Show Sampling Requests** as a text document: "N total requests in the last 7 days" plus each request (`[type data: mimeType]` placeholders for media). No token counts or costs are recorded. **[V]** `common/mcpSamplingLog.ts:12-135`; `browser/mcpServerActions.ts:1208-1247`.
- **Docs:** "The first time an MCP server performs a sampling request, the user is prompted to authorize the server to access their models"; users can restrict models; "Set reasonable token limits for sampling requests". **[V]** VS Code MCP dev guide › Sampling.

### 5.2 Output

`AssistantMessage` (`types.ts:585-625`):

- `content: (TextContent | ThinkingContent | ToolCall)[]`. MCP results have no thinking block: thinking would have to be dropped. Text blocks may carry `textSignature`. No image/audio output (image generation is a separate `generateImages()` API with `ImageModel`). **[V]**
- `stopReason: "pending" | "stop" | "length" | "toolUse" | "error" | "aborted" | "deferred"` (`types.ts:489`). Mapping to MCP is `stop→endTurn`, `length→maxTokens`, `toolUse→toolUse` **[I]**; there is **no `stopSequence`** (Anthropic's `stop_sequence` is mapped to `stop`, `anthropic-messages.ts:1678`), and `error`/`aborted` carry `errorMessage` (and `diagnostics`) and must become a JSON-RPC error. Raw provider reason in `rawStopReason`. **[V]** for the type and Anthropic mapping (`anthropic-messages.ts:1659-1690`).
- `ToolCall.argumentsError`: set when the model's arguments text was not a valid JSON object (`arguments` is then `{}`). A host mapping to `tool_use.input` must handle it. **[V]** `types.ts:444-458`.
- `model` (requested id), `responseModel` (concrete model reported by the provider, when reported), `provider`, `api`, `responseId`. MCP `result.model` is a free string. **[V]** `types.ts:585-596`.
- `usage: Usage { input, output, cacheRead, cacheWrite, cacheWrite1h?, reasoning?, totalTokens, cost { input, output, cacheRead, cacheWrite, total, totalFromProvider? } }`. `cost` is computed from the catalog (`calculateCost`, $/M tokens, with tiers) unless the provider reports a billed cost (`totalFromProvider: true`, e.g. OpenRouter). MCP has no field for usage, so Usage/Spend is purely the host's accounting. **[V]** `types.ts:459-487`; `models.ts:1236-1257`; `utils/openrouter-cost.ts:33-53`.
- `durationMs`, `timestamp`, `diagnostics`. **[V]**
- Streaming events (`text_delta`, `toolcall_*`, `done`, `error`) are available via `streamSimple()` for a live "sampling in progress" display; MCP itself returns one result. **[V]** `types.ts:821-846`.

### 5.3 What maps and what does not (summary, **[I]** over the **[V]** facts above)

- Maps: `systemPrompt`; text and image messages; `maxTokens` (with context clamping); `temperature` (with provider caveats); `tools` (plain JSON Schema, with the Anthropic schema-flattening caveat); `toolChoice` `auto`/`none`; tool calls out as `tool_use`; `stop`/`length`/`toolUse`; `model`; token usage and cost for the host's own accounting.
- Needs host code: `tool_result` splitting into `toolResult` messages and flattening non-text/non-image content; synthesizing `AssistantMessage` history records; pairing validation (pi-ai repairs rather than rejects); JSON-Schema `description` default; `argumentsError`; dropping `thinking` blocks; turning `error`/`aborted` into a JSON-RPC error; hint matching and priorities over the catalog.
- Does **not** map: **audio** input (no type); **`toolChoice: "required"`** on the provider-neutral path; **`stopSequences`** (no option; `stopReason: "stopSequence"` can never be produced); `includeContext` (policy only); `modelPreferences` speed/intelligence priorities (no catalog data); MCP `metadata` (only partly); `resource_link`/embedded-resource/`structuredContent` inside `tool_result`.
