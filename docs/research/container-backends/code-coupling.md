# How tightly the code is tied to Cloudflare Containers, a provider seam, and migration

Read-only analysis, 2026-10-28. Repo at `d2e066d`; `@cloudflare/computer` 0.8.0 (patched), computerd 0.8.0, `@cloudflare/workers-types` 5.20261021.1.
`C/` = `node_modules/.pnpm/@cloudflare+computer@0.8.0_patch…/node_modules/@cloudflare/computer/dist/`, `WT` = `node_modules/.pnpm/@cloudflare+workers-types@5.20261021.1/node_modules/@cloudflare/workers-types/index.d.ts`, `ws/` = `apps/server/src/workspace/`.

## Summary

- **The tie is narrow but runs through everything.** Every direct call to `ctx.container` is in `ws/Workspace.ts`, apart from the scan exec in `snapshots.ts`. Almost every feature module (`launch`, `snapshots`, `idle`, `resize`, `build`, `spare`, `container-preview`, `container-usage`) already takes an injected deps object. Most of the work is moving the ~20 `ctx.container` call sites in the `Workspace` constructor behind one interface, so the modules themselves need little or no rewriting.
- **computer already has a host interface you can swap.** `ContainerBackend` reaches the platform only through `IWorkspaceContainerAPI`, which comes from `ContainerBackendOptions.container().getWorkspaceContainer()`, and cloudpid already decorates it (`launch.wrap`, `withExitReports`). Through that interface the protocol uses HTTP to computerd's port (`fetchPort`) plus one WebSocket that computerd dials back. Both can be carried over a tunnel or provider port URL. computerd also has a **direct mode**: the host upgrades `/api` itself, which needs a small custom `WorkspaceBackend`.
- **computerd can be run elsewhere and redistributed.** It is MIT, its source is public (`github.com/cloudflare/computer/packages/computerd`), and it ships as a standalone Node SEA for linux-x64 (arm64 can be built). It is marked **Experimental**, and the wire protocol is not stable across releases.
- **What a new backend must provide, and what does not move:**
  - **Hard requirements:** `/dev/fuse` with libfuse ≥ 3.17, because without a real FUSE mount computerd cannot keep the Container-only paths (`node_modules`) local. Also a disk snapshot/restore primitive (Snapshots, Builds, spares) and Docker-capable kernel features (overlay2, cgroup v2).
  - **No change needed:** the DO-side file tree, the Worker Shell, the bootstrap/Toolchains, Setup/Start Scripts, the memory guard, and file-tool routing.
- **Terminals (ADR-0012) do not exist in code yet.** Issue #139 is open, and nothing calls `exec({pty})`. So the seam only needs room for a PTY; there is no code to port.
- **Cheap wins come first** (section 5). Several background paths start Containers that nobody uses interactively: the daily Build check, Build → spare cascades, spare refills, subagent work-state reads, and an idle snapshot even when nothing changed. Turn on the analytics token before anything else to find where the >$10 went.

## 2. How computer's `ContainerBackend` talks to computerd

### 2a. The connection sequence (`C/backends/container/index.js:215-312`)

1. `host.start(spec)` (`:229`): the platform launch, with env `PORT=8080`, `MOUNT_POINT`, `MOUNT_IGNORE` and `RPC_CLIENT_SECRET` (`:220-225`, `:736-740`). If a running Container's env, instance or name digest differs, it is **relaunched** (`:551-570`, `:699-711`).
2. `host.interceptOutboundHttp("computer.internal", workspaceRef)` (`:240`): computerd's outbound HTTP to that host goes to `ctx.exports.WorkspaceProxy` → `DO.fetch` → `ContainerBackend.handleFetch` (`ws/Workspace.ts:1147-1149`).
3. Health probe: `host.fetchPort(8080, "/health")` with backoff, then one `restart` (`:379-417`, `:440-458`).
4. Auth check: `GET /api` must answer 401 (`:463-476`).
5. `POST http://container/connect {base:"http://computer.internal", api:"/api", health:"/health"}` (`:477-506`). computerd dials **out**. The DO accepts the WS upgrade at `/api` with `Authorization: Bearer <clientSecret>` (`:329-347`). It uses `server.accept()`, so the socket cannot hibernate.
6. `newWebSocketRpcSession(ws)` (capnweb) (`:257`). Heartbeat `sync.watermarks()` every 20 s (`:152, 272-280`).
7. `GET /__computerd/info` checks that computerd applies exactly the declared `ignore` (`:418-439`, `:92-115`).

So, beyond starting and stopping, the protocol needs only these: **HTTP from the DO to computerd's port** (4 requests per connect) and **one WebSocket between computerd and the DO**. After connect, all traffic is capnweb over that WebSocket. FUSE I/O is local to the Container, against computerd's own store (`COMPUTERD_DB`). The WAN is crossed only when files are synced at command boundaries (push before a command, pull after: overview.md → Backends) and by exec streams.

## 4. A `SandboxProvider` seam

### 4a. Interface sketch

```ts
// apps/server/src/workspace/sandbox/provider.ts
export type SandboxSize = {
  readonly name: string;
  readonly vcpu: number;
  readonly memoryMib: number;
  readonly diskMb: number;
};

export type SandboxLaunch = {
  readonly from: { readonly image: string } | { readonly snapshot: SnapshotHandle };
  readonly size: SandboxSize;
  readonly env: Readonly<Record<string, string>>; // PORT, MOUNT_POINT, MOUNT_IGNORE, RPC_CLIENT_SECRET, CLOUDPID_RESET_STORE, …
  readonly labels: Readonly<Record<string, string>>; // cloudpid-ws=<DO id>
};

export type SandboxStatus =
  | { readonly state: "stopped" }
  | { readonly state: "running"; readonly runtimeId: string; readonly launch: LaunchDigest }
```

Implementations:

- `CloudflareSandboxProvider(ctx)`: a thin adapter over `ctx.container` plus `WorkspaceContainerAPI`. It keeps computer's `ContainerBackend`, so behaviour does not change.
- `RemoteSandboxProvider(api, tunnel)`: a control-plane client for a provider REST API or a self-hosted agent, plus a TLS tunnel for computerd and the preview ports. It pairs with a new `RemoteComputerdBackend implements WorkspaceBackend`, which copies `ContainerBackend.connect()` (§2a) but uses direct `/api`.

### 4d. Risk points

| Risk                                            | Detail                                                                                                                                                                                                                                                                                                                                          | Mitigation                                                                                                                                |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| FUSE sync latency over the WAN                  | FUSE ops are local, but each Container command does push → exec → pull (`watermarks`, `push`, `fetchChanges` ≈ 3+ RTTs) plus a 20 s heartbeat. A first full sync was already 33 s per 9k files inside Cloudflare (ADR-0016 consequences), and over the WAN it is unmeasured. `fetchChangePack` batching exists (`C/shared-awntXH49.d.ts:35-55`) | Keep `COMPUTERD_DB` on disk and snapshot it (only deltas resend). Put the provider region near the DO's region. Measure before committing |
| WebSocket DO ↔ remote                           | The DO accepts or opens a non-hibernatable socket (`index.js:337`), so the DO stays resident while the sandbox runs, as it does today. Deploys and evictions drop it → computer reconnects (07_injected_service.md → reconnect). The DO's duration is billed while the socket is open                                                           | Accept it (no change from today). Make sure the heartbeat runs across proxies                                                             |
| DO hibernation with open sockets                | Impossible with computer's current socket handling. Previews' carried sockets already pin the DO                                                                                                                                                                                                                                                | Out of scope unless computer moves to `ctx.acceptWebSocket`                                                                               |
| Auth exposure                                   | Today only the owning DO can reach computerd. Remotely, `/api` with a bearer token is on the internet. Dial-back mode uses `http://` (`index.js:488`)                                                                                                                                                                                           | Direct mode over TLS, or Access-protected tunnel hostnames plus `RPC_CLIENT_SECRET`. Never expose computerd's port publicly without TLS   |
| Provider trust boundary                         | The provider sees the launch env (`RPC_CLIENT_SECRET`), the disk (tokens a command wrote) and snapshots. GitHub tokens go per command over RPC, not in the launch env (good)                                                                                                                                                                    | Keep the scan before snapshot. Delete snapshots on removal                                                                                |
| Snapshot semantics differ                       | Cloudflare: disk only, 30 days, image-tied, ~45–90 s. Others: memory pause/resume, templates only, other lifetimes                                                                                                                                                                                                                              | `capabilities` plus `snapshotPolicy`. A memory snapshot could replace the idle snapshot and the Start Script re-run                       |
| Cross-sandbox restore for Builds                | Already unverified on Cloudflare (container.md → Builds: "Not verified")                                                                                                                                                                                                                                                                        | Gate Builds on `capabilities.crossSandboxRestore`, else use the spare-only path                                                           |
| Experimental upstream                           | computerd and the protocol are Experimental and change between releases (Dockerfile:7-9)                                                                                                                                                                                                                                                        | Pin versions. computer is already patched via pnpm (`patches/@cloudflare__computer@0.8.0.patch`)                                          |
| Egress cost between Cloudflare and the provider | Sync and exec streams cross clouds                                                                                                                                                                                                                                                                                                              | Small for text. Large for initial syncs and artifacts                                                                                     |
| FUSE or Docker unavailable on a provider        | Without a real FUSE mount, Container-only paths are lost (shim)                                                                                                                                                                                                                                                                                 | Make it a hard gate in provider selection                                                                                                 |

## 6. Suggested path

1. **Now:** wins 1, 2, 5, 6, 9, then 3/4/7 (all S, no architecture change).
2. **Seam:** add `SandboxProvider` and `CloudflareSandboxProvider` with no behaviour change, plus a fake provider for workerd tests (M).
3. **Spike:** `RemoteComputerdBackend` in direct `/api` mode against one host with `/dev/fuse` and Docker: a self-hosted Incus/Firecracker VM or one managed provider. It runs behind an Access-protected Cloudflare Tunnel. Measure the per-command sync overhead, the initial sync of this repo, `pnpm install`, and snapshot/restore times. Go or no-go on those numbers.
4. **Per-Environment `provider`** setting. Builds and snapshots are keyed by provider. Cloudflare remains the fallback.
5. **Optional later:** memory snapshots where a provider has them. Option C (drop computerd) only if the FUSE/sync costs over the WAN are prohibitive.
