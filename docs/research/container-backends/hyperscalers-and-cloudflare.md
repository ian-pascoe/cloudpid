## 0. Reference-workload definition used for every cost below

60 h running/month; 15 h at 100 % of 2 vCPU, 45 h at ~5 % → **34.5 vCPU-h used**. Sandbox shape 2 vCPU / 4 GiB (6 GiB on Cloudflare, whose custom types need ≥3 GiB/vCPU) / 12–20 GB disk.
Storage: 3 golden × 3 GB + 10 workspace × 2 GB = **29 GB** of snapshots all month. Egress 20 GB. **Heavy** = 180 h running, 45 h busy (snapshots/egress unchanged).
Worker/DO/log charges excluded everywhere (they also apply with CF). Where a provider bills allocated (not used) CPU, busy vs idle is irrelevant.

### 2.3 Snapshots & Sandbox SDK

- Container snapshots (https://developers.cloudflare.com/containers/guides/snapshots/ , limits page): FS only (no memory/processes), root writable FS only, immutable, ≤ **20 GB**, **30-day TTL refreshed on restore**, durable_object policy only, **public beta**.
- **Is snapshot storage billed? Not documented.** The pricing page has no snapshot/storage line and the snapshot guide/limits/changelog mention no price. Treat as "free during beta, price TBD" — **ask Cloudflare / watch changelog** before relying on it. (Snapshot _creation_ time while the container runs is billed as normal running time: 45–90 s × mem rate.)
- Sandbox SDK 0.x pricing = Containers pricing + Workers + DO (https://developers.cloudflare.com/sandbox/platform/pricing/ , Sep 30 2026). Sandboxes 1.0 (`@cloudflare/sandbox` 1.x, https://developers.cloudflare.com/sandbox/) now = Containers (`durable_object` policy) or Dynamic Workers; no separate fee found. R2 backup/restore of directories exists as alternative to snapshots (https://developers.cloudflare.com/sandbox/files/back-up-a-directory-to-r2/) — R2 pricing not re-checked here.
- Lifetime semantics (https://developers.cloudflare.com/sandbox/concepts/lifetime/): instance runs while DO active (request, alarm, streaming response, **or an accepted WebSocket — even a silent browser terminal**); then for `setInactivityTimeout()` (≤ **6 h**); timeout is lost on DO restart (must re-set in constructor); code inside the VM is _not_ activity (build can be killed unless an alarm pings). "An idle instance is still billed" (memory+disk).

### 2.4 Cost levers (what dominates)

Idle-hour cost is **memory-dominated**: 6 GiB × $0.009 = $0.054/h (95 % of idle cost); CPU at 5 % of 2 vCPU = $0.007/h. Busy hour: CPU $0.144 + mem $0.054 = $0.20. In the reference month (no allowances): memory $3.24 (55 %), CPU $2.48 (42 %), disk $0.18 (3 %). Heavy: mem 55 %, CPU 42 %.

1. **Wall-clock running time × provisioned GiB is the bill.** The >$10 in a few days implies tens-to-hundreds of running hours, not CPU. Find what keeps instances alive: open **WebSocket/terminal tabs** (keep DO active forever), preview connections, health-check alarms, and long `setInactivityTimeout` values. Cap with a hard max-session/idle-disconnect (close the WebSocket server-side after N min without input).
2. **Right-size memory first**: 1 vCPU/3 GiB custom = $0.030 idle/$0.102 busy vs 2 vCPU/6 GiB $0.057/$0.20 — halves memory spend. Default to 1 vCPU/3 GiB and resize up (start-time `instance:` choice per workspace, only possible with `durable_object` policy) for builds. standard-3 (8 GiB) is costlier than custom 2/6.
3. **Shorter idle timeout**: each idle minute costs ≈$0.0009 (6 GiB) / $0.0005 (3 GiB); cheap vs restore overhead, but multiply by sessions/day. 2 min is fine; the larger costs are snapshot save time (45–90 s billed) and restore time — snapshot only when FS changed ("checkpoint" cadence in the sandbox example is 15 min).
4. CPU is only 42 % and only for real work → don't pay for faster CPUs by upsizing vCPU unless builds are the bottleneck; allowances (375 vCPU-min, 25 GiB-h) are small (≈4 h of 6 GiB).
5. Disk is negligible ($0.003/h for 12 GB); egress effectively free (1 TB incl.).
6. Free-up: drop `earlyoom`/dockerd memory (docker daemon + compose services are the real memory consumers).

## 3. AWS

### 3.1 Fargate (ECS) — https://aws.amazon.com/fargate/pricing/ (read 2026-10-28) + AWS price list API (us-east-1, published 2026-10-19)

- Linux/x86: **$0.04048/vCPU-h** ($0.000011244/s), **$0.004445/GB-h**; ARM $0.03238/$0.00356; ephemeral storage 20 GB free, extra **$0.000111/GB-h** (≤200 GB). Per-second, **1-min minimum**, billed from image pull start to task stop. Allocated (not used) resources billed.
- Spot (ECS, Linux only): "up to 70 % off", price table not in static page → my estimate ≈ $1.8/60 h (**unverified number**). 2-min interruption warning.
- Sizes: 2 vCPU: 4–16 GB; 4 vCPU: 8–30 GB (max 16 vCPU/120 GB).
- **Cost** (2 vCPU/4 GiB): $0.0987/h → **$5.92 / 60 h**, $17.77 / 180 h; 6 GiB: $6.46. Storage: EBS snapshot $0.05/GB-mo × 29 GB = $1.45; egress 20 GB inside the 100 GB/mo AWS-wide free tier (https://aws.amazon.com/ec2/pricing/on-demand/) = $0. Public IPv4/NAT/CloudWatch extra (not computed).
- Capabilities: **no privileged** ("not supported … on AWS Fargate", https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_ContainerDefinition.html); **`devices` unsupported** (LinuxParameters API) → no /dev/fuse; EKS doc: privileged unsupported. ⇒ **no dockerd, no FUSE.** PTY via ECS Exec (`ExecuteCommand` returns SSM `streamUrl`+token; WebSocket, SSM protocol — heavy to implement in a Worker). Control plane is SigV4 REST (usable from Worker with aws4fetch).
- Startup: image pulled for **every task** (https://docs.aws.amazon.com/AmazonECS/latest/developerguide/fargate-pull-behavior.html); a 470 MB/1.5 GB image ⇒ tens of seconds; numeric time not documented. No stop/resume — tasks are terminate-only.
- Snapshot: ECS can attach an EBS volume created **from a snapshot at task launch** (Fargate platform ≥1.4; https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ebs-volumes.html) with `volumeInitializationRate`; no root-FS snapshot; goldens would be images in ECR.
- Verdict: ✗ (Docker/FUSE). Only useful if dockerd is dropped _and_ a daemon replaces FUSE.

- Burstable t3: unlimited-mode surplus $0.05/vCPU-h (https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/burstable-performance-instances-unlimited-mode-concepts.html); t3.medium earns ≈0.4 vCPU baseline ⇒ my estimate ≈$0.5 surplus on the reference month (approx., ignores credit accrual/launch credits).
- EBS: gp3 **$0.08/GB-mo**, gp2 $0.10, **snapshot $0.05/GB-mo** (standard), archive $0.0125/GB-mo (+$0.03/GB retrieval) (price list; https://aws.amazon.com/ebs/pricing/; 1 GB snapshot free tier only for new accts). Volumes billed per-second while provisioned — **a stopped instance still pays for EBS**; hibernated instance also pays for the RAM image stored on the root EBS (https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/Hibernate.html; requires hibernation-enabled, encrypted root, prerequisites).
- Cost (c7i.large, one persistent 20 GB gp3 root, snapshots as 29 GB): 60 h → $5.36 + $1.60 + $1.45 = **$8.4**; heavy $16.1 + 3.05 = $19.1. Spot ≈ **$5.1** / $9.3. If every one of 10 workspaces keeps its own live 20 GB volume: +$14.4 — keep them as snapshots instead (restore lazily from S3 unless Fast Snapshot Restore, extra $, not priced here).
- Capabilities: full VM ⇒ Docker ✓, FUSE ✓, PTY ✓ (you run a daemon). Start from stopped ≈ tens of seconds (not documented as a number; **misses the 2–5 s target** unless hibernated/warm pool). Hibernate resume restores RAM+processes (memory-snapshot bonus) but still stop/start latency.
- Control from Worker: EC2 REST (Query API, SigV4 via fetch) ✓. Inbound previews: security-group port or **cloudflared tunnel** from the VM ⇒ no public listener (CF-side docs, not researched here). Interruption: spot 2-min notice.
- Gotcha: you own AMI baking (golden = AMI + EBS snapshots), agent/daemon HA, auth, idle shutdown (an in-VM watchdog that calls StopInstances), vCPU service quotas for new accounts.

### 3.3 Lambda MicroVMs (new, 2026) — the AWS product aimed at this use case

Sources: https://docs.aws.amazon.com/lambda/latest/dg/lambda-microvms-guide.html , …/microvms-images.html , …/microvms-launching.html , quotas …/gettingstarted-limits.html , pricing https://aws.amazon.com/lambda/pricing/ , skill https://github.com/aws/agent-toolkit-for-aws/blob/main/skills/specialized-skills/serverless-skills/aws-lambda-microvms/SKILL.md

- **Pricing (ARM/Graviton, us-east-1; ARM is the only architecture documented — "support the ARM64 architecture")**: **$0.0000276944/vCPU-s ($0.0997/h)**, **$0.0000036667/GiB-s ($0.0132/h)**; baseline billed whenever running (idle too); burst above baseline (up to 4×) billed only for time/extra used. Snapshot storage **$0.08/GB-mo** (image min 1-week retention), snapshot write (suspend) **$0.0038/GB**, read (launch/resume) **$0.00155/GB**. Data transfer standard AWS rates. Suspended = no compute charge.
- Sizes (baseline→peak, max disk): 0.5 GB/0.25 vCPU→2/1, 8 GB; 1/0.5→4/2, 8 GB; 2/1→8/4, **8 GB**; **4/2→16/8, 16 GB**; 8/4→32/16, 32 GB. For ≥12 GB disk the smallest fit is **4 GiB/2 vCPU baseline (16 GB)**.
- Cost 4 GiB/2 vCPU: $0.2522/h → **$15.13/60 h**, $45.4/180 h; + image/snapshot storage 29 GB × $0.08 = $2.32; + ~60 suspend/resume cycles × 4 GB × ($0.0038+$0.00155) ≈ $1.3 ⇒ **≈$18.8** (heavy ≈ $49). Cheaper variant: 2 GiB/1 vCPU baseline bursting to 4 vCPU/8 GiB ≈ $9.5 compute, but only 8 GB disk (✗ requirement).
- **Hard limits**: max MicroVM life **8 h incl. suspended time** (`maximumDurationInSeconds` ≤28,800; `suspendedDurationSeconds`); so **no month-long workspace persistence** — durable state must be exported (S3/EBS) on `/suspend` or before 8 h. Account default 400 GB memory (1,024 GB in us-east-1/us-west-2/us-east-2/ap-northeast-1); RunMicrovm 5 TPS; SuspendMicrovm 2 TPS; 8–128 concurrent connections/MicroVM by size. Regions: full list not found; the four above are named.
- Images: zip with Dockerfile in S3 on a **Lambda-managed AL2023 base** (not arbitrary Ubuntu 26.04 root); Lambda builds it and snapshots **memory + disk of the booted app** (like a golden snapshot with memory!). No documented "snapshot a running MicroVM into a new image" API ⇒ per-workspace snapshots ✗/?.
- Capabilities: Firecracker; `--additional-os-capabilities '["ALL"]'` ⇒ **FUSE, EFS mounts, nested containers (containerd)** ✓ (skill doc); Docker daemon not explicitly documented but containerd is. PTY: `SHELL_INGRESS` connector → WebSocket shell on port 8022 with JWE token ✓ ("interactive PTY"). Inbound: per-MicroVM HTTPS endpoint with **JWE token (≤60 min)**, HTTP/2, WebSockets, gRPC, SSE; port routing by header/subprotocol ⇒ Worker-compatible (WebSocket subprotocol auth) ✓. Control plane: SigV4 REST via `@aws-sdk/client-lambda-microvms` / aws4fetch ✓. Idle detection = traffic at the endpoint; a quiet WebSocket shell/terminal needs care; no self-suspend from inside.
- Startup: "near-instant", prefetch from snapshot; numbers not documented. ARM ⇒ **linux-x64 lockfiles/toolchains must be rebuilt for arm64** (brief says possible).
- Verdict: closest AWS feature match, but ≈3× CF price, 8 h life cap, ARM-only, managed base image.

### 3.4 Lambda (event functions) — not viable

15 min max per invocation (90 min only for Managed Instances async), ≤10,240 MB memory, no inbound ports/long-lived sockets, no dockerd/FUSE, no persistent FS (https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html). Lambda _Web Functions_: 2 vCPU/2 GB, 512 MB /tmp, 30 s default request timeout — also no. Use MicroVMs instead (§3.3).

- Capabilities: full VM ⇒ Docker ✓ FUSE ✓ PTY ◐ (own daemon/IAP/SSH). Control: Compute REST + OAuth2 (service-account JWT signable in a Worker) ✓. Inbound previews via cloudflared tunnel or external IP + proxy. Gotchas: Spot preemption (30 s notice), start-from-stop boot time (not documented), you run the control plane/agent.

### 5.1 Azure Container Apps **Sandboxes** (new; found while researching dynamic sessions) — closest match to the requirements

Sources: https://learn.microsoft.com/en-us/azure/container-apps/sandboxes-overview (Oct 16 2026), …/sandboxes-snapshots-state-management, https://sandboxes.azure.com/docs/sandboxes/{cost,sandbox,snapshots,sandbox/lifecycle,disk-images,limits,regions}, pricing page https://azure.microsoft.com/en-us/pricing/details/container-apps ("Express and Sandboxes follow the same pay-per-second pricing as Consumption Plan"), Azure Retail Prices API (East US).

- **Rates (Consumption)**: **$0.000024/vCPU-s** ($0.0864/h), **$0.000003/GiB-s** ($0.0108/h) "active usage"; idle rate (consumption apps) $0.000003/vCPU-s and GiB-s. Free grant 180k vCPU-s + 360k GiB-s + 2M req per subscription/mo (applicability to sandboxes not stated). Sandbox docs: compute billed "per core-second / GiB-second **while the sandbox runs**"; stopped = no compute charge. It is **not documented** whether the idle rate applies to an idle running sandbox.
- **Storage** "charged (coming soon)" at **Premium Blob ZRS $0.20/GB-mo** (Retail API) for custom disk images, snapshots (memory+disk), volumes. Sandbox OS disk not billed. ⇒ 29 GB ≈ **$5.80/mo** once enabled (memory snapshots would add). Egress: first 100 GB/mo free then $0.087/GB ⇒ $0 here.
- Tiers: XS 0.25c/0.5 GiB … M 1c/2 GiB/20 GiB, **L 2 cores/4 GiB/40 GiB**, XL 4/8/80, 2XL 8/16/160, 3XL 16/32/320 (the two docs disagree on XS/S disk; L is 40 GiB in both). Max 3XL = 16 vCPU/32 GiB.
- **Cost (L)**: $0.216/h ⇒ **$12.96 / 60 h gross** ($7.56 if free grant applies); **heavy $38.9 gross / $33.5 net**; if idle running time billed at idle rate: 45 h × $0.0648 + 15 h × $0.216 = **$6.2**. + storage $5.80 when enabled. ⇒ **≈2.5× Cloudflare today unless idle rate applies.**
- Quotas (limits page): **300 concurrent active cores** per region/sub, 3,000 API req/min, 100,000 sandboxes/group, 1 M snapshots. 49 regions (East US, West US 2/3, West/North Europe, Japan East, …).
- Lifecycle: Running/Stopped (+Disabled); **auto-suspend with Memory or Disk mode** (memory incl. processes; Disk = reboot), auto-delete, resume "under a second"; network traffic can wake a stopped sandbox via ingress proxy. Snapshots: memory+disk, group-scoped, regional, **fork into many sandboxes**, depend on source disk image, "restore needs a short warm-up". **`commit` a running sandbox to a new disk image** (golden image at runtime ✓). Custom disk image built from any remote OCI image (ACR/Docker Hub) ⇒ Ubuntu 26.04 image feasible; public `azure-dev` image = "Systemd-based Ubuntu 26.04 … Docker …"; `ubuntu` image includes Buildah.
- Capabilities: **Docker ✓** (shipped in public image), FUSE **?** (not documented), PTY ✓ (`exec/stream` WebSocket in data-plane spec https://github.com/Azure/azure-rest-api-specs/blob/main/specification/app/data-plane/ContainerApps/preview/2026-09-01-preview/containerappssandbox.json ; Python SDK lacks PTY, CLI has `aca sandbox shell`), ports: HTTPS URL per port, anonymous or restricted + private endpoint/VNet; egress proxy with allowlist/credential injection. x86_64 presumably (not stated).
- API: ARM control plane (management.azure.com) + **data plane `management.azuredevcompute.io` REST/WebSocket**; auth Microsoft Entra (role _Container Apps SandboxGroup Data Owner_) ⇒ Worker would use a client-credentials token via fetch ✓ (no gRPC). **Preview API version (2026-09-01-preview)**; GA/SLA not stated.
- Gotchas: preview; storage billing not yet on; idle billing semantics unclear; FUSE unknown; 8–?-h max lifetime not documented (no limit found); anonymous ports are public URLs (need own auth proxy in front for "authenticated route").

### 5.2 Azure Container Apps dynamic sessions — custom container

- Hyper-V isolated sandboxes from your image; pool pre-warms `readySessionInstances`; session lifecycle `Timed` (idle cooldown; any request resets) or `OnContainerExit` (+`maxAlivePeriodInSeconds`); max 600 concurrent sessions; `stopSession` API (https://learn.microsoft.com/en-us/azure/container-apps/sessions-custom-container , …/session-pool).

Retail API: Dedicated vCPU **$0.057077/h**, memory **$0.004978/GiB-h**, plan management **$0.10/h** (applies to Dedicated plan; whether a session pool incurs it continuously is **not documented**). Code-interpreter sessions $0.03/session-hour (built-in Python/Node/Shell only).
- 2 vCPU/4 GiB session ≈ $0.134/h ⇒ **$8.0/60 h**, $24.1 heavy, + pool/ready-instance overhead (unquantified).
- No snapshots/persistence ("ephemeral … destroyed"); privileged/Docker/FUSE not documented; PTY not documented; API is REST with Entra token. ✗ for this workload — superseded by §5.1.

### 5.3 Azure Container Instances — https://azure.microsoft.com/en-us/pricing/details/container-instances/ (prices JS-rendered; used Retail Prices API)

## 7. Recommendations / open questions

1. **Stay on Cloudflare and cut cost at source**: audit what keeps DOs active (terminal/preview WebSockets), default to custom 1 vCPU/3 GiB, resize per task, server-side idle disconnect. CF at 2/6 is ~$0.057/h idle — already below every serverless hyperscaler option.
2. If a cheaper backend is still wanted: **spot EC2 or GCE** (≈$0.035–0.04/h for 2 vCPU) is the only ≥40 % saver that meets Docker+FUSE+snapshots; cost is building start/stop control plane + agent + tunnel and accepting 10–60 s starts (unless suspend/hibernate).
3. **Azure ACA Sandboxes** is the only hyperscaler product with equivalent semantics (sub-second memory+disk snapshots, commit-to-image, PTY, REST/WS from a Worker) but is **preview and ~2.5× price** at gross rates; re-check when storage billing and idle-rate semantics are published, and test FUSE.
4. **Lambda MicroVMs**: promising semantics, but ARM-only + 8 h cap + managed AL2023 base + ~3× price ⇒ not a cost play.
5. Unverified/estimated figures to confirm before deciding: Cloudflare snapshot billing (**not documented**); Fargate Spot $/h (estimate from "up to 70 %"); EC2 spot $ (derived from Spot Advisor discount %); t3 surplus (approx.); ACA Sandboxes idle-vs-active and free-grant applicability; GCE custom 2/4 rate; Lambda MicroVMs snapshot size per suspend (assumed = configured memory 4 GB); suspend/resume/start latencies for EC2/GCE/Fargate/ACI (not documented).
