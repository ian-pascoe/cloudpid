# Self-hosted sandbox backend: rent one machine, run the sandboxes ourselves

Read in this session; Cloudflare docs pages show "Last updated" Aug–Oct 2026, Hetzner pages were live-scraped. Prices are **excl. VAT** unless stated. USD figures use an assumed €1 ≈ $1.15 (not sourced). Anything marked **(unverified)** is background knowledge or an estimate, not read from a primary source in this session.

## TL;DR

- **A self-hosted box is a flat ~€59–99/mo (~$68–115); it only beats Cloudflare Containers if CF spend is above that.** The brief's reference workload costs about **$6.4/mo** on CF at list prices (my arithmetic below), and the heavy 3× month costs about $19. The owner's ">$10 in a few days" suggests roughly $60–100/mo at their real usage, which is roughly break-even. The self-hosted box wins when usage is high, and it removes the per-second anxiety.
- **KVM matters.** Only bare metal (Hetzner AX/Auction, OVH/Kimsufi, Rise) gives `/dev/kvm`. **Hetzner Cloud says nested virtualization is not possible** ([FAQ](https://docs.hetzner.com/cloud/servers/faq/)). **Netcup says the SVM flag is disabled and cannot be enabled, even on root servers** ([FAQ](https://www.netcup.com/en/helpcenter/documentation/server/faq)). On those you are limited to container isolation (runc/sysbox/gVisor/Incus containers).
- **Recommended:** Hetzner **AX41/AX42-class** bare metal (64 GB, NVMe RAID1), Ubuntu 24.04 host, **Incus on ZFS** (containers with `security.nesting` by default, Incus VMs where full-kernel Docker is needed), a small gateway daemon for HTTP/WS, **cloudflared + Access service token** (or Workers VPC, beta) for reach. About **€59–99/mo**. Upgrade path for memory snapshots and sub-second restore: **E2B Embed** (Firecracker).
- **Capacity:** a 64 GB box runs roughly 9 fully-committed or 12–15 overcommitted 2 vCPU/6 GiB workspaces. The owner's 1–3 concurrent sandboxes means any 64 GB box is heavily over-provisioned; a 32 GB box is enough.

**Billing, verified** ([billing FAQ](https://docs.hetzner.com/cloud/billing/faq/)):

- Hourly rate with a monthly cap. Usage is rounded up to the whole hour.
- **Stopped (powered-off) servers are still billed.** Resources stay allocated until the server is deleted.
- The workaround is snapshot + delete + recreate. Snapshots are billed per GB-month on compressed size.
- Backups cost 20% of the server price, with 7 slots.
- Only outgoing traffic is billed; 20 TB is included in the EU (1 TB in the US).
- **Nested virtualization is not possible** ([servers FAQ](https://docs.hetzner.com/cloud/servers/faq/)).
- Net: the Cloud line fits only container-class isolation, and it costs more per core than AX.

### Oracle Cloud Always Free (Ampere A1)

- Current docs: "first 1,500 OCPU hours and 9,000 GB hours per month… for Always Free tenancies, this is equivalent to **2 OCPUs and 12 GB**" ([docs](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)). **The 4 OCPU/24 GB figure in the brief is the older allowance and is no longer what the page states.**
- The allowance is arm64 only, with 200 GB block storage and a 47 GB minimum boot volume.
- "Out of host capacity" errors are acknowledged in the docs.
- Oracle **may reclaim idle Always Free instances**: below 20% CPU p95, network and memory over 7 days. A bursty single-user agent box would hit this.
- Nested virtualization/KVM on A1 is **not documented** in the page I read.
- Verdict: free, but arm64, 12 GB, reclaim risk and no documented KVM. Only suitable for a gateway or control-plane sidecar, not for sandboxes.

**Firecracker snapshot caveats** (from its own doc):

- Snapshots must be resumed on **identical hardware and software**, with only a limited host-kernel-upgrade table. A host kernel upgrade can strand memory snapshots, so keep a fallback of disk-only cold boot.
- Guest network connectivity is not guaranteed after resume.
- Diff snapshots are still developer preview.
- Restore latency is high on cgroup v1; use cgroup v2.
- Snapshots taken early in kernel boot may crash on resume.
- Clones need per-clone uniqueness handling (VMGenID/RNG).

**Wrappers.**

- _firecracker-containerd_ ([repo](https://github.com/firecracker-microvm/firecracker-containerd)) and _flintlock_ ([repo](https://github.com/weaveworks-liquidmetal/flintlock)) manage Firecracker microVMs via containerd. Both are gRPC-first, so you need an HTTP gateway. I did not confirm that they expose snapshot/restore of memory state.
- Both are low-level and not agent-oriented.
- For a Worker-controlled single box, prefer a purpose-built sandbox server (E2B, Arrakis) over either.

**E2B Embed details** ([compose README](https://github.com/e2b-dev/infra/blob/main/embed/compose/README.md), [reference](https://github.com/e2b-dev/infra/blob/main/embed/docs/REFERENCE.md)):

- It requires Linux x86-64 or arm64, KVM, `/dev/net/tun`, Docker 27+, a 4 KiB-page kernel, and cgroup v2. **Ubuntu 24.04 is the recommended host**; kernel 6.8+ on x86-64 (6.10+ on arm64).
- It recommends **12 GiB RAM and 20 GiB free disk** for the stack itself.
- It runs 4 stores (Postgres/ClickHouse etc. in containers), api, client-proxy, dashboard and an orchestrator.
- **The orchestrator's gRPC port 5008 is unauthenticated.** 13 ports listen on all interfaces, and 10 must never be reachable. The README says to give the machine no public address of its own or firewall those ports.
- It speaks **plain HTTP only**, with no TLS, so it needs a reverse proxy or tunnel in front.
- Templates are built from images through the API. The Ubuntu 26.04 image with dockerd inside needs testing of the guest kernel for overlay2/cgroup v2. The default E2B kernel config is not verified.
- It is beta-like: pinned images, no high availability, and "one machine, by design".

## 6. Recommended stack for the reference workload

**Hardware:** Hetzner **AX41 (€59/mo, €0 setup)** or an **auction box** with at least 6 cores, 64 GB RAM, NVMe RAID1, KVM. Go **AX42 (€79–99 + €49)** if you want a Zen4 8c/16t with DDR5 ECC. A 32 GB box would suffice for 1–3 workspaces, but 64 GB leaves room for overcommit.

**Software (lean path, fewest moving parts):**

1. Ubuntu 24.04 host with ZFS on the NVMe pair (mirror), cgroup v2, `unattended-upgrades`.
2. **Incus**. A golden image per environment: `incus copy golden/<env> ws-<id>` is an instant ZFS clone, which gives the "Build" snapshots. Idle stop does `incus stop` plus `incus snapshot create` (instant on ZFS); restore is `incus start`.
3. Workspaces as **system containers** with `security.nesting=true` for dockerd (overlay2 on ZFS needs a recent OpenZFS; if it fails, use an ext4/xfs zvol for `/var/lib/docker`, **unverified**). If that fails, or for untrusted code, switch the workspace to an **Incus VM** (own kernel, stateful snapshots possible).
4. A small **gateway** (Go/Node, ~500 LOC) that exposes `exec`, `pty`, `files`, `snapshot`, `start/stop` and port-proxy over HTTP/WS, wrapping the Incus API, and authenticates the Worker (Access headers).
5. **cloudflared** → gateway; Access service token for the Worker.
6. Nightly `zfs send` (incremental) to off-box storage.
7. Drop `computerd`/FUSE: `/workspace` is a bind mount or ZFS dataset, with no sync daemon.

**Upgrade path:** swap the Incus layer for **E2B Embed** if you need memory snapshots, fork or sub-second resume. Cost is the same box, minus about 12 GiB RAM for the stack. It brings its own SDK/API, so the Worker integration would target the E2B REST API.

**Estimates, all unverified (no benchmark run):** a ZFS-clone container start is about 1–3 s; Incus VM cold start about 5–10 s; Firecracker restore under 1 s (E2B's claim of near-instant resume).
