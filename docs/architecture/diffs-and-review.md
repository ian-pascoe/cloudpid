# Diffs and review

This document is being built, from the parent issue "Diff viewing and Reviews" (#235). The design was settled on the map "Diff viewing and Reviews with @pierre/diffs" (#99), and each bullet links the ticket that holds the detail. Each slice of the build replaces its bullet with the full description as it lands. Terms are in GLOSSARY.md → _Diffs and review_ (Changes, Comparison, Call diff, Run diff, Annotation, Review). Where the diffs are computed is [ADR-0022](../adr/0022-diffs-come-from-the-workspace-do.md).

- **Rendering:** [`@pierre/diffs`](https://diffs.com), pinned to an exact version (`1.6.2`, in `apps/web`).
  - Its theme is a CSS-variables theme (`cloudpid`, registered in `apps/web/src/diff-theme.ts`, which the lazy modules that draw diffs import) in the notebook skin: the `--diffs-*` variables sit beside the tokens in `styles.css`, take the tokens' light and dark values (the library's own `color-scheme: dark` on its host is reset to the page's, so its `light-dark()` washes follow the page), and show additions and deletions as washes of Run Green and Brick Red.
  - The library and its highlighter are a chunk of their own, fetched when the first diff opens (`patch-view.tsx` and the Diff pane's `changes-view.tsx` are imported lazily).
  - **The empty `FileDiff`:** a `FileDiff` whose `<diffs-container>` is detached and attached again while its first render waits for the highlighter (a StrictMode double ref, or a Suspense boundary that hides and reveals the tree) stayed an empty `<pre>` for good. `FileDiff.render` creates the `<pre>` before it knows whether it can fill it, and when the highlighter is not loaded yet leaves it empty until the highlight resolves. The new instance's `hydrate` takes any existing `<pre>` for prerendered output (`shouldRenderCode` tests `pre == null` only), so it sets up as hydrated, renders nothing, and nothing asks it to render again once the highlighter loads. Reported upstream as [pierrecomputer/pierre#1233](https://github.com/pierrecomputer/pierre/issues/1233) and fixed in `1.6.2` by [#1219](https://github.com/pierrecomputer/pierre/pull/1219): `cleanUp` removes the `<pre>`, so the next instance finds none and renders. No component of ours waits a tick to mount a diff.
  - A Call diff is a `FileDiff`, highlighted on the page. A whole source is one virtualized `CodeView` highlighted on a Worker Pool (`getOrCreateWorkerPoolSingleton`, `apps/web/src/diff-pane/workers.ts`), sized to half the cores and kept between 2 and 4 (`poolSize`, `loading.ts`). Measured against no pool on a production build in headless Chromium (4 cores, so 2 workers) on 200 files, one of 10,000 lines: opening the Pane blocked the page for 0.15–0.18 s in all with the pool and 3.5–5.6 s without (its longest task 0.1 s against 3.3–5.3 s), and scrolling the whole list 0–0.06 s against 5.3–6.5 s (the longest frame 50 ms against 200–320 ms), so the pool stays (#229).
  - A dedicated Web Worker (`line-up.worker.ts`) lines up each file pair with jsdiff (`createTwoFilesPatch`, four lines of context) under its `timeout` of 2 s (`LINE_UP_TIMEOUT_MS`, `line-up.ts`; the browser's clock moves while code runs, unlike workerd's). Past it, the file shows as a whole-file replacement (every old line removed, every new one added), marked "Replaced whole: lining it up took too long" in its header, and stays annotatable. A 0.9 MiB full rewrite shows that way about 3 s after it is asked for, the page never blocked for more than 0.13 s (without the pool, its highlighting on the page blocks it for 5–8 s).
  - The library's limits stay as they are: long lines and very long files are shown plain (`tokenizeMaxLineLength` and `maxLineDiffLength` 1,000 characters, `tokenizeMaxLength` 100,000 lines: `DIFF_LIMITS`).
  - Decided in #101, #104 and #222.
- **Call diffs** on `edit`, `write` and `codemode` cards.
  - `edit` records a patch (`details.patch`, a unified diff with four lines of context). The transcript puts a call's Call diff on its card (`artifact.diff`, only for a call that finished without an error), so a call that failed, was stopped or is still running, an `edit` from before the patch was recorded, and a `write` from before the wrapper (no `details`), show the card they always had. Built: `apps/web/src/call-diff.ts` (`CallDiff`, `callDiffOf`, `patchCounts`, `diffTotals`, `capPatch`, `diffStyleFor`, unit-tested) and `apps/web/src/chat/call-diff-card.tsx`.
  - **Card, `edit`:** the card's line carries `+n −m` (Run Green, Brick Red) beside the path. Opened, a header with the file path and an _Arguments and result_ toggle (which shows them under the diff) replaces the arguments, and the diff is drawn by `parsePatchFiles` and `FileDiff` with no way to expand unchanged lines. It is split from a card width of 720 px (`SPLIT_MIN_WIDTH`) and stacked below, measured before the first paint and followed with a `ResizeObserver`. It shows at most 2,000 diff lines (`CALL_DIFF_LINE_CAP`: added, removed and unchanged ones; the cut hunk's counts are written again), then a _Show all n lines_ button. The diff is only mounted while the card is open. Its gutter drafts Annotations (see _Annotations and Reviews_).
  - **`write`** is pi-durable's tool wrapped (`packages/extensions/src/coding-tools.ts`, the pure part in `call-diff.ts`). It reads the old file before the write and, once the write has succeeded, records in `details` the patch `edit` records (both headers name the path as the model gave it, four lines of context), plus the `path` and `created: true` for a new file (the shape is `RecordedDiff`, `@cloudpid/protocol/call-diff`, which the web app decodes too). A symbolic link is judged by the file it points to. The write is never held back by it: a diff that cannot be made leaves `write`'s own result. The patch is skipped, and only `path`, `created` and a flag recorded, when:
    - the old file is binary (a NUL in its first 8,000 bytes) or could not be read: `binary`;
    - the old and the new text together pass 1 MiB (UTF-8 bytes; an old file whose size alone puts it past that is not read), the patch passes 512 KiB (counted as it is stored, JSON-escaped, so a quote takes two bytes; a new file whose text alone passes it is not diffed at all), or the line-up of a change in the middle of a file passes 1,000 lines added and removed (jsdiff's `maxEditLength`; about 0.13 s of Node's time for a file whose every line differs): `tooLarge`. That bound needs no clock: workerd's `Date.now()` stands still while code runs, so jsdiff's 1 s `timeout`, kept as a second guard, does not fire there. A new file, an append and a truncation cost only their length, so they are not held to it.

    A write that leaves the file as it was has a patch of its two headers. A stored `write` result holds at most a 512 KiB patch (a 1 MiB write has none: a few hundred bytes), well within the 2 MB row. The old text is read outside pi-durable's per-file mutation queue, which it does not export: two writes to one file at once may show each other's text as old.

  - **`codemode`:** the same coding-tools extension has an `afterTool` hook on the `codemode` call itself. When the script ends, each nested call's result is in the call's `NestedCallDoc` (the nested task's `details` are kept there, but pi-durable's own `details` for the script list only its rows), so the hook reads those of the finished `edit` and `write` rows and adds `details.diffs`, keyed by the call's number in the script (the row's `id`) and holding the call's patch fields and its `path` (an `edit`'s is read from its patch's header; a nested row's arguments are cut for display, so the row shows the file from this). A hook that fails for any reason leaves the result as it is. A script that fails partway keeps the diffs of the calls that finished; a script stopped before its result is stored has none (Changes still has the changes). The patches of one result share 256 KiB (`MAX_CODEMODE_DIFF_BYTES`), in call order, so a script that changes many files cannot fill the 2 MB row it shares with its output and images: a call past it is `tooLarge`, as one whose patch passes 512 KiB.
  - **Cards:** an `edit` or `write` card's folded line carries `+n −m` after the path, a "new file" mark for a create, "No change" in place of `+0 −0` where a write left the file as it was, and "Too large to show here" for `tooLarge` and `binary`; opened, the same diff (or that text) replaces the arguments. A `codemode` card's Calls list gives each `edit` or `write` of a script that ended the same on its line and opens it to its diff in place (the open state is kept in the layout, under `<call>/c<n>`), and the folded `codemode` line shows the total `+n −m` of its calls.
  - **Open in Diff pane:** an opened Call diff's header has _Open in Diff pane_, which finds the call's file among the Changes the page watches (the Session's, or on a Subagent page the subagent's) (`findChange`, `apps/web/src/diff-pane/changes.ts`: the path is resolved against the Session's directory, the one repo's clone when the Session lists one repo and `/workspace` otherwise (`workspaceDirectory`), `.` and `..` included, and must be a changed file's `/workspace/<repo>/<path>` exactly) and opens the Diff pane at it, unfolded. While the current list has no Changes in the file (committed, reverted, or never listed) the header says "No Changes in this file now" in its place, until a list has the file again. A call made in another Workspace than the one whose Changes the page shows (told by the task graph's branch: a subagent's in a Subagent Workspace, seen from the Session page) has no _Open in Diff pane_; on that subagent's Subagent page it has.
  - Decided in #100, #105 and #222.
- **Changes** (#228; decided in #102, #106 and #222): each repo's working tree against its HEAD, staged or not, untracked files included and ignored ones not.
  - **The module.** `WorkspaceChangesModule` (`apps/server/src/workspace/changes.ts`) answers two Workspace DO calls, `changes({ directory, startContainer })` (the list of every repo the directory covers: its one repo, or every repo at the Workspace root) and `changeFile({ repo, path, oldPath })` (one file's two sides). It chooses the backend inside, per repo, so no caller knows which ran.
  - **Its own reading.** By default the Workspace DO reads the repo itself with isomorphic-git (1.44.5, pinned: computer does not export the copy it depends on), over a read-only view of its files whose writes fail with `EROFS` and which pauses for a turn of the event loop every 50 reads (`YIELD_EVERY`), so the Workspace DO's other calls (the agent's file tools) are served during a listing rather than after it: `statusMatrix({ refresh: false })` for the list, which never writes `.git/index` (the Container's git owns it too; a test checks its bytes), `readBlob` for the HEAD side, and the file for the working side. The Workspace DO's files have their own inodes, owners and times, so no stat matches what git recorded and every tracked file is read and hashed at each listing: there is no stat cache to drift, and none to trust wrongly (see [_Changes in the Workspace DO_](risks-and-spikes.md)).
  - **The Container's git** takes a repo over when it tracks more files than the guard (`MAX_TRACKED_FILES`, 2,000, read from the index's header), when its packs total over 16 MB (`MAX_PACK_BYTES`), when the root `.gitattributes` has rules git applies when it compares (`text`, `eol`, `binary`, `filter`, macros included), or when isomorphic-git fails on it. Its script (`changesScript`, `apps/sandbox-image/src/changes.ts`, tested in plain bash) copies the index to a private `GIT_INDEX_FILE`, adds untracked files there with `--intent-to-add`, and runs `git diff <HEAD> -M --raw --numstat -z` against HEAD (the empty tree before the first commit) with `cat-file --batch-check` for the HEAD sides' sizes; `headBlobScript` reads a HEAD side.
  - **Never started on its own.** Only a listing with `startContainer` (the owner's Refresh) starts a stopped Container; any other uses it only when it runs. A repo that needs it while it is stopped keeps its last list from the Container's git, kept in the Workspace DO's storage (`cloudpid:changes:<repo>`), marked `stale` ("may be out of date"). A listing that fails on the Container keeps that list too, with the `error`. `changeFile` never starts it: a HEAD side it would need a stopped Container for fails with a message to refresh by hand.
  - **Each repo** has its HEAD (`commit`, null before the first; `branch`, null when detached), which Comparisons use, its files sorted by path, `more` (how many changed files past the cap were not listed; a rename among them counts as two, as pairing would mean reading them), `stale`, and an `error` when its listing failed.
  - **Each file** has its path, `oldPath` for a rename, its status (`added`, `modified`, `deleted`, `renamed`) and `+a −d`.
    - **Renames** are paired only when the blob ids match; a file moved and edited is a deletion and an addition. The Container's git pairs as git does (`-M`).
    - **Binary**: a NUL in the first 8,000 bytes of either side; no counts.
    - **Too large**: a side over 1 MiB, still listed, with its counts when known (the Workspace DO does not read a working side that large, so it has none).
    - **Counts** are lined up with jsdiff within bounds of work, not time, as workerd's clock stands still while code runs (so jsdiff's `timeout` never fires deployed; it is kept as a second guard): a file is looked at for at most 500 edits (`MAX_COUNT_EDITS`), and fewer the longer it is (lines × edits up to `COUNT_WORK`, 5,000,000), so one file is under about 100 ms; a listing lines up at most `LISTING_COUNT_WORK` (25,000,000, about half a second) in all. A file past its bound, or past what is left of the listing's, gets whole-file numbers marked `approximate` ("≈"). Counts are kept by the pair of blob ids (10,000 pairs), so an unchanged file is not lined up again. A pair with a side over 1 MiB (the HEAD side too, though `readBlob` reads it whole) is not counted.
    - **Folding flags**: `generated` and `vendored`, from the root `.gitattributes` `linguist-generated` and `linguist-vendored` (the last matching rule wins; absent when no rule names the file).
    - Tracked files on Container-only paths are left out: the Workspace DO never holds them.
  - **Caps:** 2,000 files across the repos (`MAX_CHANGED_FILES`), then "and n more"; 1 MiB a side (`MAX_CHANGE_SIDE_BYTES`).
  - **On the Session socket** (`apps/server/src/session/changes.ts`, wired in `sockets.ts` as `watch_usage` is): `watch_changes` streams `changes` messages, each replacing the last, and `unwatch_changes` stops them; the watch is in the socket's attachment, so a Session woken from hibernation lists them again on the same socket. Without `conversationId` they are the Session's Workspace's; with one (a Subagent page's, ADR-0024) they are those of the Workspace that conversation works in, resolved through the Subagents document as its tools resolve it (`SessionHost.workspaceOf`: its Subagent Workspace, else its nearest ancestor's, else the Session's), and each `changes` message and failed listing's `error` names the `conversationId` the client did. A socket may watch several, one per `conversationId`; a conversation's watch follows it to another Workspace as the Subagents document changes (a Subagent Workspace given to its agent, or to an ancestor, later: `SessionHost.workspaces`). A conversation that is neither a Session branch nor a live subagent's fails the command (`watch_changes`, `refresh_changes`, `change_file`), and one deleted while watched, or while the Session hibernated, ends its watch with an `error` marked `changes` and `ended` that names its `conversationId`: the client drops the watch and does not ask for it again. Each Workspace has one broadcast, made by its first watch, so two conversations in one Workspace share its listing; a Subagent Workspace's is dropped when its last watch ends, a `refresh_changes` of one nobody watches lists nothing, and a `change_file` reads its Workspace directly. `change_file` answers a `ChangeFile` (`old` and `new`: text, binary, too large with its size, or null for a side that does not exist). `refresh_changes` lists them again; with `manual` it may start the Container, and a `changes` message with `startingContainer` over the last list says so while it does when that list had a repo marked `stale`.
  - **When they are listed:** when a client starts watching (a page connects); 1 s after the last writing call (`edit`, `write`, `bash`, `codemode`) of an agent, for the Workspace it works in (a wrap installed after the other extensions, `changesRefreshingTools`: a subagent in a Subagent Workspace lists that Workspace's again, not the Session's); and on a client's `refresh_changes` (focus, the Pane opening, the owner's Refresh). One listing serves every client: a refresh asked for while one runs is folded into one more after it. A listing reads its Workspace (the Session's, or a Subagent Workspace) without readying it, so it clones nothing. A listing that fails sends an `error` marked `changes: true` (so a client tells it from the other errors), and the last list stands.
- **Comparisons** (This branch: #231; open pull requests and the Viewed boxes: #232; decided in #103, #107 and #108): a repo's branch, or one of its open pull requests, against the point where it left its base.
  - **What it compares.** The head is the local HEAD, unpushed commits included. The base is the base branch of the branch's open pull request (found through GitHub's REST API with a GitHub token, the remote's URL read from `.git/config`, so a stacked branch compares with its parent), else the remote's default branch (`refs/remotes/<remote>/HEAD`, else `git ls-remote --symref`); a repo with no remote uses the first of `main`, `master`, `trunk` and `develop` that exists locally. A GitHub lookup that fails (no token, no network, no open PR) falls back to the default branch and is logged; a non-GitHub remote has no PR to look for and gets This branch all the same. Only a fetch, a first comparison or a changed branch (a checkout: another branch has another PR) looks up the PR: a comparison recomputed because HEAD moved on the same branch reuses the base it had. The files are the commits only (the repo's uncommitted files are the Changes': the Pane says "n uncommitted files: see Changes"), from the merge-base to the head, with the entry type, counts and caps of the Changes (binary from numstat's `-`, 1 MiB a side, 2,000 files then "and n more"). A detached HEAD reads "detached at `abc1234`"; no commits beyond the base read "Nothing to compare".
  - **The module.** `WorkspaceComparisonModule` (`apps/server/src/workspace/comparison.ts`) answers three Workspace DO calls: `comparisonSources(directory)` (each repo the directory covers with its HEAD, read with isomorphic-git, never the Container), `compare({ repo, startContainer, fetch })` and `comparisonFile({ repo, mergeBase, head, path, oldPath })`.
  - **One Container command** (`comparisonScript`, `apps/sandbox-image/src/comparison.ts`, tested in plain bash against real repos) does the fetch, the merge-base and the file list. The remote is the branch's tracked remote, else `origin`, else the only one; it follows `--` in every git call that takes it, so a remote named like an option is not read as one. The fetch is `git fetch --refmap= --no-write-fetch-head --no-auto-maintenance --no-tags --no-recurse-submodules --no-prune -- <remote> '+refs/heads/<base>:refs/cloudpid/base/<base>'` and retries once on `cannot lock ref`: it writes only the hidden `refs/cloudpid/base/*` ref, and never `refs/heads`, `refs/remotes`, `FETCH_HEAD`, the index or the tree (the tests check each; the empty `--refmap=` is what keeps git from also updating `refs/remotes/<remote>/<base>` opportunistically, which it does for a fetch of a branch that remote-tracking ref follows). The merge-base is local (`git merge-base`), and the list is `git --no-optional-locks diff -M --no-ext-diff --no-textconv --no-color --raw --numstat -z --no-abbrev <merge-base> <head>` with `cat-file --batch-check` for the sizes. It answers the list or an error kind: `no_remote`, `no_base`, `no_common_ancestor`, `shallow` or `too_big`; anything else is `failed` with the end of git's output, with credentials in a URL taken out.
  - **Kept in the Workspace DO's storage** (`cloudpid:comparison:<repo>:<merge-base>:<head>`, the last five per repo, their index under `cloudpid:comparison-keys:<repo>`, and the last pointer per repo under `cloudpid:comparison:<repo>`): a list for the same (merge-base, head) is read from there, so reopening after the Container's idle stop starts nothing (a list over 1.5 MB is not kept, and the last pointer stays at the list before it, so a pointer never names a list that is not there). A request for a repo whose HEAD is the kept list's, with no `fetch`, answers it without the Container. A request that needs one (nothing kept, or `fetch`) while the Container is stopped and may not start it answers `needs_container` (with the base, once chosen). A request that finds HEAD moved while the Container is stopped answers the last list marked `behind` (the commit HEAD moved to), which the Pane shows as "New commits: Refresh"; with the Container running it is recomputed by itself, without fetching the base again (the Container is looked at again after the base lookup, which waits on GitHub: a Container that stopped meanwhile is not started by it). Only `startContainer` (the owner's pick of This branch or Refresh) starts a stopped Container, and nothing automatic does (ADR-0022).
  - **Contents.** `comparisonFile` reads each side with isomorphic-git's `readBlob` by the blob ids the list kept (the Workspace DO holds the repo's objects), under Changes' guards: a repo whose packs total over 16 MB, or an object the Workspace DO does not have, is read by the Container's git instead (`blobsScript`: one `git cat-file --batch` for all the ids) if it runs. It never starts the Container: a side it would need one for fails with a message to refresh by hand. When the list is not kept, a side is found by commit and path: a file missing at a commit the Workspace DO has is no side, but a missing commit is an error (it must not read as an added or deleted file). A side over 1 MiB or binary is not read.
  - **On the Session socket** (`apps/server/src/session/comparisons.ts`; request commands, not a watch, as a Comparison is fixed by its SHAs): `comparison_sources` answers the repos with their HEADs, the Session's own repo first; `compare` (`repo`, `source: "branch"`, `startContainer`, `fetch`) answers a `CompareResult` (the Comparison: base and branch names, merge-base and head SHAs, commits, files and `more`; or an error state, which is an answer, not a failure); `comparison_file` answers a `ChangeFile`. A `compare` that made a Comparison also checks the drafts on that repo's branch against it (see _Annotations and Reviews_).
  - **In the Diff pane.** The source picker is grouped by repo (the Session's own first): each repo's _Changes_, then _This branch (name)_. Picking This branch, and Refresh (the header's, the error's _Retry_ and the "New commits: Refresh" line), are the owner's own actions: the Pane asks without the Container, and when the Session says `needs_container`, or answers the last list marked `behind`, it says "Starting the Container…" and asks again with `startContainer`. Refresh on This branch also fetches the base again. Each error state shows in place of the file list: "Starting the Container…", "No remote", "No common ancestor with `<base>`", "Shallow clone: base unknown", the end of git's error output for anything else, with _Retry_ (_Start the Container and compare_ for `needs_container`). When the shown repo's HEAD moves (read from the Changes refresh) the Pane compares again without the Container (never while the owner's own compare, a Refresh that fetches, runs: that is not interrupted, and the HEAD that moved meanwhile is followed when it ends); the result is the new Comparison, or the last one with the "New commits: Refresh" line. The picker's repos are asked again only when a repo's HEAD or branch moves, not at each listing of the Changes. **Session page only:** the Comparisons are the Session's own Workspace's (the socket's `comparison_sources`, `compare` and `comparison_file` carry no conversation), so a Subagent page's Diff pane (the Workspace of its subagent, ADR-0024) lists no repo for This branch and offers the Changes alone, as it draws no drafts (a subagent's This branch comes with the per-Workspace Comparisons, if the owner wants them).
  - **Pull requests** (#232). A repo whose remote is on GitHub lists its open pull requests in the picker, as _Pull requests_ under each repo's This branch: `#7 Title · author · draft · 4 files · +12 −3 · abc1234` (the file count and the head's first seven characters), the one of the checked-out branch first with "this branch" (its head branch is the repo's current branch and its head repo the same repo). They are a **Comparison** like This branch (`compare` with `source: "pull"` and `pull: <number>`; `Comparison.pull` carries the number, title, author, draft flag and `state`), and nothing about a pull request is a source of its own beyond that. Like This branch they are the **Session page's** only: a Subagent page's Diff pane lists no repo for them (its `comparison_sources` is not asked), and the Viewed boxes and pull request drafts are the Session page's too.
    - **The list.** `comparison_sources` takes `pulls: true` (the Pane always sends it: when it opens, at each opening of the picker, when the owner comes back to the page and when a repo's HEAD moves, so the list is in the picker before it opens and the 60 s keep below bounds what GitHub is asked); each repo then carries `pulls`: `{ status: "ok", pulls, fetchedAt }` or `{ status: "error", kind, message }` with `kind` `no_github` (the picker shows one disabled line, "Pull requests need a GitHub remote"), `refused` (GitHub's 401 or 403 for the token, or GraphQL's `NOT_FOUND` for a repo the token cannot see, which a private repo answers with a 200: "GitHub refused the token") or `failed` (no network, a rate limit, an answer that is not a list). A rate limit (a 429, a 403 with `x-ratelimit-remaining: 0` or `retry-after`, or GraphQL's `RATE_LIMITED`) is `failed` with a message of its own ("GitHub's rate limit is used up") and holds every GitHub request of the Workspace DO until the wait GitHub asked for is over (at most 5 minutes); it is not a refusal. The Workspace DO asks GitHub with a GitHub token, and once more with a new one when GitHub answers 401; one that cannot be minted is `failed` ("No GitHub token: <why>") (`apps/server/src/workspace/github-pulls.ts`, the one client of every GitHub call, answers recorded from the real API as its test fixtures): **one GraphQL query** (`repository.pullRequests(states: OPEN, orderBy: UPDATED_AT desc, first: 50)`, at most `MAX_PULLS` = 50, most recently updated first) that carries each pull request's title, author, draft flag, head SHA and branch, base, repo and its `additions`, `deletions` and `changedFiles`, so there is no request per pull request; the list is kept **60 s per repo** (concurrent askers share one request), and a failure **15 s** (`ERRORS_CACHE_MS`: the same call inside it answers the same failure, so a refused or rate-limited token is not asked again on every opening). A count GitHub has not computed yet is null and the picker leaves it out. The list covers only the 50 most recently updated open pull requests: an open one ranked lower is not in the picker, and loses its hidden ref (below), which `compare` fetches again on demand. It never starts the Container, and answers without waiting for the deletion of refs, which runs after it (below).
    - **Making one.** `compare` asks GitHub for the pull request's state, head and base first (`get`, REST; a 401 or 403 answers `github_refused`, a rate limit and a 404 answer `failed` with their own messages: a 404 is "GitHub has no such pull request, or the token cannot see the repo", since it may be only a number that does not exist). **Closed or merged**: the last result kept for it, marked `pull.state` (`closed` or `merged`, which the Pane says: "Merged: this is its last result"), else the error `pull_closed` or `pull_merged`; nothing is fetched. **Open**: a result kept for the same (merge-base, head) is answered without the Container. A head that moved while the request may not start the Container answers the last result marked `behind` (the new head), or `needs_container` when there is none; a pull request is never recomputed by itself, even with the Container running, as there is no HEAD to follow. A result too big to keep whole (over 1.5 MB, `MAX_KEPT_BYTES`) is cut to fit before it is kept: files are dropped from the end of the list, by halves, and counted in `more` ("and n more not listed", as past the 2,000 files cap), so there is always a list to answer a page's return with, and the Container is never run again just because a list was too big to keep. `startContainer` (the owner's pick or Refresh, or "New commits: Refresh") runs the Container command, which fetches `+refs/pull/<n>/head:refs/cloudpid/pr/<n>` together with the base and compares `refs/cloudpid/pr/<n>` with **the pull request's own base branch** (so a pull request stacked on another compares with the branch under it); a head the remote no longer has (`failed`: "Pull request #n is not on <remote>") and a repo with no remote (`no_remote`) are error states. The files carry `blob`, their head blob id (a deleted file's, the merge-base's), which the Viewed boxes are checked against.
    - **Hidden refs** (`refs/cloudpid/pr/<n>`) are the harness's own, like the Comparison bases (see _Container_ above): they never touch `refs/heads`, `refs/remotes`, `FETCH_HEAD`, the index or the tree. The Workspace DO remembers which numbers it fetched (`cloudpid:comparison-pull-fetched:<repo>`) and deletes the refs of pull requests no longer in the picker's list (the 50 most recently updated open ones: a lower-ranked one loses its ref too and is fetched again on demand) with `git update-ref -d`, only when the Container is already running (never `gc`, never a start for it). The deletion runs after the picker's list has been answered, in the background (one at a time per repo, behind that repo's own Comparison in its queue), so a picker opening never waits for it or for a Comparison that is starting the Container.
    - **Kept** under `cloudpid:comparison-pull:<repo>:<merge-base>:<head>` (the last ten per repo, `KEPT_PULL_COMPARISONS`, their index at `cloudpid:comparison-pull-keys:<repo>`; the last per pull request at `cloudpid:comparison-pull-last:<repo>:<n>`), apart from This branch's five.
  - **Viewed boxes** (#232). Each file of a pull request has a **Viewed** checkbox in its header (and nothing else does: not the Changes, This branch, or a Call diff). The Pane shows "n of m viewed" beside the totals. Ticking folds the file and unticking opens it; a Viewed file starts folded.
    - **Kept** in the Session DO (`apps/server/src/session/viewed.ts`), keyed by (repo, pull request, path) and recording the file's head `blob` at the tick (`cloudpid:viewed:<repo>:<pull>`, the keys indexed at `cloudpid:viewed`; at most `MAX_VIEWED` = 5,000 boxes and 900,000 characters of their repos, paths and blobs in all, `MAX_VIEWED_CHARS`, so a pull request's one stored value and the list sent to every client stay bounded; a tick past either is refused with a message, an untick never), so they are the same on every device. `viewed_set { repo, pull, path, blob }` ticks (`blob` the file's) or unticks (`null`) and answers `null`; the Session sends the whole list as `viewed` after `hello` on every connect (an empty list too) and to every client when it changes, as it does the drafts. A Fork or Clone copies none.
    - **Reset on change.** A box counts as ticked only while its recorded blob is the file's blob in the Comparison on the screen, so a file that changed since is unticked at once in the Pane. The Session also drops those boxes, when a `compare` makes an open pull request's Comparison: those whose file's blob differs, and those whose file the Comparison no longer lists when it lists every file (`more` is 0). A Comparison of a pull request that comes back closed or merged drops all that pull request's boxes (nothing is left to untick them by, and they would count toward the limits); one marked `behind` is not the pull request's head and changes none.
    - **Annotations** on a pull request's files are `kind: "pull"` drafts (see _Annotations and Reviews_).
- **Run diff (Last run)** (#233; decided in #220 and #109): what the latest writing Run changed in each Repo, from a copy made before its first write to the files now (live) or to a copy made when it ended (frozen).
  - **What a Run is here.** A Run opens at the first writing call (`edit`, `write`, `bash` and the other `WRITING_TOOLS`) of the root conversation, or of a subagent that works in the same Workspace while the root conversation is working (a subagent the owner messaged alone, with the root idle, opens none), after the Session went idle, and closes the moment the Session next goes idle (`onSettled`, the first step after `waitForIdle`, so the next prompt's first write opens the next Run and never finds this one): its end copy is then made in the background, and the owner's notification and the title do not wait for it. A subagent that has a Workspace of its own opens none. The call waits for the start copy (`runStart`) for at most 5 s (`WRITE_DEADLINE_MS`, a real timer, since workerd's clock stands still in code); a copy that is late leaves the Run "not captured" (`failed`), the write goes on, no later write of the Run asks again, and the Run's end says `missed` so the Workspace copies nothing more for it. A start that fails before the Workspace has saved the Run leaves the earlier Run as the Last run: the new one is not announced (nothing of it exists in the Workspace to show), and its write goes on all the same. The first write of the next Run waits just as long for the previous Run's end copy (`ending`); the Session stops waiting for the end copy after 30 s (`END_DEADLINE_MS`) but not for its answer: the Workspace goes on (a Run of several Container repos takes up to 25 s a repo), and when the answer comes the clients are told (`ended`, `last_run`, the last check of the drafts), unless a newer Run is the Last run by then. The Workspace bounds its own Container calls: a Run copy 20 s on the Container and 25 s for the Workspace, a listing by the Container's git 60 s (`CONTAINER_LISTING_TIMEOUT_MS`), so one stuck call cannot hold its queue. A second idle while the end is under way, or after it, ends nothing again; an end lost to an eviction is made again at the next idle, at the entry stored when the Run closed. Subagents' writes made after the root's turn ended, which the Session's idle does not wait for (their tasks are background work), belong to no Run: the next prompt opens the next one. `LastRun` (`@cloudpid/protocol/last-run`) says the Run (`run`, an ID the Session makes), its conversation, `startedAt` (the Session's clock at the first writing call) and `endedAt` (null while live), `firstCall` (the model's ID of its first writing call, a subagent's when it wrote first), `until` (the conversation's last entry when it ended; null while live), `empty` (ended with every repo captured and no file changed: nothing to show) and per repo the commits of the `start` and `end` copies, or why there is none (`notCaptured`: `container_stopped`, `too_many_files`, `failed`). Only the latest Run is kept, and the Runs the drafts' `run` sources still name (`keep`, so a draft on an earlier Run is not left without its lines). The Session keeps the open Run under `cloudpid:last-run:open` and the last under `cloudpid:last-run`; an eviction mid-Run finds the open Run again and ends it at the next idle.
  - **The copies** (`apps/server/src/workspace/runs.ts`, the Workspace DO; RPCs `runStart`, `runEnd`, `runDiff`, `runFile`; the Session's scope is its ID, so Sessions on one Workspace keep theirs apart): a copy is a commit made with isomorphic-git, never touching the repo's index, branches, remote-tracking refs or working tree, under `refs/cloudpid/runs/<scope>/{start,end}` (and `…/kept/<run>/{start,end}` for a kept Run). Its tree is HEAD's with the files that differ from HEAD (the uncommitted work) replaced by their bytes, written as blobs; its parent is HEAD. The differing files come from `statusMatrix({ refresh: false })` over a read-only view (so a file whose stat looks racy is hashed, not trusted). An executable bit is kept; a symlink is a blob of mode 120000. A file over 1 MiB (`MAX_CHANGE_SIDE_BYTES`) or a binary one is not stored: its size and hash (read up to 16 MiB, `MAX_RUN_HASHED_BYTES`) are recorded, so the Run diff knows it changed and shows it as such, without text. More than 2,000 files differing from HEAD (`MAX_RUN_COPY_FILES`) is "not captured: too_many_files". The writes yield to the event loop every few files. A Repo the Changes module hands to the Container's git (over 2,000 tracked files, a big pack, or `.gitattributes` rules git applies) is copied by a script on the Container (`apps/sandbox-image/src/runs.ts`) and only when the Container is running: with it stopped the Repo has no copy ("not captured: container_stopped") and nothing is started (ADR-0022). The script works on a private copy of the repo's own index (`GIT_INDEX_FILE`, so git trusts the stat data it holds and reads only the files that changed; from `read-tree HEAD` only when the repo has no index), never touching the repo's index, branches or working tree. It finds the files that differ from HEAD (changed since the index, untracked and not ignored, staged), counts them, and applies the limits **before** storing any blob: past 2,000 nothing is saved; a file over 1 MiB or with a NUL byte is left as HEAD has it and printed as an `unstored` line (size, hash up to 16 MiB, binary), as the Workspace DO's copy records it. The command stops itself after 20 s (`RUN_COPY_TIMEOUT_SECONDS`, `timeout`), so it never writes its ref after the Workspace has given up. The copies' objects are loose objects with nothing but the hidden refs to keep them: when the next Run replaces the last (or a kept Run is pruned) the refs go, and the objects stay in the repo until the owner's `git gc`. Copies of one scope are made one at a time, and a start or end replayed with the same Run ID answers the Run it already made.
  - **Live and frozen.** While the Run is live, `run_diff` lists the working tree against the start copy as the Changes are listed against HEAD (same entry types, caps and marks), with the Container's git for the Container's Repos, whose last list is shown marked `stale` when the Container is stopped. At the end the list is made once and kept (`frozen`), and a file's new side is read from the end copy; an ended Run's diff never changes, and no later write to the files touches it. A Container Repo's live list drops a file the copy did not store while the working file is as the copy recorded it (size and hash).
  - **On the socket** (`apps/server/src/session/runs.ts`): `last_run` is pushed to every client on connect (after `annotations`) and whenever the Run opens, copies or ends (`null` before any Run has written); `run_diff` answers a `RunDiff` (`run`, `live`, `repos`: each a `RepoChanges`) or null; `run_file` answers a file's two sides as `change_file` does. They never start the Container.
  - **In the Pane.** On a Subagent page there is no Last run: the Runs are the Session's, and its Diff pane (the Workspace of its subagent, ADR-0024) offers the Changes alone, as it does for This branch; a _Show changes_ link there is not drawn. The picker lists _Last run · 14:05_ (one entry, after the Changes, once a Run has written; the time is when it ended, or began while it works, fixed rather than a ticking "4 min ago"; for a Session at the Workspace root, once for all repos). The header names the Run ("Still working", or "Ended 14:05") and says per repo that nothing was captured and why; _Refresh_ lists it again without the Container, and "May be out of date" shows for a Container Repo's last list. The Pane asks for the Run diff while it shows the Last run, and again when `last_run` changes or, while the Run is live, the Changes' listing does; its files load with `run_file`. An empty Run reads "The Last run changed no files."
  - **Show changes.** Under the Run's final answer in the transcript (the last assistant message without a tool call that is no newer than `until` and no older than `startedAt`: `runAnswerId`, `last-run.ts`, which holds whichever agent wrote first) a _Show changes_ link opens the Diff pane on the Last run (`openDiffPaneAtom` with `source: "run"`, `target.ts`). The link sums up what the Run changed as the Session details sum up the Changes: "1 file +13 −0" (`DiffTally`, with "≈" for whole-file counts), the totals of its Run diff (`runTotals`, `last-run.ts`), asked once with `run_diff` while the link is shown (`runTotalsAtom`, `apps/web/src/chat/show-changes-state.ts`; an ended Run's list is the one the Session kept, so the ask starts nothing). It is not drawn until the answer comes, reads "Show changes" when the ask fails, and is not drawn when the answer is another Run's or lists no file (no repo was captured, or the captured ones changed nothing). Only the latest Run's answer has it, not while the Run is live, and not when the Run is `empty` (a `bash` call that only read files). A Run that changed nothing still replaces the Last run: the picker shows it, and the Pane says "The Last run changed no files." Nothing is added to the Session's header.
  - **Annotations** (`kind: "run"`, `RunSource`): the conversation, the Run, the repo, and the `start` and `end` commits (`end` null while the Run is live). The Run's conversation is the root conversation of the active Session branch, which is where a draft goes (the Pane's drafts carry no `conversationId`, as the Changes' do: a draft addressed to the root by ID would not show in its composer). While the Run is live its drafts follow the Changes' outdated rule against the working tree (`reviews.ts`, `runFindings`). Once it ended they are checked one last time against the end copy and never again (`observeEnded`); a draft on a Run that is no longer the latest keeps its quote and is not moved. The Review's heading is "Your changes in your last run to `<path>`: lines as of now" (live) or "…as of the end of that run", one group a file, after the pull requests and before the Call diffs (`runHeading`, `review.ts`).
  - **Measured** (see [_Known risks_](risks-and-spikes.md)): on a 1,000-file repo, local workerd, the start copy takes about 0.6 s, a live list 0.4 s and the end copy 0.9 s, and the frozen list is read in under 10 ms.
- **Diff pane** (#229; decided in #104, #222 and #109): the Pane type `diff`, one per Session, labelled "Diff" (`apps/web/src/diff-pane/`).
  - **Where it opens from:** the New pane (with the totals beside its name while there are Changes); the Changes section of the Session details, the one summary of the Changes outside the Pane (the owner decided against a Changes chip in the Session header: the header gains nothing for them) (see [_Subagents in the UI_](client-and-protocol.md)); and a Call diff's _Open in Diff pane_ (see _Call diffs_). One opened at a file unfolds that file and scrolls to it, and holds the scroll there, as the files above it load and grow, until the owner scrolls (wheel, touch, pointer or key in the scroll). Where to go is a request beside the Pane (`diffTargetAtom`, `target.ts`) that the Pane takes in and clears once the owner acts on the Pane, so its key is `diff` alone, and the URL and the Session layout keep it as they keep the other Panes.
  - **Watching:** the Session's page watches the Changes while it is open (`useChangesWatch`, `changes-summary.tsx`, through `changesAtom`), since the Session details need them, and asks for a listing (`refresh_changes`, not manual) when the owner comes back to the page (`changesOnReturnAtom`, `watch.ts`; `page-return.ts`, unit-tested): the page shown again, or the window focused again after it lost the focus to another window (not to a frame of the page, the Live View or the Browser Pane), at most once in 2 s (`RETURN_GAP`); and when the Pane opens. The Session details, the New pane and the Pane read the same watch, and its totals through `changesTotalsAtom`. Every `changes` message replaces the list (`SessionState.changes`, with `startingContainer`, the `error` of the last failed listing, and `listing`, a count of the lists the Pane reloads its files from).
  - **The header:** the source picker (the Changes and This branch, grouped by repo: see _Comparisons_; the pull requests (#232, below each repo's This branch, the list asked for again at each opening of the picker and when the page is returned to, and a filter box beside the picker) and _Last run_ (one entry after the Changes of every repo, once a Run has written: see _Run diff_); the Pane starts on the Changes of every repo, and a Call diff's _Open in Diff pane_ goes back to them), _Refresh_ (on the Changes, `refresh_changes` with `manual`, which may start a stopped Container; on This branch, `compare` with `startContainer` and `fetch`; it reads "Starting the Container…" while the Session says so), "May be out of date" while a repo's list is `stale` (Changes), what a Comparison is of (`feat` against `main` at the merge-base's first seven characters, the merge-base in full as its tooltip, with its commits counted) and "New commits: Refresh" when its repo's HEAD moved with the Container stopped, the totals (`n files +a −d`) and _Collapse all_, then Auto / Split / Stacked (Auto splits from 720 px, as a Call diff does) and _Wrap_. Layout and wrap are view preferences kept per device in `localStorage` (`cloudpid:diff-layout`, `auto` by default; `cloudpid:diff-wrap`, on by default; `prefs.ts`), not Settings. Word-level highlighting is always on. A failed listing and a repo's own `error` show under the header, over the last list.
  - **The files:** every file of the source sits in one scroll, one `CodeView` with sticky headers (`changes-view.tsx`, a lazy chunk with the library and the workers). Each header has a fold toggle, the status letter (M, A, D, R), the path (a rename as old → new), what the file is (its fold reason while folded, Binary, Too large to show, Loading…, a failure to load, the replacement mark) and `+a −d`. A Session at the Workspace root (more than one repo listed) groups the files by repo and names each with its repo in front. The **file list** is a rail beside the diff from a Pane width of 900 px (`RAIL_MIN_WIDTH`), and a folding list above the first file below it; a file there scrolls the diff to it. A repo's files past the cap show as "and n more not listed". With no Changes the Pane says so; before a first list, that it is listing them, or that they could not be listed.
  - **Folded at first** (`folding.ts`, unit-tested), decided from the list before any content loads, the first reason that applies shown in the header: deleted files; lockfiles (`pnpm-lock.yaml`, `package-lock.json`, `yarn.lock`, `Cargo.lock`, `go.sum` and the like); generated or minified names (`*.min.js`, `*.js.map`, `*.pb.go`, `*.generated.*`, …); files under a `generated/` or `__generated__/` directory (generated) or a `vendor/` or `third_party/` one (vendored); files the root `.gitattributes` marks `linguist-generated` or `linguist-vendored` (the list's `generated` and `vendored` flags; `linguist-generated=false` unfolds a lockfile or a generated name, `linguist-vendored=false` a vendored path); and files with more than 1,000 changed lines (`LARGE_FILE_LINES`). A rename is judged by its new path. Folded or opened by hand stays so only while the Pane is mounted.
  - **State:** the Pane's state is in atoms (ADR-0011), made when it mounts (`ScopedAtom`s) and gone when it unmounts: what was folded or opened by hand and the place held (`pane-ui.ts`, `pane-atoms.ts`), and, in the lazy chunk, the workers held, the loader, where the files sit in the scroll and the library's items (`view-atoms.ts`, `items.ts`). The scroll reports where its files sit; which files to load follows from that.
  - **Loading:** `change_file` is asked only for unfolded files near the visible window (a screenful each way), the ones in view first, at most 4 at a time (`MAX_FILE_REQUESTS`, `filesNear` in `loading.ts`), by an Effect program per Pane (`loader.ts`, unit-tested) that runs each file's load in a `FiberMap` keyed by the file: a load whose file is no longer wanted (scrolled away, folded) or is wanted for another change is interrupted, and the next starts as one ends. Each pair is lined up in the line-up worker and drawn over both whole sides, so the lines around a hunk can be expanded; a big file the owner opens shows in full in the main scroll. Binary and "Too large to show" files (from the list, or from `change_file`'s answer) show their mark and counts only and ask nothing. After a new list a loaded file loads again when its change differs (`entrySignature`: status, old path, counts and marks) as it comes near, and when it is in view (`needsLoad`), showing what it showed until then; a file whose text did not change is not drawn again. So Refresh, focus and the agent's writing calls, each of which lists the Changes, update an open Pane.
  - **Workers:** the Worker Pool and the line-up worker are made when the Pane opens and shut 30 s after it closes (`KEEP_AFTER_CLOSE_MS`, `keeper.ts`), so a Pane closed and opened again soon starts neither again. The line-up worker's client (`line-up-client.ts`, unit-tested) is Effect-based: a worker that errs is dropped, what it held fails, and the next pair starts another; a pair not answered in 20 s (`LINE_UP_WATCHDOG`) fails, and the worker is replaced, the other pairs it held asked again of the new one.
  - Its gutter drafts Annotations on every file with lines (see _Annotations and Reviews_): each item takes its file's drafts as `annotations` (`annotated-items.ts`, unit-tested), with one editor for the whole scroll.
- **Annotations and Reviews** (#230; decided in #108; pages #243): the owner drafts Annotations on a Call diff, the Changes, a Comparison or a page in the Browser Pane, and sends them to a conversation as one Review.
  - **An Annotation** (`Annotation`, `@cloudpid/protocol/annotations`) is a one-side line range of one file: an `id` the browser makes (so its card shows at once), the conversation it goes to (`conversationId`; absent, the active Session branch, as `submit`'s), its `source`, its `path` (and `oldPath` for a rename), its `side` (`old`, removed lines; `new`) and `start`–`end` in that side's file, the quoted lines as they were when it was drawn (`quote`, the first 50 lines and 8 KiB, the rest counted in `more`; a first line past 8 KiB alone is cut short on a code point and marked `clipped`: `cutQuote`, unit-tested), the owner's `text` (at most 4,000 characters), and the `createdAt` and `updatedAt` the Session stamps. Anchors:
    - **A Call diff's** (`kind: "call"`): the conversation whose call it is, the `callId` (the `edit` or `write`, or the `codemode` call), `nested` (the call's number in the script, for one a script made) and the `tool`; its path is absolute, a relative one (as the model gave it) resolved by the Session against the directory that conversation works in (`resolvePath`; `SessionHost.directory`). A Call diff never changes, so its drafts are never checked again; the Review says its lines are as of that call.
    - **The Changes'** (`kind: "changes"`): the repo and the HEAD commit it was written against; its path is the file's in the repo (absolute as `/workspace/<repo>/<path>`: `annotationPath`).
    - **This branch's** (`kind: "branch"`): the repo, the branch (null for a detached HEAD), the base branch, and the merge-base and head SHAs of the Comparison it was drawn on; its path is the file's in the repo, absolute like the Changes'. Drafts on a repo's branch belong together whatever commits they were written against (`sameSource` compares the repo), so they show on a newer head's Comparison too, where the check below moves them.
    - **The Last run's** (`kind: "run"`): the conversation, the Run's ID, the repo, and the start and end copies' commits (`end` null while the Run is live); its path is the file's in the repo, absolute like the Changes'. Drafts on one Run's repo belong together (`sameSource` compares the Run and the repo). See _Run diff_ for how they are checked.
    - **A page's** (`kind: "page"`, a `PageAnnotation`: no path, side or range; drafted in the Browser Pane's Annotate mode, see [_Browser Pane_](browser.md)): the Owner tab's URL without its fragment, the Owner tab it was drawn in, the element picked (`element`: its selector and tag; absent for an area), its box (or the area) in the viewport's CSS px, how far the page was scrolled and the viewport's size, all as they were; its `quote` is the element's visible text (none for an area), cut as a diff's is but measured escaped, as the Review writes it (`cutPageQuote`), and it carries a `crop` of the spot from the Pane's last frame (never a new screenshot): a JPEG with an 8 px margin, at most 640 px on its longer edge, coarser then smaller until its base64 is at most `MAX_ANNOTATION_CROP` (12,000 characters, about 9 KB), none when nothing fits. Everything but the Owner tab's ID and the crop's pixels came from the page: at each save, and again at the send with the Secrets held then, the Session cleans it (`cleanPageSource`, `cleanPageLines`: one line, no control or bidirectional characters), **redacts held Secrets** from the URL, selector, tag and quote, and only then cuts it (`clampPageSource`, `pageQuote`: the URL to 2,048 and the selector to 256 bytes escaped, the tag to 64), so a Secret the page split with a character the cleaning drops is whole when it is redacted. The Session never checks a page draft (it has no page to read): the Pane finds its element again and says when it is not found on the page. Drafts belong to their page by URL, so they show on every Owner tab at it.
  - **Drafting** (`apps/web/src/review/`): a diff draws the gutter's + on the line hovered (`enableGutterUtility`); pressing it opens an editor under that line, dragging from it down or up the gutter picks a range (`enableLineSelection` draws it). The range is one side's (`pickLines`, `selection.ts`, unit-tested): a drag across sides is cut at the side where it started, and the range stops at a gap the diff does not draw (between two hunks of a patch), so the quote is whole. The editor (Save draft, Cancel, Escape, Mod+Enter; its textarea focused a frame after it mounts, as it is slotted into the diff's shadow root) is one per diff view, a `ScopedAtom` (`editor.ts`): a card's Call diff, the Diff pane's scroll. A saved draft shows under its last line as a card with its text, _Edit_ and _Delete_, and its mark (`Outdated`, `No longer in the diff`, with a dashed border); a marked one also shows the lines it quoted, as they were when it was drawn, since the lines around it now read otherwise. Drafts are drawn on an `edit` or `write` card, on each `edit` or `write` row of a `codemode` card, on those in a subagent's card (which go to that subagent), and on the Diff pane's files (which go to the active branch). Only the Session page's Diff pane drafts: a Subagent page's shows another Workspace's Changes, which the outdated check and a Review's paths do not cover yet, so it draws no gutter + (a subagent's Call diffs on its page still take drafts, which go to it).
  - **Kept and synced** (`apps/server/src/session/annotations.ts`): the Session DO keeps the drafts in its storage (`cloudpid:annotation:<id>`, and their order in `cloudpid:annotations`), at most 100 (`MAX_ANNOTATIONS`; a save past it is refused, an edit is not), and sends them whole to every client as `annotations` after `hello` on every connect (an empty list too) and whenever they change, as it does Approval requests. `annotation_save` saves a draft new or edited (the last save wins; an edit keeps `createdAt`, and the mark while its range is the same) and `annotation_delete` deletes one (one that is gone is no error); both answer `null`. The text being typed stays in the browser that types it. A Fork or Clone copies no draft. A subagent's drafts are deleted with it (`subagent_delete`, wrapped by `annotationsPruningTools`, and the owner's delete in the Session DO).
  - **The outdated check on This branch** (`reviews.ts`): when a `compare` makes a Comparison for a client, and at each check of the Changes and before a Review is sent (a Comparison asked for without the Container, so the last one when it is stopped), the drafts on that repo's branch written against another pair of commits are checked against the Comparison's: each has its file read once (`comparison_file` at the new pair), and the ones whose quote holds, or is found once elsewhere, move to the new pair, as the Changes' do with their HEAD. One whose quote is gone is marked `outdated`, keeping its place, quote and old pair; a file the Comparison no longer lists (when it lists every file) marks it `gone`; a Comparison marked `behind` is the last one made, not the head's, and changes nothing. A commit that takes a file out of the Changes does not move its drafts to This branch, nor the other way: they are different sources. The same check runs for the drafts on a pull request (the same repo and number) when a `compare` makes its Comparison, moving them to the new pair and taking the title it has now; a pull request that is closed or merged, or `behind`, changes none, and GitHub is not asked at a send, so a pull request's drafts are checked when its Comparison is made, not before a Review is sent.
  - **The outdated check** (`outdated.ts`, unit-tested; run by `reviews.ts` after every listing of the Changes, which a writing call starts while the Changes are watched, and before a Review is sent): each draft on the Changes has its file read once (`change_file`, at most 4 at a time) and its quote looked for in its side's lines. Still in place: unchanged, an earlier mark cleared. Found exactly once elsewhere: it moves there silently, its range the same length, so an edit above the drafts does not make them all outdated. Otherwise: marked `outdated`, keeping its place, its quote and its HEAD. A file the repo's list no longer has (when the list holds every file) marks it `gone`. A repo not listed, failed or past its cap, a binary or too large side, and a file that cannot be read leave the draft as it is. A check does not write over a draft saved while it ran.
  - **Sending** (`reviews.ts`): the drafts addressed to a conversation show as chips in its composer (`a.ts:12–18`, opening on the quote and text; × deletes the draft), over a line saying it sends as a Review and that what is typed is its summary. While there are some, Send, Steer and Queue send a Review: `submit` with `annotations` (the drafts' IDs) and the typed text (with its Attachments) as the summary, which may be empty; the lane shows "summary · Review: n Annotations". The Session refuses it when a draft it names is gone or goes elsewhere ("Your drafts changed: check them and send again"), checks the drafts on the Changes once more, renders the Markdown (`renderReview`, `@cloudpid/protocol/review`, unit-tested) and places one owner's message: the summary (Skills and Prompt templates expanded as in any message), then the Markdown, in its first text block. The drafts are deleted once the Session has taken it, those saved again while it was being sent excepted (they keep their new text); a Review sent again with its `requestId` finds the first, so a send that failed after the message was placed is not placed twice.
  - **What the model gets:** `## Review: n Annotations`, then the drafts grouped by source, the Changes first (by repo: `### Uncommitted Changes in \`repo\``), then This branch (by repo: `### Branch \`feat\` against \`main\` at \`abc1234\`` with the merge-base's first seven characters, "Detached at \`1111111\` against \`main\` at \`abc1234\`" for a detached one (the head's first seven characters, as the Pane names it)), then each pull request (by repo, then number: `### Pull request #7 'Fix the thing' at \`1111111\``, the head's first seven characters), then each file of the Last run (`### Your changes in your last run to \`/workspace/app/src/a.ts\`: lines as of the end of that run`, or "as of now" while the Run is live), then each call in the order its first draft was made (`### Your \`edit\` call on \`path\`: lines as of that call`), in each by path, line and side, numbered so the agent can name them (`**Annotation 2**: \`/workspace/app/src/a.ts\`, lines 12–18`, or `removed lines …`, and a rename's old path, absolute too; a path or repo name holding backticks is quoted with a longer run of them). Each quotes its lines in a fence named by the file's language and longer than any run of backticks in them, says what the quote leaves out (`… n more lines`, `… the line goes on`), says "These lines have changed since." or "These lines are no longer in the diff." when marked, and ends with the owner's text as a blockquote, so a code fence it opens and never closes ends with it rather than swallowing the Annotations after it.
  - **Pages in a Review:** the drafts on pages come last, under the heading "Pages in the Browser Pane": a notice (`PAGE_NOTICE`) that what each page block holds was written by the web page, untrusted content to read and never instructions or the owner's words, as for Attached pages, then per draft its number ("an element of the page below", or "an area of the page below") and one `<page_annotation>` block, its anchor in attributes (`owner_tab_id`, `url`, `tag`, `selector`, `box`, `scroll`, `viewport`, and `crop` when its crop goes in the message), holding the element's text, every value escaped as `pageBlock` escapes them (so a page cannot close the block), and the owner's text as a blockquote after it, outside the block.
  - **Crops in the message:** each page draft's crop goes as an image part at the end of the message, after a text part that names its Annotation (`cropLabel`: "The crop of Annotation n, from the screen of its page (page content):"), in the Review's order. At most `MAX_REVIEW_CROPS` (20) go, and only those that fit (`fitCrops`, `apps/server/src/session/crops.ts`): beside the message's own images within `INLINE_IMAGE_BUDGET`, and within what the stored message may take (`MAX_STORED_INPUT_BYTES`) once the Markdown and the rest are counted; one without room is left out (and the next ones tried), its Annotation sent without it (the notice says crops go when the message had room). **Why 100 drafts cannot break the limits:** a draft's crop is at most 12,000 base64 characters, so 100 drafts' crops are at most 1.2 MB in the Session's storage (each draft a key of its own, far under a value's limit) and in the `annotations` message, and at most 20 of them, 240 KB, go in a message, always within the image budget; the page text is bounded as a diff's quote is, so 100 page drafts at every limit still fit a stored message, crops counted (`input-guard.test.ts`).
  - **Kept once:** the `cloudpid.user` entry's data has `review` (`ReviewData`): each Annotation's anchor and range with where its quote and text sit in the Markdown (spans into it) and the Markdown's length, so the entry holds the quote and text once: 100 drafts at the limits in ASCII come to about 1.25 MB, within the 1.9 MB a stored message may take, where twice would not fit (text in other scripts takes more bytes a character: a Review past the 1.9 MB is refused, with its size, as any message is). The transcript reads them back (`shownReview`) and shows the owner's message with its summary ("Review: n Annotations" when it has none) and a chip per Annotation under it, opening on the code it quoted, the file and lines ("as of that call" for a Call diff's) and the text. A page draft's chip (`<button> · host/path`, or `Area · host/path`) opens on the page's URL, the element, its crop, its text and the owner's: `review.crops` lists the Annotations whose crops the message carries, the last parts of the message, which the transcript takes off the message's parts and gives to their chips (`withoutCrops`).
  - **Withdrawn:** each Review the Session placed is followed until it settles (`cloudpid:reviews-pending`; the sent drafts' IDs under `cloudpid:review:<submission>` and each draft under `cloudpid:review:<submission>:<id>`, one key a draft as the drafts are kept, all written at once after the message is placed, so an eviction does not lose them). One Stop withdrew before it was placed (unanswered, with no entry) brings its drafts back as they were sent, but for those addressed to a subagent deleted meanwhile; one placed forgets them.
  - **Not in the Session header:** nothing of the drafts shows there; the composer's chips are where they wait.
- **Testing:**
  - Pure modules are unit-tested: anchoring, the outdated check, the Review Markdown, folding and budgets.
  - The Durable Objects' stores and modules have workerd tests over repos written by real git.
  - The Container's commands are tested in plain bash.
  - The UI is checked by hand on each PR's preview stage, at desktop width and 390 px, light and dark.
- **Out of scope:**
  - posting to GitHub;
  - a Subagent Workspace's Changes;
  - accepting or rejecting hunks, editing, and resolving conflicts in the view;
  - jumping from a Review card back to its lines;
  - browsing earlier Runs.
