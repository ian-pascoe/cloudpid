# MCP server requests: Sampling, Elicitation and MCP tasks

An MCP server can ask cloudpid for something during a call: a reply from one of the owner's models (a **Sampling request**), the owner's own answer on a form or a page (an **Elicitation request**), or the Workspace's roots (answered inside the core; see [_Roots_](mcp-in-a-session.md#roots)). A Modern server can also answer a `tools/call` with an **MCP task**, work it goes on doing after answering. All three rest on one question shape ([ADR-0037](../adr/0037-a-modern-mcp-servers-question-is-answered-with-a-new-request-and-a-legacy-ones-lives-only-as-long-as-its-call.md)) and are kept by the Session, never by `McpHost` ([ADR-0038](../adr/0038-the-mcp-host-object-lives-beside-the-registry-and-runs-the-sdk-through-a-stateless-engine-in-a-worker-of-its-own.md)). Sampling is [ADR-0039](../adr/0039-an-mcp-servers-sampling-request-runs-on-the-owners-models-in-a-completion-of-its-own-and-waits-for-the-owners-yes-unless-its-definition-allows-it.md), elicitation [ADR-0041](../adr/0041-an-mcp-servers-elicitation-request-is-answered-only-by-the-owner-its-answer-is-never-kept-and-a-form-that-asks-for-a-credential-is-declined-unseen.md), MCP tasks [ADR-0042](../adr/0042-an-mcp-task-waits-in-its-call-up-to-its-servers-timeout-then-goes-on-in-the-background-and-the-agent-reads-its-result-through-a-tool.md). UI copy never says "elicitation" or "sampling": it says "<server> asks for your input", "<server> asks you to open a page", "<server> asks to use a model", and always "MCP task", never "task" alone.

## Questions

- **One shape:** the core surfaces every server question as `InputRequest { key, kind: elicitation | sampling | roots, params, mode: live | deferrable }`. Roots are answered inside the core; elicitation and sampling go to the call's `onInput`, which answers, returns `"defer"` (Modern only) or resolves `"refused"` ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D11, [Sampling](https://github.com/ian-pascoe/cloudpid/issues/387) D12.1).
- **The path:** questions, progress and the abort travel as callbacks on the call, Session → `McpHost.request` → `McpEngine`; the host never calls a Session and keeps no question state. The Session's adapter is `McpHostClient` (`apps/server/src/session/mcp-host.ts`). A call's `ctx.answers: { elicitation?, sampling?, inputWaitMs? }` says what the caller can answer, and the core's `capabilities(ctx)` declares only that; a callback's presence and `ctx.answers` are also the version-skew gate on this edge ([The MCP host object](https://github.com/ian-pascoe/cloudpid/issues/382) D6.2, [Deploys under deferred code updates](https://github.com/ian-pascoe/cloudpid/issues/423) D1.2).
- **Where they are declared:**

  | Origin                                                                         | Sampling                                    | Elicitation  | MCP task (`allowTask`)                       |
  | ------------------------------------------------------------------------------ | ------------------------------------------- | ------------ | -------------------------------------------- |
  | The agent's `tools/call` (root or subagent; direct, deferred or in `codemode`) | unless the definition's `sampling` is `off` | always       | Modern, extension advertised, under the caps |
  | The agent's `read_mcp_resource` (`watch: true` included)                       | unless `off`                                | always, live | never                                        |
  | A prompt send (`prompts/get`)                                                  | unless `off`, live                          | always, live | never                                        |
  | An App View's `tools/call` / `resources/read`                                  | unless `off`, live                          | always, live | `tools/call` only                            |
  | No conversation (below)                                                        | never                                       | never        | never                                        |
  - **A read is live:** `read_mcp_resource` never defers a Modern question, even on a host that resumes: a read only asks, so one that is cut is sent again rather than kept with a `ResumeState` and markers; its questions are answered while it waits, a deferral being `cancel` ([#480](https://github.com/ian-pascoe/cloudpid/issues/480)).
  - **Capabilities:** `sampling: { tools: {} }`, never `sampling.context`; `elicitation: { form: {}, url: {} }`, never the bare `{}` (which means form only). Modern declares them per request in `_meta` client capabilities, the SDK `Client` being rebuilt per call so `capabilities(ctx)` reaches its constructor. Legacy declares them connection-wide at `initialize`; a Legacy session whose declared capabilities differ from the definition's `sampling` key is re-initialized at its next use, with `conn` and the MCP inventory unchanged ([Sampling](https://github.com/ian-pascoe/cloudpid/issues/387) D2.4, D18).
  - **Amendment ([#493](https://github.com/ian-pascoe/cloudpid/issues/493), to [Elicitation](https://github.com/ian-pascoe/cloudpid/issues/388) D1, D1.1 and D17): a Modern request does not always declare `url`.** `form` is declared as above, but `url` only when the caller defers questions and keeps pages (`ctx.answers.defer` and `pages`). A Modern page is answered by a resume once the owner is Done at it; a caller that cannot wait for that would answer it on the spot, and Open would send the server on before the owner had been there. So a Modern `read_mcp_resource` (no resume: its questions are answered live or `cancel`) and any live caller declare no `url`, and a Modern server that asks for a page anyway gets `cancel`. And `pages` is set only by a Session on a host that lists `resend` (the same flag as a Legacy `-32042`'s, [_Deploys_](mcp.md#deploys)), so a host without it (version skew) declares no `url` and no Modern server asks for a page. A Legacy connection still declares `url` connection-wide.
  - **Questions with nowhere to go:** the calls with no conversation are discovery, list refreshes, `completion/complete`, previews, Resource watch check reads, GET streams and listens, and Attached resource reads at send. On Legacy, a question from one of them or on the GET stream gets `cancel` (elicitation) or `-1` "no conversation to sample in" (sampling). On Modern nothing is declared there; if a server asks anyway, an Attached resource read gets its error line, a watch check read counts as a gap ("could not be checked"), and a preview says "open it in a conversation".
  - **Fallback** if per-request declaration fails a build check: Modern declares sampling whenever the key isn't `off`, and a request with no conversation ends locally as above ([Sampling](https://github.com/ian-pascoe/cloudpid/issues/387) D18.2).

- **Modern: deferred.** `tools/call`, `prompts/get` and `resources/read` may return `{ type: "input_required", requests, resume }`. When `onInput` answers everything at once, the core retries itself (new id, `requestState` byte-exact, ≤10 rounds, result not cacheable). When anything is deferred, the Session keeps the `ResumeState` (JSON, ≤1 MiB, a format `v` in the core's envelope) and later sends `McpHost.request({ op: "resume", … })` with the answers. A `v` past its 30 days expires the question visibly ("asked by an older version of cloudpid and can't be resumed; call the tool again"; see [_Deploys_](mcp.md#deploys)).
- **As built, Modern questions in the core, engine and host ([#480](https://github.com/ian-pascoe/cloudpid/issues/480); `packages/mcp/src/connection.ts`, `apps/mcp-worker/src/calls.ts`, `apps/server/src/mcp/request.ts`):** a Modern `tools/call`, on the client's path or the task wire, is sent with `allowInputRequired`, so an `input_required` answer comes back to the core, whose own rounds answer it (never the SDK's loop): Roots from the connection's own, an elicitation through `onInput` (`mode: "deferrable"`) when `ctx.answers.elicitation` is set and there is an `onInput` (else `cancel`), anything else not offered fails the call `ProtocolViolation` with nothing sent. A `refused` answer fails the call `Unsupported` with its message, the server told nothing. When every question is answered the call is sent again with `inputResponses` and the server's `requestState` as it came, on a new id, at most `MCP_INPUT_ROUNDS` (10) rounds (the eleventh fails `ProtocolViolation`), and a result after questions is not cacheable. A `defer` ends the round as `input_required` only for a call whose `ctx.answers.defer` is set (otherwise it is a `cancel`): `{ requests, resume }`, the `ResumeState` being `ResumeStateV1` (`{ v: 1, method, name, arguments, requestState?, answered, deferred, round }`, ≤1 MiB as JSON, else `TooLarge`), the answers given at once (Roots included) kept in `answered`, so a resume sends the whole round. `connection.resume(state, answers, tool, ctx)` answers every deferred key or sends nothing (`Unsupported`: too few answers is cloudpid's fault, never blamed on the server), refuses a state it cannot read (`Unsupported`, `MCP_RESUME_STATE_EXPIRED`) and a server no longer Modern (`Unsupported`), and goes on as a call does: a result, a task, or the next round. The engine declares `elicitation: { form: {} }` in a Modern request's `_meta` only for a call with `ctx.answers.elicitation` and an `onInput` hook, scrubs the requests (not the state) of the call's tokens, and runs `op: "resume"` as a call (`mayHaveRun`; no `-32020` refresh); the host's `resume` is in [_RPC_](mcp-connections.md#rpc). A resume is a `tools/call` sent after the server answered, so the rule that a `tools/call` is never sent twice holds per round: a resume is never sent again after a cut. The Session's half is the As built note of [_The waiting-question record_](#the-waiting-question-record): its agent's calls set `defer` when the host lists `resume`; a Session without the vault, or on a host without `resume`, answers a Modern form live, as a Legacy one (the card, its 10 minutes and the call's paused clock), the core retrying at once. Either way a form it cannot take (malformed, another mode) is a `cancel` there, never a refusal, which would end the call (`packages/extensions/src/mcp/elicit.ts`).
- **Legacy: live.** The core's `fetch` tap ties a question to the call whose POST stream carried it. The question is answerable only while that call waits; the call's `timeout` pauses meanwhile, bounded by `ctx.answers.inputWaitMs`, the largest of the kinds offered (10 min for elicitation, 12 min when sampling is offered: 10 for the owner plus 2 for the sample), and each kind enforces its own bound. `"defer"` becomes `cancel` for elicitation and an error for sampling. A Session reset (its callbacks reject, the host aborts the server request), `host_lost` or a real engine cut (`engine_lost`) ends a live question and expires its record ("the server's call ended"; see [_Failures and cuts_](mcp-connections.md#failures-and-cuts)).
- **As built, Legacy questions ([#472](https://github.com/ian-pascoe/cloudpid/issues/472); `packages/mcp/src/elicitation.ts`, `connection.ts`, `tap.ts`; `packages/extensions/src/mcp/elicit.ts`, `questions.ts`):** only an elicitation form on a Legacy server's call. The core tags an askable Legacy `tools/call` (its `ctx.answers.elicitation` set, an `onInput` given) with an `x-cloudpid-call` header, which its `fetch` tap strips and uses to tie every `elicitation/create` id seen on that POST's SSE stream to the call; the client's `elicitation/create` handler passes the question to the call's `onInput` and stops the call's clock (an Effect-clock deadline of its own, the SDK's request timer being maxed) until the answer, bounded by `inputWaitMs`. A question on the GET stream or with no call to tie to (an SDK `server.elicitInput` outside a call) gets `cancel`, as does one on a call with no `onInput`; one the Session refuses is `-32602`; the server's own `notifications/cancelled` for it calls `onInputEnded`. The engine declares `elicitation: { form: {} }` on a Legacy connection (the capability is connection-wide, so discovery declares it too and a question outside a call is cancelled), and a Legacy session row records what it `declared`, so a session from before this build, or one whose declaration changed, is initialized again once. The Session's `mcp` tools send `ctx.answers: { elicitation: true, inputWaitMs: 10 min + 15 s }` when the Session has `McpQuestions` (the Session's own 10 min comes first, so a late answer is "this request ended" and never a race with the core's bound). Modern questions' core, engine and host are in the As built note above, and the Session's half in [_The waiting-question record_](#the-waiting-question-record). The seams are `McpInputRequest.kind`, `McpAnswers.sampling` and the open `McpInputAnswer` union.
- **Who answers:** only the owner, from any client, the first answer winning; the others get "this request ended". The agent has no tool, `codemode` method or list to answer, refuse, decline or see a waiting Sampling or Elicitation request; its only lever on sampling is `settings_mcp_update`, which needs Approval. The MCP endpoint lists waiting requests with a link but never answers them (see [_Waiting requests_](mcp-endpoint.md#waiting-requests)) ([Sampling](https://github.com/ian-pascoe/cloudpid/issues/387) D20.1, [Elicitation](https://github.com/ian-pascoe/cloudpid/issues/388) D3).

## The waiting-question record

- **One record per question** in Session storage, shared by both kinds (an implementation word, not a GLOSSARY term): keyed `(owner, request key)`, where the owner is `call:<pi task id>` for a call or `mcp_task:<handle>` for an MCP task; it holds `{ kind, server, conn, conversation, call, origin, era, mode: live | deferrable, params (redacted, bounded), resumeState? (chunked), grant, status, answer?, spawn?, deadline? }`. The answer goes to `resume` (Modern), `resend` (a Legacy `-32042`) or `tasks/update` (an MCP task); cards, checks, records and protocol don't depend on which. Requests are deduplicated by `(owner, key)` across rounds and polls ([Elicitation](https://github.com/ian-pascoe/cloudpid/issues/388) D14, [MCP tasks](https://github.com/ian-pascoe/cloudpid/issues/389) D7.1).
- **Phased replay:** every MCP tool the `mcp` extension registers is `replay: "safe"`, guarded by pi-durable memos (`api.memo(name, candidate)`: first write wins, durable once resolved). The ResumeState and requests live in the record (chunked), never in memos.

  | Marker            | Written                                                       |
  | ----------------- | ------------------------------------------------------------- |
  | `mcp.sent`        | awaited before the first request leaves                       |
  | `mcp.wait.<r>`    | once round _r_'s questions are stored                         |
  | `mcp.resumed.<r>` | awaited before round _r_'s resume (or `-32042` resend) leaves |
  | `mcp.task`        | the MCP task's handle, in the commit that stores its record   |
  | `mcp.detached`    | in the commit that moves the MCP task to the background       |

  On a rerun: no `mcp.sent` is a first attempt; the latest `mcp.wait.<r>` without `mcp.resumed.<r>` waits again (or takes an answer given meanwhile); `mcp.sent` without `mcp.task` on a task-capable call settles as cut; `mcp.task` polls for what is left of the window; `mcp.detached` returns the same handle; anything else settles as cut, "may have partially run". So a `tools/call` is never sent twice, and a round's resume at most once ([Sampling](https://github.com/ian-pascoe/cloudpid/issues/387) D17, [MCP tasks](https://github.com/ian-pascoe/cloudpid/issues/389) D3.2). Built: `mcp.sent` ([#458](https://github.com/ian-pascoe/cloudpid/issues/458)), and `mcp.wait.<r>` and `mcp.resumed.<r>` with Modern questions ([#480](https://github.com/ian-pascoe/cloudpid/issues/480), below); a `-32042` round's `mcp.wait.<r>` and `mcp.resumed.<r>` with Legacy URL mode ([#487](https://github.com/ian-pascoe/cloudpid/issues/487), below); `mcp.task` and `mcp.detached` come with MCP tasks. Fallback if a build check fails: a deferred Modern call settles as cut on a restart and its card is withdrawn.

- **As built, deferred mode ([#480](https://github.com/ian-pascoe/cloudpid/issues/480); `packages/extensions/src/mcp/exchange.ts`, `rounds.ts`, `elicit.ts`, `deferred-questions.ts`, `questions.ts`; `apps/server/src/session/mcp-questions.ts`):** an agent's `tools/call` (direct or in `codemode`; never a resource read) sets `ctx.answers.defer` when the host lists `resume` (`MCP_RESUME_FEATURE`, one of `MCP_OPTIONAL_TOOL_FEATURES`) and the Session's `McpQuestions` has a vault. A Modern form that passes the checks is then kept, not shown: `onInput` stores it as a question of its own, `mcp-question:q:<id>` (`kind: "elicitation"`, the request as the owner is to see it, and later the answer), adds its id to the call's deferred record `mcp-question:d:<callId>` (the server and the questions' ids; listed in `mcp-question:deferred`), and answers `defer`, with no clock stopped. No stored value grows with the round: each holds one question, or the round's small bookkeeping, or a chunk. When the host answers `InputRequired`, round _r_ (counted by the Session from 1) is stored whole (`commitRound`): the `ResumeState` in chunks of 32 Ki characters (`mcp-question:d:<callId>:<n>`), the server's `conn`, the server's name for the tool, what `details.elicitation` holds so far and the call's count toward its cap; then `mcp.wait.<r>` is written, and only then are the round's cards shown (`showRound`, which marks the round shown; one `input` Notification as for a Legacy question). The request carries `waits: "owner"`, and the card reads "<server> waits for your answer" with no countdown; its `deadline` is 30 days off (`MCP_DEFERRED_DEADLINE_MS`), only for a client from before `waits`, which still requires one. The call waits with no clock running. Answers come over `mcp_elicitation_answer` as for a Legacy question, checked the same way, the first winning; an accepted form's content is sealed in its question with AES-GCM under `openKeptVault(SECRETS_ENCRYPTION_KEY, "mcp-elicitation")`, bound to the Session's object id and the question's id, and a decline or cancel is kept as is. Once every question of the round has its answer, `mcp.resumed.<r>` is written, the questions are settled into their records and the record and its questions deleted (the sealed answers with them), and `McpHost.request({ op: "resume" })` is sent with the opened answers, built inside `execute`; its answer is handled as a `tools/call`'s (a result, a failure such as `ServerChanged`, or round _r+1_). A rerun that finds `mcp.sent` reads the record: a round stored with `mcp.wait.<r>` and no `mcp.resumed.<r>` is shown (if the instance stopped before it was) and waited for again (an answer given meanwhile is taken at once, and no Notification is sent for a round shown before), anything else settles as "may have partially run". The cards show from the record, so they outlive the instance. A round goes: with the call's end; with Stop ("Run stopped"); answered `cancel` by cloudpid when its server is switched off, hidden or removed (the resume then goes to the host, which refuses it); and when the Session goes idle with no call of this instance for it (`dropAbandoned`, "the server's call ended"), as a `codemode` script whose `timeout_ms` passed during an eviction leaves it. A form the storage cannot take (a replaced Session's `refusingStorage`) is answered `cancel` in the round's retry ("cloudpid could not record the question"), and an `InputRequired` that cannot be stored ends the call as one that may have run, which the next instance settles so. A question's `kind` is `elicitation` (absent reads as one) or `sampling`; a round holding another kind (from a later build) is not shown, answered or waited for again, its forms included. Every key is listed before it is written (a question in its call's record, the `ResumeState`'s chunks counted in the round), so a write the storage refuses leaves nothing the call's end does not drop. Of the shared record's fields this keeps `kind`, `server`, `conn`, the conversation and call, the request (redacted, bounded), `resumeState` (chunked) and `answer`; the rest come with the work that needs them: `era` and `mode` with the Legacy `-32042` round, the first deferred question that is not Modern ([#487](https://github.com/ian-pascoe/cloudpid/issues/487); `era` explicit with Modern pages, [#493](https://github.com/ian-pascoe/cloudpid/issues/493)); `origin` with prompt sends ([#492](https://github.com/ian-pascoe/cloudpid/issues/492)), App Views ([#498](https://github.com/ian-pascoe/cloudpid/issues/498)) and MCP tasks ([#497](https://github.com/ian-pascoe/cloudpid/issues/497)), every deferred question being an agent's call's now; `status` with MCP tasks ([#497](https://github.com/ian-pascoe/cloudpid/issues/497)), the record's presence and each answer standing for it now. Not built ([#569](https://github.com/ian-pascoe/cloudpid/issues/569)): the stdio `spawn` (a Modern stdio server's question keeps no `spawn`, so a resume answered by another process gets no "restarted while it waited" line); the `codemode` withdraw reads "Run stopped" or "the server's call ended", not "the script timed out" (the sandbox's abort does not say why). Restarts during a wait count toward `restartLimit` as below.

- **As built, reads ([#471](https://github.com/ian-pascoe/cloudpid/issues/471); `packages/mcp/src/connection.ts` `withAsking`, `packages/extensions/src/mcp/exchange.ts`, `resources.ts`):** an agent's `resources/read` is an askable request as a Legacy `tools/call` is. The core's `withAsking` gives `readResource` the same `x-cloudpid-call` tie and `onInput` path (so a question on the read's SSE stream reaches the owner and stops the read's clock, bounded by `inputWaitMs`), and the host's `resources/read` passes `ctx.answers` and the Session's `onInput`, `onInputEnded` through. The Session's `read_mcp_resource` shares the call's one request routine (`send`), so it sends `ctx.answers` when the Session has `McpQuestions`, shows the card with the tool name `read_mcp_resource`, and records the answer in `details.elicitation` as a call does. A list (`resources/list`, `resources/templates/list`) sends no `answers`: a list is never asked a question, and one a Legacy server asks anyway is cancelled. The read's timeout is 30 s, or the entry's lower `timeout`, with the clock stopped while a question waits.
- **As built, live mode ([#472](https://github.com/ian-pascoe/cloudpid/issues/472); `packages/extensions/src/mcp/questions.ts`, `apps/server/src/session/mcp-questions.ts`):** a Legacy question is in memory only, as live mode says: the waiting call's `Deferred` and the full request (message and form, redacted of held Secrets) live in the `McpQuestions` service. Session storage holds `mcp-question:waiting` (who asks and when: `{ id, callId, conversationId, server, tool, askedAt }`, the id being `<callId>:<key>`), which a new instance finds and expires ("expired: the server's call ended") before any call can ask, and a settled record `mcp-question:s:<id>` per question that ended (the newest 100 kept, ≤64 KiB each, the form dropped past it): server, tool, conversation, call, the redacted message and normalized form, notes, the action, who decided and why, asked and settled times, and the names of the fields answered, **never a value**. Nothing reads the settled records yet (no card line, `/export` or span): they are the seam for those. It is one record per question, not yet the spec's shared shape (`kind`, `conn`, `era`, `mode`, `grant`, `resumeState?`, `answer?`): those come with Modern, Sampling and MCP tasks, which add them without changing these. A call's end (`settleCall`, in a `finally`), Stop (the wait's interruption), the 10-minute bound and the call's cap of 10 end a wait as the table of [_Elicitation requests_](#elicitation-requests) says. Not built: Fork/Clone copying settled records. A Legacy question needs no replaced-Session gate (it is in memory, so no answer can be lost to a storage that cannot take the record); a Modern one has it (below).

- **`restartLimit`:** pi-durable ends a tool cut off 5 times in a row (`restart_limit`), and memo writes don't reset the count, so a deferred wait through more than 5 restarts in a row ends its call, as Approval and `secret_ask` waits do. Accepted; an ask goes to pi-durable if it bites ([Sampling](https://github.com/ian-pascoe/cloudpid/issues/387) D17.2). MCP task followers are exempt (each sleep commit resets the count); the only in-memory waits on an MCP task are its inline window (≤10 min) and `mcp_task_wait` (≤30 min) ([MCP tasks](https://github.com/ian-pascoe/cloudpid/issues/389) D14.3).
- **`codemode`:** a nested call is a durable task keyed `c<VM call id>` and the script replays from its journal, so it waits for a question exactly as a direct call does, in both eras. The one extra end: the script's `timeout_ms` passing fails the script and withdraws its questions ("the script timed out") ([Elicitation](https://github.com/ian-pascoe/cloudpid/issues/388) D5.4).
- **How a wait ends** (both kinds; MCP tasks in [_MCP tasks_](#mcp-tasks); [Sampling](https://github.com/ian-pascoe/cloudpid/issues/387) D7.4, D7.5, [Elicitation](https://github.com/ian-pascoe/cloudpid/issues/388) D13):
  - **Stop** aborts the call: waiting requests are withdrawn ("Run stopped"), a running sample is aborted with its cost so far recorded, and a Modern `ResumeState` and any sealed answer are dropped.
  - **A Session restart:** a deferred Modern question survives; a live one (Legacy, prompt send, App View) is withdrawn ("the server's call ended") and a Legacy call settles as cut.
  - **A replaced Session** (a deferred code update reached it mid-call): a question arriving live whose card can't be stored gets the no-answer for its kind, never a deferral: an elicitation `cancel` (not `decline`: no owner chose), a Sampling request a refusal (Usage and the Spend limit can't be recorded); a Modern question is refused, never deferred (left to implementation: a Modern elicitation answered `cancel` in the retry, as on Legacy). A Modern `input_required` result is dropped with its call, which the new instance settles "may have partially run" ([Deploys under deferred code updates](https://github.com/ian-pascoe/cloudpid/issues/423) D4).
  - **Archiving or deleting the Session** withdraws everything waiting; **deleting a subagent** withdraws its requests ("the subagent was deleted").
  - **The server changes while a question waits:** switched off, `hidden` or removed, its card is withdrawn when the Session learns of it; an answer carries the record's `conn`, and the host refuses one whose `conn` differs (`ServerChanged`, nothing sent, card withdrawn). For sampling, a switch to `off` refuses and a switch to `allow` runs it.
  - **Signed out:** when the server's MCP sign-in is signed out while a Modern question waits, its resume fails fast with the sign-in error ([Elicitation](https://github.com/ian-pascoe/cloudpid/issues/388) D13; see [_Sign-out_](mcp-sign-in.md#sign-out)).
  - **A late answer** is refused: "this request ended".
- **Stdio:** a Legacy stdio call waiting on a question holds the Container through `WorkspaceMcpBridge` (`use: true`) until its body ends, ≤10 min, under the one-hour Hold cap. Any Container cut (`container_restart`, resize, exit, deploy) expires the record ("<server>'s call ended (Container stopped)") and the call settles as cut. A Modern wait has no open request and holds nothing; its resume is a live caller and may start the Container and respawn the server. The record keeps the bridge's `spawn` from the ask (stdio `request` results carry `spawn`): when a resume is answered by another spawn with an error, the agent and the card get "<server>'s process restarted while it waited for your answer, so it may have lost track; calling it again starts over", and a repeat ask notes "<server> restarted since it last asked" ([Elicitation](https://github.com/ian-pascoe/cloudpid/issues/388) D15).
- **Where cards show:** in the waiting area of the call's conversation; a subagent's in its thread (the Session page, its Subagent Pane and its Subagent page), with the Session page's "waiting for you" strip jumping to it. A prompt send's card waits above the composer, its lane row reading "Getting <title> from <server> · …"; an App View's is drawn in cloudpid's waiting area ("from <server>'s app"), never inside the View. Cards never take focus. While the Session isn't `live`, inputs and buttons are disabled, typed values stay in the tab, and the card reads "Reconnecting…"; a live request carries an absolute `deadline` (epoch ms) so its countdown follows the server's clock ([Sampling](https://github.com/ian-pascoe/cloudpid/issues/387) D20.2, [Elicitation](https://github.com/ian-pascoe/cloudpid/issues/388) D1.2, D1.3, D18.2).
- **Notifications:** only for agent calls (root or subagent) and MCP tasks, never prompt sends or App Views, and never with `sampling: "allow"`. One `input` Notification when a call starts waiting, none when a rerun finds it waiting; a later round of the same call (or an MCP task's later question) notifies only after 2 min with nothing waiting. The text is "<server> needs your input" or "<server> asks you to open a page", never the message, field names or URL. `PushEvent.input` gains `mcp?: { server, kind: "elicitation" | "sampling" }`, tagged `<sessionId>:mcp-input:<server>`, and opens the Session at the card ([Sampling](https://github.com/ian-pascoe/cloudpid/issues/387) D2.5, D7.1, [Elicitation](https://github.com/ian-pascoe/cloudpid/issues/388) D12, [MCP tasks](https://github.com/ian-pascoe/cloudpid/issues/389) D7.1). Left to implementation for sampling, which the sources leave open: the text "<server> asks to use a model" and none for prompt sends and App Views.
- **Several at once on Modern:** one round may carry several questions. One refusal of a Sampling request sinks the round: sibling questions are withdrawn ("the call ended"), even an answered form; a declined form is a real answer and never sinks a round. Partial answers are never sent ([Sampling](https://github.com/ian-pascoe/cloudpid/issues/387) D12.4, [Elicitation](https://github.com/ian-pascoe/cloudpid/issues/388) D7).
- **Fork and Clone** copy the settled records of the calls they copy, never waiting requests or Session grants and declines. A record never enters any model's context.

## Sampling requests

Settled in [Sampling: model choice, Approval, Usage and the transcript](https://github.com/ian-pascoe/cloudpid/issues/387) and its amendments; bare D-numbers in this section are its decisions.

- **Origins:** the agent's calls (D1.1), a prompt send and an App View call (live, the card waiting ≤5 min; a prompt's 30 s get bound pauses meanwhile; an App View's card is withdrawn when the View is torn down or its page hidden), and an MCP task's questions. The completion runs in the call's conversation: a subagent's counts as the subagent's, a prompt's as its message's conversation, an App View's as its call's (D1).
- **The definition's key:** `sampling: "ask" | "allow" | "off"`, default `ask`, part of the MCP server definition (so the agent changes it only with Approval, and the card's notes block says "may use your models without asking" when it widens). In a Repo's `.pi/mcp.json`, `allow` reads as `ask` with the entry problem "copy it into the Settings to allow it". `off` means not declared. `allow` skips only the card: caps, the Spend limit, records and spans still apply. The MCP server form shows "Model use: Ask / Allow / Off", and `settings_mcp_get` shows it (see [_Entries_](mcp-configuration.md#entries); D2, X4).
- **The card:** one per waiting call, listing that round's Sampling requests with one decision for all and one record each; an elicitation form in the same round stays its own card ("also waiting: <server>'s form", by `callId`). It shows the server, the Role and model, the system prompt, messages, tools and notes, with:
  - **Allow for this call** (main button; covers the call's later rounds and resumes, kept with the question), its menu **Allow in this Session** (this server, every conversation of the Session, subagents included; kept in Session storage, listed in Session details with ✕) and **Always allow** (the owner's write of `allow` at the entry's Scope; the owner's own servers only);
  - **Refuse**, its menu **Refuse in this Session** and **Never** (writes `off`; the owner's servers only);
  - a Role picker.

  No per-request "Allow once", no editing of the request and no review of the reply.

- **Waiting:** Modern with `ask`, the agent's call: deferred through the record, the call running as for `secret_ask`, no deadline. Legacy, the agent's call: live, 10 min with a countdown, `inputWaitMs` 12 min. With `allow`: answered live in both eras, never deferred (D7.1–D7.3).
- **Which model:** `modelPreferences.hints`, in the server's order, each matched case-insensitively as a substring of each Role's model id without the provider prefix; the first hint that matches decides, the priorities picking among several matching Roles, else the lowest. With no hint matching: `medium` when `intelligencePriority` ≥ 0.7 and above both cost and speed priorities (a missing one counts as 0), otherwise `small`. Automatic choice stops at `medium` (a card note when a hint was clamped); only the owner's Role picker goes higher. A Role whose model is missing from the Session's `Models` falls to the next lower Role; none left makes the request unservable. Thinking is off (D4).
- **The completion:** always `models.stream` through the Session's `Models`, so `aroundRequests` (scrubbing, the spend gate, spans) applies. cloudpid adds nothing: no Instructions, project context or cloudpid tools. `includeContext` is treated as `none` (card note "asked to include context; none given"). `systemPrompt` and `temperature` pass; `stopSequences` (with a card note) and `metadata` are dropped. The server's tools go to the model and cloudpid never runs them; a tool with no description gets its title or name; Anthropic's non-strict schema flattening is accepted with a note when `$defs` or `oneOf` is lost (D9, D10, D14). `toolChoice: "required"` maps per API (a golden test per row):

  | API                                                                                                               | Value                                                                 |
  | ----------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
  | `anthropic-messages`, `bedrock-converse-stream`, `google-generative-ai`, `google-vertex`, `mistral-conversations` | `"any"`                                                               |
  | `openai-completions`, `openai-responses`, `azure-openai-responses`, `openai-codex-responses`                      | `"required"`                                                          |
  | any other                                                                                                         | `auto`, with the card note "the model was not required to use a tool" |

- **Content:** text passes; images pass if the model takes them, else the request is refused; top-level audio is refused. `tool_use`/`tool_result` map to pi-ai `toolCall`/`toolResult`, one `toolResult` per block. Inside a `tool_result`: `resource_link` → `[resource: <uri>]`, an embedded text resource → its text, an embedded blob → `[binary resource: uri, mime, size]`, `structuredContent` → JSON text when there is no text, audio → `[audio omitted]`. Before the card and before the sample, the spec's pairing rules are checked (a user message with a `tool_result` holds only tool results; every assistant `tool_use` is answered exactly once in the next message; no orphan results), since pi-ai repairs mismatches silently; a failure is refused without asking the owner ("invalid sampling messages: <rule>") (D11, D15).
- **The reply** goes back as written, with thinking blocks dropped and placeholders and Secret References never resolved. Stop reasons: `stop` → `endTurn`, `length` → `maxTokens`, `toolUse` → `toolUse`; `error` and `aborted` (and a reply with `argumentsError`) are model failures. The result's `model` is the id actually used. The reply reaches the agent only inside the server's own tool result.
- **Limits:** `maxTokens` = min(asked, 8192, the model's maximum), then `clampMaxTokensToContext`; the core's 16 MiB, text ≤1 MiB, images within the Session's image limit, the request within the model's context window; ≤64 tools and 256 KiB of schemas; 2 min per sample; ≤20 samples per call and per MCP task ("sampling limit for this call reached"). Rate: ≤2 samples at once and 30 a minute per (Session, server), App View calls included, which delay a sample within the call's bounds and never refuse it. A `2025-11-25` request carrying `params.task` has `task` ignored and is answered normally (D5.3, D8.2, D11.5, X2, X9).
- **Usage and the Spend limit:** recorded as each sample ends in the Session's own ledger beside the title call's, by conversation and server; the `usage` message gains a `sampling` part, a line of its own in the header's Usage details. The Spend limit is checked before the card and before each sample at the `Models` gate; at the limit the request is refused without ending the Run. Samples already running when the limit is crossed finish (D5).
- **Secrets:** the scrub set is the `secret_ask` values plus the Environment's kept Secrets as the Registry's `sessionSecrets` hands them over (the Environment's over Global's), refreshed at most every 30 s (a Secret kept within 30 s may be missed); `mcpServerValues` resolves `${NAME}` from the same source (build test: everything it can resolve is in the set). `scrubbingModels` scrubs `messages` and `systemPrompt` but never `context.tools`, so the sampling code redacts the server's tool names, descriptions and schemas itself. Records and replies are stored redacted with the same set.
- **Refusals:** the owner's, the Spend limit, the cap, an invalid or unservable request, a model failure after pi-ai's retries, or a live bound running out (D12, X1, X10).
  - **Modern:** `onInput` resolves `"refused"` and the server is told nothing (`InputResponse` has no error form); the originating call ends locally. The agent's call gets `isError` "<server> asked for a model reply, which was <reason>. On this server's protocol that ends the call, which may have done part of its work." with `details.error: "sampling_refused"` (the same code inside `codemode`); a prompt send is refused with `MCP_PROMPT_FAILED` and the composer restored with Retry; an App View's call returns an error and its audit log notes it; an MCP task gets `tasks/cancel` and ends with `sampling_refused`, posted to its conversation if it is in the background.
  - **Legacy:** the server gets `-1` (a refusal), `-32602` (invalid or unservable) or `-32603` (a model failure), and its own result comes back with a `<harness>` diagnostic ("<server> asked for a model reply; refused by you / out of budget / over the limit"). An allowed request adds nothing.
- **Records:** one per Sampling request in Session storage outside History (the store App records use): server, origin, conversation, call, sequence, status, Role and model, hints and priorities, system prompt, messages, tools offered, `toolChoice`, reply, stop reason, tokens, cost, who decided, notes. A call's records keep the first request whole and, for each later round, only the messages after the earlier round's prefix, each text cut at 16 KiB, never reused as context. ≤256 KiB each, 16 MiB per Session, the least recently used reduced to stubs. Summaries: the call's `details` (server, Role, status, tokens, cost), a prompt's `cloudpid.user` `mcpPrompt.sampling`, an App View's App record audit log. `/export` writes "Sampling: server · Role · tokens · cost" (D6, X8).
- **Clients:** `mcp_sampling_requests` pushes the waiting requests to every client, `mcp_sampling_answer` answers, and `mcp_sampling_get` fetches a settled record when expanded.
- **Deprecation (SEP-2577):** no warning to the owner. The server's status gets `deprecated: sampling` at its first Sampling request, with a `warning` log once per server per host lifetime. A connection at a revision without sampling never declares it (D13).

- **As built, Modern Sampling ([#486](https://github.com/ian-pascoe/cloudpid/issues/486); an agent's `tools/call`, direct or in `codemode`; `packages/mcp/src/connection.ts` `answerSample`, `apps/mcp-worker/src/calls.ts` `withSampling`, `packages/extensions/src/mcp/{sampling,sampling-questions,sample,deferred-questions,questions,rounds,exchange}.ts`, `packages/protocol/src/mcp-sampling.ts`, `apps/web/src/chat/mcp-sampling-card.tsx`):** a Modern request is declared `sampling: { tools: {} }` (_Declaration_ above), and the core hands each `sampling/createMessage` of an `input_required` round to `onInput` as a `deferrable` request of era `modern`. **`allow`** is answered live, as on Legacy. **`ask`** on a call that keeps its questions (`ctx.answers.defer`, the host listing `resume`) is _checked_ as on Legacy (parameters, pairing, Spend limit, a model to run it, the 20-per-call cap; a failed check is refused live, with no card) and then answered `defer`: the request is kept with the call's round beside the round's forms, as a question of kind `sampling` under the slot `sampling:<id>` (its parameters, redacted, chunked to the storage `mcp-question:p:<id>:<n>` and at most 1 MiB; one over it is not kept and is refused), its record written `waiting` (`mcp-sampling:waiting`), and the round's count of samples kept with the round (`sampled`). A standing grant (_Allow in this Session_, a call's _Allow for this call_) answers it as it does live, with no card. The call's _Allow for this call_ is kept at `mcp-sampling:call:<callId>`, so it covers the later rounds and resumes of a call after a restart; the card's `allow_call` also reaches the call's other waiting Sampling requests, and a Session or Always choice reaches those of the server, rather than asking once per request. **The card** is the Legacy one (`McpSamplingRequest`, shown, answered and revoked through the same messages) with `waits: "owner"`, a field of the request a client of an older build ignores: it shows "<server> waits for your answer" for the countdown, and its `deadline` is the far one an elicitation's is (`MCP_DEFERRED_DEADLINE_MS`) for a client that does not read `waits`. There is one card per Sampling request, as the protocol's request is one request, not one per round with one decision for all as the card above says. **Waiting** is as for a Modern form: no clock on the call, kept through an eviction, one `input` Notification when the call first waits (`kind: "sampling"` if it was a Sampling request that did), withdrawn with the call by Stop or by the script's timeout. **Running:** the sample is not made when the owner says yes but when the round resumes, once every question of the round is answered: `rounds.ts` runs each answered request's sample (`sampled`: on the stored, redacted parameters, the Role the owner picked, the Spend limit checked again) before it stores `mcp.resumed.<r>`, and its reply goes in the one resume beside the form answers, so the call is sent once and resumed once however many requests the round holds. The reply is never stored; a restart before the `mcp.resumed.<r>` mark makes the sample again (its cost twice) rather than losing the call. **Refusal** (the owner's, a Never, a refused standing grant, a sample that fails at the resume, a limit reached) _sinks the round_: an `InputResponse` has no error form, so the server is told nothing and gets no resume; every other question of the round, answered forms too, settles `cancel` by cloudpid ("the server's call ended"), its card withdrawn, and the call ends locally with `isError`, `details.error: "sampling_refused"` and the words in _Refusals_ above (a script's call fails with the same words). The core's part is only that a refused request in a Modern round fails the call `Unsupported`; the Session decides what the refusal reads as (`sampling.sunk()`, and `Resumed` `{ kind: "sunk" }` for one found at the resume), so no new error type crosses the host. On a Session older than this change over this engine, the Modern request (declared by the engine) is answered live through the Legacy card path: it has no `defer` to use, and `allow` is live in both eras. **Records and details** are the Legacy ones: a deferred request's record is `waiting` until the owner decides or the round settles it (`refused`, `by: "owner"` or `"cloudpid"`, `why: "unanswered"` for one that no one decided), and the call's `details.sampling` lists it. **Not built:** a switch of the definition to `allow` while a request waits does not run it (it is answered by its card, or ends with its call); the "also waiting: <server>'s form" line on a card; prompt-send, App View and MCP task origins ([#492](https://github.com/ian-pascoe/cloudpid/issues/492), [#498](https://github.com/ian-pascoe/cloudpid/issues/498), [#497](https://github.com/ian-pascoe/cloudpid/issues/497)); the `/export` lines and stdio ([#569](https://github.com/ian-pascoe/cloudpid/issues/569)). **Tests:** the core answers and refuses a Modern Sampling request (`packages/mcp/src/modern-questions.test.ts`), the engine declares it per request (`apps/mcp-worker/src/modern-questions.test.ts`), the Session defers, shows, grants, refuses and resumes it (`packages/extensions/src/mcp-sampling-modern.test.ts`, `mcp-deferred.test.ts`), the card reads `waits` (`apps/web/src/chat/mcp-sampling-card.test.tsx`), and the whole path runs through the real host, engine and a fake Modern server (`apps/server/src/session/mcp-sampling-modern.workerd.test.ts`) and, for a script's call across an eviction, through a fake host (`apps/server/src/workspace/mcp-codemode.workerd.test.ts`: one `tools/call` and one resume).

## Elicitation requests

Settled in [Elicitation in form and URL modes as durable requests](https://github.com/ian-pascoe/cloudpid/issues/388) and its amendments; bare D-numbers in this section are its decisions.

- **No per-server key:** disabling the server or "Decline in this Session" are the off switches. A Repo server's card says "from <owner/repo>". The header shows the server's configured name (never `serverInfo`) and source badge, and an origin line: "during `mcp__github__create_issue` · the agent", "· subagent <name>", "getting prompt <title>", "<server>'s app" or "MCP task" (D2, D6.4).
- **Waiting** (D1, D5, D18.1):
  - **The agent's call, Modern:** deferred, no deadline, the Run running as for `secret_ask`.
  - **The agent's call, Legacy:** live, 10 min from the ask with a countdown ("<server>'s call ends in 9:12"), then `cancel` and the call goes on. The server's own `notifications/cancelled` for the question withdraws the card ("<server> stopped waiting").
  - **A prompt send:** live in both eras and modes, no Notification, 5 min (the 30 s get bound pauses from the ask until the answer), then `cancel` and the get goes on; the lane row reads "Getting <title> from <server> · waiting for your answer". The form holds that conversation's prepare queue for at most 5 min; commands, Fork, Clone and other conversations go ahead, and a steer's prompt waits the same way while the Run goes on. Stop, and so abort, withdraws the message and its card, and the ones waiting behind it ([_Getting a prompt at send_](mcp-in-a-session.md#getting-a-prompt-at-send)).
  - **An App View call:** live, 5 min, no Notification; withdrawn when the View is torn down but not when its page is hidden (URL mode sends the owner to another tab); at most one waiting request per View, another getting `cancel` and an audit-log line.
- **The form:** the Session normalizes `requestedSchema` into cloudpid's own `ElicitationForm { fields }` with kinds `text | email | url | date | date_time | number | integer | boolean | choice | multi_choice`; a pure validator in `@cloudpid/mcp/types` runs in the web before submit and again in the Session, and the web never reads raw JSON Schema (D6).
  - **Widgets:** string → `input` (a textarea when `maxLength` > 200); `email`/`uri` → `type=email`/`type=url`; `date` → `type=date`; `date-time` → `datetime-local`, sent as RFC 3339 with the browser's offset, the zone shown; number/integer → `type=number` with min/max (step 1 for integers); boolean → checkbox; a single enum → radios up to 5 options, else a `select`, showing `oneOf` titles (or legacy `enumNames`) and sending values; a multi enum → a checkbox group with `minItems`/`maxItems`.
  - **Filling:** defaults prefilled, the SDK's `applyDefaults` off; required fields marked and Submit disabled until valid; empty optional fields omitted; values sent as JSON types. A form with no fields (a confirmation gate) shows Accept and Decline.
  - **Text:** all server text is plain (no Markdown or HTML, URLs never clickable), control and bidi-override characters stripped, held Secrets redacted. A standing footer: "Only <server> gets what you enter, and its reply to the agent may repeat it. Never enter a password or key here." No Secret picker, Secret Reference resolution or masked input.
  - **Refused unseen as malformed:** root `type` not `object`; a property outside the subset (a nested object, an array of non-enums, `$ref`/`allOf`, no or unknown `type`); `required` naming a missing property; over the bounds. Ignored with a note in the record: unknown keywords (`pattern`, `additionalProperties`, `examples`), an unknown `format` (shown as plain text), an invalid default (dropped).
  - **Bounds:** ≤32 fields, ≤100 options per enum, schema ≤64 KiB; the message shown up to 4,000 chars then cut with a note; titles 120, descriptions 500, option titles 200 chars; a value ≤16 KiB (or the server's smaller `maxLength`), an answer ≤64 KiB.
- **Answers** (D7): Submit (or Accept), Decline, and a quiet Cancel ("closes without answering; <server> may ask again"); no owner note.

  | Event                                           | Legacy                                            | Modern                  |
  | ----------------------------------------------- | ------------------------------------------------- | ----------------------- |
  | Submit / Accept                                 | `accept` + `content`                              | the same, in the resume |
  | Decline / Cancel                                | `decline` / `cancel`                              | `decline` / `cancel`    |
  | 10-min bound                                    | `cancel`                                          | n/a                     |
  | Per-call cap, App View limit                    | `cancel`                                          | `cancel`                |
  | Malformed                                       | `-32602` "unsupported elicitation form: <reason>" | `cancel`                |
  | cloudpid's own rules, "Decline in this Session" | `decline`                                         | `decline`               |

  The agent sees the server's own result, plus, when the answer was not `accept`, one `<harness>` line: "The user declined <server>'s request for input. Don't repeat the call unless the user asks." ("cancelled" likewise; cloudpid's own: "cloudpid declined/cancelled it: <reason>"). `details.elicitation` is `[{ server, mode, action, by: owner | cloudpid, reason?, fields: names, host? }]`. cloudpid's own refusals never end the call locally (unlike sampling): the server can go on.

- **Forms asking for a credential are declined unseen** (`decline`): a free-text field (`type: "string"` with no `enum`/`oneOf` and no `format` in the subset), or any string with `format: "password"` or `writeOnly: true`, whose name or title, each split into words at `_`, `-`, spaces and camelCase (acronym runs too: `APIKey` → `api key`) and lowercased, ends in `password`, `passwd`, `passphrase`, `token`, `secret`, `apikey`, `cvv` or `cvc` (or a plural), or in `api key`, `access key`, `private key`, `secret key` or `card number`. `key` alone never matches, and the message and descriptions are never checked. Passes: `reveal_secret`/`confirm_delete_token` (boolean), `token_type` (enum), `max_tokens` (number), `password_hint`; accepted miss `password_confirmation`; declined `confirm_password`, `githubToken`, a title "Your API key"; accepted false positive `page_token`. The agent's diagnostic: "it asked for a credential ('<field>'), which MCP servers must not ask for in a form; the user can give the server a key through its MCP server definition (a Secret as `${NAME}`), or the server can ask on its own page."
- **Every submitted string is checked in the Session** before it leaves, against sampling's scrub set (with `Redactions` encodings), `credentialCheck` and `holdsPlaceholder`; a match bounces back to the card with the field marked ("matches one of your Secrets"), nothing stored.
- **The owner learns of every unseen decline** (credential, URL, cap, "Decline in this Session"): a line on the call's card from `details.elicitation` ("cloudpid declined <server>'s form: it asked for a credential ('API token')"), on a prompt's chip, or in an App View's audit log; the server's status counts "asked for a credential in a form · N times" (`settings_mcp_get`); a `warning` log once per server per host lifetime. No Notification and no card (D8).
- **URL mode** (D9, D16):
  - **Declined unseen:** a scheme other than `https:`, userinfo in the URL; `localhost`, `*.localhost`, `*.local`, `*.internal`, or a loopback, private, link-local, CGNAT or ULA IP literal; cloudpid's own hosts (the stage's app host and the App sandbox zone). An invalid URL or one over 8,192 chars is malformed.
  - **The card:** "<server> asks you to open a page", the message, the full URL in a monospace box with the registrable domain emphasized, the host in ASCII (punycode) with a warning for an IDN or mixed scripts, and "<server> is at <host>" for HTTP servers. Nothing is prefetched. **Open** is an `<a target="_blank" rel="noopener noreferrer">` whose click records consent (`accept`); it opens only in the owner's own browser (the system browser on an iOS PWA), never the agent's browser, the Browser Pane, an Owner tab, a Live View, the App sandbox or an iframe. Decline and Cancel are offered until the owner opens it. URL mode is never an MCP sign-in (see [_Sign-in requests_](mcp-sign-in.md#sign-in-requests)).
  - **Legacy in-call:** Open sends `accept` at once; the card reads "Opened · <server> goes on when you finish there" with Open again, and closes on `notifications/elicitation/complete` for its `elicitationId` on the call's own POST stream ("Finished at <host>"; the core's `onInputComplete({ key })` hook, the host keeping no `elicitationId` state; completions on other streams are ignored), the call's end, or 10 min. The call's timeout stays paused until then.
  - **Legacy `-32042`** (URL elicitation required) ends its call, so it waits durably: the core returns it as `input_required` with a resume state that sends the original request again with a new id. One card per listed elicitation, shown one at a time; "Done, try again" is enabled once every listed URL has been opened (from any client), Decline and Cancel from the start. Done resends once; a new `-32042` naming an already-opened id brings the card back as "Not finished at <host> yet", with no new Notification. Cancel settles the call with the server's error plus the answer line. No automatic retry. On a prompt send or App View call it is live, 5 min, Done resending once within it. A `-32042` round is round _r_ for the markers, so a `tools/call` is sent again only after a `-32042`, once per Done, at most **10 resends per call** (the 11th: the server's error plus "<server> kept asking for the same page; stopped after 10 tries"). The agent's `read_mcp_resource` follows the same rule.
  - **Modern:** Open records the owner's click on the question and answers nothing; "Done, try again" answers the round's pages `accept` (with no `content`) in the resume, once every page of the round is opened. A next round with the same key and URL shows "Not finished at <host> yet". Decline is offered until the owner opens the page and answers `decline`; after Open the way out is Cancel, which answers `cancel`. Each answers that page only: unlike a Legacy `-32042`'s Decline or Cancel, which answers the whole round (and whose Decline is offered throughout), a declined Modern page never sinks the other questions of its round. The wire outcome is what the spec first said: the server hears `accept` after Open and Done, `cancel` after Open and Cancel, `decline` before Open and Decline.
- **Values are never kept:** Legacy answers pass in memory to the waiting callback. Modern and `-32042` answers are sealed in the record's `answer` with AES-GCM (HKDF purpose `mcp-elicitation` from `SECRETS_ENCRYPTION_KEY`) and deleted once `mcp.resumed.<r>` resolves or the record is withdrawn; the resume is built inside `execute`, so values never enter memos, arguments or the journal. Typed values live only in the tab and are lost on reload (D10.2, D13).
- **Several at once:** one card per request; within one call shown one at a time (key order on Modern, arrival order on Legacy), "1 of 3 from <server>", with "Decline all 3". At most 10 distinct requests per call or per MCP task (repeats of an opened URL don't count); beyond that `cancel`, "elicitation limit for this call reached". **Decline in this Session** (card menu) declines this server's later requests unseen in every conversation of the Session; listed in Session details with ✕. No hourly rate limit (D11).
- **Records:** one settled record per request, outside History in the sampling record store, ≤64 KiB: server, source, origin, conversation, call, era, mode, the redacted message (≤4,000 chars) and normalized form, the URL's origin only, the action, who decided and why, notes, asked and settled times, and the names of the fields answered; **never a value**. Summaries: the call's `details`, a prompt's `cloudpid.user` `mcpPrompt.elicitation`, an App View's audit log. `/export`: "Elicitation: <server> · form · submitted (name, email)", "· page on <host> · opened", "· declined" (D10).
- **Clients:** `mcp_elicitation_requests { requests }` (after `hello`, an empty list too, and in full on every change; each request carries its `callId`) and `mcp_elicitation_answer { id, request, action: accept | decline | cancel | opened | done, content?, scope?: "session" }`; failures return as the command's failure (field errors, "matches one of your Secrets", "this request ended") (D12.3).
- **As built ([#472](https://github.com/ian-pascoe/cloudpid/issues/472); Legacy form mode on an agent call only):**
  - **Wire:** `mcp_elicitation_requests { requests }` (each `{ id, callId, conversationId, server, tool, message, form, notes, deadline, source?, waits?, page? }`, `page` being `{ url, host, domain, warning?, opened, retry?, again?, finished? }` of a URL-mode question, `waits: "owner"` on a Modern question (below), whose `deadline` a newer card ignores; `source` being `{ kind, slug? }` of where the server is defined; sent after `hello` on every connect, the empty list too, and in full on every change) and `mcp_elicitation_answer { id, request, action: accept | decline | cancel | opened | done, content? }` (`packages/protocol/src/mcp-elicitation.ts`, `session.ts`). `opened` and `done` come with URL mode (below; each request then has `page?`) and `scope` with "Decline in this Session". A refusal returns as the command's `error`: the field's problem ("name: is required", "name: matches one of your Secrets") or "This request ended"; the answer's command fails with it on the web, and the card shows it (below). A request's `id` is `<callId>:<n>`, `n` counting the call's questions, so it is unique even if a server reuses its own request key.
  - **The form and its checks:** `normalizeElicitationForm`, `validateElicitation`, `answeredFields` and the bounds are in `@cloudpid/mcp/types` (`elicitation.ts`), run by the Session on the server's schema and again on the owner's answer, and by the web before Submit; the credential matcher's pass and decline lists are its tests (`elicitation-form.test.ts`): names are folded to NFKC, split into words, stripped of trailing digits and of the fillers `value`, `field`, `input`, `text` and `entry`, and `pass` + `word` split across words counts (`pass_word`, `password2`, `password_value`). A field's name must be plain (non-empty, at most 120 characters, no control characters or extra spaces) or the form is malformed, and names are used only as own keys (`__proto__` and `constructor` are ordinary names). The Session's answer check adds the Secrets it holds (in any encoding redaction knows), the deploy-time credentials and any Secret Reference placeholder.
  - **What the server wrote:** the message is plain text (control, bidi-override and zero-width characters stripped, newlines kept), cut at 4,000 characters with the note "the message was cut at 4,000 characters"; every name cloudpid quotes in a reason, a diagnostic line or `details.elicitation` is cleaned (quote marks, angle brackets and backslashes dropped, cut to 60 characters) and put between quotes. The settled record keeps the redacted message, form and notes the owner was shown.
  - **The agent's call:** a form answered, declined or cancelled, or ended by cloudpid, is in `details.elicitation: [{ server, mode: "form" | "url", action, by, reason?, fields, host?, finished? }]` (never a value; a page's `host` and, when the server said the owner finished there, `finished`); the server's own result stays as it is, plus one `<harness>` line per question not accepted ("The user declined <server>'s request for input. Don't repeat the call unless the user asks."; "cancelled" likewise; cloudpid's own: "cloudpid declined/cancelled <server>'s request for input: <reason>"). A credential form is declined unseen with the spec's diagnostic, with no card and no Notification; a malformed one, or a URL-mode request that fails the rules above, is refused `-32602` "unsupported elicitation form: <reason>" and recorded. Both count toward the call's cap of 10 like any request: past it the server is told `cancel`, "elicitation limit for this call reached". The call's timeout stops while a question waits, by the one `pausableDeadline` (`packages/mcp/src/deadline.ts`) that both ends of a call use: the core's (askable Legacy calls only; every other call keeps the SDK's timeout and its reset on progress) and the Session's `lost` deadline. It resets on each attempt, and a `clear` leaves no timer behind. Stop interrupts the wait and withdraws the card.
  - **Withdrawn:** a card goes away when the owner or the server ends it, the call ends or is stopped, the 10 minutes pass, and when its server is switched off, hidden (its own Exposure) or removed (`withdrawServer`, run after each request start that changes the inventory): the server is told `cancel`. The withdraw is seen at the next request start of any conversation, and none comes while the root's only call waits, so in a one-conversation Session a server switched off mid-wait keeps its card until it is answered or the 10 minutes pass. A question whose record the Session's storage cannot take is never shown (the server is told `cancel`, "cloudpid could not record the question"), so no card outlives its record.
  - **The owner:** `McpElicitationCard` (`apps/web/src/chat/mcp-elicitation-card.tsx`, in the waiting area) draws the widgets above with defaults prefilled, required fields marked, Submit off until the values validate, a confirmation gate (Accept, Decline) for a form with no fields, Decline and a quiet Cancel, the standing footer and a countdown "<server>'s call ends in m:ss" from the request's `deadline`, or, for a request with `waits: "owner"` (a Modern question, [#480](https://github.com/ian-pascoe/cloudpid/issues/480)), "<server> waits for your answer" and no countdown. The origin line reads "during <tool> · the agent" or "· subagent <name>", with a badge for where the server is defined (Global, This environment, "from <owner/repo>"); a date and time field says "In your time zone, <zone>". Typed values are React state in the tab. An answer the Session refuses (a value that matches a Secret, a field's problem, a request that ended, a lost connection) comes back to the card: the buttons are on again, the field is marked with the reason, or the reason shows on the card. The card stays through a dropped connection, off and reading "Reconnecting…", with what was typed; the next socket's list says which still wait. For assistive technology each input says `aria-required`, `aria-invalid` and `aria-describedby` (its description, its time zone note and its problem), and a group of radios or checkboxes is named by its title. One `input` Notification ("<server> needs your input", `PushEvent.input.mcp`, tag `<sessionId>:mcp-input:<server>`) when a call starts waiting, and for a later question of the same call after 2 minutes with nothing waiting.
  - **The call's card:** the MCP tool call's card in the transcript lists each question under "Questions" from `details.elicitation` ("You answered <server>'s form (name)", "You declined …", "cloudpid declined <server>'s form: it asked for a credential ('API token')…", "cloudpid cancelled <server>'s form: the owner did not answer in time").
  - **The endpoint:** `status` and `waitForChange` list each waiting question as `{ kind: "elicitation", request_id, agent_id, summary: "<server> needs your input" ("<server> asks you to open a page" for a page), since, url }`, never its message ([_The MCP endpoint_](mcp-endpoint.md#waiting-requests)).
  - **Records:** one settled record per question in the Session's storage (`mcp-question:s:<id>`, the newest 100 kept) and the list of those waiting (`mcp-question:waiting`), which a new instance finds and expires. Nothing reads the settled records yet; `McpQuestionsService.records` is the seam, and the call card's richer lines and `/export` ([#569](https://github.com/ian-pascoe/cloudpid/issues/569)) are its reader next.
  - **Tests:** the 10-minute bound runs through the real engine against a fake Legacy server (`apps/server/src/session/mcp-elicitation.workerd.test.ts`), with the bound shortened to 300 ms for a Session named `mcp-short-wait-*` and nothing else changed; the unshortened bound and the paused timeout are in `packages/extensions/src/mcp-questions.test.ts`, `mcp-elicitation.test.ts` and `packages/mcp/src/deadline.test.ts`, over a test clock.
- **As built, URL mode on Legacy ([#487](https://github.com/ian-pascoe/cloudpid/issues/487); an agent call only):**
  - **The rules:** `checkElicitationUrl` (`packages/mcp/src/elicitation-url.ts`, its own subpath `@cloudpid/mcp/elicitation-url`, not `./types`, so the web and the Registry do not load the Public Suffix List; its 70-odd golden cases in `elicitation-url.test.ts`) decides declined or malformed and makes the card's `{ url, host, domain, warning? }`; `isOwnHost` (`apps/server/src/mcp/own-hosts.ts`) is the deployment's own hosts, a pure predicate over constants (`pi.ianpascoe.dev`, `cloudpid-server-<label>.ian-g-pascoe.workers.dev`, the `ianpascoe.app` App sandbox zone), passed in by `Session`. The registrable domain is the Public Suffix List's, private section included (`tldts` with `allowPrivateDomains`, in `packages/mcp`), so it names the page's owner, not its host platform: `attacker.github.io` emphasizes `attacker.github.io`, `auth.example.co.uk` emphasizes `example.co.uk`, and an IP literal or a bare suffix is its own.
  - **Capabilities and the core:** a Legacy connection declares `elicitation: { form: {}, url: {} }` at `initialize` (`apps/mcp-worker/src/call-context.ts`); Modern declared `form` only until [#493](https://github.com/ian-pascoe/cloudpid/issues/493) (below). In the core (`packages/mcp/src/connection.ts`) an `elicitation/create` with `mode: "url"` asks the host's `onInput` like a form and, once the owner accepts, keeps the call's clock paused until `notifications/elicitation/complete` for its `elicitationId` arrives on the call's own POST stream (`onInputComplete({ key })`), the call ends, or the 10 min pass (`tap.ts` `Ties.onComplete`). A `-32042` is kept only where the host can wait durably (Legacy, `onInput`, the answers declare `elicitation`, `defer` and `pages`): the call returns `pages_required` with a `ResendState { v: 1, method, name, arguments, deferred, round, message }` of its own (not an optional field of the `ResumeState`), and `connection.resend` sends the original request again as it was when every page was accepted, and otherwise fails with the server's own `-32042` error. The host carries it as `PagesRequired` and `request({ op: "resend" })`, listed as the host feature `resend`: an older engine or host refuses the op as unknown, a Session sets `ctx.answers.pages` only when the host lists the feature, and an engine from before it drops the key, so a `-32042` is then the server's error as it was. The 11th round fails with "<message>. <server> kept asking for the same page; stopped after 10 tries". A read's `-32042` (`read_mcp_resource`) is kept the same way but with no state: `readResource` returns `pages_required` with the server's message only, the Session counts the rounds (the 11th fails with the same line), and once every page is accepted it sends the original read again; a read is replay-safe, so nothing of it is durable across a restart, and a rerun sends the read afresh (so the 10-round count is per instance, bounded by the restart limit). A read's `defer: true` answer therefore means "may keep pages": the read keeps only a `-32042`'s pages, and a Modern form is still a `cancel`.
  - **The Session:** `McpQuestionsService` (`packages/extensions/src/mcp/questions.ts`, `deferred-questions.ts`, `rounds.ts`) makes a page question's request with `page: { url, host, domain, warning?, opened, retry?, again? }`, `form: { fields: [] }` and the same `id`s; `mcp_elicitation_answer` takes `opened` and `done`. A live page (`retry` absent) answers the server `accept` on the first `opened`, keeps the card as `opened` and holds the Session's clock (`whileOpen`) until the page is finished; `done` there is refused. A `-32042` round waits as a deferred round (era `legacy`, `McpDeferredRound.state` tagged `Resend` for a call or `Read` for a read, one question per listed elicitation, the cap of 10 distinct pages counting a page the owner was done at and the server asks for again as no new one). Those pages are kept in the Session's storage (`mcp-question:pages:<callId>`, the newest 64 keys of at most 200 characters each, with how many came again, which numbers their questions, gone with the call), so a repeated page reads "Not finished" after a restart too, with no new Notification (a round that is all repeats is told to nobody) and no new count; `done` answers every page of the round `accept` once each is opened (from any client), a Decline or Cancel of any page answers the whole round that way. A page that fails the rules is declined unseen: the server is told `decline`, and the call's `details` and `<harness>` line say "cloudpid declined <server>'s request for input: <reason>".
  - **The owner:** the card (`mcp-elicitation-card.tsx`) shows the URL as plain text in a monospace box with its registrable domain bold, the ASCII host, a warning for `idn` and `mixed_script`, and Open, an `<a target="_blank" rel="noopener noreferrer">` that is never followed by the card and whose first click sends `opened`; after it, a live page reads "Opened · <server> goes on when you finish there" with Open again and no Decline, and a `-32042` page offers "Done, try again" once every page of its call has been opened (the card reads the whole list), with Decline and Cancel throughout; `again` reads "Not finished at <host> yet". When the server says the owner finished (`notifications/elicitation/complete` on the call's own stream), the card reads "Finished at <host>" with nothing to press for a moment (`MCP_PAGE_FINISHED_SHOWN_MS`, 4 s, `page.finished`) and the call's clock goes on at once; a call that ends right behind it (the usual case) leaves that card to its timer rather than removing it. The call's card lists "You opened a page on <host> for <server>; finished there" (`details.elicitation` with `mode: "url"`, `host` and `finished`, never the address). The push and the endpoint read "<server> asks you to open a page" (`PushEvent.input.mcp.page`); the record keeps `era`, `mode` and the page's origin only.
  - **Not built here:** "<server> is at <host>" for an HTTP server (the Session does not hold its URL); "1 of N" and "Decline all" ([#569](https://github.com/ian-pascoe/cloudpid/issues/569), which also owns showing the pages of one `-32042` round one at a time: each page shows its own card at once, and "Done, try again" is on once all are opened).
  - **Not built:** each is in a ticket that says so: Modern forms are deferred ([#480](https://github.com/ian-pascoe/cloudpid/issues/480), in [_The waiting-question record_](#the-waiting-question-record)), the rest of Modern in [#455](https://github.com/ian-pascoe/cloudpid/issues/455) and [#486](https://github.com/ian-pascoe/cloudpid/issues/486); the prompt-send, App View and MCP task origins of Sampling ([#492](https://github.com/ian-pascoe/cloudpid/issues/492), [#498](https://github.com/ian-pascoe/cloudpid/issues/498), [#497](https://github.com/ian-pascoe/cloudpid/issues/497)); the server status count ([#501](https://github.com/ian-pascoe/cloudpid/issues/501)); a prompt send's origin ([#492](https://github.com/ian-pascoe/cloudpid/issues/492)), an App View's ([#498](https://github.com/ian-pascoe/cloudpid/issues/498)) and an MCP task's ([#497](https://github.com/ian-pascoe/cloudpid/issues/497)). In [#569](https://github.com/ian-pascoe/cloudpid/issues/569): the once-per-host `warning` log and the spans; `/export` lines; "Decline in this Session"; "1 of 3 from <server>" and "Decline all" (each waiting question shows its own card, in arrival order); Fork and Clone copying the settled records; Legacy questions over stdio (the host's `request` says stdio "comes later"). Also not built: the `conn` check on a Legacy answer (`ServerChanged`: an answer for a server whose definition changed while the card waited is not refused; a Modern resume has it at the host), the push that withdraws a card mid-wait, and the withdraw of a server already gone when its question is asked ([#569](https://github.com/ian-pascoe/cloudpid/issues/569)); a card in a subagent's thread (the card shows in the root's waiting area, with the subagent named).
  - **Known limits:** a question asked after its server already left the inventory is never withdrawn; stdio declares elicitation but cancels every question ([#569](https://github.com/ian-pascoe/cloudpid/issues/569)); look-alike letters (a name spelled with another script's letters) can still slip past credential detection, and the Secret check on the answer is the backstop.
- **As built, URL mode on Modern ([#493](https://github.com/ian-pascoe/cloudpid/issues/493); an agent's `tools/call` only):**
  - **Declared:** a Modern request declares `elicitation: { form: {}, url: {} }` in its `_meta` only for a call whose caller offers elicitation, has an `onInput`, **and** keeps a question for later and sends the call again once it is answered (`ctx.answers.defer` and `pages`, `apps/mcp-worker/src/call-context.ts`); any other Modern call declares `form` (or nothing), as before. So a Modern page is always a question that waits durably, never one answered on the spot: a read has no `resume` (`readResource` declares from the answers without `defer`), so a Modern read is never offered a page, and a Session on a host that does not list `resend` sets no `pages`. A Modern server that asks for a page it was not offered gets `cancel` ("the call cannot wait for a page"), which the call's `details` and `<harness>` line report as cloudpid's.
  - **The round:** the page is a question of the round like a form (`input_required`'s `inputRequests`, `{ method: "elicitation/create", params: { mode: "url", url, message } }`, no `elicitationId`): it goes through `onInput` and `checkElicitationUrl`, is kept by `defer` (`retry`, so its card offers "Done, try again"), stored in the round with `mcp.wait.<r>` and shown, as above. The question's request carries the era (`McpInputRequest.era`, `legacy` | `modern`, set by the core), which the Session keeps on the record (`DeferredQuestion.era`, `McpQuestionRecord.era`; a record or a request from before it reads as `legacy` for a page and `modern` for a form).
  - **Open and Done:** Open (`opened`) records the click on the question and answers nothing, as for a `-32042`; "Done, try again" (`done`) is on once every page of the round is opened and answers **the round's pages** `accept`, a form beside them keeping its own answer; the round's resume goes once every question has one. A page's `accept` carries no `content` (`{ action: "accept" }`): this holds for a Legacy `-32042`'s `resend` too, which used to carry `content: {}` and ignores the answers either way. **Decline** is offered until the page is opened: the Session refuses a Decline of an opened Modern page ("This page is open: cancel it instead") and the card hides it (the request's `page.era`, a new optional key of `McpElicitationPage`, says `modern`; a card from before it keeps offering Decline and is refused), and likewise a live Legacy page's Decline after Open, which the server was already answered `accept` for. **Cancel** after Open sends `cancel`. Each answers **that page only** and never sinks the round, where a Legacy `-32042`'s Decline or Cancel answers the whole round and its Decline is offered throughout; "Decline all" is [#569](https://github.com/ian-pascoe/cloudpid/issues/569)'s. The `details.elicitation` line is `mode: "url"` with the host. A page's `accept` has no content to seal: the question's record keeps `{ accept, page }` until the resume is built, then goes with the round, so nothing the owner typed exists to be kept.
  - **Not finished:** a Modern server has no `elicitationId`, so a page is named by its question's key and its address together (`pageIdentityOf`, a short hash of the address, in the same `mcp-question:pages:<callId>` as a Legacy page): a next round with the same key and address reads "Not finished at <host> yet", quietly, uncounted and across a restart, and the same key with another address is a new page.
  - **Not built here:** "<server> is at <host>" and "1 of N" ([#569](https://github.com/ian-pascoe/cloudpid/issues/569)); Modern pages on a prompt send, an App View or an MCP task's `tasks/update` ([#492](https://github.com/ian-pascoe/cloudpid/issues/492), [#498](https://github.com/ian-pascoe/cloudpid/issues/498), [#497](https://github.com/ian-pascoe/cloudpid/issues/497): they are live, so a Modern page there is not declared until they answer it as a live page).
  - **Tests:** the engine declares it (`apps/mcp-worker/src/modern-questions.test.ts`), the core hands the page to `onInput` (`packages/mcp/src/modern-questions.test.ts`), the Session keeps, answers and repeats it (`packages/extensions/src/mcp-url-elicitation.test.ts`), and a fake Modern server's flow runs end to end through the real engine (`apps/server/src/session/mcp-elicitation.workerd.test.ts`: Open, Done and one resume with the accept; "Not finished" and the next resume; Decline).
- **Slicing order:** Legacy declares `{ form: {}, url: {} }` from [#487](https://github.com/ian-pascoe/cloudpid/issues/487), which ships in-call URL mode, `-32042` and its resends (a server that sees `url` may answer `-32042`); Modern declares `url` from [#493](https://github.com/ian-pascoe/cloudpid/issues/493), which ships Modern URL mode (D17).

## MCP tasks

Settled in [MCP tasks as durable long-running requests](https://github.com/ian-pascoe/cloudpid/issues/389) and its amendments; bare D-numbers in this section are its decisions.

- **Scope:** the `io.modelcontextprotocol/tasks` extension, Modern only; cloudpid is only ever the requester (never a task receiver: `ext-tasks`' `/receiver` is unused, and a Legacy `params.task` on sampling or elicitation is ignored). Legacy keeps the synchronous rules: a `taskSupport: "optional"` tool is called synchronously, a `required` one gets a per-tool problem and is not offered, and a task-shaped Legacy answer (or a task answer to `prompts/get` or `resources/read`) is a `ProtocolViolation`. The `2025-11-25` experimental tasks are never declared. cloudpid's own MCP endpoint returns no tasks (D1, [The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) E2).
- **The wire:** the SDK's Modern codec refuses `resultType: "task"`, so a task-capable `tools/call` and `tasks/get`/`update`/`cancel` go on a second `StreamableHTTPClientTransport` the core owns per Modern connection, through `McpHost.request({ op: "tasks/get" | "tasks/update" | "tasks/cancel" })`, each carrying `server`, `tool` and the pinned `conn` and returning `spawn` (stdio) and the MCP sign-in id; `pollIntervalMs` is clamped to 1 s–5 min, and `tasks/cancel` is allowed for a switched-off server. Timeouts, byte limits and retries are in [_Requests and Legacy sessions_](mcp-connections.md#requests-and-legacy-sessions) and [_Failures and cuts_](mcp-connections.md#failures-and-cuts) ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D8; [The MCP host object](https://github.com/ian-pascoe/cloudpid/issues/382), input from MCP tasks).
- **Declaration (`ctx.allowTask`):** on every `tools/call` by an agent or an App View when the server is Modern, advertised the extension and is under the caps; never elsewhere. No per-server or per-tool switch. At a cap the call goes out without it; a `-32021` naming the extension then becomes "<server> needs to run this as an MCP task, which cloudpid couldn't offer here: …" (D2).
- **The handle:** cloudpid's own `mcp-task-<n>`, per Session. The server's `taskId` never reaches a model, the transcript, a client, an export or a span (spans get an 8-hex hash) (D3.4).
- **The inline window:** an agent's call (root, subagent or nested in `codemode`) waits for `min(timeout, 10 min)` from the task's creation, `timeout` being the MCP server definition's (default 60 s), polling in memory; this window is its own wall clock, apart from the pause of a Legacy call's `timeout` while a question waits. A task that ends within it returns the server's `CallToolResult` as a synchronous call would, plus `details.mcp_task`. One still `working` or `input_required` at the window's end, or when the owner steers during it, detaches: the call returns a non-error result, "<server>'s `<tool>` runs as MCP task `mcp-task-3` and is still working after 60 s … `mcp_task_wait` waits for it now, `mcp_task_cancel` stops it, `mcp_tasks` lists them" (plus the Container warning for stdio). A nested `codemode` call gets an `isError` value naming the handle with `details.error: "mcp_task_background"`, and the follower delivers to the script's conversation. The agent has no per-call argument (D3.1, D3.3, D10.1, D14).
- **The follower:** the detach commit creates one `cloudpid.mcp-task` pi-durable task owned by the calling conversation with `background: true`; phases poll → `sleepUntil` → deliver/hold, plus an `abort` that sends `tasks/cancel`. Every sleep commit resets its restart count, so evictions and deploys never end it. It never runs in `McpHost`, which has no alarm (D3.2).
- **Polling cadence:** `pollIntervalMs` honoured (clamped, re-read each response); without one 2 s until 1 min old, 5 s until 10 min, then 30 s. At least 5 s in the background, at most 60 s for stdio, at least 30 s while every question waits on the owner. +0–10% jitter. Error backoff 5 s, 15 s, 30 s, 1 min, 2 min, 5 min, then 10 min, honouring `Retry-After`. The record is written only on a change. Push through `subscriptions/listen` is left for later (D4.1, D4.2).
- **Failures** (D4.3, D16):

  | Event                                                           | Outcome                                                                                                                                                                                                                                                                                                       |
  | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | Unreachable, 5xx/408/429, cut                                   | backoff; after 24 h of failures, `unknown`                                                                                                                                                                                                                                                                    |
  | `sign_in` / `rejected` / `step_up`                              | polling pauses for a Sign-in request "to keep following MCP task …" (not built: the follower treats each as a failure, with the backoff above, and the task is `unknown` after a re-pin or 24 h; the Sign-in request it would raise is [built](mcp-sign-in.md#sign-in-requests), `mcp_sign_in_ask`'s service) |
  | `-32602`                                                        | retried for 2 min, then `unknown` ("no longer knows it")                                                                                                                                                                                                                                                      |
  | Era drop, extension no longer advertised, `-32021` on `tasks/*` | `unknown`                                                                                                                                                                                                                                                                                                     |
  | Server switched off                                             | `tasks/cancel`, then `cancelled` (owner-caused)                                                                                                                                                                                                                                                               |
  | Identity changed (`mcpServerIdentity`)                          | `stopped`, nothing sent                                                                                                                                                                                                                                                                                       |
  | `headers` or `oauth` only changed                               | re-pinned to the new `conn` on `ServerChanged`; a `-32602` or 401 after a re-pin → `unknown`                                                                                                                                                                                                                  |
  | Stdio: any `conn` change, or the process gone                   | `unknown`, with the reason                                                                                                                                                                                                                                                                                    |
  | Engine or host deploy                                           | the poll is retried                                                                                                                                                                                                                                                                                           |

  `mcpServerIdentity` is SHA-256 of `{ source, normalized name, type, url }`, beside `conn` in `@cloudpid/config`. `timeout`, `description`, `enabled`, `exposure`, `toolExposure` and `sampling` are outside `conn` and never touch a task.

- **The record:** in the Session DO, in the follower's input and checkpoint plus the Session document `cloudpid.mcp-tasks`, written in the same commits; Fork and Clone don't copy it, and the host keeps nothing. Fields: handle and `taskId` (≤1 KiB); `conn`, identity, server name, source, transport, `workspace` + `spawn`, MCP sign-in id, protocol version; origin (agent | app), conversation, agent, the call's pi task id, `callId`, `nested`; `createdAt`, `startedAt`, `ttlMs`, `pollIntervalMs`, `status`, `statusMessage` (≤1,000 chars, sanitized, redacted), `lastPolledAt`, `nextPollAt`, failures; `phase`, `delivery`, question keys (answered, `update: sending | sent`), cancel, end. The last 50 ended records are kept. After a restart a `sending` `tasks/update` is resent once, as is `tasks/cancel`; delivery is deduplicated by `requestId: "mcp-task:<handle>"`; `tools/call` is never resent. A sweep at every wake cancels records whose owner is gone (an inline record whose call is terminal; an App record with no live View request) (D5.1, D5.2).
- **A replaced Session:** when a code update replaced the Session mid-call and the new task's record can't be written, it sends a best-effort `tasks/cancel` through the host with the id it holds in memory; if that fails the task is orphaned until the server's TTL. A task whose record was written is followed by the new instance ([Deploys under deferred code updates](https://github.com/ian-pascoe/cloudpid/issues/423) D4.3).
- **TTL and caps:** the server's `ttlMs` is shown ("kept by <server> until …") and not enforced. cloudpid stops following 7 days after creation (`tasks/cancel`, then `stopped`). ≤16 live MCP tasks per Session and ≤8 per (Session, server) (D5.3).
- **Lifecycle** (D5.4, D14.1):

  | Event                                   | Inline                                | Background                                                                                                        |
  | --------------------------------------- | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
  | Stop                                    | `tasks/cancel`, call aborted          | untouched (like subagents)                                                                                        |
  | Stop all                                | cancel, within 2 s                    | the conversation's followers aborted → `tasks/cancel` within 2 s, held result dropped; another branch's untouched |
  | Archive                                 | cancel, within 2 s                    | cancelled on every branch within 2 s, held results dropped                                                        |
  | Delete                                  | best-effort cancel within 2 s         | the same                                                                                                          |
  | Subagent delete (cancel acts like Stop) | its calls aborted                     | its followers cancelled                                                                                           |
  | Spend limit                             | nothing cancelled; polls aren't gated | the Run that delivers is refused at the model seam; the result stays kept                                         |

- **Results:** a `completed` result takes the ordinary MCP result path (text, images, Result Spill, resource links, `isError`; `structuredContent` validated against `outputSchema`, hence `tool` on `tasks/get`); an App View in the original call card gets it whenever it arrives. `failed` → `mcp_task_failed` with the server's `error.message` and code; server-side `cancelled` → `mcp_task_cancelled`; `unknown` → `mcp_task_unknown`; `stopped` → `mcp_task_stopped`; `completed` with `isError` → an ordinary error result. The converted result is stored in Session KV, in a 16 MiB pool per Session, for 7 days after the end, the oldest dropped when full (D6, D15).
- **Delivery:** a waiting `mcp_task_wait` claims the result. Otherwise it is held until the conversation is idle (and stays claimable), then posted as one batched `cloudpid.mcp-task-ended` entry carrying **no server text**, only cloudpid's header:

  ```
  [MCP task ended | task=mcp-task-3 | server=github | tool=mcp__github__deploy | status=completed | after=14m | result=12 KB, 1 image]
  MCP task mcp-task-3 ended. Read its result with mcp_task_wait (task "mcp-task-3"); it is kept until <date>.
  ```

  A root gets it as a `followUp` submit, which starts a Run, and records it in `notify-submissions` so that Run pushes `finished`/`failed`; a subagent gets `startTurn(tx, doc, { agentId, content, whenBusy: "followUp", from: "mcp-task-3" })` (`ReporterInput.from` widens to an agent or an MCP task), delivered only while the agent record's conversation is the one that started the task, and its answer is reported to its parent. Ends the owner caused (Cancel, Stop all, switching off, Archive) leave a model-visible `cloudpid.mcp-task-notice` and start no Run. The delivering Run's spend is ordinary Usage; polls cost no Usage. A `failed`, `cancelled`, `unknown` or `stopped` entry carries cloudpid's reason only. A Run a subagent's delivery starts sends no Notification yet (left for later, with subagent reports) (D8, D11, D12, D14.1, D15).

- **The agent's tools** (in the `mcp` extension, deferred, registered beside `mcp_sign_in_ask` and loaded into a conversation at its first detach; callers `model` and `tools`, `replay: "safe"`, structured outputs; each conversation acts on its own MCP tasks only; D9):
  - `mcp_tasks { status? }` → `{ tasks: [{ task, server, tool, status, status_message, started_at, background, delivery, waiting_for, result_kept_until }] }`;
  - `mcp_task_wait { task, timeout_s? }` (default 300, max 1800): an ended task returns at once, as often as the result is kept, as the converted `CallToolResult`; a working one waits until it ends, `timeout` or `steered`; one open wait per task; a result it returns is claimed and never posted;
  - `mcp_task_cancel { task }` → "cancel sent".
- **Questions in a task** (`input_required`): keyed `(mcp_task:<handle>, key)`, answered through the Elicitation and Sampling paths above with the "MCP task" origin line; the card appears in the task's conversation's waiting area even with no call waiting; one `input` Notification when the task first waits on the owner, another only after 2 min with nothing waiting; `onIdle` skips these records. The answer path sends `tasks/update` itself, marks the key `sent` and deletes the sealed value; a key that reappears after `sent` is never asked again, and after 10 min the status reads "waiting for <server> to take your answer". URL mode: Open sends `accept` at once, with no "Done, try again"; a new key with the same URL shows "Not finished at <host> yet". A sampling refusal sends `tasks/cancel`. The agent sees "waiting for the owner" in `mcp_tasks` and `mcp_task_wait` (D7).
- **Cancellation:** by the owner (the call card or the Session details row), the agent (`mcp_task_cancel`), Stop, Stop all and the lifecycle events. `tasks/cancel` is sent once (one retry on a cut); the card reads "Cancelling…" with a 2-min grace, then "Cancelled", "Finished before the cancel took effect" (result kept) or "Cancel sent; <server> didn't stop it. cloudpid stopped following" (D8).
- **App View calls** are live: the Session polls while the View is mounted, ≤15 min; teardown or the bound sends `tasks/cancel`. Questions follow the App View rules (live, 5 min). The call has an `app` record for the sweep and never appears in `mcp_tasks` (D10.2; see [_Server requests from a View's calls_](mcp-apps.md#server-requests-from-an-app-views-calls)).
- **Stdio:** polls go to the bridge with `use: true, start: false`: uses that keep the Container from its idle stop, but not activity, so the Hold cap ends a background stdio task an hour after the last activity, posted as `unknown` (which starts a Run and so a Notification). An inline wait is part of a Run, held by the Run's heartbeat. The card warns at detach and offers **Keep the Container** (socket `container_keep`), which notes owner activity in the Workspace and resets the cap by an hour; viewing the Session and polls don't extend it (D4.4, D18).
- **Following, not running:** followers don't count toward the Session's `active` status, `onIdle` or Workspace activity, so a conversation that only follows MCP tasks is idle. A pending or running follower arms the 60 s heartbeat; a sleeping one adds its `until` to `wakeAt` (as built the host merges it, not `wake.ts`: see _As built_ below). The Registry gets `mcpTasks: n` at each settle, which drives a muted "Following n MCP tasks" in the Session list and a header chip. Letting a resident Session rest between sleeps is left for later (D17).
- **The owner's UI:** the call card reads "Running as an MCP task · <statusMessage> · 0:42" with Cancel while inline; "In the background" with status, elapsed, "kept by <server> until …", Cancel (and the stdio warning and Keep the Container) after a detach; the result and "<status> · told the agent at …" at the end. Session details has an MCP tasks section, the Subagents Pane's background list shows followers, and Stop all is offered while one is live. The socket gains an `mcp_tasks` list (after `hello` and on change, never carrying `taskId`) and an `mcp_task_cancel` command. Progress travels in that list, never in a running call's `details`. MCP tasks are never listed in a server's MCP status (D11).
- **As built — the wire** ([#455](https://github.com/ian-pascoe/cloudpid/issues/455); `packages/mcp/src/{task-wire,connection,types}.ts`, `apps/mcp-worker/src/calls.ts`, `apps/server/src/mcp/request.ts`): the core's `Outcome` is `Complete | TaskStarted` and `connection.task.{get,update,cancel}` send the three `tasks/*` requests on the second transport (`task-wire.ts`: JSON-RPC over `StreamableHTTPClientTransport`, the Modern `_meta` envelope and the `Mcp-Method`, `Mcp-Name` and `Mcp-Param` headers, the last from `xMcpHeaders` in `tool-headers.ts`). A `tools/call` is offered a task only when `ctx.allowTask` is set **and** the connection is Modern **and** the server advertised `io.modelcontextprotocol/tasks`; the core never sets it, so a caller without `allowTask` never gets a task (tested in the core, the engine and the host). The engine returns `task`, `task_state` (the snapshot, and for a `completed` task its `CallToolResult` as any result's value, checked against the tool's `outputSchema`) and `task_ack`; the host answers `Task` (with the connection's `conn` and `identity`), `TaskState` and `TaskAck`, the last two with the sign-in id and, never yet, `spawn`. The host passes `allowTask` on only for origin `agent` or `app` and an HTTP server; an answer of the wrong kind for its request (a task for a call that was not offered one, or `task_state`, `task_ack` or a result where another was asked) is `CallFailed` `ProtocolViolation`; the core says the same of a server that answers a task to a call that did not declare the extension ("The server started an MCP task that was not asked for"), so the caller never gets one. The `ProtocolViolation` does not cancel the server's task: the core's gate keeps it from happening to a request the host has offered nothing, so there is no task to cancel. A `tasks/*` request whose `conn` is not the server's current one is answered `ServerChanged` (carrying the current `conn` and `identity`, so the caller can tell a re-pin from a new server) with nothing sent; `tasks/cancel` alone is allowed for a switched-off server. A `-32021` naming the extension reads as the message in _Declaration_, built in the core from the target's `name`. Limits and policies: `tasks/get` reads up to 16 MiB (`LARGE_READ`), `tasks/update` and `tasks/cancel` 1 MiB and `mayHaveRun`; `MCP_TASK_TIMEOUT_MS` (30 s, from `@cloudpid/mcp/types`) bounds each `tasks/*` request in the core and at the host, apart from the call's `timeout`; the span carries `mcp.task`, the first 8 hex digits of the SHA-256 of the `taskId`, never the id, set before the request is sent, so a timeout, a cancel or a missing slot still names the task. **Retries:** after a cut (a stream that ends before its answer; a connection that breaks under a read is `Unreachable` and is not sent again, as for any read), `tasks/get` is sent once more as a read, and `tasks/update` and `tasks/cancel` once more though the first may have run (a repeated answer or cancel changes nothing the task did not already); a resend that is cut too fails `Cut`, with `mayHaveRun` true for the two commands and false for `tasks/get`. A `tools/call` is never sent again after a cut. **Re-checked at every attempt:** the era and `capabilities.extensions` are read again after every reconnect, before a `tasks/*` request is sent or a `tools/call` is offered a task, so a server that dropped its era, or no longer advertises the extension, is never sent a task request, and a `tools/call` sent again after such a drop is made on the client's own path, declaring nothing. A `tasks/*` request to a server that no longer qualifies fails `Unsupported` ("…Legacy protocol, which has no MCP tasks" or "…no longer advertises MCP tasks"); with `-32021` on a `tasks/*` request (a `ServerError` with `code` -32021) these are what the follower reads as `unknown` in the Failures table. **Spans:** a host `tasks/get` that carries `ctx.lastStatus` is spanned only when the answer is another status or an error, and counted otherwise; one without it is spanned as before.
- **As built — not yet:** a `tools/call` made with the extension declared and answered `resultType: "input_required"` (a question instead of a task) is answered by the core's rounds as any Modern call is, and resumed on the task wire ([#480](https://github.com/ian-pascoe/cloudpid/issues/480); _Questions_ above); a task created or polled in `input_required` passes through as it is, its snapshot keeping `inputRequests` opaque, and `tasks/update` sends the answers it is given. Stdio servers run no tasks yet: `allowTask` is never passed to one and a `tasks/*` request for one is `HostUnsupported` ([#494](https://github.com/ian-pascoe/cloudpid/issues/494)). The `pollIntervalMs` clamp, the caps (calling without `allowTask` at one) and the handle, follower and tools belong to the Session slices; the host only passes `allowTask` through. `features` gains `"tasks"` (`MCP_HOST_FEATURES`), so a Session can tell a host that knows the ops.
- **As built — the Session's side** ([#488](https://github.com/ian-pascoe/cloudpid/issues/488); `packages/extensions/src/mcp/task-{state,policy,poll,results,host,port,inline,follow,tools}.ts`, `exchange.ts` (`followsTasks`, the task branch of `send`), `tools.ts`; `apps/server/src/session/mcp-tasks.ts`, `mcp-host.ts`, `host.ts`): the root conversation's own direct `tools/call` to an HTTP server is offered a task (`ctx.allowTask`) through one predicate, `followsTasks`: not a subagent's call, not one nested in a `codemode` script, not stdio, not an App View's, and under the caps (16 live per Session, 8 per server; at a cap the call goes out without it). The tools and the follower are registered only when the host lists `tasks` (`MCP_TASKS_FEATURE`, one of `MCP_OPTIONAL_TOOL_FEATURES`) and the Session gives `tasks` options (`McpToolOptions.tasks`; the Session's key-value storage for the result pool, and `submitted`, which adds the follower's Run to `notify-submissions`).
  - **The record** is the Session document `cloudpid.mcp-tasks` (`McpTasksDoc`, keyed by handle `mcp-task-<n>` from a counter that never repeats; the newest 50 ended records kept), one commit per change, and it holds the `taskId`; the follower's input is only the handle. The call's record is keyed by its `callId` and is the source of truth: `mcp.task` and `mcp.detached` mirror it and are written right after the commit that stores it, not in it (pi-durable's `commit` and `memo` are two steps). A rerun that finds `mcp.sent` therefore looks the record up by `callId`, whether or not the memo followed, and follows it from where it was; `tools/call` is never sent again (tested for the crash between the commit and the marker, and through a Session eviction inside the window and after the detach).
  - **Inline:** a result pooled before the end is committed (so a rerun that finds the record ended finds the result), `details.mcp_task`, the window being the entry's `timeout` (default 60 s) up to 10 minutes from creation, the polls in memory at the server's `pollIntervalMs` or the cadence above; Stop sends `tasks/cancel`. A task still going at the window's end detaches: one commit marks the record `background`, creates the follower (`createTask`, `background: true`, owned by the conversation) and returns a non-error result with the handle that loads `mcp_tasks`, `mcp_task_wait` and `mcp_task_cancel` (`control.addTools`).
  - **The follower** (`cloudpid.mcp-task`): phases `poll` (one `tasks/get`, then a durable `sleepUntil`), `deliver` (held until the conversation is idle, claimable meanwhile), `post` and `notice`; its `abort` sends `tasks/cancel`, ends the record `cancelled` (by Stop) and drops the held result. A wait that is open claims the result; a task the server ends (`completed`, `failed`) or cloudpid ends (`unknown`, `stopped`) is posted as a `followUp` submit with the request ID `mcp-task:<handle>` (so a restart posts it once) and the entry kind `cloudpid.mcp-task-ended`; the host runs `settleOnFollowers` so the Run it starts is notified as the owner's own (`finished` or `failed`). An end the owner or the agent caused (a cancel the server took, one it ignored for 2 minutes → `stopped`, a server switched off) leaves a `cloudpid.mcp-task-notice` through `McpNotices.write` and starts no Run (the installed pi-durable 1.4.0's `ConversationHandle.submit` takes input only, so the Harness' `write` submission is the way). **`tasks/cancel` goes out at most once per instance** of the Session for a task, whoever asks (the agent, Stop all, a sweep, an aborted call): a cancel the record marks `sent` (or `failed`) is never sent again, and the instance remembers in memory (per client, `cancelAttempted`) the cancels it began. A `sending` mark that another instance left does not stop Stop all, Archive, Delete or the sweep (`cancelDue`), however fresh: that instance may be gone, and a duplicate cancel does no harm where a task nobody cancels runs on, so after an eviction the new instance can send a cancel the old one had begun (an inline Stop that is followed by an eviction before its `sent` is written likewise gives the sweep a second one). Only the follower's own retry of an agent's cancel waits for the mark to be old, `MCP_TASK_CANCEL_SENDING_MS` = 75 s, which is longer than any send of a live call: the request's 30 s bound (`MCP_TASK_TIMEOUT_MS`), the wire's one resend of a cut (another 30 s) and `MCP_TASK_CONNECT_MARGIN_MS` (15 s for connecting), so that retry never races a send that is alive. The wire resends a cut, and any other answer (an error, a refusal) is not asked again. **Bounded at 2 s:** every cancel a Stop all, an Archive, a Delete, an inline call's Stop and the sweep sends is bounded (`MCP_TASK_STOP_CANCEL_MS`, `sendCancelWithin`), and the aborts of a conversation's followers run side by side, as do the branches' (`stopEverything`) and the sweep's orphans, so a server that never answers `tasks/cancel` holds Stop all, Archive, Delete or the settle that runs the sweep for 2 s in all, not 2 s each. The record still ends (`cancelled` by Stop, with the notice and no Run); the server's own TTL ends the task it did not cancel. An inline call that Stop ended may not live to commit its end: the cancel is sent beside the commit, and the sweep ends a record that is left, without sending another. The follower's `abort` (Stop all, Archive, delete) cancels the task on the server, drops a result held for an idle conversation from the pool, and leaves the model-visible `cloudpid.mcp-task-notice` that says so, which starts no Run; a result already claimed or posted stays.
  - **Results** are converted as any MCP result is (`completedResult`) and pooled in the Session's key-value storage in 256 KiB chunks, 16 MiB in all, for 7 days after the end, the oldest dropped when full; `mcp_task_wait` reads one as often as asked. A result over the pool is not kept and `mcp_task_wait` says so.
  - **Decisions that differ from the sections above:** `Retry-After` is not read (the wire does not carry it): the backoff is the table's. Polls are counted at each written change, not at each poll, so `mcp.task.polls` undercounts a quiet task; `cancelled_by` names a canceller only when there was one (a task the server cancelled itself names the server, a completed one none). The timing constants are all in `task-policy.ts`, and `timing.unknownGraceMs` shortens the `-32602` grace. `McpHostRequestContext.lastStatus` is the one addition to the host's `ctx`. The host's `quietPolls` counts live in a module-level map bounded to 1,000 tasks (emptied when a new task would pass it), so a count is lost with the isolate or when it is emptied: the next span then reports fewer left-out polls than there were. The Sign-in pause is not built (above). `statusMessage` and a `failed` task's error message are redacted of the Session's held Secrets (`McpTasksOptions.redact`, the Session's `Secrets`) and then sanitized (control and bidi characters, 1,000 characters) before they are stored or shown. A `failed` task's `error.message` reaches the model only through `mcp_task_wait`, never the ended entry. A `-32021` for a task-only tool a call could not offer a task (a subagent's, at a cap) is the server's error as for any call, not D2's message ([#494](https://github.com/ian-pascoe/cloudpid/issues/494)).
  - **Following, not running, the Registry and the sweep** (`apps/server/src/session/{host,wake,mcp-host,mcp-tasks}.ts`, `packages/extensions/src/mcp/task-{follow,sweep,port}.ts`): the host tells a follower (a live task of the kind `cloudpid.mcp-task`) from work by its kind. A follower is left out of `active`, of `idle()`, of `follow()` (so of the MCP endpoint's `status`) and of the Workspaces' activity, by one rule, `working(tasks)` in `host.ts`, which the wake, `idle()` and `follow()` all read, so a Session that only follows tasks reads idle everywhere and its `onIdle` runs. `follow()` also says whether a follower of the addressed conversation (the active branch's, by default) lives (`following`; one of a branch that is not active is not counted, since Stop all does not reach it): the endpoint's `session_stop` with `subagents: true` (Stop all) does not stop at "already idle" for such a Session but runs the host's Stop all, which is how the owner cancels a follow-only Session's tasks over the endpoint; a plain stop has no Run to stop and leaves them, and a Session whose only followers are on another branch reads idle and its Stop all is a no-op. One that is pending or running keeps the 60 s heartbeat and one that sleeps asks for the alarm at its `until`; both go to the same `rest` the other wake times go through, as `earliest(wakeAt, heartbeat, until)`: `wake.ts`'s `wakeAt` gains no source of its own, since the host already reads the live tasks and an `until` is theirs (the rejected alternative was a `followers` effect passed to `wakeAt`, which would have the Session read the Harness twice). Each phase of a follower ends by telling the host (`McpTasksOptions.changed`, which the host answers with the settle a Run's start already asks for), so a follower that ended, or slept until another time, moves the alarm and the count at once and not at the next beat. `Stop all` settles too (a notice-only end starts no Run). The Registry gets the number of followers with the status, at each settle where it changed; the count last told is kept in the Session's key-value storage (`mcp-tasks-reported`, -1 after a failed report), so a Session that never followed a task makes no Registry call and a new instance does not tell a count again: Registry migration 33 (`sessions.mcp_tasks INTEGER`, null until a Session reports), the additive RPC `setSessionMcpTasks({ id, count })`, `SessionRegistry.reportMcpTasks` and the optional `mcpTasks` of `SessionRecord` (absent when none; an archived Session's last report is kept). A report that fails is told again by the next settle or beat. The Session list's "Following n MCP tasks" and the header chip are [#494](https://github.com/ian-pascoe/cloudpid/issues/494)'s: the field is there and unread. **The sweep** runs whenever a settle finds nothing working, which includes every wake and the settle at the end of a Run, before the idle report (`SessionHostMcp.sweep` → `McpTools.sweepTasks`, with the runtime clock): an inline record whose call task (`callTask`, the call's pi-durable task id, which the record now keeps; optional: a record without one cannot be told from a live call, so the sweep leaves it alone) is no longer live is cancelled at the server, once and best effort, and ended `cancelled` by Stop with the delivery `none`; a background one has its follower, an ended one needs nothing, and a call that is live is left. App records are [#498](https://github.com/ian-pascoe/cloudpid/issues/498)'s. **The lifecycle table** is tested end to end, with the owner's real paths. **Stop all** is the socket's `abort` with `subagents` (and the endpoint's `session_stop` with `subagents: true`): `host.abort` stops the addressed conversation (the active branch's) with `background: true`, which aborts the follower the conversation owns, and every subagent below it; the follower's `abort` cancels the task at the server within 2 s, leaves the agent the notice and starts no Run. It does not reach another Session branch (a follower of a branch that is not active is untouched, and that Session reads idle at the endpoint). **Archive and Delete** are `stopEverything` (`lifecycle.ts` `stopSession`), which also aborts every other branch's background work (`abort(context, { background: true })`), since a follower of a branch that is not active would otherwise go on; the branches stop side by side (tested with a follower on a branch that is not active, and a subagent on one, which the active branch's stop reaches too). A subagent's followers are [#494](https://github.com/ian-pascoe/cloudpid/issues/494)'s. **A replaced Session** that cannot store a new task's record sends one best-effort `tasks/cancel` with the id it holds in memory and fails the call as before (`startTask`); a task that was recorded is followed by the new instance. **The host's `tasks/get` span:** `ctx.lastStatus` (optional, additive: an older host ignores it) is the status the caller last saw; the host does not sample the poll's span and emits one, without children and with its duration, only when the answer is another status or an error, counting the polls it left out in the next one's `mcp.task.quiet_polls` (the count is in the host's memory, bounded, and lost with it). A caller that sends none has every poll spanned, as before. **Left as it is:** the sweep needs the Session's MCP tools, which are built from its settings: a Session evicted before it ever kept them (its settings, with its Environment, are kept at its first request start) has no tools at a wake, so an orphan left by such a Session waits for its next request; any Session that made an MCP call has kept them. A resident Session does not rest between sleeps (D17); while a follower runs its poll the heartbeat is the alarm, so an evicted Session's next poll can be up to a beat late.
  - **Elsewhere:** subagents, `codemode` and stdio tasks, the web rendering of the two new entry kinds, the Session list label and header chip, the call card, the socket list and Cancel ([#494](https://github.com/ian-pascoe/cloudpid/issues/494)); questions in a task (`input_required` is polled at 30 s or more and shown as `waiting_for: "owner"`; [#497](https://github.com/ian-pascoe/cloudpid/issues/497)); App View calls and their records ([#498](https://github.com/ian-pascoe/cloudpid/issues/498)).

## Telemetry and testing

- **Spans:** one per sample (server, origin, Role, model, tokens, cost, outcome, who decided; never its content); one per Elicitation request (server, origin, mode, action, who decided, field count, wait time; never the message, schema, URL path or a value); one Session-side `mcp.task` per MCP task (server, tool, origin, inline or background, polls, failures, question rounds, who cancelled, outcome, duration; never the `taskId`, `statusMessage` or results). The host's `tasks/get` spans are emitted only on a status change or an error, and counted otherwise (the follower and the inline window tell the host the status they last saw, `ctx.lastStatus`); the Session-side `mcp.task` span is built, one per task that ended.
- **Tests:**
  - golden tests of the `toolChoice` table and the hint/priority mapping; the message pairing checks; the form normalizer, widgets' value encoding and the credential matcher's pass/decline lists; the URL decline rules;
  - workerd (`apps/server`, a fake Modern server), [Elicitation](https://github.com/ian-pascoe/cloudpid/issues/388) D5.4's test: a `codemode` script's nested call gets one elicitation and one sampling request; across `evictDurableObject` both records remain, the fake gets one `tools/call`, and answering both sends one resume. Variants: `timeout_ms` passing during the eviction (records withdrawn, no resume) and a Legacy fake (record withdrawn, cut error);
  - a replaced Session over the `refusingStorage(storage)` gate: a live question gets its kind's no-answer, and an unrecordable MCP task gets `tasks/cancel`;
  - MCP tasks: a fake Modern task server (`@modelcontextprotocol/ext-tasks` 0.2.x, a devDependency only) and workerd tests for an eviction inside the window, detaching at the window, eviction inline and in the background, the `-32602` grace, an ignored cancel, a stdio stop, and Stop, Stop all and Archive; build checks that a tool's commit can create a conversation-owned `background` task, `fork(at)` doesn't copy `cloudpid.mcp-tasks`, `subagent_delete` aborts the child's background work, `ReporterInput.from` widens without migrating reporters in flight, and a nested `isError` value passes the structured-output check.
