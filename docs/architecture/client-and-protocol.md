# Client and protocol

- **Wire:** the contract lives in `packages/protocol`, shared by server and web ([ADR-0009](../adr/0009-session-socket-messages-over-alchemy-rpc.md)).
  - **Session socket:** `GET /sessions/:id/socket` on the main Worker, forwarded to the Session DO, which accepts it as a hibernatable WebSocket. A Session the Registry does not know answers 404. Messages are JSON in the Cloudflare pi example's shapes, as Effect `Schema`. The Session greets a client with `hello` and its active branch's conversation (as `root`, its name from before Session branches; see _Session tree_), with `copying` while it is still being filled as a Fork or Clone. Commands carry an optional `id`, which a `result` or an `error` answers, also when the command cannot be read. Keys a command does not define are an error.
  - Commands: `submit` (with `whenBusy` and a `requestId` that deduplicates), `abort`, and `watch`/`unwatch`. `configure` picks the root agent's model and thinking level (the active branch's) (`null` follows the default in the settings again); the Session says which fields it picked (`picked`, after `hello` and to every client after a `configure`); it is a socket command, not Registry RPC, because the pick belongs to one Session, is applied by that Session's Harness, and reaches every watching client as an `agent_changed` event. `submit` and `abort` take an optional `conversationId` of a live subagent, and `abort` an optional `subagents` flag that also stops everything below it (see [_Subagents_](agent-capabilities.md#subagents): Stop). `watch_task_graph`/`unwatch_task_graph` start and stop `task_graph` messages: a summary of the Session's live work (`agents`: ID, parent, conversation, role, model, `working` or `idle`; `background`: live background tasks other than the subagents' own bookkeeping), made from pi-durable's `watchTaskGraph()` and the Subagents document, at most one every 250 ms, and only when it changed. The watch is kept in the socket's attachment and restarts on wake, like a conversation's. Watching a conversation also streams its Todo List: after the snapshot, a `todos` message (`conversationId`, `tasks`) with the whole list, and another each time it changes; each replaces the last of that conversation, and `unwatch` stops them. `secret_answer` answers a Secret request with the values entered in a masked form (or `null` to cancel); the Session sends the waiting requests (`secret_requests`) after `hello` and to every client when they change, and the values never reach a client again. The Session likewise sends the Browser Handoffs waiting for the owner (`browser_handoff_requests`, with no Live View link) after `hello` on every connect, an empty list too, and to every client when they change; `live_view { requestId }` mints links to one of them for the asking client alone (see [_Browser_](browser.md)), and there is no answer command, as the owner finishes in the Live View. `owner_tab_view { open }` mints links to the Owner tab the Browser Pane shows the same way, for the asking client alone, opening one when `open` asks and the owner has none (see [_Browser Pane_](browser.md)); `owner_tab_drivers { drivers: [{ ownerTabId, conversationId }] }` says which `browser` calls work in Owner tabs, after `hello` on every connect (an empty list too) and to every client when it changes. `owner_tab_list { watching? }`, `owner_tab_open`, `owner_tab_show { ownerTabId }` and `owner_tab_close { ownerTabId }` list and change the Owner tabs (the tab strip; `watching` marks the listing as the heartbeat of a Pane in view, see [_Browser Pane_](browser.md) → _Keep-alive while watched_); each is answered with the `OwnerTabListing`, and the three that change them also send it to every client as `owner_tabs`. `submit` takes `pages: [{ ownerTabId, screen? }]`, the Owner tabs the composer attaches (see _Attached pages_, below), whose menu reads the same listing. `catalog` and `command` serve the composer's Slash commands, and `files` its `@` mentions (below). `history { before, conversationId? }` answers a `HistoryPage` of the active branch's or a live subagent's History before entry `before`, read newest first and sent oldest first: at most 200 entries read (`MAX_HISTORY_ENTRIES`) and the ones a transcript shows kept (no system prompts or bookkeeping) until they pass about 4 MiB of JSON (`MAX_HISTORY_BYTES`, well under workerd's 32 MiB message cap), the entry that passes it included, with the `before` to ask for next (`null` when nothing is left; `apps/server/src/session/history.ts`). `tree`, `navigate` and `switch_branch` serve the Session tree, and `active_branch` follows it (see _Session tree_, below). `approval_answer { request, approve, reason? }` answers an Approval request; the Session sends the waiting ones (`approval_requests`, without the value the call checks) after `hello` on every connect, an empty list too, and to every client when they change (see [_Approval_](agent-changes.md#approval)). `viewed_set { repo, pull, path, blob }` ticks or unticks a pull request file's Viewed box, which the Session sends as `viewed` the same way (see [_Comparisons_](diffs-and-review.md)). `annotation_save { annotation }` and `annotation_delete { annotationId }` save and delete the owner's draft Annotations, which the Session sends as `annotations` after `hello` on every connect (an empty list too) and to every client when they change; `submit` with `annotations` (the drafts' IDs) sends them as a Review, its input the summary (see [_Annotations and Reviews_](diffs-and-review.md)). Still to come: `reset`.
  - `whenBusy: "steer"` joins the running Run at its next boundary, after the tool calls in progress. A steer that finds the Run giving its final answer starts the next Run, as `followUp` does.
  - `watch(conversationId)` streams `events`: a batch holding a `snapshot`, then pi `AgentEvent` batches unchanged. The socket's attachment names its watches. A Session woken from hibernation restarts them, each with a fresh snapshot, on the same socket. A watch that ends, or cannot restart, is dropped with an `error` naming its `conversationId`. A client whose socket closed (an eviction, a deploy) reconnects and watches again.
  - `watch_usage`/`unwatch_usage` start and stop `usage` messages: what the Session has spent (input, output, cache read and cache write tokens, total tokens, and `cost` in US dollars) and its spend `limit` (`null` for none), each replacing the last, at most one every 500 ms and only when it changed. One read of the ledgers is in flight per watch, and changes that come meanwhile ask for one more; a limit changed in the settings is sent when the Session next reads them (a connect, a prompt, a `configure`). The totals are pi-durable's session total (`harness.usage()`, every conversation's `pi.usage` summed, subagents included) plus the title calls'. Each message also carries `container`, what the Containers of the Session's Workspace and of its Subagent Workspaces have cost (see [_Operations_](operations.md) → Telemetry → Container cost), read from each Workspace DO (`containerUsage`, which starts nothing) with the ledgers and summed (`sumContainerUsage`); it is left out when no Container ran, the Session has no Workspace, or the read failed. Each message also carries `context`, how full the active branch's Context Window is (`apps/server/src/session/context-usage.ts`): `tokens`, the size of its next request as pi-durable reckons it before compacting (pi-ai's `estimateContextTokens` over the branch's model context: the newest answer's usage plus estimates of the messages after it), out of its model's `contextWindow` (from the model catalog, with the proxy's caps), `compactAt`, where automatic compaction starts (the background threshold, or the blocking one without background compaction; null when it is off), and `parts`, `tokens` split in proportion to estimates of the system prompt and tool definitions, the owner's messages, the answers and the tool results. It is read again only when the branch, its newest entry, its model's window or the compaction settings changed, and left out when the model's window is not known or the read failed. A move to another branch and a `configure` send a message at once. Like the task graph, the watch is read when the task graph changes (a response's usage is committed with it), kept in the socket's attachment, and restarted on wake. The composer's toolbar shows a ring filled to the share of the context window used (in Ink once the context is within 85% of where it compacts); hovering, focusing or tapping it shows the breakdown: a bar of the window with each part and the compaction point marked, each part's tokens and the room left, then the spend (the models' cost plus the Containers', ticking each second while a Container runs, from the rates the message carries up to the idle stop it names), the spend limit, input, output, cache read and cache write tokens, and the Container's run time, CPU time, and memory, CPU, disk and egress cost. Near the spend limit the ring takes the warning border, and at it the error colour and "Limit reached" (the limit holds the models' cost only).
  - The runtime answers the client's `ping` heartbeat with `pong` without waking the Session.
  - **Attachments:** `PUT /sessions/:id/attachments/:name` on the main Worker (behind Access, beside the socket) takes a file's raw bytes as the body and writes them into the Session's Workspace at `/workspace/.cloudpid/uploads/<session-id>/<name>`, answering 201 with `{ name, path }` (`StoredAttachment`); `DELETE` of the same path removes one that was not sent (204, also when it is gone). A Session the Registry does not know answers 404, and neither touches a Workspace. The name is one escaped path segment, sanitised (`sanitizeAttachmentName` in `@cloudpid/protocol`): letters, digits, `.`, `_` and `-` kept, every other run of characters one dash, never starting or ending with a dot or dash (so never `.`, `..`, hidden or an option), at most 100 code points and 200 UTF-8 bytes (Linux allows 255) with its extension kept, `attachment` when nothing is left; one that is taken gets `-2`, `-3`, … before its extension. Every path is built from the Session's ID and that name, so nothing a client sends reaches outside the Session's directory. A body over 25 MB (`MAX_ATTACHMENT_BYTES`, by its length header or as it is read) answers 413 and writes nothing, and one cut off (shorter or longer than its length header, or stopped by the client) answers 400: the Workspace DO holds the whole file in memory to write it (its storage keeps it in 512 KiB chunks), in 128 MB that runs the rest of the Workspace. A body with a length header is read into one buffer of that size, and the Workspace writes it without copying it again. The write goes through the file operations a Session's environment uses, which make the directory with `ensureDirectory`. Two uploads of one name at the same moment could both find it free, the later write winning; the web app names its own uploads apart, so only two pages uploading one name at once meet that. `DELETE` removes any file of that name in the Session's directory, sent or not: the route cannot tell them apart, and the owner is the only one who reaches it. Uploaded files stay in the Workspace after sending, as a Deleted Session's files do.
  - **Registry:** `RegistryRpcs`, an Effect `RpcGroup` over HTTP (`POST /rpc`, JSON), lists, creates, renames, archives, unarchives and deletes Sessions (each in a new Workspace of an Environment or in one that exists), lists, creates, renames and deletes Environments, adds and removes an Environment's Repos (`addRepo`, `removeRepo`), reads and saves an Environment's Container settings (`getEnvironmentSettings`, `updateEnvironmentSettings`), reads and saves the Container settings at Global (`getGlobalContainerSettings`, `updateGlobalContainerSettings`, the latter and `updateEnvironmentSettings` taking `{ set?, reset? }`: see [_Container settings_](container.md)), lists, keeps, flags and deletes Secrets kept for an Environment or Global, never answering a value (`listEnvironmentSecrets`, `setEnvironmentSecret`, `setEnvironmentSecretBuild`, `deleteEnvironmentSecret`: see [_Secrets_](agent-capabilities.md#secrets)), lists the Environments' Builds and makes one again (`listBuilds`, `rebuildEnvironment`: see [_Builds_](container.md)), lists an Environment's Agent changes and reverts or dismisses one (`listAgentChanges`, `revertAgentChange`, `dismissAgentChange`: see [_Agent changes_](agent-changes.md)), lists and removes Workspaces (`listWorkspaces`, `removeWorkspace`; a Subagent Workspace's removal deletes its subagent), reads what a Workspace has not pushed (`workspaceWork`; a clone missing or not on the Workspace's branch is listed, with why, as `unsettled`), restarts a Workspace's Container (`restartContainer`, answered by its Workspace DO; a Workspace the Registry does not list is refused), makes a Fork or Clone of a Session (`forkSession`: see _Session tree_), reads and replaces the settings overrides, and lists the Settings' Agent changes and reverts or dismisses one (`listSettingsChanges`, `revertSettingsChange`, `dismissSettingsChange`: see [_Settings changes_](agent-changes.md#settings-changes)). After it answers, `listSessions` also wipes some of what was left from before Environments (see _Registry migrations_) and keeps the Environments' spare Workspaces (see [_Spare Workspace_](workspace.md)) and their Builds.
- **Reducer:** `view.ts` and `transcript.ts` from Cloudflare's `agents` example `examples/next/harnesses/pi` (MIT, attributed). They are extended for `nestedTools`, compactions, subagents, and earlier Context Windows: a head marker (a Handoff's reset, a compaction) moves what is before its head from `messages` to `earlier` rather than dropping it, a snapshot keeps a view's `earlier` when the view saw the snapshot's marker (a woken Session's fresh snapshot loses nothing) and otherwise starts it empty with `before` at the marker's head, and `withEarlier` puts a `history` page in front. The thread shows `earlier` then `messages`, so a turn a page boundary splits is whole again. This reducer is the only code that interprets `AgentEvent`s.
- **UI:**
  - Vite, React 19 and Tailwind v4 in `apps/web`, built by the Server's deploy (an alchemy `Command.Build` in `apps/server/src/worker.ts`) and served as static assets by the main Worker. Its state lives in Effect Atom over one runtime (`apps/web/src/runtime.ts`; [ADR-0011](../adr/0011-web-app-state-in-effect-atom.md)). The manifest in `apps/web/public/` is linked with `crossorigin="use-credentials"`, since Access guards it.
  - **Serving and deploys.** The Worker's assets use `notFoundHandling: "single-page-application"`, so the asset layer answers a file that exists without waking the Worker, gives `index.html` to a _navigation_ to an unknown path (`/sessions/:id`), and passes every other request, a missing `/assets/…` file included, to the Worker. The Worker answers `/assets/*` with a 404 that is not cached (`missingAsset`, `apps/server/src/missing-asset.ts`); it used to fall through to the hello answer (200, `text/plain`), which a browser reports as a module script with the wrong MIME type. Only the current build's files exist (a deploy replaces the set), and the chunks are hashed, so a tab opened before a deploy loses its lazy chunks (the Call diff's `patch-view`, the Diff pane's `changes-view`) and their stylesheets. The page then reloads once for the new build (`apps/web/src/stale-build.ts`): Vite fires `vite:preloadError` for the failed import or stylesheet, the page takes it over and reloads, unless it already reloaded in the last 60 s (a stamp in the tab's `sessionStorage`, so it cannot loop) or something unsent is held: any `<textarea>` on the page with text in it (a Session's composer, the draft's, a settings editor), or the new-Session draft kept off screen (`draftHeldAtom`: its text, files or attached pages). Then, and for a failure Vite does not report, the lazy part (`LazyView`, over `lazyChunk`) shows "The app was updated. Reload to open this." in place of the part. A reload keeps what is in `localStorage` (the Pane area's width `cloudpid:pane-width`, each Session's layout `cloudpid:session-layouts`, the Diff pane's layout and wrap, the draft's last Environment, collapsed groups, the sidebar's width and `cloudpid:sidebar-collapsed`) and loses what is in memory: composer and draft text and Attachments not yet sent (the reload waits for those, as above), a Session composer's text that is not on screen, and the draft's Workspace, branch and base fields.
  - assistant-ui `ExternalStoreRuntime`: steers map to `steerItems`, follow-ups to `items`, and `onCancel` to abort.
  - `streamdown` for Markdown, with Tailwind v4 and shadcn.
  - **Composer:** one box with the input and a toolbar: the root conversation's model and thinking level (one `model:level` chip whose menu lists the models, each with a submenu of the thinking levels; picking a level sends `configure` with both) on the left, the context ring (see `watch_usage` above), Attach, then Send, or Steer, Queue and Stop while a Run is in progress, on the right; Attachment tiles sit above the input, and the chips of attached pages above them (see _Attached pages_). A `/` at the start of the message opens a menu of Slash commands; those the web app runs itself are `/model [model]` and `/thinking [level]` (`configure`, or open the picker without an argument, on the models or on the levels of the model in effect), `/name <title>` (`renameSession`), `/new` (`createSession` in a new Workspace of the shown Session's Environment), `/archive`, `/settings`, `/tree`, `/fork` and `/clone` (see _Session tree_), `/stop`, `/stop-all` and `/copy` (the last answer to the clipboard); a subagent's composer has only the last three. The Session's own commands, Prompt templates and Skills come from `catalog`, asked for when the menu first opens and again once the answer is 30 s old: the `/` menu lists Commands (the web app's and the Session's), then Prompt templates, then Skills as `/skill:name`, and a `$` at the start of a word opens a menu of the Skills alone (none when nothing matches, so `$HOME` is left alone). An `@` at the start of a word (not in an email address or inside backticks) opens a menu of the conversation's files and folders (`files`, below). A subagent's composer offers the Session's commands, addressed to its conversation, and its directory's templates, Skills and files. A `/name` the web app does not know is sent as written, for the Session to expand. An owner's message the Session expanded shows as typed, with a closed "Skill · name" disclosure for the Skill a `/skill:` embedded (a `$name` link has none).
  - **Slash commands** (`docs/adr/0001-expand-skills-and-prompt-templates-at-submit.md`). `catalog` (optional `conversationId`) answers `{ commands, templates, skills }` for the conversation's directory (its `cwd`, else its Workspace's directory): the Session's commands (name, description, argument hint, whether the argument is `none`, `optional` or `required`, and its `choices`; `/rollover` only where the conversation's agent has `context_rollover`), and the Prompt templates and Skills found from that directory up to `/workspace`, nearest first, each with its name, description and argument hint; Skills include the `disable-model-invocation` ones, which exist for the owner to name. A Workspace that cannot be asked leaves the templates or Skills out (logged), not the commands. The commands are also `SESSION_COMMANDS` in `@cloudpid/protocol` (`sessionCommandsFor`), so the web app runs one typed before the catalog arrives, or after it could not be had, instead of sending it to the model; it offers `/rollover` in the root's composer only. `command { name, args, conversationId? }` runs one on the root conversation or a live subagent's and answers `{ notice?, file? }`; a command that cannot run fails with why, shown under the composer:
    - `/compact [focus]`: pi-durable's manual compaction (`Conversation.compact`), the focus at most 2,000 characters, as a Rollover's. While a Run is in progress it waits for the conversation to be idle, the request kept in the Session's storage so an eviction does not lose it, and runs then.
    - `/rollover [focus]`: the Rollover request, steered (see [_Context management_](agent-capabilities.md#context-management)). Not offered, and refused, in a conversation without `context_rollover`: a subagent is never granted it, so a subagent's composer has no `/rollover`. A client whose socket closes before a command's answer is told that it may have run.
    - `/todo clear`: clears the conversation's Todo List, moving its revision, so watching clients are sent the empty list.
    - `/export`: the conversation's whole History, every Context Window, as Markdown (`file`: name, MIME type, content), which the web app downloads. Each page of entries is rendered as it is read and counted in UTF-8 bytes of the JSON string it travels as, and an export over 8 MiB is refused as soon as it passes that: the file is one `result` message, which workerd caps at 32 MiB, and while it is built the Session holds the Markdown, the message and a page of entries at once in an isolate of 128 MB that runs the Session's work too, so a quarter of the message limit leaves room for them.
  - **`@` mentions.** `files { query, conversationId? }` answers `{ paths }`: at most 50 paths relative to the conversation's directory (as for `catalog`) that match `query` (what follows the `@`, at most 1,024 characters), best first, a folder's ending in `/`. They come from one `ExecutionEnv.listFiles` walk of the directory (above): what git ignores is left out (the `.gitignore` files of the directory, below and above it in its work tree, and `.git/info/exclude`; below a directory in no work tree, each repository's own), and so are `.git` and `node_modules`, at most 50,000 entries, the walk cut off after 8 s (a cut-off listing is logged); a folder above a listed path that the listing lacks is added. Also left out: a path holding whitespace, which a mention cannot hold (it ends at the first space, and the agent reads no quoting), every Session's Attachments (`/workspace/.cloudpid/uploads`) and the mount of the Skill set the Workspace holds (`/workspace/.agents/skills`). Paths are ranked by `rank` in `@cloudpid/protocol`, the function the composer's menu ranks with (exact, prefix, word start, substring, letters in order; a match in the last segment, a folder's name, before one elsewhere), shallower paths first among equals, so an empty query lists the top level first; each listing is lower-cased and split once, and a request keeps only its best 50 as it ranks. The Session holds each directory's listing for 30 s (`apps/server/src/session/file-search.ts`), at most 4 directories and 100,000 paths, the least recently asked settled one dropped first (one being made is never dropped); requests made while a directory is listed share that listing, at most 2 listings run at once, and one that fails or has not ended within 10 s is not held, so the next request lists again. A conversation without an environment has no files; a Workspace that cannot list, or does not answer in time, fails the request. The web app sends the query 120 ms after the owner stops typing and narrows the last answer with the same ranking meanwhile; an answer serves while the menu stays open and for 30 s, so opening the menu again asks afresh. With no rows, the menu shows "Searching files…" until the first answer, "No matching files or folders." when there is none, and "Could not search the files." when the request failed (cleared when the menu closes), in a live region announced as it changes. A row shows the name (a folder's with its `/`) and, muted, the folder it is in, cut from its start on a narrow screen. A pick inserts `@path` and a space at the caret, in place of what was typed after the `@`; a folder inserts `@dir/` with no space, so the menu stays open and typing on narrows into it. The message keeps the mention as plain text: nothing is inlined, and the agent opens the path with its own tools.
  - **Prompt templates** are `.agents/prompts/*.md` (not below), found by the Workspace DO's `prompts(cwd)` next to the files, as skills are (`ComputerExecutionEnv.discoverPrompts`; `@cloudpid/extensions/prompt-templates`), the nearest winning a name, at most 100. Parsing follows local pi: the name is the file's, the description its `description` frontmatter or its body's first line cut to 60 characters, and `argument-hint` its hint. The listing carries no bodies (a template's file is read when a message uses it), and leaves out a file over 256 KiB (by its size, before reading it) and one whose name holds whitespace, which a Slash command could not name.
  - **Expansion at submit.** Before the Session admits the owner's message it asks the conversation's Workspace for its Skills and templates when the text may name one (it starts with `/` or holds a `$` that may start a name): `/skill:name [args]` at the start becomes local pi's `<skill name location>` block (`SKILL.md` without its frontmatter, "References are relative to" its directory), then the arguments; `$name` naming a known Skill (exactly, case-sensitively), in the prose of the message or of a `/skill:`'s arguments, becomes in place a Markdown link to its `SKILL.md`, `[$name](/path/to/SKILL.md)` (the path URI-encoded, and `?`, `#`, `(` and `)` too; only an absolute, well-formed path is linked), every occurrence, in order, as the owner's pi extension pi-skills-selector makes it: no file is read for it, and the model reads the Skill when it needs it; `/name args` naming a template becomes the template with local pi's substitution (`$1`…, `$@`, `$ARGUMENTS`, `${N:-default}`, `${@:N}`, `${@:N:L}`, bash-style quoting, no re-substitution). A name nothing knows is left as typed, as are `$HOME` and other expressions, an escaped `\$name`, a `$name` glued to a word (a letter, digit, `_`, `$`, `/`, `+` or `-` before or after it, or `.` and a word after it), and one in code or in an existing link (inline, reference or automatic) or link definition. A `/skill:` or template whose file cannot be read or is over 256 KiB is left as typed too (a `/skill:` so left keeps its references linked), and so is the whole message when the expansion and the typed text together would be over 1 MiB (an entry is one SQLite row, at most 2 MB); what was left so is logged. A Workspace that cannot be asked, or does not answer within 5 s, leaves the message as typed. Messages are admitted in the order they arrive (a lock separate from the alarm's), so one sent while the message before it waits on its Workspace is not admitted first. The prose is found with marked's lexer, as pi-skills-selector finds it (`apps/server/src/session/skill-references.ts`, ported from its `skill-references.ts` with its tests). An expanded message is placed as a `cloudpid.user` entry whose model message is the expansion and whose data is `{ display, skills: [{ name, location }] }`, `skills` naming only the Skill a `/skill:` embedded: the transcript projection and the title show `display`, and the queue lanes show the text the client sent.
  - **Attachments** (GLOSSARY.md → Messages). The composer's Attach button (a file picker, any files), a paste of files, or a drop anywhere on the thread (a subagent's thread for its own composer) attach files, which upload over the route above one at a time, in the order they came (an `XMLHttpRequest`, for its upload progress), each named apart from the composer's others (a file over 25 MB fails at once, without an upload); removing one before sending stops its upload or deletes the stored file, also when the upload ended as it was removed. Files uploaded but not sent stay in the Workspace when the composer goes (the subagent's card closes, the page changes or reloads), as sent ones do; a removed one is the only one deleted. A subagent's composer uploads to the same Session's `.cloudpid/uploads/<session-id>/`. A message with Attachments is sent by the composer itself (assistant-ui sends text only), as a steer while a Run is in progress (Enter, Ctrl/Cmd+Shift+Enter) or a follow-up (Alt+Enter, Queue): its input is the typed text as one text part, then a text part of each Attachment's `@/workspace/.cloudpid/uploads/<session-id>/<name>` on a line of its own (a part of its own, so a Prompt template or Skill the Session expands from the first part takes no path for an argument and drops none), then each picture inline as an image part. The text and Attachments leave the composer when it is sent and come back, with the Session's reason under the box, when the Session refuses it. A picture is decoded in the browser once, drawn at a 1568 px long edge (kept until it is sent or removed), and encoded from that drawing as JPEG, or WebP (PNG where the browser cannot encode WebP) when it has transparency; all of a message's pictures take one quality, the best of 0.85, 0.72, 0.6, 0.48 and 0.36 at which they share 1.5 M base64 characters (`INLINE_IMAGE_BUDGET`), and when even the lowest is over, the largest goes as a file only and the rest are fitted again (`apps/web/src/chat/image-budget.ts`, with the encoder injected). A GIF goes unchanged, still animated, at the best quality when it fits the budget alone; at the others it is a still like any picture, and its tile says so. One that does not fit, or that the browser cannot decode (some HEIC, a corrupt file) or encode, is attached as a file only, and its tile says why (a picture over 25 MB fails instead, as any file does). The fitting runs as Attachments are added or removed, so the tiles say it before sending; Send is disabled, saying why under the box, until every upload is done and every picture fitted, and a failed upload must be removed first. The lanes show the typed text and the Attachments' names. The transcript shows a message's images (an expanded message keeps them: `display` replaces only its first text part).
  - **Attached pages** (GLOSSARY.md → Messages: Attached page; `apps/web/src/chat/page-chips.tsx`, `attached-pages.ts`, `attachments-state.ts`; `packages/protocol/src/attached-pages.ts`). While the Session has Owner tabs, the composer (the root agent's and a subagent's) has a page button in its toolbar beside Attach (nothing while it has none: the tab strip's `owner_tab_list` is asked once the socket is live, on each reconnect and each time the menu opens, and the menu reads the Owner tabs the Session last said, `ownerTabsAtom`; a failed ask offers nothing). Its menu lists the Owner tabs by title with the one the Browser Pane shows first and focused (so Enter attaches the shown page), a check on the ones attached; picking one attaches it, picking an attached one takes it off. Several pages may go in one message (at most `MAX_ATTACHED_PAGES`, 10). Each is a chip above the Attachments' tiles (title, a thumbnail of its screen when it has one), removed with its button before sending. Pages are the composer's own state next to the Attachments' (`AttachmentsState.pages`), taken off the composer while the message is submitted and back with the text when the Session refuses it. A page alone makes a message.
    - **What goes with a page.** The composer sends only the Owner tab (`PageRef`: `ownerTabId`, and `screen` when the message carries its picture); the Session reads the rest from the browser as the message is admitted, under the lock that admits messages in arrival order and only for a message it has not admitted before (a resent `requestId` finds the first submission without reading again, so a page closed since cannot fail it; `Prompt.attachPages`, run in `SessionHost`'s `admit`; `BrowserPane.attach` → the host's `readOwnerTabPages(ids)`, `OwnerTabs.read`, a connection the host opens for the call): the tab's URL and title now (`Target.getTargets`) and, for the Owner tab the Browser Pane shows only, the text the owner has selected in it (`Target.attachToTarget` and `Runtime.evaluate` of the selection of the field being typed in, else the document's; the other pages go with URL and title alone; a selection that cannot be read leaves the page with its URL and title). The script reads nothing from a password field or any other whose value is masked (`type=password`, an `autocomplete` of a one-time code, card or password, text shown as dots by `-webkit-text-security`). The page's text is cut in one place, `clampPage`: selections to `MAX_PAGE_SELECTION` (4,000 code points), titles to 300, URLs to 2,048, Owner tab IDs to 100; the page only guards what crosses to the Session (`MAX_PAGE_SELECTION_READ`, 16,000 UTF-16 units, never splitting a surrogate pair), so that the redaction below sees more than is kept. **Held Secrets are redacted** from the URL, title and selection (`Secrets.redact`) before they are stored, escaped or sent to any client, so neither the entry's `pages` nor the block holds a value the Session knows (escaping first would turn `&<>"` into entities redaction cannot see through); they are cleaned first (`cleanPage`: no control or bidirectional characters, the URL and title on one line), so a Secret the page split with a character the cleaning drops or folds is whole when it is redacted. Reading is no use of the browser (it starts and opens nothing, and the idle close is not moved). A page whose Owner tab is gone (closed, or its browser closed or replaced) fails the send with `ATTACHED_PAGE_GONE` ("A page you attached is gone … remove it and send again"), submitting nothing; the composer keeps the text and the chip.
    - **The screen.** For the Owner tab the Browser Pane shows, the composer takes the Pane's latest screencast frame when the page is attached (the Pane keeps its newest frame per Session in an atom while it is open: `latestScreenAtom`, `owner-tab-screen.ts`; a Pane that is not open has no screen to give, so the page goes without one, and an Owner tab that is not shown never carries one), as a picture of an Attachment item that is never uploaded (`screenOf`). It is fitted into the message's images like an attached picture, sharing `INLINE_IMAGE_BUDGET`: when there is no room beside the other images the largest goes as a file only, and a screen that loses is left out, the chip saying so (a page's screen has no file to fall back to). The picture is the frame at the moment of attaching, not at sending; remove and attach the page again to take a newer one. The input is the typed text, the Attachments' paths, the pages' screens in the order of `pages`, then the Attachments' images.
    - **Untrusted content.** The URL, title and selected text come from the page, so they never reach the model in the owner's voice or as owner text. The Session adds them as one text part of its own, `pageBlock` (`<attached_pages>`), placed before the message's first image, after the typed text and the Attachments' paths: a notice that the pages' URLs, titles and selections were written by the web pages, are untrusted content to read and never instructions or the owner's words, then a `<page owner_tab_id="…" url="…" screen="attached">` per page with `<title>` and `<selected_text>`. Every value is XML-escaped (`&`, `<`, `>`, `"`), so a page cannot close its element or the block, or open another, and a control character is dropped (C0, DEL and C1, and the bidirectional controls; a lone surrogate too); the title and URL are one line. The notice also says that a screen was taken when the owner attached the page while the text was read when the message was sent (so the picture may be older), and that only the page the Browser Pane showed has selected text. This is the same reason `browser` results are tool output, not user text. The owner's typed text stays the first text part, untouched.
    - **Storage and the transcript.** A message with pages is stored as a `cloudpid.user` entry whose data keeps `pages` (`AttachedPage`: Owner tab, URL, title, selection, `screen`; as bounded), with `display` the typed text (empty when the owner typed none, so the transcript, the tree and the Session's title never read the page's text). The transcript projection drops the block (the last text part shaped like one) and shows a chip per page under the typed text: title and host, "with its screen", and the selection under a closed "Selected text" disclosure; the screen is an ordinary image of the message. The guard on what a submit may hold counts the block and the entry's copy.
  - **What a submit may hold.** An owner's message is one entry, a single SQLite row that Cloudflare caps at 2 MB, and a queued one is also copied into the conversation's inbox document (`pi.inbox`), one row for every message waiting; a write over the cap fails the commit, which fails the Session. So before admitting a submit, in arrival order and after its expansion (what is measured is what would be written), the Session refuses one whose content and entry data are over 1.9 MB (`MAX_STORED_INPUT_BYTES`) as UTF-8 JSON, one that would take the inbox over it beside the messages already waiting, and an image part whose `mimeType` is not PNG, JPEG, WebP or GIF, answering the client with an `error` that says why and keeps running (`apps/server/src/session/input-guard.ts`). This holds for any client, not only the web app's budget. miniflare's SQLite does not enforce the 2 MB cap, so the workerd test shows the refusal and the Session going on, not the failure it prevents.

- **Session tree** ([ADR-0017](../adr/0017-session-tree-in-session-forks-and-clones-as-sessions.md); GLOSSARY.md → Session tree, Session branch, Fork, Clone): local pi's `/tree`, `/fork` and `/clone`. Labels on the tree's nodes are not done yet (#180).
  - **Session branches** are pi-durable forks (`fork(at)`) of the root conversation inside the Session DO, and the Session keeps which one is the active branch in a session document (`cloudpid.session-tree`, `apps/server/src/session/tree.ts`: the active one, and when each was last active). Everything that took the root conversation follows the active branch: `hello`, `submit` and `abort` without a `conversationId`, `configure` and the default model, the task graph's root, and the Subagents document's root agent (`activeBranch`, and `branches`, every branch's conversation), so a subagent the root agent starts belongs to the branch it was started from, keeps running when the owner moves, and reports and sends its `agent_message`s to that branch (`reportConversationOf`). A `conversationId` that names the active branch is the active branch, following the settings and the owner's pick as one left out does; one that names another Session branch is refused, as that branch is reached by making it active. `hello` still calls the active branch `root`, the name it had when the root conversation was the only one, so a client open across a deploy reads it as before. The transcript is the active branch's whole path, as pi-durable's fork-aware history reads it.
  - **`tree`** answers a `SessionTree`: one node per entry a transcript shows (ID, parent, branch, `user`, `input`, `assistant`, `tool` or `notice`, its text cut to one line of 200 characters, whether an answer ends its Run, its time), parents before children and siblings oldest first, with the active branch, its last node (`leaf`) and every branch's last activity. A branch with no entry of its own is left out. Clients compute the rest: siblings are nodes with one parent.
  - **`navigate { entryId, position, summary? }`** (a `TreePoint` and the summary asked for) moves the active branch to just before an owner's message (`before`, which answers its text for the composer) or just after an entry (`at`), and answers `Navigated` (the branch, the text). Where an existing branch's last entry is the point, that branch becomes active (the one active last, when several); otherwise a new branch is forked there (`planNavigation`), and before the Session's first message it is a fresh conversation, with the agent of the branch left. It is refused while the active branch is busy: a Run in progress, a compaction, messages waiting to be placed, or a `/compact` waiting. `summary { instructions? }` (at most 2,000 characters) has the active branch's model summarize the entries of the branch left that the branch entered does not share (pi's `collectEntriesForBranchSummary` and its prompt, `apps/server/src/session/branch-summary.ts`, at most about 100k tokens of the branch, newest kept), on the Session's spend as a title call is; the summary is placed in the branch entered as a `cloudpid.branch-summary` entry the context reads with pi's framing and the transcript shows as a "Branch summary" notice. `switch_branch { conversationId }` makes a branch active as it stands, refused likewise. Either announces `active_branch { conversationId }` to every client, which stops watching the branch it watched, watches the new one, and asks for the tree again.
  - **Fork and Clone** (`forkSession { source, point?, workspace?, branch? }`, answering the new Session and the text for its composer): a Fork is a new Session from a point of the source's active branch (just before an owner's message, whose text goes into the new Session's composer, or after an answer); a Clone, with no point, is one from its latest entry, refused while the active branch is busy (as `navigate` is). Either is refused while the source is itself still being filled. The source answers what to copy (`forkSource`, `apps/server/src/session/fork-host.ts`, with what is copied in `fork.ts`: the branch, the last entry, `pi.agent` as of the point (pi-durable's default before the Session's first message, so the Fork takes the settings in force), the fields of model and thinking level it picked itself, each as the branch ran with it at the point (the others follow the default in the Fork too), the Notes and the Todo List as they are now), and the Registry registers the new Session (titled `<source's title> (fork)` or `(clone)`, `Untitled session` standing for a source with none, cut to the longest title (`forkTitle`), with its `origin`: the source's ID and `fork` or `clone`), then fills it with the branch's path through the point (every Context Window), a page at a time (at most 200 entries and about 8 MiB of JSON: `exportEntries`, `importEntries`, in the loop `fillSession` that the tests drive too), into the new Session's root conversation, renumbered, its heads and edits pointing at the entries it was given, then hands it the rest (`importFinish`). Other branches, held Secrets and Usage are not copied: the new Session starts at none. Until it is filled the new Session refuses messages and moves, saying it is still being made, and greets with `copying` (the Registry answers once it is filled, so the source's page says the new Session is being made meanwhile, and makes one Fork or Clone at a time); once filled it closes its sockets with 1012, so the clients connect again and are greeted afresh. `workspace` is the source's Workspace by default (`same`); `new` makes one of the source's Environment on `branch` (or `cloudpid/<id>`, refused as `createSession` refuses one), refused while anything of the source works (any branch's Run or queued messages, any subagent, a `/compact` waiting: the Harness's live tasks that are not background work, and its unsettled submissions); from then until the files are carried (`releaseFork`, or 30 minutes at most) the source takes no message, so nothing changes them meanwhile. Once the Session is filled the source's Workspace DO carries its files there (see [_Carried files_](workspace.md)). A Fork that fails leaves nothing: its Session is deleted, or its new Workspace removed with it, and the source takes messages again.
  - **In the web app:** under each owner's message and each answer that ends a Run on the active branch, a bar has a Branch button (`navigate`: to just before the message, its text put back in the composer, or just after the answer) and Fork, a split button (the main part in this Workspace, its menu "Fork in a new workspace…", which asks for the new Workspace's optional git branch); under the answer the active branch ends with (past any notices), Fork reads Clone and Branch, with nowhere to go, is disabled. "Branch" there is a verb, the button's action; the noun stays _Session branch_. Clone's icon is a split path, not a copy's. Branch and Fork show on hover or focus with a fine pointer, always on a touch screen; an archived Session's bar only forks and clones, and a subagent's thread has no bar. The first message of a Session branch with siblings shows chevrons ‹ n/m ›, whatever it is (an owner's message, a subagent's report, an answer or a step of one, a tool result, a branch summary's notice), each landing on the most recently active branch through that sibling (`switch_branch`), disabled while the branch is busy (a Run in progress or messages waiting; the Session refuses a compaction's time itself); an archived Session shows none. The Branch button or a pick in the Pane asks whether to summarize the branch left (No summary, Summarize, or Summarize with a focus) unless `branchSummary.skipPrompt` is on. The **Session tree Pane** (`tree`, one per Session, opened from the New pane or by `/tree`) shows the tree, indented only where it branches, the active branch's path marked and its last node too, with filters (the owner's messages and the answers that end a Run, by default; all but tool results; the owner's messages; everything); a pick moves there as the Branch button does. An archived Session's New pane does not offer the tree, and its Pane's picks are disabled. A Fork or Clone opens the new Session with the text in its composer, and its header says "Forked from" or "Cloned from" the source, a link while the source exists. The root composer's `/tree`, `/fork` and `/clone` run in the web app, taking no argument: `/fork` opens a dialog of the active branch's owner's messages to pick from, and both ask where, in this Workspace or a new one, as the bar's buttons do; an archived Session has no `/tree`.

- **Notifications:** Web Push when a Run ends, fails, or needs input.
  - **Keys:** `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT` are deploy-time secrets read by the Registry DO (`Config.Redacted`). The public key reaches the web app through `getPush`; the private key never leaves the Worker.
  - **Subscriptions:** a device's `PushSubscription` (endpoint and keys) is a row of the Registry DO's `push_subscriptions` table, over `getPush`/`subscribePush`/`unsubscribePush`. The Settings page's Notifications section turns notifications on (permission, subscribe, `subscribePush`) and off (`unsubscribePush`, unsubscribe) per device. `getPush` says whether the Registry holds the asked endpoint, and the page gives it back a subscription the browser holds but the Registry lost.
  - **Sending:** the Registry DO's `notify(sessionId, event)` (`apps/server/src/push`) encrypts one message per subscription (RFC 8291 `aes128gcm`) and signs it with VAPID (RFC 8292), both on WebCrypto. The body is a title (the Session's title), one line, the Session's page and a tag, a few hundred bytes. Each push is given up on after 5 s, 16 at a time, so the Session's 20 s wait holds for up to 64 browsers (a Session that gave up sooner would send it again). A 404 or 410 from the push service deletes the subscription; any other failure is logged and the subscription kept. Only endpoints at known push services (FCM, Mozilla, Apple, Windows) over https are accepted. A Session DO reaches it through `SessionRegistry.notify`, and extensions through the `OwnerNotifications` service in `@cloudpid/extensions/notify`, which takes a `notice` event (title, body, url; the title, body and url are bounded so a push fits one message).

A notification the Registry could not take stays pending and goes out with the next settle. A Secret request notifies when it is first asked, in the background so the request neither waits for the push nor is held past an abort (`input`, naming the Secrets and the agent's reason, never a value). An Approval request does the same (`input` with `approval`, the change and its target, and the agent's reason: `Approval needed: …`). A Browser Handoff notifies the same way (a `notice` with the instructions as its body and, as its `url`, the query `?pane=live-view:<requestId>`, which the push puts on the Session's page so a tap opens the handoff's Live View Pane; never a link). - **Titles:** a background task asks the `small` role for a 3–6 word title (from the first message as the owner typed it, not its expansion), stored in the Registry DO and shown in the Session list. The owner renames a Session from its ⋯ menu or with `/name` (`renameSession`); its header shows the title only.
  - **Source:** a Session's record has a `titleSource`: `owner` (named at creation or renamed), `generated`, or null while it has no title. The Registry enforces the rules, not the Session: `setGeneratedTitle` sets a title only while `titleSource` is null, so a generation never replaces an owner's title (set before or while the model worked) and happens at most once; `renameSession` always wins. There is no way to clear a title.
  - **Task:** the Session host (`apps/server/src/session/titles.ts`) runs it beside the Run, never inside it. Once per answer to a submission to the root conversation (and, in an instance that only resumed work after an eviction, when the Session settles idle), it asks the Registry whether a title is wanted, reads the root's first message and first answer (each cut to 2,000 characters), asks the `small` role's model (the Session's own model, its pick or else the default, if there is no `small` role) for a title through the Session's models, so the request is scrubbed of held Secrets like any other, and offers the sanitized reply to the Registry (first line, no `Title:` label, quotes, markdown, control, zero-width or bidi characters, or ending punctuation, at most 80 characters). Subagent conversations are never named: only the root's messages are read.
  - **Durability:** what it keeps in the Session's storage is whether it is done and how often it failed. An attempt counts when it starts, so an eviction mid-request uses one; a failed request, an empty reply or an unreachable Registry leaves the task open for the next answer or wake, and it gives up after 6 attempts. A Session the owner named is marked done on the first check. The call's tokens and cost are logged (`Session title request`) and added to the Session's spend, kept in the Session's storage because no conversation's `pi.usage` holds them; the call is not held to the spend limit (see [_Operations_](operations.md) → Telemetry).
