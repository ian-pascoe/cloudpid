# MCP Apps

An **MCP App** is the interactive page an MCP server declares for one of its tools; cloudpid is a host of the Stable MCP Apps extension (`io.modelcontextprotocol/ui`, `2026-01-26`) in both Protocol eras. Each tool call that has one gets an **App View**, shown in the call's card or an **App Pane**, running in the **App sandbox** on `ianpascoe.app` ([ADR-0031](../adr/0031-app-views-run-in-a-secretless-sandbox-on-a-domain-of-their-own.md)). The App View's HTML and all its traffic go through the owner's Session socket to the Session DO and `McpHost`, never from the sandbox to cloudpid. Exhaustive detail is in [Rendering an MCP App in the web UI](https://github.com/ian-pascoe/cloudpid/issues/384) (D0–D18; a D-number below without a ticket name is its) and [What must an MCP Apps host implement?](https://github.com/ian-pascoe/cloudpid/issues/375).

## Declaring and reading Apps

- **Negotiation:** the core declares `{ mimeTypes: ["text/html;profile=mcp-app"] }` under `io.modelcontextprotocol/ui` always, in both eras, on every request (Legacy `initialize`'s `capabilities.extensions`, Modern per-request `_meta` client capabilities), whether or not a browser is attached ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D23; [_Extensions_](mcp.md#extensions)). Servers may then list App variants of their tools, so the declaration shapes `tools/list`. A per-server "Apps off" switch is left for later.
- **Declaration:** a tool is an **App tool** when its `_meta.ui.resourceUri` names a `ui://` resource. The MCP inventory keeps a tool's whole `_meta`, and the `mcp` extension passes it on each call as `details.meta` ([_Calls and results_](mcp-in-a-session.md#calls-and-results)). The page learns the App tools from `mcp_app_tools` ([_Socket messages_](#socket-messages)).
- **Tool visibility:** a tool's `_meta.ui.visibility` (`["model"]`, `["app"]` or both, the default). The model reaches a tool only if it includes `"model"`, and then by [_Exposure_](mcp-in-a-session.md#exposure); an `["app"]`-only tool is never declared to the model, in any Exposure, and an `mcp__*` entry in `tools.offered` cannot lift it. An App View reaches a tool only per [_An App View's calls_](#an-app-views-calls) (D7).
- **`ui://` resources elsewhere:** `ui://` and `text/html;profile=mcp-app` resources are left out of resource lists and the composer's `@` menu but stay readable ([MCP resources](https://github.com/ian-pascoe/cloudpid/issues/385) D4.4; [_Resources_](mcp-in-a-session.md#resources)). What a `ui://` resource link in a tool result shows is left for later: [MCP resources](https://github.com/ian-pascoe/cloudpid/issues/385) D5 hands it to this document, and no ticket settles it.
- **Reading the HTML:** for an App call, `McpHost` reads the `ui://` resource with `resources/read` in parallel with `tools/call`, only when the stored hash for (server, uri) is stale for the inventory's `version`. The content must be exactly one item, `text` or `blob`, with MIME exactly `text/html;profile=mcp-app`, at most 4 MiB (the core's read limit for `ui://`); `_meta.ui` (`csp`, `permissions`, `domain`, `prefersBorder`) is taken from the content item, then from the resource's listing entry (the draft's fallback, read side only, D13). A failed read never fails the call: the first mount retries it (`McpHost.request { op: "ui/html" }`, [_RPC_](mcp-connections.md#rpc)) or pins what it gets (D4).
- **HTML storage:** `McpHost` keeps App HTML by SHA-256 in its SQLite (`mcp_app_ui`, `mcp_app_html` chunked, `mcp_app_html_meta`; [_Storage_](mcp-connections.md#storage)), 64 MiB per Environment, the least recently mounted evicted and pruned at writes ([The Environment's MCP host object](https://github.com/ian-pascoe/cloudpid/issues/382) D3.2). A replaced host's App HTML writes are best-effort and heal at the next read ([Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423) D3.2; [_Deploys_](mcp-connections.md#deploys)). Each call's App record pins its `htmlHash`; tabs cache HTML by hash in memory and fetch it with `mcp_app_html { hash }`, which the Session serves through `op: "ui/html"`.
- **As built** ([#466](https://github.com/ian-pascoe/cloudpid/issues/466); `apps/server/src/mcp/app-html.ts` for the checks, `app-reads.ts` for the reads, `app-store.ts` for the storage, `request.ts` for the two ops): the host's side only; the App record and the socket messages are built by [#473](https://github.com/ian-pascoe/cloudpid/issues/473) (below), the View is not built yet.
  - **The read:** a `tools/call` of an App tool (`appUriOf`: `_meta.ui.resourceUri` a `ui://` URI of at most 2048 characters) whose (`conn`, URI) has no stored page, or one read at another inventory `version`, starts the read: the engine's `resources/read` op, which the core's `readResource` sends (a read, so a cut sends it once more), through the same server cap and host cap as the call, with the call's target and access, and in the engine queue as background work (a mount's own read, as a call). **The call never waits for it.** It answers when it is done, with `Completed.app.htmlHash` (an optional, best-effort field) only if the page is stored by then; otherwise the read goes on, bounded by the core's 30 s page timeout (`PAGE_TIMEOUT_MS`, `connection.ts`), and stores the page when it ends, and the first mount finds it or joins the read (`ui/html`). While the call runs, the caller's abort cancels the read the call started; once the call has answered the caller's stubs are gone, and a read goes on alone.
  - **Beside the call or after it:** the read goes beside the call only when the connection is established already (a Modern server, or a Legacy one with a session row), so the two never `initialize` at once; on a Legacy server with no session, over HTTP or stdio, a second `initialize` makes a stdio bridge spawn a child that replaces the call's, so the read starts when the call has answered and made its session. A stdio read runs in the call's Workspace.
  - **One flight, one slot, a failure remembered** (`McpAppReads`): the reads that several calls start for one (`conn`, URI), and a mount's `ui/html { uri }`, share one flight. The engine round takes no host-wide slot, so a server that is slow to answer delays no other's read. The host decodes one streamed answer at a time, from reading the stream to the page's keeping, since the engine's answer, its JSON, the HTML and its bytes are alive together (as the Session does for large results); an answer that is inline (≤1 MiB) takes no slot. A read that waits for the slot longer than 30 s (`APP_SLOT_WAIT_MS`, half of `MCP_STREAM_HOLD_MS`, which the engine lets a stream go unread for) cancels the stream and fails as `TimedOut`, remembered as a failure. The `resources/list` that completes a page with no `_meta.ui` is waited for 10 s (`APP_LIST_TIMEOUT_MS`) and never read as a stream. A read that failed or hung for a (`conn`, URI) is not started again by a call until the inventory `version` moves or a minute (`APP_READ_BACKOFF_MS`) has passed, so a broken App server costs the calls after it nothing; a mount's read is never held back, and a cancelled read is no failure. At most 256 failures are remembered (the expired go first, then the oldest). A read belongs to the caller that started it: a call's abort cancels its read, and a mount that joined it reads once more rather than fail for another caller's abort (a second cancel is the mount's own `Cut`). The core limits an App's read of its `ui://` resource to `MCP_APP_READ_BYTES` (12 MiB of JSON, `tap.ts`; the host's read says it is an App's with `app` on the engine's `resources/read`, and any other read, the agent's of a `ui://` resource included, has 16 MiB), which holds 4 MiB of HTML as base64 or escaped; the host then checks the HTML itself (below), decoding a blob in slices and counting a text's UTF-8 without copying it. Content that is not an App's page fails as `ProtocolViolation` or `TooLarge`.
  - **`_meta.ui`:** from the content item, else, for an item with no `_meta.ui` object, from the resource's listing entry (one `resources/list`, a stream not read). Only `csp` and `permissions` (objects), `domain` (text) and `prefersBorder` (a boolean) are kept, at most 16 KiB of them.
  - **The hash** is the SHA-256 of the `_meta.ui` (keys sorted), a newline and the HTML: `htmlHash` names the page as served, with its meta, so a page that two servers give with different declarations (a different CSP) is two pages, and one given twice is kept once. `mcp_app_ui` holds (`conn`, URI) → hash and the `version` it was read at; `mcp_app_html_meta` the hash's size, `_meta.ui` and last mount; `mcp_app_html` its UTF-8 in chunks of 1 MiB. A write (`putApp`) is one transaction: the page if new (else its mount time), the `mcp_app_ui` row, then the eviction of the least recently mounted pages past 64 MiB (never the one just written, so a lone page over the bound stays) and of the `mcp_app_ui` rows that named one. A `ui/html` by hash marks the page mounted. A `conn`'s `mcp_app_ui` rows go with its status (`pruneOutsideSet`); the pages stay until evicted, for the App records that pin them.
  - **Stale** means the row's `version` is not the inventory's, which is Environment-wide (`versionsOf` over the held set): any server joining, leaving or changing moves it, and every App page is then read again at its next call. That is a known limit; so is a server that changes its HTML without its tools changing, whose page is not read again until the version moves.
  - **Known limits:** a read that goes on after its call has answered is bounded by the core's 30 s page timeout (`PAGE_TIMEOUT_MS`), not by any hook of the caller's; a call that joins a read in flight for an older inventory `version` answers the hash that read keeps, which a mount's `ui/html { hash }` serves all the same; and a Legacy server with a session row whose child (stdio) or session has since died is read beside its call, so the two may each see an `initialize`; and a mount that joined a read that kept its page, on a host replaced just after, reads the page back from a storage that refuses and answers `HostFailed` rather than the page (the new instance serves it at the next mount).
  - **A failed read** (a server error, a wrong MIME type, too large, a hung read, a refused write) never fails the call: `Completed` has no `app`, and the first mount reads again. `app.htmlHash` is set only for a page the host holds for this inventory, never for one it failed to keep, and a stale page is read again, never answered.
  - **`op: "ui/html"`:** `params: { hash }` serves the kept page as `AppHtml { hash, html, meta }` (`NoAppHtml` when evicted or never kept: the mount then reads by URI); noting the mount, which decides the eviction order, is best-effort, so a page the host could read is served although a replaced instance's storage refuses the note ([_Deploys_](mcp-connections.md#deploys)). It touches nothing remote, so it needs only a server of the set (`UnknownServer` otherwise), whatever its Exposure, sign-in state or Workspace: the Views of a wholly `hidden` server mount, and only their calls are refused ([_Lifecycle_](#lifecycle), D7). `params: { uri }` reads the resource now, keeps it under the inventory's `version` and answers it, or `CallFailed` with why; it has the checks of a call (a server that may be called, so not `hidden`, not at `sign_in`, and, for a stdio server, the request's own `ctx.workspace`, which may start its Container) and a URI that some listed tool of the server declares as its App. A hash is not tied to a server, since an App record pins a hash its (`conn`, URI) may no longer name.
  - **The Session's gate** (left to implementation): the host lists the feature `app_html` in `requestStart`'s `features`, and the Session, once it sends `ui/html`, does so only when it is listed, and reads `app` off a `Completed` only if it is there; an older host's `HostUnsupported` is the backstop, and an older Session drops an `app` it does not know. `MCP_TOOL_FEATURES` does not name it, so no tool is held back for it.
- **As built ([#473](https://github.com/ian-pascoe/cloudpid/issues/473); `packages/extensions/src/mcp/apps.ts` and `app-tools.ts`, `appUriOfMeta` in `packages/mcp/src/types.ts`):**
  - **App tools** are read by `appUriOfMeta` (the host's `appUriOf` takes it too), and the Session's inventory of them is `appToolsOf`: every tool of a server that is not switched off whose `_meta.ui.resourceUri` names a `ui://` resource, under its model-facing name and with its `visibility` (`["model", "app"]` when `_meta.ui.visibility` is absent), at most `MAX_MCP_APP_TOOLS` (1000) of them. `reachesModel` and `appToolsOf` read the visibility through one reader, `visibilityOf` (`mcp/exposure.ts`).
  - **App-only tools** (a `visibility` without `"model"`) were already never registered (`reachesModel` in `mcp/exposure.ts`, as for any tool); a test now holds that for every Exposure and for offered sets that name them, so such a tool is in none of the model's tools, `codemode`'s namespaces or a child's grant. It is in `mcp_app_tools`, which is what an App View may call.
  - **A `ui://` resource link in a result is an ordinary link:** the model's line and `details.resources` have it (a link to one is read with `read_mcp_resource` as any), and it mounts no App and writes no record. An App is mounted only from an App tool's call. Mounting from a link was rejected, since a link has no call whose arguments and result a View is given; dropping the read clause for it was rejected, since the model could then not read what its own result named.
  - **The gate:** `app_html` is now one of the optional tool features (`MCP_OPTIONAL_TOOL_FEATURES`): a host that lists it has `Completed.app.htmlHash` read into the record and `mcp_app_html` served through its `ui/html`; a host that does not gets a record without a hash and an `unsupported` answer, and no tool is held back. The host does not wait for the page's read, so the record of a call made before the page was kept has no hash. Reading the page by its URI and pinning the hash to that record are left to the View ticket (D4); a record without a hash is a record all the same.

## App records

- **What it holds:** one record per App call, direct or nested in `codemode`, root or subagent, written by the Session DO in the `mcp` tool's `execute` into Session storage outside History: server, conversation, parent call, arguments, `htmlHash`, the whole Secret-redacted `CallToolResult` (`structuredContent` and result `_meta` included, which the script value drops), the App View's audit log and its App context state (D5). Live mounts and replays read the same record, so a client that connects later, a reload or a phone gets `tool-input` and `tool-result` again from it.
- **Bounds:** ≤1 MiB a record (over it: drop `structuredContent`, then cut texts to 64 KiB, `truncated: true`; live and replay see the same), 32 MiB per Session, least recently mounted evicted. An evicted record leaves a stub, and its card shows only the call's summary ("App data no longer kept"), with no Reopen and no re-run.
- **Copies and schema:** Fork and Clone copy the records of the calls they copy. Records are additive-only with fallback members and no format `v` ([Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423) D3.4; [_Deploys_](mcp.md#deploys)).
- **Other writers:** the summaries of Sampling requests, Elicitation requests and MCP tasks raised by an App View's own calls go into the record's audit log; an App View call kept as an MCP task has a small entry in the Session's key-value storage (`mcp-task:app`) for the task sweep, never a record in `cloudpid.mcp-tasks` ([_Server requests from an App View's calls_](#server-requests-from-an-app-views-calls)).
- **As built ([#473](https://github.com/ian-pascoe/cloudpid/issues/473); `packages/protocol/src/mcp-apps.ts` for the record, its bounds and `boundAppRecord`, `packages/extensions/src/mcp/apps.ts` and `tools.ts` for the write, `apps/server/src/session/mcp-apps-store.ts` for the storage):**
  - **The write:** the `mcp` tool's `execute` hands a draft (everything the call knows) to the Session's `McpAppRecorder` once its result is read, for a completed call of an App tool, an `isError` result too, direct or nested in `codemode` (`parentCall` is the script's call), and a failed write is logged and never fails the call. The store redacts the Secrets held, bounds the record and writes it in one synchronous run, so no reader sees half of it. The audit log and the context stay empty until the tickets that fill them.
  - **Storage:** the Session's key-value storage (no migration): the record's JSON in parts of 256 KiB under `cloudpid:mcp-app:<callId>:<n>`, and an index of every record and stub, oldest first, under `cloudpid:mcp-apps`, written last.
  - **Bounds, in order:** over 1 MiB, `structuredContent` is dropped, then the Secrets are redacted over what is left (so none is cut into a piece that cannot be recognized), texts are cut to 64 KiB, the largest binary blocks are dropped, then the result's `_meta` and last the arguments, with `truncated: true` from the first. Last, so that the bound always holds, `withinBound` drops the result's keys that a `CallToolResult` does not have, then replaces content blocks from the end by a line that says how many went (as many as it takes, found by halving), and, if even one block is too much, leaves the line alone with the result's `isError`. Past 32 MiB the least recently mounted record (never the one just written) is evicted to a stub. Two bounds the design does not name keep the index small: 1000 records, past which the least recently mounted is evicted, and 2000 stubs, past which the oldest stub is dropped and reads as no record.
  - **Mount:** `mcp_app_mount` answers the record and marks it the most recently mounted, its stub when it was evicted, or `none`.
  - **Fork and Clone:** a page of `ExportPage` carries `apps`, the records and stubs of the calls whose results its entries hold and of the calls nested in them (counted in the page's size, so a page is cut as before), and `importEntries` takes them as an optional second argument and keeps them as the root conversation's, bounded as any record is, all in one write of the index; a copy of a kind this build does not know is skipped (`McpAppCopy` has a `{ kind: string }` fallback), so a Fork from a newer Session is still made. A copied stub is the target's conversation's and keeps its call's time (`McpAppStub.at`). One entry's calls that weigh more than a page (a `codemode` script with many App calls) have their records past `MAX_COPY_PAGE_SIZE` carried as stubs, since a page is one RPC's value and an entry is not split from its copies. A source from before App records sends none.

## App Views in the transcript

- **Which App Views are live:** an App View is live inline in its call's card while its call is in the newest **generation** of its server's App calls in the conversation: the App calls of the latest assistant message that made any, and within a `codemode` script the last call per server. Older App Views collapse to the call's result text and last App context, with **Reopen**, which keeps an App View live until the owner collapses it. A focused App View is never collapsed. Defaults derive from the transcript, the same on every device; Reopen, Collapse and Pop out are per device, in the Session layout (D0).
- **Where it renders:** a direct call in its card; nested calls in a strip under the `codemode` card, outside its disclosure, live by the same rule; a subagent's calls in its thread (card, Subagent Pane, Subagent page), latest-live per conversation, with its App messages going to that thread's composer and its App context to its conversation. One mount per page, by precedence App Pane > Subagent Pane or Subagent page > card; every other place shows "Shown in …" (D8).
- **The card's frame:** an "App · <server>" frame around the App View; the iframe's title is "App: <title> (<server>)"; a mount never takes focus. The card's details list the App's CSP domains, its sandbox origin (with a copy button), any `_meta.ui.domain` as "asked for X" (never honoured), and the audit log. `prefersBorder` is honoured (D3, D9, D17).
- **Remounting:** messages are keyed by ID and nothing is virtualized, so paging in earlier history, scrolling and wake snapshots never remount an App View; it sits outside the card's disclosure. Leaving the page, closing a subagent card, moving to a branch without the call, and moving to or from an App Pane remount it, always after `ui/resource-teardown`. The chat keys one assistant message per turn by the user message before it (`<userId>:reply`; its tool calls are parts by position), which holds as the live message commits, the tool runs and its result entry arrives, so a commit never remounts an App View (D12, D15; the design keyed by the message's first tool call's ID, which the turn key makes unnecessary: see _As built_ ([#496](https://github.com/ian-pascoe/cloudpid/issues/496)) below).
- **Teardown:** `ui/resource-teardown` is sent and awaited for at most 2 s before any unmount; teardown cancels the App View's in-flight requests.
- **As built ([#482](https://github.com/ian-pascoe/cloudpid/issues/482); `apps/web/src/app-view/`: `app-call.tsx` the card's child, `app-frame.tsx` the frame, `atoms.ts` and `load.ts` the loading, `availability.ts` the states, `frame-url.ts` the frame's URL):** `ToolCallCard` (`chat/parts.tsx`) renders an `AppCall` under its card, outside the disclosure, for a call of an `mcp__…` tool (a finished one in #482; a streaming one too since [#496](https://github.com/ian-pascoe/cloudpid/issues/496), below); it adds nothing unless the call is an App's (the inventory's `mcp_app_tools` lists its tool, or `mcp_apps` has an entry for it). `availability.ts` decides what the card says from those two and the server's chip state (`mcpStatusesAtom` of the Session's Environment): a kept record mounts, with a badge "Server offline" (`unavailable`, `failed`, `unknown`) or "Needs sign-in" (`sign_in`, `rejected`); a tool the inventory no longer lists as an App's, or a disabled server, is "App unavailable" and never mounts; an evicted record is "App data no longer kept". A record pins the `viewHash` of the server that made the call (`Completed.app.viewHash`, `McpAppRecord.viewHash`), and `mcp_app_html` answers `unavailable` for a page whose server's `view` differs: an owner's `docs` that shadows a Repo's has the same name but another origin, so the old call is "App unavailable", never mounted at the new server's origin (a record that predates it pins none and is not checked). The check is made when the page is fetched: a remount from the in-memory cache does not ask the Session again (it is the record's own page, at the record's own origin, under a key that carries `viewHash`, so it cannot be another server's; re-checking on every remount would cost the round trip the cache saves). Mounting is `mcp_app_mount` (the record, or a stub, or none), then `mcp_app_html` by the call, which also returns the origin the Session built; the page is kept in memory by the record's `viewHash` (its Environment, source and server, so its origin) and the page's hash, never by server name and hash alone: the same page of one server in two Environments is two entries, each at its own origin, and a record that pins no `viewHash` is not cached at all. A remounted card or a second call of the App does not fetch the HTML again (at most 8 pages and 8 M characters). Only an origin of the shape `https://<26 base32>[--<label>].ianpascoe.app`, or the local sandbox's, is ever framed (`isSandboxOrigin`); the frame is `sandbox="allow-scripts allow-same-origin"` with `referrerPolicy="no-referrer"`, no `allow`, no focus, and its URL carries the declared CSP as `?csp=` (`frameUrl`; a longer-than-8 KiB declaration is left out, which the Worker reads as none). Its height follows the View's `size-changed` up to min(640 px, 70 % of the scroller), 160 px before the first. The frame's header is "App · <server>", the badge, and **Details** (the declared CSP domains, the sandbox origin with a copy button, `_meta.ui.domain` as "asked for X"); `prefersBorder: false` drops the frame's border. A load or start failure is "App couldn't load: <why>" with **Retry**, which loads or builds the frame again. **Teardown:** a card that ends a View itself (the call evicted, the server off or shadowed, another page, a later Collapse) does not remove the frame first: `AppFrame` goes to _closing_, sends `tool-cancelled` first when its call did not finish (`cancelled`, supplied by [#496](https://github.com/ian-pascoe/cloudpid/issues/496), below), then `ui/resource-teardown`, and removes the frame only when the View has answered or 2 s have passed (`retire` in `bridge.ts`; `AppMount` in `app-call.tsx` shows the note then). #490's Collapse and Reopen use the same `closing` and `onClosed` props. **Not built there, built by [#490](https://github.com/ian-pascoe/cloudpid/issues/490) (the next bullet):** the generation and live rule, collapse and Reopen, Pop out and the App Pane, fullscreen, the remount rules and the placement of a `codemode` strip or a subagent's thread. The audit log in Details is [#489](https://github.com/ian-pascoe/cloudpid/issues/489); a View that mounts as its call streams (`toolcall_start`, `tool-input-partial`, `tool-cancelled`) is [#496](https://github.com/ian-pascoe/cloudpid/issues/496) (below); as built by #482 a View mounted only when its record existed, that is when the call had finished. The example View was run in a DOM, not in a browser (below).

- **As built ([#490](https://github.com/ian-pascoe/cloudpid/issues/490); `apps/web/src/app-view/`: `generation.ts` the rule, `places.ts` where a View shows, `teardown.ts` the registry and the guards, `app-pane.tsx` the Pane, `display-mode.ts` the modes; `app-call.tsx` the card, the place mount and the strip):**
  - **Generation.** `appGenerationAtom` reads the loaded transcript (`generation.ts`): a generation is one pi assistant message (its tool-call IDs, not the chat library's turn message), counted per server. Direct calls of the newest message that made any are all live; in a `codemode` call the last nested call per (script, server) is, by `at` and then list order, and evicted records count as calls. A call not in the loaded messages is ignored (paging earlier history in never changes what is live). A focused View is not collapsed by the generation, and collapses when the focus leaves it if it still is not in the newest: the View that holds the focus is the one whose frame is the document's active element (`focus.ts`), which the window's blur and focus and `focusin` report, plus a 250 ms poll while a frame holds it, because focus moving straight from one frame to another fires nothing at the page. An archived Session collapses every View until Reopen. The owner's choices, per device, are `openApps` (reopened or popped out) and `collapsedApps` (collapsed) in the Session layout (`appChoiceAtom`). A collapsed card shows "App · <server> collapsed" and **Reopen**; the result text is the card's own result, and the last App context is shown by [#495](https://github.com/ian-pascoe/cloudpid/issues/495).
  - **Places.** `AppPlaces` (`places.ts`) is a store of the places that claim a call: App Pane 3 > Subagent Pane or Subagent page 2 > card 1; the winner mounts the frame and the rest say "Shown in <place>". Pop out, fullscreen and Reopen follow the spec literally: the frame in the old place closes (teardown, at most 2 s) and the new place mounts after it has `closed`. The codemode strip (`AppStrip`, under the `codemode` card, outside its disclosure) has a row for every App call the script made, none cut off: the live ones mount and the rest are collapsed rows with Reopen, with liveness decided over all the script's calls. A script with more than 20 shows the last 20, its live calls and any the owner reopened on this device, and "N earlier" for the rest, which opens them all and stays open (closing it again would unmount a View the owner reopened).
  - **Teardown on an unmount React drives.** A persistent frame layer was **not built**, and the Limit of #482 stands for what the guards below do not cover. A frame that outlives its card needs an overlay positioned over a placeholder; that loses the scroll chaining of the chat scroller (a wheel or a touch over an inline View would stop at its frame, which a phone makes unusable; fixing it means proxying wheel events through the sandbox page, and a fling cannot be), lies above the page's sticky card and subagent summaries, the Session details and the completion menu (so it needs clip or occluder hacks), and follows its placeholder by polling every frame, none of which could be checked without a real browser. Instead every mounted frame registers in `appViews` (`teardown.ts`), and the owner-driven unmounts call `afterTeardown(action, within?)` before they go: the router's `navigate` to another pathname (a changed query is the same page), closing a subagent card, and closing a Pane (`PaneArea`, and the card's "Show here", which is offered only for a View shown in an App Pane and looks the Pane up by its `data-pane` key, `paneElement`). What goes is named explicitly: an element (the Views inside it), `null` (an element that is not there: nothing), or `EVERY_VIEW` (a page change); a missing element never means every View. The action runs when every View has answered or after 2 s. Moving to another branch (the tree actions, dialog and bar, through `useBranchMove`) is `afterBranchTeardown`: it tears down, and waits for, only the Views whose calls the branch moved to does not hold (`callsDroppedBy` over the thread's loaded messages and the entries `keptByPoint` or `keptByBranch` name), and leaves alone the Views it keeps, which are never reloaded, and an App Pane's, which stays where it is; a View it tore down is not made again before the move unmounts it, and is made again if the move did not happen. While the Session tree is not yet known it is not known what goes, so no View is asked and the move is made as it is. A subagent thread's Views are not in the branch's messages, so a branch switch does not ask them: they go unguarded with their cards. **Not covered:** the browser's Back and Forward (the page has changed when `popstate` is seen), closing or reloading the tab, and any other unmount; those lose the View without `ui/resource-teardown`. The alternative, if the owner wants those covered, is the layer with wheel forwarding in `apps/app-sandbox`.
  - **Display modes** (`display-mode.ts`): `inline` and `fullscreen`. A request for fullscreen pops the View out, one for `inline` from an App Pane closes the Pane, and `pip` or an unknown mode answers the current mode. Escape in the App Pane's own chrome (its header and buttons) returns focus to the chat (`focusChatOnEscape`). **Limit:** a key pressed inside the View's frame never reaches the page, and ext-apps has no message for a View to hand Escape back with, so from inside a View Escape is the View's own and the way out is Tab or the Pane's "Back to chat".
  - **Archived Sessions, read only.** A View that is live in an archived Session was reopened by the owner (every View starts collapsed, in its card and in an App Pane alike, and an App Pane shows the same collapsed row with Reopen), and is mounted `readOnly` (a View still mounted when the Session is unarchived is torn down and made again with every call served, so its badge and handlers agree): `viewRequestHandlers` serves `resources/read` only, so `tools/call` is answered as not found; `hostCapabilities` advertises `serverResources` and `logging` but no `serverTools`; and the frame is badged "Read only". The Session refuses a `tools/call` of an archived Session as well (`mcp-app-calls.ts`), so a frame built before the Session was archived is still refused.

- **As built ([#496](https://github.com/ian-pascoe/cloudpid/issues/496); `apps/web/src/app-view/`: `partial-input.ts` the pacing, `app-call.tsx` and `app-frame.tsx` the card and the frame, `load.ts`/`atoms.ts` the running call's page, `generation.ts` `runningAppCalls`; `packages/protocol/src/view.ts` the projection; `mcp_app_html`'s `tool`):** a View mounts as its call starts, and the commit and the result remount nothing (D12, D15).
  - **What streams.** pi-durable's conversation view holds the message being generated (`pi.live.generation.message`), each call's arguments already parsed by pi-ai's streaming JSON parser, and the watch's operations change them as they stream, so the page parses no JSON. `projectView` takes the names of the tools whose streamed arguments it keeps (`StreamedTools`, the inventory's `mcp_app_tools` that the client holds: none until it has told them); **every other tool's call in the live message shows no arguments** until its message is committed, so a long `write` re-renders nothing per token. The Session sends the operations whole: what is kept is the client's choice.
  - **Mounting.** `toThreadMessages` marks the calls of the live message (`artifact.streaming`); `ToolCallCard` renders an `AppCall` for every `mcp__…` call, with a `CallProgress` while it has no result: `streaming` (the model is still emitting it), `running` (its message was committed) or `stopped` (it ended with none), none once it has one. A running call has no record, so its page is its tool's: `mcp_app_html` gained `tool` (the model-facing name of an App tool, with `callId` for the host's log), which the Session answers by reading the `ui://` resource the inventory says the tool declares, with the origin, pinning nothing (`pageOfTool`). A Session that predates it takes `callId` for a record's and answers `missing`, which `loadRunningView` reads as no View yet: the View mounts when the call has finished, as before. The page is kept in memory by the host's `view` and hash, as a record's is. The generation rule counts the calls that run (`runningAppCalls`: an App tool's calls of the turn after the last user message with no result and no record, while the run goes on) as the newest of their server's, so an earlier View collapses as a new one mounts. A card that saw its call run keeps its View while the call runs, after it ended until its record is there, and when it stopped; only the owner's Collapse ends it. A call that stopped and was never seen running (a later load) is the card alone, its summary. **Pop out and fullscreen are offered once the record exists** (the Pane mounts from the record alone); until then the card's View can be collapsed only.
  - **Shadowing.** A page made before the record is of the server the inventory named when the call started, and keeps the `view` (the `viewHash` the Session built its origin from, `AppPage.view`). The record that arrives is checked against it before the View is told anything: a record of another server's name, a `viewHash` other than the page's `view`, or a record load the Session answers `unavailable` retires the frame (`tool-cancelled`, then `ui/resource-teardown`) and the card says "App unavailable"; neither the arguments nor the result reach it (an owner's `docs` that shadows a Repo's mid-call, or back, never gets the other server's result at its origin). A record that pins no `viewHash` is compared by the server's name only, as #482's check skips what it cannot compare.
  - **Telling the View.** `AppFrame` takes the record or, until there is one, the `running` call. `partial-input.ts` paces `tool-input-partial`: the latest arguments at most every 250 ms (the first at once), only when their JSON changed, and none once it is over 1 MiB of UTF-8 (it never resumes; `tool-input` carries them all); the bridge holds only the latest partial until the View's `initialized` and sends none after `tool-input`. At the commit (`final`) the View is sent `tool-input` once; when the record comes, `tool-input` (if it was not sent) and `tool-result`, into the same frame, whose page is the one it was made with (the record's is not swapped in). The bridge sends each of `tool-input`, `tool-result` and `tool-cancelled` at most once.
  - **Cancelled.** A call that ends with no result (`stopped`) sends `tool-cancelled` at once, the frame staying until the owner closes it. A View torn down while its call is unfinished (a card that goes with its message dropped, a retry, a collapse) is sent `tool-cancelled` first and then `ui/resource-teardown`, in `retire`. A call that has its result and no record 2 s later (the Session's list of records comes on its own, hence the grace; the tool failed before it ran) is sent `tool-cancelled` the same way, and its View stays until the owner closes it; a record that comes within the grace is delivered as usual. `tool-cancelled` ends the call for the bridge: no `tool-input` or `tool-result` is sent after it, so a record that comes after the grace is not delivered.
  - **Keying.** The chat renders one assistant message per turn, keyed by the user message before it (`${userId}:reply`; its calls are parts by position), so the live message's commit, the tool's start and its result entry keep the same message and the same position for the call, and its frame is the same element throughout (`app-streaming.test.tsx` renders the whole path through assistant-ui and checks it). This holds the D12/D15 rule (a commit never remounts a View) without the first tool call's ID as a key: the turn's own key is stabler, as it is the same for a turn of several messages.
  - **Limits.** A running call's View cannot call its server or send App context or messages: the Session has no record to name the server from, and the early page's `view` is never sent to it, so a shadowed View's calls would go to the record's server. The frame refuses `tools/call`, `resources/read`, `ui/message` and `ui/update-model-context` itself (`-32000`, "The host serves this once the call has finished") for as long as it has no record, which closes the window for a View that is shadowed (its record never reaches it). A remount of a running call's card (leaving the page and returning mid-call) reads the page again by the tool. The tool-input is sent at the commit of the message, so a message with two App calls sends the first's final input when both have been emitted.

## Lifecycle

- **Mounting:** the App View mounts as its call starts. For an App tool the model calls directly, the card renders as the call appears in the live message, and **partial input** (`tool-input-partial`) streams: the page parses the partial arguments with pi-ai's streaming JSON parser and sends the latest at most every 250 ms after the App View's `initialized`, only when changed and not past 1 MiB, then `tool-input` once with the final arguments, then the result. The web projection keeps the streamed arguments of App tools' calls (D12). As built: [#496](https://github.com/ian-pascoe/cloudpid/issues/496) in _App Views in the transcript_ (the arguments arrive already parsed, so the page parses no JSON).
- **Results:** `tool-result` carries the record's whole result; an `isError` result still mounts the App View and delivers it. An agent's App call that goes on in the background as an MCP task still delivers its final result to the App View in the original card whenever it arrives ([MCP tasks as durable long-running requests](https://github.com/ian-pascoe/cloudpid/issues/389) D6.1). _As built ([#498](https://github.com/ian-pascoe/cloudpid/issues/498)):_ the task's record (`McpTaskRecord.app`: the call's arguments and parent call) makes the App record when the task completes, inline or in the background, so a mount of the card reads the whole result.
- **Cancelled:** Stop, a timeout, an eviction or a cut sends `tool-cancelled { reason }`; later loads show the summary.
- **Load failure:** a read error, a wrong MIME, HTML over 4 MiB, or no `ui/initialize` within 10 s shows the summary and "App couldn't load: <why>" with Retry.
- **Server states:** unreachable → the App View mounts from cached HTML, its calls error and the card shows an "offline" badge; disabled, removed or shadowed → "App unavailable" and no mount; a wholly `hidden` server's App Views mount but their calls are refused (D7).
- **Archived Session:** App Views are collapsed (in a card and in an App Pane); Reopen mounts read-only ("reads only", read as forwarding only `resources/read`, #490); App messages are refused.
- **Socket drop:** in-flight App View requests fail ("connection lost"), the App View stays mounted, and pending App context is resent on reconnect (D15).
- **Elsewhere:** `/export` writes "App: <server>/<tool> (not rendered)" with the result text and last App context; App messages and App context never send a Web Push (D17).

## App Panes

- **Opening:** fullscreen (`ui/request-display-mode { mode: "fullscreen" }`) or the card's **Pop out** opens an App Pane, Pane type `app`, key `app:<callId>`, one per App View, a sheet on a phone; it remounts the App View there (teardown first) and the card says "Shown in …". Escape in the App Pane's own chrome returns focus to the chat; a key pressed inside the View's frame never reaches the page, so inside a View Escape is the View's (D0, D17; the limit is under App Views in the transcript).
- **Modes:** `inline` (the card) and `fullscreen` (the App Pane); `pip` is refused, replying with the current mode.
- **Sizing:** inline, width is fixed and height flexible up to min(640 px, 70 % of the scroller), 160 px until the first `size-changed`, which the host follows. In a Pane both axes are fixed, and a resize sends a debounced `host-context-changed` (D9).
- **As built ([#490](https://github.com/ian-pascoe/cloudpid/issues/490); `app-pane.tsx`, `pane-area.tsx`, `panes.ts`):** the Pane's tab is "App" with the server's name; `app:<callId>` is accepted up to 512 characters and the Pane area looks the call's server up in the Session's state, so a Pane for a call the Session does not have says "This App is not in this Session.", and one that cannot mount (record evicted, server off) says why; either stays to be closed. On a phone the Pane area is already a sheet, so the App Pane is that sheet. The frame's `containerDimensions` is the Pane's measured `{ width, height }`. The rest, the places, modes and teardown, is under App Views in the transcript.

## The App sandbox

Why it is shaped this way is ADR-0031's; this section is what to build.

- **Domain and Worker:** `ianpascoe.app`, a registrable domain kept for nothing else, served by one public sandbox Worker on the route `*.ianpascoe.app/*` with a proxied wildcard record `*.ianpascoe.app AAAA 100::` (no origin exists), under Universal SSL (one-level wildcard, no Advanced Certificate Manager). The apex is not routed and serves nothing; `www` hits the route and gets a 404 ([Verify the App sandbox on a deployed stage](https://github.com/ian-pascoe/cloudpid/issues/399)). The Worker is `@cloudpid/app-sandbox` (`apps/app-sandbox`), a plain Worker (`AppSandbox`, [`workers.md`](../development/workers.md#effect-workers-and-plain-workers)) with no bindings, `workersDev: false` and no Access; the stack declares it with the route and the record only for `prod` (`infra/alchemy.run.ts`).
- **Origins:** an App View's origin is `https://<hash>.ianpascoe.app` on prod and `https://<hash>--<label>.ianpascoe.app` on any other stage. `hash` is the first 26 characters of base32 of SHA-256 over `"v1\0" + environmentId + "\0" + source + "\0" + normalizedName`, with `source` `owner` (Global or Environment entries) or `repo:<owner/repo>`; the base32 variant is lowercase RFC 4648, unpadded (`a`–`z`, `2`–`7`; what the probe's hostnames in [Verify the App sandbox on a deployed stage](https://github.com/ian-pascoe/cloudpid/issues/399) show). App Views of different servers, Environments or sources never share an origin; editing a server's URL, headers or other config keeps it. The longest host label is 26 + 2 + 35 = 63 characters (D3).
- **Stage labels and app origins:** `stageLabel(stage)` is the stage lowercased with `_` → `-`; `deployment()` refuses, never truncates, a label that is empty, longer than 35 characters, starts or ends with `-`, or has characters outside `[A-Za-z0-9_-]`. Every non-prod stage names its main Worker `cloudpid-server-<label>`, so `appOrigin(stage)` is `https://cloudpid-server-<label>.ian-g-pascoe.workers.dev` (`WORKERS_DEV_SUBDOMAIN = "ian-g-pascoe"`), and prod's is `https://pi.ianpascoe.dev` (prod keeps its alchemy name). `stageLabel`, `appOrigin` and the constant live in `apps/server/src/deployment.ts`, which has no imports; every stage's deploy fails unless `server.url === appOrigin(stage)` ([How the App sandbox learns a non-prod stage's app origin](https://github.com/ian-pascoe/cloudpid/issues/421) D1, D3). Giving a stage its fixed name replaces its main Worker and wipes its Durable Objects once; `dev_$USER` is destroyed and redeployed ([How the App sandbox learns a non-prod stage's app origin](https://github.com/ian-pascoe/cloudpid/issues/421) D1.5). The check is `Output.map(server.url, …)` in `infra/alchemy.run.ts` (`checkedAppOrigin`), which throws when the stack's output resolves, before the preview comment that uses it is posted; `alchemy dev` serves on localhost and skips it. The main Worker's Access application, `Server/Access`, enrolls the Worker by its script id rather than by hostname, so it follows the replacement. A non-prod Worker reads its label from the `CLOUDPID_STAGE_LABEL` var; `prod`'s is unset, so no suffix.
- **The origin from the hostname alone:** the sandbox maps `<hash>` to prod's app origin and `<hash>--<label>` to `appOrigin` of that label, a pure function with nothing stored or read at load; the 26-character hash makes a label containing `--` unambiguous. A hostname that doesn't parse gets a 404. The mapping is `apps/server/src/view-host.ts` (`viewHost(hash, stage)`, `appOriginOf(host)`, importing only `deployment.ts`), exported as `@cloudpid/server/view-host` for the sandbox and, later, the main Worker, so the sandbox package depends on the server's and never the reverse (Turborepo refuses a cycle). `appOriginOf` is case-insensitive, accepts only a label `stageLabel` can produce, and reads a label of `prod` as a non-prod stage's (`PROD` is not `prod`; `labelOrigin` in `deployment.ts` builds it). The sandbox never takes the origin from its URL, `Referer` or `document.referrer` (unlike the reference proxy), and the main Worker builds App View URLs from its deploy-time label var, never from the request's `Host` ([How the App sandbox learns a non-prod stage's app origin](https://github.com/ian-pascoe/cloudpid/issues/421) D1.3, D1.4; [Verify the App sandbox on a deployed stage](https://github.com/ian-pascoe/cloudpid/issues/399)).
- **Who deploys it:** only `prod` deploys the sandbox Worker, its route and the wildcard record (the stack checks `stage === "prod"`); every other stage frames prod's sandbox. So the label rule and the mapping change only additively: the sandbox accepts old and new forms until no open preview uses the old one, and a change to the proxy page or the mapping is tried on a deployed stage only once merged. `alchemy dev` serves the proxy page from a second local port, one shared origin for every App View ([How the App sandbox learns a non-prod stage's app origin](https://github.com/ian-pascoe/cloudpid/issues/421) D2).
- **As built, locally ([#482](https://github.com/ian-pascoe/cloudpid/issues/482); `LocalAppSandbox` in `apps/app-sandbox/src/resource.ts`, `LOCAL_SANDBOX_PORT` and `localAppOriginOf` in `apps/server/src/view-host.ts`, the Worker's local mode in `apps/app-sandbox/src/worker.ts`):** under `alchemy dev` the stack declares `LocalAppSandbox`, the same Worker with `dev: { port: 1338, strictPort: true }` and the var `CLOUDPID_APP_SANDBOX_LOCAL` set to `true` (and no route, no record), instead of `AppSandbox`; a deployed stage never has it. Every View there has one origin, `http://127.0.0.1:1338`, on the loopback address rather than `localhost` because cookies are not scoped by port: a View at `localhost:1338` would share the owner's cookie jar with the app at `localhost:1337` and Vite's `localhost:5173`, and `127.0.0.1` is cross-site to both. It has no hostname to tell it the app origin, so the page says it: the frame's URL carries `?host=<the page's origin>`, which the Worker honours only when it is one of `http://localhost:1337` (the app) and `http://localhost:5173` (Vite), and answers 404 otherwise; the page's `<meta name="cloudpid-host-origin">`, `frame-ancestors` and the proxy's checks then follow that origin. The Session's `viewOrigin` gives the local origin when the main Worker's `LOCAL_MODE_VAR` (`alchemy dev`) is set, and the page frames it as it does any sandbox origin. `/proxy.js` is served at the local origin with no `?host=`. The page frames that origin only when it is itself at a local app origin (`isSandboxOrigin(origin, location.origin)`, `location.origin` being in `LOCAL_APP_ORIGINS`; `alchemy dev` serves a production build at `:1337`, so the test is the page's origin, not the build mode): a deployed page never frames a loopback address. The runtime listens on `127.0.0.1`. Both ports are fixed (`strictPort`), so a port that is taken fails the start rather than moving to one the allow-list does not know.
- **What it serves:** only the spec's proxy page at `/` (ported from ext-apps' reference `basic-host` sandbox) and its script at `/proxy.js`, on `GET` and `HEAD`. Any other path gets a 404, any other method a 405 (a host that doesn't parse gets a 404 first). No Access, no secret, no cookie read or set; every response, errors included, sends `Cache-Control: no-store`, `Referrer-Policy: no-referrer` and `X-Content-Type-Options: nosniff` (`headers.ts`).
- **CSP:** sent as an HTTP header built from the `?csp=` query the page puts in the proxy's URL (the header is fixed before the HTML arrives), sanitised, never looser than the server's `_meta.ui.csp`: its declared domains only, and without `ui.csp` only inline script and style and `data:` images, with `connect-src 'none'`; scripts also from `'self'` for `/proxy.js`; nested frames blocked. Any domain naming cloudpid's own hosts is dropped from every list: `ianpascoe.dev` and `ianpascoe.app` and every host under them (prod's app origin, the model proxy, other Views), and any `<name>.ian-g-pascoe.workers.dev` whose name contains `cloudpid-server-` (every non-prod stage's app origin, also behind a version prefix), so each stage's app origin is covered. A wildcard source is dropped whole when it could match one of those (`*.ianpascoe.dev`, `*.workers.dev`, `*.dev`, `*.app`); it is never narrowed. The workers.dev refusal is by name, not by account, so the owner's own MCP servers on that account stay allowed. `frame-ancestors` is exactly the stage's app origin. The App View inherits the header CSP through `document.write` ([Verify the App sandbox on a deployed stage](https://github.com/ian-pascoe/cloudpid/issues/399)).
- **The CSP builder** (`csp.ts`, `buildCsp(csp, frameAncestor)`): `?csp=` is JSON of the spec's `McpUiResourceCsp`; absent, longer than 8 KiB, not JSON or of another shape, it is read as no declaration, never as looser. Each domain must be an origin exactly as declared: `https:` (`wss:` also for `connectDomains`), a host name with an optional leading `*.`, an optional port, and at most a trailing `/`. An entry with a path, query, fragment or credentials is dropped whole, not reduced to its origin (a source with a path allows that path only; its origin would allow the whole host, which is looser than declared), and so is anything else (a scheme-only or `*` source, `http:`, an IPv6 host, `;`, quotes, spaces, a trailing dot). `resourceDomains` go to `script-src`, `style-src`, `img-src`, `font-src` and `media-src`; the policy is `default-src 'none'`, `script-src 'self' 'unsafe-inline'`, `style-src 'unsafe-inline'`, `img-src data:`, `object-src 'none'`, `form-action 'none'`, `base-uri 'none'` and `frame-src 'none'` unless declared, and no `blob:` or `'unsafe-eval'`.
- **Frames:** the page frames the proxy with `sandbox="allow-scripts allow-same-origin"`, and the proxy loads the App View's HTML, sent to it by `postMessage` from the Session page, into an inner iframe on the same origin. The proxy accepts messages only from its parent at the app origin and from its inner frame, and the page only from the App View's origin; both relay nothing else.
- **`_meta.ui.domain`** is shown, never honoured (ADR-0031).
- **Permissions:** only `clipboard-write`, granted with the iframe's `allow` when the App declares it; camera, microphone and geolocation are denied and not advertised, since a grant keys to the top-level origin and would cover every App View (D11).
- **As built, Permissions ([#495](https://github.com/ian-pascoe/cloudpid/issues/495); `apps/web/src/app-view/app-frame.tsx`, `bridge.ts`, `host-context.ts`; the proxy's side is [#482](https://github.com/ian-pascoe/cloudpid/issues/482)'s):** the card reads `_meta.ui.permissions.clipboardWrite` off the page's kept meta and, only when it is declared, does three things: the outer frame gets `allow="clipboard-write"` (a permission reaches the proxy's inner frame only if every frame above it delegates it), the bridge sends `permissions: { clipboardWrite: {} }` in `sandbox-resource-ready` (the proxy then sets the inner frame's `allow` from it, and from nothing else), and `hostCapabilities.sandbox.permissions` says `clipboardWrite`. Nothing else the View declares (`camera`, `microphone`, `geolocation`) is passed on or advertised, and a View that declared none gets no `allow` attribute and no `permissions` in its page. The grant is the browser's own, to the sandbox origin the View runs at: it is a Permissions Policy for one origin, not an ask the owner sees, so it is as wide as the origin (one server's Views), and the card's details do not list it.
- **Proxy script:** served as a plain string (`proxy.ts`), not a module, so a test runs the very text served in a fake window. It runs only framed and only where `window.top` cannot be read (the reference's self-test); takes the app origin once from a `<meta name="cloudpid-host-origin">` in the page (the sandbox's hostname, never `document.referrer`); accepts a message from its parent only at that origin and from its inner frame only at its own, and posts to its parent only at that origin, never `"*"` (its posts to the inner frame use `"*"`, as the reference's: that frame's origin is the proxy's own, and a document being written has no origin to name). The inner frame does not exist until `sandbox-resource-ready` arrives: a frame's `sandbox` flags and permissions policy are fixed when its document is created, so the proxy makes it then, sets the string `sandbox` (else the reference's `allow-scripts allow-same-origin allow-forms`) and, only for `permissions.clipboardWrite`, `allow="clipboard-write"` before appending it, removes any earlier frame first, and loads `html` with `document.write` (the `srcdoc` fallback of the reference).
- **Zone settings:** Web Analytics automatic setup, email obfuscation, server-side excludes, automatic HTTPS rewrites and browser check are off and `security_level` is lowered on `ianpascoe.app`, so nothing is injected into or challenges the proxy page; the apex and `www` parking records are removed. These are the owner's one-time steps ([Verify the App sandbox on a deployed stage](https://github.com/ian-pascoe/cloudpid/issues/399)).
- **Credentials:** `cloudpid-ci-deploy` holds Zone Read, DNS Write and Workers Routes Write on `ianpascoe.app` (`infra/github.ts`); `cloudpid-ci-preview` holds nothing on it ([How the App sandbox learns a non-prod stage's app origin](https://github.com/ian-pascoe/cloudpid/issues/421) D2). The token and zone steps land before the sandbox does, or prod's deploy fails; the order is fixed names, then those steps, then the sandbox ([How the App sandbox learns a non-prod stage's app origin](https://github.com/ian-pascoe/cloudpid/issues/421) D5.2).
- **cloudpid's own CSP:** if cloudpid's pages gain a Content-Security-Policy, it must allow `frame-src https://*.ianpascoe.app` (D17).
- **Visuals:** the sandbox also hosts Visuals, at one origin per Session (a hash of the Session's ID, kept apart from MCP servers' hashes), with no change to the Worker; the frame's URL, the frame-protocol half of the bridge, the style variables, `open-link`, `focus` and `places` move from `apps/web/src/app-view/` into `apps/web/src/sandbox-frame/`, which App Views and Visuals both import ([ADR-0045](../adr/0045-visuals-are-first-party-and-kept-apart-from-mcp-apps-sharing-only-the-app-sandbox-and-the-frames-components.md); [_The frame_](visuals.md#the-frame)). Neither cloudpid's pages nor the sandbox may become cross-origin isolated, and no frame is delegated `cross-origin-isolated`, `local-network` or `loopback-network` ([ADR-0044](../adr/0044-visuals-run-in-the-app-sandbox-one-origin-per-session-with-no-connections-and-resources-only-from-cdnjs-and-google-fonts.md)).

## The bridge

- **Implementation:** cloudpid's own small bridge in `apps/web`, on ext-apps' `spec.types.ts` wire types, with the proxy page ported from the spec's reference host, tested against ext-apps' example Views. ext-apps' `AppBridge` is not used: it would put the MCP SDK and zod in the web bundle beside cloudpid's own MCP core. `@modelcontextprotocol/ext-apps` is a devDependency of `apps/web` only, imported for types only (`import type`), which the import rule's lint allows; nothing of it is bundled (D16; [The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D23; [_Packages and objects_](mcp.md#packages-and-objects)).
- **Protocol:** JSON-RPC over `postMessage`. The proxy announces `sandbox-proxy-ready`, the page sends the HTML (`sandbox-resource-ready`), the App View sends `ui/initialize`, the host answers with its capabilities and `hostContext`, the App View sends `initialized`, and the host sends `tool-input-partial` ([_Lifecycle_](#lifecycle)), `tool-input` once, then `tool-result` or `tool-cancelled`, `host-context-changed` as it changes, and `ui/resource-teardown` before removal. Full method names are ext-apps' `ui/…` and `ui/notifications/…` forms.
- **`hostContext`:** `toolInfo`; `theme` from `prefers-color-scheme`; CSS variables mapped from cloudpid's design tokens as resolved values (unmapped ones omitted); system font stacks; `displayMode` and `availableDisplayModes`; `containerDimensions`; `locale`; `timeZone`; `platform` (`mobile` below `md`); `deviceCapabilities`; `safeAreaInsets` in a sheet (D9).
- **`hostCapabilities`:** `serverTools`, `serverResources` (no `listChanged`), `openLinks`, `logging`, `sandbox { permissions: { clipboardWrite }, csp }`; nothing unimplemented is advertised.
- **App View → host methods:** `tools/call` and `resources/read` ([_An App View's calls_](#an-app-views-calls)), `ping`, `notifications/message` (to telemetry), `ui/open-link`, `ui/message` and `ui/update-model-context` ([_App messages and App context_](#app-messages-and-app-context)), `ui/request-display-mode` and `size-changed`. Any other method answers `-32601`, including the draft-only `ui/download-file`, View sampling, View-initiated teardown and host→View app tools, left for later until a dated revision makes them Stable (D13).
- **`ui/open-link`:** `http(s)` only; a confirmation in the card or App Pane shows the full URL with its host emphasised, with Open (`window.open(url, "_blank", "noopener,noreferrer")`) and "Open in Browser Pane"; dismissing answers `-32000`; a newer request replaces a pending one (D10).
- **As built, `ui/open-link` ([#495](https://github.com/ian-pascoe/cloudpid/issues/495); `apps/web/src/app-view/open-link.ts`, `app-frame.tsx`):** only `http` and `https` URLs with a host and no credentials, at most 4096 characters, are taken (anything else is `-32602`, and nothing is shown). The card then shows a confirmation above the frame with the whole URL as the browser would go to it, the host (with its port) in bold, and Open (`window.open(url, "_blank", "noopener,noreferrer")`), "Open in Browser Pane" (the card opens the Browser Pane and tells its Owner tab to navigate there; offered wherever the card can) and Dismiss (Escape too). Nothing opens before the owner chooses; dismissing answers `-32000`; a newer request replaces the pending one, which is answered `-32000`, as is one that the frame's teardown ends. The bridge advertises `openLinks: {}` for every frame; `message` and `updateModelContext` (each `{ text: {} }`) only for a frame whose Session takes them and whose Session is not archived (an archived Session's View is refused `{ isError: true }` and `-32000` when it sends them anyway), and `sandbox.permissions.clipboardWrite` only when declared.
- **As built ([#482](https://github.com/ian-pascoe/cloudpid/issues/482); `apps/web/src/app-view/bridge.ts`, `host-context.ts`, `page-environment.ts`):** `createBridge` knows nothing of React, the DOM or the socket: the proxy frame's window, the page's message events and the timers are handed to it. A message counts only when its `source` is the proxy frame's window **and** its `origin` is the sandbox origin the frame was pointed at, and every post goes to that origin, never `"*"`; either check alone can be forged by another frame, so a failing message is dropped and reported as `rejected`. Nothing from the View counts before the proxy has been given its page. It answers `ui/initialize` (protocol version `2026-01-26`, `hostInfo`, `hostCapabilities`, `hostContext`), `ping` and `ui/request-display-mode` (a handler of #490's, see App Panes); holds `tool-input`, `tool-result` and the rest until the View's `initialized`, then sends them in order; sends `host-context-changed` with only the keys that differ (`changedContext`; the card sends it, debounced 150 ms, on a theme or width change); fails with "The App did not start within 10 seconds" (or "The App sandbox did not answer…") if `ui/initialize` does not come in 10 s; and `teardown()` posts `ui/resource-teardown` and resolves on the answer or after 2 s. **`hostCapabilities` was `{ sandbox: { csp } }` when the frame has no Session client, and with one added `serverTools`, `serverResources` and `logging` ([#489](https://github.com/ian-pascoe/cloudpid/issues/489))**; [#495](https://github.com/ian-pascoe/cloudpid/issues/495) adds `openLinks`, `message`, `updateModelContext` and the clipboard permission, each only while the frame serves it (see its note below). Every other request answers `-32601` through the **`handlers` seam** (own properties only: a View's `constructor`, `toString` or `__proto__` is no handler), a map of method → handler that overrides the built-ins: [#489](https://github.com/ian-pascoe/cloudpid/issues/489) adds `tools/call` and `resources/read`, [#495](https://github.com/ian-pascoe/cloudpid/issues/495) `ui/open-link`, `ui/message`, `ui/update-model-context` and the clipboard `allow` (built, below), and [#490](https://github.com/ian-pascoe/cloudpid/issues/490) the `ui/request-display-mode` that pops a View out. `hostContext` has the tool (`toolInfo`: the inventory's title and its `inputSchema` when `mcp_app_tools` carries it, at most 2048 characters each and 65,536 for the list, else a bare object schema), the theme, the mapped tokens (16 colors read from the page's resolved custom properties, the radii, weights and font stacks as constants), `displayMode` (`inline` or `fullscreen`) with `availableDisplayModes` `[inline, fullscreen]`, the card's width with a `maxHeight` or an App Pane's `{ width, height }` as `containerDimensions`, locale, time zone, user agent, `platform` and the device's touch and hover; `safeAreaInsets` only in an App Pane on a phone (a sheet's), read from the page's `env(safe-area-inset-*)`. ext-apps is imported for types only (`import type`); nothing of it is bundled.

## An App View's calls

- **Path:** page → Session socket (`mcp_app_request { callId, requestId, method, params }`) → Session DO → `McpHost.request` with `ctx.origin: "app"`, the call's `callId` and conversation → server. The server always comes from the call's App record, never from the App View (D6). The core's `McpCallContext.origin` is `app` ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D7).
- **Allowed:** `tools/call` of a tool whose Tool visibility includes `"app"`, on the App View's own server, whose Exposure is not `hidden`, while the server is enabled; the Session checks, and `McpHost` checks again (`NotAllowed`). `resources/read` likewise on the App View's own server. No Approval and no Harness hooks; results are redacted by the Session and returned raw, not shaped as the model's ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D17). An App View's calls never reach the model.
- **Limits:** ≤4 in flight per App View, 60 a minute; cancelled on teardown; forwarded only while the page is visible, so no background tab keeps a Container awake. A stdio server's calls run in the Container of the call's conversation's Workspace.
- **Sign-in:** a server needing an MCP sign-in fails the call fast, and the card links Sign in ([_Sign-in requests_](mcp-sign-in.md#sign-in-requests)).
- **Audit and telemetry:** one span per call; the App View's `notifications/message` goes to telemetry; the card's details keep an audit log of the last 50 calls and reads (arguments ≤2 KiB, text ≤500 characters).
- **As built ([#489](https://github.com/ian-pascoe/cloudpid/issues/489); `apps/server/src/session/mcp-app-calls.ts` and its store `mcp-apps-store.ts`, `packages/extensions/src/mcp/app-request.ts`, `apps/web/src/app-view/requests.ts`):** the checks run in this order, and the first to fail answers: the page is visible (a socket's `page_visible { visible }`, sent once `hello` says `appViews` and on each `visibilitychange`, is kept in the socket's attachment, and a socket that has not said is not visible, so a hidden tab's request is refused `hidden` and wakes nothing); the limits (4 in flight, 60 a minute, for each socket and call, counted when the request arrives, a refused one too; `limit`); the method (`tools/call` and `resources/read` only, else `-32601`) and its params (an object or none, else `-32602`); the call's kept record (the server is the record's, never the request's; none is `unavailable`); an archived Session (`tools/call` is refused, a read is not; if the Registry cannot say, it counts as archived); the extension's `appRequestOf` (the server enabled and not `hidden`, the tool's Tool visibility including `"app"`); and the host, which checks the visibility again (`NotAllowed`) and the record's `viewHash` against the server's now (`ServerChanged`, as `ctx.viewHash`: an App shadowed by another server's is not called by its old View). A `tools/call` carries `ctx.answers`, `onInput` and `allowTask` ([#498](https://github.com/ian-pascoe/cloudpid/issues/498), below); a `resources/read` carries none of them. The answer is an `McpAppRequestAnswer` through the socket's `result`: the server's result (a `CallToolResult` or `ReadResourceResult`) redacted of the Session's Secrets, or an `error` with the JSON-RPC `code` and `message`, a `reason` (`sign_in` with the `server` and `stepUp`, `hidden`, `limit`, `refused`, `cancelled`, `unavailable`, `failed`), and the audit entry kept. A stream result over 1 MiB is refused (and the stream cancelled); `mcp_app_cancel { callId, requestId }`, the socket closing and the View's teardown cancel the request, and the host's call with it. One span `mcp.app_request` covers a request, with the method, the server, the outcome and its reason, never its arguments. The audit entry (`kind` the method, `summary` from `appAuditSummary`: the arguments ≤2 KiB and the text ≤500 characters, only after redaction) is kept under its own storage key per call, `cloudpid:mcp-app-audit:<callId>`, so a request does not rewrite the call's whole record, and is merged into the record's `audit` when the record is read (last 50, evicted with the record). The web bridge's handlers (`viewRequestHandlers`) hand each request to the client's `appRequest` and map the answer to the View's result or `RpcError`; the frame's abort interrupts it, which sends `mcp_app_cancel`. A `sign_in` error turns the card's badge into "Needs sign-in" with a Sign in link (`/oauth/mcp/start`, a new tab, `stepUp` when the sign-in it has is not enough, back to the Session), as does the server's own state when its chip says so; the details list the audit log. A frame advertises `serverTools` and `serverResources` only when it has a Session's client to serve them (`hostCapabilities(csp, serverCalls)`, which then also says `logging: {}`, since the View's log lines are taken); without one, the bridge answers those methods `-32601` and advertises nothing it does not serve. The details' audit log is the last 50 of the record's entries and the ones since (`auditLog`), the Session's own bound. A request that the connection ends (the socket drops with it in flight) is answered with a `-32603` error that says "Connection lost". **The View's `notifications/message`** goes to the bridge's `logs` option, which cuts it to 2 KiB of text (a level and logger to 128 characters; a message that is not a log line is dropped) and sends it as `mcp_app_log { callId, level, logger?, message }`; the Session drops it for a call with no kept record or past 60 a minute for the View (counted as requests are, on arrival), redacts it of the Secrets held (after the client's own cut to 2 KiB, so a Secret that straddled the cut arrives as a fragment: a guard against an accident, not a hostile View), keeps it to 2 KiB and puts a `warning` or above on an `mcp.app_log` span as an `mcp.app_log` event (level, logger, message; a level the Session does not know is named `unknown`, never the View's text), the same rule as a server's log (`mcp-in-a-session.md`); lower levels are dropped, and nothing reaches the model, a transcript, the audit log or the owner. A Session says in `hello` (`appViews: true`) that it takes `page_visible` and `mcp_app_log`; the web client sends neither to one that does not ([_Deploys_](mcp.md#deploys)). No feature gate or host op was added.
- **Threat model:** an App View gives its server nothing it lacks: credentials stay in the Durable Objects and the Container, and the sandbox reaches nothing of cloudpid's. Injection timing, spoofing inside a card and waking Containers are mitigated by App context's delivery rule, the card's frame and the limits. A Repo's server is treated the same ([ADR-0029](../adr/0029-repo-mcp-servers-run-as-its-scripts-do.md)).

## Server requests from an App View's calls

[_MCP server requests_](mcp-server-requests.md) holds the rules; for an App View's calls, in short:

- **Sampling:** live, the card waiting ≤5 min, withdrawn on teardown, or when the page is hidden while it still waits (a sample the owner approved runs on); a Modern refusal errors the App View's `tools/call` ([_Sampling requests_](mcp-server-requests.md#sampling-requests)).
- **Elicitation:** live, ≤5 min, no Notification, its card in the conversation's waiting area, never inside the App View; withdrawn on teardown but not when the page is hidden; one waiting per App View ([_Elicitation requests_](mcp-server-requests.md#elicitation-requests)).
- **As built ([#498](https://github.com/ian-pascoe/cloudpid/issues/498); `packages/extensions/src/mcp/{app-asking,app-request,task-view,task-view-store}.ts`, `apps/server/src/session/{mcp-app-calls,sockets}.ts`, `apps/web/src/chat/mcp-origin-line.tsx`):** the rules and their code are in [_MCP server requests_](mcp-server-requests.md) → _As built, App View calls_. What is the App's own: its card names "<server>'s app" and is drawn in the waiting area; the Session keeps a page's visibility (the socket's `page_visible`) and a signal a hide aborts, and one elicitation slot for each (socket, call); each question's audit line is a note in the request's summary (`McpAppAuditSummary.notes`, appended in parentheses, never a value); a task's entry in the Session's storage (`mcp-task:app`) is what the sweep cancels a lost request's task by. The agent's own App call that goes on as a task makes its App record when the task ends (_Results_ above).
- **MCP tasks:** declared on an App View's `tools/call` to a Modern server; polled while the request is in flight (the App View is mounted), ≤15 min from the task's creation, then `tasks/cancel`; the task's questions are asked on the same cards and rules as the call's own, and answered with `tasks/update`; never in `mcp_tasks` ([_MCP tasks_](mcp-server-requests.md#mcp-tasks)).

## App messages and App context

- **App message (`ui/message`):** a chip above the composer input, like an Attached page, never written into the textarea; one per App View, at most 3 in a composer, on the composer of the conversation whose App View sent it. Edit moves its text into the input (then it is the owner's), Discard drops it, Send sends the owner's typed text, then the app's as its own part with `app: { callId }` (`submit.app`); the transcript marks it "sent from the <server> app". The App View gets `{}` once the chip is held. It never starts a turn on its own, and is refused in an archived Session (D1).
- **App context (`ui/update-model-context`):** held pending in the Session, the latest per (conversation, call), deduplicated by hash (remounts resend it), ≤4 KB, control characters stripped, held Secrets redacted. Pending contexts are flushed as one `write` (`kind: "cloudpid.mcp-app-context"`, marked untrusted) when input is admitted to the conversation, or at the next boundary while it is busy, one in flight. A collapsed App View's pending context is still delivered, and nothing delivered is withdrawn. A new Context Window does not resend delivered contexts (pending ones flush into it); Fork, Clone and a new Session branch start with none and drop the source's pending ones. The card shows the last context as a chip (D2).

- **As built, App messages ([#495](https://github.com/ian-pascoe/cloudpid/issues/495); `apps/web/src/app-view/app-messages.ts`, `app-frame.tsx`, `app-call.tsx`, `apps/web/src/chat/attachments-state.ts`, `app-message-chips.tsx`, `composer.tsx`; `apps/server/src/session/host.ts`, `sockets.ts`):** the bridge's `ui/message` handler takes a `user` role and text blocks (other kinds of block are left out; no text is `-32602`), cuts the text to 16 KiB and hands it to the composer of the conversation the View is **shown in now**, read when the message arrives (`shownInAtom` in `apps/web/src/app-view/shown-in.ts`): the root's thread when its loaded History holds the model's tool call (the codemode script's call for one nested in it), else the thread of a watched subagent that does. It is not the conversation the call's entry in `mcp_apps` names: a View kept across a move of the active branch is of a call made in a conversation the Session has left, and its message belongs to the branch the owner sees. A call that no loaded thread holds, and one shown in a thread whose composer is not mounted (a subagent's call inline in the root's thread, which has no composer of its own there; an App Pane with no composer of that conversation open), is answered `{ isError: true }`: the composers count themselves mounted (`apps/web/src/chat/composer-mounts.ts`), so a chip is never held where the owner cannot see it. The chip lives in the composer's Attachments state beside pages and resources (`apps`, `addAppMessage`, `removeAppMessage`): one for each View (a newer message of the same call replaces it in place), at most 3 in a composer, a fourth View's is answered `{ isError: true }` and so is any message to an archived Session or to one whose `hello` does not say `appMessages`; a success is `{}`. The chip shows the text as one line (the whole is its tooltip) with "From the <server> app" ("From an app" for a call whose record is gone; `fromApp` in `packages/protocol/src/mcp-apps.ts` is the one phrase the chip, the transcript and `/export` use), and has Edit (the text goes into the input after what is typed, set apart by a blank line, and the chip goes: it is the owner's from then on) and Discard. It is held off the composer while a send is answered and comes back, before any a View sent meanwhile, when the Session refuses. Send sends the owner's text (which may be empty when a chip is held) with `submit.app: [{ callId, text }]`; a client sends it only to a Session that says `appMessages` in `hello`, and refuses locally, with the chips back, to one that does not. The Session names the server from the call's record (`""` when it is gone), cleans and redacts each text, refuses `submit.app` together with a Review ("App messages cannot go with a Review: send or discard them first": a Review's summary is its own message, and a chip is words the owner still has to choose to send, so the two are never one message), and adds it as a text part of its own after the owner's text and the pages' and resources' blocks; the `cloudpid.user` entry keeps `app: [{ callId, server, text }]`, and the transcript drops those parts from the owner's text and shows each as a block "Sent from the <server> app". An App message never starts a turn: it is a chip until the owner sends; branching from such a message gives back what was typed only, not the App's text (a limit). `/export` writes each as "Sent from the <server> app" with its text quoted, and a tool result whose `details.meta.ui.resourceUri` is a `ui://` URI as "App: <server>/<tool> (not rendered)", followed, when the call has a context, by "Last App context (…):" with its text quoted. The parenthesis is from the point of view of the conversation exported: "sent to the model" or "pending, not yet sent" when the context was held for it, and "held for another Session branch" when it was held for another (a context is kept for one conversation at a time, so it is not said to have been sent to a model it was not held for; it says no more than that, since a branch made after a delivery inherits its notice in its History).
- **As built, App context ([#495](https://github.com/ian-pascoe/cloudpid/issues/495); `apps/server/src/session/mcp-app-context.ts`, `packages/extensions/src/mcp/app-context.ts`):** `ui/update-model-context` takes text blocks only (`structuredContent` is not advertised and is ignored; an update with no text clears the View's pending context) and is sent as `mcp_app_context { callId, text, conversationId? }` to a Session that says `appContext` in `hello`, answered `held` (with the context as held) or `refused` with why, which the View hears as `HOST_REFUSED` (`-32000`, `apps/web/src/app-view/bridge.ts`; `ui/open-link` keeps its own `DISMISSED`). `conversationId` is the conversation the page shows the View in when it sends (`shownIn`, as for a message; the root's is the active branch's ID): the Session gives the context to it when it differs from the conversation the call's record names and that conversation's History holds the call (`historyHolds`, `apps/server/src/session/branches.ts`: its entries, which for a branch include those it was forked from, up to 20 pages of them), else to the record's. So a View kept across a move of the active branch speaks to the branch the owner sees, and a page that names a conversation the call was never in speaks to the call's own. **A branch the active branch has left takes no context** (its pending ones were dropped when it was left, so one held now would wait for good and take a slot of its 16): when the page names no conversation (an App Pane) and the call's own conversation is such a branch, the active branch takes it if its History holds the call, and otherwise the context is refused (`refused`, which the View hears as `HOST_REFUSED`); the same when the page names a branch that has been left. Rejected: holding it for the left branch, where it is never read. The History is read only after the call's record and the View's 60-a-minute limit have passed, so a page cannot make the Session scan 10,000 entries by sending contexts; a call not found in the History of a conversation that exists is remembered (a conversation made before a call never holds it), one found stays found, and a conversation that does not exist yet is not remembered. A context is deduplicated by hash **within a conversation**: one a View sends again after the branch moved is held again, pending, for the new one, though the same text was delivered to the old (a limit: a model on the new branch can read it a second time, which the owner is shown as it is a notice). The Session holds it in its own storage keys (`cloudpid:mcp-app-context:<callId>` and an index), outside History and apart from the App record: cleaned of control characters, redacted of the Session's Secrets, cut to 4 KB at a character with "…" when over, and deduplicated by the SHA-256 of what is held (a remount that resends it changes nothing); the latest for a call replaces the last; at most 16 are pending in a conversation, 128 are kept in all, and a View may send 60 a minute (counted when it arrives). **Decisions:** (1) _16 pending in a conversation_: the cap counts distinct calls, so a seventeenth call's context is refused but a call's own update always replaces its last and is never refused for it; a conversation's notice is one block the model reads at the next input, and past 16 Apps' notes it would read more of the Apps' words than of the owner's, and a View that fills it cannot starve the others' updates (rejected: dropping the oldest pending, which would silently lose what an App told the model, and counting each update, which a View updating one context would trip alone). (2) _60 contexts a minute for each View_: a View posts on every selection change, so the limit stops a runaway page from rewriting storage and filling the 16 slots with churn, as 60 a minute does for its requests ([_An App View's calls_](#an-app-views-calls)); the same bound for both keeps one number to remember (rejected: a lower one, which a lively but honest View would hit while the owner drags a slider). (3) _App messages refused with a Review_: see the send above. **Delivery:** when input is admitted to the conversation (`admitDraft`, before the input is written, and not again for a re-sent request), every pending context of it is written as one `write` of kind `cloudpid.mcp-app-context` whose text is an `<mcp_app_context>` block that says, first, that what follows is untrusted notes written by the Apps' servers and never the owner's words, then one `<app server tool>` element each, escaped so none can close the block; a transcript notice "App context" (`untrusted: true`) shows it. While the conversation is busy (a Run is going), a context that arrives is written at once and placed by pi-durable at the next boundary, one write in flight at a time, the rest following when it is placed; while it is idle it stays pending, never starting a Run, a Container or a wake. A collapsed or unmounted View's pending context is delivered all the same, and nothing delivered is withdrawn or resent into a new Context Window. Fork, Clone and a new branch carry none and drop the source's pending ones (the branch left and a deleted subagent drop theirs). The record the card reads (`McpAppEntry.context`: text, hash, time, whether delivered) makes the chip "Told the model: <line>" with "Pending" or "Sent to the model", on the card and on the collapsed row.

## Socket messages

Additive, with no protocol break; old tabs skip unknown messages (`Schema.decodeOption`) (D14):

- **Client → Session:** `mcp_app_mount { callId }` (the record's replay), `mcp_app_html { hash }`, `mcp_app_request { callId, requestId, method, params }`, `mcp_app_cancel`, `mcp_app_log`, `page_visible`, `mcp_app_context`, and `submit.app` on a submission.
- **Session → client:** `mcp_apps`, per conversation on `watch` (as `todos`); `mcp_app_tools`, after `hello` and on an inventory change.
- **As built ([#473](https://github.com/ian-pascoe/cloudpid/issues/473); `McpAppMount` and `McpAppHtml` in `packages/protocol/src/session.ts`, `McpAppsMessage` and `McpAppToolsMessage` in `mcp-apps.ts`, the handlers in `apps/server/src/session/sockets.ts`):** `mcp_app_mount { id, callId }` and `mcp_app_html { id, hash }` are answered through the socket's `id`/`result` reply, with an `McpAppMounted` or an `McpAppHtmlAnswer` (`status` `html`, `missing`, `unsupported` or `failed`) as the result, so there are no new reply messages. A page is served only for a hash some record pins, through the host's `ui/html` for that record's server, and only when the host lists `app_html`. `mcp_apps { conversationId, apps }` follows the first events of a `watch` and comes again each time a record is kept, evicted or copied (an `McpAppEntry` has the call's identity, its state `kept` or `evicted` and its hash, never its data); `mcp_app_tools { tools }` is sent after `hello` on every connect, an empty list too, and to every client when the inventory's App tools change. The web client keeps both (below). [#489](https://github.com/ian-pascoe/cloudpid/issues/489) adds `mcp_app_request`, `mcp_app_cancel`, `mcp_app_log` and `page_visible` ([_An App View's calls_](#an-app-views-calls)); `mcp_app_context` and `submit.app` are [#495](https://github.com/ian-pascoe/cloudpid/issues/495)'s (below).
- **As built ([#495](https://github.com/ian-pascoe/cloudpid/issues/495); `McpAppContextCommand` and `Submit.app` in `packages/protocol/src/session.ts`, `McpAppContextAnswer`, `AppMessageRef` and `SentAppMessage` in `mcp-apps.ts`, `apps/web/src/session/client.ts`):** `mcp_app_context { id, callId, text, conversationId? }` (text at most 64 KiB before the Session cuts it; `conversationId` the conversation the page shows the View in, optional so that a client from before, and a call no loaded thread holds, send none and the context goes to the call's own) is answered through the socket's `id`/`result` reply with an `McpAppContextAnswer` (`held` with the context as held, or `refused` with a `message`); `Submit.app` is an array of at most 3 `{ callId, text }`. `hello` gains `appMessages` (the Session takes `submit.app`) and `appContext` (it takes `mcp_app_context`); the client sends neither to a Session that does not say so (a `submit` with `app` is refused locally, with the chips given back, and `appContext` answers `refused` with nothing sent), and decides again at each `hello` ([_Deploys_](mcp.md#deploys)). `mcp_apps` entries may carry `context` (the last context and whether it was delivered). `TranscriptMessage.app` and the `cloudpid.user` entry's `app` carry what a sent message had from Apps.
- **As built ([#482](https://github.com/ian-pascoe/cloudpid/issues/482); `McpAppHtml` in `packages/protocol/src/session.ts`, `pageOf` in `apps/server/src/session/mcp-apps-store.ts`, `apps/web/src/session/client.ts`):** `mcp_app_html` is now `{ id, hash?, callId? }`, at least one of them. **By `callId`** the Session reads the call's record, uses the hash the record pins and, when the record has none or the host no longer keeps that page, reads the page by the URI the tool declared (the host's `ui/html { uri }`) and pins the new hash into the record; the page is always of a server the Session's own record names, so a client cannot ask for another server's page, and so cannot name another server's origin. The web client sends the call; `hash` alone stays for a client that already has one. A page answers with `view` (the 26 characters the host named the server's origin by, `McpHostAppHtml.viewHash`, an optional field a host that predates it leaves out) and `origin`, which the Session builds from that and its deploy-time label (`viewOrigin`, from `CLOUDPID_STAGE_LABEL`, or the local sandbox's in `alchemy dev`); a page whose `view` is not the `viewHash` its record pinned is answered `{ status: "unavailable" }` (the server has been shadowed), pinning nothing; with no `viewHash` there is no origin, and the page fails to load ("App couldn't load", Retry) rather than guess one. The web `SessionState` keeps `mcpAppTools` (null until the Session says) and `mcpApps` by conversation, each message replacing the last, and has the commands `mountApp(callId)` and `appPage(callId)`. The two messages are read from every conversation, but a card asks by its own call ID, so a subagent's call mounts the same way ([#490](https://github.com/ian-pascoe/cloudpid/issues/490) decides where it shows).

- **As built ([#496](https://github.com/ian-pascoe/cloudpid/issues/496); `McpAppHtml` in `packages/protocol/src/session.ts`, `pageOfTool` in `apps/server/src/session/mcp-apps-store.ts`, `appToolPage` in `apps/web/src/session/client.ts`):** `mcp_app_html` gained `tool?`, the model-facing name of an App tool of the inventory, for the page of a call that is still running and has no record: the Session reads the `ui://` resource the tool declares, through the host's `ui/html { uri }`, answers it with the origin as for a record's, and pins nothing; `callId` is then the running call's, for the host's log. A tool the inventory does not list as an App's is `missing`. The edge only gains: a Session from before it ignores `tool` and, finding a `callId` of no record, answers `missing`, which the page reads as "no View yet" and mounts the View when the call has finished; a client from before it never sends `tool`.
