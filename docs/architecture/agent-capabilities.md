## Tool discovery

The model is offered a small set of tools; every other tool is _deferred_ (`GLOSSARY.md` → Offered tool, Deferred tool), the exposure of the owner's local pi (codemode first, a small offered set).

- **`tool_search`** is pi-durable's tool (`@earendil-works/pi-durable/tool-search`): BM25 over the names, descriptions, and parameters of the conversation's deferred tools, whose matches are loaded with `control.addTools`. That writes the conversation's `modelTools`, so loaded tools stay offered on that branch, also after a compaction. It is not callable from scripts, which have `searchTools()`.
- **The offered set** is the settings' `tools.offered`: tool names or patterns (`*` matches any run of characters), snake_case, edited in Global's Tools section of the Settings page (an entry that is not one is refused, and a saved list with a bad entry is dropped whole, with the other overrides kept). The default is `read`, `write`, `edit`, `bash`, `ls`, `find`, `grep`, `codemode`, `tool_search`, the context tools (`context_notes`, `context_history`, `context_rollover`), and `secret_ask`. The first nine are the owner's local default tools (pi's own `read`, `bash`, `edit`, `write`, and `defaultTools`: `codemode`, `find`, `grep`, `ls`, `tool_search`; `fffind` and `ffgrep` are not ported). The context tools stay offered because Rollover depends on them (the Rollover request tells the model to call `context_rollover`). `secret_ask` stays offered because the `secrets` prompt section, which tells the model to call it instead of asking the owner to paste a credential, is gated on the secret tools; that section is also rendered while they are all deferred (with a line to load them), so the guidance never depends on a search. `tool_search` and `context_rollover` are offered whatever the settings say: without the first the model cannot reach a deferred tool, and without the second the compaction hook finds no `context_rollover` and silently falls back to pi-durable's own compaction. The order of `tools.offered` does not matter: the tools keep registry order, followed by the ones loaded.
- **Deferred by default:** `web_search`, `web_fetch`, `browser`, `browser_handoff`, `secret_list`, `secret_forget`, `todo`, `container_restart`, `container_resize`, `skill_search`, the six subagent tools (`subagent`, `agent_message`, `subagent_wait`, `subagent_status`, `subagent_cancel`, `subagent_delete`), and the `environment_*` tools, and so any tool a later extension adds. A prompt section gated on its tool being offered is hidden until the tool is loaded: `subagent_roles` (the role hints, shown once `subagent` is loaded) and `todo`'s guideline; the `deferred_tools` section names the tools, so the model knows to search.
- **Mechanism:** the `tool-search` extension (`@cloudpid/extensions/tool-search`) wraps every tool of the other extensions (`wraps`) and sets `deferred` when its offered set does not name the tool. Wraps are pure, as pi-durable requires, so the extension is built from one offered set, and when the Session reads settings that changed it (`SessionHostOptions.reload`) it installs the extension again over the earlier one ("an extension is the unit of reload"): pi-durable applies that to the next phase it starts, never to one under way. A model's tool call spans two phases (the generation, then the call), so a read that lands between them can defer a tool the request offered: that call fails as unavailable, which is rare, and the model can load the tool with `tool_search` and call it again. A change reaches the next request of every conversation, new and idle ones as the other settings do, and a tool that was loaded stays offered. The `deferred_tools` prompt section names every tool the settings defer, in name order, loaded or not, so loading a tool does not change it and the provider's prompt cache keeps hitting; it is left out for an agent that has no `tool_search`. Up to 40 are named on one line; past that, a line per family of two or more tools of one prefix (`- environment_*: environment_get, …`, the prefix being the name up to its first `_`), then the tools alone in theirs on a last line (`- others: …`).
- **Scripts:** a deferred tool is still enabled, so nested calls resolve it and `codemode` scripts call it without loading it; its `tools.<name>` declaration is not in the `codemode` section's inline list, and scripts find it with `searchTools()`, `describeTool()`, and `describeNamespace()`.

## Values for programs

A `codemode` script gets the value of each tool it calls (a nested call). A tool that declares `structuredOutputSchema` returns a `structuredOutput` matching it on every result that is not an error, which pi-durable checks (a nested call whose value breaks the schema becomes an error, and a model-issued call's is reported to the host as a broken tool), and its `tools.<name>` declaration shows the value's type; a tool that declares none gives the script its model-facing text as a string, cut to the usual text limits. The text the model reads and the `details` the UI reads are the same either way: the value is a third channel, built from the same data as the text, never parsed from it.

- **Tools that give a value:** every tool a script can call whose result is data or an outcome. The reads give their data: `environment_list` and `environment_get` (an Environment's or Global's settings, each marked own or inherited, its variables, Secret names, Skills and Build), `settings_get` (each setting with where it is set), `secret_list` (names, Scopes and expiries, never values), `browser_owner_tabs`, `skill_search`, `ls`, `find` and `grep` (cloudpid's own wrappers: exactly the entries the text shows, as items, with the text's limit flags), and `context_notes`, `context_history`, `todo`, `web_search` and `web_fetch`. The changes give their outcome: every `environment_*` and `settings_*` tool, `container_restart`, `container_resize`, `secret_ask`, `secret_forget`, `browser_handoff`, and the six coordinator tools (see [_Subagents_](#subagents)). pi-durable's `bash` declares its own.
- **Tools that give text:** pi-durable's `read`, `write` and `edit` (`read`'s text is the file, and the other two only report success), and `browser`, whose result is what the caller's own code returned or printed, so the script already controls its shape. `codemode`, `tool_search` and `context_rollover` are not callable from scripts.
- **Shapes:** keys are snake_case, "none" is null rather than a missing key, and each field carries a description. What tools share is in one module (`@cloudpid/extensions`' `outputs.ts`): an Environment or Global as `{ id, name }` (id `*` for Global), an Agent change (`id`, `field`, `before`, `after`, and whether either was inherited), and the outcome of a change, `{ scope, changes, unchanged, approval }`, which every Environment and Settings change tool gives (an unchanged call lists its field in `unchanged`), with whom a Container setting change reached (`own`, `new_build`, and for a change at Global the Environments that override it and those whose Build was asked for). `approval` is the owner's answer for a change that waits for their Approval (`{ approved, reason }`, the reason null unless they declined with one; a declined change lists no changes), and null for a change that does not wait for it, or that asked no one because the target already had the value. An area's own shapes are in its module (`environment-outputs.ts`, `environment-lifecycle-outputs.ts`, `settings-outputs.ts`, `secrets/outputs.ts`, `browser/outputs.ts`, `subagents/outputs.ts`).
- **Bounds:** a nested call's value is stored in one row, and `ResultBounds` turns one over 1.5 MiB into an error (see [_The rest of one tool result_](workspace.md)), so a tool cuts its own value well under that: each list that can grow keeps its first items within a bound counted as stored, and each text without a bound is cut, each with a `<field>_truncated` flag. The bound is 256 KiB (`MAX_PART_BYTES`) for a value with one or two such parts, and smaller for one with more (`environment_get`, `settings_get`, `environment_skill_install`, `environment_skill_update`), so that a value stays under 1 MiB at its worst; an Agent change's `before` or `after` over 128 KiB is null with `before_truncated` / `after_truncated`. `ls`, `find` and `grep` also keep `truncated`, the text's own 50 KB cut, apart from `structured_truncated`, their value's.
- **Secrets:** the Secrets extension's `afterTool` redaction walks the whole result, the value included, before pi-durable checks it, so a Secret a tool's value holds reaches the script as its reference, as in the text.

## Subagents

The tool surface and semantics stay as they are today:

- Canonical IDs such as `agent-1` and `agent-1.reviewer` (a leading `root.` is accepted; `root` and `parent` are reserved), plus tombstones and a depth cap. A deleted agent's ID is free again: a spawn that names it starts a new, unrelated agent, while an automatic `agent-<n>` never names a deleted one ([ADR-0039](../adr/0039-deleted-subagent-ids-are-reusable.md)).
- Model roles.
- `read`/`modify` toolset presets under a capability ceiling.
- `session_context`: `omit`, `inherit` (the parent's conversation quoted before the task), or `compact` (a summary of it, made by the `small` role's model, or the child's own when no `small` role is configured).
- Wait events: `turn`, `message`, `timeout`, and `steered`. One open wait per caller and child; a second is refused.

They are rebuilt on pi-durable primitives, following its example 23 (`@cloudpid/extensions/subagents`):

- Children are conversations owned by a background anchor task.
- Each input to a child is a turn, carried by a background reporter task in its parent's conversation. A Session document records the agents, their recent turns, tombstones, and open waits, and one commit decides each delivery.
- **Deleted IDs** ([ADR-0039](../adr/0039-deleted-subagent-ids-are-reusable.md)). A delete tombstones each ID and keeps, by ID, what it leaves a later agent of that ID (`SubagentsState.freed`): where its turn numbering goes on, so a turn ID never names two turns of one ID, and its Subagent Workspace. A spawn that takes the ID again removes that Workspace first, since the Registry answers a Subagent Workspace by Session and subagent ID, and is refused, naming it, while it cannot be removed; its commit drops the tombstone and the `freed` entry (`takeId`). An ID tombstoned before IDs were freed has no entry and stays retired. What could mistake the new agent for the old checks the agent's identity rather than its ID (`runs`: the agent still runs the conversation that was read): each tool decides only while its calling conversation still runs the caller (`decide`); a wait, message or delete decides only while its target does, and a cancel or delete stops nothing once it does not (`stopSubtree`); the owner's Stop all stops nothing more once its agent is deleted, and its delete deletes only the agent it read (`deleteAgent`); and a reporter delivers and settles only the turn whose `reporter` is its own task.
- A settled turn's answer goes to a `subagent_wait` blocked on it. Otherwise it is held (`delivery: "pending"`) until the parent is idle, so a later `subagent_wait` in the parent's run can still claim it, and then reported as a follow-up, deduplicated by `requestId`. The rule is the same for every parent: the root gets the report as follow-up input, and a parent that is itself a subagent gets it as a new turn, whose answer is reported further up. Inputs steered into one run end in one answer, which is delivered once; the other turns are `duplicate`.
- **Stop.** Stop aborts one conversation, never the agents below it: a subagent's work is background work (its anchor is a background task), so the root's Stop leaves it running, and it reports as usual. **Stop all** (`abort` with `subagents: true`, offered beside Stop while a subagent or background task is live, or while the run goes on with any subagent below it (an idle one can have a report held for that run), and in the Subagents Pane) aborts the conversation and every subagent below it with `background: true`, which also aborts their reporters, so the reports held for the parent are dropped (`delivery: "none"`) and nothing starts a new run. A report that is already held when a plain Stop lands is still delivered once the root is idle, which starts a new run: pi-minimal-subagents holds it until the next run, but a reporter that waits for a run that may never come would stay live (and keep the Session's alarm armed) indefinitely, so the rule stays one for every parent, and Stop all is how the owner silences everything.
- **The owner and a subagent.** The owner may submit to and abort a live subagent's conversation from its thread. The Session checks that the conversation is the root's or a live subagent's (the Subagents document maps it; a deleted agent's conversation, or any other, is refused). Input to a subagent is a plain user message: `whenBusy: "steer"` joins its run at the next boundary, `"followUp"` waits for its next run, as for the root. It is not a turn: nothing waits on its answer, so the answer is not reported to the parent, and the parent's `subagent_wait` and reports are untouched. An input the owner steers into a run that also carries a turn of the parent ends in one answer, which the turn reports as usual. Aborting a subagent ends its running turn `aborted` (nothing reported), and keeps the agent for more input.
- **To programs.** Each coordinator tool declares its structured output (`structuredOutputSchema`, `subagents/outputs.ts`; see [_Values for programs_](#values-for-programs)), so a `codemode` script that calls one gets the value, which pi-durable checks against it, rather than an error (pi-durable fails a nested call whose tool returns structured output without a schema). A child's answer in it (`subagent_wait`'s `output`, `subagent_status`'s `latest_output`) is cut to 1 MiB stored, with `output_truncated` / `latest_output_truncated`, so it fits one nested call's result (see [_The rest of one tool result_](workspace.md)).
- `subagent_wait` is a durable task that waits in its phase, watching the Subagents document and the caller's inbox, until its deadline, which a timer of its invocation marks (`TaskRuntime.setTimer`, armed again for what is left when the phase runs again): a durable sleep (`sleepUntil`) holds no invocation, so it could not watch. A rerun of the call after an eviction finds it.
- A child's tools are exactly its grant (`AgentState.tools`): ordinary tools within its caller's, never `context_rollover` (a Handoff would end the child's run without the turn's answer), plus all six coordinator tools when it was launched with `delegation: "fanout"` below the depth cap, or only `agent_message` otherwise.
- The roles come from the settings' `roles`; the depth cap, the Subagent Workspace limit and toolsets from `extensions.subagents` (`maxSubagentDepth`, default 2; `maxSubagentWorkspaces`, default 1; `baseToolset`, `readToolset`, `modifyToolset`).
- **Subagent Workspaces** (GLOSSARY.md; [ADR-0021](../adr/0021-subagents-in-workspaces-of-their-own.md)). `subagent` takes `workspace: "shared" | "new"` (default `"shared"`: the child works in its spawner's Workspace). With `"new"` it also takes `base` (the remote branch to start from; default the spawner's Workspace's branch) and `branch` (the child's own; default `cloudpid/<id>`; one that is not the agent's to take, `ownBranchProblem`, is refused), which are refused without it. The Session's `SubagentWorkspaces` (`apps/server/src/session/subagent-workspaces.ts`) asks the Registry DO's `createSubagentWorkspace` for one before the spawn commits: a Workspace of the Session's Environment recorded as the Session's and the subagent's (`workspaces.session`, `workspaces.subagent`, migration 19), made as `createSession`'s new Workspace is (the Environment's spare when it has one, with the branch then checked out over it from `base` and no new spare made behind it, else a Workspace readied from the Build; an Environment with no Repos gets one too, a Container of its own), and idempotent by Session and subagent, so a spawn an eviction cut off gets the same one. The Build upkeep follows (`builds.of`), but not the spare's: no new spare is made behind it (see [_Spare Workspace_](workspace.md)). It is refused for a Session the Registry does not list, for a branch another Workspace of the Environment is on, and past the **Subagent Workspace limit** (`extensions.subagents.maxSubagentWorkspaces`, default 1: the Subagent Workspaces that exist in the Session, counted in the same transaction), whose refusal names the limit and points to `subagent_delete` and `settings_subagent_workspaces_set`. A host without `SubagentWorkspaces` refuses `"new"`. The spawn result names the child's Workspace and branch, and warns, reading the spawner's Workspace's clones (see _Reading unpushed work_ below; no fetch), of uncommitted changes, commits on `base` that no remote branch has, and a `base` the remote lacks: they do not reach the child, since the hand-over is a pushed branch and nothing is copied across. The child's first input starts with where it works and that its parent sees its work only through the remote (`workspacePreamble`), and to push its branch.
  - **Placement per conversation.** The agent's record in the Subagents document keeps its Workspace (`AgentRecord.workspace`: id, branch, Workspace DO object name, directory), so it survives an eviction. Every tool a conversation runs uses its conversation's Workspace (`conversationWorkspace`: its agent's own, else its nearest ancestor's, else the Session's): the Session's `env` (files, shell, skills and project instructions, `cwd`), the composer's lookups (`lookupEnv`), `ls`/`find`/`grep` (`WorkspaceFiles`, a function of the calling conversation) and `container_restart`/`container_resize` (`WorkspaceContainer`, given the conversation), so a child's restart or resize stops only its own Container. A child started `"shared"` by a child with a Subagent Workspace shares that one. The Session readies a Subagent Workspace as it readies its own (`workspaceReadiness`, each Workspace counted apart): its settings, Build and Secrets handed over, its Repos cloned on its branch; a refresh of the kept Secrets is handed to every one of them too. The parent never reads or runs anything in a child's Workspace.
  - **Handing back.** Each report the parent gets of a child with a Subagent Workspace (a `subagent_wait` result or a follow-up) ends with a line read from the child's Workspace (_Reading unpushed work_) in the reporter's deliver phase, before its commit: `[Subagent Workspace <id> | branch <b> | everything is committed and pushed]`, or what is not (`app: 2 commits not pushed, 1 uncommitted change`), or that it could not be read. A clone that is missing or has another branch than the Workspace's checked out (a set-up that never switched a spare's clone, `cloudpid/spare`, to it) is never called clean: it reads `app: not set up (on cloudpid/spare, not cloudpid/<id>)` or `app: not set up (no clone)` (`unsettledClone`; `workStateScript` reports each clone's checked-out branch, and a Repo it printed nothing for counts as not cloned). It is kept on the turn (`Turn.handBack`).
  - **Reading unpushed work** (`workState` on the Workspace DO; `WorkspaceWorkStateModule`, `apps/server/src/workspace/work-state.ts`) answers as `workStateScript` (`apps/sandbox-image/src/workspaces.ts`) does on the Container: per Repo, whether it is cloned, its checked-out branch, its `git status --porcelain` line count, the commits of the branch no `refs/remotes/*` ref has (`rev-list --count <branch> --not --remotes`), and whether `origin` has the branch. While the Container runs, its git reads every Repo, as it sees what is not synced yet. While it is stopped, the Workspace DO reads each clone itself with isomorphic-git ([ADR-0022](../adr/0022-diffs-come-from-the-workspace-do.md)), over the files the last sync left, and starts no Container: `statusMatrix({ refresh: false })` counted as git's lines (an untracked file in a directory with no tracked file below it is that directory's one line; a file the index lost but the tree has is two), and a walk of the commits newest first by committer date that stops once nothing left is reached from the branch alone and all of it is older than every commit counted, as git's walk does. A Repo it cannot read as git would goes to the Container's git, starting it, and the log says why (`work state: …`): the Changes' guard (`needsContainer`: root `.gitattributes` rules git applies, a pack over 16 MB, more than 2,000 tracked files), submodules, a `.git` that is not a directory, a repo setting that changes what `status` lists (`status.showUntrackedFiles` other than `normal`, `core.sparseCheckout`), a tracked file on a Container-only path, staged deletions beside staged additions (which git may pair as renames), a walk past 10,000 commits (`MAX_WALKED_COMMITS`), or isomorphic-git failing. It does not see untracked files on Container-only paths that the repo does not ignore (those paths hold dependencies and build output, which repos ignore), a global `core.excludesFile`, or skip-worktree bits. `subagent_status` shows each agent's branch and Workspace, and the task graph's agents carry the branch (`GraphAgent.branch`), which a subagent's card, its row in the Subagents Pane and its Subagent Pane's header show.
  - **Lifetime.** A Subagent Workspace lasts as long as its subagent. `subagent_cancel` keeps it, and its Container idle-stops as usual. `subagent_delete` removes it (Workspace removal: its object, then its record) and refuses, naming each, while one in the deleted subtree has uncommitted changes or unpushed commits, a clone not set up on its branch, or could not be read, unless `discard: true`; a Workspace that could not be removed is named in the result, left in the Workspaces section of the Settings page, until a spawn that takes its agent's ID removes it (_Deleted IDs_ above). The delete records what it took out with its commit and is `replay: "safe"`, so a rerun after an eviction past the commit removes the Workspaces still there. A spawn whose commit did not land (refused, say because another spawn took its ID meanwhile) removes the Workspace made for it, unless an agent's record has it. Deleting the Session removes all of them (`removals`' `deleteSession`: the Session's object, then each Subagent Workspace, then its record). The owner's _Remove_ of one in the Workspaces section runs `removeWorkspace`, which asks the Session to delete its subagent as `subagent_delete` with `discard: true` does (`deleteSubagent`, through `deleteAgent` of `@cloudpid/extensions/subagents`), after a confirmation that names the unpushed work (`workspaceWork`), its own and that of the Subagent Workspaces of the subagents below it; one whose Session or subagent is gone, or whose subagent does not work in it, is removed on its own. A Subagent Workspace takes no new Session (`createSession` refuses it).
  - A child runs at the Environment's size and can `container_resize` itself up to `maxInstance`. Out of scope: copying uncommitted or unpushed work into the child, Files, Changes or Terminal panes for a child's Workspace, a smaller default size for children, and the owner starting a subagent in a new Workspace from the UI.
- **A child's offered tools** (what its model is offered; the rest of its grant is deferred) are not the root's loaded set. A child given a preset or an exact list is offered every tool of it, deferred or not, because the spawner or the owner's toolset settings named them (`todo`, in the default `baseToolset`, is offered to every such child); its coordinator tools are always offered. A child that inherits its caller's tools (`tools` omitted) is offered what the settings offer every conversation among them and has `tool_search`, which it inherits, for the rest; when the grant has no `tool_search` (the caller is a preset child), nothing could load a deferred tool, so the whole grant is offered and the `deferred_tools` section is left out. Tools loaded by the parent do not carry over.

## Context management

pi-context-management's `context_notes`, `context_history`, and `context_rollover` (`@cloudpid/extensions/context`), with its parameters and limits:

- **Notes** are a conversation document (`defineDoc`, `fork: "current"`), which also keeps the last saved Handoff. A Handoff does not touch documents, so Notes outlive it.
- **History** reads entries from storage, also those before a Handoff or compaction; Context Windows start at each head marker (`pi.reset`, `pi.compaction`). Lineage scope covers the conversations of the agent's ancestors and descendants in the Session's subagents document; references are `context:<conversationId>:<entryId>` and `context:<conversationId>:note:<name>`.
- `context_rollover` must be the only call of its round and is not callable from scripts. It returns `control: { handoff }` with the Handoff and a Note Index; pi-durable applies it after the whole round, so the Handoff never splits a tool batch. It also queues a follow-up, so the task continues in the new context, unless the run's only inputs are Rollover requests, as when one is placed after the task's final answer: then the run stops at the Handoff.
- A `CompactionTask` `beforeCompact` hook, in conversations that offer `context_rollover`, turns a background threshold compaction (`backgroundTokens` below the blocking threshold) into a prepare-then-rollover turn: it declines, which blocks nothing, and while a run is live steers a Rollover request into it, once per Context Window. A blocking threshold compaction and an overflow compaction are the Emergency Rollover, because declining a blocking one would send a request without pi-durable's overflow recovery: the summary is the last saved Handoff and the Note Index, on pi-durable's cut, which keeps tool calls with their results. With `backgroundTokens: 0` every Rollover is an Emergency Rollover. A manual compaction keeps pi-durable's summary.
- The transcript shows Handoffs, compaction summaries, and Rollover requests as notices; an extension's input entry asks for a notice with a `notice` title in its data. A Rollover or a compaction does not take the earlier Context Windows off the transcript: what a client watched stays above the notice, and a snapshot that starts with a head marker leaves out the History before the marker's head, which the top of the thread offers as "Show earlier messages", a `history` page at a time (see [_Client and protocol_](client-and-protocol.md)).
- The owner's `/rollover [focus]` steers the Rollover request into the conversation, with the focus (at most 2,000 characters) appended as Handoff-only instructions, as local pi-context-management's command does; its request ID marks it as a Rollover request, so one made while idle stops at the Handoff. `/compact [focus]` is pi-durable's manual compaction, the focus as the summary's additional focus. Both are Session Slash commands (see [_Client and protocol_](client-and-protocol.md) → Slash commands).
- Not ported: Idle Rollover, the `/context` command, and the Rollover Tail (`tailTokens`): a Handoff starts the context from the Handoff alone.

## Todo

pi-todo's `todo` tool (`@cloudpid/extensions/todo`): `list`, `add`, `update`, `remove`, `clear`, its parameters, and its structured output (`structuredOutputSchema`, so a script's `todo` call returns `{ action, tasks | task | id | cleared }`). The owner's `/todo clear` is a Session Slash command (see [_Client and protocol_](client-and-protocol.md) → Slash commands) that clears the list as the tool's `clear` does. Not ported: the TUI widget and renderers, and the troubleshooting Skill.

- The list is a conversation document (`defineDoc`, `fork: "current"`): `nextId`, a `rev` that counts its changes, and the Todo Items (the tool, the document and the socket call them "Tasks", as pi-todo does; background tasks are another thing). Every conversation has its own, a subagent's included (`todo` is in the default `baseToolset`, so a child has it whatever preset it was given), and a Handoff or compaction does not touch it. A call reads and changes it in one commit, so a batch `add` or `update` with one bad entry (an empty title, an unknown or repeated ID) changes nothing and spends no ID. The list holds at most 200 Todo Items, 300 characters of title and 2,000 of description each, and 20,000 characters and 500 lines in all as the model reads it, because every result shows the whole list (pi-durable keeps at most 50 KB and 2,000 lines of a result) and every watching client is sent it whole. The tool accepts `null` for a field the model leaves out, as pi-todo's `acceptNullForOptionalArguments` does.
- Each result's text ends with the whole list, and its `details.todoRev` is the `rev` it shows. pi-todo keeps hidden snapshots among the messages, each at a fixed place with fixed text, so the provider's prompt cache (a breakpoint on the last message) keeps hitting; here the context needs the list back in three cases, each handled at a place that does not move or, for the last, at the end of the request:
  - A script's nested `todo` calls leave no result in the context. The document remembers the call (`changedBy`) and a `ToolTask` `afterTool` hook appends the list to that call's result, with `details.todoRev`, so it is committed with the result. It does so only when the result and the list fit pi-durable's limits (which keep the head of a result, after the hook); a result too long to show the list whole does not claim to, and the third case applies.
  - A Handoff or compaction took the `todo` results out. A `GenerationTask` `beforeRequest` hook finds that the Context Window holds no `todo` result and puts the list at the end of the window's first message (the Handoff or summary, which is a user message, so no user message follows another), after a header saying it is the extension's note. The window is told by that message's timestamp, and the text is recorded in the document (`shown`) at the window's first request, so every later request of the window sends the same bytes however the list changes in between. A recorded text is never rewritten, and a window that holds a `todo` result gets none. It asks the agent to reconcile unfinished Todo Items when the context holds no `todo` result at all, and sends nothing for a list that was never used.
  - The list changed and no result in the window shows it (the last `todoRev` in the request, or the recorded text's, is not the document's `rev`): a Stop during a script after its nested call, an interrupted call, parallel scripts whose results finish out of order, a result too long for the list. Rare, so the request gets a short note at the end of its last message, asking the model to call `todo` with `action: "list"`; nothing before it changes, so the prompt cache keeps its prefix, and the note goes when the model calls `todo`, as that result shows the list.
    Known limitation: `fork: "current"` gives a fork the source's latest list, not the list as of the fork point as pi-todo's branch-following snapshots do. A fork's context may then be behind the list or ahead of it; the note above covers the first case. A Session branch is such a fork (see [_Session tree_](client-and-protocol.md)), and so is what a Fork or Clone copies: both take the list as it is when they are made.
    A `todo` section holds the tool's guideline.
- The web app shows the list live: `watch` of a conversation also streams `todos` messages (see [_Client and protocol_](client-and-protocol.md)), which the Session details over the chat show for the root (see [_Pane area_](client-and-protocol.md)) and a subagent's thread for that subagent.

## Secrets

| Kind        | Holds                                                                                                                                                               | Storage and use                                                                                                                                                                                                                                                                                        |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Deploy-time | Commissary API key for the model proxy, 1Password service-account token (v2), VAPID keys. In v1 also the GitHub App's ID and private key and the Exa/Parallel keys. | Read with `Config.Redacted` in `infra/` and bound as Worker secrets                                                                                                                                                                                                                                    |
| Runtime     | Values entered through `secret_ask`, which opens a masked form in the UI                                                                                            | Encrypted with AES-GCM in the Session DO under a key held as a Worker secret. Referenced by pi-secret's double-brace `secret:NAME` placeholder or `$PI_SECRET_*`. Injected into exec env only at call time. Redacted by an `afterTool` hook and at the Session's model seam. Expires after 15 minutes. |
| Environment | Values the owner keeps for one Environment or Global in the Secrets section                                                                                         | Sealed with AES-GCM in the Registry DO (migration 14), bound to their scope and name. Used, injected and redacted as runtime ones are, in every Session of the Environment, and never expire. One marked for the Build also reaches every Setup Script of the Environment as `$PI_SECRET_*`.           |

`packages/extensions/src/secrets` ports pi-secret (`NOTICE.md`). The key is `SECRETS_ENCRYPTION_KEY`, from which HKDF derives one AES-GCM key per Session; each record is bound to its name and expiry. A `secret_ask` waits on a durable request: the Session sends the waiting requests to every client (`secret_requests`), the owner answers in a masked form (`secret_answer`), and the request and answer survive eviction, so a call cut off by one finds its answer when it reruns. Values never enter durable state: pi-durable records the arguments a `beforeTool` hook returns, so that hook only blocks calls naming a Secret the Session does not hold, and wraps of the tools that use Secrets (coding tools, Files, `web_fetch`; never `web_search`, whose queries leave for a search provider) resolve placeholders, inject `$PI_SECRET_*` into their commands' environment, and redact streamed output and the command's Result Spill (raw output in the Workspace's `/workspace/.cloudpid/tmp`, which both backends see) inside `execute`. Every held Secret is in every wrapped command's environment, so a process left running in the background keeps it past expiry and `secret_forget`. Provider requests are scrubbed at the Session's `Models` (`scrubbingModels`), so generations, compaction summaries, and a subagent's `compact` summary are all covered; a message is indexed by an unkeyed SHA-256 of its JSON, so its scrubbed form survives eviction, expiry, and a key change. Tools whose arguments become conversation content (code mode, subagents, Notes, Handoffs) are not wrapped; the calls they lead to resolve their own references. Redaction covers each value's common encodings. `secret_ask` and `secret_forget` are parent-only; children read and use the parent's Secrets. An alarm deletes each Secret when it expires, and a request whose call is gone (abandoned while the object was evicted) is withdrawn once the Session is idle. A value a command writes to a file outlives that expiry: under `/workspace` it is in the Workspace DO's storage, and on the Container's disk it is in the next snapshot, kept up to 30 days (the scan before a snapshot searches for the GitHub token and the Environment's Secrets, not for these: see [_Snapshots_](container.md)).

**Environment Secrets** ([ADR-0016](../adr/0016-environments-and-a-container-per-workspace.md)) are kept by the owner for one Environment or Global (`listEnvironmentSecrets`, `setEnvironmentSecret`, `setEnvironmentSecretBuild`, `deleteEnvironmentSecret`; see [_Environments from the UI_](workspace.md)). A name is one `secret_ask` takes (`SECRET_NAME`, at most 128 characters); a value is not empty, holds no NUL and is at most 32 KiB of UTF-8; a scope keeps at most 100. The main Worker passes the value to the Registry DO, which seals it (AES-GCM under a key HKDF derives from `SECRETS_ENCRYPTION_KEY` for the Registry, bound to the scope, an Environment's id or `*`, and the name, so a row moved to another scope or name does not open) and stores only the ciphertext (`environment_secrets`). No RPC answers a value, an error names the problem and never the value, and nothing logs one. An Environment's own Secret wins over one of the same name kept Global. A value that is not secret (an email, a URL) is a variable, not a Secret: variables can be kept Global too (see [_Container settings_](container.md)), and a Secret's value found on a Container's disk stops its snapshot (see [_Snapshots_](container.md)). Values leave the Registry DO only over Durable Object RPC within the deployment, opened for:

- **A Session** (`sessionSecrets`, by the Session's Environment), which holds them in memory only, never in its storage, and asks again at its first use of Secrets 30 s after the last answer (5 s after a failure, keeping what it held meanwhile). It uses them as held `secret_ask` ones: Secret References, `$PI_SECRET_*` in its wrapped commands, redaction of output and of provider requests. They never expire; `secret_list` shows each as kept for this Environment or Global, `secret_forget` refuses them (the owner deletes one in the Secrets section), and a `secret_ask` value of the same name wins while it is held. A value deleted or replaced is still redacted by the Session until the object is evicted. Before using a set, the Session hands it to its Workspace DO (`updateEnvironmentSecrets`), and keeps the set it held when that fails, so no value reaches a command before the Workspace searches for it.
- **A Workspace's set-up** (`getWorkspaceSetup`, `upkeepSpares`): the readying hands them to the Workspace DO, and a spare's request carries them (`prepareSpare` keeps them apart from the set-up it stores).
- **A Build** (`environmentSecrets`): see [_Builds_](container.md).

**Keeping what `secret_ask` asked for** ([ADR-0019](../adr/0019-the-agent-manages-its-environments-and-settings.md)). `secret_ask` takes an optional `keep`: `session` (the default), `environment` or `all`. It only pre-selects the choice in the masked form (`secret_requests` carries it as `keep`): the form always offers all three (_This Session only_, _Keep for this Environment_, _Keep at Global_) and the owner's choice is final (`secret_answer` carries it as `keep`; an answer without one holds the Secrets for the Session). The tool's result says the scope the owner chose for each name (`provided`, with its expiry; `kept`, with `scope`, `environment` or `every`, and `shadowed` when the Environment's own Secret of the name wins), never a value. A kept Secret takes the path of the Secrets section: the Session hands the value to the Registry DO over Durable Object RPC (`keepAskedSecrets`, not an HTTP RPC), which checks it with the owner's rules (name, value, at most 100 per scope), seals it as `setEnvironmentSecret` does and stores the ciphertext, then the Session runs the Builds' upkeep (each Environment's, for `all`). The Session does not hold the value as an entered one: it is not in its storage, does not expire after 15 minutes, and comes back through the kept Secrets like any other (`secret_list` shows it as kept for this Environment or Global; `secret_forget` refuses it); the Session still redacts it. A Secret that cannot be kept (the Registry refuses it, cannot be reached, or the Session has no Registry) is held for the Session only, and the result says why in `notKept`. The value never enters durable state, a tool argument, a result, the history or a log. Which Secret reaches a Build is a separate switch: `environment_secret_build` (see [_Agent changes_](agent-changes.md)).

The Workspace DO keeps its copy sealed in its storage (AES-GCM, HKDF purpose `workspace`, bound to the object's id and the name; `SECRETS_ENCRYPTION_KEY` is bound to the Workspaces Worker too), not in memory only, because what needs it runs on the DO's alarm after an eviction or a deploy, when nothing hands it again: the idle stop's snapshot, a spare's preparation and snapshot, a Build. It searches the Container's disk for each before every snapshot and takes each out of what a command prints as its Secret Reference. A copy that does not open (the key changed or is missing) is a set of values the DO cannot show to be absent from the disk, so its snapshots are skipped and its Builds fail until the next handover replaces it. So is the copy a handover leaves when the Registry could not open the Environment's Secrets (the set-up then carries `secretsUnavailable`, a fixed reason, in place of `secrets`: `environmentSecretsUnavailable`, which keeps the values it held before for redaction). The Setup Scripts of the Workspace's Container, and of a clone its readying makes, get those marked for the Build from the copy, each as `$PI_SECRET_<NAME>`, as a Build's do (`buildSecretEnvironment`): a Workspace made from a Build runs its Setup Scripts again, and a script that needs one would fail there without it. No other script or command gets them that way. A copy is replaced whole: a Secret deleted is no longer searched for, and what a command wrote with it stays where it is.

An Environment no Secret reaches never needs the Registry's key. While `SECRETS_ENCRYPTION_KEY` is malformed, the Registry DO answers everything else: the set-up of a Workspace whose Environment has Secrets carries none and says why (`secretsUnavailable`, `secrets unavailable: …`), so the Workspace takes no snapshot that would need them; that Environment's Build is left as it is (logged); and `setEnvironmentSecret`, `sessionSecrets` and `environmentSecrets` fail, saying the Secrets cannot be kept or opened.

From v2, secret references may name 1Password items. Credentials then move into a single dedicated vault, and deploy-time secrets shrink to the model proxy key, the 1Password token, and VAPID.

## Web

`packages/extensions/src/web` ports pi-web-tools (`NOTICE.md`): `web_search` over Exa or Parallel (keys are optional deploy-time secrets; a Session with both picks one by a stable hash of its conversation ID) and `web_fetch` (Markdown, text, or HTML; JSON re-indented; `offset`/`limit` line paging). A Worker has no temp file the model can read, so a result over 50 KiB or 2,000 lines is cut to whole lines and ends with a note naming the `offset` that reads on, instead of spilling to disk. HTML converts without a DOM in one linear pass; a page nested more than 1,024 levels deep (browsers stop at 512) or converting to more than 20 MiB of Markdown fails with a note to use `format: html`, so a hostile page cannot stall the Session.

**SSRF guard.** `web_fetch` reaches the network only through `guardedFetch`, which follows redirects itself and, for the URL and every hop, refuses non-HTTP(S) schemes, URLs with credentials, and any host that is or resolves to a loopback, private, link-local, CGNAT, unique-local, multicast, reserved, or cloud-metadata address (`169.254.169.254`, `fd00:ec2::254`, `metadata.google.internal`, `*.internal`, `*.local`, single-label names). Numeric hosts are decoded as a resolver would (decimal, hex, octal, short forms) and IPv6 forms that carry an IPv4 address (mapped, compatible, NAT64, 6to4) are judged by it.

A Worker cannot resolve a name before `fetch`, so a public-looking name that resolves to a private address is caught by a DNS-over-HTTPS lookup of its A and AAAA records through Cloudflare's resolver before each hop; a lookup that fails refuses the hop. The residual risk is DNS rebinding: the platform's own lookup at `fetch` time is separate from ours, so a name that answers differently to two queries in quick succession can pass. Both lookups share Cloudflare's caching resolver, which holds an answer for its TTL, and Cloudflare's edge also refuses Worker subrequests to private and internal addresses (the guard does not rely on that), so what is left is a narrow race for an attacker who controls a name's records and wants the Session to reach a public address of their choosing, which the guard does not try to prevent.
