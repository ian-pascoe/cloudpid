# cloudpid's MCP endpoint and Session import

The **MCP endpoint** (GLOSSARY.md) is cloudpid's own MCP server at `/mcp`. A **Local agent** (pi first, on the Legacy lane; Claude Code second, on both lanes) works there as the owner: it lists Environments and Sessions, starts, messages, follows and stops Sessions, reads transcripts, and makes a **Session import** of a local pi Session. It never asks the Local agent anything and answers nothing that waits for the owner. The tool surface has no ADR: every choice can be undone by adding a tool, a field or a setting ([What cloudpid's MCP server offers](https://github.com/ian-pascoe/cloudpid/issues/392)). The Session import's contract with laptop code is [ADR-0043](../adr/0043-a-session-import-sends-the-local-agents-raw-transcript-for-cloudpid-to-translate-and-moves-the-working-tree-only-through-the-repos-remote.md). cloudpid's own agents as callers of the endpoint are neither a target nor blocked (see [_Self-use_](#self-use)).

## Access and identity

- **Its own Access application** ([Verify the MCP endpoint behind Access managed OAuth on a deployed stage](https://github.com/ian-pascoe/cloudpid/issues/419), "shape B"): on every deployed stage a shared `Cloudflare.Access.Application` (`self_hosted`) with `public` destinations `pi.ianpascoe.dev/mcp` on prod and `<appOrigin(stage) host>/mcp` elsewhere (`cloudpid-server-<label>.ian-g-pascoe.workers.dev/mcp`), which also covers sub-paths. It sits beside the Worker's owner-only application from `deployment(stage)`, which is unchanged. Managed OAuth is never turned on for the Worker's own application: there an OAuth token minted for `/mcp`, or the service token, would open `/` and `/rpc` too.
  - **`oauthConfiguration`:** access tokens `5m`, grant `336h`, DCR on with `allowAnyOnLocalhost` and `allowAnyOnLoopback`.
  - **Policies:** the owner-email Allow, plus Service Auth with the rule `{serviceToken: <cloudpid-local-agent's id>}`, never `anyValidServiceToken` (see [_The Local agent's service token_](#the-local-agents-service-token)).
  - **Its paths** stay outside `/oauth/mcp/*` and outside the bypass application of [ADR-0035](../adr/0035-cloudpid-identifies-itself-with-a-public-client-document-and-takes-authorization-responses-outside-access.md) (see [_The client document and the callback outside Access_](mcp-sign-in.md#the-client-document-and-the-callback-outside-access)).
- **Access is the authorization server** ([How can cloudpid serve MCP from behind Cloudflare Access?](https://github.com/ian-pascoe/cloudpid/issues/378)); the Worker has no OAuth code, no `workers-oauth-provider` and no `McpAgent`.
  - A cookieless `POST /mcp` gets `401` with `WWW-Authenticate: Bearer … resource_metadata="https://<host>/.well-known/cloudflare-access-protected-resource/mcp"`, which Access serves; the team's RFC 8414 metadata has a `registration_endpoint`. The RFC 9728 paths at the host root stay behind the main application (302); pi and Claude Code read `resource_metadata` from the 401 instead.
  - Access tokens are opaque; Access strips `Authorization` before the Worker. Refresh tokens rotate, and the old one stays usable, so a raced refresh doesn't fail.
  - Access checks a token only when it admits a request: a 300 s wait whose token expires midway finishes.
  - No WAF rule that requires a User-Agent may sit on `/.well-known/*` or Access's OAuth endpoints: Claude Code's discovery and DCR requests send an empty one.
  - Managed OAuth takes 1–2 minutes after a deploy to take effect (errors `1042`/302 until then).
- **The guard** ([Whether workers.dev stages serve the client document](https://github.com/ian-pascoe/cloudpid/issues/422) D9; its shared rules, the main routes and the `alchemy dev` local rule are in [_The client document and the callback outside Access_](mcp-sign-in.md#the-client-document-and-the-callback-outside-access)). It checks both audiences: the main application's on every route, and on exactly `/mcp` (`isMcpRoute`: the path normalised as the router reads it, so `/mcp/`, `/MCP` and a sub-path are main routes) the MCP endpoint's. On `/mcp` the main Worker verifies `Cf-Access-Jwt-Assertion` itself, failing closed, with `aud` equal to the **MCP endpoint application's** `aud` (the deploy-time var `CLOUDPID_MCP_ACCESS_AUD`, from the alchemy output), and classifies the caller from the assertion, never `ctx.access.getIdentity()` (which returns `undefined` for a service token). The verdict carries who it is, a `Caller` that the guard provides to the route as the `AccessCaller` service:
  - **owner** (`{kind: "owner", clientId?}`): `email == OWNER_EMAIL`; the assertion's `oauth.client_id` (the DCR registration's opaque id) is its audit mark;
  - **service token** (`{kind: "service_token", clientId}`): no `email`, `sub` empty or absent, and `common_name ==` the deploy-time `MCP_SERVICE_TOKEN_CLIENT_ID` (the token's full client id, ending `.access`); any other `common_name` on `/mcp` is refused as `not_service_token`, and a Worker without the client id refuses the token alone;
  - **local** (`{kind: "local"}`): the `alchemy dev` rule below;
  - anyone else: `403 not_owner`; a Worker without `CLOUDPID_MCP_ACCESS_AUD` refuses `/mcp` altogether (`not_configured`). On every other route a `common_name`, or `/mcp`'s `aud`, is refused, and so is a token whose `aud` lists both applications' audiences, on either kind of route (`wrong_audience`), so neither credential opens the other's routes (Access already answers them there with a 302 to its login).
  - Under `alchemy dev` (no Access) the local rule admits the owner on `/mcp` as on every guarded route, as `local`: `McpAuth` gains `"local"` beside `oauth` and `service_token`, so a Session started in local dev is marked as such, not as a credential it did not use.
- **Identity stays in `api`:** `ctx.access` doesn't reach `McpWorker`, so the request forwarded to `serve` carries no `Cf-Access-*` header (every header whose name starts `cf-access-`, whatever Access adds), no cookie and no `Authorization`; the main Worker closes the identity over the `api` target and never passes it as an argument. Both kinds of caller get every tool.
- **The client's name** (display only, untrusted), the first present of: an `X-Cloudpid-Client` header sanitized to ≤40 characters (pi's `mcp.json` `headers`, or `/cloudpid`'s); Modern `_meta["io.modelcontextprotocol/clientInfo"].name`; the first non-generic `User-Agent` product token (`claude-code`), skipping `node`, `undici`, `Bun`, `curl` and the like; else none ("via MCP").
- **Marks:** `SessionRecord` gains an optional `marks: {kind: "mcp" | "import", client?, auth: "oauth" | "service_token" | "local"}`, beside `origin`, which stays the Fork and Clone origin alone, so a version that predates the marks still reads the record; each input sent over the endpoint carries `via`, its `SessionVia` `{client?, auth, era?}`, in the `cloudpid.user` entry. The API's own `Via` is `{client?, era}`: the main Worker adds `auth` from the verified caller before the Session object sees the request (`owner` is `oauth`; the `api` target's `auth` getter says it, and the span records it). A member a version does not know (a newer `auth`, `era` or mark kind) decodes as `unknown` or reads as none, never as a failure. The web shows "MCP · `<client>`" and "Imported · `<client>`" chips on the Session and "via `<client>` (MCP)" on inputs. The email is never recorded. The owner's `oauth.client_id` travels in the `Caller` and is recorded by the tools that start Sessions (the `via` marks, as [Verify the MCP endpoint behind Access managed OAuth on a deployed stage](https://github.com/ian-pascoe/cloudpid/issues/419) suggested); the read tools have nothing to mark.
  - **As built** ([Start, send to and stop Sessions over `/mcp`](https://github.com/ian-pascoe/cloudpid/issues/456)): `session_start` writes the Session's `marks` (`kind: "mcp"`; the Registry keeps them in its origin columns) and marks the first input; `session_send` marks its input; both with `via` = `{client?, auth, era, clientId?}`, where `auth` comes from `identityOf(caller)`, never from an argument.
  - **Local dev:** a Session started under `alchemy dev` gets `auth: "local"`, the guard's own verdict (the owner on loopback, with no Access credential), rather than `oauth` or `service_token`, which would name a credential it did not use. Rejected: reading it as `oauth`, which would make the audit mark lie, and leaving the mark off, which would make a local Session look like a version that predates the marks.
  - **The owner's `oauth.client_id`** is recorded in `via.clientId` (an optional, gain-only member of `SessionVia`), in the `cloudpid.user` entry of every input the owner's grant sends, and nowhere else: not in `marks` (which the Registry lists and `sessions_list` shows the Local agent as `origin`, and which would name one grant for a Session that several may later send to), not as a `SessionOrigin` (the Fork and Clone origin alone), and not only in the span (traces are not an audit trail: they are sampled, and absent where the runtime has no `tracing`). It is never shown: the web chip and the transcript text name the client alone, and the service token's and local dev's inputs carry none.
  - **The web** shows `marks` as "MCP · `<client>`" (or "Imported · `<client>`") beside the Environment under the Session's title (`session-origin.tsx`), and `via` as a chip "via `<client>` (MCP)" under the input (`chat/via-chip.tsx`, from `TranscriptMessage.via`); with no client name they read "MCP" and "via MCP".
- **No switch:** there is no Settings toggle for the endpoint in v1. Access is the switch: revoke grants, rotate the service token, or turn managed OAuth off.

## The handler

- **Where:** the main Worker routes `/mcp`, after the guard, to `MCP_SERVER.serve(request, api)`: the `McpServer` entrypoint of `McpWorker` (`apps/mcp-worker`), beside `McpEngine` ([ADR-0038](../adr/0038-the-mcp-host-object-lives-beside-the-registry-and-runs-the-sdk-through-a-stateless-engine-in-a-worker-of-its-own.md); see [_Packages and objects_](mcp.md#packages-and-objects)). `McpServer` binds neither the Registry nor the Sessions; it reaches them only through `api`, which it `dup()`s while its SSE body is open.
- **The SDK:** `@modelcontextprotocol/server`'s own `createMcpHandler` with `legacy: "stateless"`, pinned exactly with the client (2.4.0), not `agents`' ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D24; [ADR-0036](../adr/0036-the-mcp-core-is-the-official-sdk-inside-cloudpids-own-era-agnostic-module.md)). It adds `originValidationResponse` and `hostHeaderValidationResponse` (bare-fetch mounts skip them), and never imports the client core, the host object or pi-mcp. A new `McpServer` is made per request. The handler is `serveMcp(request, {api, version, gate, observe})` in `@cloudpid/mcp/server` (`packages/mcp/src/server/`), which knows nothing of Workers: `McpWorker`'s `McpServer` entrypoint (`apps/mcp-worker/src/server.ts`) wraps it, and the conformance run serves it over `node:http`. Its checks run before the SDK: `405` for any method but `POST`, `400` for an `Origin` or `Host` that is not the hostname of the request's own URL, and the SDK's `413` past 5 MiB.
- **Eras:** Modern `2026-07-28`, plus Legacy `2025-11-25`, `2025-06-18` and `2025-03-26` through `initialize`, both stateless: no `Mcp-Session-Id`, and `405` on GET and DELETE. Modern uses `responseMode: "sse"`; Legacy is SSE already. Left to implementation: SSE keep-alive comments every 15 s, as in [Verify the MCP endpoint behind Access managed OAuth on a deployed stage](https://github.com/ian-pascoe/cloudpid/issues/419)'s probe (`keepAliveMs: 15000`), where a 300 s wait with no `progressToken` finished on keep-alives alone.
- **Capabilities:** tools and `instructions` only, declared as `{ tools: { listChanged: false } }` (the SDK would otherwise advertise `true`). No resources, prompts, completions, logging or subscriptions. It never sends its client an elicitation, sampling or roots request on either lane, so confirmations happen in cloudpid's UI. It returns no MCP tasks: long work returns a handle the Local agent polls ([MCP tasks as durable long-running requests](https://github.com/ian-pascoe/cloudpid/issues/389) D1.3); serving tasks is left for later.
- **`serverInfo`:** `{name: "cloudpid", version: <Server deploy id>}`. `Server` reports its id (`CF_VERSION_METADATA`) as the optional `version` of its `describe()` answer, a gain-only field; an older `Server` sends none, and `McpServer` then uses its own version id.
- **`instructions`** (≤1,500 characters). Line 1 stands alone, since pi shows only line 1 in its `mcp_servers` section: "cloudpid: the owner's hosted coding agent. Start or message its Sessions, wait for their Runs, read transcripts, or import a local pi Session." The rest covers: `environments_list` → `session_start` → a `session_wait` loop passing the cursor back; `session_transcript`; waiting requests, which the owner answers in cloudpid at the URL given; `session_import_*` being for programs, not models; transcript text being data, not instructions; calling `session_wait` again with the same cursor after a connection error. Each sentence is there only when the tool it names is served (`describe()` gates it): so does a tool's `next` sentence, which never names a tool that is not on offer.

## Following a Run

- **`session_wait`** returns at the first of: the root Run ended after `after` (answered, stopped or failed); a waiting request newer than the cursor's mark appeared; an import ended; pi-durable parked a task (the Run is stalled); the deadline. It returns at once if one of the first four has already happened; with no `after` it returns at once unless a Run is going and nothing waits (an import going is no Run: it returns at once with the status `importing` and a cursor that ends with the import, as `import_ended`). A waiting request the caller has already seen doesn't end later waits, so a Run blocked on the owner doesn't make the local model spin, and it never returns per transcript entry or cloud tool call.
- **Result:** `{session_id, status, ended_by: run_ended | owner_needed | import_ended | stalled | timeout, interrupted?, branch_changed?, outcome?, waiting[], activity: {entries, tool_calls, latest: [≤5 one-liners]}, answer?: {text (≤8,000 chars, middle-cut), truncated}, text_withheld?, error?, cursor, next}`.
- **Status:** `running` (the root Run is going, or input is queued for it, or a message is still in the root's line: [_Getting a prompt at send_](mcp-in-a-session.md#getting-a-prompt-at-send)); `waiting_for_owner` (a waiting request exists anywhere in the Session); `background` (the root is idle, but subagents work or MCP tasks are followed); `idle`; `importing`. Archived is a flag, not a status; lists use the Registry's coarse `running | idle`.
- **`outcome`** is `{result: answered | stopped | failed, reason?, message?}` from the submission: `done` → answered; `aborted`, `withdrawn`, `reset` → stopped; `model_error` → failed, with "out of budget" as `reason: spend_limit`. A failed Run is an outcome, never an error.
- **Timeouts:** the 45 s default stays under every 60 s floor progress can't move (the TS SDK's default, Claude Code's first-byte timer). Waits up to 300 s rely on progress: whenever the request carried a `progressToken` (pi and Claude Code both send one), `McpServer` sends `notifications/progress` ("Run running · 2m10s") at the start and every 10 s from its own timer, which re-arms pi's timeout and Claude Code's 5-minute idle timer.
- **Disconnects:** a client disconnect ends the wait, never the Run; the Session side still ends at its deadline. At most 8 concurrent waits per Session (`too_many_waits`); each pending wait keeps the Session object resident. If the RPC is cut on the Session side (a deploy, an eviction), the main Worker reads `status()` once and returns `ended_by: "timeout"`, `interrupted: true` and **the cursor that was passed in**; only if that read also fails does it return `unavailable`.
- **The cursor** is opaque: base64url of `{conversation, entry id, waiting mark, newest settled input, importing?}`, valid for the Session's life. The settled-input mark is what tells a Run that ended after the cursor from one that ended before it, and `session_send` and `session_start` answer a cursor whose mark sits just before their own input, so a wait from it ends with that input's Run and no earlier one's. A waiting request has no time of its own: the Session object stamps each when it first sees it (kept in storage), and the mark is the newest stamp. The Session object re-reads its state every 500 ms while it holds a wait (`waitForChange`), rather than being pushed by events. A bad one is `invalid_cursor`. When the owner moves the active branch, results say `branch_changed: true` and the cursor keeps following the old conversation; a call without a cursor picks up the new one.

## Transcripts

- **Rendering** happens in the Session object at read time, by a pure `renderTranscript` beside `projectEntries` in `@cloudpid/protocol`, so a page is cut by its rendered size and megabytes of tool results never cross the RPC. One block per entry, oldest to newest: `### user · 14:02` / `### assistant` headers with text ≤2,000 chars (`summary`) or ≤8,000 (`full`), middle-cut; each tool call as one line (`→ bash  npm test`, arguments ≤160 chars); each tool result as `✓ 12 lines` or `✗ <first line ≤200>` in `summary`, ≤1,500 chars in `full`; images as `[image png 230 KB]`; notices on one line; thinking always left out.
- **Paging:** no cursor reads the latest page; `before` reads older entries, `after` newer. A page holds whole entries up to `max_chars`, always at least one (trimmed to fit), at most 200. Result: `{session_id, agent_id?, entries: [{entry_id, role, at, text}], older?, newer, branch_changed?, next?}`, the text only in `entries[].text`. The 12,000 default stays under pi's 20 KB middle cut; the 40,000 maximum under Claude Code's 50k-character spill and 25k-token cap.
- **Subagents** are read separately by `agent_id` from `session_get.agents`; the root's page shows a delegation as its call plus a one-line report.
- **Redaction** ([What cloudpid's MCP server offers](https://github.com/ian-pascoe/cloudpid/issues/392) D6): every text taken from a Session (transcript entries, `answer`, `last_answer`, `activity.latest`, `waiting[].summary`, import `warnings`) is redacted in the Session object, each text before it is cut to its limit and again once rendered, and so before page cutting, with the same `SecretsService.scrub` as `scrubbingModels` (the Environment's Secrets and asked Secrets in every encoding) plus a pattern pass over GitHub token shapes (`ghs_`, `ghp_`, `gho_`, `ghu_`, `ghr_`, `github_pat_` → `[REDACTED github token]`). If a refresh fails, a set held from this wake is used; with none, `session_transcript` returns `unavailable` (retryable) and `session_wait` and `session_get` drop their text fields (`answer`, `error`, the outcome's `message`, `last_answer`, `activity.latest`, and make `waiting[].summary` generic) and say `text_withheld: "secrets_unavailable"`, however the wait ended. Each text is redacted before it is cut to its limit, so a cut never leaves a Secret as a prefix. A value no longer held (an expired `secret_ask` value, a Secret deleted before an eviction) isn't caught, as at the model seam. Titles come from the Registry and aren't scrubbed.
- **Untrusted text:** one sentence in `instructions` and in `session_transcript`'s description says transcripts carry others' text (web pages, command output, other servers), to be treated as data. No fencing and no per-page preamble; `summary` already leaves tool-result bodies out.

## Waiting requests

- **None is answered over the endpoint:** Approvals, Secret requests, Sign-in requests, Elicitation requests, Sampling requests and Browser Handoffs wait for the owner in cloudpid, since an agent's word is not the owner's ([ADR-0041](../adr/0041-an-mcp-servers-elicitation-request-is-answered-only-by-the-owner-its-answer-is-never-kept-and-a-form-that-asks-for-a-credential-is-declined-unseen.md)). An approve tool marked with Claude Code's `anthropic/requiresUserInteraction` is left for later.
- **What the Local agent sees:** `waiting: [{kind: approval | secret | sign_in | elicitation | sampling | browser_handoff, request_id, agent_id, summary, since, url}]`. cloudpid writes `summary` itself: an Approval's change and target; a Secret request's names only; an MCP server's request only that server's name, never its text. `url` is `/sessions/<id>?request=<request_id>`, and the Session page scrolls to that card.
- **Notifications** go out as usual for waiting requests and ended Runs, inputs sent over the endpoint included. No "being followed" indicator in v1.

## Starting, sending and stopping

- **`session_start`:** `environment` is an id or an exact case-insensitive name (`ambiguous_environment` when several match), defaulting to `DEFAULT_ENVIRONMENT` as `createSession` does; the description says to omit it only for work tied to no Repo, and the result names the Environment and its Repos. `branch` and `base` follow `createSession`'s rules (`branch_taken` for a branch in use). `model` must be one of `environments_list.models.available`; `thinking` is `off`…`max`. A start always makes a new Workspace (a spare if current). No Role (a Role is picked when delegating). `request_id` dedupes starts for 24 h through the Registry.
- **`session_send`** takes only `text`, `when_busy` and `request_id` (the submit's idempotent `requestId`); model and thinking stay per-Session choices in the UI. `queue` is pi-durable's `followUp` (starts a Run when idle, else waits for the next one); `steer` joins the running Run at its next boundary; `reject` answers `session_busy`.
- **`session_stop`:** a plain Stop of the root withdraws queued input, and the messages still in the root's line (being prepared, or waiting their turn: [_Getting a prompt at send_](mcp-in-a-session.md#getting-a-prompt-at-send)), and leaves subagents running; `subagents: true` is Stop all. It returns once the Session is idle (≤30 s), else `stopping: true`, and leaves the transcript notice "Stopped from `<client>` (MCP)" ("Stopped over MCP" when the caller gave no name, as its chip reads "via MCP"). It is idempotent: a plain Stop while no Run is going (an idle Session, or only subagents working) does nothing and leaves no notice. A message in a line is not idle: a Stop that finds one withdraws it. The `session_send` that sent it answers `stopped` ("Stopped before it was sent"), as there is no submission to follow.
- **As built** ([Start, send to and stop Sessions over `/mcp`](https://github.com/ian-pascoe/cloudpid/issues/456)):
  - **`session_start`** checks its arguments before anything is made (`input_too_large`; `invalid_argument` for a `branch` or `base` that no branch can be named, a `model` outside `environments_list.models.available`, a `thinking` outside the levels, an empty `title`; `not_found` or `ambiguous_environment` for the Environment), then makes three calls in order: the Registry's `createSession` (a new Workspace, `marks`, `requestId`, `maxRunning`; the spare and Build upkeep run after the answer, as for the owner's own start), the Session's `configure` (only when `model` or `thinking` was given, so the first Run uses them), and the Session's `submit` of the first message. `branch_taken` and `too_many_running` are the Registry's refusals, and nothing is sent after one.
  - **`request_id` dedupe** has two halves that agree: the Registry answers the first Session of a `request_id` for 24 h (the table is `session_requests`), and the first message is submitted under the same id, which the Session already dedupes. A repeated start therefore makes no Session and sends nothing, answers the first one's cursor, and mends a start that was cut between the Registry and the Session (the repeat sends the message it never got). A repeat is answered before the cap is looked at, even when the Session was archived since (the Session answers a request id it has admitted before it checks it), and never runs `configure` again: the Registry marks the Session it answers for a repeated `request_id` (`repeated: true`), and only a first start picks the model, so a repeat cannot clobber a pick the owner changed. A repeat that finds the first message unsent (a start cut after the Session was made) sends it, and nothing else. `request_id` is global, not per identity.
  - **A start that fails after the Session was made** (its model could not be picked, its first message was not sent) answers the failure with `details: {session_id, url}` and says how to go on (repeat the call under the same `request_id`, or `session_send` to that id), so the caller never has a Session it cannot name.
  - **`session_send`** answers `not_found` from the Registry before any Session object is woken, and hands the rest to the Session's `submit` as the socket's admission does; `when_busy` is `queue` unless given (`followUp`). `session_stop` does the same with `stop`, and its Stop notice is the Session's (see above).
- **No confirmations:** there is no `confirm` argument. The caller is authenticated as the owner; spending is bounded by the Spend limit and the running cap.

## The `api` target

`api` fills in [ADR-0038](../adr/0038-the-mcp-host-object-lives-beside-the-registry-and-runs-the-sdk-through-a-stateless-engine-in-a-worker-of-its-own.md)'s `serve(request, api)`: an `RpcTarget` the main Worker builds per request over the Registry and Session code it has (`apps/server/src/mcp/api.ts`; types in `@cloudpid/protocol`'s `mcp-api`).

```ts
type Via = { client?: { name: string; version?: string }; era: "legacy" | "modern" };
type ApiResult<T> = { ok: true; value: T } | { ok: false; error: { code; message; retryable; details? } };
interface McpApi {
  describe(): { operations: string[]; limits: { maxInputBytes; maxSliceBytes; maxImportBytes; maxWaitMs }; version?: string };
  environments(); sessions(q); session(id);
  start(r & { via }); send(r & { via }); wait(r); transcript(r); stop(r & { via });
  importBegin(r & { via }); importAppend(r); importFinish(r); importCancel(r);
  limited?: { retryAfterS: number }; // a getter: `await api.limited` counts one call, and answers only when over the rate
  auth?: "oauth" | "service_token" | "local"; // a getter: how the caller got in, for the span
}
```

- **Absolute URLs:** every `url` the result holds (a Session's page, a waiting request's) is built from the origin of the request's own URL, so a preview stage links to itself. `sessions`' `environment` is resolved in `api` (an exact id, else an exact name in any case, `not_found` or `ambiguous_environment` otherwise), not by `McpServer`, which knows no Environment. A Session id is checked to be a UUID, and a Session the Registry does not know is `not_found`, before any call reaches a Session object (so a made-up id never makes one). A failed RPC or a defect on any of these edges is `unavailable`.
- **Served:** `describe()` lists the operations this version has (`environments`, `sessions`, `session`, `transcript`, `start`, `send`, `stop`: `MCP_API_OPERATIONS_SERVED`); the target's `wait` still answers `unsupported`, which is how a `McpServer` that is ahead of `Server` finds out and leaves the tool out. A tool is added to `McpServer` and its operation to `MCP_API_OPERATIONS_SERVED` together, so an older `McpServer` or `Server` pairing shows fewer tools, never a broken one.
- **The main Worker owns** authorization, validation, Registry and Session calls, cursors and rendering; **`McpServer` owns** the SDK, schemas, descriptions, the text and `structuredContent` envelope, framing caps, progress and error mapping. Failures travel as values. Nothing streams across `api` in v1.
- **New Server pieces:** the Session object (socket-only today) gains RPC methods `status()`, `waitForChange({after, deadline})`, `transcriptPage(…)`, `submit({input, whenBusy, requestId, via})` (the socket's admission), `stop({subagents, via})`, `configure({model?, thinkingLevel?})` (the socket's `configure`, `agentChange` shared, and open pages are told the pick, for a start that names a model) and `stageImport*`; `createSession` gains `marks`, `requestId` and `maxRunning`; `sessions()` filters and pages `listSessions`.
- **Version skew** ([Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423) D1): every edge only gains (methods, optional fields). `McpServer` deploys before `Server`, so it gates its tools on `describe()`, cached per isolate for 60 s: a tool appears only once the deployed `Server` supports it, and a missing method answers `unsupported`. The main Worker → Session edge has no gate (a loud failure that heals); main Worker → `McpServer` relies on deploy order (Workspaces → McpWorker → Server). The tools change only additively; a breaking change is a new tool or `format`. The other MCP edges' gates are in [_Deploys_](mcp.md#deploys).

- **Domain failures** are `isError` results with `structuredContent: {error: {code, message, retryable, details?}}` and one actionable sentence. `stopped` answers a `session_send` the owner's Stop withdrew before it was placed (also when it is sent again under the same `request_id`); it is never retryable. Codes: `not_found`, `ambiguous_environment`, `invalid_argument`, `invalid_cursor`; `session_busy`, `session_importing`, `session_archived`, `branch_taken`, `stopped`; `input_too_large`, `too_many_running`, `too_many_waits`, `rate_limited`; `offset_mismatch`, `import_too_large`, `import_expired`, `checksum_mismatch`, `unsupported_format`; `unsupported`, `unavailable`.
- **As built, the running cap** ([Start, send to and stop Sessions over `/mcp`](https://github.com/ian-pascoe/cloudpid/issues/456)): the cap is the Registry's `createSession` input `maxRunning: 10`, and it counts in the same transaction that inserts the Session, so starts made in parallel cannot all pass it. It counts the Sessions whose origin is `mcp` or `import`, not archived, that are `running`, or were made less than 2 minutes ago and have not yet reported a Run (their status has not changed): a start's first Run is reported a moment after it is made, and without the second term a burst of starts would all see the same count. The owner's own starts pass no cap, and neither does `session_send` to a Session that is idle: only a start is capped, so a Session sent to again may run beside ten others. A refusal is `too_many_running`, retryable (it clears when a Run ends), with `details: {limit}`, and registers no Workspace. The edge has no gate (`mcp.md` → Deploys): a Registry still on the previous code, for the few minutes a deferred update may take, ignores `maxRunning` as it does `marks` and `requestId`, so the cap can be passed in that window.
- **An oversized page:** a page is cut by characters where it is read, and a character can take up to six bytes of JSON, so `structuredContent` can pass 64 KiB (CJK text, control characters). `session_transcript` then answers a non-retryable `invalid_argument` saying to ask again with a lower `max_chars`; the same request would fail again. Any other tool's oversized result is a non-retryable `unavailable`.
- **Schema failures** are the SDK's `isError` results; only an unknown or disabled tool is `-32602`.
- **HTTP:** `401` from Access; `403` for a caller who isn't the owner; `405` for GET and DELETE; `413` for an oversized body; `400` for a bad `Origin` or `Host`; `503` (`Retry-After`) when the main Worker cannot reach `McpServer` (a deploy behind or cut).

## Self-use

No guard stops a cloudpid Session from using its own MCP endpoint. It takes the owner's Approval for the MCP server definition (see [_Approval_](mcp-configuration.md#approval)) and a service token kept as an Environment Secret. It is bounded by the running cap and the rate limit, but not by subagent depth or a shared Spend limit.

## Session import

A Session import ([Handing off a local pi Session to cloudpid](https://github.com/ian-pascoe/cloudpid/issues/393); [ADR-0043](../adr/0043-a-session-import-sends-the-local-agents-raw-transcript-for-cloudpid-to-translate-and-moves-the-working-tree-only-through-the-repos-remote.md)) brings the whole active branch of a local pi Session, never a summary (that is `session_start(text, branch)`) and never the tree's other branches. cloudpid translates the raw pi file; the working tree moves only through the Repo's remote; the Session lands in a new Workspace on the same branch name, so coming back is `git pull`. D-numbers in this section are that ticket's.

### The import channel

- **For a program, never a model:** the `session_import_*` tools are driven by `/cloudpid` (see [_The `/cloudpid` command_](#the-cloudpid-command)); the owner's model-facing `cloudpid` entry hides them.
- **Order:** begin (which may refuse `branch_taken`), then the Local agent's pushes, then the slices, then finish (D4.1). A failed push calls `session_import_cancel` and deletes the carry ref.
- **Begin** checks `environment` (required; id or name), `format` (only `pi-session-jsonl`, else `unsupported_format`) and `size_bytes` (≤64 MiB, else `import_too_large`), registers the Session (status `importing`; like a Fork while it fills, it refuses messages and moves: see [_Client and protocol_](client-and-protocol.md) → Fork and Clone) and claims `branch` for its new Workspace (a spare if current). It returns `carry_ref`, which the server owns so its scheme can change while older bundles stay installed (D16; left to implementation: the scheme, today's Fork and Clone one being `refs/cloudpid/carry/<branch>`). `branch_taken` carries `details: {workspace, sessions: [{id, url, title, status}]}`. `text?` is kept with the import.
- **Append:** slices cut at any character boundary by UTF-8 byte offset (one pi line can reach 4.6 MB), ≤2 MiB of `data` each (the body cap is 5 MiB for JSON escaping). `offset` must equal `received`, else `offset_mismatch` with `details.received`; a repeated slice is a no-op. The Session object stores the slices as rows (`stageImport*`).
- **Finish** checks the size and `sha256` (`checksum_mismatch`), translates, waits ≤30 s inline, else returns `importing`; `session_wait` later reports `import_ended`. Its `summary` counts `cut`, `dropped` (by kind, `custom:<type>` for extension state) and `closed`; `warnings[]` (redacted) carries the model fallback and `context_over_window`.
- **Expiry:** an import with no append for 1 h expires (`import_expired`); an expired or cancelled one deletes its Session; a failed, cancelled or expired one discards its kept `text` (D23).
- **The Workspace** is always a new one or the spare, never an existing one (D7). It clones the branch in the cwd's Repo and applies the Carried Changes from `carry_ref` (the existing `apply_carry`; see [_Carried Changes_](workspace.md#filesystem-and-tools)). The Environment's other Repos are cloned onto the branch from `origin` when it has it, else from their default branch; no `base` is sent (D5, D19). Left to implementation: readying it only once finish has accepted the payload, the first point at which the pushes are known to be done.
- **Model and thinking:** `model` comes as `provider/id`. It is used if it is among the owner's Models, else the Environment's default with a `warnings[]` entry; `thinking` is clamped to what the model supports. The import never fails over either.
- **Title:** begin's `title` (pi's session name) as `titleSource: owner`; without one, the Session's title task runs once when the import ends.
- **Context Window:** at finish the context is estimated as the last assistant message's `usage` plus about 4 characters per token after it; over a threshold of the model's window (left to implementation) it adds a `context_over_window` warning (D21). Nothing compacts ahead: the first request takes the normal path (an Emergency Rollover from the mapped Handoff and the Note Index, or a Rollover request).
- **The instruction:** begin's `text` is submitted after the import notice once the import ends, marked as from the Local agent (`via`); without it the Session waits for the owner. Finishing an import sends no Notification; a Run it starts notifies as usual.
- **Usage:** imported turns record no Usage and never reach the Spend limit. Imported assistant messages keep their own `usage` field (it feeds the estimate above); pi's `usage` entries are dropped.

### Translation

- **Input** (`format: pi-session-jsonl`): the pi file's header line plus the active branch's entries (`getBranch()`), one `JSON.stringify` per line, byte-identical to the file. The server takes the path ending at the last line.
- **Mapping** onto pi-durable entries, filled into the root conversation through the Fork and Clone fill path (`importEntries`, heads and edits renumbered; [What does a local pi Session hold, and how could pi-durable take it in?](https://github.com/ian-pascoe/cloudpid/issues/379)):
  - `message` `user` / `assistant` / `toolResult` → `pi.user` / `pi.assistant` / `pi.tool-result`, same pi-ai types, content unchanged;
  - `compaction` → `pi.compaction` with `head` its first kept entry; `branch_summary` → `cloudpid.branch-summary`; `custom_message` (extension context) → a user-message entry; `context_edit` → `edits`;
  - system messages are never imported, and no `toolsRemoved` or system entry is written (they would break `findBaseline`);
  - `model_change` and `thinking_level_change` make no entries (begin's `model` and `thinking` set the Session's); labels, `session_info`, `usage` entries, header ids and `parentSession` are dropped; only message timestamps survive;
  - any other kind (for example pi's `bashExecution` messages, which pi keeps in context) is dropped and counted in `summary.dropped`; mapping one is left to implementation.
- **Extension state,** from Effect Schema copies of the three formats pinned in the translator (citing their source commit in `ian-pascoe/pi-extensions`, with sanitized fixtures from real sessions): the last `pi-todo-state` → `TodoDoc` (`rev: 1`); `pi-context-note` records replayed in order into `ContextDoc.notes` (`null` deletes); the latest `pi-context-handoff` → `ContextDoc.handoff`. Anything else, an unknown version, a failed schema or anything over cloudpid's limits is dropped and counted as `custom:<type>`, never failing the import (D13). Mapping other extensions' state, once cloudpid ports them, is left for later.
- **Bounds:** live caps first (images capped; an oversized image becomes a text placeholder); then each translated entry is held to cloudpid's largest live row total (about 5 MB, one exported constant) by middle-cutting its largest text parts, counted in `summary.cut`.
- **Tool calls** are kept, never dropped or flattened by default: providers accept history calls to tools the request doesn't declare when it declares at least one, and every cloudpid request does. A dangling call is closed with an error result ("Not run: the laptop's turn ended before this call had a result"), counted in `summary.closed`. A provider that rejects such history gets, for that provider only, calls to absent tools flattened into text; a live probe per provider is the translator's acceptance criterion (D25). MCP tool names in those calls are mapped through cloudpid's snake_case normalization, the same pure function as [_Tool names_](mcp-in-a-session.md#tool-names) (`mcp__x__getUser` → `mcp__x__get_user`), and unknown names are left as they are ([MCP tools in a Session: exposure, naming and the prompt cache](https://github.com/ian-pascoe/cloudpid/issues/381)'s input to the Session import ticket; D25 covers dangling calls and absent tools, not naming).
- **The import notice** is one model-visible user-role text entry, always the last imported entry (an invariant, tested). It names the laptop cwd; each Repo with its `/workspace/<dir>` and the branch; whether Changes were carried (the cwd's Repo only); whether Todo and Notes came across; any model fallback; the cut, dropped and closed counts; the laptop tools this Session lacks (≤30, then "and N more": "these ran on the laptop; you can't call them here"); and "the owner brings work back with `git pull` on `<branch>`: commit and push your work there when you finish".

### The working tree

- **Only through the Repo's remote** (ADR-0043): no file or patch upload, no `wip:` commit.
- **Commits:** the local branch is pushed as the branch, fast-forward only; a diverged remote refuses the import ("pull first").
- **Uncommitted Changes** (tracked and untracked, never ignored, so no `.env`) are read through a private index and force-pushed, hooks off, as one commit on HEAD to `carry_ref` (a port of `carryWorkspaceScript`'s `carry()`); with nothing to carry, a stale carry ref is deleted. The local index and work tree are untouched. Only the cwd's Repo carries its Changes (D19); carrying the Environment's other Repos' is left for later.
- **The branch:** the local branch's name, or its upstream's name on `origin`. On the default branch or a detached HEAD, `/cloudpid` prompts for a name (prefilled with a slug of the title) and runs `git switch -c`.
- **Importing again** onto a branch another Workspace holds is refused with `branch_taken`; `/cloudpid` offers removing that Workspace in the UI then retrying (warning that removal deletes its Sessions), a new branch name, or cancel (D15). Landing in the Workspace already on the branch, when it is clean, idle and an ancestor of the pushed HEAD, is left for later.
- **Coming back** is git only: `/cloudpid` prints `git switch <branch> && git pull --ff-only`, then `git stash drop`. The conversation stays in cloudpid (D12). A `/cloudpid-pull` helper and exporting a Session back to a pi file are left for later (D17).

### The `/cloudpid` command

- **Package:** `packages/pi-cloudpid` (`@cloudpid/pi-cloudpid`), a pi extension in this repo in the standard shape (dev loop `pi -e packages/pi-cloudpid/src/index.ts`). It may import `@cloudpid/protocol` and `@modelcontextprotocol/client` at the monorepo's pin (bundled: ADR-0036's import rule is about Workers); never `cloudflare:*`, workerd, alchemy, pi-durable or `@cloudpid/extensions` (oxlint `no-restricted-imports` and the build enforce it). It registers no MCP server: the model-facing `cloudpid` entry is the owner's own `~/.pi/agent/mcp.json` (managed OAuth) with `toolExposure: {"session_import_*": "hidden"}`, a snippet in the README.
- **Command:** `/cloudpid [instruction]`; everything after it is the instruction (begin's `text`); no subcommands, and not `/handoff`.
- **Configuration:** the endpoint's URL from `CLOUDPID_URL` (never `mcp.json`); the token from `CLOUDPID_ACCESS_CLIENT_ID` / `CLOUDPID_ACCESS_CLIENT_SECRET` (filled from Keychain or 1Password), sent as `CF-Access-Client-Id` / `-Secret`; unset, it refuses with setup steps; a 401 or 403 reads "service token rejected or expired: run `local-agent-token`". It sends `X-Cloudpid-Client: pi-cloudpid/<main sha>`.
- **Compatibility:** it checks `tools/list` for what it needs, else refuses with "the endpoint is older than this extension".
- **The Environment:** the repo root (`git rev-parse --show-toplevel`)'s `origin` normalized (scp-style and `ssh://` → `https://host/path`; userinfo, `.git`, a trailing `/` and case dropped) and matched against `environments_list`'s Repo URLs: one match is used, several give a select, none (or no git, or no `origin`) refuse with "add this Repo to an Environment first". No flag; it never creates an Environment.
- **Flow:** refuse unless `ctx.isIdle()` and the Session is persisted; a confirm shows the Environment, branch, commits to push, carried files (count and names), size and model; begin, push, slices, finish; print "imported", or "still importing; it will start on your instruction when done", with the URL and `summary`; offer `git stash push -u -m "cloudpid: imported as <url>"`; then `pi.appendEntry("cloudpid-import", {session, url, branch, environment})` and a notify. It never follows the Run. A `cloudpid-import` marker already on the branch asks "already imported as `<url>`; import again as a new Session?".
- **Distribution:** `bun build --target=node --format=esm` makes one `dist/index.js`, with the pi host packages (`@earendil-works/pi-*`, `typebox`) external as `peerDependencies: "*"`; `dist/package.json` has `pi.extensions` and no dependencies or scripts. After `Deploy prod` succeeds, a `pi-cloudpid` CI job (`needs: deploy`, `contents: write`, no deploy credentials) appends a commit naming the `main` SHA to the orphan branch `pi-cloudpid`, never force-pushing. The owner runs `pi install git:github.com/ian-pascoe/cloudpid@pi-cloudpid` once; `pi update` follows it. The extension is published only after the deploy it targets.

### The Local agent's service token

- **One per stage that serves the endpoint:** alchemy's `Access.ServiceToken` `cloudpid-local-agent` on `prod` and `cloudpid-local-agent-<label>` on the other stages (alchemy finds a token by name, so stages must not share one; `duration: "8760h"`), allowed by an inline Service Auth (`non_identity`) policy with `{serviceToken: <id>}` on the MCP endpoint's application only. It passes Access on `/mcp`; on `/` and `/rpc` Access answers it with a 302 to its login. Until the endpoint's slice gives the guard `/mcp`'s audience, the Worker's guard answers a request on `/mcp` (the token's or the owner's) with a bare 403.
- **CI:** the deploy and preview tokens need **Access: Service Tokens Write** (`a1c0fec57cf94af79479a6d827fa518c`, in `infra/github.ts`) to declare it; the main Worker needs only `MCP_SERVICE_TOKEN_CLIENT_ID` (and the application's `aud`, `CLOUDPID_MCP_ACCESS_AUD`), never the secret. A deploy that declares the token fails without the permission, so `ci:setup` runs before the change's preview deploys ([`docs/development/infra.md`](../development/infra.md) → _CI credentials_).
- **Reading it:** `bun --cwd infra run local-agent-token --stage <s>` prints the client ID, secret and `expiresAt` from alchemy state, on demand; the provider keeps the secret redacted, and CI never prints it.
- **Rotation:** bump `clientSecretVersion`, deploy, rerun the script; the old secret lasts until `previousClientSecretExpiresAt`. The provider has no refresh, so renewing at a year is the dashboard's Refresh or a new token.
