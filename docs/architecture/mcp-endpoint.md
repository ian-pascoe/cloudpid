# cloudpid's MCP endpoint and Session import

The **MCP endpoint** (GLOSSARY.md) is cloudpid's own MCP server at `/mcp`. A **Local agent** (pi first, on the Legacy lane; Claude Code second, on both lanes) works there as the owner: it lists Environments and Sessions, starts, messages, follows and stops Sessions, reads transcripts, makes a **Session import** of a local pi Session, and manages Environments and Settings with the tools a Session's agent has ([_Environment and Settings tools_](#environment-and-settings-tools)). It never asks the Local agent anything and answers nothing that waits for the owner: what needs the owner's Approval waits for them in cloudpid, and the caller can only follow it. The tool surface has no ADR: every choice can be undone by adding a tool, a field or a setting ([What cloudpid's MCP server offers](https://github.com/ian-pascoe/cloudpid/issues/392)). The Session import's contract with laptop code is [ADR-0043](../adr/0043-a-session-import-sends-the-local-agents-raw-transcript-for-cloudpid-to-translate-and-moves-the-working-tree-only-through-the-repos-remote.md). cloudpid's own agents as callers of the endpoint are neither a target nor blocked, except that a Session does not get the management tools from its own endpoint (see [_Self-use_](#self-use)). The management tools' design is [#685](https://github.com/ian-pascoe/cloudpid/issues/685) and [ADR-0050](../adr/0050-an-approval-asked-through-the-mcp-endpoint-is-kept-by-the-registry-and-applied-by-the-owners-approve.md).

## Access and identity

- **Its own Access application** ([Verify the MCP endpoint behind Access managed OAuth on a deployed stage](https://github.com/ian-pascoe/cloudpid/issues/419), "shape B"): on every deployed stage a shared `Cloudflare.Access.Application` (`self_hosted`) with `public` destinations `pi.ianpascoe.dev/mcp` on prod and `<appOrigin(stage) host>/mcp` elsewhere (`cloudpid-server-<label>.ian-g-pascoe.workers.dev/mcp`), which also covers sub-paths. It sits beside the Worker's owner-only application from `deployment(stage)`, which is unchanged. Managed OAuth is never turned on for the Worker's own application: there an OAuth token minted for `/mcp` would open `/` and `/rpc` too.
  - **`oauthConfiguration`:** access tokens `5m`, grant `336h`, DCR on with `allowAnyOnLocalhost` and `allowAnyOnLoopback`, and `allowedUris` with the stage's Self-use redirect URI ([_Self-use_](#self-use)) and executor.sh's callback, `https://executor.sh/api/oauth/callback`, so the owner can add the endpoint as an Executor app (`mcpOauthConfiguration(stage)`).
  - **Policies:** the owner-email Allow alone: there is no Service Auth policy, so no service token passes Access on `/mcp` (see [_The Local agent's service token_](#the-local-agents-service-token)).
  - **Its paths** stay outside `/oauth/mcp/*` and outside the bypass application of [ADR-0035](../adr/0035-cloudpid-identifies-itself-with-a-public-client-document-and-takes-authorization-responses-outside-access.md) (see [_The client document and the callback outside Access_](mcp-sign-in.md#the-client-document-and-the-callback-outside-access)).
- **Access is the authorization server** ([How can cloudpid serve MCP from behind Cloudflare Access?](https://github.com/ian-pascoe/cloudpid/issues/378)); the Worker has no OAuth code, no `workers-oauth-provider` and no `McpAgent`.
  - A cookieless `POST /mcp` gets `401` with `WWW-Authenticate: Bearer … resource_metadata="https://<host>/.well-known/cloudflare-access-protected-resource/mcp"`, which Access serves; the team's RFC 8414 metadata has a `registration_endpoint`. The RFC 9728 paths at the host root stay behind the main application (302); pi and Claude Code read `resource_metadata` from the 401 instead.
  - Access tokens are opaque; Access strips `Authorization` before the Worker. Refresh tokens rotate, and the old one stays usable, so a raced refresh doesn't fail.
  - Access checks a token only when it admits a request: a 300 s wait whose token expires midway finishes.
  - No WAF rule that requires a User-Agent may sit on `/.well-known/*` or Access's OAuth endpoints: Claude Code's discovery and DCR requests send an empty one.
  - Managed OAuth takes 1–2 minutes after a deploy to take effect (errors `1042`/302 until then).
- **The guard** ([Whether workers.dev stages serve the client document](https://github.com/ian-pascoe/cloudpid/issues/422) D9; its shared rules, the main routes and the `alchemy dev` local rule are in [_The client document and the callback outside Access_](mcp-sign-in.md#the-client-document-and-the-callback-outside-access)). It checks both audiences: the main application's on every route, and on exactly `/mcp` (`isMcpRoute`: the path normalised as the router reads it, so `/mcp/`, `/MCP` and a sub-path are main routes) the MCP endpoint's. On `/mcp` the main Worker verifies `Cf-Access-Jwt-Assertion` itself, failing closed, with `aud` equal to the **MCP endpoint application's** `aud` (the deploy-time var `CLOUDPID_MCP_ACCESS_AUD`, from the alchemy output), and classifies the caller from the assertion, never `ctx.access.getIdentity()`. The verdict carries who it is, a `Caller` that the guard provides to the route as the `AccessCaller` service:
  - **owner** (`{kind: "owner", clientId?}`): `email == OWNER_EMAIL`; the assertion's `oauth.client_id` (the DCR registration's opaque id) is its audit mark;
  - **local** (`{kind: "local"}`): the `alchemy dev` rule below;
  - anyone else: `403 not_owner`; a Worker without `CLOUDPID_MCP_ACCESS_AUD` refuses `/mcp` altogether (`not_configured`). An assertion with a `common_name` (a service token's) is refused on every route, `/mcp` included (`common_name`; there is no `service_token` caller), and on every other route so is an assertion without the main application's `aud` (`/mcp`'s alone), so neither credential opens the other's routes (Access already answers them there with a 302 to its login). An `aud` that lists both applications' audiences is admitted on either kind of route: on prod, once the owner had signed in to the MCP endpoint (managed OAuth) as well as the app, the owner's assertions on both routes listed both audiences (the guard's log, 2026-11-05; #419 had seen one `aud` on `/mcp`), and Access only lets a request through the policy of the route's application. Refusing them would refuse the owner's web app and `/mcp` alike.
  - Under `alchemy dev` (no Access) the local rule admits the owner on `/mcp` as on every guarded route, as `local`: `McpAuth` gains `"local"` beside `oauth` (and the retired `service_token`), so a Session started in local dev is marked as such, not as a credential it did not use.
  - **The claim profile it logs:** an admitted owner's assertion has its claim profile logged once per isolate per distinct profile, never the email, `sub` or `oauth.client_id`; `local` admissions (`alchemy dev`, no Access) log none; no verdict changes. What it holds, and how to read it, are in [_The Access guard_](mcp-sign-in.md#the-client-document-and-the-callback-outside-access).
- **Identity stays in `api`:** `ctx.access` doesn't reach `McpWorker`, so the request forwarded to `serve` carries no `Cf-Access-*` header (every header whose name starts `cf-access-`, whatever Access adds), no cookie and no `Authorization`; the main Worker closes the identity over the `api` target and never passes it as an argument. Both kinds of caller (the owner and `local`) get every tool.
- **The client's name** (display only, untrusted), the first present of: an `X-Cloudpid-Client` header sanitized to ≤40 characters (pi's `mcp.json` `headers`, or `/cloudpid`'s; the `cloudpid` server pi-cloudpid registers sends none, so a model's calls are named by Modern `clientInfo` or the `User-Agent`, i.e. "pi"); Modern `_meta["io.modelcontextprotocol/clientInfo"].name`; the first non-generic `User-Agent` product token (`claude-code`), skipping `node`, `undici`, `Bun`, `curl` and the like; else none ("via MCP").
- **Marks:** `SessionRecord` gains an optional `marks: {kind: "mcp" | "import", client?, auth: "oauth" | "service_token" | "local"}` (the server no longer writes `service_token`, since [#636](https://github.com/ian-pascoe/cloudpid/issues/636); records and inputs written under the old token still decode and show), beside `origin`, which stays the Fork and Clone origin alone, so a version that predates the marks still reads the record; each input sent over the endpoint carries `via`, its `SessionVia` `{client?, auth, era?}`, in the `cloudpid.user` entry. The API's own `Via` is `{client?, era}`: the main Worker adds `auth` from the verified caller before the Session object sees the request (`owner` is `oauth`; the `api` target's `auth` getter says it, and the span records it). A member a version does not know (a newer `auth`, `era` or mark kind) decodes as `unknown` or reads as none, never as a failure. The web shows "MCP · `<client>`" and "Imported · `<client>`" chips on the Session and "via `<client>` (MCP)" on inputs. A Session a Trigger started is marked `{kind: "trigger", auth: "trigger", trigger: {id, name}}`, and each input a Fire sent carries `via: {auth: "trigger", trigger}` ([`triggers.md`](triggers.md) → _Fire records, origin marks and notifications_); `McpAuth` gains `trigger` for them, which no caller of the endpoint has. The email is never recorded. The owner's `oauth.client_id` travels in the `Caller` and is recorded by the tools that start Sessions and by the management tools that change something (the `via` marks and an Agent change's `via`, as [Verify the MCP endpoint behind Access managed OAuth on a deployed stage](https://github.com/ian-pascoe/cloudpid/issues/419) suggested); the read tools have nothing to mark.
  - **As built** ([Start, send to and stop Sessions over `/mcp`](https://github.com/ian-pascoe/cloudpid/issues/456)): `session_start` writes the Session's `marks` (`kind: "mcp"`; the Registry keeps them in its origin columns) and marks the first input; `session_send` marks its input; both with `via` = `{client?, auth, era, clientId?}`, where `auth` comes from `identityOf(caller)`, never from an argument.
  - **Local dev:** a Session started under `alchemy dev` gets `auth: "local"`, the guard's own verdict (the owner on loopback, with no Access credential), rather than `oauth`, which would name a credential it did not use. Rejected: reading it as `oauth`, which would make the audit mark lie, and leaving the mark off, which would make a local Session look like a version that predates the marks.
  - **The owner's `oauth.client_id`** is recorded in `via.clientId` (an optional, gain-only member of `SessionVia`), in the `cloudpid.user` entry of every input the owner's grant sends, and in `agent_changes.via_client_id` for each Agent change a management tool makes ([_The recorded author_](#the-recorded-author)), and nowhere else: not in `marks` (which the Registry lists and `sessions_list` shows the Local agent as `origin`, and which would name one grant for a Session that several may later send to), not as a `SessionOrigin` (the Fork and Clone origin alone), and not only in the span (traces are not an audit trail: they are sampled, and absent where the runtime has no `tracing`). It is never shown: the web chip and the transcript text name the client alone, and local dev's inputs (and those written under the old service token) carry none.
  - **The web** shows `marks` as "MCP · `<client>`" (or "Imported · `<client>`") beside the Environment under the Session's title (`session-origin.tsx`), and `via` as a chip "via `<client>` (MCP)" under the input (`chat/via-chip.tsx`, from `TranscriptMessage.via`); with no client name they read "MCP" and "via MCP".
- **No switch:** there is no Settings toggle for the endpoint in v1. Access is the switch: revoke grants, or turn managed OAuth off.

## The handler

- **Where:** the main Worker routes `/mcp`, after the guard, to `MCP_SERVER.serve(request, api)`: the `McpServer` entrypoint of `McpWorker` (`apps/mcp-worker`), beside `McpEngine` ([ADR-0038](../adr/0038-the-mcp-host-object-lives-beside-the-registry-and-runs-the-sdk-through-a-stateless-engine-in-a-worker-of-its-own.md); see [_Packages and objects_](mcp.md#packages-and-objects)). `McpServer` binds neither the Registry nor the Sessions; it reaches them only through `api`, which it `dup()`s while its SSE body is open.
- **The SDK:** `@modelcontextprotocol/server`'s own `createMcpHandler` with `legacy: "stateless"`, pinned exactly with the client (2.4.0), not `agents`' ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D24; [ADR-0036](../adr/0036-the-mcp-core-is-the-official-sdk-inside-cloudpids-own-era-agnostic-module.md)). It adds `originValidationResponse` and `hostHeaderValidationResponse` (bare-fetch mounts skip them), and never imports the client core, the host object or pi-mcp. A new `McpServer` is made per request. The handler is `serveMcp(request, {api, version, gate, observe})` in `@cloudpid/mcp/server` (`packages/mcp/src/server/`), which knows nothing of Workers: `McpWorker`'s `McpServer` entrypoint (`apps/mcp-worker/src/server.ts`) wraps it, and the conformance run serves it over `node:http`. Its checks run before the SDK: `405` for any method but `POST`, `400` for an `Origin` or `Host` that is not the hostname of the request's own URL, and the SDK's `413` past 5 MiB.
- **Eras:** Modern `2026-07-28`, plus Legacy `2025-11-25`, `2025-06-18` and `2025-03-26` through `initialize`, both stateless: no `Mcp-Session-Id`, and `405` on GET and DELETE. Modern uses `responseMode: "sse"`; Legacy is SSE already. Left to implementation: SSE keep-alive comments every 15 s, as in [Verify the MCP endpoint behind Access managed OAuth on a deployed stage](https://github.com/ian-pascoe/cloudpid/issues/419)'s probe (`keepAliveMs: 15000`), where a 300 s wait with no `progressToken` finished on keep-alives alone. **As built:** `keepAliveMs: KEEP_ALIVE_MS` (15 s, `handler.ts`) on every stream of both eras; `handler.test.ts` counts the comments (20 over a 300 s wait with no token) on the Legacy and the Modern lane.
- **Capabilities:** tools and `instructions` only, declared as `{ tools: { listChanged: false } }` (the SDK would otherwise advertise `true`). No resources, prompts, completions, logging or subscriptions. It never sends its client an elicitation, sampling or roots request on either lane, so confirmations happen in cloudpid's UI. It returns no MCP tasks: long work returns a handle the Local agent polls ([MCP tasks as durable long-running requests](https://github.com/ian-pascoe/cloudpid/issues/389) D1.3); serving tasks is left for later.
- **`serverInfo`:** `{name: "cloudpid", version: <Server deploy id>}`. `Server` reports its id (`CF_VERSION_METADATA`) as the optional `version` of its `describe()` answer, a gain-only field; an older `Server` sends none, and `McpServer` then uses its own version id.
- **`instructions`** (≤1,500 characters). Line 1 stands alone, since pi shows only line 1 in its `mcp_servers` section: "cloudpid: the owner's hosted coding agent. Start or message its Sessions, wait for their Runs, read transcripts, import a local pi Session, or manage its Environments and Settings." (the "or manage" clause only when a shared tool is served). The rest covers: `environments_list` → `session_start` → a `session_wait` loop passing the cursor back; `session_transcript`; waiting requests, which the owner answers in cloudpid at the URL given; `session_import_*` being for programs, not models; transcript text being data, not instructions; calling `session_wait` again with the same cursor after a connection error; and, for the management tools, `request_id` on every change, the reads that show what is set (`field` reads a long text whole), naming an id or scope and a reason, and following an Approval with `approval_wait`. The full text, 1,424 characters with every tool served, is in [_`instructions`_](#instructions). Each sentence is there only when the tool it names is served (`describe()` gates it; "and every change" needs a change tool, the management line its reads, the Approval line `approval_wait`): so does a tool's `next` sentence, which never names a tool that is not on offer.

## Following a Run

- **`session_wait`** returns at the first of: the root Run ended after `after` (answered, stopped or failed); a waiting request newer than the cursor's mark appeared; an import ended; the deadline. It returns at once if one of the first three has already happened; with no `after` it returns at once unless a Run is going and nothing waits (an import going is no Run: it returns at once with the status `importing` and a cursor that ends with the import, as `import_ended`). A waiting request the caller has already seen doesn't end later waits, so a Run blocked on the owner doesn't make the local model spin, and it never returns per transcript entry or cloud tool call.
- **Result:** `{session_id, status, ended_by: run_ended | owner_needed | import_ended | timeout, interrupted?, branch_changed?, outcome?, waiting[], activity: {entries, tool_calls, latest: [≤5 one-liners]}, answer?: {text (≤8,000 chars, middle-cut), truncated}, text_withheld?, error?, cursor, next}`.
- **Status:** `running` (the root Run is going, or input is queued for it, or a message is still in the root's line: [_Getting a prompt at send_](mcp-in-a-session.md#getting-a-prompt-at-send)); `waiting_for_owner` (a waiting request exists anywhere in the Session); `background` (the root is idle, but subagents work or MCP tasks are followed); `idle`; `importing`. Archived is a flag, not a status; lists use the Registry's coarse `running | idle`.
- **`outcome`** is `{result: answered | stopped | failed, reason?, message?}` from the submission: `done` → answered; `aborted`, `withdrawn`, `reset` → stopped; `model_error` → failed, with "out of budget" as `reason: spend_limit`. A failed Run is an outcome, never an error.
- **Timeouts:** the 45 s default stays under every 60 s floor progress can't move (the TS SDK's default, Claude Code's first-byte timer). Waits up to 300 s rely on progress: whenever the request carried a `progressToken` (pi and Claude Code both send one), `McpServer` sends `notifications/progress` ("Waiting for the Run · 2m10s": `McpServer` does not know the Run's status while it waits, since nothing streams across `api`) at the start and every 10 s from its own timer, which re-arms pi's timeout and Claude Code's 5-minute idle timer.
- **Disconnects:** a client disconnect ends the wait, never the Run; the Session side still ends at its deadline. At most 8 concurrent waits per Session (`too_many_waits`); each pending wait keeps the Session object resident. If the RPC is cut on the Session side (a deploy, an eviction), the main Worker reads `status()` once and returns `ended_by: "timeout"`, `interrupted: true` and **the cursor that was passed in** (with none passed, the status's cursor with its marks cleared, so the next wait ends at once with what is already there and misses nothing that changed during the cut); only if that read also fails does it return `unavailable`.
- **The cursor** is opaque: base64url of `{conversation, entry id, waiting mark, newest settled input, importing?}`, valid for the Session's life. The settled-input mark is what tells a Run that ended after the cursor from one that ended before it, and `session_send` and `session_start` answer a cursor whose mark sits just before their own input, so a wait from it ends with that input's Run and no earlier one's. A waiting request has no time of its own: the Session object stamps each when it first sees it (kept in storage), and the mark is the newest stamp. The Session object re-reads its state every 500 ms while it holds a wait (`waitForChange`), rather than being pushed by events. A bad one is `invalid_cursor`. When the owner moves the active branch, results say `branch_changed: true` and the cursor keeps following the old conversation; a call without a cursor picks up the new one.
- **As built** ([Add `session_wait` and waiting requests to `/mcp`](https://github.com/ian-pascoe/cloudpid/issues/457)):
  - **The Session's side** (`waitForChange`, with its ended-by rules in `session/mcp-follow.ts`, the stamped waiting marks, the cap of 8 and `invalid_cursor`) came with the Session's endpoint in [#451](https://github.com/ian-pascoe/cloudpid/issues/451); this change adds the `api` operation and the tool over it. "A waiting request already seen doesn't end later waits" is tested at both layers: the pure rule (`mcp-follow.test.ts`) and over real storage, where the first wait ends as `owner_needed`, and a wait from its cursor then runs to its deadline (`mcp.workerd.test.ts`).
  - **`wait` on the `api` target** checks the id and asks the Registry first (a made-up id never wakes a Session object), sets the deadline to now plus `timeout_s` (45 s when not given), a number of seconds, fractions included, that the tool's schema holds to 0–300 and the target clamps to the same range again (the deadline is in milliseconds, so nothing is rounded), and makes the one RPC `waitForChange({after?, deadline})`. Its answer gets the Session's id, and each waiting request's `url` is made absolute at the request's origin, as `session_get`'s are. The Session's own refusals (`too_many_waits`, `invalid_cursor`, `unavailable`) pass through as values.
  - **Interrupted:** only an RPC that is cut or cannot be reached (a defect on the edge) is read as interrupted: the status is read once (`status({after})`) and the answer is `ended_by: "timeout"`, `interrupted: true`, `activity` empty, the status's `waiting`, `branch_changed` and `text_withheld`, and **the cursor that was passed in**, so a Run that ended or a request that appeared during the cut is still reported by the wait from it. With none passed, the cursor is the status's with `e`, `w` and `s` cleared (`unseen`, `api.ts`): the same conversation (and import flag), nothing seen. The status's own cursor would mark the newest finished Run and the requests now waiting as seen, so the next wait would never report them; the cost of the cleared one is that the next wait may end at once with the last Run's outcome or the requests that were already waiting, which a first wait with no cursor does too. Rejected: omitting the cursor (the result requires one, and `next` names it). Only if the status read fails too is it `unavailable`. A failure the Session answers as a value, `unavailable` included, is not an interruption.
  - **Progress** is `McpServer`'s own timer (`reportProgress`, `handler.ts`), for any tool that has a progress text (`session_wait` alone): `notifications/progress` at the start and every 10 s (`PROGRESS_MS`) while the call is open, only when the request carried a `progressToken`, on both lanes; the timer stops when the call settles or the request's signal aborts. `progress` is the seconds elapsed (kept increasing), with no `total`, and the message reads "Waiting for the Run · 2m10s", not "Run running": nothing streams across `api`, so `McpServer` does not know the Run's status while it waits. A client with no `progressToken` gets none and finishes on the keep-alives.
  - **A disconnect** ends the stream and `McpServer`'s side of the wait; the request carries no `AbortSignal` over RPC (`endpoint.ts` forwards `signal: null`), so the Session side runs to its deadline and holds one of its 8 slots until then, as the section above says.
  - **Words:** `session_start`'s and `session_send`'s descriptions and the `next` sentences point at `session_wait` where it is served, worded over the tools `McpServer` serves (`describe()`), as `instructions` are, so an older `Server` pairing never names a tool it cannot call. The `too_many_running` refusal is worded by the `api` target itself, over `MCP_API_OPERATIONS_SERVED` (`tooManyRunning`, `api.ts`): it names `session_wait` and `session_get` only where their operations are listed. That is the `Server`'s own list, not the `describe()` an `McpServer` has cached; deploy order (McpWorker first) keeps the two from disagreeing except in a rollback of `McpServer` alone. `session_wait`'s own `next` follows `ended_by`: after `run_ended`, `session_send` or `session_transcript`; after `owner_needed`, that only the owner can act, and to wait again from the new cursor.
  - **Telemetry:** a `session_wait` span records `ended_by`, `interrupted` and `waited_ms`.

## Transcripts

- **Rendering** happens in the Session object at read time, by a pure `renderTranscript` beside `projectEntries` in `@cloudpid/protocol`, so a page is cut by its rendered size and megabytes of tool results never cross the RPC. One block per entry, oldest to newest: `### user · 14:02` / `### assistant` headers with text ≤2,000 chars (`summary`) or ≤8,000 (`full`), middle-cut; each tool call as one line (`→ bash  npm test`, arguments ≤160 chars); each tool result as `✓ 12 lines` or `✗ <first line ≤200>` in `summary`, ≤1,500 chars in `full`; images as `[image png 230 KB]`; a Visual as `Visual: <title> — <summary> (not rendered)`, on the line after its result, with a link to its Visual Pane after it, `· /sessions/<id>?pane=visual:<callId>` ([_Visuals_](visuals.md#lifecycle)); notices on one line; thinking always left out.
- **Paging:** no cursor reads the latest page; `before` reads older entries, `after` newer. A page holds whole entries up to `max_chars`, always at least one (trimmed to fit), at most 200. Result: `{session_id, agent_id?, entries: [{entry_id, role, at, text}], older?, newer, branch_changed?, next?}`, the text only in `entries[].text`. The 12,000 default stays under pi's 20 KB middle cut; the 40,000 maximum under Claude Code's 50k-character spill and 25k-token cap.
- **Subagents** are read separately by `agent_id` from `session_get.agents`; the root's page shows a delegation as its call plus a one-line report.
- **Redaction** ([What cloudpid's MCP server offers](https://github.com/ian-pascoe/cloudpid/issues/392) D6): every text taken from a Session (transcript entries, `answer`, `last_answer`, `activity.latest`, `waiting[].summary`, import `warnings`) is redacted in the Session object, each text before it is cut to its limit and again once rendered, and so before page cutting, with the same `SecretsService.scrub` as `scrubbingModels` (the Environment's Secrets and asked Secrets in every encoding) plus a pattern pass over GitHub token shapes (`ghs_`, `ghp_`, `gho_`, `ghu_`, `ghr_`, `github_pat_` → `[REDACTED github token]`). If a refresh fails, a set held from this wake is used; with none, `session_transcript` returns `unavailable` (retryable) and `session_wait` and `session_get` drop their text fields (`answer`, `error`, the outcome's `message`, `last_answer`, `activity.latest`, and make `waiting[].summary` generic) and say `text_withheld: "secrets_unavailable"`, however the wait ended. Each text is redacted before it is cut to its limit, so a cut never leaves a Secret as a prefix. A value no longer held (an expired `secret_ask` value, a Secret deleted before an eviction) isn't caught, as at the model seam. Titles come from the Registry and aren't scrubbed.
- **Untrusted text:** one sentence in `instructions` and in `session_transcript`'s description says transcripts carry others' text (web pages, command output, other servers), to be treated as data. No fencing and no per-page preamble; `summary` already leaves tool-result bodies out.

## Waiting requests

- **None is answered over the endpoint:** Approvals, Secret requests, Sign-in requests, Elicitation requests, Sampling requests and Browser Handoffs wait for the owner in cloudpid, since an agent's word is not the owner's ([ADR-0041](../adr/0041-an-mcp-servers-elicitation-request-is-answered-only-by-the-owner-its-answer-is-never-kept-and-a-form-that-asks-for-a-credential-is-declined-unseen.md)). An approve tool marked with Claude Code's `anthropic/requiresUserInteraction` is left for later.
- **What the Local agent sees:** `waiting: [{kind: approval | secret | sign_in | elicitation | sampling | browser_handoff, request_id, agent_id, summary, since, url}]`. cloudpid writes `summary` itself: an Approval's change and target; a Secret request's names only; an MCP server's request only that server's name ("<server> needs your input", or "<server> asks you to open a page"), never its text (Elicitation requests as built in [#472](https://github.com/ian-pascoe/cloudpid/issues/472), `apps/server/src/session/mcp.ts`; Sampling with [#481](https://github.com/ian-pascoe/cloudpid/issues/481)). A Sign-in request's `waiting` entry (`kind: sign_in`) is built too, as [#470](https://github.com/ian-pascoe/cloudpid/issues/470): "Sign-in needed: <server>", never the agent's reason, with the card's `request-<id>` anchor. `url` is `/sessions/<id>?request=<request_id>`, and the Session page scrolls to that card.
- **Notifications** go out as usual for waiting requests and ended Runs, inputs sent over the endpoint included. No "being followed" indicator in v1.
- **As built** ([Add `session_wait` and waiting requests to `/mcp`](https://github.com/ian-pascoe/cloudpid/issues/457)): the Session page reads `?request=<request_id>` (`requestParamAtom`, `router.ts`) and scrolls to the card whose DOM id is `request-<request_id>` (`chat/request-anchor.ts`: Approval cards, Secret forms, Browser Handoffs, MCP elicitation cards and Sign-in cards (`chat/mcp-sign-in-card.tsx`, as [#470](https://github.com/ian-pascoe/cloudpid/issues/470)) carry it; `useRequestInView`, called by `WaitingRequests`, runs `followRequest` over the browser's page; the tests give it a page of their own), the way the Settings page scrolls to a field named after `#`: at once if the card is there, else when it renders, for up to 10 s, once per request named. A request already answered has no card and leaves the page where it is. The parameter is read only: opening or closing a Pane keeps it, and the Session's saved layout still applies, since only `pane` parameters stand in for it. Sampling cards do not exist yet; they take the same id when they do.

## Starting, sending and stopping

- **`session_start`:** `environment` is an id or an exact case-insensitive name (`ambiguous_environment` when several match), defaulting to `DEFAULT_ENVIRONMENT` as `createSession` does; the description says to omit it only for work tied to no Repo, and the result names the Environment and its Repos. `branch` and `base` follow `createSession`'s rules (`branch_taken` for a branch in use). `model` must be one of `environments_list.models.available`; `thinking` is `off`…`max`. A start always makes a new Workspace (a spare if current). No Role (a Role is picked when delegating). `request_id` dedupes starts for 24 h through the Registry.
- **`session_send`** takes only `text`, `when_busy` and `request_id` (the submit's idempotent `requestId`); model and thinking stay per-Session choices in the UI. `queue` is pi-durable's `followUp` (starts a Run when idle, else waits for the next one); `steer` joins the running Run at its next boundary; `reject` answers `session_busy`.
- **`session_stop`:** a plain Stop of the root withdraws queued input, and the messages still in the root's line (being prepared, or waiting their turn: [_Getting a prompt at send_](mcp-in-a-session.md#getting-a-prompt-at-send)), and leaves subagents running; `subagents: true` is Stop all. It returns once the Session is idle (≤30 s), else `stopping: true`, and leaves the transcript notice "Stopped from `<client>` (MCP)" ("Stopped over MCP" when the caller gave no name, as its chip reads "via MCP"). It is idempotent: a plain Stop while no Run is going (an idle Session, or only subagents working) does nothing and leaves no notice. A message in a line is not idle: a Stop that finds one withdraws it. The `session_send` that sent it answers `stopped` ("Stopped before it was sent"), as there is no submission to follow.
- **As built** ([Start, send to and stop Sessions over `/mcp`](https://github.com/ian-pascoe/cloudpid/issues/456)):
  - **`session_start`** checks its arguments before anything is made (`input_too_large`; `invalid_argument` for a `branch` or `base` that no branch can be named, a `model` outside `environments_list.models.available`, a `thinking` outside the levels, an empty `title`; `not_found` or `ambiguous_environment` for the Environment), then makes three calls in order: the Registry's `createSession` (a new Workspace, `marks`, `requestId`, `maxRunning`; the spare and Build upkeep run after the answer, as for the owner's own start), the Session's `configure` (only when `model` or `thinking` was given, so the first Run uses them), and the Session's `submit` of the first message. `branch_taken` and `too_many_running` are the Registry's refusals, and nothing is sent after one.
  - **`request_id` dedupe** has two halves that agree: the Registry answers the first Session of a `request_id` for 24 h (the table is `session_requests`), and the first message is submitted under the same id, which the Session already dedupes. A repeated start therefore makes no Session and sends nothing, answers the first one's cursor, and mends a start that was cut between the Registry and the Session (the repeat sends the message it never got). A repeat is answered before the cap is looked at, even when the Session was archived since (the Session answers a request id it has admitted before it checks it), and never runs `configure` again: the Registry marks the Session it answers for a repeated `request_id` (`repeated: true`), and only a first start picks the model, so a repeat cannot clobber a pick the owner changed. A repeat that finds the first message unsent (a start cut after the Session was made) sends it, and nothing else. `request_id` is global, not per identity.
  - **A start that fails after the Session was made** (its model could not be picked, its first message was not sent) answers the failure with `details: {session_id, url}` and says how to go on (repeat the call under the same `request_id`, or `session_send` to that id), so the caller never has a Session it cannot name.
  - **`session_send`** answers `not_found` from the Registry before any Session object is woken, and hands the rest to the Session's `submit` as the socket's admission does; `when_busy` is `queue` unless given (`followUp`). `session_stop` does the same with `stop`, and its Stop notice is the Session's (see above).
- **No confirmations:** there is no `confirm` argument. The caller is authenticated as the owner; spending is bounded by the Spend limit and the running cap.

## Environment and Settings tools

The endpoint serves the tools a Session's agent has for Environments and Settings ([#684](https://github.com/ian-pascoe/cloudpid/issues/684); design: [#685](https://github.com/ian-pascoe/cloudpid/issues/685)), so a **Local agent** can manage the harness it works with. The settled premises:

- **The in-session tools stay.** `/mcp` serves the same tools from shared definitions, over services the main Worker's `api` target implements on the Registry. Replacing the in-session tools with Self-use was rejected.
- **Approval still applies.** The caller is the owner's model, never the owner's yes ([ADR-0041](../adr/0041-an-mcp-servers-elicitation-request-is-answered-only-by-the-owner-its-answer-is-never-kept-and-a-form-that-asks-for-a-credential-is-declined-unseen.md)). A change that waits for Approval in a Session waits for it over the endpoint, kept by the Registry ([ADR-0050](../adr/0050-an-approval-asked-through-the-mcp-endpoint-is-kept-by-the-registry-and-applied-by-the-owners-approve.md); [_Approvals with no Session_](#approvals-with-no-session)).
- **What the agent changes through the endpoint is an Agent change** ([`agent-changes.md`](agent-changes.md)), recorded with who made it, listed under the Scope and revertible there.

The stages below are not built yet; until a stage lands, its tools are not served (`describe().harness`). What differs from the in-session tools is stated here; everything else is as [`agent-changes.md`](agent-changes.md), [`mcp-configuration.md`](mcp-configuration.md) and [`agent-capabilities.md`](agent-capabilities.md) say.

### Built so far: S1b

The read tools are split into shared definitions and cores; the endpoint does not serve them yet (S1d wires the dispatcher, so none of the five names is in `MCP_TOOL_NAMES`).

- **Definitions** are in `packages/protocol/src/harness-tools/` (`@cloudpid/protocol/harness-tools`): `environments_list`, `environment_list`, `environment_get`, `settings_get` and `settings_mcp_get`, with their input and output schemas, annotations and surface-dependent descriptions. An oxlint override in `packages/protocol/.oxlintrc.json` limits the folder's imports to `effect`, `@cloudpid/config` and its own files.
- **Cores** are `packages/extensions/src/environment-reads.ts`, `settings-reads.ts` and `settings-mcp-reads.ts`, with shared helpers in `harness.ts` (`HarnessRead`, text cutting, field pages). Each takes a `surface` and bounds; the in-session `defineEffectTool` wrappers call them with the session surface and the in-session bounds, and the session text and `tool_search` snapshot are unchanged.
- **Reads without a Session** are `environmentReads`, `settingsReads` and `settingsMcpReads` in `apps/server/src/session/`; the Session builders spread them, so the same reads serve a caller with no Session.
- **Errors** carry an optional `code` (`not_found`, `invalid_argument`) for the dispatcher to map.
- **Endpoint output** is built from the endpoint's structured value, not from the in-session text: flat objects with optional keys, `_truncated` flags, and a field page whose text ends in a `[Characters a-b of N …]` footer. `settings_mcp_get` leaves an entry or the layers out when they pass 4 KiB (`entry_truncated`, `layers.truncated`), and sheds parts until the answer fits 56 KiB.

### Shared definitions and the core/wrapper split

- **`@cloudpid/protocol/harness-tools`** (a new subpath) holds, for every shared tool: its name, input and output schemas and annotations; its descriptions, with the sentences that differ by surface; and the description pieces they use (`SIZE_LINES`, `PLAIN_VALUES`, `Reason`, `idOrGlobal`). `McpServer` and the in-session extensions both import it, so a description is written once.
  - **Its import rule** is `effect` and `@cloudpid/config` only, enforced by an oxlint override or a bundle check in McpWorker (pi-cloudpid's `build-check.ts` is the model). `@cloudpid/protocol` depends on pi-durable today (`conversation-id`, `mcp-api`, `mirror`, `session`, `transcript`, `view`), and only convention keeps that out of McpWorker; the subpath makes it a rule.
- **Each in-session tool splits in two.**
  - A **core** in `@cloudpid/extensions`: an Effect over the services (`Environments`, `SettingsAccess`, …) plus an author and a surface. It makes the checks and the service call, and returns the result text and the structured output. It never touches `ToolExecutionApi`. Each core that can wait for Approval exports `prepare`, `apply` and `render` ([_Approvals with no Session_](#approvals-with-no-session)).
  - The `defineEffectTool` **wrapper**: replay, `executionMode`, memos, `AgentChangeLog`, `details`. The in-session behaviour is unchanged; the session surface's text stays byte-identical to today's (the prompt cache and `tool_search` read it), which S1 tests.
- **No Session.** The services a core uses are written so that a Session is not needed:
  - **Reads:** S1 extracts `environmentReads(registry)` (list, get, global) from `session/environments.ts`, with `current` = `succeed(null)` on the endpoint, and the same for the Settings and `settings_mcp` reads.
  - **Writes:** S2a replaces `session: string | undefined` in `sessionEnvironments`, `sessionLifecycle`, `sessionSettingsAccess` and `sessionSettingsMcpAccess` (and S3b's `sessionEnvironmentRemoval`) with an **author source**, `{kind: "session", id}` or `{kind: "endpoint", via, request?}`. Extension `ChangeAuthor.conversation` becomes optional.
  - S2a creates one shared module that builds these no-Session layers (for example `apps/server/src/harness/layers.ts`), used by `/mcp`'s `api` target and, from S3a, by the Registry RPC's approve route. S1d creates `apps/server/src/harness/services.ts` (reads) and `harness/dispatch.ts`.
  - `McpEndpoint` (the route's handle on the main Worker) gains `mcpHosts` (the host inventory the `settings_mcp` reads use) and `appOrigin` (the Self-use rule) in S1d, then `builds.rebuild` and `mcp` in S2a.
- **The `api` target** runs the core over those layers and returns `{text, structured}`; `McpServer` adds the envelope, the caps and `next`. The text of a shared tool is therefore built by the `api` target, not by `McpServer` (see [_The `api` target_](#the-api-target)).

### Names and surfaces

- **The same names as in-session**, `environments_list` (the session tool) included. The descriptions name each other: `environments_list` is "pick an Environment or a model for `session_start`", `environment_list` is "manage". The `next` sentences differ. On `/mcp` no Environment is marked "this Session's".
- **`surface: "session" | "endpoint"`** is a parameter of the shared descriptions and cores, with neutral sentences by default. On the endpoint:
  - `environment_create` says "start a Session in it with `session_start` and this id";
  - `environment_secret_build` says the owner keeps Secrets on the Secrets page;
  - `settings_mcp_add`, `_update` and `_enable` report the status `not_checked` and say "`settings_mcp_get` shows it later; the owner signs in on the Settings page" (the in-session tools wait up to 10 s for the status);
  - a change to a Container setting says it applies "at each Workspace's next Container start" ([_After a change_](#after-a-change-and-notifications)), with no `container_restart` pointer.
- **Every harness tool's output schema is a flat object**, with optional keys for variant fields (a field page included). On the Legacy lane `outputSchema` must have `type: "object"` at its root, and the pinned SDK (`@modelcontextprotocol/server` 2.4.0) wraps a non-object root as `{result: …}`, which would give `structuredContent` a different shape on each lane.

### The dispatcher and `describe().harness`

- **One dispatcher:** `harness({tool, input, requestId?, via})` → `ApiResult<{text, structured, pending?}>`. `describe()` gains an optional `harness: string[]` (`HARNESS_TOOLS_SERVED`), and `operations` gains `harness`. `McpServer` offers tool T only when it knows T's declaration **and** `describe().harness` lists T; a deploy that serves a tool in `Server` before `McpServer` knows it, or the reverse, shows fewer tools, never a broken one ([_Version skew_](#the-api-target)).
  - The dispatcher decodes `input` again with the shared schema and handles `request_id` in one place ([_Retries_](#retries-request_id)).
  - A path a stage has not built yet (a Limit's reset before S3a) is refused as `unsupported`, naming the stage.
- **Endpoint-only tools** get their own operations, as `wait` does: `approval_wait` and `approval_withdraw` (S3a), and later `environment_test_build_wait` and `_cancel` (S4a). `describe()`'s `operations` lists `approvalWait` and `approvalWithdraw` once S3a serves them.
- **Annotations** use the legend above: **RO**, **W·idem**, **W**, **D·idem**, and **D** (a destructive, non-idempotent write). `openWorldHint` is false except on `environment_skill_install` and `_update` (they reach GitHub), `settings_mcp_reload` (it reaches the MCP servers), `session_start` and `session_send`.
- **How the Session's needs map to the endpoint:** Secret checks → [_Secret checks_](#secret-checks); `AgentChangeLog` → [_After a change_](#after-a-change-and-notifications); a card's `details` → the result only; replay → `request_id`; root-only → [_Self-use_](#self-use).
- **C†** (Container setting tools): the main Worker runs the Builds' and spares' upkeep, and the text says "at each Workspace's next Container start". **S‡** (Settings tools): no reload; the text says Sessions pick it up at their next admitted input.

### The recorded author

- **The author source** ([_Shared definitions_](#shared-definitions-and-the-corewrapper-split)) carries `via` from the verified caller: `auth` comes from `identityOf(caller)`, never from an argument, as `session_start`'s marks do.

### Secret checks

- **Shape checks** (GitHub token shapes, the GitHub App's key, Secret Reference placeholders) run in the shared core, as in a Session.
- **The Registry also checks every text a write keeps** (the `reason` included) against the kept Secrets, in the encodings `Redactions` knows. This runs **only for writes whose author carries `via`**; in-session writes are unchanged. An Environment write checks that Environment's Secrets plus Global's; a `*` write checks every Scope.
  - **When:** the vault opens asynchronously and Registry writes are `transactionSync`, so the check runs in the same Registry call just **before** the transaction, which re-reads a stamp (the count and the maximum `updated_at` of the Secrets over the Scopes) inside and refuses "kept Secrets changed meanwhile, try again" when it differs. It runs again when an Approval request row is written (S3a), and again at apply. A deploy-skew probe, `agentChangeFeatures()`, makes a core refuse (fail closed) while the Registry is still on code that does not check.
  - **Not covered:** `secret_ask` values one Session holds, and values resolved from 1Password.
  - **Cost** (an estimate): at most 200 vault opens for an Environment write, and at most 100 × (Environments + 1) for `*`. S2a's workerd test times the worst case; a cache of opened Secrets is added only if it is needed.

### Retries: `request_id`

- **An optional `request_id` on every tool that records an Agent change**, on `/mcp` only (the in-session schemas do not get it). A repeat with the same id returns the first answer; the same id with other arguments is `invalid_argument`. Reads, `settings_mcp_reload` and the endpoint-only `approval_*` tools take none.
- **The table is `change_requests`** (a Registry migration; at the time of writing the next free after `via`'s, 36), not `session_requests`, which is STRICT with `session NOT NULL`. It holds `{id, tool, args digest, answer}` for 24 h. The final `{text, structured}` is stored (≤64 KiB) and replayed. The first claim is written in the change's own transaction. For an effect outside the Registry (a Test Build), the row is written after the effect and the effect's id is derived from the `request_id`.
- **Replaying a claim with no answer** (the first call was cut after its write): an answer is built from the recorded changes and returned at once with `replayed: true`. The settle is awaited before the reply, and the after-steps run in the background; `upkeepFor(changes)` is extracted from revert for that. An id beginning `approval:` is refused on the endpoint (it is the Registry's own, for an approved apply, below).

### After a change, and Notifications

- **The main Worker runs the Builds' and spares' upkeep** as after the owner's save. **Nothing is pushed to live Workspaces or Sessions:** Workspaces take a change at their next readying or Container start, and Sessions at their next admitted input. The text says so: no `container_restart` pointer and no "your next request".
- **A Notification per call that made changes.** A new `pushOwner({title, body, url, tag})` in `apps/server/src/push`, with no Session, sits beside `pushNotifier` and shares its send (`pushNotifier` returns early without a Session, and `describeEvent` needs one). The service worker (`apps/web/public/sw.js`) already opens any same-origin URL.
  - One Notification per call, tagged `mcp-changes:<clientId ?? client>`, so a burst replaces itself. The body lists that caller's changes from the last 10 minutes and links to the Scope's Agent changes section (`agentChangesPath(scope, id?)`).
  - The Approval's Notification (`input`) is tagged `approval:<id>` and links to its `url`.
- **Failures after the write** (an upkeep step, the McpHost push) leave the change standing, with a warning in the text, and heal as after the owner's save.

### Approvals with no Session

[ADR-0050](../adr/0050-an-approval-asked-through-the-mcp-endpoint-is-kept-by-the-registry-and-applied-by-the-owners-approve.md) is the decision; this is the shape.

- **Asking.** The tool keeps its in-session name. Its core's `prepare(args)` only reads, and returns a refusal, `unchanged`, or `{card, expected}`. Otherwise the Registry stores a request `{id, tool, args (decoded), scope (an Environment's id, or *), card ("asked via <client> (MCP)"), expected, author: {tool, reason, via}, request_id?, status, created_at, expires_at (7 days), outcome?}` and an `input` push goes out (`pushOwner`). The tool answers `{status: pending, approval_id, url, expires_at, next}` and is W (it takes `request_id`).
  - **The URL** is `/settings/<all|id>/<section>?request=<id>`. There is no separate Environment page: both Scopes are `SettingsPage`. `settingsPath`, `GLOBAL_SEGMENT` and `agentChangesPath(scope, id?)` move to `@cloudpid/protocol` in S2a. The page scrolls to the card as a Session's does (`useRequestInView`).
  - **Limits.** At most 10 pending per identity (`too_many_approvals`); the identity is `auth` (oauth or local), and the count is the pending rows plus the approved ones not yet finished. Asking for the same tool, target and value while one waits returns that one: dedupe is a global digest that leaves out the reason and `request_id`, and a different `expected` supersedes the older row.
  - The Secret check runs when the row is written (S3a) and again at apply ([_Secret checks_](#secret-checks)).
- **Following.** `approval_wait({approval_id, timeout_s? 0–300, default 45})` is RO, with progress as `session_wait`'s (0 makes it a get). It answers `{status, finished, reason?, result?}`. The stored statuses are `pending`, `approved`, `finished`, `declined`, `changed_since`, `refused`, `expired` and `withdrawn` (`superseded` and `environment_deleted` are outcomes, not statuses); `approved` with `finished: false` is an apply not done yet. `approval_withdraw({approval_id})` is D·idem. Both are endpoint-only, with their own `api` operations. A settled row is kept for 24 h, then `not_found`.
- **The owner's Approve applies the change.** The approve/decline route is the Registry RPC's, under the main Access application and not `/mcp`. It records `approved` first, then the main Worker runs the tool's `apply(args, expected, author, known?)`. `apply` re-reads the Scope's view when `known` is absent and builds "before" from `expected` (an in-session closure captured it before the ask). It makes the Registry write with `expected`, then the after-steps (Builds' and spares' upkeep, `removals`, the McpHost push). The outcome `{text, structured}` goes in the row.
  - **The Registry's refusal** settles `changed_since` or `refused`, and the card says "Not applied: … is now …".
  - **A partial or cut apply** stays `approved`, not finished, and resumes idempotently. **The triggers** are: the card's **Try again**; the caller's `approval_wait` (except a long apply, such as deleting an Environment); and the owner's next visit (`background(approvals.resumeStale)` on `listSessions` and `listApprovals`). **There is no Registry alarm**: the Registry has none, and it cannot run `removals`. Every step is idempotent, because the context is cancelled on a disconnect, `waitUntil` gives at most 30 s and a Worker's subrequests are limited ([`workers-long-apply.md`](../research/workers-long-apply.md)).
  - **The attempt** of an approved apply is the approval's id (stable), recorded as a `change_requests` claim under `approval:<id>`, and the row's lease keeps two runs from applying at once. On resume: a claim with an answer finishes with that answer; one with no answer, for a single-write tool, builds the answer from the recorded changes ([_Retries_](#retries-request_id)) and finishes; one with no answer, for a multi-write tool (a Global Skills install or update), reruns `apply` under the same attempt (Skills already applied come back unchanged); no claim runs `apply`. Settle the claim, then finish the row.
  - **After-steps that fail** once the write is committed leave the change standing with a warning, and heal as after the owner's save.
- **In a Session the same `prepare`/`apply` run.** `prepare` → `withApproval` in the Session's store → `apply` → the Session's own after-steps (hand-over, `SettingsReload`, the 10 s MCP status wait, `AgentChangeLog`). The in-session code already applies from `(args, expected)`. Session-held Approvals stay as they are; `ApprovalAsk` moves to `@cloudpid/protocol` to be shared.
- **The card** is the same component with the same content, on the target's Settings page in a "Waiting for you" area. A request is withdrawn on expiry, by `approval_withdraw`, or when its Environment is deleted.
- **A Skill save's files at `*`** (S4b): the row holds `{name, files: {path: hash}}`, and the texts live in `skill_files`, which `dropUnreferencedSkillFiles` keeps while a row references them. S3b's Global Skills rows hold pins, never file bodies.
- **The owner's route** gains a cross-origin check as its own PR (S3a-0): `Sec-Fetch-Site` is read first and only `same-origin` is admitted; without it, `Origin`'s host must be one the request names; with neither header the call is admitted. It applies to `/rpc` and the Session socket upgrade, as `answerForm` does. A refusal of an approve whose caller carries `oauth.client_id` was considered and dropped: it rests on an unverified claim profile, and Access routing, the guard's audience and this check already cover it.

### Reading a whole field, and the endpoint's limits

- **`field` and `offset`** (S1), on the endpoint only: `environment_get` and `settings_get` take `field?` and `offset?`. `field` is an Agent-change field path: `setupScript`, `startScript`, `toolchains`, `ignore`, `variables.<NAME>`, `instructions`. The answer is `{id, field, text, offset, total_chars, next_offset?}`. A page is at most 40,000 characters **and** at most 48 KiB stored. A cut `environment_get` says "pass `field` to read it whole".
- **`environment_get` on the endpoint** lists every variable in force (at most 50) by name, with values cut at about 160 bytes and a per-item `value_truncated`. `environment_get` can reach about 800 KiB in a Session, so the endpoint cuts harder, with `_truncated` flags, and never past `content` ≤12,000 characters and `structuredContent` ≤64 KiB ([_Limits and errors_](#limits-and-errors)).
- **Per-tool limits** are the in-session ones (the 64 KiB script, the 16 KiB Toolchains, the 4,096-character variable value, a `reason` of 1–500 characters). A Skill save's total file text is at most 2 MiB (`MAX_MCP_SLICE_BYTES`), and the description sends bigger Skills to `environment_skill_install`.

The text of [_The handler_](#the-handler)'s `instructions` bullet with every tool served (1,424 characters, line 1 being 180):

```
cloudpid: the owner's hosted coding agent. Start or message its Sessions, wait for their Runs, read transcripts, import a local pi Session, or manage its Environments and Settings.

session_send messages a Session (when_busy: queue, steer or reject). session_stop ends its Run; the owner is told.

To manage rather than start: environment_list, environment_get and settings_get show what is set (pass field to read a long text whole); the other environment_* and settings_* tools change it, naming an id or scope ("*" is Global) and a reason. The owner sees and can revert each change.
A change that needs the owner's Approval answers pending with an approval_id: follow it with approval_wait.
A request waiting for the owner (an approval, a secret, a sign-in) is answered by the owner in cloudpid at the url shown, never by you.
The session_import_* tools are for programs, not models.

```

Each sentence is there only when the tool it names is served: line 1's "or manage its Environments and Settings" clause only when a shared tool is served; "and every change" only when a change tool is served; the "To manage" line only when its reads are served; the Approval line only when `approval_wait` is served.

## The `api` target

`api` fills in [ADR-0038](../adr/0038-the-mcp-host-object-lives-beside-the-registry-and-runs-the-sdk-through-a-stateless-engine-in-a-worker-of-its-own.md)'s `serve(request, api)`: an `RpcTarget` the main Worker builds per request over the Registry and Session code it has (`apps/server/src/mcp/api.ts`; types in `@cloudpid/protocol`'s `mcp-api`).

```ts
type Via = { client?: { name: string; version?: string }; era: "legacy" | "modern" };
type ApiResult<T> = { ok: true; value: T } | { ok: false; error: { code; message; retryable; details? } };
interface McpApi {
  describe(): { operations: string[]; limits: { maxInputBytes; maxSliceBytes; maxImportBytes; maxWaitMs }; version?: string; harness?: string[] };
  environments(); sessions(q); session(id);
  start(r & { via }); send(r & { via }); wait(r); transcript(r); stop(r & { via });
  importBegin(r & { via }); importAppend(r); importFinish(r); importCancel(r);
  harness(r & { via }); approvalWait(r); approvalWithdraw(r); // the management tools (S1 on; the approvals S3a on)
  limited?: { retryAfterS: number }; // a getter: `await api.limited` counts one call, and answers only when over the rate
  auth?: "oauth" | "service_token" | "local"; // a getter: how the caller got in, for the span (`service_token` is no longer produced)
}
```

- **Absolute URLs:** every `url` the result holds (a Session's page, a waiting request's) is built from the origin of the request's own URL, so a preview stage links to itself. `sessions`' `environment` is resolved in `api` (an exact id, else an exact name in any case, `not_found` or `ambiguous_environment` otherwise), not by `McpServer`, which knows no Environment. A Session id is checked to be a UUID, and a Session the Registry does not know is `not_found`, before any call reaches a Session object (so a made-up id never makes one). A failed RPC or a defect on any of these edges is `unavailable`.
- **Served:** `describe()` lists the operations this version has (`environments`, `sessions`, `session`, `transcript`, `start`, `send`, `stop`, `wait`, and the import channel's `importBegin`, `importAppend`, `importFinish`, `importCancel`: `MCP_API_OPERATIONS_SERVED`; the management tools add `harness` from S1 and `approvalWait` and `approvalWithdraw` from S3a, and `describe().harness` lists which of them it serves); an operation it does not list has no method on the target (a `Server` that predates it), which `McpServer` reads as `unsupported`, which is how a `McpServer` that is ahead of `Server` finds out and leaves the tool out. A tool is added to `McpServer` and its operation to `MCP_API_OPERATIONS_SERVED` together, so an older `McpServer` or `Server` pairing shows fewer tools, never a broken one.
- **The main Worker owns** authorization, validation, Registry and Session calls, cursors and rendering; **`McpServer` owns** the SDK, schemas, descriptions, the text and `structuredContent` envelope, framing caps, progress and error mapping. **The exception is the management tools** ([_Environment and Settings tools_](#environment-and-settings-tools)): the `api` target's `harness` operation runs the tool's shared core and returns `{text, structured}`, which `McpServer` only wraps (the envelope, the endpoint's caps, `next`), because the same text is the in-session tool's result. `McpServer` still knows the tool's declaration from `@cloudpid/protocol/harness-tools` and offers it only when `describe().harness` lists it. Failures travel as values. Nothing streams across `api` in v1.
- **New Server pieces:** the Session object (socket-only today) gains RPC methods `status()`, `waitForChange({after, deadline})`, `transcriptPage(…)`, `submit({input, whenBusy, requestId, via})` (the socket's admission), `stop({subagents, via})`, `configure({model?, thinkingLevel?})` (the socket's `configure`, `agentChange` shared, and open pages are told the pick, for a start that names a model) and `stageImport*`; `createSession` gains `marks`, `requestId` and `maxRunning`; `sessions()` filters and pages `listSessions`.
- **Version skew** ([Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423) D1): every edge only gains (methods, optional fields). `McpServer` deploys before `Server`, so it gates its tools on `describe()`, cached per isolate for 60 s: a tool appears only once the deployed `Server` supports it, and a missing method answers `unsupported`; the management tools add a second gate, the tool name in `describe().harness`, so a `Server` that serves some of a stage's tools shows only those. The main Worker → Session edge has no gate (a loud failure that heals; the import's `stageImport*` calls on a Session object still on the previous code fail as `unavailable`, and begin deletes the Session it made); main Worker → `McpServer` relies on deploy order (Workspaces → McpWorker → Server). The tools change only additively; a breaking change is a new tool or `format`. The other MCP edges' gates are in [_Deploys_](mcp.md#deploys).

A call is counted when `McpServer` awaits the `limited` getter of the `api` target, once per `tools/call` (not per HTTP request: a `tools/list` costs nothing), and `retry_after_s` is the 60 s period, since the binding does not say when a key frees. | Imports                                                 | slices ≤2 MiB of `data`, ≤64 MiB in total, ≤2 open per identity, 1 h with no append                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

- **Domain failures** are `isError` results with `structuredContent: {error: {code, message, retryable, details?}}` and one actionable sentence. `stopped` answers a `session_send` the owner's Stop withdrew before it was placed (also when it is sent again under the same `request_id`); it is never retryable. Codes: `not_found`, `ambiguous_environment`, `invalid_argument`, `invalid_cursor`; `session_busy`, `session_importing`, `session_archived`, `branch_taken`, `stopped`; `input_too_large`, `too_many_running`, `too_many_waits`, `rate_limited`; `offset_mismatch`, `import_too_large`, `import_expired`, `checksum_mismatch`, `unsupported_format`; `unsupported`, `unavailable`; and for the management tools `too_many_approvals`, and `invalid_argument` for a `request_id` reused with other arguments or an `approval:`-prefixed one. A management tool's refusals (an unknown id, a value the owner's save would refuse, a Secret check, a path a stage has not built: `unsupported`, naming the stage) are domain failures as above; an Approval's outcome (`declined`, `changed_since`, `refused`, `expired`, `withdrawn`) is a status of `approval_wait`, never an error.
- **As built, the running cap** ([Start, send to and stop Sessions over `/mcp`](https://github.com/ian-pascoe/cloudpid/issues/456)): the cap is the Registry's `createSession` input `maxRunning: 10`, and it counts in the same transaction that inserts the Session, so starts made in parallel cannot all pass it. It counts the Sessions whose origin is `mcp` or `import`, not archived, that are `running`, or were made less than 2 minutes ago and have not yet reported a Run (their status has not changed): a start's first Run is reported a moment after it is made, and without the second term a burst of starts would all see the same count. The owner's own starts pass no cap, and neither does `session_send` to a Session that is idle: only a start is capped, so a Session sent to again may run beside ten others. A refusal is `too_many_running`, retryable (it clears when a Run ends), with `details: {limit}`, and registers no Workspace. The edge has no gate (`mcp.md` → Deploys): a Registry still on the previous code, for the few minutes a deferred update may take, ignores `maxRunning` as it does `marks` and `requestId`, so the cap can be passed in that window.
- **An oversized page:** a page is cut by characters where it is read, and a character can take up to six bytes of JSON, so `structuredContent` can pass 64 KiB (CJK text, control characters). `session_transcript` then answers a non-retryable `invalid_argument` saying to ask again with a lower `max_chars`; the same request would fail again. Any other tool's oversized result is a non-retryable `unavailable`.
- **Schema failures** are the SDK's `isError` results; only an unknown or disabled tool is `-32602`.
- **HTTP:** `401` from Access; `403` for a caller who isn't the owner; `405` for GET and DELETE; `413` for an oversized body; `400` for a bad `Origin` or `Host`; `503` (`Retry-After`) when the main Worker cannot reach `McpServer` (a deploy behind or cut).

## Self-use

No guard stops a cloudpid Session from using its own MCP endpoint ([#644](https://github.com/ian-pascoe/cloudpid/issues/644)). The owner adds `https://<host>/mcp` as an HTTP MCP server (it takes the owner's Approval for the definition when the agent adds it, see [_Approval_](mcp-configuration.md#approval)) and signs in with cloudpid's own MCP sign-in, through Access managed OAuth like any OAuth server:

- **The sign-in** registers cloudpid over DCR at Access, which advertises neither the client document nor `iss`, with `none` auth and the redirect URI `https://<origin>/oauth/mcp/callback/<hash of the team's issuer>` ([_Client registration_](mcp-sign-in.md#client-registration)). Managed OAuth takes DCR redirects on loopback and localhost, and that exact URI, listed per stage in `allowedUris` beside executor.sh's callback (`selfUseRedirectUri(stage)`, `apps/server/src/mcp-access.ts`).
- **The fetches to its own host.** `McpWorker`'s engine reaches `https://<host>/mcp` with the owner's bearer; it has `global_fetch_strictly_public`, so the request goes through Cloudflare's front door and passes Access as an external client's would, rather than failing as a Worker's fetch to a Worker on the same zone (error 1042; `workers.dev` hosts included) or reaching the origin past Access. The Registry's one sign-in read on the host, the resource metadata Access serves there (named by the endpoint's 401, which a start with none recorded asks for first), is made from `McpWorker` too (`fetchPublic`; [_Code_](mcp-sign-in.md#tokens-reach-the-host-object)); the registration and the token requests go to the team's own host, from the Server Worker. The Server Worker has no such flag.
- **The guard** admits the calls as the owner, with the registration's `clientId` ([_Access and identity_](#access-and-identity)): an assertion that lists both applications' audiences is admitted on `/mcp`, and nothing in the guard changed for Self-use.
- **The rule** ([#684](https://github.com/ian-pascoe/cloudpid/issues/684)): an HTTP MCP server whose URL is this stage's own endpoint registers none of the tools that have an in-session twin: every tool declared in `@cloudpid/protocol/harness-tools` (`HARNESS_TOOL_NAMES`, the keys of `HARNESS_TOOLS`), the endpoint-only ones (`approval_*`, `environment_test_build_*`) included. The session tools (`environments_list`, `sessions_list`, `session_*`: `MCP_TOOL_NAMES`) stay. With the management tools never registered, root-only has nothing to catch, and the Session's own `environment_*` and `settings_*` tools are the only ones it sees.
  - **`isOwnEndpoint(url, appOrigin)`** is pure: `new URL(url).origin === appOrigin` and the pathname is exactly `MCP_ROUTE`, normalised the way `isMcpRoute` normalises it (`/mcp/` and `/MCP` count). It lives in `packages/extensions/src/mcp/exposure.ts` beside `reachesModel`; `MCP_ROUTE` moves to `@cloudpid/protocol`. The Session passes `env.CLOUDPID_APP_ORIGIN` (`APP_ORIGIN_VAR`); without it (`alchemy dev`) the rule is off.
  - **Where it applies:** everywhere `reachesModel` does (`mcp/tools.ts`, `mcp/servers.ts`, `settings-mcp-values.ts`), computed in `mcp.ts` beside `signIn` (`McpBuildServer` drops the URL) and filtered in `listedTools`.
  - **There are no host aliases:** prod is the custom domain only, other stages workers.dev only. Rejected: `isOwnHost`, which is too broad.
  - **Tests:** S1's exposure test asserts that exactly `HARNESS_TOOL_NAMES` are hidden from the Session's own endpoint and every `MCP_TOOL_NAMES` tool stays; a handler test asserts that each tool the endpoint offers is in exactly one of the two lists.
- **Bounds:** the running cap (a Session's starts over its own endpoint count among the ≤10) and the rate limit (120 calls per 60 s, keyed `owner`, so shared with the owner's other clients). Not subagent depth, and not a shared Spend limit: a Session it starts is not its subagent.
- **Verified** on a preview stage: pending the owner's sign-in in a browser (#644's pull request lists the steps).

## Session import

A Session import ([Handing off a local pi Session to cloudpid](https://github.com/ian-pascoe/cloudpid/issues/393); [ADR-0043](../adr/0043-a-session-import-sends-the-local-agents-raw-transcript-for-cloudpid-to-translate-and-moves-the-working-tree-only-through-the-repos-remote.md)) brings the whole active branch of a local pi Session, never a summary (that is `session_start(text, branch)`) and never the tree's other branches. cloudpid translates the raw pi file; the working tree moves only through the Repo's remote; the Session lands in a new Workspace on the same branch name, so coming back is `git pull`. D-numbers in this section are that ticket's.

### The import channel

- **For a program, never a model:** the `session_import_*` tools are driven by `/cloudpid` (see [_The `/cloudpid` command_](#the-cloudpid-command)); the owner's model-facing `cloudpid` entry hides them.
- **Order:** begin (which may refuse `branch_taken`), then the Local agent's pushes, then the slices, then finish (D4.1). A failed push calls `session_import_cancel` and deletes the carry ref.
- **Begin** checks `environment` (required; id or name), `format` (only `pi-session-jsonl`, else `unsupported_format`) and `size_bytes` (≤64 MiB, else `import_too_large`), registers the Session (status `importing`; like a Fork while it fills, it refuses messages and moves: see [_Client and protocol_](client-and-protocol.md) → Fork and Clone) and claims `branch` for its new Workspace (a spare if current). It returns `carry_ref`, which the server owns so its scheme can change while older bundles stay installed (D16; left to implementation: the scheme, today's Fork and Clone one being `refs/cloudpid/carry/<branch>`). `branch_taken` carries `details: {workspace, sessions: [{id, url, title, status}]}`. `text?` is kept with the import.
- **Append:** slices cut at any character boundary by UTF-8 byte offset (one pi line can reach 4.6 MB), ≤2 MiB of `data` each (the body cap is 5 MiB for JSON escaping). `offset` must equal `received`, else `offset_mismatch` with `details.received`; a repeated slice is a no-op. The Session object stores the slices as rows (`stageImport*`).
- **Finish** checks the size and `sha256` (`checksum_mismatch`), keeps `changes_carried?` (whether the Local agent pushed uncommitted Changes to `carry_ref`; on finish, not begin, because the carry push comes after begin; additive, and a client that does not send it leaves the notice saying it is not told), translates, waits ≤30 s inline, else returns `importing`; `session_wait` later reports `import_ended`. Its `summary` counts `cut`, `dropped` (by kind, `custom:<type>` for extension state) and `closed`; `warnings[]` (redacted) carries the model fallback and `context_over_window`.
- **Expiry:** an import with no append for 1 h expires (`import_expired`); an expired or cancelled one deletes its Session; a failed, cancelled or expired one discards its kept `text` (D23).
- **The Workspace** is always a new one or the spare, never an existing one (D7). It clones the branch in the cwd's Repo and applies the Carried Changes from `carry_ref` (the existing `apply_carry`; see [_Carried Changes_](workspace.md#filesystem-and-tools)). The Environment's other Repos are cloned onto the branch from `origin` when it has it, else from their default branch; no `base` is sent (D5, D19). Left to implementation: readying it only once finish has accepted the payload, the first point at which the pushes are known to be done.
- **Model and thinking:** `model` comes as `provider/id`. It is used if it is among the owner's Models, else the Environment's default with a `warnings[]` entry; `thinking` is clamped to what the model supports. The import never fails over either.
- **Title:** begin's `title` (pi's session name) as `titleSource: owner`; without one, the Session's title task runs once when the import ends.
- **Context Window:** at finish the context is estimated as the last assistant message's `usage` plus about 4 characters per token after it; over a threshold of the model's window (left to implementation) it adds a `context_over_window` warning (D21). Nothing compacts ahead: the first request takes the normal path (an Emergency Rollover from the mapped Handoff and the Note Index, or a Rollover request).
- **The instruction:** begin's `text` is submitted after the import notice once the import ends, marked as from the Local agent (`via`); without it the Session waits for the owner. Finishing an import sends no Notification; a Run it starts notifies as usual.
- **Usage:** imported turns record no Usage and never reach the Spend limit. Imported assistant messages keep their own `usage` field (it feeds the estimate above); pi's `usage` entries are dropped.
- **As built** ([Add the Session import channel](https://github.com/ian-pascoe/cloudpid/issues/465)): the four tools are served end to end (`api.ts`: `importBegin`, `importAppend`, `importFinish`, `importCancel`; the Session's `stageImportBegin`, `stageImportAppend`, `stageImportFinish`, `stageImportCancel`, in `session/import.ts`).
  - **`import_id` is the Session's id.** Begin makes the Session (the Registry's `createSession` with `marks.kind: "import"`, the running cap, `request_id` deduping for 24 h) and then tells its object to start importing; every other tool takes that id and first checks the Registry lists it as an import, so none of them reaches the object of a Session that is not one, and `session_import_cancel` never deletes one. Rejected: a separate import id, which needs a Registry table and a lookup on every call to find the Session it names. A begin whose Session cannot be set up deletes the Session it made (a repeated begin that found its Session leaves it). A `request_id` finds the Session an earlier call made whatever that call was, so a begin whose `createSession` answers a Session that is not marked `import` (a `session_start`'s id reused) is refused `invalid_argument` and touches nothing.
  - **The slices** are rows of the Session object's own SQLite (`import_slices`, rows of at most 1 MiB, in tables the Session migrates itself, once they exist and on every read and write after (a migration added later reaches an object that already has them): `session/import-staging.ts`, with `session/migrations.manifest.ts` pinning the migration as the Registry's is), beside the import's record (`import_state`: phase, declared size, `model`, `thinking`, `text`, `via`, the Workspace's branch and Repos, expiry). `append` answers `offset_mismatch` with `details.received` unless `offset` is where the held bytes end; a slice already held is a no-op. Finish checks the declared size (`offset_mismatch` while bytes are missing), then the `sha256` (`checksum_mismatch`, leaving the bytes so the right checksum finishes).
  - **`carry_ref` is `refs/cloudpid/import/<session id>`** (`importCarryRef` in `@cloudpid/sandbox-image/workspaces`), a ref of the import's own, so only that import's Workspace applies what is pushed there. The Session knows its id without a Registry column (it is the `import_id`) and says it when it readies its own Workspace (`importReadying`, `session/import-readying.ts`): `WorkspaceClones.carry` makes the readying script's `apply_carry` read that ref instead of `refs/cloudpid/carry/<branch>`, and, as for a Fork's, take it off the remote once applied (and leave it there, for the owner, when it does not apply). Changes an import left behind (cancelled, expired, or a laptop that died after its push) are therefore never applied to another Workspace made later on the same branch, by `session_start` or a Fork; the stray ref is garbage on the remote that the Local agent deletes when it cancels (it owns the push), and nothing applies. Rejected: the Fork and Clone ref (`refs/cloudpid/carry/<branch>`), which `apply_carry` reads for any Workspace on the branch; deleting the ref ourselves on cancel and expiry, which would need the GitHub App's credentials in the Session for a repo the Session may not know. The notice says whether Changes were carried when finish's `changes_carried` says so; without it, it tells the agent to check (see _Translation_).
  - **Readying only once finish accepts.** A Workspace is readied lazily, when a Session first works in it (`session/workspace.ts`), so begin readies nothing; the Session's `prepare` refuses while it is importing, which keeps the Repos' clones (and so `apply_carry`) from running before the Local agent's pushes are known to be done. The import ends (the notice is the last entry, the Session takes messages) and the first use of the Workspace readies it. `session_import_finish` itself never touches the Workspace.
  - **`context_over_window` fires at 90 % of the model's window** (`CONTEXT_OVER_WINDOW_RATIO`, `session/import-model.ts`), by the same estimate the Session header shows (`readContextUsage`: the last answer's usage plus about 4 characters per token after it), read after the entries are in and the model is applied. The estimate is rough, so the warning comes before the window is passed.
  - **Finish** runs the translation in a fiber of the Session object and waits for it up to 30 s (`IMPORT_FINISH_WAIT_MS`), then answers `status: "importing"` with the cursor the Session's status gives; the fiber goes on. **Every start is counted first and durably** (`attempts` in the import's record), so a translation that crashes the object (memory, CPU, a reset) cannot be started again for ever: the alarm starts a cut-off one again every minute, and after five starts the import is given up (`failed`: bytes and `text` discarded, the Session stays `importing` and finish says why until it is cancelled or expires). **Once the entries are in the Session** (`held` in the record, set once the last page is written), none of that applies: the import has no expiry, its starts are no longer counted, and it is never given up; the alarm runs it again every minute until the Registry has been told it ended (`endSessionImport` failing, as a new Session against an old Registry does during a deploy, is a logged defect that heals), so a Session whose Run is working from the entries is never deleted over it. Telling the Registry and recording the end are one uninterruptible step. Accepting a file also starts its hour: a translation that is still not done at the end of it expires like any import, and **cancel works from `finishing`** (it interrupts the fiber, then reads the record again: a translation that reached its end first has ended the import, and the cancel is refused with `invalid_argument`). A file that cannot be translated (`invalid_argument`: no header, a line that is not an entry) fails the same way at once. The translated entries go into the root conversation a page at a time, each page one commit, and the import is `held` only after the last (a cut leaves a root nothing reads, which the run again fills in; see _Translation_), and the instruction is sent under a fixed `request_id` so it is never sent twice. A finish repeated after the import ended answers its summary again.
  - **Title:** begin's `title` is the Registry's owner title at `createSession`; with none, the Session's title task runs once when the import ends, over the first message and answer.
  - **Model:** begin's `model` is used when it is one of `SUPPORTED_MODELS` (`isModelId`, the check `session_start` makes), and then stays the Session's picked model; any other is replaced by the Environment's default, with the warning, and the Session keeps following the default. `thinking` is clamped with pi-ai's `clampThinkingLevel` against the model the Session runs with, and stays picked. `warnings[]` go through the Session's Secrets redaction and the GitHub token pass.
  - **The instruction** is submitted after the import ends, through the same `submit` as `session_send`, with begin's `via`, so the Run it starts and its `via` chip are the Local agent's. When the Session refuses it (it cannot be sent: too large for the Session's own check, say), the import still ends and `warnings[]` says the instruction was not sent and to send it with `session_send`; it is never dropped silently.
  - **Expiry and cancel:** every append moves the expiry to an hour on. An expired import answers `import_expired` to the call that finds it, and the Session's alarm deletes it: the Registry's record first, then the Workspace when no other Session is in it, and the object's own storage last (`removals.removeOwnSession`, shared with the owner's delete and `session_import_cancel`'s). The wipe runs in the alarm itself and never resets the object, so the alarm ends normally and is not retried over empty storage; the object's import tables are made only by the first begin (never by opening the object), the alarm checks the import before anything else and a Session that deleted itself runs nothing more, so an alarm retried over the wiped storage finds no record and brings nothing back. `import.workerd.test.ts` checks the Registry record, the Workspace and the storage, empty, after the alarm and after two more, and over a new instance (the object evicted first): waking it opens only the Harness's own empty tables and notes what it reports, and the alarm over them changes nothing. A deletion that fails leaves the import, and the alarm tries again in five minutes. `session_import_cancel` has the Session discard the bytes and `text` at once, then the main Worker deletes the Session and Workspace the way the owner's delete does; it is idempotent (a Session that is gone was cancelled), and refuses an import already ended (`invalid_argument`).
  - **Refusals while it fills** are the Fork's (`session/fork-host.ts`): the Session reports `importing`, `session_send` answers `session_importing`, and the owner's messages, `/tree` moves and forks are refused with "still importing".
  - **Open imports and `importing` in the Registry.** The Registry knows a Session is importing from its own column (`sessions.importing`, Registry migration 31: set when `createSession` registers a Session marked `import`, cleared by `endSessionImport`, which the Session calls when the import ends; the row is gone with a cancelled or expired import). `SessionRecord.importing` (optional, `true`) lets `sessions_list` say `importing` (`McpSessionSummary.status` gains the member; an older `McpServer` reads it as `unknown`) and the web's Session list show "Importing" in place of the time or "Running" (`SessionLink`); the `idle` and `running` filters of `sessions_list` leave an importing Session out. **At most two imports per identity may be open** (`MAX_MCP_OPEN_IMPORTS`): `createSession`'s `maxOpenImports` counts the Sessions marked `import` by the same `auth` (how the caller got in: the owner's grants and local dev each have their own two; Sessions the old service token imported count under `service_token`, which no new import adds to) that are still importing, in the same transaction as the insert, as `maxRunning` is, unless `request_id` finds its Session. The refusal is `too_many_running` (retryable, `details.limit`), worded for imports; a begin that is refused registers no Session or Workspace.

### Translation

- **Input** (`format: pi-session-jsonl`): the pi file's header line plus the active branch's entries (`getBranch()`), one `JSON.stringify` per line, byte-identical to the file. The server takes the path ending at the last line.
- **Mapping** onto pi-durable entries, filled into the root conversation through the Fork and Clone fill path (`importEntries`, heads and edits renumbered; [What does a local pi Session hold, and how could pi-durable take it in?](https://github.com/ian-pascoe/cloudpid/issues/379)):
  - `message` `user` / `assistant` / `toolResult` → `pi.user` / `pi.assistant` / `pi.tool-result`, same pi-ai types, content unchanged;
  - `compaction` → `pi.compaction` with `head` its first kept entry; `branch_summary` → `cloudpid.branch-summary`; `custom_message` (extension context) → a user-message entry; `context_edit` → `edits`;
  - system messages are never imported, and no `toolsRemoved` or system entry is written (they would break `findBaseline`);
  - `model_change` and `thinking_level_change` make no entries (begin's `model` and `thinking` set the Session's); labels, `session_info`, `usage` entries, header ids and `parentSession` are dropped; only message timestamps survive;
  - any other kind (for example pi's `bashExecution` messages, which pi keeps in context) is dropped and counted in `summary.dropped`; mapping one is left to implementation.
- **Extension state,** from Effect Schema copies of the three formats pinned in the translator (citing their source commit in `ian-pascoe/pi-extensions`, with sanitized fixtures from real sessions): the last `pi-todo-state` → `TodoDoc` (`rev: 1`); `pi-context-note` records replayed in order into `ContextDoc.notes` (`null` deletes); the latest `pi-context-handoff` → `ContextDoc.handoff`. Anything else, an unknown version, a failed schema or anything over cloudpid's limits is dropped and counted as `custom:<type>`, never failing the import (D13). Mapping other extensions' state, once cloudpid ports them, is left for later.
- **Bounds:** live caps first (images capped; an oversized image becomes a text placeholder); then each translated entry is held to cloudpid's largest live row total (about 5 MB, one exported constant) by middle-cutting its largest text parts, counted in `summary.cut`.
- **Tool calls** are kept, never dropped or flattened by default: providers accept history calls to tools the request doesn't declare when it declares at least one, and every cloudpid request does. A dangling call is closed with an error result ("Not run: the laptop's turn ended before this call had a result"), counted in `summary.closed`. A provider that rejects such history gets, for that provider only, calls to absent tools flattened into text; a live probe per provider is the translator's acceptance criterion (D25). MCP tool names in those calls are mapped through cloudpid's snake_case normalization, the same pure function as [_Tool names_](mcp-in-a-session.md#tool-names) (`mcp__x__getUser` → `mcp__x__get_user`), and unknown names are left as they are ([MCP tools in a Session: exposure, naming and the prompt cache](https://github.com/ian-pascoe/cloudpid/issues/381)'s input to the Session import ticket; D25 covers dangling calls and absent tools, not naming).
- **The import notice** is one model-visible user-role text entry, always the last imported entry (an invariant, tested). It names the laptop cwd; each Repo with its `/workspace/<dir>` and the branch; whether Changes were carried (the cwd's Repo only); whether Todo and Notes came across; any model fallback; the cut, dropped and closed counts; the laptop tools this Session lacks (≤30, then "and N more": "these ran on the laptop; you can't call them here"); and "the owner brings work back with `git pull` on `<branch>`: commit and push your work there when you finish".
- **As built** ([Translate a pi Session into cloudpid entries](https://github.com/ian-pascoe/cloudpid/issues/474)): the translation is a seam, `ImportTranslator` (`session/import-translate.ts`: the file's lines, re-readable, and what is known of the Workspace and the Session's tools in; the counts, the entries as pages, the two documents, or a one-sentence failure out), and `translatePiSession` is it.
  - **Three reads, no more than a page in memory.** A file can be 64 MiB, so the translation never holds its entries. The first read finds the active branch (the path that ends at the last line, by `id`/`parentId`; every entry of a branch sent whole is on it) and the entries a context edit names; the second makes every entry and keeps only the counts, the Todo List, the Notes and the Handoff; `pages()` makes them again, `IMPORT_PAGE_ENTRIES` (200) or `IMPORT_PAGE_BYTES` (4 MiB) at a time, as they are written. A line that is no entry fails the import before anything is written. Entry IDs are 1 to N in order, and a head or an edit names one.
  - **Mapping.** `compaction` → `pi.compaction` with `model` pi's framed summary and `head` the first kept entry (or, when that made no entry, the next one that did; none kept starts the context at the summary, as pi does), `data: {reason: "manual"}`; `branch_summary` → `cloudpid.branch-summary` with the Fork's own `summaryMessage`; `custom_message` → `pi.user`; `context_edit` → an entry of kind `cloudpid.context-edit` (`CONTEXT_EDIT_KIND`) that carries `edits` and no message, an omission or the target's message with its content replaced (an edit of an entry that made no entry, or of a summary, makes nothing). Not counted, because begin's `model` and `thinking` or the Session replace them: `model_change`, `thinking_level_change`, labels, `session_info`, `usage` entries and system messages. **Counted in `summary.dropped`:** `bashExecution` messages (`message:bashExecution`; left to implementation, and the default holds: pi keeps them in context as text, and mapping them is a later change), any other message role, any other entry type, and each `custom` entry that is not carried (`custom:<type>`, including every other extension's: pi-git-checkpoints and minimal-subagents write hundreds of them).
  - **Extension state** is `session/import-pi-state.ts`: Effect Schema copies of `pi-todo-state`, `pi-context-note` and `pi-context-handoff`, each citing its source file and the commit of `ian-pascoe/pi-extensions` they were read at (`1a9d7cc684b74ff08a367694623361ab315cbdcd`), with fixtures shaped as real sessions (`import-pi-session.fixture.ts`). A record is taken only if it passes its Schema (the note's allows no other key, as pi's does), pi-todo's own list rules (`parseTodoStateSnapshot`: IDs ascending, trimmed titles, `nextId` past the last) and cloudpid's limits (`MAX_TASKS`, the title and description lengths, `todoListFits`, `MAX_NOTES`, the Note name and `MAX_NOTE_CHARACTERS`, a non-empty Handoff); otherwise it is dropped as `custom:<type>` and the earlier valid one stands. `importFinish` takes the documents: the Todo List with `rev: 0` (it becomes 1; an empty list is no list), the Notes with each `updatedAt` the entry's time, in the order they were first written.
  - **Bounds** are `session/import-bounds.ts`. The live caps first: an image over `MAX_IMAGE_CHARACTERS` (from `@cloudpid/extensions/images`: 750,000 base64 characters, what `read` and the browser keep) or of a type the models do not take becomes text, and the images of one tool result are kept in order up to `MAX_RESULT_IMAGE_CHARACTERS` (1,500,000) in all, as a live result's are. Then each entry is held to `MAX_IMPORTED_ENTRY_BYTES` (5,000,000 bytes of the JSON the Session stores; the name was left to implementation) by cutting its largest strings (a message's text and reasoning, a call's arguments, a result's details) in the middle to one level, so each keeps its start and end, with a note of how many characters went; a cut block loses its provider signature, which a provider rejects once the words change; if the text cannot make it fit, the largest images become text; one that still does not fit is dropped (`oversize:<kind>`), except a tool result, which is never dropped, because its call would stay open: its `details` (which the model never sees) become `{reason: "import_too_large"}`, and if it still does not fit the result becomes an error result (`TOO_LARGE_TEXT`) counted in `summary.closed`. `summary.cut` counts the entries that are kept and were changed by any of this.
  - **Paging and the all-or-none guarantee.** The Session writes each page in one commit (`importTranslated` in `session/fork-host.ts`), not all entries in one: a single transaction would hold every entry, which is what the pages avoid. All-or-none holds for everything that can see them: until the import ends the Session is `importing`, takes no message and no move, and a Run never starts from the root; a cancelled, expired or given-up import deletes the Session with its entries; and `held` (a Run may work from them) is set only after the last page (`importWritten`). A translation cut off between pages is started again, makes the same pages, reads the root's entries back, eight at a time (their IDs, by position, which also rebuilds the map heads and edits are renumbered by) and appends only the rest. The first run notes the translation (`TRANSLATOR_VERSION` and its entry count) before its first page; a run again that finds another version or count, or a root with more entries than the translation makes, does not resume: the import is given up (`failed`, cancel and begin again). The comparison is made only when the root has entries: a root that is empty is written from the start and notes the translation again, and a root that has entries and no note (written whole in one transaction by a version before the note) is taken as written, as `held` is. `import.workerd.test.ts` cuts a write after one page and checks that no entry is twice, the compaction's head still names the same entry, and the notice is last.
  - **Tool calls.** A call with no result is closed with `NOT_RUN_TEXT` as an error result, before the next message of any other kind or the notice, and counted in `summary.closed`; an assistant message pi-durable leaves out of the context (`aborted`, `error`, `deferred`) opens none. MCP names in calls and results go through `mcpToolNameFromPi` (the snake_case question: they are mapped; unknown names stay). **The probe** (`session/import-provider-probe.test.ts`) sends each provider in `SUPPORTED_MODELS` (today `anthropic`) a history that calls a tool the request does not declare, through the model proxy, and checks the provider's switch in `session/absent-tools.ts` (`FLATTEN_ABSENT_TOOL_CALLS`) matches what it does, and that the flattened history is accepted. It is opt-in: it runs only with `MODEL_PROXY_URL` and `MODEL_PROXY_API_KEY` set (`bun --cwd apps/server vitest run src/session/import-provider-probe.test.ts`; [`docs/development/infra.md`](../development/infra.md) → _Secrets_ has the key) and is skipped without them, as in CI. A provider that refuses has its requests' calls to absent tools flattened into text by a wrapper of the Session's model seam (`absentToolFlatteningModels`, beside the image limit), for that provider only and at the request, so the stored history is untouched; the switch is `false` for every provider until the probe has said otherwise (the probe is an owner check on the pull request: it needs the proxy's key, which the implementation did not have). Turning a switch on has a cost the switch's comment names: the seam sees messages, not where they came from, so it flattens every Session's calls to absent tools for that provider, not only an import's, and a Session already running loses its prompt-cache prefix once.
  - **The notice** (`session/import-notice.ts`) names the cwd, each Repo with its directory, the branch, whether Todo and Notes came across, the model fallback, the counts (with the kinds dropped), the laptop tools the Session lacks (the history's called names the root conversation's agent does not declare, `NOTICE_TOOL_LIMIT` = 30 and then "and N more"; MCP tools are left out, which the Session may reach through code mode or `tool_search`; none when the Session's tools could not be read) and the `git pull` sentence, and is the last entry (tested over files of every shape). **Changes carried** is what finish's `changes_carried` said (kept in the import's record, from the finish that is accepted): carried, or none to carry. The server cannot see the remote's carry ref, so a client that does not send it leaves the notice saying it is not told, and to run `git status`.

### The working tree

- **Only through the Repo's remote** (ADR-0043): no file or patch upload, no `wip:` commit.
- **Commits:** the local branch is pushed as the branch, fast-forward only; a diverged remote refuses the import ("pull first").
- **Uncommitted Changes** (tracked and untracked, never ignored, so no `.env`) are read through a private index and force-pushed, hooks off, as one commit on HEAD to `carry_ref` (a port of `carryWorkspaceScript`'s `carry()`); with nothing to carry, a stale carry ref is deleted. The local index and work tree are untouched. Only the cwd's Repo carries its Changes (D19); carrying the Environment's other Repos' is left for later.
- **The branch:** the local branch's name, or its upstream's name on `origin`. On the default branch or a detached HEAD, `/cloudpid` prompts for a name (prefilled with a slug of the title) and runs `git switch -c`.
- **Importing again** onto a branch another Workspace holds is refused with `branch_taken`; `/cloudpid` offers removing that Workspace in the UI then retrying (warning that removal deletes its Sessions), a new branch name, or cancel (D15). Landing in the Workspace already on the branch, when it is clean, idle and an ancestor of the pushed HEAD, is left for later.
- **Coming back** is git only: `/cloudpid` prints `git switch <branch> && git pull --ff-only`, then `git stash drop`. The conversation stays in cloudpid (D12). A `/cloudpid-pull` helper and exporting a Session back to a pi file are left for later (D17).
- **As built** ([Build `packages/pi-cloudpid` and `/cloudpid`](https://github.com/ian-pascoe/cloudpid/issues/475); `packages/pi-cloudpid/src/git.ts`, `flow.ts`):
  - **Order:** the checks that touch nothing first (idle, saved, token set, marker, `origin`, Environment, the push plan, the carry's file list), then the confirm, then begin; only then `git switch -c`, the push, the carry, the slices and finish. A refused, declined or `branch_taken` import therefore leaves the checkout as it was.
  - **The Repo's URL** is the checkout's own `remote.origin.url` as its config has it, not `git remote get-url`'s, which expands `url.<base>.insteadOf`: a laptop that rewrites `https://github.com/…` to ssh still names the Repo as an Environment lists it. `git remote get-url origin` is the fallback, tried only when the configured URL matches no Environment and its own answer does. Rejected: `get-url` first, which would make the match depend on the owner's rewrites.
  - **The branch:** the upstream's name on `origin` when the local branch tracks another name there (and it is not the default branch, which would push the owner's work onto it), else the local name; the coming-back line names the local branch. The default branch is `origin/HEAD`'s, else the remote's own `HEAD` (`ls-remote --symref`), else a local `main` or `master`. The name prompt is `ctx.ui.editor` with the slug prefilled (the title's, else the first message's, at most 40 characters of lower-case words): `ctx.ui.input` has no initial value. A name git refuses (`check-ref-format`), a local branch has already, or that is the default branch asks again, up to five times.
  - **The push plan** reads `origin`'s tip with `ls-remote`, fetches just that commit when it is not known locally, and asks `merge-base --is-ancestor`: ahead or diverged refuses "pull first" before begin; git's own non-fast-forward refusal at push time (a push raced in) says the same. A new branch lists the commits no `origin/*` ref has, for the confirm (`--remotes=origin`, so a branch off `main` lists only its own). The branch push is not taken back when the import fails afterwards: it is the owner's own branch, pushed as they would.
  - **The carry** is `carryWorkspaceScript`'s `carry()` over the owner's checkout: `read-tree HEAD`, `add -A` and `write-tree` on an index file in the OS temp directory (`GIT_INDEX_FILE`, removed afterwards), skipped when the tree is HEAD's own, then `commit-tree` on HEAD with the owner's `user.name` and `user.email` (else cloudpid's) and `push --force`, with `core.hooksPath=/dev/null`, to `carry_ref`. The confirm lists the files from `diff-tree` of HEAD and that tree, so it names what will be carried. With nothing to carry the ref is looked up and deleted when it is there. A failure after begin calls `session_import_cancel` and deletes the carry ref, and what could not be undone is named.
  - **`branch_taken`** loops: the owner removes the Workspace in the web app and retries (asked again if it is still there), or picks a new name (which makes a new push plan, and may refuse "pull first"), or cancels. The prompt lists the Sessions in `details` with their URLs and says that removal deletes them.
  - **After finish** the local branch gets `origin/<branch>` as its upstream when it did not track that (it had none, was made by `git switch -c`, or tracked another branch such as `origin/main`), best effort, so the `git pull --ff-only` it prints pulls the branch just pushed; when git refuses, the line is `git pull --ff-only origin <branch>`. The stash is offered only when something was carried, and `git stash drop` is in the coming-back line only when it was made.

### The `/cloudpid` command

- **Package:** `packages/pi-cloudpid` (`@cloudpid/pi-cloudpid`), a pi extension in this repo in the standard shape (dev loop `pi -e packages/pi-cloudpid/src/index.ts`). It may import `@cloudpid/protocol` and `@modelcontextprotocol/client` at the monorepo's pin (bundled: ADR-0036's import rule is about Workers), and `@ian-pascoe/pi-utils` (npm; its `layered-settings` is bundled); never `cloudflare:*`, workerd, alchemy, pi-durable or `@cloudpid/extensions` (oxlint `no-restricted-imports` and the build enforce it). It registers the `cloudpid` MCP server with pi from the same setting (below), so no `mcp.json` entry is needed.
- **Command:** one command with subcommands ([Sign in to cloudpid with OAuth and read the endpoint from pi settings](https://github.com/ian-pascoe/cloudpid/issues/635); it supersedes "no subcommands" here and the command shape of #393), and not `/handoff`:
  - `/cloudpid import [instruction]`: the import flow below; everything after `import` is the instruction (begin's `text`), verbatim. An explicit verb, so an instruction that starts with `login` or `logout` is never misread.
  - `/cloudpid login`: signs in to the configured endpoint now, replacing a stored sign-in. `/cloudpid logout`: deletes the stored sign-in of the configured endpoint, and of no other.
  - `/cloudpid` alone or an unknown subcommand prints the usage and the configured endpoint (or the setup steps when there is none) and does nothing else. The subcommands complete in pi's command autocompletion (`getArgumentCompletions`).
- **Configuration:** the endpoint is the `cloudpid.baseUrl` pi setting, never `mcp.json` and no environment variable. It is read with `defineLayeredSettings` (`@ian-pascoe/pi-utils/layered-settings`; namespace `cloudpid`, schema `{ baseUrl?: string (minLength 1) }` with no other property, no session layer) from `~/.pi/agent/settings.json`, then `.pi/settings.json` of a trusted project (the project wins), on every `/cloudpid` run, so a change needs no `/reload`.
  - `baseUrl` is the cloudpid origin: `/mcp` is appended to its path once (a URL already ending `/mcp` is taken as is); https only, http for loopback (`alchemy dev`).
  - **No default.** Unset, `/cloudpid` refuses with setup steps that name `cloudpid.baseUrl` and the two files. An invalid block (an empty or non-string `baseUrl`, another property, a value that is not a URL or not https, a settings file that is not JSON) refuses naming the file and the field, and never falls back to another layer or a default.
  - **Superseded:** [#393](https://github.com/ian-pascoe/cloudpid/issues/393) D18.2's setup (`CLOUDPID_URL`, and the Local agent's service token in `CLOUDPID_ACCESS_CLIENT_ID` / `CLOUDPID_ACCESS_CLIENT_SECRET`, sent as `CF-Access-Client-Id` / `-Secret`) is replaced by [#635](https://github.com/ian-pascoe/cloudpid/issues/635): the three variables are no longer read and no `CF-Access-Client-*` header is sent.
  - **The sign-in** is OAuth against the endpoint's Access application (managed OAuth; see _Access and identity_): `/cloudpid login` and, when there is no sign-in or the stored one is no longer accepted, `/cloudpid import` (it asks first). Both commands need pi's interactive mode: `/cloudpid import` refuses without it up front, even with a stored sign-in, and `/cloudpid login` opens a browser or asks for the pasted redirect URL, so the owner signs in from interactive pi. The guard admits the owner's OAuth caller to every tool, import tools included, and marks it `auth: "oauth"` with its `clientId`. It sends `X-Cloudpid-Client: pi-cloudpid/<main sha>`.
- **The MCP server:** the model's connection is pi's own MCP support's. On every `session_start` (startup, `/reload`, `/new`, `/resume`, `/fork`; pi keeps no registration) the extension reads `cloudpid.baseUrl` as `/cloudpid` does (the same reader, so the same endpoint URL, `/mcp` appended once, and an untrusted project's file ignored) and calls `pi.registerMcpServer("cloudpid", {url: <the endpoint URL>, toolExposure: {"session_import_*": "hidden"}, description})`, `exposure` left at pi's default and no headers. The import tools are hidden because they are for `/cloudpid import` and never for a model. Unset or invalid settings register nothing and show nothing (`/cloudpid` still refuses when run). The settings are read at each `session_start` only, so a change reaches the model's connection at the next one (`/reload` is one). An `mcp.json` `cloudpid` entry wins over the registration (pi's rule, shown in `/mcp`). pi builds a new extension runtime (a new registry, the factory run again) at each session start, so a registration never carries over: a session that resolves no URL registers nothing. Within one load, for a `session_start` that fires again, the extension remembers the URL it registered: the same URL registers nothing again, another one replaces the registration (pi closes the old connection and connects the new), and none calls `unregisterMcpServer`, only if it registered one (defensive). An exception from `registerMcpServer` (another extension owns the name, a config pi rejects, a pi without the API) is caught and shown as one warning notice per distinct reason, and never thrown. pi signs in the model's connection (`/mcp` → Sign in; `mcp-auth.json`); `/cloudpid import` keeps its own connection and sign-in (`/cloudpid login`), because a command handler has no `executeTool` (only a tool's `execute()` does) and the import tools are hidden, so the command cannot go through pi's connection.
- **Compatibility:** it checks `tools/list` for what it needs, else refuses with "the endpoint is older than this extension".
- **The Environment:** the repo root (`git rev-parse --show-toplevel`)'s `origin` normalized (scp-style and `ssh://` → `https://host/path`; userinfo, `.git`, a trailing `/` and case dropped) and matched against `environments_list`'s Repo URLs: one match is used, several give a select, none (or no git, or no `origin`) refuse with "add this Repo to an Environment first". No flag; it never creates an Environment.
- **Flow** (`import`): refuse unless `ctx.isIdle()` and the Session is persisted; a confirm shows the Environment, branch, commits to push, carried files (count and names), size and model; begin, push, slices, finish; print "imported", or "still importing; it will start on your instruction when done", with the URL and `summary`; offer `git stash push -u -m "cloudpid: imported as <url>"`; then `pi.appendEntry("cloudpid-import", {session, url, branch, environment})` and a notify. It never follows the Run. A `cloudpid-import` marker already on the branch asks "already imported as `<url>`; import again as a new Session?".
- **Distribution:** `bun build --target=node --format=esm` makes one `dist/index.js`, with the pi host packages (`@earendil-works/pi-*`, `typebox`) external as `peerDependencies: "*"`; `dist/package.json` has `pi.extensions` and no dependencies or scripts. After `Deploy prod` succeeds, a `pi-cloudpid` CI job (`needs: deploy`, `contents: write`, no deploy credentials) appends a commit naming the `main` SHA to the orphan branch `pi-cloudpid`, never force-pushing. The owner runs `pi install git:github.com/ian-pascoe/cloudpid@pi-cloudpid` once; `pi update` follows it. The extension is published only after the deploy it targets.
- **As built** ([Build `packages/pi-cloudpid` and `/cloudpid`](https://github.com/ian-pascoe/cloudpid/issues/475)):
  - **Layout and seams:** `index.ts` registers the one command, and the MCP server (`mcp-server.ts`) on `session_start`, and routes the command's line (`command.ts`: `parseCommand`, a pure function, and the completions); `run.ts` runs a subcommand (`import`, `login`, `logout`, or the usage); `flow.ts` is `importSession(host, instruction, deps)`, over two seams: `Host` (pi: the cwd, `isIdle`, a snapshot of the Session, the model, `ui`, `appendEntry`) and `Deps` (the endpoint's `config()`, git, `endpoint(config)`, `signIn(config)`, the disk). `config.ts` is the settings, `auth-store.ts` the sign-in file, `oauth.ts` the SDK's `OAuthClientProvider` and its fetch, `signin.ts` the browser flow. The integration test (`import.test.ts`) runs the real flow against cloudpid's own handler (`serveMcp` from `@cloudpid/mcp/server`) behind a stub authorization server (`oauth.fixture.ts`) over a fake `api` that keeps an import in memory, a temp checkout with a bare remote, and pi's own `SessionManager` for the file; `git.test.ts` holds the carry and the push plan to real git (the index file, status and branches are unchanged; ignored files never carried; hooks never run).
  - **The MCP server** ([pi-cloudpid: register the cloudpid MCP server from settings](https://github.com/ian-pascoe/cloudpid/issues/639); `mcp-server.ts`, `index.ts`; the rules are in the _MCP server_ bullet above): the settings need a session's `cwd` and project trust, which the extension's load does not have and `session_start`'s context does (it has no settings manager either, so `index.ts` reads the files as `/cloudpid` does, through the one `settingsOf`), so the registration is made there. pi emits `session_start` after it bound the extension, so a registration made in the handler connects at once (`mcp_servers_change`), whichever of the built-in MCP support's own `session_start` handler and ours runs first. A `Refusal` from `readConfig` is no registration; any other error is rethrown. `mcp-server.test.ts` runs the extension against a fake `pi` and real settings files.
  - **The Session** is `getHeader()` and `getBranch()` as one `JSON.stringify` per line, and `session.test.ts` checks it is byte-identical to the file pi writes (and leaves a branch that is not active out). "Persisted" is `getSessionFile()` set and the file on disk: pi writes it with the first message, and `ReadonlySessionManager` has no `isPersisted()`.
  - **`@cloudpid/protocol` is imported for types only** (`import type`): its Schemas are built on `effect` and pull the Registry, which the bundle must not carry. The four values the extension shares with the endpoint (the format, the 2 MiB slice, the 64 MiB limit, the title length) and the required tool names are copies, and `constants.test.ts` fails when they drift from the protocol's or when the bundled SDK is not `packages/mcp`'s pin. Answers are read field by field (`json.ts`, with `effect/Predicate`, the one Effect module the bundle carries). The SDK's validator is switched off, which keeps Ajv from being built, though the SDK's own entry still bundles it (the bundle is about 0.9 MB).
  - **The connection:** the SDK's Legacy handshake (`initialize`, stateless) with the sign-in as the transport's `authProvider` (`oauth.ts`), then `tools/list` (paged) against `REQUIRED_TOOLS`. `redirect: "manual"` stays, so a token never follows a redirect. `X-Cloudpid-Client` is `pi-cloudpid/` and the first 12 characters of the commit, which keeps it within the 40 the endpoint shows.
    - **The command context has no settings manager** (pi 1.4), so each run reads the two files with pi's own `SettingsManager.create(cwd, getAgentDir(), { projectTrusted: ctx.isProjectTrusted() })` and `defineLayeredSettings`' `readLayers` / `readSettings`; `getAgentDir()` honours `PI_CODING_AGENT_DIR`. The bundle imports `@earendil-works/pi-coding-agent` for these two values (a declared peer, external) and bundles only `layered-settings` of pi-utils: `typebox` is external and a declared peer, and the lock-file code of pi-utils is never reached (nothing here writes settings).
    - **The store** is `<agent dir>/cloudpid-auth.json`, mode 0600, written atomically (a temp file in the directory, then a rename) and in order within the process, one entry per endpoint URL string: the Dynamic Client Registration, the tokens, when they were obtained (`obtainedAt`, the base of `expires_in`) and the discovery result (Access serves the resource metadata away from the host's root, so a refresh needs the stored `resource_metadata` URL). A project pointed at a preview stage keeps its own sign-in. `logout` deletes the configured endpoint's entry alone. A file that is not this one's (not JSON, no `endpoints`) is refused naming it, never overwritten. Two pi processes writing at once is last-writer-wins per file (no cross-process lock).
    - **The provider** (`CloudpidOAuthProvider`) is the SDK's `OAuthClientProvider`, and the SDK's `auth()` runs the protocol: discovery from the 401's `resource_metadata`, Dynamic Client Registration as `pi-cloudpid` (a public client: PKCE `S256`, no secret) with the redirect `http://127.0.0.1:<ephemeral port>/callback`, the code exchange, and the refresh. Every rotated refresh token is stored before the access token that came with it is read back for a request. Tokens are never logged. On the connection (not in `/cloudpid login`, which is the owner's consent) the provider never registers a client or drops one on its own: with tokens but no client, or a client stamped by another authorization server, `clientInformation` throws `SignInRequired` before `auth()` can send a registration, and `invalidateCredentials` refuses to drop the client.
    - **Refresh:** before a request when the access token has under a minute left (`obtainedAt + expires_in`; one refresh at a time), and on a 401 (the SDK refreshes and retries once). A refresh that fails with `invalid_grant` drops the stored tokens (the registration stays); one that fails with `invalid_client` or `unauthorized_client` (the registration is no longer known) keeps the entry as it is and registers nothing until the owner agrees to sign in. Either way the connection fails with `SignInRequired`: "sign-in rejected or expired: run `/cloudpid login`", which `/cloudpid import` turns into a question to sign in again. The SDK `console.warn`s (`[mcp-sdk] …`) as it recovers from these; they would be written over pi's screen, so the extension captures them while connected or signing in and shows them as pi warnings (its "invalidating the stored credentials" wording is replaced by "the authorization server refused the stored sign-in", since the provider invalidates nothing without the owner). A grant that ends in the middle of an import is the same refusal, but no question is asked then: the import cannot be cancelled without a sign-in, so it is left open (it expires after an hour) and the notice says to run `/cloudpid login`, then `/cloudpid import`.
    - **Access may answer an expired bearer with a 401 or with a 302 to its login page.** A redirect on a request that carries a bearer is never followed and is read as a 401, so the SDK refreshes and retries once; if the retry is redirected again the sign-in is rejected (the same refusal). A 403, or a redirect on a request with no bearer, is that refusal too.
    - **With nothing stored** the connection first asks the endpoint for something with no credential (a 401, or a redirect, says it wants a sign-in): `SignInRequired`, raised before the SDK registers a client, so declining the question leaves no registration behind. An endpoint that wants none (`alchemy dev`) is connected to with no token.
    - **Signing in** (`signin.ts`) discovers from the unauthenticated 401's `resource_metadata`, registers a fresh client, starts a loopback server on `127.0.0.1` (one request with the matching `state` completes it; another `state` is refused and the wait goes on; it gives up after five minutes), opens the browser (a seam: `open`, `xdg-open` or `cmd /c start`; the URL is also printed) and also asks for a pasted redirect URL with `ctx.ui.input` (a laptop reached over SSH has no browser to reach the port; the first of the two to answer wins, and dismissing the prompt cancels). The stored entry is replaced only once the new tokens are in, so an abandoned sign-in leaves the working one.
  - **Retries:** a failure the endpoint marks `retryable` is retried up to three times, after `details.retry_after_s` seconds (at most 60) or a second more each time; `session_import_begin` is never retried here, since its failures (`too_many_running`, `branch_taken`) are the owner's. An `offset_mismatch` resumes from `details.received`; three answers without progress fail the import. A `checksum_mismatch`, an expired import and every other failure cancel the import, and `import_expired` and `too_many_running` say what to do.
  - **After the import is made** (finish answered) nothing cancels it: the upstream, the stash, the marker and the notice each run on their own, and a step that fails (the session file cannot be written, the stash) is a warning beside the notice, which still gives the URL. Before that, a failure cancels the import and deletes the carry ref; when `git switch -c` had run, the notice says which branch the owner is on now and how to go back.
  - **`changes_carried`:** `session_import_finish` is sent `changes_carried` (whether a carry commit was pushed) only when `tools/list` declares it in the tool's `inputSchema`, so an older endpoint is never sent a property it may refuse.
  - **Refusals** that need no endpoint (no git, not in a repo, no `origin`, no Environment with the Repo) all end in "add this Repo to an Environment first"; a `git` that cannot be started (`ENOENT`) is one of them. The endpoint not being set up refuses before any of these, with the setup steps. Messages that say to run the command again say `/cloudpid import`.
  - **Order of the marker:** the `cloudpid-import` entry is written once finish has answered, whether it said `imported` or `importing`, and the "import again?" question comes before any network call.
  - **Build:** `build.ts` runs `bun build --target=node --format=esm` with `--external=@earendil-works/*` and `typebox`, defines `process.env.PI_CLOUDPID_SHA` (the environment's, else `git rev-parse HEAD`), and fails when the metafile shows the bundle reaching `cloudflare:*`, `@cloudflare/*`, workerd, alchemy, pi-durable or `@cloudpid/extensions`, or leaving an import external that is neither a Node module nor a declared peer (`build-check.ts`, tested). `dist/package.json` has `pi.extensions: ["./index.js"]` and the peer dependencies (`@earendil-works/pi-coding-agent`: `*`, `typebox`: `*`), and `dist/` also has the README. `@ian-pascoe/pi-utils` (`layered-settings` alone) is bundled; `index.js` imports `@earendil-works/pi-coding-agent` for `getAgentDir`, `SettingsManager` and `CONFIG_DIR_NAME`, and `typebox` (with `typebox/value`), and both are the host's own, so nothing in it is external but Node's modules and those two peers.
  - **CI:** the `pi-cloudpid` job runs `bun run build` in `packages/pi-cloudpid` itself, with `PI_CLOUDPID_SHA` set to the `main` commit, not through turbo, whose cached `dist/` would carry an older commit, and skips an older run's rerun when the branch's tip was built from a `main` commit that descends from it; the `static` part builds the package through turbo to keep the build checked ([`docs/development/infra.md`](../development/infra.md) → _CI_).
