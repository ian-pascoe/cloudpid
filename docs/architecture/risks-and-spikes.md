# Known risks and spikes

- **Worker Shell `git status` is not git's.** `git status` stays on the Worker Shell because a cheap status is what the model runs most, but `@cloudflare/computer` 0.5.1's client prints `1 XY path` and `? path` lines (not git's long format), sorts them by path, lists untracked files one by one (git collapses a directory to `dir/`), and gets the staged column wrong whenever the index holds staged entries: a staged, otherwise clean modification prints `MM` (git: `M `), a staged new file `AM` (git: `A `), and a staged new file modified again `A ` (git: `AM`). Unstaged changes, deletions, and untracked files match git, and `.gitignore` is honored. Staged entries come from `git add`, which runs in the Container and reaches the Worker Shell through sync, so `git add` then `git status` is the case that is wrong; if that proves a problem in practice, route `status` to the Container too (one entry in `GIT_ON_WORKER`, at the cost of #22's acceptance example). A tracked file under `TOOLCHAIN_IGNORE` shows as deleted, since the Worker Shell's tree does not hold ignored paths. The Worker Shell and the Container have two different git implementations over one tree, so a repository one wrote is read by the other; the Workspace DO builds the Worker Shell's git client anew for every call (`workerShellGit`, `git.ts`), because one long-lived client caches the index and, having read a repository before its first `git add` (no `.git/index`), kept reporting every committed file as deleted after the Container committed (seen deployed; the workerd test replays it with files real git wrote).
- **Worker Shell git memory.** isomorphic-git reads a whole packfile into memory, and the Workspace DO has 128 MB for everything it hosts, so `git status` or `git log` in a clone with a big pack could take the Workspace down. The Worker Shell's git client (`apps/server/src/workspace/git.ts`) is built anew for every call, so a pack is read again each time, and it refuses any command in a repository whose `.git/objects/pack/*.pack` files total more than 16 MB (`MAX_PACK_BYTES`): the command fails with a message to rerun with `backend: "container"`. Loose objects are not counted, and 16 MB is a conservative guess, not a measurement of where the DO runs out.
- **Changes in the Workspace DO, measured** (#228; local workerd only, see below). `changes.bench.workerd.test.ts` (run with `CHANGES_BENCH=1`) lists repos real git made of 1,000, 5,000 and 20,000 tracked files of about 300 bytes (50 to a directory, one commit, packed, 10 files edited), written into a Workspace DO as computer's sync writes them. Times are from the test's side of each call, as workerd's clock stands still while code runs; three runs (two with the inspector attached), on a 4-vCPU AMD EPYC container:

  | Tracked files | `statusMatrix({ refresh: false })` | Whole listing (10 changed) | `readBlob` of 100 files | Live heap at the peak, `statusMatrix` / listing |
  | ------------- | ---------------------------------- | -------------------------- | ----------------------- | ----------------------------------------------- |
  | 1,000         | 1.1–1.4 s                          | 1.0–1.2 s                  | 0.27–0.44 s             | +5 MB / +5 MB                                   |
  | 5,000         | 5.9–7.5 s                          | 4.4–6.0 s                  | 0.29–0.51 s             | +29 MB / +15 MB                                 |
  | 20,000        | 35–40 s                            | 34–39 s                    | 0.54–1.2 s              | +104 MB / +63 MB                                |
  - **Every tracked file is read and hashed at every listing.** isomorphic-git trusts the index's stat only when mode, times, owner, inode and size all match, and the Workspace DO's files never match what the Container's git recorded (their own inodes, owners and times), so `refresh: false` (which keeps `.git/index` unwritten) means nothing is ever cached. That is stat drift at its worst, and the measurement: writing every file again with the same bytes changed nothing (`statusMatrix` took as long, 0.9 / 4.6–5.4 / 37–39 s, and still found the 10 edited files). The flip side is that a same-second, same-size edit git could miss (racy git) is never missed here.
  - **Time is the limit, not memory.** About 1.1–1.5 ms a file up to 5,000 and 1.8 ms at 20,000, all of it synchronous: the provider reads SQLite in-process, so a listing that never paused would hold the Workspace DO from start to end (the agent's file tools waiting), and 20,000 files is past the 30 s CPU a request gets by default. So the listing pauses every 50 reads (`YIELD_EVERY`, about 60 ms of work), which costs time, not memory (the measurements' pausing runs show it), and the Workspace DO's other calls run in the pauses (`changes.workerd.test.ts` checks a read sent during a listing is answered before it ends). `readBlob` is a few ms a blob once the pack is loaded, so the HEAD sides of the changed files (at most 2,000) cost little next to the walk. The live heap (sampled from outside after a forced collection every 0.5 s, with the walk pausing every 20 reads so the samples land during it: `scripts/heap-poll.mjs`, as workerd shows a Worker no memory figures) grows about 5 KB a tracked file, so 20,000 files would take most of the 128 MB the isolate has for everything.
  - **The guard is 2,000 tracked files** (`MAX_TRACKED_FILES`): about 2.5 s and 10 MB, at each refresh (1 s after an agent's last write, on connect, on focus), in slices of about 60 ms. A stat cache (path → size and time → blob id, kept by the Workspace DO) would make a refresh read only what changed; it is a follow-up. A bigger repo goes to the Container's git, as one with a pack over 16 MB does, and shows its last list, "may be out of date", while the Container is stopped.
  - **Not measured on Cloudflare.** The ticket asks for a deployed stage too; it was not done here (the preview stage sits behind Access, and a deployed run needs a temporary route that seeds a repo through the Container). Cloudflare's CPUs may be faster or slower than this container's, so the guard may move once it is: measure with the same phases there, through a temporary route on the Workspaces Worker that has the Container make the repo with real git and then calls the listing.

- **The Run copy in the Workspace DO, measured** (#233; local workerd only, not deployed). `runs.bench.workerd.test.ts` (run with `CHANGES_BENCH=1`) copies the 1,000-file repo of the Changes measurements (10 files edited before the Run, 10 during it) through the DO's `runStart`, `runDiff` and `runEnd`: the start copy took 0.6 s, a live list 0.4 s, the end copy 0.9 s and the frozen list under 10 ms (two runs, same container as above). The 5,000- and 20,000-file repos are over `MAX_TRACKED_FILES`, so they are the Container's git's: with the Container stopped they have no copy ("container_stopped") and nothing is started; the Container's script is tested in plain bash (`apps/sandbox-image/src/runs.test.ts`) but not measured on a Container.

- **Preview packages.** `@cloudflare/computer` is a preview: its container backend, the Worker Shell, and computerd are experimental. Pin versions and keep the image and package in lockstep.
- **pi-durable storage version.** pi-durable 1.4.0 migrates a Session's `pi_` tables to its SQLite schema version 2 when it opens them, which 1.3.0 cannot open: a deploy cannot be rolled back to a build with pi-durable 1.3.

- **Exposure of the shared browser session.** Raw CDP in the shared browser session can read cookies and filled values, so prompt injection from pages is the main threat. Mitigations are host-side fills, origin checks, and per-item approval; text taken from a page for the model (the owner's attached pages) is redacted of held Secrets, fenced as untrusted page content, escaped and apart from the owner's words ([_Attached pages_](client-and-protocol.md)). A Live View link, a Browser Handoff's or the Browser Pane's, is part of this exposure. A link opens **every page of the browser session**, not only the tab it names (putting another page's target ID in its path connects to that page), and connects any number of times until its deadline, 60 s after it was minted; Browser Run cannot revoke it, and its `expiresInMs` only bounds when a connection may _start_: a connection opened in time outlives it (the spike kept two open for 15 minutes), and Done, Failed, or Stop does not close it. Anyone holding a link within its minute, or a connection opened with one, controls the shared, logged-in browser and can watch later work in it. So links are minted only when the owner's Live View Pane asks (`live_view`, or **Open in Cloudflare**) or the owner's Browser Pane does (`owner_tab_view`), one per open, reconnect or window, and go to that client alone: none is stored in the Session or the browser host, sent to other clients, put in a push, or shown to the agent ([ADR-0013](../adr/0013-own-live-view-with-links-minted-on-open.md)). The Pane's own connections are the owner's to close; the Live View Pane closes when the handoff ends. Since the Browser Pane, a link can be minted whenever the owner's client asks, not only while a handoff waits: the exposure of each link is the same, but one can now exist for as long as a Browser Pane is open on one of the owner's devices, and the browser it opens holds whatever the owner signed in to in an Owner tab, as well as the agent's logins. **Recorded addresses (#240):** the browser host keeps each Owner tab's address in its storage and replays it when it reopens the tab in a new browser. The `#fragment` is dropped before storing (an OAuth `#access_token=` or `id_token` lives there), but the query string is kept, so a secret in it (an OAuth `code=`, a magic-link token, a signed URL) is held in the host's storage until the tab moves on or closes, and is replayed when a replaced browser reopens the tab; a single-use token is normally spent by then, a reusable one is not. Only `http(s)` and blank addresses are kept. **Container previews (#251, ADR-0023):** the browser's routes reach the dev servers on the Session's Workspace's Container at `http://<port>.cloudpid.internal/` for eight ports, with no public URL, token or credential anywhere (not in the agent's code or results, the browser's history, or a screenshot of the address). Only pages in the Session's browser reach them: the agent's code in any tab, the owner in an Owner tab, and any page either opens, prompt-injected ones included, as on a laptop's `localhost`. From an `https` page a request to a Container preview is blocked as mixed content (the spike, #244). A page with an `http` or `null` origin can send a dev server blind requests (a `no-cors` GET or a form POST) but cannot read the answers, which the dev server's own CORS decides (Vite's allows only its own origins); such a page cannot write into a Container preview's carried socket, as the socket endpoints need a header that forces a preflight and the page's own `Origin`, and a carried socket's ID is unguessable. What a dev server serves (often the source and its config) is readable by code running in the Container preview's own origin and by the agent, who can read the Workspace anyway. Only the eight Container preview ports are routed or served (never computerd's 8080), and the `Browsers` Worker reaches nothing of a Workspace DO but its Container preview. An open Container preview keeps the Container running (its carried socket counts as use) until the page or the browser closes or stops reading.
