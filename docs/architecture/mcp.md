# MCP

cloudpid speaks MCP on both sides of the protocol. As a **client and host** it reaches the MCP server set of each Environment for the agent and the owner: remote Streamable HTTP servers from the Durable Objects, and stdio servers lazily in a Workspace's Container. As a **server** it offers the MCP endpoint, through which a Local agent works with cloudpid as the owner, above all to hand a local pi Session off as a Session import. Everything here ships in milestone v2 (see [_Milestones_](overview.md#milestones)).

## Scope

- **The spec:** every client and host feature of the MCP specification from `2025-11-25` to the present, MCP Apps included, at parity with pi's MCP (`mcp__<server>__<tool>` names, the four Exposures, the `mcp_servers` section, resource tools, entries compatible with pi's `mcpServers` shape). pi's CLI and `/mcp` TUI become cloudpid UI: the Settings page's MCP servers section and Slash commands.
- **Deprecated but specified features are built:** Roots, Sampling, Logging and Dynamic Client Registration are deprecated in `2026-07-28` but still in the spec, so cloudpid implements them ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D19–D22). Remote servers are offered no `roots` ([_Roots_](mcp-in-a-session.md#roots)).
- **Transports:** Streamable HTTP, sent from the Durable Objects' side through `fetch`; stdio only in the Container, through cloudpid's own bridge ([_The stdio bridge_](mcp-connections.md#the-stdio-bridge)), never on the Worker Shell. The legacy HTTP+SSE transport is refused, as pi refuses it.
- **Out of scope:** Enterprise-Managed Authorization (the owner's one exception, kept for a later version as [Enterprise-Managed Authorization for MCP servers (future version)](https://github.com/ian-pascoe/cloudpid/issues/404)), the `2025-11-25` experimental tasks, the legacy HTTP+SSE transport and stdio on the Worker Shell. Skills over MCP and Server Cards wait for tickets of their own ([_Extensions_](#extensions)).
- **Left for later:** the map's "Not yet specified" items (among them MCP status in the UI, fast stdio cold starts, Telemetry and Usage for MCP calls) are not specified here.

## Protocol eras

cloudpid speaks both Protocol eras (`GLOSSARY.md` → Protocol era) and hides the difference behind `@cloudpid/mcp` ([ADR-0036](../adr/0036-the-mcp-core-is-the-official-sdk-inside-cloudpids-own-era-agnostic-module.md)).

- **Versions:** Legacy offers `2025-11-25` and accepts `2025-06-18`, `2025-03-26` and `2024-11-05`; Modern is `2026-07-28` only, and on `-32022` uses the highest version both sides support. The SDK's `supportedProtocolVersions` is set to exactly those five (its `2024-10-07` dropped). A server with no common version is `failed` ("supports only <list>"). Features follow the negotiated version and the server's capabilities ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D1).
- **The probe:** when the MCP host object first discovers a server, the core probes its era with the SDK's `versionNegotiation` (`mode: "auto"`, `server/discover`, 15 s, no retry) and the SDK's own classifier, as is (it reads `-32020`/`-32021` as Legacy; a Modern server misread that way fails its `initialize`, and the problem quotes the probe's error). A 408 or 429 is retried once after `Retry-After` (≤10 s) and then reads as unavailable, never as Legacy. The outcome table (401, 403, 5xx, redirects, non-JSON-RPC answers) is in [The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D2. A stdio server's era is probed by the bridge on the child's stdin, hinted by `x-cloudpid-era` (D4; [_The stdio bridge_](mcp-connections.md#the-stdio-bridge)).
- **The era cache:** one `mcp_eras` row per connection key `conn` ([_Storage_](mcp-connections.md#storage)), with the negotiated version and `server/discover`'s result (≤64 KiB) and a format `v`, passed to the engine as `prior` so a Modern server reconnects with no round trip. Modern is kept until contradicted; Legacy is re-probed at the next `initialize` once 24 h old. The row is dropped on a Modern server's 400 (no Modern error), 404 or 405 (the request is resent once, `tools/call` included, since it was refused before it ran), a failed Legacy `initialize`, `-32022`, a change to the server's `conn` (or its leaving the set), and a reload ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D3, keyed by `conn` per [The Environment's MCP host object](https://github.com/ian-pascoe/cloudpid/issues/382) D3.1). Since `conn` leaves out `description`, `timeout`, `enabled` and Exposure, editing those never re-probes.
- **What the owner sees:** a server's negotiated protocol version, read-only (its status, `settings_mcp_list`, `settings_mcp_get`), never the word "era". No key forces an era.
- **Questions follow the era** ([ADR-0037](../adr/0037-a-modern-mcp-servers-question-is-answered-with-a-new-request-and-a-legacy-ones-lives-only-as-long-as-its-call.md)): a Modern server's Elicitation request or Sampling request can wait durably for the owner; a Legacy one lives only as long as its call. Sampling, elicitation and MCP tasks build on that one shape ([_Questions_](mcp-server-requests.md#questions)).

## Extensions

An MCP extension is a protocol extension the spec's `extensions` capability declares, not a pi extension. The rule ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) E2, D23):

- **Implemented:** Stable official extensions, except Enterprise-Managed Authorization, and Beta extensions headed for the core spec (today, tasks).
- **Declared** in Legacy `initialize`'s `capabilities.extensions` and in Modern per-request `_meta` client capabilities:
  - **MCP Apps** (`io.modelcontextprotocol/ui`): `{ mimeTypes: ["text/html;profile=mcp-app"] }`, always, in both eras, on every request ([_Declaring and reading Apps_](mcp-apps.md#declaring-and-reading-apps)).
  - **Tasks** (`io.modelcontextprotocol/tasks`): Modern only, on the core's own task wire ([_MCP tasks_](mcp-server-requests.md#mcp-tasks)).
  - **OAuth Client Credentials** (`io.modelcontextprotocol/oauth-client-credentials`): only on connections using that grant ([_Client Credentials_](mcp-sign-in.md#client-credentials)).
- **Not declared, waiting for a ticket of their own:** Beta extensions with no destination in cloudpid yet, Skills over MCP and Server Cards (left for later: the map's "Not yet specified").
- **Never:** Experimental features until they reach Beta, the `2025-11-25` experimental tasks included: their capability is never declared, a tool with `execution.taskSupport: "optional"` is called synchronously, and one with `"required"` gets a per-tool problem and is not offered. Third-party extensions are never declared.

- **The SDK pin:** `@modelcontextprotocol/client`, `core` and `server` at exactly 2.4.0, one version for all three, pinned on their own (not to `agents`' peer, which `apps/browser` keeps as its own unused copy). `@modelcontextprotocol/ext-tasks` is a devDependency of `packages/mcp` only, for its fake server and fixtures, and `@modelcontextprotocol/ext-apps` a devDependency of `apps/web` only. A bump passes the upgrade gate: the client CHANGELOG, the conformance suite at the SDK's own CI version against `packages/mcp/conformance/baseline.json`, the fake servers, golden tests of the SDK behaviour the core leans on, and the workerd tests ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D9). Protocol fixes go upstream to the SDK, not to pi; pi gets only the sign-in additions, as an issue first.
- **The import rule:** only `packages/mcp` imports `@modelcontextprotocol/*` at runtime, and only `McpEngine` and `McpServer` load it: the SDK adds about 9–10 MiB of cold heap per package to every isolate that loads it, and a Worker's Durable Objects share isolates. Everything else uses RPC. Sessions, the `mcp` extension, `McpHost` and the web app import `@cloudpid/mcp/types` (the bridge is a lone dependency-free script in the image, which imports nothing at runtime; the engine and the Workspaces Worker take its wire constants from `@cloudpid/sandbox-image/mcp-bridge`); the Registry and the main Worker (which runs `/oauth/mcp/start` and the callback) import `@cloudpid/mcp/types` and `@cloudpid/mcp/oauth`, neither of which loads the SDK. Tests outside `packages/mcp` (the engine's) take the fake MCP servers from `@cloudpid/mcp/testing`, which loads the SDK server and is imported by tests and their fixtures only. `apps/web` may import types only from `@modelcontextprotocol/ext-apps` for its own App bridge ([Rendering an MCP App in the web UI](https://github.com/ian-pascoe/cloudpid/issues/384) D16), which the lint rule allows. oxlint's `no-restricted-imports` enforces the rule, and a bundle test fails if the main Worker or `apps/browser` bundles any `@modelcontextprotocol/` module ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D10, D23, refined by [The Environment's MCP host object](https://github.com/ian-pascoe/cloudpid/issues/382) E1). The rule is about Workers: `packages/pi-cloudpid` imports and bundles `@modelcontextprotocol/client` at the same pin ([Handing off a local pi Session to cloudpid](https://github.com/ian-pascoe/cloudpid/issues/393) D8.1, D14).
- **The core's seam:** `connect(target, deps) → McpConnection`, with `list(kind)` (every page), `callTool`, `getPrompt`, `readResource` (with a SHA-256 of its contents), `complete`, `resume(state, answers)`, `listen(filter)` and `task.get`/`update`/`cancel`. Results are an `Outcome`: `complete` (with `cacheable`), `input_required` (with its requests and a `ResumeState`), or `task` (`tools/call` only). Errors are a tagged `McpError`: `SignInRequired`, `StepUpRequired`, `Unreachable`, `Cut { mayHaveRun }`, `TooLarge`, `TimedOut`, `ServerError`, `NotFound`, `Unsupported`, `ProtocolViolation`. Everything outside the core is injected, never created: `fetch` (guarded, queued, or the Container port), `auth`, the era and Legacy session stores, `capabilities(ctx)`, `extensions`, `roots(ctx)`, `onInput`, `onLog`, `clientInfo` (`{ name: "cloudpid", version: <deploy> }`); the clock is Effect's `Clock`. `connect` lives in a `Scope` and closes the SDK client with it. One connection serves one HTTP server, or one (stdio server, Workspace) ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D7). Retries, cuts, timeouts and byte limits are in [_Failures and cuts_](mcp-connections.md#failures-and-cuts).
- **Inside the core:** the stores hold each `prior` row as JSON, which the core decodes by its format `v` (a row it cannot read is absent). `McpError` and the rows' Schemas are in `@cloudpid/mcp/types`, since they cross the engine edge; `McpErrorWire` is `McpError` with its fallback member, `OtherMcpError`: a tag this build does not know, or a known tag whose fields do not fit, reads as this tag of its own, keeping the original in `tag`, and may have run unless it says `mayHaveRun: false`. `mayHaveRun(error, method)` says whether a failed request may have run, so whether it may be sent again: for a `tools/call`, a `Cut` that says so, an `OtherMcpError` that does not say not, and every failure after the server took the call (`TimedOut`, `TooLarge`, `ProtocolViolation`, `Unreachable` with a 5xx) may have; what the server refused before running it (`Unreachable` with a 408, 429 or no status, sign-in, step-up, `ServerError`, `NotFound`, `Unsupported`) did not. Any other method runs nothing, so only an explicit `mayHaveRun` counts. `callTool` takes the tool's definition, not its name: its `inputSchema` gives the `Mcp-Param` headers, and its `outputSchema` is withheld from the SDK, which would otherwise refuse a result without `structuredContent`, since the engine validates `structuredContent` itself (D17); the SDK's own validator is replaced by one that validates nothing, so it never builds one. The probe's `failed` rows (a 403 without `insufficient_scope`, a redirect to another origin) are `ServerError` with the HTTP status, a 2xx that is not JSON-RPC is `ProtocolViolation`, and 5xx, 408, 429 and network errors are `Unreachable`. The core's `fetch` tap does what the SDK does not: it retries at the seam, refuses cross-origin redirects, counts bytes, and fails a request whose stream ends without its answer by answering it with a JSON-RPC error that names the core's own verdict, so the SDK settles the request at once.
- **Not built in the core:** a `-32020` (a header the server rejects) fails the call as `ServerError` with that code, since the SDK, given the tool's definition, does not refresh it; the engine refreshes `tools/list`, retries once and returns the fresh tools for the catalog ([_The engine_](mcp-connections.md#the-engine); [The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D14). Remote Legacy SSE resume (`Last-Event-ID`, D15) is not built: every connection runs with `maxRetries: 0`, so a Legacy request stream that ends without its answer is a `Cut` at once. The tap answers such a stream with its verdict before the SDK could reconnect, so resuming means teaching the tap to hand the SDK's resumed GET the rest of the request's events; that is core transport work, left for [#542](https://github.com/ian-pascoe/cloudpid/issues/542) ([_Requests and Legacy sessions_](mcp-connections.md#requests-and-legacy-sessions)).
- **Not terms:** "MCP host object", "MCP engine", "MCP connection", "MCP input request" and "MCP extension" are implementation words for these documents, never shown to the owner. The spec's "host" is the whole application.

## RPC edges

```
main Worker ─serve(request, api)──────────────────────────▶ McpServer (McpWorker) ─api: McpApi─▶ Registry, Sessions
main Worker ─apply, servers───────────────────────────────▶ McpHost (Server)
Session DO  ─requestStart, servers, request, apply────────▶ McpHost
McpHost     ─mcpServerSet, mcpServerValues, mcpAccessToken▶ Registry (same script)
McpHost     ─discover, request, listen, control───────────▶ McpEngine (McpWorker)
McpEngine   ─fetch────────────────────────────────────────▶ remote MCP server
McpEngine   ─mcpBridge────────────────────────────────────▶ WorkspaceMcpBridge (Workspaces) ─▶ Workspace DO ─▶ Container bridge ─stdio─▶ server
callbacks on a call: engine → host (auth, opened; a server's logs come back in the result, not through a hook); engine → host → Session (onInput, onProgress); untilAborted settles from the caller's end
```

- **Bindings are one way:** `Server` binds `MCP_ENGINE` and `MCP_SERVER` (`McpWorker`'s Outputs, not literals); `McpWorker` binds `MCP_BRIDGE` = `Cloudflare.WorkerEntrypoint(workspaces, "WorkspaceMcpBridge")`. There is no cycle, so a fresh preview stage deploys in one pass ([ADR-0038](../adr/0038-the-mcp-host-object-lives-beside-the-registry-and-runs-the-sdk-through-a-stateless-engine-in-a-worker-of-its-own.md)).
- **`McpHost`'s four methods** (`requestStart`, `servers`, `request`, `apply`) are typed with Effect Schemas in `@cloudpid/mcp/types`, failures returned as values ([_RPC_](mcp-connections.md#rpc); [The Environment's MCP host object](https://github.com/ian-pascoe/cloudpid/issues/382) D6.1). The host also calls the Registry's `reportMcpAuth`.
- **Nothing calls a Session**, and the Registry never calls out ([ADR-0030](../adr/0030-mcp-tools-reach-a-session-as-an-extension-rebuilt-from-the-mcp-inventory.md), [ADR-0032](../adr/0032-a-resource-watch-is-held-while-its-conversation-runs-and-checked-by-re-reading-after-every-gap.md)). A server's questions, progress and logs reach a Session as callbacks passed down the call, Session → host → engine; the main Worker (owner's saves, Repo changes, sign-in callbacks) and the Sessions (`settings_mcp_*`, watch ends) carry the Registry's changes to `apply` ([The Environment's MCP host object](https://github.com/ian-pascoe/cloudpid/issues/382) D6.3); the host pulls the MCP server set from the Registry when a Context Window opens.
- **Callbacks:** function and `RpcTarget` arguments pass as native stubs two hops deep, through alchemy's Effect Durable Object Tag too, and live only as long as the invocation that made them, so the Session awaits the call for its whole length. RPC carries no `AbortSignal`: every call carries `untilAborted()`, and the engine holds each call's work under `ctx.waitUntil` so a dead host reaches it as that callback rejecting ([Verify MCP host ↔ engine RPC](https://github.com/ian-pascoe/cloudpid/issues/409) answers 1, 2, 5; detail in [_RPC_](mcp-connections.md#rpc) and [_The engine_](mcp-connections.md#the-engine)).
- **Large results and connection slots:** a result over 1 MiB passes engine → host → Session as a byte `ReadableStream` the host returns unread, never as an Effect `Stream`; Workers' six connections waiting for headers count only the engine's own `fetch`es, never RPC ([Verify MCP host ↔ engine RPC](https://github.com/ian-pascoe/cloudpid/issues/409) answers 3, 7; [_The engine_](mcp-connections.md#the-engine)).

## Deploys

The stack keeps the platform's default Durable Object code update strategy (`deferred`, `max_delay` 300 s), so a busy Session or `McpHost` runs older or newer code than the other for up to five minutes, and a stateless engine call finishes on the version it started on ([`workers.md` → _Deploys and Durable Object code updates_](../development/workers.md#deploys-and-durable-object-code-updates); [Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423) D1–D2).

- **Deploy order:** Workspaces → Browsers / CodemodeSandboxes / `McpWorker` → `Server`. Only `prod` deploys the App sandbox.
- **Every MCP edge only gains**, the ones inside `Server` included: new methods, `op`s, tags and optional fields. A change of meaning is a new method or `op`, never an optional field (an old callee's Schema drops unknown keys). An unknown method or `op` fails loudly (`HostUnsupported`, `Unsupported`). Failure tags and states carry a fallback member read as a generic failure (for `tools/call`, one that may have run), in RPC and in storage. A new success shape is returned only when the caller asked for it (`ctx.allowTask`, `ctx.answers`).
- **Gates, per edge:**

  | Edge                                                                                                         | Gate                                                                                                                                                                                                 |
  | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | Session → host                                                                                               | `features: string[]` from `requestStart`; the Session rebuilds `mcp` when the features its tool declarations used change                                                                             |
  | host / engine → Session callbacks                                                                            | the callback's presence; `ctx.answers` for the kinds of question                                                                                                                                     |
  | `McpServer` → `api`                                                                                          | `describe()`, cached per isolate for 60 s                                                                                                                                                            |
  | engine → Container bridge                                                                                    | `x-cloudpid-bridge: <level>` on every response, with a minimum; below it the server is `failed` ("this Container runs an older bridge; restart it"); the minimum rises ≥7 days after an image change |
  | main Worker → host; host → Registry; main Worker → Session (`McpApi`); Session → Registry (`settings_mcp_*`) | none: a loud failure that heals (the next `windowOpened`, backoff, "not available yet")                                                                                                              |
  | host → engine; main Worker → `McpServer`; engine → `WorkspaceMcpBridge`                                      | deploy order, with the loud failure as backstop                                                                                                                                                      |

- **Removals** merge ≥24 h after the change that stopped using them reached prod, or after the retention of a stored payload that can hold them (`ResumeState`: 30 days).
- **Stored payloads that cross an edge:** `prior` rows (era, Legacy session) carry a format `v`, and an unknown `v` reads as absent (probe or `initialize` again); `ResumeState` carries `v` in the core's envelope, old `v`s readable ≥30 days, after which the question expires visibly and its call settles as a cut that may have run. Structured records cloudpid owns (host tables, MCP task and App records) stay additive with fallback members, without a `v` ([Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423) D3.4).
- **Calls in flight:** an `McpWorker` deploy cuts nothing, since calls finish on the engine version they started on. A real cut is `Cut { mayHaveRun: true }` with `details.cut: "engine_lost"`, or `"host_lost"` on the Session's side when the host's end goes ([Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423) D5). What a replaced host or a replaced Session does with its calls is in [_Deploys_](mcp-connections.md#deploys) there. `Server`'s edges outside MCP are audited apart, in [Audit Server's RPC edges and reverts for deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/426).

## Request flow

- **Configuration:** the Registry resolves an Environment's MCP server set (Global, the Environment's Overrides, each Repo's `.pi/mcp.json`) and hands it to `McpHost` through `apply({ kind: "set" })`, carried by the main Worker or a Session, and through `mcpServerSet` when a Context Window opens ([_From the Registry to the host_](mcp-configuration.md#from-the-registry-to-the-host)). An Environment with no MCP servers never wakes its host: a Session whose `sessionSettings` says `mcp: { servers: 0 }` and that holds no Resource watch skips `requestStart` ([_The host object_](mcp-connections.md#the-host-object)).
- **Request start:** at each request start (where it refreshes its Settings) the Session calls `requestStart`. The host answers the MCP inventory's content-hash `version`, `promptsVersion`, `features` and Resource watch changes, and starts any discovery that is due; on a changed version the Session reinstalls `mcp`, `codemode` and `tool-search` together from the inventory ([_The `mcp` extension_](mcp-in-a-session.md#the-mcp-extension)).
- **A call:** an `mcp__<server>__<tool>` call (direct, or nested in `codemode`) goes Session → `McpHost.request({ op: "tools/call", ctx })` with its callbacks. The host resolves the definition's `${NAME}` values (`mcpServerValues`) and the `prior` rows, then calls `McpEngine.request`; the engine gets an access token through its `auth` hook, which the host answers from the Registry's `mcpAccessToken` ([_Tokens reach the host object_](mcp-sign-in.md#tokens-reach-the-host-object)). The engine `fetch`es a remote server, or reaches a stdio server through `WorkspaceMcpBridge` → the Workspace DO (which may start the calling Workspace's Container) → the Container bridge → the child's stdin. The result and the updated rows return; the host stores the rows and the Session the result. Every MCP tool is `replay: "safe"`, with pi-durable memo markers, so a `tools/call` is never sent twice and an eviction mid-call settles as "may have partially run" ([Sampling](https://github.com/ian-pascoe/cloudpid/issues/387) D17; [_Calls and results_](mcp-in-a-session.md#calls-and-results)).
- **A question:** a Legacy server's question arrives live on the call's stream and reaches the Session through `onInput`; a Modern one returns `input_required`, whose `ResumeState` the Session keeps and later sends back with the owner's answer as `request({ op: "resume" })` ([_Questions_](mcp-server-requests.md#questions)).
- **The owner's side:** App Views, MCP prompts, completions and Attached resources go web app → Session socket → Session → `McpHost`; Settings and status go through `RegistryRpcs` and the main Worker. MCP sign-ins stay in the Registry ([`mcp-sign-in.md`](mcp-sign-in.md), [`mcp-apps.md`](mcp-apps.md)).
- **The MCP endpoint:** a Local agent's request passes Access, the main Worker verifies the Access assertion and calls `MCP_SERVER.serve(request, api)`; `McpServer` answers through `api`, an `McpApi` `RpcTarget` over the Registry and Sessions ([_The `api` target_](mcp-endpoint.md#the-api-target)).

## Testing and tracing

- **Conformance:** the official `@modelcontextprotocol/conformance` suite runs in CI, pinned to the SDK's CI version (`0.2.0-alpha.12`, from the SDK's `test/conformance/package.json` at its 2.4.0 tag; [`dependencies.md`](../development/dependencies.md)), against the committed `packages/mcp/conformance/baseline.json`: the client in every mode (`2026-07-28`, `2025-11-25`, `2025-06-18`, `2025-03-26`) through a small Node scenario client over the core, and the MCP endpoint's server scenarios in every mode ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D25). The client (`conformance/client.ts`) reads the scenario the runner hands it and drives `connect`, `list` and `callTool` with a plain `fetch` and in-memory stores; `conformance/server.ts` serves the endpoint (`serveMcp` from `@cloudpid/mcp/server`) over `node:http` with a fixed in-memory `api`; `conformance/run.ts` runs the client scenarios and then the server scenarios for one mode (`bun --cwd packages/mcp run conformance <mode>`), one `Conformance (<mode>)` job each in `ci.yml`, which `Check` waits for. The baseline has a section per mode (the runner keys entries by scenario name alone, and a scenario can pass in one mode and fail in another), each with `client` and `server` entries grouped by the reason they fail, each entry a scenario, or `<scenario>:<check-id>` for one check of it. A failure outside it fails the job, and so does an entry that now passes (the runner reports it as stale), so the baseline only shrinks: a slice that makes the core drive a scenario removes its entry in the same change. A scenario the client cannot drive exits 1, so it is baselined and not skipped. Baselined today: the `auth/*` scenarios (the OAuth flow is the Registry's sign-in through `@cloudpid/mcp/oauth`, never the core's or the SDK's, so they stay baselined unless the scenario client is given a sign-in of its own; [`mcp-sign-in.md`](mcp-sign-in.md#tokens-reach-the-host-object) → _Tokens reach the host object_ → Code), `sep-2322-client-request-state` and `elicitation-sep1034-client-defaults` (no questions yet), `sse-retry` (Remote Legacy SSE resume is kept, [#394](https://github.com/ian-pascoe/cloudpid/issues/394) D15, but not built yet, [#542](https://github.com/ian-pascoe/cloudpid/issues/542)). The `http-invalid-tool-headers` exclusion checks pass since [#449](https://github.com/ian-pascoe/cloudpid/issues/449): `client.ts` filters a Modern server's listed tools through `xMcpHeaderProblems` (`@cloudpid/mcp/types`, the check discovery makes) before calling them. The server side baselines what the endpoint does not serve: the suite's fixture tools (`test_simple_text`, `test_error_handling`, the `input-required-result-*` and diagnostic ones), which only its own everything-server has; resources, prompts, completions and logging (the endpoint advertises `tools` only); and the Legacy SSE session scenarios (both eras are stateless: `GET` is `405`, so no priming event, `retry` field or second stream). The runner counts a `WARNING` check as a failure once a baseline is given, so a SHOULD the endpoint skips is baselined too. Everything else passes: `tools/list`, `initialize`, `ping`, DNS-rebinding protection, the HTTP header checks and the stateless checks of `2026-07-28`.
- **Fake servers** behind the injected `fetch`, on the SDK server, cover what the suite does not: Modern, Legacy stateless, Legacy stateful with a GET stream, tasks, and a hostile server (cut streams, oversize bodies, bad headers, odd 400 bodies); plus the bridge, eviction, byte limits and resume.
- **The import rule's bundle test** and the SDK upgrade gate are above ([_Packages and objects_](#packages-and-objects)); the host, engine and replaced-instance workerd tests are in [_Testing_](mcp-connections.md#testing).
- **Tracing:** Workers tracing joins the main Worker, Session, host and engine of one call into one trace with no manual parenting; work another invocation started (a listen reopened later, a background discovery) records the causing trace's ID as an attribute, since spans can't be re-parented or linked. `traceparent`/`tracestate` go in `_meta` only to cloudpid's own bridge, never to remote servers, and `baggage` is never sent ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D18; [Verify MCP host ↔ engine RPC](https://github.com/ian-pascoe/cloudpid/issues/409) answer 6). The spans themselves are in [_Telemetry_](mcp-connections.md#telemetry). **As built** ([#453](https://github.com/ian-pascoe/cloudpid/issues/453)): the ID is the runtime's trace ID of the span current when the discovery was started (`spanContext().traceId`, through `currentTraceId` in `@cloudpid/telemetry`), recorded as `mcp.cause_trace_id` on `mcp.discover`; a runtime that gives none falls back to Effect's own.
