# Container and Toolchains

[ADR-0004](../adr/0004-mise-toolchains-with-preinstalled-defaults.md) covers this design.

- **Image:** `ubuntu:26.04` (pinned by digest, as every base image is) plus `fuse3`, the everyday command-line tools agents and scripts expect (`curl`, `wget`, `jq`, `ripgrep`, `fd-find` with `fd` linked to its `fdfind`, `unzip`, `zip`, `xz-utils`, `procps`, `psmisc`, `lsof`, `iproute2`, `dnsutils`, `netcat-openbsd`, `less`, `file`, `tree`, `openssh-client`, `gnupg`, `sudo`, `sqlite3`, `tzdata`, and from exe.dev's exeuntu list `rsync`, `socat`, `net-tools`, `iputils-ping`, `bubblewrap`, `locales` with `en_US.UTF-8`, and `time`), `build-essential` with `pkg-config` and the headers native npm and pip packages build against (`libssl-dev`, `zlib1g-dev`, `libffi-dev`), Docker (see _Docker_, below), `earlyoom` (the memory guard: see _Memory guard_), `computerd` (pinned to match `@cloudflare/computer`, run under the image's supervisor: see _Exit reports_), and `mise` ([#169](https://github.com/ian-pascoe/cloudpid/issues/169), ADR-0004's second revision). Every versioned program a project uses, `git` and `gh` included, is a mise Toolchain, never an apt package (an apt `git` a package pulled in would be behind mise's shims on `PATH` anyway); the image preinstalls the base Toolchains into mise's system directory (next bullet), where they are still found and managed as Toolchains, through the Workspace's mise config. `python3-pip` and `pipx` are left out, since they would bring apt's Python beside mise's. The image must be glibc-based, so no Alpine. exeuntu itself is not the base: it is a VM image with systemd, exe.dev's integrations and a desktop's libraries, 1.8 GB compressed against this image's few hundred MB, which every launch from the image and every Snapshot would pay.
- **Preinstalled Toolchains:** the image holds mise's installs of the base `mise.toml`'s Toolchains, one exact version each of `conda:git`, `gh`, Node (the LTS), pnpm, Python and uv (`BASE_MISE_TOML` in `apps/sandbox-image/src/toolchains.ts`; the image builds from its copy, `apps/sandbox-image/image/mise.toml`, which a test keeps equal). They are in mise's system directory (`mise install --system`, `/usr/local/share/mise/installs`, shims in `/usr/local/share/mise/shims`, on `PATH` after the user shims), which mise searches for a version a config asks for before it downloads one, so they are used by any Workspace or repo whose config asks for exactly those versions, and by none that does not: a project's versions still decide (ADR-0004). `mise ls` labels them `(system)`. The image also makes the base file's `mise.lock` (`BASE_MISE_LOCK`, `/usr/local/share/cloudpid/mise.lock`), because `mise lock` downloads the aqua and Python artifacts it checksums (90 MB for these), which would undo the preinstall. The versions are exact because mise locks a prefix (`node = "24"`) to the newest release, which the image soon would not have. Refreshing them is an image change: a new Workspace then gets the new versions, and an existing one keeps its own, downloaded if the image no longer has them.
- **Persistence:** `mise.toml` and `mise.lock` live in the workspace and are synced; a Workspace with no mise config gets its Environment's Toolchains as its root `mise.toml` on the first Container start (its `toolchains` Container setting), or the base `mise.toml` (the image's preinstalled Toolchains: see above) with the image's `mise.lock` for it beside it when the setting is empty. The bootstrap records the SHA-256 of the copy it wrote, with the lockfile made for it, in `/var/lib/cloudpid/toolchains` (`TOOLCHAINS_STATE_DIRECTORY`, outside `/workspace`, so nothing syncs it and a snapshot carries it), and replaces a root `mise.toml` that still has that hash (or is the base file, which it wrote before it kept a record) when the Environment's Toolchains change, with the recorded lockfile when it is for the same copy; a root `mise.toml` the Workspace changed is its own and stays, and so does a root with a mise config of another name; a root `mise.toml` the Workspace changes later is locked by the bootstrap (`mise lock --global`, to `linux-x64`). The Toolchains themselves (`MISE_DATA_DIR`, `MISE_CACHE_DIR`) stay in mise's default place on the Container's disk, `/root/.local/share/mise` and `/root/.cache/mise`, with `TMPDIR` as `/tmp` on the same disk, so an install never renames across a filesystem or the ignore boundary (no `EXDEV`) and nothing of it reaches the Workspace DO. computer's `ignore` (`TOOLCHAIN_IGNORE` in `apps/sandbox-image/src/toolchains.ts`) lists `**/node_modules`, `**/.venv`, `/target` and `/*/target`, pnpm's store (`**/.pnpm-store`: where an install made before the pnpm configuration below, or by an older pnpm, left it, at the mount's root because the home directory is on another filesystem), caches (`**/.cache`, `**/__pycache__`, …), and build tools' caches and environments by names no source directory has (`**/.turbo`, `**/.next`, `**/.nuxt`, `**/.svelte-kit`, `**/.parcel-cache`, `**/.terraform`, `**/.gradle`, `**/.tox`, `**/.nox`, `**/.direnv`, `**/.wrangler`, `**/.astro`, `**/.angular`, `**/.expo`, `**/.nx`, `**/.docusaurus`, `**/.nyc_output`, `**/.hypothesis`, `**/.dart_tool`, `**/.zig-cache`, `**/.stack-work`): they stay container-local and out of DO SQLite. Names some repos commit (`dist`, `build`, `coverage`, `vendor`, `.yarn`, `_build`, `.output`, `deps`) stay synced, since a tracked file on an ignored path shows as deleted in the Worker Shell's git; so does `.alchemy` (it can hold real deploy state). Ignoring a path only keeps it out of the Workspace DO: computerd still serves every file operation on it through FUSE, which is what made `pnpm install` 3–6× slower than on plain disk (see [_Known risks_](risks-and-spikes.md)), so a path that should be fast has to be off `/workspace` as well, which is what the next bullet does for pnpm and Turborepo. An Environment adds its own paths after these (its `ignore` setting, at most 50, each checked against computer's pattern rules when saved, since computer refuses a bad one when it builds the Container's backend): the last pattern that matches a path wins, so a `!` pattern keeps a built-in one synced. Ignoring a path the Workspace already holds does not remove its files from the Workspace DO; they stay until deleted. Under `alchemy dev` no list is applied (see [`docs/development/infra.md`](../development/infra.md) → _Docker for the Container image_). The first plan put the Toolchains under `/workspace/.mise` on that list; see [_Known risks_](risks-and-spikes.md) for why they are not.
- **pnpm and Turborepo off the mount** (#151): pnpm's files are on the Container's disk, outside `/workspace`, so `/workspace/<repo>/node_modules` is mostly symlinks (784 in the root's of this repo, with 61 other files) and the install does not go through FUSE. The bootstrap writes pnpm's global configuration, `config.yaml` in `$XDG_CONFIG_HOME/pnpm` or `~/.config/pnpm` (pnpm 11 and later read it, and 11.0–11.22 ignore two of its keys: see below; `PNPM_GLOBAL_CONFIG` in `apps/sandbox-image/src/toolchains.ts`), each key only when the file does not already have it (so a Container's own `pnpm config set --global` stays): `storeDir: "$HOME/.pnpm-store"` (`/root/.pnpm-store`, the content-addressed store in `v11/files`), `virtualStoreType: global` together with `enableGlobalVirtualStore: true` (pnpm's global virtual store under its two names: `virtualStoreType` is read from 11.23, `enableGlobalVirtualStore` from 11.0 and still later, and pnpm 11.0–11.22 would else put the store on the Container's disk and the virtual store on the mount, which copies packages instead of hard-linking them; pnpm 11.20 ignores `virtualStoreType` and `confirmModulesPurge` in the global file with a warning at each install, and 11.28 and 12.15 take both keys without one, and a repo's `virtualStoreType: project` or `enableGlobalVirtualStore: false` wins on them; the store's packages are linked once into `<storeDir>/v11/links`, on the same filesystem as the store, so pnpm still hard-links, and each project's `node_modules` holds symlinks into it plus a small `node_modules/.pnpm` of its lockfile and hoisted links) and `confirmModulesPurge: false` (pnpm's install no longer asks before it purges `node_modules`, which would hang a command: an install made the old way moves to the new layout at the next `pnpm install`). `virtualStoreDir` is not set: set globally it would also be where a repo that chooses the project layout keeps its virtual store, shared with every other repo (the global setting applies to `virtualStoreType: project` too), and unset the global virtual store is under the store. `CI` is not set for commands, since it changes other tools' behaviour. These are in the global file and not in environment variables because pnpm lets `pnpm_config_*` variables override a repo's `pnpm-workspace.yaml` and the global file loses to it: a repo that sets its own `storeDir`, `virtualStoreDir` or `virtualStoreType: project` (or `enableGlobalVirtualStore: false`) keeps it (checked with pnpm 12.15), and gets the old speed. A repo's pnpm older than 11 does not read the file and works as before, with its store at the mount's root. `**/.pnpm-store` and the `node_modules/.pnpm` of the project layout are what the token scan skips (see _Snapshots_). Node resolution under a global virtual store (checked on a deployed Container): a package's declared and peer dependencies resolve from its real path in the virtual store, so vitest, vite and `tsc` find theirs; a dependency a package does not declare resolves through the `NODE_PATH` that pnpm sets for what it starts (`pnpm run`, `pnpm exec`, a `node_modules/.bin` shim), for CommonJS and, since pnpm 11.23, for ESM through an `--import` hook in `NODE_OPTIONS`; a `node` started by hand, without pnpm's environment, finds the dependencies of the project's own `package.json` and what each package declares, and not an undeclared one (`Cannot find module`). TypeScript does not use `NODE_PATH`: a library whose `.d.ts` imports `react` without declaring `@types/react` found it only in the project layout's hoisted directory, so `apps/web`'s `tsc` failed under the global virtual store (`event` implicitly `any`, `use(RegistryContext)` of type `unknown`; `atom-react`, assistant-ui, `lucide-react`, `streamdown` and `react-textarea-autosize` are such libraries) until its `tsconfig.json` mapped `react` and `react-dom` to its own `@types` with `paths`; a repo with the same problem declares the missing dependency with `packageExtensions` or does the same. A repo that chooses the project layout itself (`virtualStoreType: project`, or `enableGlobalVirtualStore: false`) keeps it, but with the store on the Container's disk and `node_modules/.pnpm` on the mount, pnpm copies the packages instead of hard-linking them ("Packages are copied from the content-addressable store"): that repo should set its own `storeDir` too. Turborepo's cache is `TURBO_CACHE_DIR=/root/.cache/turbo` in every command's environment (`toolchainEnv`), instead of `.turbo/cache` in the repo; `**/.turbo` stays ignored for the rest of what Turborepo writes there. The variable beats a repo's `turbo.json` `cacheDir` (checked with turbo 2.11: only `--cache-dir` beats the variable), and turbo has no global configuration file to put the default in, so a repo that sets `cacheDir` gets the variable's directory anyway.
- **Bootstrap:** before the first command of each Container start, `ToolchainBackend` (`apps/server/src/workspace/toolchains.ts`, a wrapper around computer's `ContainerBackend`) runs `apps/sandbox-image`'s `bootstrapScript` through the Container's shell. It writes the Environment's Toolchains as the root's `mise.toml`, or the base `mise.toml` when it has none (with the image's lockfile for it, or the recorded lockfile of that same copy: see _Persistence_), where the root's `mise.toml` is still the copy it wrote last, or the root has no mise config of any kind mise reads (`mise.toml`, `.mise.toml`, `mise.local.toml`, `.config/mise.toml`, `.config/mise/config.toml`, `.mise/config.toml`, `.tool-versions`); locks the root's `mise.toml` (`mise lock --global`, when the lockfile is missing or older than the config); runs `mise install` (from `mise.lock`; a no-op for what is present) in `/workspace` and in each repo directory with a mise config; sets git's identity and credentials; writes pnpm's global `config.yaml` (see _pnpm and Turborepo off the mount_); and, when that succeeded, runs the Setup Scripts that are due (see _Setup Scripts_), then the Start Scripts (see _Start Scripts_). It reads the Workspace's Container settings once, as it begins: their variables are the environment of the bootstrap, its scripts and every command of that Container start (see _Command environment_), their Setup and Start Scripts are the Environment's, and their Toolchains are the `mise.toml` it writes. Before all of that it makes the directories the Workspace holds read-only (`/workspace/.agents/skills`, the Skill set the Workspace holds, empty by default) read-only on the Container too, with a bind mount remounted `ro`, when the Container can mount; that never fails the bootstrap. Commands that arrive meanwhile wait for it; computer has pushed the Workspace's files to the Container by then. A command killed or timed out while it waits is not run afterwards. A failed bootstrap is logged (never with the token) and does not stop commands: the command that waited for it starts with a note on stderr (the failure's output, redacted), later ones with a pointer to it, and the next attempt comes after a minute, doubling with each failure in a row up to 15 minutes. A new connection to the same Container does not repeat the bootstrap. A cold start takes about 10 seconds on Cloudflare plus the install, which is nothing for the base `mise.toml` (the image has its Toolchains) and about 10 seconds for Node 22 and Python 3.13 when a Workspace asks for those instead; a restart reinstalls from the lockfile. With a snapshot to restore (see _Snapshots_) the Container starts with its Toolchains in place, and the bootstrap finds nothing to install.
- **Setup Scripts:** a repo can prepare itself on the Container (typically installing its dependencies) with a Setup Script, its `.cloudpid/setup.sh` (`SETUP_SCRIPT`; under `.cloudpid/`, not the `.agents/` other agents read, since only cloudpid runs it: [ADR-0020](../adr/0020-repo-scripts-live-in-cloudpid.md)), and an Environment can have one of its own (its `setupScript` Container setting, bash, at most 64 KiB of UTF-8), for what its Workspaces need whatever the repo (system packages, a Docker image). Once the Toolchains are installed (not after a failed install, whose retry does it), the bootstrap lists the scripts that are due (`pendingSetupScripts` in `apps/sandbox-image/src/toolchains.ts`): first the Environment's, which that same exec writes to `/var/lib/cloudpid/environment/setup.sh` (base64 in the command, so no quoting or heredoc can meet its text; an empty setting removes the file), then the repos' (directories directly below `/workspace`). A script is due when its SHA-256 differs from the last one that succeeded on this Container's disk, recorded in `/var/lib/cloudpid/setup/<repo>` (the Environment's under `@environment`, a name no Repo can have), outside `/workspace`, so nothing syncs it and a snapshot carries it. It runs each one after the other as an exec of its own (`setupScriptRun`), the Environment's first: with bash, in the repo's directory (the Environment's in `/workspace`), with no input and a command's environment (Toolchains on `PATH`, the GitHub token, the Environment's variables) plus the Environment's Secrets marked for the Build, each as `$PI_SECRET_<NAME>` (from the Workspace DO's copy: see [_Secrets_](agent-capabilities.md#secrets); no other script or command gets them that way), stopped with every process it started after 15 minutes (`timeout`, which signals its process group; computer's exec limit is a minute longer). A script that succeeds records its hash, so it runs again only when its content changes, or on a Container started from the image (a Container restored from a snapshot has the record and what the script installed, its dependency directories being Container-only paths on the disk). Commands wait for them as for the install, and the Container counts as in use meanwhile (the idle stop), whether or not a command still waits. A failed or stopped script does not stop commands and is not retried in that Container: it is logged, the first command that starts after it (the one that waited, unless it was killed meanwhile) gets a note on stderr carrying the end of its output (redacted), and later commands in that Container a one-line pointer to it; it is due again at the next Container start. A script that exits with `timeout`'s status (124) on its own is reported as that exit status: only the run's own last line (`SETUP_TIMED_OUT_MESSAGE`) marks a script stopped for its time. The install snapshot is taken after the scripts, so it keeps what they installed, and their time is not the snapshot's; a script that succeeded counts as an install for it, and one that failed does not (see _Snapshots_). This repo's own script (`.cloudpid/setup.sh`) runs `CI=1 SKIP_REFERENCE_REPOS=1 pnpm install --frozen-lockfile`: `CI` so pnpm asks nothing, and `SKIP_REFERENCE_REPOS` so `prepare` does not clone effect and pi into `.repos/` (about 5,150 files, 355 MB, not ignored, so they would sync into the Workspace DO). A clone that a Workspace's readying makes after the bootstrap gets its script run right after it is made (see [_Workspaces_](workspace.md)).
- **Start Scripts:** what a snapshot cannot hold (running services: a database, `docker compose up`) is started at each Container start by Start Scripts: the Environment's (its `startScript` Container setting, at most 64 KiB) and each repo's `.cloudpid/start.sh` (`START_SCRIPT`). After the Setup Scripts and after the install snapshot (so no service is writing to the disk while it is taken, and none is in it), the bootstrap runs the Environment's in `/workspace` (`environmentStartScriptRun`, which writes it to `/var/lib/cloudpid/environment/start.sh` as the Setup Script is written), then lists the repos that have one (`startScriptDirectories`) and runs each in its repo's directory (`startScriptRun`): each an exec of its own, with bash, no input and a command's environment, stopped with every process it started after 5 minutes (`START_TIMEOUT_SECONDS`; computer's exec limit is a minute longer). Nothing records them: they run at every Container start, a restored one included, and not after a mere reconnect; a new bootstrap on a Container that already runs (after the Workspace DO was evicted) runs them again, so a Start Script should leave a service that is already up alone. An exec ends when the script has and nothing holds its output, so a service a Start Script starts must detach: `setsid nohup cmd >/tmp/cmd.log 2>&1 &` (outside the script's process group, which `timeout` signals, and off its output). Commands wait for them, as part of the bootstrap. One that fails or is stopped is reported as a Setup Script is (logged; a note with the end of its output for the first command that starts after it, a pointer for later ones; a stopped one's note says to detach), stops no command and does not count as an install. A clone that a Workspace's readying makes while the Container runs gets its Start Script run once, after its Setup Script (see [_Workspaces_](workspace.md)).
- **Global default:** the root's `mise.toml` is also mise's global config (`MISE_GLOBAL_CONFIG_FILE`), so the base Toolchains (git and gh among them) resolve from any directory, not only under `/workspace` (a scratch clone in `/tmp`, the git calls pip and npm make from their own temp directories). The Workspace's own `mise.lock` stays the lockfile; mise locks a global config only through `mise lock --global`, which the bootstrap runs. A root whose config lives elsewhere (`.config/mise.toml`) is installed but is not the global default.
- **Command environment:** computerd starts a command with `PATH` (the image's, with mise's shims first) and `HOME` only, not the image's other variables, so the Workspace DO adds the rest to each command's exec environment (`toolchainEnv`): `MISE_GLOBAL_CONFIG_FILE`, `MISE_TRUSTED_CONFIG_PATHS=/workspace`, `MISE_YES=1`, `GIT_TERMINAL_PROMPT=0`, `TURBO_CACHE_DIR=/root/.cache/turbo` (see _pnpm and Turborepo off the mount_), `BASH_ENV` (the memory guard's note: see _Memory guard_) and the GitHub tokens minted for the command (`githubTokenEnv`; see [_Git_](workspace.md#git)), under what the caller passes. The Environment's variables (its `variables` Container setting: names a shell can export, values of at most 4096 characters) are under those, and under them the variables kept Global (see _Container settings_): an Environment's own of the same name wins, and the 50 variables an Environment may have count both maps, an overridden name once. Neither can replace them: the names `toolchainEnv` sets, `PATH`, `HOME`, `PWD`, `SHELL`, `USER` and any `CLOUDPID_` one are refused when saved (`variableNameProblem`). The Workspace DO reads them once per Container start, at its bootstrap, and gives them to the bootstrap, its scripts and every command of that Container start, so a change applies at the next start. They are plain: the agent can read them, and they are not taken out of output (a value to keep from the agent is a Secret kept for the Environment: see [_Secrets_](agent-capabilities.md#secrets)). The token, and each Secret kept for the Environment as its Secret Reference, are taken out of what a command prints (`redact.ts`, also when split across output chunks), which stops accidents (`env`, `set -x`) from reaching the Session's history, not a command that encodes one.
- **Under `alchemy dev`:** the local Container has no `/dev/fuse`, and computerd's userspace shim refuses an ignore list (it exits), so the stack sets `CONTAINER_FUSE=false` and the Workspace DO asks for none: `node_modules` and the rest then sync into the local DO like any file. The bootstrap is the same.
- **Container settings:** each Environment has nine Container settings, eight of which its Workspaces' Containers take, the Container's size (`lite`, `basic`, `cpu-1`, `standard-1`, `mem-4`, `standard-2`, `cpu-2`, `mem-8`, `standard-3`, `cpu-3`, `mem-12`, `standard-4`; default `cpu-1`: 1 vCPU, 3 GiB memory, 12 GB disk; the image, 1.3 GB on disk on Debian and larger on Ubuntu with Docker, is unchecked on `lite`'s 2 GB disk: see [_Known risks_](risks-and-spikes.md)), its size limit (`maxInstance`, one of the same names, default `cpu-2`: the largest the size may be and the largest the agent's `container_resize` may start a Container on, see _Resize by the agent_; a Limit, GLOSSARY.md, which the agent changes only with the owner's Approval, ADR-0019; sizes are ordered by memory, then vCPU, `compareInstances` in `packages/config/src/container-settings.ts`, so `cpu-1` is below `standard-1`, `standard-1` below `mem-4`, `standard-2` below `cpu-2`, `mem-8` below `standard-3` (the same memory on fewer vCPU), `cpu-3` between `standard-3` and `mem-12`, and `mem-12` below `standard-4`; a save of a size above the limit is refused with a message naming both, `instanceLimitProblem`, checked by the Registry's `updateEnvironmentSettings` and by the Limits section before it, and a read raises a saved limit below the saved size to the size, so an Environment saved larger than `cpu-2` before the limit existed keeps its size as its limit), its idle time in minutes (1 to 1440; default 2), extra Container-only paths (`ignore`, none by default; see _Persistence_), variables (none by default; see _Command environment_), its own Setup and Start Scripts (`setupScript`, `startScript`, none by default; see _Setup Scripts_ and _Start Scripts_), and its Toolchains (`toolchains`: the text of a `mise.toml`, at most 16 KiB of UTF-8 with no NUL, which mise reads and the save does not; empty by default, the image's base Toolchains; see _Persistence_ and _Bootstrap_); the ninth, whether it keeps a Spare Workspace (`spareWorkspace`, on by default: [#323](https://github.com/ian-pascoe/cloudpid/issues/323)), is the Registry's to read when it keeps the spares (see [_Spare Workspace_](workspace.md)), not a Container's: it applies at once, and makes no new Build (`buildKey` leaves it out). A Workspace DO's copy holds it with the rest and uses it for nothing. **At Global, with an Environment's Overrides** ([ADR-0027](../adr/0027-settings-at-two-scopes-with-explicit-overrides.md), which extends [ADR-0023](../adr/0023-variables-for-every-environment.md)): every Container setting is kept at Global too, and an Environment's value of a field is its **Override** (GLOSSARY.md) of Global's. Global's are one JSON document in the Registry's `documents` table (`every-environment`, the name it had when it held only the variables kept Global, so the document saved then reads as it is), holding only what differs from the defaults (`containerOverridesFrom`; strict writes, lenient reads: a field that no longer resolves falls back to its default and is reported); an Environment's are its row's `environments.settings`, holding exactly the fields set on purpose, even one equal to Global's (`ContainerOverrides`, every field optional and without a default; read leniently field by field, `resolveContainerOverridesLeniently`, so one that no longer resolves is left out and inherits Global's). The settings in force are the Overrides over Global's (`resolveEnvironmentContainerSettings`: each field replaced whole, the variables merged name by name, `{ ...global, ...own }`, `withGlobalVariables`, then the limit raised to the size, `withLimitAtLeastSize`). Nothing moved in the deploy that brought this: the fields Environments had saved became their Overrides and Global started at the defaults (or the variables kept Global), so every Environment resolved as before, its Workspaces were handed the same settings and no Build key changed (`global-container.workerd.test.ts`). The RPCs: `getEnvironmentSettings` answers `{ settings, global, overrides, problem? }` (in force, Global's in force, the explicit Overrides) and `updateEnvironmentSettings` takes `{ environment, set?, reset? }`: `set` merges into the Overrides field by field (the variables name by name), `reset` takes fields out by their path (`idleMinutes`, `variables.<NAME>`: the variables one by one), which then inherit Global's (`patchContainerOverrides`; a form that edits whole settings sends the difference, `containerPatchBetween`). `getGlobalContainerSettings` answers `{ settings, overrides, overriddenIn, problem? }`, `overriddenIn` naming the Environments that override each field by its path (for the page's "Overridden in N environments"), and `updateGlobalContainerSettings` takes `{ set?, reset? }` the same way (a reset goes back to the default). On the Settings page, Global's Container and Setup sections and the size limit of its Limits save through `updateGlobalContainerSettings` (each changed field set, one put back to its default reset), an Environment's through `updateEnvironmentSettings` (its Overrides set or reset), and each field is marked Inherited or Overridden at an Environment (see [_Client and protocol_](client-and-protocol.md) → Settings page → Scopes and marks). Both saves run in one storage transaction. The size limit is checked where a save changes it: an Environment's save when it changes its own size or limit (a save that changes the size of an Environment saved larger than its limit before it had one keeps that raised limit as its own); Global's own when it changes Global's size or limit, and, for each Environment, when it changes the size or limit that Environment inherits (before the raise, so one saved larger than its limit before it had one runs as it did through any other change at Global, and a new limit at Global below its size is refused as for any Environment), refusing the save and naming each such Environment. The Workspace DO does not know Global: the Registry hands it the settings in force, as overrides of the defaults, in `getWorkspaceSetup`, `upkeepSpares` (both through `withSettings`) and `workspaceOverrides` (for the Session's own Workspace after an Agent change), so a Workspace gets them at its next readying and applies them at its next Container start; the spares' upkeep reads the Spare Workspace setting in force. `buildWork` hands the Environment's Overrides and Global's settings apart, and the Build upkeep and Test Builds resolve them (`buildSettingsOf`) before the Build key is computed and the request made. The 50 variables apply to the merged set, which the Workspace DO's schema would otherwise refuse as a whole: a save of an Environment's settings is refused when the merged set would pass 50, and so is a save at Global when any Environment's would (the message says how many it would have). Variables are plain at both Scopes: a value that is not secret (an email, a URL) belongs here, not in a Secret (see [_Secrets_](agent-capabilities.md#secrets)). `ContainerSettings` (`packages/config/src/container-settings.ts`) is a Schema with decoding defaults like the Settings (writes strict, reads lenient). The UI reads and writes them through `getEnvironmentSettings`/`updateEnvironmentSettings` (the Environment's Scope on the Settings page, see [_Client and protocol_](client-and-protocol.md) → Settings page: the Container section has the size, idle time, Container-only paths and the Spare Workspace checkbox, Setup the Toolchains and scripts, Limits the size limit; each shows the settings in force with the Environment's own variables only and saves only the fields the owner changed in it, so a field left alone keeps whether it is inherited; the Spare Workspace checkbox shows its trade-off: new Sessions that start without waiting, against the Container time each spare takes to prepare). The Workspace DO cannot bind the Registry (its Worker deploys before the main Worker that hosts it), so each Workspace DO keeps a copy in its own storage (`apps/server/src/workspace/settings.ts`), which a Session's readying replaces when the Environment's differ (`updateContainerSettings`, see [_Workspaces_](workspace.md)), and reads that copy when it launches its Container (the size, idle time and paths) and when the Container's bootstrap begins (the variables, scripts and Toolchains): a change reaches a Workspace when one of its Sessions next readies it, at most a minute later while it works. **They apply at the next Container launch**: `ContainerLaunch` (`launch.ts`) captures the size, idle time and Container-only paths when it launches and keeps them while that Container runs, because computer relaunches a running Container whose launch differs from the one asked for, so a saved change must not reach a reconnect to the running one. computer's `ContainerBackend` takes its `ignore` list when it is built, so the Workspace DO builds one per list (`PerLaunchContainerBackend`, `per-launch-backend.ts`), asking `ContainerLaunch` before each connection which list the Container it reaches has.
- **Size per launch:** under `schedulingPolicy: "durable_object"` the Workspace DO chooses the size in `ctx.container.start({ instance })` at each launch (the Container application on Cloudflare declares none; alchemy's `instanceType` is not valid for this policy), so one Container class serves every size and the deploy, prod included, is unchanged. `ContainerLaunch.wrap` decorates the Container API computer's `ContainerBackend` launches through, adding `instance` and `containerSnapshot` to its `start` and `restart`. A launch takes the size the agent's resize recorded (see _Resize by the agent_) instead of the settings' size, while it is within their size limit; the launch record keeps the size each Container launched with, whichever it was. The sizes are stored by name in the Workspace's settings (`INSTANCE_TYPES`): Cloudflare's named types (`lite` to `standard-4`) under their own names, and the custom sizes in two families, each named by what it is built around. **`cpu-<vCPU>`** has the most vCPU Cloudflare allows for its memory (3 GiB per vCPU): `cpu-1`, 1 vCPU, 3 GiB (3072 MiB) memory and 12 GB disk (`{ vcpu: 1, memoryMib: 3072, diskMb: 12000 }`), `cpu-2`, 2 vCPU, 6 GiB (6144 MiB) memory and 12 GB disk (`{ vcpu: 2, memoryMib: 6144, diskMb: 12000 }`), and `cpu-3`, 3 vCPU, 9 GiB (9216 MiB) memory and 12 GB disk (`{ vcpu: 3, memoryMib: 9216, diskMb: 12000 }`, about $0.084 a running hour with its disk, $0.216 a fully busy CPU hour); no `cpu-4`, which would be `standard-4` with less disk. **`mem-<GiB>`** has more memory for few vCPU, for work that needs memory more than cores (a single-threaded `tsc`, tools that start a worker per core, which the memory guard would otherwise stop): `mem-4`, 1 vCPU and 4 GiB (`{ vcpu: 1, memoryMib: 4096, diskMb: 12000 }`, about $0.039 a running hour), `mem-8`, 1 vCPU and 8 GiB (`{ vcpu: 1, memoryMib: 8192, diskMb: 12000 }`, about $0.075), and `mem-12`, 2 vCPU and 12 GiB (`{ vcpu: 2, memoryMib: 12288, diskMb: 12000 }`, about $0.111, `standard-4`'s memory with at most half its CPU cost); no 6 GiB one, which on 1 vCPU would be `standard-2`. Fewer vCPU do not make a size cheaper to run, since CPU is billed only while busy: they cap what a busy Container costs and how many workers a tool sized by its cores starts. `cpu-3`, `mem-8` and `mem-12` are above the default size limit, so an owner raises the limit to them or larger before the size or the agent's resize can use them. The `cpu-<vCPU>` sizes were `custom-<vCPU>` until #249: the old names stay readable wherever one was stored (saved settings, a Workspace's copy, its launch record, resize and usage ledger, Agent changes and the values an Approval was asked against) and in what a Workspace DO still on the release before reports (its usage), each read as its new name (`RENAMED_INSTANCE_TYPES`, `currentInstanceName`); a save that names one is taken too and stored under the new name, so a revert of an older Agent change writes it back. Nothing is migrated and a Container launched on `custom-2` is adopted as `cpu-2`, whose resources are the same; a release before #249 cannot read the new names (its lenient read drops a saved `cpu-*` or `mem-*` size, and a launch record or resize naming one is not a size it knows), so a rollback past it needs a fix forward. A custom size needs 1 to 4 vCPU, at most 12 GiB memory and 20 GB disk, and at least 3 GiB memory per vCPU ([limits](https://developers.cloudflare.com/containers/platform-details/limits/)); every custom size keeps the same 12 GB disk, so a snapshot or Build taken on one restores on the others. `containerInstance` (`packages/config/src/container-settings.ts`) maps the custom sizes to those resources at each launch. A stored name never changes meaning (a future custom size gets a new name), and the launch record keeps the name, not the resources.
  - **Why these defaults:** Cloudflare bills a Container's CPU only for active use, and its memory and disk for as long as it runs ([pricing](https://developers.cloudflare.com/containers/pricing/)), so memory is most of what a running Container costs: on `cpu-2` (`custom-2` then, the default until #189) $0.054 of its $0.057 a running hour, with CPU at $0.144 a fully busy hour. `cpu-1` halves the memory (about $0.030 a running hour with its disk, $0.072 a fully busy CPU hour), keeping `standard-2`'s vCPU and disk; the disk costs little, and keeping it means a snapshot or Build taken on `cpu-2` (or `standard-2`) still fits on `cpu-1`. Every idle minute costs the Container's full memory, against about 2 s for a small restore (a Workspace with a large `pnpm` store has measured about 27 s, and its idle stop's snapshot 45–60 s): hence the 2-minute idle default, which an Environment whose Workspaces restore slowly can raise. A repo whose checks need more than about 2.5 GB at once (this repo's `turbo run typecheck lint test` reached 5.9 GB: see _Memory guard_) should set its Environment to `cpu-2` or larger (`mem-8` where it is memory, not cores, that it needs), or run its tools with less concurrency.
  - **Changing a default:** a field neither Global nor the Environment saved follows the default at its next launch; one either saved keeps it. At Global, saving a value equal to the default stores nothing, and one equal to a former default, such as `standard-2`, `cpu-2` or 5 minutes, is stored. An Environment stores each field it is given, one equal to the default or to Global's too, and a field it leaves unset follows Global's (an Environment that left the size or idle time at the default before #189 follows the new one). A Container that runs is never relaunched for it: `ContainerLaunch` keeps the launch it recorded (a running Container found with no record, at `start` or `restart`, is taken to be on `standard-2`, the default when launches were first recorded).
  - A snapshot is a disk image labelled with its image and Container-only paths, not a size, so one taken on `standard-2` restores on `cpu-2` and the reverse, and one taken on any custom size restores on the others (all have 12 GB of disk).
- **Snapshots:** `snapshotContainer()` captures the Container's root file system (not memory, processes or separate mounts) and `start({ containerSnapshot })` restores it, on the `durable_object` policy only, under a 30-day lifetime that each restore refreshes. `ContainerSnapshots` (`snapshots.ts`) takes one **after the first successful bootstrap of a Container that started from the image, when that bootstrap installed something** (inline, after its Setup Scripts and before the commands that waited for the bootstrap are sent, so nothing else writes) and **on idle stop** (before the Container is destroyed, unless nothing that may change its disk ran since its restore: see _Idle stop_; a spare Workspace's Container is stopped this way once the spare is prepared: see [_Spare Workspace_](workspace.md)), keeps only the latest handle in the Workspace DO's storage, and the next launch restores it. A bootstrap installed something when its install ended its stdout with `BOOTSTRAP_CHANGED` (`apps/sandbox-image/src/toolchains.ts`: each step of the script that changes the disk in a way worth a snapshot sets its `changed=1`, which `mise install` does when mise's installs directory differs from before it) or when a Setup Script succeeded (`ToolchainBackend`, which runs them as execs of their own). A Setup Script that failed does not count by itself: it runs again at the next Container start, from the image or from a snapshot, whose record does not have it; with mise's installs or another script's success the snapshot is still taken, and keeps what the failed one left. A bootstrap that installed nothing (the base `mise.toml` on the image, all preinstalled, and no Setup Script due) is not snapshotted, so its first command does not wait for one (logged at info); its Container is snapshotted at its idle stop. When the install snapshot is not taken (failed, or given up on), a later bootstrap in the same Container (after the Workspace DO was evicted) tries again though it installs nothing itself (`installPending` in the launch record). The handle is labelled with the image the Container runs, recorded per launch (the deployed image for a launch from the image, the snapshot's for a restore), not the image a launch would run now: Containers outlive a deploy, so one still on the old image is not snapshotted (and an adopted Container with no launch record gets none). A snapshot is not portable to another image, so a deploy that changes the image discards it. One close to the 30-day lifetime (counted from its creation or latest restore) is not restored, and neither is one taken with other Container-only paths than the launch has (computerd's store and the disk's copies of those paths are laid out for the old ones): the snapshot record keeps the list (built-in paths included), and a Workspace whose paths changed starts its next Container from the image. So does every Workspace after a deploy that changes `TOOLCHAIN_IGNORE`, and a Container still running from before such a deploy is relaunched by computer at its next connection, as for any change to its launch; a snapshot recorded before lists were (2026-10-22) is not restored either. A Container restored from a snapshot is not snapshotted again after its bootstrap: its idle stop does, when something may have changed its disk since (see _Idle stop_). A launch with no restorable snapshot of its own starts from the Environment's Build when there is a usable one, and is snapshotted after its bootstrap as a launch from the image is (see _Builds_, next). Snapshots are off under `alchemy dev` (`CONTAINER_FUSE=false`: no real mount).
- **Builds** ([ADR-0016](../adr/0016-environments-and-a-container-per-workspace.md), GLOSSARY.md → Build): each Environment has a Build, a Snapshot of a Container with its Toolchains installed and what its Setup Scripts download cached outside `/workspace`, which a new Workspace (a spare included) starts its first Container from. **Made** by the Environment's Build object, a Workspace DO named `build:<environment id>` (`BuildRunner`, `apps/server/src/workspace/build.ts`), on its alarm, since a Build outlasts the main Worker's `waitUntil` (as a spare's preparation does; the idle stop shares the alarm and holds the Container meanwhile): it hands itself the Environment's Container settings without the Setup and Start Scripts (`buildContainerSettings`; no service runs in a Build), starts its Container (whose bootstrap installs the Environment's Toolchains, or the base ones, and records the copy it wrote and its lockfile, so a Workspace started from the Build writes the same `mise.toml` with that lockfile and installs nothing), then runs, each a script of its own (`@cloudpid/sandbox-image/builds`) that must exit 0: a full clone of each Repo's default branch into `/var/tmp/cloudpid-build` (`BUILD_ROOT`, outside `/workspace`, so nothing syncs it; git's hooks off, `SKIP_REFERENCE_REPOS=1`, `mise install` where a clone declares Toolchains, with the scratch root in `MISE_TRUSTED_CONFIG_PATHS`), the Environment's Setup Script in that root, then each Repo's `.cloudpid/setup.sh` in its clone, each as the bootstrap runs one (15 minutes at most, a command's environment); it reads each clone's commit, stops every process the scripts left running (each script's environment carries `CLOUDPID_BUILD_RUN=<request id>`, which the clean-up finds in `/proc/*/environ`: `dockerd` then `containerd` get 30 s after `SIGTERM`, the rest 5 s, then `SIGKILL`), deletes the clones and the Setup Scripts' records, so a Workspace started from the Build runs its own scripts once (fast, with the downloads cached), snapshots the Container (`ContainerSnapshots.capture`, with the scan for the GitHub tokens and the Environment's Secrets, labelled `build`) and stops it. A step that fails ends the Build with its reason (the end of its output, redacted of the GitHub tokens and the Environment's Secrets), and the last good Build stays in use; a Build cut off by an eviction is begun again at the next alarm, three times at most. The Build object takes no snapshots of its own. **Kept current** by the main Worker after an answer, as the spares are (`buildUpkeep`, `apps/server/src/registry/builds.ts`): after `createEnvironment`, `addRepo`, `removeRepo`, `updateEnvironmentSettings`, a change to the Environment's Secrets (to each Environment's, for one kept Global), a change of the Container settings at Global (`updateGlobalContainerSettings`, an Agent change at `*` or its revert: each Environment's, and the spares too when the Spare Workspace setting changed; one that overrides the field keeps its key, so it is asked for nothing), a Session created in a new Workspace, and behind `listSessions` and `listBuilds` (each Environment; once a run finds nothing to do or under way, that isolate asks nothing for an hour). One Registry call (`buildWork`) gives each Environment's Repos and Overrides, and the Container settings at Global (`global`), which the Builds resolve the Overrides over (`buildSettingsOf`); each Build object answers what it holds and the image a launch runs now (`buildState`), and is asked for a Build (`startBuild`) when the key of the one wanted (`buildKey`, `apps/server/src/workspace/build-record.ts`: a SHA-256 of the Repos' names and addresses, the variables (the merged ones: the Environment's own over those kept Global, so an Environment that inherits none has the key it had before them; every field of the key is the one in force, its Override or Global's), the Setup Script, the Toolchains (only when there are some, so the keys of Builds without stay what they were), the Container-only paths and the image, and, where the Environment has Secrets marked for the Build, an HMAC-SHA256 of their names and values under a key the Registry derives from `SECRETS_ENCRYPTION_KEY` (`buildSecretsDigest`, carried by `buildWork`), so a value is never in a key in the clear; not the size, idle time or Start Script) is neither the last good one's nor under way: so a deploy that changes the image makes each Environment's Build again. A failed Build of the wanted key is tried again a day after its attempt. Once a day the Build object is asked for a look instead (`check`): the Build object asks for each Repo's default branch head itself (`remoteHeads`, `apps/server/src/workspace/remote-heads.ts`), **without starting its Container**: a GitHub repo through GitHub's REST API as the GitHub App (`GET /repos/<owner>/<repo>/commits/HEAD`, with the installation token for the repo's owner, else the app owner's, which reads any public repo; with no token where the app is not set up, which reads public repos only; an empty repo has no head), a repo on another host through git's smart HTTP (`info/refs`, without credentials, reading only the first lines of the advertisement). It builds (starting the Container then) only when a head differs from the Build's commits, or the Build is older than 20 days (`BUILD_REFRESH_MS`, well within a snapshot's 30); a look that finds nothing moved holds and starts no Container, and only notes that it looked (it sets an alarm ten minutes on, `CHECK_RESUME_MS`, so a look the object's eviction cut off is begun again). A remote that cannot be asked (GitHub's error, its rate limit, a repo the app cannot see) fails the look: the last good Build stays in use, the failure shows as the Build's state, and the next look is due a day after the attempt, as a failed Build is tried again. An Environment with no Repo, no Setup Script and no Toolchains has no Build. What the object answers (its last good Build, and the one under way or the last failure) is recorded in the Registry (`recordBuild`, Registry migration 13), which hands the last good Build with each Workspace's set-up (`getWorkspaceSetup`, `upkeepSpares`), and the readying gives it to the Workspace DO when it differs from the one it holds (`updateEnvironmentBuild`). Deleting an Environment destroys its Build object. **Used:** `ContainerLaunch` starts a Container from the Workspace's own snapshot when it has a restorable one, and otherwise from the Build it holds when that Build is of the image a launch runs now, has the launch's Container-only paths, is younger than a snapshot's lifetime and has not failed in this Workspace. The launch then sets `CLOUDPID_RESET_STORE=1` in the Container's environment, which has the image's supervisor delete computerd's store (`COMPUTERD_DB`, with its `-wal` and `-shm`) before computerd starts, since the Build's store holds another Workspace's sync positions; the variable is asked for again on a reconnect to that Container, so computer adopts it rather than relaunching. A Workspace started from a Build takes its own install snapshot after its bootstrap. A Build that the Container did not start from (refused, or the health probe failed and computer restarted it) is remembered as failed in that Workspace (the last ten), which starts from the image, and the Workspace's own snapshot is never forgotten for it. A Workspace that has a snapshot of its own never uses a Build, so a Workspace made before a Build reaches it only after [_Restart container_](workspace.md). **Secrets:** the main Worker asks the Registry for the Environment's Secrets (`environmentSecrets`) only when it asks for a Build, and hands them with the request (`startBuild`), apart from the request the Build object stores; the object keeps them sealed as any Workspace DO does (see [_Secrets_](agent-capabilities.md#secrets)). The Environment's Setup Script and each Repo's get those marked for the Build, each as `$PI_SECRET_<NAME>` (the variable a Session's commands get it as), in their environment only (`buildSecretEnvironment`): not the clone, the clean-up or any other step, not the settings the object hands itself (`buildContainerSettings`, stored in the clear), and never in a script's text. Every Workspace made from the Build shares its Snapshot, so the others never reach it. Since the clean-up deletes the Setup Scripts' records, a Workspace made from the Build runs its Setup Scripts again: they get the same marked Secrets there, from the Workspace DO's copy (see _Setup Scripts_). The scan before its snapshot searches for every one of the Environment's Secrets, marked or not, and a Build object that cannot open its copy fails the Build with that reason. **Shown** in the Container section of the Environment's Scope on the Settings page (`listBuilds`: none, building since, built at, or failed with its reason, and what new Workspaces start from meanwhile), with _Rebuild_ (`rebuildEnvironment`), which asks for a Build now even when the last good one is current. **Test Builds** (GLOSSARY.md → Test Build; the agent's `environment_rebuild` with `proposed`: see [_Agent changes_](agent-changes.md)): a Build of proposed, unsaved changes, made by the Environment's Test Build object, a Workspace DO of its own named `test-build:<environment id>` (`testBuildObjectName`), so it never waits for a Build of the saved settings, holds one up, or replaces one under way. The Session asks for one through the Builds (`Builds.test`, `apps/server/src/registry/builds.ts`): it reads the Environment's saved Repos and settings (`buildWork`, read leniently), puts the proposed fields in their place as Overrides of its own (each whole: the Repos' list, the variables' map, the Setup Script, the Toolchains, the Container-only paths; never the size, idle time or Start Script, which a Build does not use), checks them as the owner's save does (`writeEnvironmentSettings`, with the variables kept Global counted in the 50, and the Repos as `addRepo` parses one), resolves them over the Container settings at Global (Global's variables under the proposed map), refuses them when nothing is left to build, computes their key as a Build's (`buildKey`, never compared with the Environment's or written over it), and hands the request to the object with the Environment's Secrets (`startBuild` with `test`, the id of the asking call: `<session>/<task>`). The object makes it as a Build is (`BuildRunner`: the same steps, timeouts, Secrets marked for the Build, redacted failure reason, and three attempts across evictions and steps the platform cut off), but takes no snapshot (nor the snapshot's scan), since its result is never kept, and answers its outcome (`BuildState.test`: building, succeeded once every step passed, failed with its reason, or cancelled) instead of keeping it as the last good Build: nothing is recorded in the Registry, and no Workspace or spare is handed it. One runs per Environment at a time: a request with another id while one runs is refused, saying so, and a request with the same id (the asking call run again after an eviction) finds the one under way or its outcome. `cancelBuild(id)` stops it: one that waits for the alarm never begins, and one that runs has its Container stopped and runs no step after. Deleting an Environment destroys its Test Build object with its Build object. Builds are off under `alchemy dev`: a request fails at once, saying so. Not verified on a deployed stage: a Test Build end to end on a real Container (its steps, the cancel's stop of a running script), a Container restored from another Durable Object's snapshot, the store reset reaching the supervisor through the launch's environment (computer's `ContainerBackend` passes `env` through `ContainerLaunchSpec`), the clean-up stopping a Docker daemon a Setup Script started before the snapshot, how large a Build's snapshot gets and how long it takes, and how much of a new Workspace's first start it saves.
  - **What is in it:** the Container's disk only. `/workspace` is a FUSE mount the snapshot does not hold, but computerd's store behind it is on the disk (`COMPUTERD_DB=/var/lib/computerd/state.db` in the image), with the synced files' contents and its sync positions, so the Workspace's files are in the snapshot through it and a restored Container is sent only what changed since the snapshot. computer resends every file when the store is behind the Workspace DO's push position (`reconcileWatermarks`), as for a Container that died after its install snapshot; with computerd's default in-memory store every launch was that resend, which for a Workspace of ~96k files held the Workspace DO for minutes (prod, 2026-10-22). computer's `ignore` paths are held by computerd on the Container's disk (`/tmp/workspace/...`), so `node_modules`, `.venv` and caches are in the snapshot and come back with it, while the Worker Shell and the Workspace DO still never see them.
  - **No secrets:** the bootstrap writes no token (git's credential helper reads `$CLOUDPID_GITHUB_TOKENS` and `$GITHUB_TOKEN` from the environment, and `~/.gitconfig` holds only that helper and `useHttpPath`), and a command that does write one (`~/.netrc`, a copied `.env`) must not reach a snapshot: before each snapshot a process of the Container's own (`ctx.container.exec`, so no connection to computerd is needed in the idle alarm) searches (all of it, or only what changed since the Container started: see _Scan of what changed_) every top-level directory but `/proc`, `/sys`, `/dev`, `/run` and `/workspace` (the mount; the Workspace's files are searched in computerd's store) for each GitHub token the Workspace DO minted that has not expired (one that has is harmless) as it is and as base64 of it and of `x-access-token:<token>`, and for each Secret kept for the Environment as it is and as base64 of its UTF-8 (`scanPatterns`: of a value of several lines, its longest line, a key's body rather than a header any file holds; of a long one, 256 characters from its middle; a value under 8 characters is not searched for, as it would be found by chance). The patterns go in its environment, one group per kind of match (the GitHub tokens together, each kept Secret on its own) and each split over variables of 64 KiB at most, never its command line; the labels of the groups stay in the Workspace DO. It skips directories named `.pnpm-store` or `.pnpm` (pnpm's store, `/root/.pnpm-store`, with the global virtual store in it, `v11/links`, and the project virtual store in `node_modules`), which hold only the packages pnpm installed and are most of the disk after an install (see [_Known risks_](risks-and-spikes.md)); the rest of `node_modules`, such as `.cache`, is searched, and a token a command or an install script writes into those two is not found. A hit skips the snapshot (the earlier one stays), a token in a file of the Workspace included, since computerd's store holds it. The warning names, per file, what each holds, "a GitHub token" or "the Secret `NAME`" (`leakReason`: _a GitHub token in /root/.gitconfig; the Secret `API_KEY` and a GitHub token in /root/state.db_), never a value, an excerpt or a base64 form, and for the first five files, then a count: so a refused snapshot traces to a token written into a git remote URL or an `insteadOf` rule, or to a kept Secret whose value is also in git's settings or the Workspace's files. After a hit, one more `grep` per group over the first 20 files found tells which group holds which (a few files, so the run time is that of the search); a file beyond those is listed without its cause, and a pattern that two Secrets share (a long value's middle) names both; a scan that cannot run or finish in 30 s skips it too. A value written in another encoding is not found. The Workspace DO searches for the copy of the Environment's Secrets it holds (see [_Secrets_](agent-capabilities.md#secrets)), and takes no snapshot while it cannot open that copy. `secret_ask` values are not searched for (the idle alarm has no access to a Session's held Secrets): one a command wrote to the Container's disk stays in a snapshot for up to 30 days (see [_Secrets_](agent-capabilities.md#secrets)).
  - **Scan of what changed** (#320): a Build's scan, and the first snapshot's of a Container started from the image or from a Build, search the whole disk as above. Every later snapshot's searches only the regular files whose status-change time (ctime) is after the Container's start marker (`/run/cloudpid-started`, `CONTAINER_START_MARKER` in `@cloudpid/sandbox-image/supervisor`, which the image's supervisor deletes and makes anew at each start, before computerd or the memory guard starts, then waits 20 ms so that nothing started after it writes in the same tick of the kernel's coarse file clock; `/run` is not searched), with the same exclusions and patterns: `find` lists them and `grep` reads them in batches. That holds while the files the Container has not changed since it started were shown clean of all it searches for now. Each snapshot records what its scan searched for (`ScanCoverage`: an HMAC-SHA-256 under the Workspaces' key, `KeptVault.digest`, of each kept Secret's patterns and of each GitHub token's forms, never a value, and when the snapshot was taken, after its scan); the launch record carries the restored snapshot's (`LaunchRecord.scanned`), then each later snapshot's of that Container (not of another Container launched while it was taken). The whole disk is searched again, at the next snapshot, when: a kept Secret was added or its value changed since (it may have been on the disk already, under no name; one removed does not count), and so once after each such change; a GitHub token that has not expired was minted before that snapshot was taken and its scan did not search for it (one minted more than a minute after cannot be in its files, the minute allowing for the Workspace DO's clock differing from one host to the next; one minted while the scan or the snapshot ran, or kept before tokens recorded their minting, counts as before); there is no coverage (a snapshot taken before #320, a Container computer restarted from the image, a Worker without `SECRETS_ENCRYPTION_KEY`); or the Container has no marker, its marker's modification time differs from its ctime (its times were set since it was made), or its ctime is ahead of the clock. The note of a snapshot taken says which it did (_the scan searched the files changed since the Container started_, or _the whole disk_). ctime, not the modification time: every write, `chmod`, rename or link changes it and only the clock sets it, so a file a command writes after the start is found wherever it is (`/root`, `/tmp`, `/var/lib/docker`, the Workspace's files through computerd's store, `COMPUTERD_DB`, whose ctime each write to it changes), even when `cp -p`, `tar`, `git` or `touch -d` gave it an old modification time. Files restored from a snapshot have ctimes from before the marker, whether the restore keeps the snapshot's or sets its own before the Container starts, and a restored file whose ctime is ahead of the marker (the snapshot's Container had a clock ahead of this one) is only searched again; not verified on a deployed stage: how a restore sets ctimes (were it to set them after the start, every restored file would be searched again, which is safe and saves nothing). **What it no longer covers:** a file a restored snapshot holds is not searched again for what that snapshot's scan searched for, so a file written between a snapshot's scan and the snapshot itself (a process left running at idle; not found by that scan before #320 either) is no longer found by a later Container's scan, which before refused the next snapshot (the earlier one, which holds it, stayed). A clock set back after the start by less than the time since makes a file changed meanwhile look older than the marker, and is not detected. A command that rewrites the marker (`touch` it) after writing a file hides that file: as for a value written in another encoding, the scan is not a guard against a command that means to hide one. Not yet measured on a deployed stage (see [_Known risks_](risks-and-spikes.md)).
  - **Time:** a snapshot, its scan included, is given up on after 120 s (`SNAPSHOT_TIMEOUT_MS`), after the install and on idle stop alike. The commands that waited for the bootstrap are held for the install's meanwhile (the Setup Scripts before it do not count), so a snapshot that takes long delays the first command by as long, up to 120 s; that is kept so that nothing else writes while it is taken (a command could write the token after the scan, or a file the snapshot half holds). It was 60 s for the install (#156), which lost snapshots that needed longer: `snapshotContainer` runs on after the limit, with its handle dropped. Past 120 s the snapshot is given up on and not recorded, the commands run, and `installPending` stays set, so the idle stop's snapshot or the next bootstrap's tries again.
  - **A restore that does not come up** falls back to the image. A start the platform rejects outright for the snapshot (an expired or unknown handle) is retried once from the image, and the snapshot is forgotten. A Container that fails its health probe (computer's budget is 60 s in all, 30 s for each of the launch and its one restart) falls to computer's restart, which `ContainerLaunch` turns into a launch from the image; the snapshot is forgotten when the Container died, and kept when it was merely slow (the new Container's own snapshot replaces it once it is taken). A snapshot larger than the disk of a smaller size cannot be restored there, and takes the same way out.
  - **Measured** (see [_Known risks_](risks-and-spikes.md); on `standard-2`, the default size then): a cold Container with the base `mise.toml` (all preinstalled, so no install snapshot) answers its first command in about 2.5 s on a host with the image (17 s on one without), a restored one in under 2.5 s; with versions the image does not have (Node 22 and Python 3.13), about 28–30 s with the install snapshot against 2 s.
- **Idle stop:** computer never stops the Container it starts (its WebSocket, heartbeat timer and container monitor keep the Workspace DO alive, and the platform's inactivity timeout never fires), so the Workspace DO stops it: every connect, push and pull on the Container records a use, and a Durable Object alarm snapshots the Container's disk and destroys it once the Workspace's idle time has passed without one (`apps/server/src/workspace/idle.ts`). A command still running on the Container counts as use: the Workspace stub the DO hands out (`tracked.ts`) holds the command until its client disposes the exec handle, and the alarm waits again while any is held. A bootstrap also holds the Container itself while it runs (`ToolchainBackend`'s `activity`), Setup Scripts included, whether or not a command still waits for it: a Setup Script can run for 15 minutes, past the idle time, after the command that waited was killed. The idle stop counts holds, so the command's and the bootstrap's own nest and each ends its own. The idle time is the one the Container was launched with. The first use of a Container comes before its launch is recorded, so the alarm is armed with the default (2 minutes) and brought forward once the real time is known; a Workspace whose own idle time is longer finds at that first alarm that the Container is not yet due and waits again for the rest (`IdleStop.alarm`). A snapshot takes seconds and the alarm holds no input gate, so a command may arrive during it and connect to the Container: after the snapshot the alarm checks that the Container is still idle (no use and no running command since it decided), and keeps the Container if not, leaving the alarm the use re-armed to take over. An idle stop that stops a running Container forgets the size the agent's resize recorded (`ContainerResizes.stopIdle`, `apps/server/src/workspace/resize.ts`), so the launch after it is on the Environment's size again; an alarm that finds no Container running (one a resize or `container_restart` stopped since its last use) keeps it for the Container the next command starts. The alarm is the Workspace DO's only one, which a spare Workspace's preparation shares (see [_Spare Workspace_](workspace.md)). **Hold cap** (#325): a hold or a stream of uses could keep a Container forever (a command whose exec handle is never disposed; an open Container preview, whose socket holds it and whose dev server's pings are uses), so a Container is kept no longer than `CONTAINER_HOLD_CAP_MS` (an hour, or the idle time when that is longer; `idle.ts`) after the last owner or agent activity in its Workspace. Activity (`IdleStop.noteActivity`) is not a use: a command started on any backend (`tracked.ts`), the Workspace DO's own included (a Build's steps, a spare's preparation, the Container's git for the Changes, none of which runs unasked or on a timer), a file operation of a Session that writes (`fileOperation`: a model tool's write; a read is not, as a watcher polls), and a Session at work (`noteSessionActivity`, which the Session host sends when it admits a message and at each 60 s heartbeat while a Run or other task is live, to its Workspace and its Subagent Workspaces; `workspaceActivity` in `Session.ts`); a Container preview's requests and sockets, a bootstrap's hold and a Session's file reads are not. The cap counts from the last activity, never from the Container's start, so a long build or test run the agent waits on is never stopped: its Run's heartbeat is activity. A command left running after its Run ended (a dev server, a background build) is stopped an hour after the last activity, as is a page the owner browses in a Container preview while no Session works. The last activity is kept in storage (`cloudpid:container-last-activity`, written at most once a minute), and with none known the cap counts from the alarm that first finds the Container kept. The alarm that finds a running Container kept past the cap (by holds, or by uses within its idle time) does a **held stop**: it snapshots the disk as the idle stop does, and stops the Container unless activity came during the snapshot (then it keeps it, holds and all, and arms again); the stop ends every command running there, other Sessions' too, as `container_restart` does, and the next command starts a Container from the Snapshot. Its holds are dropped (each hold is its own, so the late end of a dropped one never releases a later command's), and a cap that passes with no Container running only drops them. A held stop is logged (`workspace.container.held-stop`, with the minutes since the last activity and the holds dropped) and kept, the latest 10, in `cloudpid:container-held-stops`. The Workspaces Worker cannot reach the Sessions, so each Session asks for the held stops after the last it showed (`containerHeldStops`) when a client connects and before it admits input, and writes each to its active branch as a display-only entry (`cloudpid.container-held-stop`, a `write` submission with a request ID per stop, so it is written once; `apps/server/src/session/held-stops.ts`) that the transcript shows as the notice "Container stopped: held for N minutes without owner or agent activity" and the model never sees. A Session's first check only marks where it starts; a client already open sees the notice at the owner's next message or reconnect, since no Session in the Workspace was at work when the Container stopped. A Subagent Workspace's held stops are logged and kept, but no Session shows them. `ContainerUsage.until` counts the cap too while no command runs (it is null while one does, as before). **No snapshot when nothing changed** (#324): an idle stop, a held stop included, of a Container restored from the Workspace's own snapshot in which nothing that may change its disk has run since takes no snapshot: it logs so (_Idle stop: nothing that may change the disk ran in the Container since its restore from snapshot `<id>`: no snapshot taken, that one stays current_) and stops the Container, and that snapshot stays the Workspace's, so a Container woken only to be read stops in seconds instead of after a snapshot's tens of seconds. What may change the disk is told to the idle stop (a hold that writes, `IdleStop.hold`'s default, as it begins, and `IdleStop.noteWrite`) and kept in the launch record (`diskUnchanged`, which `ContainerLaunch.noteWrite` clears), so an eviction keeps it: every command on the Container (the agent's `bash` and every other command a Session or the Workspace DO runs there: a spare's preparation, a Build's steps, carrying clones to a Fork's Workspace; a Terminal's input must reach the Container the same way, #139); a model tool's write of a Container-only file (ADR-0018: `ContainerAccess.run` with `writes`); and in the bootstrap, an install that changed something (`BOOTSTRAP_CHANGED`) or failed, and each Setup or Start Script it runs, whether or not it succeeds (`ToolchainBackend`), so a restored Container whose bootstrap installed something, and every Container of a Workspace with a Start Script, snapshots as before. Not counted: a Container preview's socket and requests (the dev server they reach was started by a command or a Start Script, which counted), the bootstrap's own hold, the agent's resize (it snapshots itself), the file tools' reads of Container-only paths, and the Container's git for the Changes, Comparisons, the Run diff and the work state, which writes only to the repos' synced files (`.git` included, which no built-in Container-only path matches), which a restored Container is sent anyway. A bootstrap cut off by an eviction while it installed tells of nothing, and the next bootstrap in that Container may find nothing left to install: its Container is then stopped without a snapshot, and the next start installs again. A Container started from the image, from a Build or by computer's restart, one whose launch record is older than this, and one launched by a command (whose write is told before the launch is recorded, so the launch asks whether a hold that writes is on, `IdleStop.writing`) always snapshot at their first idle stop, and so does one whose snapshot the Workspace no longer keeps. A Container kept after its idle snapshot (a use came during it) stays marked, since a process it left running may still write; the resize's snapshot is never skipped. Not yet measured on a deployed stage.
- **Exit reports:** the platform keeps a Container's own output (computerd's stdout and stderr) where no API reads it, and computer logs only `workspace.container.exited` with the exit status, so a Container that dies mid-command left nothing in the Workers logs to say why (prod saw two `exit code: 1` deaths on 2026-10-21/22, each after commands hung for minutes). The image's entrypoint is therefore a supervisor (`apps/sandbox-image/image/supervise`, bash): it runs computerd, passes its output through to the Container's log as before, keeps its last 200 lines (at most 32 KB) in memory, never on the disk a snapshot captures, replacing the payload of each `data:<mime>;base64,<payload>` run of 64 characters or more with `[base64 dropped]` in that kept copy (computerd's log lines carried file contents that way, hundreds of KB a line, which filled the 32 KB and pushed out the crash `uncaughtException: Error: log <id>: append after exit` and its stack; a line-buffered `sed -u -E` between `tee` and `tail` does it, so a line of any size is handled as it comes, one cut off by the end of its line included, and the Container's own log keeps the full output), and forwards SIGTERM and SIGINT to it. When computerd exits without having been signalled through the supervisor, the supervisor posts its status (128 + the signal for one a signal killed), how long it ran and those lines to `http://cloudpid.internal/container-exit` (bash's `/dev/tcp`, so it needs no HTTP client; five seconds at most) and then exits with computerd's status. The Workspace DO intercepts that host for each Container it launches, right after computer intercepts `computer.internal` and again after a restart (`withExitReports`, `exit-report.ts`); `ContainerExitReports` (`worker.ts`) logs the report as `workspace.container.output` with the Workspace DO's id (also the Container instance's id in the dashboard), with anything shaped like a GitHub token taken out (the Worker does not know the tokens its objects minted), then the Workspace DO's tokens and the Environment's kept Secrets: it asks the Workspace DO the report names (`redactExitReport`, through the Workspaces Worker's own `WORKSPACES` binding), which takes its tokens out and each Secret out of the lines as its Secret Reference with the copy it keeps sealed (see [_Secrets_](agent-capabilities.md#secrets)). When that copy does not open or the DO cannot be reached, the report is logged with its status and uptime only, and `withheld` says why its lines are not. Anything in the Container can post a report, so it is only ever logged. computer's own `computer.internal` proxy forwards only its `/api` and `/health`, which is why the report has a host of its own. A Container the platform kills outright (out of memory, a host lost) takes the supervisor with it and sends none; the exit status then still says how it ended. The memory guard's lines are among computerd's (next).
- **Memory guard:** the Container has no swap, and when its commands use up the memory (this repo's `turbo run typecheck lint test` at Turborepo's default concurrency: from 0.3 GB to 5.9 GB of `custom-2`'s (now `cpu-2`) 6 GiB in 100 s, 2026-10-23) the kernel evicts the pages of computerd's own program long before its OOM killer acts. computerd, which serves `/workspace` and runs every command, then stalls on the disk, and every command hangs, `echo` included, until the Container is restarted. The image's supervisor therefore runs a memory guard beside computerd (`apps/sandbox-image/image/cloudpid-memory-guard`): earlyoom (Ubuntu's 1.7), which stops the process with the highest OOM score (in effect the largest) with SIGTERM once the memory available is below the lower of 15% and 1 GiB, and with SIGKILL below the lower of 8% and 512 MiB (`MEMORY_GUARD_PERCENT` and `MEMORY_GUARD_KIB` in `apps/sandbox-image/src/memory-guard.ts`; on `cpu-2` about 950 MB and 510 MB, against about 400 MB where computerd's pages were being evicted; on `mem-4` about 640 MB and 340 MB; on the default `cpu-1` about 480 MB and 260 MB, not yet measured there, so a SIGKILL may come after computerd has started to stall). It never stops computerd, the supervisor or the guard (`--avoid`, by the 15 characters of a name the kernel keeps); a service a Start Script started, Docker's daemon included, is stopped like any process. Its lines go where computerd's do: the Container's log, and the lines of an exit report. **The note:** a command whose process was stopped would only show the process dying (status 143 or 137, or a tool's own error), so the guard reads earlyoom's announcement of each stop (`sending SIGTERM to process <pid> uid <uid> "<name>": badness <n>, VmRSS <n> MiB`, printed before the signal; earlyoom's own hook, `-N`, runs only once the process has exited, by when its command has often ended) and leaves a note for it in `/run/cloudpid-memory-guard` (`MEMORY_NOTES_DIRECTORY`): a file named by the time in microseconds, written beside its name and renamed into place. A process sent SIGTERM and then SIGKILL gets one note. Every command's environment carries `BASH_ENV` (`toolchainEnv`, so an Environment's variable may not have the name), which the command's `exec bash -c` reads before the command: `/usr/local/share/cloudpid/command.bash` (`image/command.bash`) sets an EXIT trap that prints on stderr, when the command ends, each note left since it started, and unsets `BASH_ENV`, so a bash the command starts prints none again. The command's text is unchanged, so its line numbers are its own. The value is `$([ -r <file> ] && echo <file>)`, which bash expands, so a Container still running an older image after a deploy reads nothing instead of printing at each command that the file is missing. The note names the process, its pid and its memory, says when, and suggests running less at once (Turborepo's `--concurrency`, Vitest's `--maxWorkers`) or restarting the Container at a larger size with `container_resize` (see _Resize by the agent_). Every command running when a process is stopped gets the note, not only the one the process belonged to. Not covered: a command that sets its own EXIT trap or `exec`s another program gets no note, one that ends within milliseconds of the stop may miss it, and bash skips `BASH_ENV` when its stdin is a socket and `SHLVL` is unset (it takes itself for a command rshd started), which computerd's `/dev/null` stdin never is. The supervisor removes the notes before it starts the guard and computerd, since a snapshot may keep `/run`. **Measured** (2026-10-23, `custom-2`, a Container with the guard and `command.bash` installed by hand): this repo's `turbo run typecheck lint test --force`, which had frozen the Container without the guard (and, another time, ended only because a test timed out under the load and Turborepo stopped the run), brought the memory available down to 692 MB; the guard stopped two `tsc` processes (1.16 GB and 0.93 GB), the run failed with `@cloudpid/server#typecheck` exiting 137 and both notes in its output, and the Container answered throughout. A Python process growing by 500 MB/s was stopped at 5.1 GB with 855 MB still available, and its command ended with the note.
- **Restart by the agent:** a Container can stop answering while the Workspace DO still does (computerd starved of memory the memory guard did not free in time, or wedged): every command then hangs until its timeout, `echo` included, and no command can fix it. `container_restart` (formerly `restart_container`, renamed with no alias under ADR-0019's `container_*` naming; a saved `tools.offered` entry that names the old name is read and saved as the new one, and is not reported as a problem: `withRenamedTools`, `packages/config/src/settings.ts`; the `container` extension, `packages/extensions/src/container.ts`; deferred, so the model finds it with `tool_search`, and the `bash` tool's description points to it) stops the Container of the calling conversation's Workspace (the Session's, or a subagent's Subagent Workspace: see [_Subagents_](agent-capabilities.md#subagents)) at once through its Workspace DO (`stopContainer`, which has the platform destroy the Container, so it works whatever computerd is doing, and runs no command), without a snapshot of its own. It takes a `reason` (1 to 500 characters), which the transcript shows as the call's summary, and asks no one: the agent restarts when it judges the Container hung. By default the Workspace keeps its Snapshot, so the next command starts a Container from it, as after an idle stop, with the Start Scripts run again, on the size the agent's resize recorded if there is one (with `fresh` too; the owner's [_Restart container_](workspace.md) forgets it, so the owner's restart starts on the Environment's size); with `fresh` the Snapshot is forgotten first, as the owner's [_Restart container_](workspace.md) does (GLOSSARY.md → Container restart), for when a restart from the Snapshot did not help. Commands running in the Container end, other Sessions' in the Workspace too. The tool is `replay: "unsafe"` (a rerun after an eviction would stop the Container the next command started) and sequential. It does not ready the Workspace, and starts no Container.
- **Resize by the agent** (GLOSSARY.md → Container resize, ADR-0019): `container_resize({ size, reason })` (the `container` extension; deferred) restarts the calling conversation's Workspace's Container (as `container_restart` picks it) at another size, for that Container alone, until its idle stop: the agent's way to more memory when the memory guard stops its processes, and back to a smaller size once that work is done. `size` is an `INSTANCE_TYPES` name (the description lists each with its resources, by memory), `reason` is 1 to 500 characters, shown as the call's summary as `container_restart`'s is, and it asks no one. Through the Workspace DO's `resizeContainer` (`ContainerResizes`, `apps/server/src/workspace/resize.ts`), which holds the Container from the idle stop meanwhile: a `size` above the Environment's size limit (`maxInstance`, as the Workspace DO's copy of the settings has it) is refused, naming the limit and that the owner can raise it, and nothing is stopped. Otherwise a running Container is snapshotted as at the idle stop (`ContainerLaunch.snapshot`, labelled `resize`; the scan for the GitHub tokens and the Environment's Secrets included) and destroyed, whatever runs on it: commands running there end, other Sessions' in the Workspace too, and the result says so. A snapshot that could not be taken does not stop the resize, and the result says the next Container starts from the last one. The size is recorded in the Workspace DO's storage (`cloudpid:container-resize`) before the stop, as a one-launch override, so the next launch, whichever command starts it, is on that size and restores the snapshot, `node_modules` and the other Container-only paths included. With no Container running the size is only recorded. A resize to the Environment's own size records nothing (it forgets the override), and one to the size the running Container already has does not stop it and says so. The idle stop forgets the override (see _Idle stop_; it is forgotten just before the Container is destroyed, so a resize that lands during the stop is kept), and so does the owner's [_Restart container_](workspace.md); `container_restart` keeps it. A snapshot that cannot be restored on the target size (larger than its disk) takes the fallback to the image (see _Snapshots_), and the result warns of that when the target's disk is smaller than the current size's. The Session's Container cost already prices each launch at its own size, so a resize needs nothing there. The tool is `replay: "unsafe"` and sequential, as `container_restart` is, and subagents have it too. It does not ready the Workspace: the settings are the Environment's as the Workspace DO last had them, handed over at each readying (at most a minute old while the Session works). Not yet verified on a deployed stage: a resize of a running Container, then a command that launches on the new size from that snapshot with `node_modules` restored.
- **Egress:** unrestricted direct egress in v1, and not logged. A per-Workspace allowlist, and logging with it, come later.
- **Docker** (measured in [#170](https://github.com/ian-pascoe/cloudpid/issues/170) on a deployed Container): the image has `docker.io`, `docker-compose-v2` and `docker-buildx`, which run there with the overlay2 driver and cgroup v2, for a Start Script to bring up services (databases, dev dependencies) that a Snapshot cannot hold. Nothing runs systemd, so nothing starts the daemon on its own: `cloudpid-dockerd` (`apps/sandbox-image/image/cloudpid-dockerd`) does nothing when `docker info` answers, and otherwise starts `dockerd` detached (`setsid nohup`, its output in `/var/log/dockerd.log`) and waits up to 60 s for it to answer, under a lock so two calls at once start one daemon; arguments go on to `dockerd`. The Container's `/proc/sys` is read-only, so a default `dockerd` fails while it enables IP forwarding: the image's `/etc/docker/daemon.json` turns off `iptables`, `ip6tables` and `ip-forward`, and the helper sets `DOCKER_ALLOW_IPV6_ON_IPV4_INTERFACE=1`. Default compose files then work: bridge networks, with published ports reachable on the Workspace's localhost through Docker's userland proxy. Bridge-networked containers get no internet, since nothing forwards their packets; `network_mode: host` does. Images and volumes are in `/var/lib/docker`, on the Container's disk, so a Snapshot carries them. Postgres through compose was ready 10 s after `up`, the image pull included. Custom images for the Container itself are not offered ([ADR-0016](../adr/0016-environments-and-a-container-per-workspace.md)).
