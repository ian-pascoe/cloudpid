# Browser

[ADR-0007](../adr/0007-browser-and-credentials.md) covers this design.

- **Tool:** `agents/browser` `Browser` with `browserRun(env.BROWSER, { keepAliveMs: 10 min })` (the binding wrapped so that every acquisition carries the Container previews' routes: see _Container preview_, below) in a browser host DO (`BrowserHost`), one per Session, in the plain `Browsers` Worker (`apps/browser`). `agents/browser/pi`'s `browserTool()` there runs the model's CDP code in a Worker Loader isolate (`LOADER`). The Session DO cannot host it: `browserTool` keeps its runs in a `CodemodeRuntime` facet the hosting Worker must export, and the Server Worker, an alchemy Effect Worker, exports only its Effect DO classes. The Session DO's `browser` tool (`packages/extensions/src/browser`) reaches the browser host DO over RPC, takes its description from it, and passes the calling conversation's ID, and, with `tab`, the Owner tab to run in (see _Browser Pane_ → _The agent in Owner tabs_). The host builds one `browserTool` whose `scope` is a function of the call: the scope the host gives it (`owner-tab:<id>`), else the conversation's (`conversation:<id>`); the tool builds each scope's connector when first asked and runs a scope's calls in turn. `Browser` keeps its record through an explicit `DurableBrowserSessionStore`, so no `Lifecycle` is installed: it would take over the object's `fetch`, `alarm`, and WebSocket handlers.
- **Session:** one shared Browser Run session per Session, with a tab per conversation (the root and each subagent: `conversation:<id>` scope), the Owner tabs (each an `owner-tab:<id>` scope: see _Browser Pane_, below), and shared cookies. Logins last as long as the Browser Run session.
- **Keep-alive:** Browser Run reclaims a browser after `keep_alive` without a CDP command (10 minutes here, so a long gap in the middle of a turn does not lose it; its maximum is 20). The Session closes it sooner, through the browser host DO, once the Session has been idle 5 minutes after the browser's last use, so an abandoned browser is not billed for the rest of the `keep_alive`: the time of the last use is kept in the Session DO's storage (noted before a run and after it), joins the Secret expiry as a wake time of the host's alarm (`wakeAt`), and the close runs when the host settles idle (`onIdle`) under a 5-second timeout, so a slow host cannot stall admission. A Session that is never idle is not closed by it; Browser Run's own timeout still applies. **While a Browser Pane is in view** (see _Browser Pane_ → _Keep-alive while watched_) neither close takes the browser: the Pane's poll of the Owner tabs is a heartbeat the idle close counts from, and each poll is a command to the browser for Browser Run's own `keep_alive`.
- **Results:** a screenshot is returned as an image part and shown in the tool's card. It is kept in the transcript, so one over about 560 KB (750,000 base64 characters, the bound `read`'s images are held to: see [_Filesystem and tools_](workspace.md#filesystem-and-tools)) is replaced by a note to retake it as a smaller JPEG, and only PNG, JPEG, and WebP are kept. Only the latest 3 screenshots go to the model in a request (older ones read `[screenshot omitted]`, at the model seam next to Secret scrubbing), and the transcript snapshot a client gets carries the latest 10, so neither a provider's image limits nor a socket message's size limit grows with a long browsing Session. A screenshot is pixels: it cannot be redacted of a Secret the page shows. Results are redacted of held Secrets by the secrets extension's `afterTool` hook; `browser` is not one of the tools that resolve Secret references, since its code is stored with the run.
- **`browser_handoff({ instructions })`** (`packages/extensions/src/browser/handoff.ts`, host side `apps/browser/src/handoff.ts`): Browser Run's structured handoff (Human in the Loop), taken over in our own Live View ([ADR-0013](../adr/0013-own-live-view-with-links-minted-on-open.md)). The browser host attaches to the conversation's active tab over a CDP connection of its own (`agents/browser`'s `CdpConnection` hands its caller no events), notes the tab's viewport (`innerWidth`, `innerHeight`, `devicePixelRatio`), sends `Cloudflare.handoff` with the instructions and `timeout` of 30 minutes (Browser Run's maximum), and hears the owner press Done or Failed as the `Cloudflare.handoffComplete` event on that connection (`success`, `reason`); Browser Run fires it on its own timeout too. It mints no link at the start. A conversation with no open tab gets an error telling the model to open the page with `browser` first.
  - **Link:** no Live View link is minted until the owner opens a Live View, and none is stored, sent to every client, or pushed. The Session keeps the request (instructions, conversation, deadline) in its key-value storage and sends the waiting requests to every client (`browser_handoff_requests`, sent after `hello` on every connect, an empty list too, so a client can tell "none waits" from "not heard yet", and to every client whenever the list changes), and pushes a `notice` with the instructions whose `url` is the Session's page with the handoff's Live View Pane open (`/sessions/:id?pane=live-view:<requestId>`: the extension sends the query, `liveViewPaneQuery` of `@cloudpid/protocol`, and the push puts it on the Session's page; the Pane's key is `liveViewPaneKey`). The UI shows a card with the instructions beside the Secret form, naming the subagent (ID and role) when the tab is not the root agent's; its **Take over** opens the Live View Pane, and a small **Open in Cloudflare** beside it mints a link the same way and opens Browser Run's hosted Live View (a fallback). The Pane never opens on its own. To connect, the client sends `live_view { id, requestId }` (a socket command shaped like `catalog` and `files`, ADR-0009), which the Session passes to the browser host's `liveView(requestId)` over `BROWSER_HOST` and answers to the asking client alone with `LiveViewLinks`: `{ tab: { targetId, link }, windows: [{ targetId, openerId, title, link }] }`. Each `link` is a fresh `Cloudflare.getLiveView` (`mode: "tab"`) with `expiresInMs: 60000` (Browser Run's minimum) and an explicit `targetId` (without one, Browser Run picks the newest page of the browser, not the handed-over tab), given as its `webSocketDebuggerUrl`, a `wss` URL the client opens straight from our origin (Browser Run checks the JWT, not the `Origin`). The windows are the page targets of `Target.getTargets` on the host's browser-level connection whose `openerId` leads back to the handed-over tab, directly or through another window (every pop-up and new tab carries one, `noopener` ones included: the spike, #152; a page with no opener, such as a tab the agent made, is not a window), breadth first. The client asks again when the Pane opens, on every reconnect, when the tab hears `Page.windowOpen`, and when a window's connection closes. Once the handoff has ended (or for a request the Session does not have) `live_view` fails with "the handoff is over" (`LIVE_VIEW_HANDOFF_OVER`). A link is in no socket message but that answer, no push, no storage of the Session or the host, and no tool argument, result, `details`, transcript entry, snapshot, or model request; a workerd test asserts that on every other socket message to every client, the pushes, the Session's key-value storage, the Harness's tables, the snapshot, and the model's requests. What a link exposes is set out in [_Risks_](risks-and-spikes.md) → Exposure of the shared browser session.
  - **Completion:** the owner's Done or Failed (with an optional reason) in the Live View Pane is the signal; there is no client command. The Pane sends `Cloudflare.handoffComplete { success, reason }` on the handed-over tab's own connection, as the hosted page does, and the host hears the event; the Pane also hears it on its connection and closes when another device finishes. The Pane closes when the handoff ends (Done, Failed, Stop, timeout); closing it does not end the handoff. The tool's result says how it ended: the user finished, the user could not (with their reason), timed out after 30 minutes, or ended without a word (Browser Run no longer had the handoff); and how many windows the tab opened are still open, each by its origin only (never the URL: an OAuth redirect carries a code), read when the handoff is ended (`endHandoff`'s `windowOrigins`); when the host could not read them in the five seconds a cleanup gets, the result says it is not known whether windows are open, never that there are none. It names no link. Stop withdraws the request and ends the handoff in Browser Run, over a new connection when the browser host restarted since it started.
  - **Cleanup:** there is no link to purge: the Session drops the request from its storage when the call ends, and the host deletes its record when the Session ends the handoff. **The agent's viewport:** the Pane sets the tab's size (`Emulation.setDeviceMetricsOverride`), one override shared by every connection, which closing a connection does not undo and a clear from another connection undid unreliably (the spike). So at every ending (Done, Failed, Browser Run's timeout, a handoff Browser Run lost, Stop) the host sets the size it noted at the start explicitly (`setDeviceMetricsOverride { width, height, deviceScaleFactor, mobile: false }`, Browser Run's default 780×493 at DPR 1 when it could not be read), checks `innerWidth` and `innerHeight` and sets it once more if they differ; then, on every window of the handoff that is still open (which never had an agent override), it clears the Pane's override in the window's own session and, if the window does not show the size the host read when `liveView` first listed it (before the Pane had a link to it), sets that size explicitly. All this before `waitHandoff` answers the ending and before `endHandoff` forgets the handoff. The Pane also clears its override before Done and Failed, on close and on `pagehide`, best effort; a size the agent had set itself before the handoff is the one put back, though not its `mobile` flag, which the page cannot tell. A record the Session never ended (it was deleted, or the call was cut off for good) carries its deadline and is pruned by the host's alarm five minutes past it, and the Session does not show or push a request past its deadline plus the grace it gives the host. A request that was ended leaves a one-hour tombstone in the host, so a start that arrives late is refused instead of opening a handoff nobody ends; a second start of the same request while the first is in flight joins it. The host reads the conversation's tab from `agents/browser`'s stored records without resolving a browser: a conversation with no browser or tab of its own gets the no-open-tab error, and no browser is started for it. When the host cannot reopen its connection, only Browser Run saying the browser or tab is gone ends the handoff (`ended`); any other failure is retried by the Session's rounds.
  - **Durability:** the tool is `replay: "safe"` and waits in rounds of 25 s on the host's `waitHandoff`, so no call outlives an eviction; the request and its deadline are in the Session's storage, and the rerun after an eviction waits for the same handoff (`startHandoff` is idempotent by the call's task ID, and the host keeps its record in its own storage). A host that restarted reconnects and asks `Cloudflare.getHandoffState`: a handoff that is over with no end event heard ends as "ended". A request whose call is gone is ended once the Session is idle, as an abandoned Secret request is.
  - **Keep-alive:** each round also notes the browser as used, so the Session's 5-minute idle close never runs under a pending handoff (a live tool call means the Session is not idle anyway), and the host's quiet-round `getHandoffState` poll is a CDP command, which keeps Browser Run's own `keep_alive` from reclaiming the browser while the owner works.
- **Browser Pane** (`browser`; `apps/web/src/live-view/browser-pane.tsx`, `browser-pane.ts` and `browser-pane-atoms.ts`; host side `apps/browser/src/owner-tabs.ts`): the owner's own way into the Session's browser, at any time and apart from any Browser Handoff ([ADR-0013](../adr/0013-own-live-view-with-links-minted-on-open.md), amended). The New pane offers it (an archived Session's does not), and it is kept in the Session layout and the URL like the other Panes; it never opens on its own. Its tab is labelled "Browser". The Session's side is `BrowserPane` (`packages/extensions/src/browser/pane.ts`), between the socket and the host.
  - **Owner tabs:** pages of the shared browser the owner opened, apart from the conversations' tabs but sharing their cookies and logins. Each is an `agents/browser` scope of its own, `owner-tab:<id>`: opened with `Browser.connect({ scope })` (which reattaches to the browser that runs, and starts one only when none does) and `Target.createTarget` (`about:blank`), and recorded as that scope's active tab (`openTab`, `apps/browser/src/tab.ts`), so the scope's record names the tab and the browser it is in. The host keeps the list of Owner tabs and the one the Pane shows in its storage (`owner-tabs`: `{ tabs: [{ id, url? }], shown }`; no link; `url` is what the host last read from the browser, without its fragment, see _Recorded and reopened_ below); an Owner tab that is gone leaves the list when another is shown, and its scope record is deleted (`forgetScope`, under the lock `agents/browser` writes scope records under), so it does not count against `MAX_BROWSER_SCOPES`. The owner may have several (the tab strip, below); attaching a page to a message is a later ticket of #236.
  - **Tab strip** (#239; `apps/web/src/live-view/owner-tab-strip.tsx`): each Owner tab by its title (`New tab` for a page without one; page content, shown as text; no favicon), the one shown marked, a close button on each, and **+** for a new blank Owner tab, which focuses the URL bar once shown. Closing the last leaves the Pane empty, with **+**. Which Owner tab is shown is the browser host's (`owner-tabs.shown`), so every device shows the same one: a switch, open or close goes through the Session (`owner_tab_show`, `owner_tab_open`, `owner_tab_close`, answered with the `OwnerTabListing` `{ tabs: [{ id, title, url? }], shown? }` and sent to every client as `owner_tabs`, which holds no link), and each Pane connects afresh to the tab the Session says is shown (`follow`). `owner_tab_list` answers the same listing, and a Pane asks every 5 s while the page is visible (and when its tab hears `Page.windowOpen`) for the tabs a page opened and for titles that changed (with `watching` while the Pane is in view: the heartbeat, below); the listing is the host's (`ownerTabs()`, `openOwnerTab()`, `showOwnerTab(id)`, `closeOwnerTab(id)`), read from Browser Run's targets on a browser-level connection the host opens for the call. A listing starts nothing (with no browser running it is empty, with `lost` saying how many Owner tabs a closed or replaced browser took that are still on record to reopen, by `statesOf`: absent for an owner who has none, closed the last, or whose Owner tabs were all closed in a browser that still runs) and keeps the stored list when every Owner tab is gone (the browser was closed or replaced), so `owner_tab_view` with `open` can reopen them and say it did; otherwise the ones that are gone leave the list (their scope records are deleted) and the one shown gives way to its neighbour on the right, else on the left. `owner_tab_open` is a use of the browser, as an `owner_tab_view` that opened is, and is refused in an archived Session; at most 20 Owner tabs. Closing an Owner tab closes the windows it opened (not the Owner tabs it opened) with it, after looking at the list once, so tabs it opened are not left without an owner.
  - **Tabs a page opens:** a page that descends from an Owner tab (by `openerId`, through windows too) and cannot reach its opener (`canAccessOpener: false`: a link with `target=_blank`, a middle click, `noopener`) is adopted as an Owner tab of its own (`adoptTab`: writes its scope record, which names the page, under the lock `agents/browser` writes scope records under; it starts no browser, and fails when the browser has closed or been replaced since the pages were listed, so a listing starts nothing) when the list is next read, and shown when the Owner tab it came from (directly or through a window) is the one shown (on every device, as the shown Owner tab is the Session's: unlike a desktop browser, a middle click on a link opens the tab and shows it, since the host cannot tell a middle click from a click); one that can reach its opener (`window.open`, an OAuth window) stays a window of its tab, listed in `OwnerTabLinks.windows` and shown as the Live View shows windows, and is not an Owner tab. A page with no opener (a conversation's tab, made with `Target.createTarget`) is never listed, shown or closed here. A tab a link opened is left out of its opener's `windows` at once, before the list adopts it. Not checked against Browser Run yet: that `canAccessOpener` is false for a `target=_blank` link and true for `window.open` there.
  - **Links:** `owner_tab_view { id, open }` (shaped like `live_view`, ADR-0009), which the Session passes to the browser host's `ownerTabView(open, workspace)` over `BROWSER_HOST` (`workspace`: the Session's Workspace, for the Container previews' routes, below) and answers to the asking client alone with `OwnerTabLinks`: `{ ownerTabId, tab: { targetId, link }, windows: [{ targetId, openerId, title, link }] }`, minted as `live_view`'s are (`Cloudflare.getLiveView`, `mode: "tab"`, `expiresInMs: 60000`, an explicit `targetId`, on a browser-level connection the host opens for the call and closes after it; the windows found by their openers, breadth first; a window that closed before the listing or before its link was minted left out; `mintViewLinks` in `apps/browser/src/cdp.ts`, which a Browser Handoff's `liveView` uses too). With `open` (the Pane's first ask that succeeds, and a Pane in view that finds its Owner tabs on record in a browser that is gone), the Owner tab shown is used while it is still there; else, with none of the owner's still there, every Owner tab that a closed or replaced browser took with it is reopened at its recorded address (see _Recorded and reopened_) and the one shown before is shown again; else another of the owner's that is still there is shown and the ones closed in the browser that runs leave the list; with none on record, a new one is opened (in the browser that runs, or a new one) and shown. Two Panes opening at once open one. The answer then says whether it opened one (`opened`), whether the one shown before is gone (`replaced`) and, when it reopened Owner tabs in a new browser, how many (`reopened`, absent otherwise), and the Pane says so above the screen until the owner dismisses it. An archived Session opens nothing: the Session asks the Registry whether it is archived at each ask with `open`, and asks the host without `open` when it is (the Pane, which reads the Session's `archived` as the tree Pane does, never asks to open there either, and offers no new Owner tab). Without `open` (every reconnect, a window opening or closing) nothing is started or opened, and an Owner tab that is gone fails with "the Owner tab is gone" (`OWNER_TAB_GONE`): its scope's record names a browser that was closed or replaced, Browser Run no longer has the browser, or the tab is not among its pages (`tabIn` reads the stored records, as a handoff's tab lookup does, and starts nothing). The link-leak workerd test covers `owner_tab_view` too.
  - **Browsing:** a URL bar over the Owner tab, with back, forward and reload, all sent on the Pane's own connection to the tab: the field shows the tab's URL (`Page.getNavigationHistory`, read when the tab connects and again on the main frame's `Page.frameNavigated` and on `Page.navigatedWithinDocument`), Enter navigates (`Page.navigate`; a page that does not open says its `errorText` under the bar), back and forward move through that history (`Page.navigateToHistoryEntry`), and reload is `Page.reload`. The URL bar takes an http or https URL, an address without a scheme over https (`example.com/a`), or `about:blank` (`apps/web/src/live-view/address.ts`); text that is not an address is refused with a note, not searched for or guessed at, and so is any other scheme. The screen, input, viewport and windows are the Live View's (`connection.ts`, `live-screen.tsx`), on desktop and on a phone.
  - **Viewport and closing:** the Pane sizes the Owner tab to itself as the Live View does, and clears its override when it closes (best effort); the host restores nothing, as an Owner tab is not an agent's tab. Closing the Pane leaves the Owner tabs open in the browser, and opening it again shows the same tab; two devices on the Browser Pane at once see the same Owner tab, the one the host says is shown, and follow its switches.
  - **The agent in Owner tabs** (`apps/browser/src/owner-tab-agent.ts`; `packages/extensions/src/browser/tool.ts` and `drivers.ts`): the agent reads and drives the owner's pages.
    - **`browser({ code, tab? })`:** without `tab` the code runs in the conversation's own tab, as before. With `tab` (an Owner tab's ID, or `"shown"` for the one the Browser Pane shows) the Session first asks the host for the Owner tabs (`ownerTabs()`, the tab strip's listing) and resolves `tab` among them, then asks `run(code, conversationId, ownerTabId)`, and the host runs the code in that Owner tab's own scope (`owner-tab:<id>`), whose active tab is the Owner tab, so `sessionId: "active"` is that tab and the conversation's own tab and active tab are left as they were.
    - **What a call in an Owner tab may not send:** the connection `browserTool` drives an Owner-tab scope through (`confinedToOwnerTabs`) refuses, by name: the commands that size the page (`Emulation.setDeviceMetricsOverride`, `clearDeviceMetricsOverride`, `setVisibleSize`, `setPageScaleFactor`, `resetPageScaleFactor`, `Browser.setWindowBounds`, `Browser.setContentsSize`) and `Page.captureScreenshot` with `captureBeyondViewport: true` (which resizes the page while it captures), so the Pane's size stands; `Target.createTarget`, `attachToBrowserTarget`, `autoAttachRelated` and `sendMessageToTarget`; `attachToTarget`, `activateTarget`, `closeTarget` and `exposeDevToolsProtocol` on any page but the Owner tab; and `Target.setAutoAttach` on the browser (on the Owner tab's session it reaches the tab's frames and workers only). So the scope's active tab stays the Owner tab. Each refusal fails the call with a sentence saying why and what to do instead. It is a denylist that keeps a well-meaning agent out of the owner's way, not a security boundary: what the code makes the page do is not refused, so a `window.open`, a link with `target=_blank` or a middle click it dispatches (`Input.dispatchMouseEvent`) still opens a page, which joins the Owner tabs (and may be shown on every device) as the owner's own would; the `browser` description asks the agent not to. A conversation's scope is never confined (the wrapper changes only the Owner-tab scope's connections, each made afresh per pass).
    - **A tab that is gone:** calls in one Owner tab go one at a time (`OwnerTabCalls`, as `browserTool` queues a scope's), and each looks the Owner tab up from the stored records (`tabIn`) when its turn comes: one the host does not have, or that is not open (closed, or its browser closed or replaced), fails without running anything, since `browserTool` would open a blank tab in its place, or start a browser, under a scope whose record was just deleted. Every connection to an Owner-tab scope is looked up the same way first, and refused with the same error, so a tab that goes during a call does not start a browser either. One that is closed during the call (it is no longer open when the call ends) makes the result an error that says so, before what the code returned. Both are error results, not failures. A call is a use of the browser (`BrowserSession.touch`), as before.
    - **What the agent knows:** `browser_owner_tabs` (no parameters) lists the Owner tabs, in the strip's order: each one's ID, title (quoted, as the page's own words, cut to 200 characters), origin (`originOf`, which a Browser Handoff's windows are told by too: the listing gives the origin, never the URL, which may carry a token; `about:blank` for a blank page), and which one the Browser Pane shows. It is the tab strip's listing (`ownerTabs()`, with each page's `url`), from which the Session keeps the origin only: no code runs, and no browser is started (a tab a page opened joins the list, as it does for the strip). With no Owner tab open, it, and a `browser` call with `tab`, say there are none and that the user opens them in the Browser Pane, which the agent cannot open; a `tab` that names no open Owner tab is refused with the listing. The `browser` description says how to use them. Neither names a Live View link.
    - **Who is driving:** while a `browser` call works in an Owner tab, the Session lists it (`OwnerTabDrivers`, in memory: an eviction cuts the call off) and tells every client `owner_tab_drivers { drivers: [{ ownerTabId, conversationId }] }`, after `hello` on every connect (an empty list too) and whenever it changes. The tab strip marks each driven Owner tab, shown or not, and the Browser Pane shows a note over the screen while the Owner tab it shows is driven; both say "The agent is driving this tab", or name the subagent by its ID and role (`agentLabel`, from the task graph) for a subagent's call (`apps/web/src/live-view/driving.ts`, `use-driving-note.ts`), the strip's mark as its label and tooltip. The owner keeps using the tab meanwhile.
  - **Attaching a page:** the composer attaches Owner tabs to a message (see [_Attached pages_](client-and-protocol.md)). Its menu offers the tab strip's listing (`owner_tab_list`: IDs, titles, the one shown); the host reads the ones a message attaches at send time (`readOwnerTabPages(ids)`, `OwnerTabs.read`: URL and title from Browser Run's targets, the selected text from the page over `Runtime.evaluate`, all of it the page's to say). A read mints no link, starts no browser and is no use of it. The URL here is the full address, unlike the origin the agent is told of an Owner tab (`originOf`): the owner chose to give this page to the model, which an OAuth redirect's code or a link's token could be in, so the owner sees it as the chip's host and the model's block holds it redacted of held Secrets.
  - **A browser that is gone:** an ask that opened an Owner tab (and perhaps started the browser for it) is a use of the browser (`BrowserSession.touch`), and the Session settles after it, so an idle Session wakes to close the browser 5 minutes after (the same idle close as the agent's use). Showing, reconnecting and browsing are not uses, but a Pane in view keeps the browser by its heartbeat (below). A Pane whose Owner tab is gone (the tab was closed, or its browser closed or replaced) loses its connection, asks again without `open`, is told the Owner tab is gone, and says so, offering **Open a new Owner tab** (`owner_tab_open`, like **+**, so every device is told). In view, with Owner tabs on record (`lost`), it first asks by itself with `open` (`owner_tab_view`, once per 30 s at most), which reopens them (below); one the owner closed the last of, or an archived Session's, is not reopened. The strip stays (**+** alone, with the URL bar), and the Pane keeps following: when the Session reports an Owner tab shown (this device or another opened one), the Pane connects to it.
  - **Keep-alive while watched** (#240): a Browser Pane **in view** (its tab shown in the Pane area, the area not hidden, the page visible: `useInView`, `apps/web/src/live-view/browser-pane.tsx`) marks its poll of the Owner tabs as its heartbeat: `owner_tab_list { watching: true }`, every 5 s (`OWNER_TABS_POLL`) and at once when it comes into view. There is **one mechanism**: the poll the tab strip already makes is the heartbeat, with no second command. It is a heartbeat that lapses, never an open/closed flag: a Pane that is hidden (the area hidden, another Pane shown, the page in the background), closed or cut off sends no `watching`, so an eviction or a dropped connection cannot leave a flag stuck on. The listing is itself a command to the browser (`Target.getTargets`), so Browser Run's `keep_alive` counts it, and when the host answers with Owner tabs (a browser runs) the Session notes the beat (`BrowserPane.watchedTabs` → `BrowserSession.watch`, key `browser-pane-watched` in the Session's storage; a listing that finds no Owner tabs notes nothing, so a Pane that finds its browser gone holds nothing open). The Session writes it at most every 30 s (`WATCH_WRITE_MS`, far less than the 5-minute window), so a 5-second poll does not write storage each time. The idle close counts from the later of the last use and the last beat (`closeAt`), so a Pane in view holds off the 5-minute idle close for as long as it polls, and once it stops (hidden, closed, forgotten) the browser closes 5 minutes after the last beat, as an abandoned browser does: a forgotten Pane is not billed for hours. A beat that sets a close time where there was none settles the Session in the background, so its alarm is armed (a beat before that only moves a time the armed alarm checks again on waking, `closeIfIdle`). The times are in the Session's storage and the alarm survives an eviction, so an evicted Session wakes and finds the beats fresh (the close is held off, and the alarm set again for the window after the last beat) or lapsed (it closes the browser). **Live View traffic and `keep_alive`:** the heartbeat is a CDP command because Browser Run's documentation names commands as what keeps a session from its inactivity timeout (`keep_alive`: a browser that "received no commands" for the timeout is closed). Whether the traffic of the Pane's own Live View connections (the screencast and the owner's input) also counts as activity is not documented, and **it was not tested on a deployed stage**, so the design does not rely on it. Whether a Pane left open and in view for 30 minutes keeps a real browser, and whether one hidden past the window loses it, is for a deployed stage to confirm; the heartbeat and the idle close are tested with a Session over a fake host (`handoff.workerd.test.ts`: held off while polls are fresh and run once they lapse, across an eviction).
  - **Recorded and reopened** (#240): the host records each Owner tab's address in its list (`url`, without its `#fragment`; the title is not kept, listings read titles from the live pages, so a page whose title keeps changing does not write host storage), read from the pages `Target.getTargets` lists whenever it reconciles the list (`#reconcile`: every `owner_tab_list`, so while the Pane is in view an address is at most 5 s old; every change of the tabs), and for up to 2 s just before it closes the browser (`BrowserHost.close`, so the idle close records where the owner left off). A tab on an address that cannot be reopened (an error page, `file:`, `chrome:`) keeps its last recorded one; a new tab reopens blank. The order is the list's, and `shown` the one the Pane shows. - **Container preview** ([ADR-0023](../adr/0023-container-previews-through-browser-run-outbound-workers.md); `apps/browser/src/container-preview.ts`, `apps/server/src/workspace/container-preview.ts` and `container-preview-script.ts`): a dev server running in the Session's Workspace's Container opens in the Session's browser, for the owner in the Browser Pane and for the agent's `browser`, at `http://<port>.cloudpid.internal/`, with no public URL or token. Browser Run refuses `localhost` (`ERR_BLOCKED_BY_ADMINISTRATOR`, a Chrome policy), cannot reach the Container, and cannot sign in to the main Worker's Access.
  - **Routes:** the host acquires every browser with Browser Run's outbound Workers (`outboundByHost`), which send the browser's requests for the hosts it names to a Worker `Fetcher` instead of the network: eight hosts, one per port, `3000`, `3001`, `4173` (`vite preview`), `4321` (Astro), `5173` (Vite), `5174`, `8000` and `8787` (`wrangler dev`) (`CONTAINER_PREVIEW_PORTS` in `packages/extensions/src/browser/contract.ts`), as Browser Run takes at most eight hostnames, fixed at acquisition, on port 80 and plain `http` only. 8080 is computerd's and is never on the list. All eight go to the Session's Workspace; none is kept for Subagent Workspaces. Each is the `ContainerPreviews` entrypoint the `Browsers` Worker exports, made with `ctx.exports.ContainerPreviews({ props: { workspace } })` for the Session's Workspace DO (`ws:<id>`); it takes the port from the host (another host, or a port in the URL, is a 404) and hands the request on through the service binding `CONTAINER_PREVIEWS` to the Workspaces Worker's `WorkspaceContainerPreviews` entrypoint (a failed call is a plain-text 502). That entrypoint offers one call, `containerPreview(workspace, request, port)`, for an object named `ws:<id>` only (anything else, a Build's object among them, is a 404), which it hands to that Workspace DO's `containerPreview(request, port)`: the `Browsers` Worker reaches no other method of the DO. `agents/browser`'s `browserRun` takes only `keepAliveMs`, `recording` and `guardrails`, so the host hands it a wrapper of `BROWSER` whose `acquire` adds `outboundByHost` (`ContainerPreviewRoutes`), wherever the browser is acquired from: a run, an Owner tab opened from the Pane or with **+**, a browser replacing one Browser Run lost. **How the host learns the Workspace:** the calls that can acquire a browser (`run`, `ownerTabView`, `openOwnerTab`) name the Session's Workspace as a trailing optional argument (`ContainerPreviewWorkspace`: the Workspace DO's name, from the Session's placement; none when the Session has none or the Registry could not be asked, which leaves the one the host knows), and the routes are made for the latest it was given, held in memory only, so the host stores nothing about it. The host takes only a value shaped `ws:<id>` (`isContainerPreviewWorkspace`) and ignores anything else, so a Session and a host deployed apart (a Session from before, which names none; a rollback, whose host ignores the extra argument) never route to a wrong object. A browser acquired before any call named a Workspace, or before this shipped, has no routes until it is acquired again, and a route keeps the entrypoint code it was made with (the Fetcher keeps the version of the object that made it) until then. A binding with only the HTTP API (fully local dev) acquires browsers without routes. The routes outlive the call and the object that made them.
  - **The Workspace DO's side** (`containerPreview(request, port)`, `ContainerPreview`): a fetch from the Container's port (`ctx.container.getTcpPort(port)`, as computer's `fetchPort` does) to `http://localhost:<port>` with the page's path, method, body and headers (`Origin` passed through as it is: set to the dev server's own, Vite's CORS would answer every origin; `Host` the dev server's own, `localhost:<port>`, so a dev server that checks it, as Vite's `allowedHosts` does, takes the request; `X-Forwarded-Host` the Container preview's host and `X-Forwarded-Proto: http`, for a dev server that builds URLs from them; `cf-*` and the incoming forwarding headers dropped), redirects not followed. A `Location` the dev server answers with that points at itself (`http://localhost:<port>`, or `127.0.0.1` or `0.0.0.0` on that port, made from the `Host` it was sent) is turned back into the Container preview's address. It serves the eight Container preview ports only: any other, computerd's 8080 among them, is a 404 page that asks nothing of the Container. It **never starts the Container**: a stopped one answers a 503 page saying so, and a port with nothing listening a 502 page saying the dev server must listen on `0.0.0.0`, as the port is reached on the Container's interface, not its loopback (Vite's default host does not answer). Each request it serves (not a refused one) is a use of the Workspace (a spare's is no longer a spare: `SparePreparation.noteUse`) and of the Container (`IdleStop.touch`).
  - **WebSockets over HTTP:** Browser Run routes only HTTP requests, not WebSocket upgrades, so the Workspace DO puts a script (`CONTAINER_PREVIEW_SCRIPT`) at the start of every HTML page it serves (in its `<head>`, else after its doctype; never in another type; `Content-Length`, `Content-Encoding` and `ETag` dropped), which replaces `WebSocket` for the page's own host with a carried socket, carried over HTTP, and leaves a socket to any other host to the browser: `GET /__cloudpid/ws/open?path&protocols` is a stream of server-sent events, read with `fetch` (`open` with the socket's ID and protocol, each message as `{ text }` or `{ binary }` in base64, `close` with its code and reason), and `send` (the body, `binary=1` for bytes) and `close` (`{ code, reason }`) are POSTs, sent one after another in order. A socket that cannot open (the Container stopped, the server down) fires `error`, then `close` with 1006, as a WebSocket does, which Vite's restart ping takes as the server still down. The script also hides `SharedWorker`, since Vite pings for a restarted server from one when it can, where the script does not reach. The Workspace DO opens the real socket to the Container (from the page's origin, with its cookies and protocols), listening to it before it accepts it, so the dev server's first message (Vite's `connected`, sent at once) is not lost; holds it in memory by its ID; and counts it as a running command (`IdleStop.begin`/`end`, the end always after the begin) until it closes, so an open page holds off the idle stop until the page or the browser closes (Vite's client also pings every 30 s); each message from the Container is a use. It closes the socket when the stream goes away or stops being read: a keep-alive comment is written every 15 s (`CONTAINER_PREVIEW_KEEP_ALIVE_MS`); a write that fails (or the stream cancelled) is the page gone, and a tick that finds something unread and nothing read since the last tick is a page that stopped reading, whose stream is then failed. The stream is written in 64 KiB slices, so a page reading a large message slowly shows progress at every tick and is never cut off for it; an absolute bound on what may wait unread (`CONTAINER_PREVIEW_MAX_UNREAD_BYTES`, 96 MiB, far above any WebSocket message) only caps the memory a stopped page holds between two ticks. **The endpoints refuse** (403) a request without `x-cloudpid-preview: 1`, a header a page of another origin cannot send without a CORS preflight, which nothing answers, and one whose `Origin` is not the page's own; a carried socket's ID is 256 random bits, told only in its stream, so `send` and `close` to an unknown ID are a 404.
  - **What a page is:** its origin is `http://<port>.cloudpid.internal`, not `localhost` and not a secure context (no service workers, `crypto.subtle` or clipboard API), and an app that expects `localhost` (OAuth redirect URIs, CORS allow-lists, hard-coded URLs) sees another origin. A restart of the Workspace DO or of the Container drops every Container preview's carried socket, and Vite reloads the page once the server is back (503 while the Container is stopped, then 502 until the dev server runs again), losing its state. A dev server whose client opens sockets from a worker, or to another host, needs more of the script; a page whose Content-Security-Policy forbids inline scripts gets no WebSockets. A Container's processes never survive a stop, so the dev server must be started again after one (by the agent, or a Start Script).
  - **The agent:** the `browser` description says that `localhost` is refused, that a dev server on port N is at `http://N.cloudpid.internal/` (the eight ports listed), that it must listen on `0.0.0.0`, and what a stopped Container or an idle port answers. Every tab of the browser has the routes, so a tab the agent opens to the address loads the Container preview with nothing secret in its code.
