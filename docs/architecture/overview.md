# cloudpid

A personal, always-on coding agent that recreates the local pi harness on Cloudflare. pi-durable runs the agent, `@cloudflare/computer` holds the files and runs commands, alchemy provisions everything, and Effect is the application language.

These documents record the settled design (first settled on 2026-10-20). Terms follow [`GLOSSARY.md`](../../GLOSSARY.md); the hard-to-reverse choices have ADRs in [`docs/adr/`](../adr/). How to run, deploy and upgrade the stack is in [`docs/development/`](../development/).

## Scope

- **Single user**, behind Cloudflare Access. There are no tenants, quotas, or per-user isolation.
- **v1 clients:** an HTTP and WebSocket API and a web UI. A terminal client comes later. Triggers on a Schedule or a webhook (GitHub's included) are designed in [`triggers.md`](triggers.md) and not built yet; Slack triggers come later.
- **Lean on existing packages.** Prefer Earendil (`pi-durable`, `pi-ai`, `pi-codemode`, `pi-mcp` for MCP sign-in only, `pi-telemetry`; the MCP core is the official SDK, [ADR-0036](../adr/0036-the-mcp-core-is-the-official-sdk-inside-cloudpids-own-era-agnostic-module.md)) and Cloudflare (`@cloudflare/computer`, `agents/browser`) building blocks over writing our own.

## Architecture

```
Browser (web UI, PWA) ──Access──▶ Main Worker ──WS─────▶ Session DO (per Session)
                                       │                    ├─ pi-durable Harness (SQLite, prefix pi_)
                                       │                    ├─ browser tool ─▶ Browser Worker (BrowserHost DO per Session → Browser Run)
                                       │                    └─ RemoteCodemodeSandbox ─▶ Codemode Sandbox Worker (DO per Session)
                                       ├──────────────▶ Registry DO (singleton)
                                       ├──────────────▶ McpHost DO (per Environment) ─▶ McpWorker (McpEngine) ─▶ Workspaces (WorkspaceMcpBridge) ─▶ Container MCP bridge
                                       ├──/mcp────────▶ McpWorker (McpServer) ─▶ Registry, Sessions
                                       └──────────────▶ Workspace DO (per Workspace)
                                                            ├─ computer Workspace (SQLite VFS)
                                                            ├─ Worker Shell backend (just-bash, Worker Loader)
                                                            └─ Container backend ─▶ Container (computerd + mise)
```

### Durable Objects

A Session import's pi file is kept in tables of its own beside the Harness's (`import_slices`, `import_state`, made by the import's first call and migrated apart from the Harness's: see [_Session import_](mcp-endpoint.md#session-import)).                                                                                                                                   |
| **Workspace DO**            | `ws:<id>`, the Workspace's id | One `@cloudflare/computer` Workspace and its Container: one Workspace's clones. Its Sessions share it.                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Registry DO**             | singleton                     | Environments, Workspaces and Session listings (title, timestamps, status, subagents), settings overrides, push subscriptions, and MCP sign-ins, client registrations and bindings, sealed (see [_MCP sign-ins_](mcp-sign-in.md#mcp-sign-ins)).                                                                                                                                                                                                                                                                     |
| **MCP host DO** (`McpHost`) | `mcp:<environment id>`        | One Environment's MCP state: its MCP server set, the MCP inventory and its versions, server status, protocol era and Legacy session rows, Resource watches and MCP App HTML. It runs the MCP SDK only through `McpEngine`, a stateless entrypoint of the `McpWorker` Worker, which only `Server` binds ([ADR-0038](../adr/0038-the-mcp-host-object-lives-beside-the-registry-and-runs-the-sdk-through-a-stateless-engine-in-a-worker-of-its-own.md); see [_The host object_](mcp-connections.md#the-host-object)). |
| **Codemode sandbox DO**     | Session DO id                 | QuickJS script execution. It lives in a separately deployed Worker so scripts run in another isolate.                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Browser host DO**         | Session DO id                 | The Session's one Browser Run browser (`agents/browser`) and the runs of the model's CDP code. It lives in the `Browsers` Worker, which binds the `Workspaces` Worker's Container previews entrypoint.                                                                                                                                                                                                                                                                                                             |

The Harness and the Workspace live in separate objects ([ADR-0001](../adr/0001-session-and-workspace-durable-objects.md)). An Environment's Build is made by a Workspace DO of its own, `build:<environment id>` (`buildObjectName`; see [_Builds_](container.md)). The Workspace DO is hosted by its own plain Worker, `Workspaces` (bound as `WORKSPACES`): the Worker Shell reaches the DO through a `WorkspaceServiceProxy` entrypoint the hosting Worker must export (`ctx.exports`), and an alchemy Effect Worker's generated entry exports only `default` and its Effect DO classes. Session DOs bind it across scripts with `Cloudflare.DurableObject("Workspace", { scriptName: Workspaces.workerName })`, the Output and not a literal, so `Workspaces` deploys first; they call it through the raw `DurableObjectNamespace` stub, which `getWorkspace()` and `ComputerExecutionEnv` need. The two Workers deploy separately, so `ComputerExecutionEnv`'s requests to the DO only ever gain operations, never change existing ones. The `Browsers` Worker binds the `Workspaces` Worker too, through a service binding to its `WorkspaceContainerPreviews` entrypoint (`Cloudflare.WorkerEntrypoint`), which offers a Workspace's Container preview and nothing else of the DO ([_Container preview_](browser.md)); the Session DOs and the browser host DOs deploy apart as well, so the host's methods only ever gain trailing optional arguments. `McpWorker` (`apps/mcp-worker`) also serves the MCP endpoint (`/mcp`) through its `McpServer` entrypoint, after the main Worker's Access check, and binds the `Workspaces` Worker's `WorkspaceMcpBridge` entrypoint to reach stdio MCP servers in a Container; the App sandbox Worker, deployed by `prod` only on `ianpascoe.app`, runs App Views (see [_Packages and objects_](mcp.md#packages-and-objects)).

### Session host

The Session DO opens the Harness with `openDurableObjectSqliteStorage(ctx.storage, { prefix: "pi_" })` and wakes itself from its alarm. It follows the pattern in pi-durable's `test-workers/worker.ts`, not Cloudflare's `PiHarness` ([ADR-0002](../adr/0002-own-session-host.md)).

- Arm a 60 s heartbeat alarm while any task is live, a sleeping one included; a blocked task (no definition takes it) and one that waits on others do not count. pi-durable 1.5.0 has `HarnessOptions.onWake` and `Harness.wake()`, but they are not used: `wake()`'s `active` leaves out a sleeping task, which may be a Run's generation sleeping out a retry backoff, so the Session would report itself idle and clear its calls' state mid-Run. Without `onWake` the Harness keeps a timer for the earliest sleep itself, and `resume()` after an eviction wakes a sleep that came due.
- pi-durable 1.5.0 ends a task cut off by a crash, eviction or reset 5 times in a row without committing a new state (`settings.restartLimit`, left at its default), where 1.4 parked it: a tool call ends with an error result ("Tool <name> was interrupted 5 times in a row; it is not run again") and the Run goes on, a generation ends its Run with `pi.live.runFailure` (`restart_limit`), a compaction fails into `compactionFailure`, and a task of an extension's kind ends `faulted`. The Harness's `onReport` gets `task_interrupted` (or `task_faulted`) with the reason `restart_limit`. A task that sleeps between steps (an MCP task's follower) resets its count at each sleep commit. The Harness's `onReport` (a task ended or faulted, a hook or listener that threw) is logged as a warning.
  - **A wait for the owner is progress** ([#647](https://github.com/ian-pascoe/cloudpid/issues/647)). A Session whose calls only wait for the owner does no I/O, so it hibernates, and each heartbeat starts a new instance, which reruns the calls: a restart. A tool call that waits for the owner (an Approval, `secret_ask`, a Sign-in request, a deferred MCP question or a kept Sampling request) marks its wait as progress once the wait is stored and it is about to await (`reachedWait`, over `ToolExecutionApi.progressed`, a cloudpid patch of pi-durable: [_Dependencies_](../development/dependencies.md)). Its restart count then starts over at each rerun, and so do its owners' (a `codemode` call, which waits for its nested call in memory), up to the first that is being aborted, so it waits for the owner however long they take. An attempt cut off before its wait still counts. The cost of the reset: a task above a waiting call whose own code crashes the instance each time is never ended either, and reruns about once a heartbeat until the owner answers or stops the Run.
  - **A tool call the limit ends has its requests withdrawn.** When pi-durable reports a tool call it ended at the limit (`task_interrupted`, `restart_limit`: one cut off 5 times before it reached a wait), the host withdraws the owner requests the call left, and those of the tool calls below it, which its end aborts without running them again (`withdrawCall`: an Approval, Secret request and Sign-in request by the call's task, an MCP server's questions by its tool call), so no answer is taken and then dropped, and a Run that goes on and asks again shows nothing dead. The calls below it have ended by the time of the report (pi-durable aborts them, and waits for them, before it commits the end), so the host reads them as the Harness opens, for each tool call at the limit then: a restart is counted only at an open, and such a call ends when it is next reserved, before it runs again or makes another call. A request the report finds no call for (an instance stopped first) is withdrawn once the Session is idle (`onIdle`). A call an earlier build parked is ended by pi-durable when it next reserves it.
- Arm the alarm before admitting work. Call `resume()` from the constructor and the alarm.
- Long model streams are bound by the platform's wall-time limits. pi-durable resumes interrupted work.

### Effect boundary

Effect is the language everywhere except pi-durable's own core ([ADR-0003](../adr/0003-effect-around-pi-durable.md)).

- Each DO builds its Layers once and keeps a `ManagedRuntime`. Services (`Context.Service`) include `Harness`, `WorkspaceClient`, `Models`, `Settings`, `Secrets`, `Registry`, and `Telemetry`.
- `packages/effect-durable` provides `defineEffectTool` (Effect `Schema` parameters compiled to TypeBox/JSON Schema), `reachedWait` (a call's mark that it reached a durable wait: [_Session host_](#session-host)), `effectHook`, `effectSection`, `frozenSection` (a section read once per context and then shown as it was; its `whenShown` hook runs for each request that finds it already shown), and `effectTask`. Chord `Context` cancellation becomes fiber interruption, and typed failures become tool error results (`effectTask`: the task's `failed` outcome; a defect faults it, as a native throw does). A task's phases run as Effects but still commit their checkpoints through `runtime`. Its `/sqlite` export is `migrate`, the versioned SQLite schema every Durable Object with tables runs from its constructor, and `/sqlite/testing` is `refusingStorage` (a replaced instance's storage) and the shipped-migration check ([`workers.md`](../development/workers.md#deploys-and-durable-object-code-updates)).
- Harness internals, commits, documents, and task phases stay native. Effect reaches them through thin facades (`Effect.tryPromise`), never a parallel scheduler.

### Models

- Requests go to the existing proxy `api.ai.ianpascoe.dev` with a Commissary API key, sent as each provider's native API key (`x-api-key` for Anthropic). The proxy is Commissary's API host, which sits outside Cloudflare Access and rejects service tokens. Model IDs match `~/.pi/agent/models.json`.
- Default `anthropic/claude-opus-5-5` at `high` thinking.
- Roles: `small` haiku-5-5, `medium` sonnet-5-5, `large` opus-5-5, `xlarge` fable-5-1, with the hints from `~/.pi/agent/settings.json`.

### Settings

- A typed Effect `Schema` with defaults in `packages/config`: every field has a decoding default, so decoding the overrides gives the resolved settings, and the schema's `Encoded` side is the overrides' shape (a deep partial that rejects unknown keys). Invalid overrides fail with one readable line per problem.
- They are kept at two Scopes ([ADR-0027](../adr/0027-settings-at-two-scopes-with-explicit-overrides.md)). **Global**: a Registry DO document (the `documents` table, named `settings`), editable in the UI in Global's General, Instructions, Models, Tools and Limits sections of the Settings page (`/settings/all/<section>`; see [_Client and protocol_](client-and-protocol.md) → Settings page) over `getSettings`/`updateSettings`. The document is added by a Registry migration (the `documents` table). A write is strict and keeps only what differs from the defaults, so a setting left alone follows later default changes; a read is lenient: saved overrides that no longer resolve (a model a release dropped) are left out one by one and listed in `problem`, and the rest still apply. `getSettings` also answers, for each field, the Environments that override it (`overriddenIn`). **An Environment**: its Settings Overrides, in its row (`environments.settings_overrides`, Registry migration 27; none for an Environment stored before, which inherits Global whole), over `getSettingsOverrides { environment }` (its `overrides`, the Global settings it inherits as `global`, and the two resolved as `settings`) and `updateSettingsOverrides { environment, set?, reset? }`. An Override is explicit: exactly the fields set on purpose, even one equal to the Global value (it is then pinned, and Global's later change does not reach it), until a reset removes it. `set` is a deep partial merged field by field; `reset` names fields. The fields (`packages/config/src/settings-overrides.ts` → `overrideFields`, also the Agent changes' fields) are `model`, `thinkingLevel`, each Role (`roles.<name>`, its model and hint as one value: one set in part is completed from the Role in force), each compaction setting (`compaction.enabled`, …), `tools.offered` (the list replaced whole), `spendLimit.perSession` (an Override of null is no limit for the Environment), `branchSummary.skipPrompt` and each extension option (`extensions.<extension>.<key>`; null resets it). The Instructions are no Override field: they add up rather than being replaced (ADR-0027; `INSTRUCTIONS_ROOT` in `settings-overrides.ts`), so an Environment's settings carry Global's, and Overrides that hold `instructions` are refused on a write and left out, listed in `problem`, on a read. An Environment's own Instructions are kept beside its Overrides, in its row (`environments.instructions`, Registry migration 28; empty for none, and deleted with the Environment), under the same 64 KiB cap: `getSettingsOverrides` answers them as `instructions`, and `updateEnvironmentInstructions { environment, instructions }` replaces them whole, refusing more than 64 KiB. Its Sessions are shown Global's, then these (see [_Instructions_](workspace.md)). A write is checked strictly over Global; a read is lenient: an Override that no longer resolves is left out, its field inheriting Global, and listed in `problem`. The renamed-tools fix-up (`restart_container` read and saved as `container_restart`) applies at both Scopes.
- **Resolution**: an Environment's settings are its Overrides over Global over the defaults (`resolveOverridesLeniently`). Each Session reads what it resolves from the Registry (`sessionSettings { session }`: Global's overrides, its Environment's Overrides, and the Environment's name with its own Instructions) when a client connects and before it admits input (outside the alarm lock, and not again for 30 s after a failed read), and keeps the last read in its own storage (`settings-source`, the Environment's Instructions with it; a Session that kept only Global's overrides before Overrides existed, `settings-overrides`, starts from them as before), so a change at either Scope applies to the next request of new and idle Sessions without a redeploy and is what a client first sees, and a Registry that is down never stops one. Its subagents run with the same settings: they share the Session's Environment. Two Sessions in different Environments can run with different models, offered tools and spend limits. The web app's branch summary prompt reads the shown Session's Environment's settings. A default changed during a Run reaches the Run from its next provider request, as a pick does. The Harness's `compaction` is a getter over that copy. The default model and thinking level are written to the root conversation's agent before each request unless the Session picked its own (see `configure`); a pick of a model the settings no longer accept is ignored.
- They cover models, roles, thinking level, compaction, the offered tools (`tools.offered`, see [_Tool discovery_](agent-capabilities.md#tool-discovery)), the spend limit (`spendLimit.perSession`, US dollars, off by default; see [_Operations_](operations.md) → Telemetry), whether a move in the Session tree asks about a branch summary (`branchSummary.skipPrompt`, off by default; see [_Session tree_](client-and-protocol.md)), the MCP servers (`mcp.servers`, keyed by name; an Environment overrides one whole or by an MCP server adjustment; see [_Scopes, adjustments and the set_](mcp-configuration.md#scopes-adjustments-and-the-set)), the owner's **Instructions** (`instructions`, Markdown of at most 64 KiB of UTF-8, refused above, as an `AGENTS.md` is cut at 64 Ki characters; empty by default; every conversation's model is shown them as a frozen system prompt section before `project_context`: see [_Instructions_](workspace.md)), and extension options. A Workspace's Container size, size limit, idle time, extra Container-only paths, variables and Setup and Start Scripts are not in this document: they are its Environment's settings, kept in the Registry with the Environment (see [_Container settings_](container.md)).
- **The agent changes them too** (ADR-0019, ADR-0027, [_Agent changes_](agent-changes.md)): the `settings_*` tools change the model and thinking level, the roles, the offered tools, compaction, the branch summary prompt and extension options, each at a `scope` the agent must name (`*` for Global, or an Environment's id), and `settings_reset` resets a field (an Environment's Override removed, or Global's back to its default). Each change is checked and written as `updateSettings` or `updateSettingsOverrides` is, recorded with its reason under the Scope, listed with a revert in the Scope's Agent changes section of the Settings page, and reaches the next provider request of the Sessions that run with it. The Limits (`spendLimit.perSession`, `subagents.maxSubagentDepth`, `subagents.maxSubagentWorkspaces`) change only with the owner's Approval, at either Scope, set or reset (`settings_spend_limit_set`, `settings_subagent_depth_set`, `settings_subagent_workspaces_set`, `settings_reset`: [_Approval_](agent-changes.md#approval)), and so do the Instructions, Global's or an Environment's own (`settings_instructions_set`; `settings_reset` does not take them). `settings_get` shows the Instructions whole. The `settings_mcp_*` tools change the MCP servers, a definition or a widening only with the owner's Approval (see [_The agent's changes_](mcp-configuration.md#the-agents-changes)).

## Repository layout

The repo is a Turborepo with Bun workspaces ([ADR-0028](../adr/0028-bun-for-installs-and-scripts-and-tsrs-for-typecheck.md)). Internal packages are just-in-time: `exports` point at `src/*.ts`, and the Workers' bundlers compile them.

```
infra/                    alchemy stack (alchemy.run.ts): Workers, DOs, Container, Access, secrets
apps/server/              main Worker: Session, Registry, McpHost DOs; HTTP/WS API; static assets.
                          Workspaces Worker (src/workspace): Workspace DO
apps/codemode-sandbox/    codemode sandbox Worker
apps/app-sandbox/         App sandbox Worker (public, prod only): the MCP App proxy page on *.ianpascoe.app
apps/browser/             browser Worker: BrowserHost DO (agents/browser on Browser Run), ContainerPreviews entrypoint
apps/mcp-worker/          McpWorker: McpEngine (the MCP SDK, stateless) and McpServer (the MCP endpoint, /mcp)
apps/web/                 Vite + React UI
apps/sandbox-image/       image/Dockerfile (computerd, mise, preinstalled Toolchains, C toolchain; the Docker build context), base mise.toml, bootstrap
packages/effect-durable/  Effect ↔ pi-durable adapters and service facades
packages/computer-env/    ComputerExecutionEnv
packages/extensions/      one subpath export per extension (/subagents, /context, /todo, /web, /secrets, /browser, /visuals, …)
packages/protocol/        Session socket messages, RegistryRpcs, conversation-view projection and transcript
packages/config/          settings Schema and defaults, model roles, shared tsconfig and vitest bases
packages/mcp/             @cloudpid/mcp: the era-agnostic MCP core over the official SDK; ./types, ./oauth
packages/pi-cloudpid/     /cloudpid, the pi extension on the owner's machine for a Session import
```
