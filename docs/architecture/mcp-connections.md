# MCP: connections, the host object, the engine and stdio

One Durable Object per Environment owns its MCP servers, and a stateless engine in a Worker of its own does the protocol work for it ([ADR-0038](../adr/0038-the-mcp-host-object-lives-beside-the-registry-and-runs-the-sdk-through-a-stateless-engine-in-a-worker-of-its-own.md)). Stdio servers run in the calling agent's Workspace Container behind a bridge that serves each one as Streamable HTTP. Exhaustive detail is in [The Environment's MCP host object: what it owns and its RPC](https://github.com/ian-pascoe/cloudpid/issues/382) and its amendment comments; a bare D-number in this document is that ticket's. "MCP host object" and "MCP engine" are implementation words, not GLOSSARY terms: the owner never sees them, and the spec's "host" is the whole application (D14.1).

## The host object

- **Identity:** `McpHost`, an Effect Durable Object named `mcp:<environment id>`, in `Server` beside the Registry and the Session DOs (`apps/server/src/mcp/`, `McpHostLive` beside `SessionLive` and `RegistryLive`). It holds all MCP state and policy and imports only `@cloudpid/mcp/types`, never the SDK (the import rule and its bundle test: [_Packages and objects_](mcp.md#packages-and-objects)).
- **Runtime:** one `ManagedRuntime` per instance over `McpHostStore`, `McpEngineClient` (over the `MCP_ENGINE` binding, or a fake), `McpRegistryPort` (the Registry, or a fake), `Clock` and `Telemetry`. The inventory, the scheduler, watches, App HTML and the caches are internal modules, not services. Background work (discovery, refreshes, listens, gap checks) runs as in-memory fibers in that runtime (D7.5, D13.1).
- **No alarm:** the object never arms one, since an alarm would wake idle Environments and bill duration. Retries are demand-driven (see [_States_](#discovery-and-the-mcp-inventory)), watch expiry (7 days without a request) is swept at every `requestStart` and `apply` before the caps are checked, and inventories, App HTML and stdio session rows are pruned at writes. A Legacy `DELETE` is best effort and never retried (D10.3).
- **Never woken without MCP servers:** a Session whose `sessionSettings` says `mcp: { servers: 0 }` and that holds no Resource watch skips `requestStart`, and an empty set is pushed only to an Environment whose previous set was not empty (D2.1; [_From the Registry to the host_](mcp-configuration.md#from-the-registry-to-the-host)).
- **Nothing Global:** each Environment's object connects to a Global MCP server on its own, since `${NAME}` resolves per Environment (D2.3). MCP sign-ins are the exception, kept Global in the Registry ([_MCP sign-ins_](mcp-sign-in.md#mcp-sign-ins)).
- **Destroy:** deleting an Environment (`registry/removal.ts`) ends with the Registry noting its host to be wiped, only if the host was ever handed a set; the main Worker's next sync, whatever it is for, sends `apply({ kind: "destroy", revision })` and tells the Registry once it was done ([_From the Registry to the host_](mcp-configuration.md#from-the-registry-to-the-host)). The host aborts calls, makes a best-effort Legacy `DELETE` within 2 s, closes streams, and calls `deleteAll()` (the tables are made again empty, with `revision` kept in `mcp_wiped` as the floor of what may fill it again); the first slice has only the storage to wipe. A wipe the storage refuses answers `HostFailed`, and the Registry sends it again. The Environment's MCP sign-ins stay in the Registry, listed as unused (D2.2).

## Storage

- **Connection key `conn`:** SHA-256 over the canonical `{ source, normalized name, type, url, headers, oauth, command, args, env, cwd }`, with `${NAME}` unresolved, so no Secret enters a hash. It is a pure, synchronous function in `@cloudpid/config`, beside `resolveMcpServerSet` (`mcpConnectionKey`). `source` is `owner` (Global's and an Environment's own entries) or `repo:<owner/repo>`; the name is normalized (lower case, `-` as `_`); `type` is `stdio` or `http` (`streamable-http` is `http`); the `url` is `new URL(url).href` without its fragment; `oauth` leaves out `callbackPort` and `callbackUrl`, which are ignored; every key is read with its defaults, so an empty `args` and none are one connection. Every other key (`description`, `timeout`, `enabled`, `sampling`, `exposure`, `toolExposure`) is left out: editing it bumps the inventory's version but never reconnects or re-probes (D3.1). The era cache, the inventory, status and Legacy session rows all key by `conn`, never by the Registry's per-entry hash. Beside it, `mcpServerIdentity` is SHA-256 of `{ source, normalized name, type, url }`, which MCP tasks use to tell a re-pin from a new server ([MCP tasks as durable long-running requests](https://github.com/ian-pascoe/cloudpid/issues/389) D16).
- **Tables** (SQLite through `migrate`, which lives in `@cloudpid/effect-durable/sqlite` for the Registry and `McpHost` both (it moved there from `apps/server/src/registry/store.ts`; each object's migrations have a shipped-digest manifest, [_Deploys_](../development/workers.md#deploys-and-durable-object-code-updates)); migrations only add; D3.2, D3.6):

  | Table                                                                                   | Holds                                                                                                                                   | Bounds and retention                                                                                                                           |
  | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
  | `mcp_meta`                                                                              | `set_hash`, `revision`; later slices add `version`, `prompts_version`, `last_used_at` and `sign_ins_revision`                           | —                                                                                                                                              |
  | `mcp_wiped`                                                                             | `revision`: the revision the host was wiped at, one row once it was                                                                     | a set no newer than it is refused                                                                                                              |
  | `mcp_servers(name, entry_hash, conn, entry_json, position)`                             | the MCP server set as received; `entry_json` is `{ source, server, identity }`, the entry in force with `${NAME}` unresolved            | the set's own bounds ([_Entries_](mcp-configuration.md#entries))                                                                               |
  | `mcp_inventories(conn, part ∈ tools \| prompts \| meta, json, hash)`                    | `meta`: protocol version, `serverInfo`, `instructions` (≤16 KiB), capabilities, `discovered_at`, `discovered_in`, `ttl_until`, problems | rows of a `conn` that left the set kept 30 days, at most 20 such `conn`s, pruned at each set apply, so a revert reuses its inventory           |

- **Format `v` on `prior` rows:** era and Legacy session rows cross the engine edge as `prior`, so each carries a format `v`, and an engine that does not know a row's `v` treats it as absent (probes or initializes again). The host's own tables stay additive-only with fallback members, without a `v` ([_Deploys_](mcp.md#deploys); [Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423) D3.4).
- **Memory only** (D3.3): access tokens; resolved `${NAME}` values (asked again at the first use 60 s after the last answer, served stale while refreshing; [_`${NAME}` values_](mcp-configuration.md#name-values)); the resources list cache (LRU, 4 MiB per object and 8 MiB per isolate; [_Resource tools_](mcp-in-a-session.md#resource-tools)); the log ring; single-flight, holds and in-flight calls.
- **Kept elsewhere** (D3.4): the Session keeps `ResumeState` and MCP task ids (the host keeps no task state and lists no tasks); the bridge keeps stderr tails; the Registry keeps MCP sign-ins.
- **Versions are content hashes, not counters** (D3.5): `version` is 128 bits of SHA-256 over the canonical tools projection, covering per server the config that shapes tools, a coarse state (has an inventory | connecting | sign-in), `instructions`, tools, per-tool problems and the resources capability. `promptsVersion` covers prompts and their problems, so a prompts-only change never reinstalls the `mcp` extension. Each server also gets a `toolsHash` and a `promptsHash`. A flip back brings the old version back, and the Session builds only from stored canonical JSON, so a reinstall over unchanged tools is byte-identical (what the Session does with them: [_The prompt cache and the `mcp_servers` section_](mcp-in-a-session.md#the-prompt-cache-and-the-mcp_servers-section)).

## RPC

- **Four methods** on `McpHost`, typed with Effect Schemas in `@cloudpid/mcp/types`, failures returned as values (D6.1, amended by [Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423) for `features`):

  | Method         | Arguments                                                                                                                                     | Returns, and what it does                                                                                                                                                                                                                                                                                                          |
  | -------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `requestStart` | `{ caller: { session, conversation, workspace }, windowOpened? }`; `known`, `waitFor` and `waitMs ≤10 s` come with the inventory (#449)       | `{ version, promptsVersion, features, servers: { [name]: { toolsHash, promptsHash, state } }, watches: { changed, ended } }`. Marks the conversation active, sweeps watch expiry, starts due refreshes, reopens watched streams with gap checks, and asks the Registry for the set when `windowOpened`.                            |
  | `servers`      | `{ names?, parts: ("tools" \| "prompts" \| "instructions" \| "status")[], waitMs?, workspace? }`                                              | Per server: config, state, error, negotiated protocol version, where and when discovered, counts, and the parts asked for. Serves the `mcp` extension's inventory reads, `serverStatus`, `settings_mcp_list`/`get`, the composer and Settings. Never starts a Container.                                                           |
  | `request`      | `{ op, server?, params, ctx: { callId?, origin, session?, conversation?, workspace?, start?, timeoutMs?, answers?, allowTask? } }` plus hooks | `op` is `tools/call`, `prompts/get`, `resources/read`, `resources/list`, `resources/templates/list`, `completion/complete`, `resume`, `tasks/get` \| `tasks/update` \| `tasks/cancel`, or `ui/html`. Errors are the core's tags plus `NotRunning`, `NotAllowed`, `UnknownServer`, `ServerChanged`, `Cancelled`, `HostUnsupported`. |
  | `apply`        | `set` \| `sign_ins` \| `reload` \| `end_watches` \| `destroy`                                                                                 | The pushes and teardown.                                                                                                                                                                                                                                                                                                           |

- **`apply` answers as a value:** `Applied { hash, changed }`, `Stale { hash, revision }` for a set whose `revision` is below the one the host holds, or no newer than the one it was wiped at, `hash` then empty (the host keeps what it has, and answers with it), `Destroyed` for `destroy`, `HostUnsupported { message, op }` for a `kind` this build does not know, or `HostFailed { message, tag? }`, the fallback every other failure reads as; the caller reads an answer it cannot place as `HostFailed` (`readMcpApplyResult`). A set is stored whole with its `revision` (`mcp_meta`), an empty one too; the same hash under a newer revision only raises the revision.
- **Placeholders before the inventory (#449):** until it exists, `requestStart` answers `version` as the held set's hash, `servers: {}` and `promptsVersion: ""`, and takes `windowOpened` as a boolean; `known`, `waitFor` and `waitMs` are not arguments yet.
- **`features`:** `requestStart` lists what the host supports; a Session uses a feature only once it is listed, and rebuilds `mcp` when the features its tool declarations used change (the gate: [_Deploys_](mcp.md#deploys)).
- **Callbacks, Session → host → engine** (D6.2): a server's questions, progress and logs reach the Session only through hooks passed down the call; nothing ever calls a Session. The hooks are `onInput` (questions; `ctx.answers` says which kinds the caller can answer, and `capabilities(ctx)` declares only those), `onInputComplete({ key })` (a `notifications/elicitation/complete` on the call's own POST stream; completions on the GET stream are ignored), `onProgress` (at most 10/s), `onLog`, and `untilAborted()`, a pending callback that resolves on an abort and rejects if the caller dies, since RPC carries no `AbortSignal`. Either way the engine aborts the server request (Legacy `notifications/cancelled` and stream close; Modern stream close; through the bridge, a cancel of the child's request). A Modern question's `ResumeState` goes back to the Session as `input_required`, and the host keeps nothing; MCP tasks work the same way ([_Questions_](mcp-server-requests.md#questions)). A stub lives only as long as the invocation that made it, so the Session awaits the call for its whole length ([_RPC edges_](mcp.md#rpc-edges)).
- **Additive fields from other areas:** stdio `request` results carry the bridge's `spawn`; an answer carries the `conn` shown on its card, and the host refuses one whose `conn` differs (`ServerChanged`, nothing sent) ([Elicitation in form and URL modes as durable requests](https://github.com/ian-pascoe/cloudpid/issues/388) D13, D15); `tasks/*` requests carry `server`, `tool` and the pinned `conn`, results carry `spawn` and the MCP sign-in id, `tasks/cancel` is allowed for a server switched off, and `ServerChanged` carries the name's current `conn` and `mcpServerIdentity` ([MCP tasks as durable long-running requests](https://github.com/ian-pascoe/cloudpid/issues/389) D4.3, D16). A `resources/read` with `watch: true` whose watch row could not be kept returns its content with the watch not started ([Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423) D3.2).
- **Pushes:** the Registry never calls out, so the main Worker (owner Settings saves, `addRepo`/`removeRepo`, a Repo Reload, an MCP sign-in's callback, sign-out or rebind, from the Registry's answer) and the Sessions (`settings_mcp_*`, watch ends) carry its changes to `apply`. A lost push heals at the next `windowOpened`, which passes the hash the host holds and is answered with the current one and `signInsRevision`, 0 until sign-ins exist (D6.3; [_From the Registry to the host_](mcp-configuration.md#from-the-registry-to-the-host), [_Tokens reach the host object_](mcp-sign-in.md#tokens-reach-the-host-object)).
- **Host → Registry** (same script; D6.4): `mcpServerSet({ environment, heldHash }) → { hash, signInsRevision, set?, revision? }`, which runs the Registry's 10-minute look at Repos' `.pi/mcp.json`; `mcpServerValues({ environment, server, conn })`, resolving `${NAME}` against Secrets then Variables (Variables only for a Repo's entries), never logged, and answering `{ status: "values", env, headers, missing }` (a name that resolved to nothing stays as written and is listed in `missing`), `{ status: "unknown_server" }` or `{ status: "server_changed", conn }`, with a fallback for a status this build does not know; and `mcpAccessToken` and `reportMcpAuth` ([_Tokens reach the host object_](mcp-sign-in.md#tokens-reach-the-host-object)).
- **For the UI,** through `RegistryRpcs` (D12.3; the UI itself is left for later, the map's "MCP status in the UI"): `mcpServers({ environment })` → the servers with status, tools and prompts, to which the main Worker adds Exposure with the pure resolver; `mcpServerLog({ environment, server, workspace? })` → the log ring plus the stderr tail from `bridge_status`, never starting a Container; `mcpReconnect` → `apply({ kind: "reload", servers })`. Sign-in controls stay the Registry's.
- **The Session side** (D13.3): a `McpHostClient` service with the four methods, used by `@cloudpid/extensions/mcp` and `@cloudpid/extensions/settings-mcp`; the live adapter is `apps/server/src/session/mcp.ts`, with an in-memory fake for tests. It calls `McpHost` through alchemy's Tag, which passes function and `RpcTarget` arguments as native stubs, turns a dead host into `RpcCallError`, and hands a returned `ReadableStream` to the caller as an Effect `Stream` ([Verify MCP host ↔ engine RPC on a deployed stage](https://github.com/ian-pascoe/cloudpid/issues/409) answer 5).

## The engine

- **`McpWorker`** (`apps/mcp-worker`, `@cloudpid/mcp-worker`): a plain async Worker, `workersDev: false`, no routes, no `nodejs_compat`. It exports `McpEngine`, a stateless `WorkerEntrypoint` running `@cloudpid/mcp`; `McpServer`, cloudpid's own `/mcp` ([_The handler_](mcp-endpoint.md#the-handler)); and a default that answers 404. It binds `MCP_BRIDGE` = `Cloudflare.WorkerEntrypoint(workspaces, "WorkspaceMcpBridge")`; `Server` binds `MCP_ENGINE` and `MCP_SERVER` through Outputs. Deploy order is Workspaces → Browsers / CodemodeSandboxes / McpWorker → Server (E1).
- **Interface** (`McpEngineMethods` in `@cloudpid/mcp/types`; D1): `discover(target, prior, hooks)`, `request(target, prior, req, hooks)`, `listen(target, prior, filter, hooks)` (an event stream of newline-delimited JSON), and `control(target | workspace, "bridge_status" | "bridge_stop" | "session_delete")`. Each returns its result plus `state: { era?, session? }` (null means drop), which the host stores. `target` carries `conn`, the name and the timeout, plus the URL and resolved headers for HTTP, or `workspace`, `start` and the resolved `env` for stdio.
- **Hooks** besides the Session's: `auth(stale)`, through which the host asks the Registry's `mcpAccessToken`, so tokens never reach a Session, a Workspace DO or a Container; and `opened()`, called when response headers arrive, so the host keeps the core's outbound queue of 5 across engine calls.
- **Built so far** ([#447](https://github.com/ian-pascoe/cloudpid/issues/447)): `discover` and `request` for HTTP targets, with `tools/call` and the list `op`s; `listen`, `control`, stdio targets, `McpServer`, `MCP_SERVER` and `MCP_BRIDGE` come with [#451](https://github.com/ian-pascoe/cloudpid/issues/451), [#448](https://github.com/ian-pascoe/cloudpid/issues/448) and [#460](https://github.com/ian-pascoe/cloudpid/issues/460). An `op` this engine does not know fails as `Unsupported`, sending nothing.
- **Stateless:** each call rebuilds the SDK client with `connect(target, deps)` from `prior` and the hooks, and keeps nothing between calls. One `ManagedRuntime` per isolate holds the byte budget, the validator cache and `Telemetry` (D13.2).
- **Aborts:** each call races `untilAborted()`, which resolves when the caller aborts and rejects when it dies; either way the work is interrupted, which aborts the server request (a Legacy server gets `notifications/cancelled`), and the call fails as `Cut { mayHaveRun: true }`.
- **`-32020`:** a `tools/call` whose headers the server rejects lists the server's tools again and is sent once more with the fresh definition; the result carries the fresh `tools` for the host's catalog. The server refused the first before running it, so the call runs at most once.
- **`ctx.waitUntil`:** the engine holds each call's work under `this.ctx.waitUntil(…)` as well as returning it. Without it, a dead host's call is cancelled silently with its fetches, and a Legacy server or the bridge is never told; with it, `untilAborted()` rejects at once and the engine sends its cancel ([#409](https://github.com/ian-pascoe/cloudpid/issues/409) answer 2).
- **Load caps** (D7.3, D8): ≤8 requests in flight per HTTP server, ≤4 per (stdio server, Workspace), ≤32 per host object; requests over a cap wait FIFO, and the wait counts toward their timeout. The outbound queue of 5 serves calls first; background work takes at most 3 of its slots. The Workers limit of six connections waiting for headers applies to the engine's own `fetch`es only: RPC (Session → host, host → engine) neither counts toward it nor queues behind it ([Verify MCP host ↔ engine RPC on a deployed stage](https://github.com/ian-pascoe/cloudpid/issues/409) answer 7).
- **Memory** (D9.1): per `McpWorker` isolate, 24 MiB of counted bytes in flight, one large slot for a single body over 4 MiB (up to 16 MiB) and an 8 MiB pool for bodies of 4 MiB or less; waiting is backpressure upstream (peak about 3 × 24 MiB plus ~20 MiB of SDK, under 128 MB). Each call holds one lease, grown as its `fetch`es count bytes (moving to the large slot past 4 MiB) and given back when the call ends, or for a large result once its stream is read; a Legacy GET stream is capped per event instead. The permits are plain Promises, not an Effect `Semaphore`: a stateless isolate's waiter must be woken by the releasing call itself, and an Effect wake-up scheduled on a timer belongs to an invocation that may already have ended.
- **Large results** (D9.2): a result over 1 MiB passes engine → host → Session as a byte `ReadableStream` that the engine produces on pull; the host returns it unchanged, unread and never as an Effect `Stream` ([_RPC edges_](mcp.md#rpc-edges)). The engine scrubs the access-token echo and validates `structuredContent` before serializing; the Session takes one slot per isolate to decode a result over 4 MiB, and spills large ones to the Workspace ([_Calls and results_](mcp-in-a-session.md#calls-and-results)).
- **Validation and compiling:** output validation runs in the engine (D9.3; the rule is [The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D17's: `structuredOutput: valid | invalid` with the first errors). TypeBox compiles at discovery only, in the engine, through its interpreted fallback, cached by schema hash (2,000 entries), yielding between schemas (a Worker's clock stands still while it computes, so it cannot measure ~20 ms); nothing compiles at module scope.

## Discovery and the MCP inventory

- **What discovery does** (D7): the cached era (or a probe), connect, `tools/list` and `prompts/list` within their bounds, record the resources capability, compile schemas, store, and recompute the versions. It is single-flight per `conn`, ≤3 at once per object and ≤2 stdio per Workspace, and the version bumps only when content changes.
- **The era probe and cache:** the probe runs at first discovery; its outcomes, the cache's lifetime and what drops it are in [_Protocol eras_](mcp.md#protocol-eras). Beyond those: 5xx or a network error makes the server `unavailable`; a cross-origin redirect, a non-`insufficient_scope` 403 or a 2xx that is not JSON-RPC makes it `failed`; 202 or an empty stream runs to the probe's timeout; 401 and 403 `insufficient_scope` follow [_Requests and Legacy sessions_](#requests-and-legacy-sessions) ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D2). `mcp_eras` rows are fed to the engine as `prior`, and `reload` drops them as a `conn` change does.
- **Bounds and problems:** per server ≤500 tools and ≤1 MiB of declarations (in list order; the rest dropped with a problem), descriptions cut at 4,000 characters, `instructions` ≤16 KiB, ≤100 prompts and ≤64 KiB of prompt metadata; a schema TypeBox rejects, an invalid `x-mcp-header`, or `execution.taskSupport: "required"` makes a per-tool problem (which of these still registers the tool: [_Exposure_](mcp-in-a-session.md#exposure); prompt problems: [_The `/` menu and the catalog_](mcp-in-a-session.md#the--menu-and-the-catalog)).
- **Set changes, per name** (D7.1):
  - **a new `conn`:** an HTTP server is discovered at once if the object was used in the last 24 h, else at first demand; a stdio one at first demand. A kept inventory for that `conn` is served at once.
  - **a changed or removed `conn`:** abort its calls (`ServerChanged`), a best-effort Legacy `DELETE`, `bridge_stop` with `start: false`, close streams, end its Resource watches ("server changed"), then rediscover. A kept MCP sign-in for (source, name, URL) applies again at once ([The agent's changes to MCP servers](https://github.com/ian-pascoe/cloudpid/issues/391) D8).
  - **switched off or `hidden`:** close the connection and streams, end watches, keep the inventory.
  - **only keys outside `conn`** (`description`, `timeout`, `enabled`, `sampling`, `exposure`, `toolExposure`): a version bump, with no reconnect or re-probe.
- **Other triggers** (D7.2): first use; `list_changed` refreshes that one list; TTL (Modern `ttlMs` capped at 24 h, Legacy 10 min), checked on read, serving the stale list while it refreshes; `reload` (`settings_mcp_reload`, `mcpReconnect`) drops eras and Legacy sessions, then rediscovers HTTP servers at once; an MCP sign-in change (`signed_in`, `replaced`, `rebound`) rediscovers `sign_in` and `rejected` HTTP servers at once, with no Container; `signed_out` follows [_Sign-out_](mcp-sign-in.md#sign-out).
- **States** (D7.4):
  - `connecting`: one older than 120 s at wake returns to its previous state with no backoff.
  - `sign_in`: waits for an MCP sign-in change; calls fail fast with no network call.
  - `unavailable`: demand-driven backoff of 30 s, 1, 2, 5, then 10 min; a call still tries at once.
  - `failed`: no automatic retry; a set change, reload, sign-in change or call retries it, at most once a minute per server. An inventory it already has is kept.
  - Left to implementation: the full list of `state` values. The sources also name a connected state and `rejected` (a second 401 with a fresh token), and `settings_mcp_*` reports `connected`, `needs_sign_in`, `failed` or `connecting` ([_Results_](mcp-configuration.md#results)); every state gets a fallback member ([_Deploys_](mcp.md#deploys)).
- **The first request's wait:** a server with an inventory is never waited for. `requestStart` waits ≤10 s (`waitFor`, `waitMs`) only for servers with none yet whose Exposure can yield `direct` tools, and the wait ends for a server at `sign_in`, `unavailable` or `failed`; the rest discover in the background ([MCP tools in a Session](https://github.com/ian-pascoe/cloudpid/issues/381) D7).
- **Stdio discovery** runs in the calling agent's own Workspace Container (a subagent's Subagent Workspace included), never `build:<env>`; the inventory is per Environment by `conn`, so every Workspace's Sessions share it (D4).
- **Who may start a Container** (D4.1, D11.3): only a `workspace` a live caller supplied. `requestStart` finding no inventory for a stdio `conn` (any Exposure) and `request` (calls, prompt gets, the agent's reads, Attached resource reads) may; `servers({ waitMs })`, completions (`not_running`), previews, gap re-reads, listens, Settings and composer reads never do, and every background request uses `start: false`. TTL refreshes and `list_changed` use only a running process.
- **Stdio rediscovery is narrow** (D4.2): no inventory yet; a set change or reload; `list_changed` from any process on any stream; TTL from a running process; `-32602` for an unknown tool. When two Workspaces' processes of one stdio server list different tools, the latest discovery wins (a known limit).

## Requests and Legacy sessions

- **One connection** per HTTP server, or per (stdio server, Workspace).
- **Legacy sessions** ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D5, D15): a row per connection holds `{ sessionId, protocolVersion, serverInfo, capabilities, instructions, initializedAt }`. On wake the engine rebuilds the transport with `sessionId` and `protocolVersion`, so the SDK skips `initialize`; the resumed client has no capabilities, so the core serves them from the row and runs with `enforceStrictCapabilities: false`. The GET stream is not resumed: the span without it is a gap ([ADR-0032](../adr/0032-a-resource-watch-is-held-while-its-conversation-runs-and-checked-by-re-reading-after-every-gap.md)). A 404 on a known session drops it, initializes fresh and resends once, `tools/call` included (the request never reached the server); a second 404 is `failed`. On a Modern server a 404 is an era drop instead. A session whose declared capabilities differ from what the entry now asks (a `sampling` change) is re-initialized at its next use, with `conn` and the inventory unchanged ([Sampling](https://github.com/ian-pascoe/cloudpid/issues/387) D2.4).
- **Remote Legacy SSE resume:** decided as kept, with the server's `retry` clamped to 0.5–10 s, and the request aborted after 2 resumes fail in a row; not built yet. Every connection, Legacy included, uses `maxRetries: 0`, so a Legacy request stream that ends without its answer is a `Cut` ([_Packages and objects_](mcp.md#packages-and-objects)).
- **Timeouts** ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D15):

  | Request                                               | Timeout                                                                                                                                   |
  | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
  | probe or `initialize`                                 | 15 s                                                                                                                                      |
  | through the bridge (Container start, spawn and probe) | 60 s                                                                                                                                      |
  | a list                                                | 30 s a page, 120 s a walk                                                                                                                 |
  | `tools/call`                                          | the entry's `timeout` (default 60 s), reset on progress, enforced in the host; the Session's RPC wait is capped at the timeout plus slack |
  | `resources/read`, `prompts/get`                       | 30 s, or the entry's lower `timeout`                                                                                                      |
  | `completion/complete`                                 | 5 s                                                                                                                                       |
  | listen ack                                            | 10 s                                                                                                                                      |
  | `tasks/*`                                             | 30 s each                                                                                                                                 |

  A call's timeout pauses while a Legacy question on it waits for the owner ([_Questions_](mcp-server-requests.md#questions)).

- **Byte limits** (D16), counted in the `fetch` wrapper over the raw body or the whole SSE stream as bytes arrive; a `Content-Length` over the limit aborts before reading: 16 MiB for `tools/call`, `tasks/get`, `resources/read`, `prompts/get` and each list page; 1 MiB for `completion/complete`, `server/discover`, `initialize` and each event on a listen or GET stream. A `tools/call` over the limit is an error result, never truncated: "over 16 MiB and dropped; the tool may have run" (`details.error: "too_large"`).
- **Tokens and 401/403 at the connection** ([Signing in to remote MCP servers](https://github.com/ian-pascoe/cloudpid/issues/390) D1.9, D1.10, D6, D7.2): before connecting an OAuth-capable HTTP server the host asks `mcpAccessToken`; `required` or `unavailable` makes the server `sign_in` or `unavailable` with no tools and no network call. A 401 at `initialize` or `server/discover` without a token makes it `sign_in`, with no retry. A 401 with a token asks again with `stale` and retries once; a second one is reported `rejected`, tokens kept. 403 `insufficient_scope` fails the call and reports `step_up`. A 401 on an entry with an `Authorization` header is `failed`, never `sign_in`. The token cache, resource binding, `redirect: "manual"` and `[REDACTED]` are in [_Tokens reach the host object_](mcp-sign-in.md#tokens-reach-the-host-object); what a sign-out closes is in [_Sign-out_](mcp-sign-in.md#sign-out).
- **Listens** ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D12): at most one `resources/subscribe` set or `subscriptions/listen` per server, carrying the list-change flags the host wants (it never opens one for prompts alone); a filter change opens the new listen and closes the old once acknowledged, so two may be open. The core never reconnects a listen or GET stream: every end is `remote`, a gap the host handles by reopening and gap-checking at the next `requestStart` of a watching conversation ([ADR-0032](../adr/0032-a-resource-watch-is-held-while-its-conversation-runs-and-checked-by-re-reading-after-every-gap.md); holding rules in [_Resource watches_](mcp-in-a-session.md#resource-watches)).
- **Outbound requests** go through the guarded `fetch` and the queue of 5. `clientInfo` is `{ name: "cloudpid", version: <deploy> }`. `traceparent`/`tracestate` go in `_meta` only to cloudpid's own bridge, never to remote servers; `baggage` is never sent.

## The stdio bridge

- **Why a bridge:** a Container port reached through `getTcpPort(p).fetch` carries a long-lived stream with no platform time limit, and the Container and its processes survive a Durable Object restart; `exec` with `pty` breaks JSON-RPC framing, and no existing bridge (supergateway, either mcp-proxy) does lazy shared children with server→client forwarding ([Can a Cloudflare Container carry a long-lived stdio MCP stream?](https://github.com/ian-pascoe/cloudpid/issues/376); proven in [A stdio MCP server reached as Streamable HTTP through a Container bridge](https://github.com/ian-pascoe/cloudpid/issues/383)).
- **The bridge:** one small Node script in the sandbox image (`apps/sandbox-image`), started by the image's supervisor at each Container start, listening on `0.0.0.0` at a fixed `MCP_BRIDGE_PORT` outside the Container preview ports. It keeps nothing across a stop and needs nothing restored. **As built** (#441; the values are `@cloudpid/sandbox-image/mcp-bridge`'s, which the script repeats and a test keeps equal): `apps/sandbox-image/image/cloudpid-mcp-bridge.ts`, a dependency-free TypeScript file that Node runs by stripping its types, copied to `/usr/local/share/cloudpid/mcp-bridge.ts`; it imports no MCP SDK and nothing of cloudpid's at runtime (its type imports are erased by type stripping; the import rule, [`mcp.md`](mcp.md#packages-and-objects)), and its shared constants and wire types are in `@cloudpid/sandbox-image/mcp-bridge`, which the engine and the Workspaces Worker import, since the script itself is copied into the image alone. `MCP_BRIDGE_PORT` is 17781. The supervisor runs it with the Node the image's base `mise.toml` installs (`mise which node`, run against that file so it needs no Workspace config), only when the launch's environment has `CLOUDPID_MCP_BRIDGE_TOKEN` (the bridge exits without one), its lines going where computerd's do; the supervisor then unsets the token, so computerd and its commands never see it (D5.2); it does not restart a bridge that exits, so a dead bridge is mended by `container_restart`. A request is `POST /mcp` (or `GET /mcp` with a Legacy session) and names its server in `x-cloudpid-stdio-config`, the base64url of its config's JSON; the key is the SHA-256 of the config's canonical form (`mcpBridgeKey`). A child gets only `PATH` and `HOME` from the bridge, plus the config's `env`: never the token. Children lead their own process groups, so stopping one stops what a launcher (`npx`, `uvx`) started.
- **Bridge token** (D5.2): the Workspace DO mints a 256-bit token at each Container launch, keeps it in the launch record, hands it to the bridge as `CLOUDPID_MCP_BRIDGE_TOKEN`, and adds it as `Authorization: Bearer` on every forward; the bridge checks it on every request. The engine and the host never see it. It is defence in depth: the agent is root in the Container.
- **Children** ([A stdio MCP server reached as Streamable HTTP through a Container bridge](https://github.com/ian-pascoe/cloudpid/issues/383) decision 7): a request names its server by its config (`command`, `args`, `env`, `cwd`) in a header; the key is the config's hash, so a changed config is a new server. A Legacy `initialize` without a session spawns (replacing a live child of that key) and answers `Mcp-Session-Id` = the spawn; a stale session gets 404. A Modern request goes to its key's child, spawned if none. Children are shared by every caller, lazily spawned, and forgotten at every stop.
- **Eras at the bridge** ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D4): the engine passes the host's cached era as `x-cloudpid-era`; the bridge probes a child on stdin with `server/discover` once per spawn unless the hint names an era, and an exit, any other error or 15 s of silence means Legacy (the child is respawned and sent `initialize`). It presents the child at its own era: for Modern it answers the engine's `server/discover` with the child's result; for Legacy it answers 400 with no Modern error. For a Modern child, bodies pass verbatim with ids rewritten and `Mcp-*` headers stripped, request-scoped progress and logs go out on the POST's SSE, a closed POST becomes `notifications/cancelled` on stdin, `subscriptions/listen` streams back and every open listen ends `remote` when the child exits, and a request the child sends goes to the stderr tail; `Mcp-Session-Id` is used only for Legacy children. The hint is `x-cloudpid-era: legacy|modern`. A probed child that answers Legacy is stopped and the verdict kept for its key until a Legacy `initialize` spawns it again or a hint of `modern` overrides it; a sessionless request that is not `initialize` for a Legacy key is 400 (`-32600`) without spawning. `DELETE` is 405: a shared child is not ended by one caller (the control call stops it).
- **Messages:** request ids are rewritten to the bridge's own, so callers never collide on a shared child. Server→client messages go to the stream of the request their progress token names, else the newest request in flight, else the GET stream, else wait for one. A caller that disconnects cancels its request (`notifications/cancelled`). A Legacy child's server→client requests (sampling, elicitation, roots) travel on the call's own SSE stream, and their answers come back as POSTs (202).
- **Responses and control** (D5.3, [Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423) D1.2): every response carries `x-cloudpid-spawn` (the spawn id) and `x-cloudpid-bridge: <level>`. `GET /_bridge/status` lists children, spawn ids, exits and each stderr tail (≤64 KiB); `POST /_bridge/stop { key }` stops one. Neither control call ever spawns a child. The bridge reports a child's exit, which ends that process's Resource watches ("server process ended"). `GET /_bridge/health` answers readiness for the Workspace DO's poll (`200 { "status": "ok" }`; D5.1 only implies the poll). **As built:** every call, the control ones too, needs the token (401 otherwise, still with `x-cloudpid-bridge`); `x-cloudpid-spawn` is on every response about a child, a stale session's 404 and a Modern request's 400 included (the live child's, when there is one) and absent from health, status, stop and a refusal; status lists live children and the last exit of each key that has none (`{ level, children: [{ key, spawnId, command, args, cwd?, pid?, era, state, startedAt, inFlight, listens, getStream, queued, exit?: { code, signal, reason?, error?, at }, stderrTail }] }`, never a server's `env`; the tail is the last 64 KiB in bytes, cut on a UTF-8 character); `POST /_bridge/stop { key }` answers `{ stopped }` once the process group is gone (SIGTERM, SIGKILL after 2 s). **A child that exits ends the streams of its requests and listens with no answer** (never a JSON-RPC error), which the engine reads as `Cut`; the status then names why (D5.4). A spawn that fails (`ENOENT`) is such an exit, with `error: "spawn failed: …"`.
- **`WorkspaceMcpBridge`** (D5.1): a new entrypoint of the Workspaces Worker, `mcpBridge(workspace, request, { start, use }) → Response`, for `ws:*` objects only; it answers 404 `no_workspace` when the Workspace DO has no record of itself. A stopped Container with `start: false` answers 503 with `x-cloudpid-container: stopped`; with `start: true` it starts the Container as a command does (runs `true` on its container backend, `writes: false`, single-flight), then polls `/_bridge/health` every 250 ms for up to 15 s, inside the 60 s bridge timeout.
- **Uses and holds:** `use: true` (calls, prompt gets, reads, completions, discovery, MCP task polls) is `IdleStop.touch()`, then `hold({ writes: true })` until the response body ends, fails or is cancelled (a stdio server may write the disk); never `noteActivity`. `use: false` (the GET stream, listens, subscribe and unsubscribe, bridge control) neither touches nor holds. An open session, an idle child, a stream and the server's own messages are not uses, so a stdio server never keeps the Container awake between requests, and its state across an idle stop is lost. A background MCP task's polls are requests, so they do keep it, within the Hold cap ([MCP tasks as durable long-running requests](https://github.com/ian-pascoe/cloudpid/issues/389) D4.4).
- **Idle stop and the Hold cap:** an idle stop never cuts a call, since the call holds the Container. A call in a Run is covered by the Run's heartbeat (activity), so the Hold cap cuts it only after an hour with no activity; a Legacy stdio question waiting on the owner (≤10 min) stays under it, and a stdio MCP task in the background lives within it, with **Keep the Container** to extend it ([_MCP tasks_](mcp-server-requests.md#mcp-tasks); [`container.md`](container.md) → Idle stop, Hold cap). `container_restart`, a resize, the memory guard, an OOM kill and a held stop can cut a call; a deploy does not. The memory guard's `--avoid` list spares the bridge (its process is named `cloudpid-mcp-bridge`; [`container.md`](container.md) → Memory guard): stopping it would cut every stdio server at once, where the guard's choice, the largest process, is a server that grew.
- **Roots:** only bridge connections declare `roots`, offering the Repos of the Workspace whose Container runs the server ([_Roots_](mcp-in-a-session.md#roots)).
- **Cold starts:** time to a stdio server's `initialize` answer was 2.6–6.2 s cold on `cpu-1`, 0.6–0.95 s warm, and 0.8–1.1 s from caches a Snapshot kept, plus the Container's own start when stopped. The npm and uv caches are on the Container's disk, so only a Workspace's first call downloads; an unpinned `npx -y` asks the registry at every start. No preinstall; warming the caches in a Build is left for later (the map's "Fast stdio cold starts").
- **Secrets in a stdio server's `env`** are readable by the agent's commands through `/proc/<pid>/environ`: accepted, as a Secret already reaches commands as `$PI_SECRET_*` and output redaction applies.

## Failures and cuts

- **A stream that ends without its answer** fails its request at once as `Cut { mayHaveRun: true }`, never waiting for a timeout (the `fetch` tap aborts the request's signal, since the SDK drops `onRequestStreamEnd`).
- **Naming a stdio cut** (D5.4): from the bridge's status, checked with `start: false`: "Container stopped", "stdio server exited (code/signal)" with the last 2 KiB of stderr, or "cut".
- **Retries** ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D14, D15): after a cut, read-only requests (`*/list`, `resources/read`, `prompts/get`, `server/discover`, `tasks/get`) and `tasks/update`/`tasks/cancel` once, after a re-initialize where needed; `completion/complete` never; `tools/call` never, in either era: the agent gets "cut before its answer arrived; it may or may not have run". 408, 429 and 5xx retry read-only requests once after 1 s (honouring `Retry-After` up to 10 s). `-32020` (a header the server rejects) refreshes `tools/list` and retries once. A `tools/call` is sent again only when the server refused it before it ran: a Legacy 404, a Modern era drop, or a Legacy `-32042` ([_Elicitation requests_](mcp-server-requests.md#elicitation-requests)).
- **Lost ends** (D6.2 as amended by [Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423)): a dead host makes the Session report a cut with `details.cut: "host_lost"` (also for `Network connection lost.`, whichever end lost it), and its live Legacy questions expire. A dead Session makes its callbacks reject, so the engine aborts the server request and the result is dropped; the `mcp` tool is `replay: "safe"` with memo markers, so the Session's rerun, finding `mcp.sent` and no wait to resume, settles the call "may have partially run" ([_The waiting-question record_](mcp-server-requests.md#the-waiting-question-record)). A real cut between host and engine is `Cut { mayHaveRun: true }` with `details.cut: "engine_lost"`; a cut listen is a gap.
- **Learned at the next contact, with no push** (D11.2): a destroyed Workspace (404 `no_workspace`), a `container_restart` or a resize (a changed spawn id, a 404, or a listen ending `remote`).
- **An old bridge:** an `x-cloudpid-bridge` level below the engine's minimum makes the server `failed` ("this Container runs an older bridge; restart it").

## Deploys

The deploy strategy (deferred code updates, `max_delay` 300 s), the rule that every MCP edge only gains, and each edge's gate are in [_Deploys_](mcp.md#deploys) and [`workers.md`](../development/workers.md#deploys-and-durable-object-code-updates). What the host and the Sessions do with calls in flight ([Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423) D3–D5):

- **A replaced host** (a code update reached it mid-call) still returns its results. Its writes for a call (era, Legacy session, inventory, status, App HTML) are best-effort: a refused write never turns a result into an error, a result never claims what was not kept, and what is lost heals as after a restart (a 404 → initialize, discovery reruns, versions are content hashes). At any failed storage operation, reads included (never matching the error's text), it stops background work: no new discovery or refresh, and its listens close; the new instance reopens and gap-checks at the next `requestStart` of a watching conversation. While both run, the caps count per instance and a listen may be held twice until its swap.
- **A replaced Session** keeps the call's invocation, so the call runs to its end within its timeout; its result is dropped, and the new instance settles it through pi-durable's recovery ("may have partially run"; never retried for `tools/call`). Nothing hands the result over and nothing cancels the call. A question reaching it gets the no-answer for its kind, and an MCP task it cannot record gets a best-effort `tasks/cancel` ([_The waiting-question record_](mcp-server-requests.md#the-waiting-question-record)).
- **An `McpWorker` deploy cuts nothing:** calls in flight finish on the engine version they started on (15 min observed), and new calls reach the new version.
- **A reset outside a deploy** (a runtime update, an eviction): engine calls whose host died see `untilAborted()` reject and abort; listens end, and the span until they reopen is a gap; Legacy rows are reused; stdio children survive; token, value and validator caches are asked for again; a `connecting` status older than 120 s returns to its previous state; live Legacy questions die ([ADR-0037](../adr/0037-a-modern-mcp-servers-question-is-answered-with-a-new-request-and-a-legacy-ones-lives-only-as-long-as-its-call.md)).

## Telemetry

- **Spans** (D12.1): in the host `mcp.request_start`, `mcp.request`, `mcp.discover`, `mcp.listen`, `mcp.gap_check` and `mcp.registry`; in the engine `mcp.engine.*` children (HTTP status, retries, era drop, re-initialize, bytes). How Workers tracing joins them, and what background work records instead, is in [_Testing and tracing_](mcp.md#testing-and-tracing). Spans never record argument or result values, header values, tokens, resolved `${NAME}` values or full URIs (scheme and host only). `tasks/get` spans are emitted only on a status change or an error and counted otherwise, with an 8-hex hash standing in for the `taskId`.
- **Server logs** (D12.2): `notifications/message` reaches the host through `onLog`: `warning` and above becomes a span event (`data` cut to 2 KiB and redacted), and everything goes to a ring of the last 50 per server; never to the model (levels: [_Server logging_](mcp-in-a-session.md#server-logging)).
