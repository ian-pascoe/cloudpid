# MCP: connections, the host object, the engine and stdio

One Durable Object per Environment owns its MCP servers, and a stateless engine in a Worker of its own does the protocol work for it ([ADR-0038](../adr/0038-the-mcp-host-object-lives-beside-the-registry-and-runs-the-sdk-through-a-stateless-engine-in-a-worker-of-its-own.md)). Stdio servers run in the calling agent's Workspace Container behind a bridge that serves each one as Streamable HTTP. Exhaustive detail is in [The Environment's MCP host object: what it owns and its RPC](https://github.com/ian-pascoe/cloudpid/issues/382) and its amendment comments; a bare D-number in this document is that ticket's. "MCP host object" and "MCP engine" are implementation words, not GLOSSARY terms: the owner never sees them, and the spec's "host" is the whole application (D14.1).

## The host object

- **Identity:** `McpHost`, an Effect Durable Object named `mcp:<environment id>`, in `Server` beside the Registry and the Session DOs (`apps/server/src/mcp/`, `McpHostLive` beside `SessionLive` and `RegistryLive`). It holds all MCP state and policy and imports only `@cloudpid/mcp/types`, never the SDK (the import rule and its bundle test: [_Packages and objects_](mcp.md#packages-and-objects)).
- **Runtime:** one `ManagedRuntime` per instance over `McpHostStore`, `McpEngineClient` (over the `MCP_ENGINE` binding, or a fake), `McpRegistryPort` (the Registry, or a fake), `Clock` and `Telemetry`. The inventory, watches, App HTML and the caches are internal modules, not services; the scheduler is one more service, `McpDiscovery`, which keeps the discoveries in flight in a `FiberMap` by `conn` within the runtime's scope, so they outlive the call that started them. Background work (discovery, refreshes, listens, gap checks) runs as in-memory fibers in that runtime (D7.5, D13.1). **As built** ([#449](https://github.com/ian-pascoe/cloudpid/issues/449)): in `apps/server/src/mcp/`, `server-state.ts` (each server's state, when it is due, the versions), `discovery.ts` (the scheduler and the discovery), `limits.ts` (`McpLoadCaps`, the load caps, a service of the runtime too), `inventory.ts` (bounds, problems and versions), `engine.ts` (`McpEngineClient`), `registry-port.ts` (`McpRegistryPort`), and the store in parts that change apart: `set-store.ts` (the set and `mcp_meta`), `status-store.ts` and `inventory-store.ts` (the inventories and the engine's rows), joined in `store.ts` with the migrations, the wipe and the pruning.
- **No alarm:** the object never arms one, since an alarm would wake idle Environments and bill duration. Retries are demand-driven (see [_States_](#discovery-and-the-mcp-inventory)), watch expiry (7 days without a request) is swept at every `requestStart` and `apply` before the caps are checked, and inventories, App HTML and stdio session rows are pruned at writes. A Legacy `DELETE` is best effort and never retried (D10.3).
- **Never woken without MCP servers:** a Session whose `sessionSettings` says `mcp: { servers: 0 }` and that holds no Resource watch skips `requestStart`, and an empty set is pushed only to an Environment whose previous set was not empty (D2.1; [_From the Registry to the host_](mcp-configuration.md#from-the-registry-to-the-host)).
- **Nothing Global:** each Environment's object connects to a Global MCP server on its own, since `${NAME}` resolves per Environment (D2.3). MCP sign-ins are the exception, kept Global in the Registry ([_MCP sign-ins_](mcp-sign-in.md#mcp-sign-ins)).
- **Destroy:** deleting an Environment (`registry/removal.ts`) ends with the Registry noting its host to be wiped, only if the host was ever handed a set; the main Worker's next sync, whatever it is for, sends `apply({ kind: "destroy", revision })` and tells the Registry once it was done ([_From the Registry to the host_](mcp-configuration.md#from-the-registry-to-the-host)). The host aborts calls, makes a best-effort Legacy `DELETE` within 2 s, closes streams, and calls `deleteAll()` (the tables are made again empty, with `revision` kept in `mcp_wiped` as the floor of what may fill it again). As built, it interrupts its discoveries (the engine aborts their server requests) and wipes; the Legacy `DELETE` and the streams come with `control` and listens ([#448](https://github.com/ian-pascoe/cloudpid/issues/448), [#451](https://github.com/ian-pascoe/cloudpid/issues/451)). A wipe the storage refuses answers `HostFailed`, and the Registry sends it again. The Environment's MCP sign-ins stay in the Registry, listed as unused (D2.2).

## Storage

- **Connection key `conn`:** SHA-256 over the canonical `{ source, normalized name, type, url, headers, oauth, command, args, env, cwd }`, with `${NAME}` unresolved, so no Secret enters a hash. It is a pure, synchronous function in `@cloudpid/config`, beside `resolveMcpServerSet` (`mcpConnectionKey`). `source` is `owner` (Global's and an Environment's own entries) or `repo:<owner/repo>`; the name is normalized (lower case, `-` as `_`); `type` is `stdio` or `http` (`streamable-http` is `http`); the `url` is `new URL(url).href` without its fragment; `oauth` leaves out `callbackPort` and `callbackUrl`, which are ignored; every key is read with its defaults, so an empty `args` and none are one connection. Every other key (`description`, `timeout`, `enabled`, `sampling`, `exposure`, `toolExposure`) is left out: editing it bumps the inventory's version but never reconnects or re-probes (D3.1). The era cache, the inventory, status and Legacy session rows all key by `conn`, never by the Registry's per-entry hash. Beside it, `mcpServerIdentity` is SHA-256 of `{ source, normalized name, type, url }`, which MCP tasks use to tell a re-pin from a new server ([MCP tasks as durable long-running requests](https://github.com/ian-pascoe/cloudpid/issues/389) D16).
- **Tables** (SQLite through `migrate`, which lives in `@cloudpid/effect-durable/sqlite` for the Registry and `McpHost` both (it moved there from `apps/server/src/registry/store.ts`; each object's migrations have a shipped-digest manifest, [_Deploys_](../development/workers.md#deploys-and-durable-object-code-updates)); migrations only add; D3.2, D3.6):

- **Format `v` on `prior` rows:** era and Legacy session rows cross the engine edge as `prior`, so each carries a format `v`, and an engine that does not know a row's `v` treats it as absent (probes or initializes again). The host's own tables stay additive-only with fallback members, without a `v` ([_Deploys_](mcp.md#deploys); [Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423) D3.4). **As built** ([#467](https://github.com/ian-pascoe/cloudpid/issues/467)): the `v` is the core's (`EraRowV1` and `SessionRowV1`, `@cloudpid/mcp/types`, both `v: 1`), written by the engine into `McpEngineState` and kept by the host as the JSON it was given, never decoded or rewritten by it, so a row a newer build stored is handed to the engine as it is, read as absent there, and replaced by the row the engine then makes; no host migration was needed.
- **Memory only** (D3.3): access tokens; resolved `${NAME}` values (asked again at the first use 60 s after the last answer, served stale while refreshing; [_`${NAME}` values_](mcp-configuration.md#name-values)); the resources list cache (LRU, 4 MiB per object and 8 MiB per isolate; [_Resource tools_](mcp-in-a-session.md#resource-tools)); single-flight, holds and in-flight calls.
- **Kept elsewhere** (D3.4): the Session keeps `ResumeState` and MCP task ids (the host keeps no task state and lists no tasks); the bridge keeps stderr tails; the Registry keeps MCP sign-ins.
- **Versions are content hashes, not counters** (D3.5): `version` is 128 bits of SHA-256 over the canonical tools projection, covering per server the config that shapes tools, a coarse state (has an inventory | connecting | sign-in), `instructions`, tools, per-tool problems and the resources capability. `promptsVersion` covers prompts and their problems, so a prompts-only change never reinstalls the `mcp` extension. Each server also gets a `toolsHash` and a `promptsHash`. A flip back brings the old version back, and the Session builds only from stored canonical JSON (`inventory.ts`; the projection's state is that coarse one, so a server with no inventory that is `unavailable`, `failed` or `skipped` counts as connecting), so a reinstall over unchanged tools is byte-identical (what the Session does with them: [_The prompt cache and the `mcp_servers` section_](mcp-in-a-session.md#the-prompt-cache-and-the-mcp_servers-section)).

## RPC

- **Four methods** on `McpHost`, typed with Effect Schemas in `@cloudpid/mcp/types`, failures returned as values (D6.1, amended by [Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423) for `features`):

  | Method         | Arguments                                                                                                                                                                                   | Returns, and what it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
  | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `requestStart` | `{ caller: { session, conversation, workspace }, windowOpened?, known?, waitFor?, waitMs? }`; `known` is the `version` the caller built from, absent before its first build; `waitMs ≤10 s` | `{ version, promptsVersion, features, servers: { [name]: { toolsHash, promptsHash, state } }, watches: { changed, ended } }`. Marks the conversation active, sweeps watch expiry, starts due refreshes, reopens watched streams with gap checks, and asks the Registry for the set when `windowOpened`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
  | `servers`      | `{ names?, parts: ("tools" \| "prompts" \| "instructions" \| "status")[], waitMs?, workspace?, demand? }`                                                                                   | `{ version, promptsVersion, servers: [...] }`, in the set's order. Per server: name, source, config (`${NAME}` unresolved), `conn`, state, error, negotiated protocol version, where and when discovered, `toolsHash`, `promptsHash`, counts, whether it offers resources, problems, and the parts asked for. Serves the `mcp` extension's inventory reads, `serverStatus`, `settings_mcp_list`/`get`, the composer and Settings. It is a demand for HTTP servers (a due one starts discovering) unless `demand: false`, which answers what the host holds and starts no discovery (`settings_mcp_list`/`get` ask so, since they connect to nothing; `reload` never calls `servers`); it waits up to `waitMs` (none by default) for those discovering, and never starts a Container. A host from before `demand` ignores it and treats the read as a demand (the edge only gains), so across a deploy such a read may still start an HTTP discovery. |
  | `request`      | `{ op, server?, params, ctx: { callId?, origin, session?, conversation?, workspace?, start?, timeoutMs?, answers?, allowTask? } }` plus hooks                                               | `op` is `tools/call`, `prompts/get`, `resources/read`, `resources/list`, `resources/templates/list`, `completion/complete`, `resume`, `tasks/get` \| `tasks/update` \| `tasks/cancel`, or `ui/html`. Errors are the core's tags plus `NotRunning`, `NotAllowed`, `UnknownServer`, `ServerChanged`, `Cancelled`, `HostUnsupported`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
  | `apply`        | `set` \| `sign_ins` \| `reload` \| `end_watches` \| `destroy`                                                                                                                               | The pushes and teardown.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

- **`requestStart` and `servers` fail as a value too:** a host that cannot read what it holds (a replaced instance whose storage is refused) answers `HostFailed`, never an empty inventory that would read as no servers; a write it cannot make (the last use, the versions) is best-effort and only stops its background work (`McpRequestStartResult`, `McpServersResult`).
- **`serverLog` reads storage only:** `{ server, workspace? }` → `ServerLog { entries, stderr? }` (the ring, oldest first), `NoServer` for a name the held set does not have, or `HostFailed`. It starts no discovery, asks neither the engine nor the Registry, and touches no Workspace or Container, whatever `workspace` it is given; the stderr tail of a stdio server comes with the bridge, read from `bridge_status` with `start: false` ([_Telemetry_](#telemetry)). Added to the host's methods with the status reads; a host that does not have it fails the call, which the main Worker reads as `Unavailable`.
- **`apply` answers as a value:** `Applied { hash, changed }`, `Stale { hash, revision }` for a set whose `revision` is below the one the host holds, or no newer than the one it was wiped at, `hash` then empty (the host keeps what it has, and answers with it), `Destroyed` for `destroy`, `Reloaded { servers }` for `reload` (the names of the set it reloaded), `HostUnsupported { message, op }` for a `kind` this build does not know, or `HostFailed { message, tag? }`, the fallback every other failure reads as; the caller reads an answer it cannot place as `HostFailed` (`readMcpApplyResult`). A set is stored whole with its `revision` (`mcp_meta`), an empty one too; the same hash under a newer revision only raises the revision.
- **`request` as built** ([#452](https://github.com/ian-pascoe/cloudpid/issues/452); `apps/server/src/mcp/request.ts`, the types in `@cloudpid/mcp/types`): `op: "tools/call"` to an HTTP server, or, as of [#460](https://github.com/ian-pascoe/cloudpid/issues/460), to a stdio server run in the caller's Workspace (`ctx.workspace`, required: a call that names none is `NotAllowed`; the call may start that Container), with the `untilAborted` and `onProgress` hooks; `op: "ui/html"` as of [#466](https://github.com/ian-pascoe/cloudpid/issues/466) (App HTML by hash or by `ui://` URI, answered `AppHtml` or `NoAppHtml`: [_Declaring and reading Apps_](mcp-apps.md#declaring-and-reading-apps)); `op: "prompts/get"` as of [#463](https://github.com/ian-pascoe/cloudpid/issues/463) (the bullet _As built — `prompts/get`_ below); any other `op` is `HostUnsupported`. It answers `Completed { result, structuredOutput?, app? }` (the engine's value, inline or a stream, `isError` included), `CallFailed { error }` (the core's failure), `UnknownServer`, `NotAllowed` (switched off or `hidden`, a stdio server with no Workspace named, or a tool the inventory does not list), `HostUnsupported` or `HostFailed`; the Session reads a tag it does not know as `HostFailed` (`readMcpHostRequestResult`). A server at `sign_in` or `rejected` is not sent the call: it answers `CallFailed` with `SignInRequired`. The call goes through the server's cap, the host's, then the queue as a call, and the caller's abort ends it wherever it is: before the engine was given it, `Cut` with `mayHaveRun: false`; after, or when the engine's RPC breaks, `Cut` with `mayHaveRun: true` (and `lost: "engine"` for the RPC that broke). The wait for those slots counts toward the call's timeout (Load caps): a call still waiting when it passes is never sent, and is answered `Cut` with `mayHaveRun: false` ("waited for a free slot past its timeout, and was not sent"); a sent one gives the engine what is left of it as `timeoutMs`. A server with a sign-in is called as a discovery connects it (`requestAccess`): through the engine's `auth(stale)` hook when a token stands, without a token on `required`, and not at all with no token that stands (`SignInRequired` or `Unreachable`); what it answered is reported to the Registry on transitions only. The rows the call changed are stored as a discovery's are, and the logs the engine returned go to the server's ring (`recordLogs`; a ring that fails to write is logged and never costs the call its answer). The target sent carries the server's Secret values as `redact`, as a discovery's does (`targetOf`). A stdio server has no sign-in, so its call takes no token and reports nothing to the Registry; its rows are the Workspace's (`prior(conn, workspace)`), and the `spawn` id of the answer is kept with them (`applyEngineState`), a changed one calling the `McpProcessEnded` service (`apps/server/src/mcp/stdio.ts`, the seam for [#478](https://github.com/ian-pascoe/cloudpid/issues/478), which does nothing until that lands; `mcpHostLayer` takes it as an option), as does an answer of `Unreachable` with status 404 (the Workspace is gone), from a call or a discovery. The fresh `tools` a `-32020` result carries are not yet put back in the inventory.
- **`features`:** `requestStart` lists what the host supports (as built: `inventory`, for `known`, `waitFor`, `waitMs`, `servers` and `reload`; `call`, for `request({ op: "tools/call" })` with its hooks; `app_html`, for `Completed.app` and `request({ op: "ui/html" })`; `resources`, for `request({ op: "resources/list" | "resources/templates/list" | "resources/read" })` and `Completed.sha256`: an optional feature, which a Session lacking it does without); a Session uses a feature only once it is listed, and rebuilds `mcp` when the features its tool declarations used change (the gate: [_Deploys_](mcp.md#deploys)).
- **Callbacks, Session → host → engine** (D6.2): a server's questions, progress and logs reach the Session only through hooks passed down the call; nothing ever calls a Session. The hooks are `onInput` (questions; `ctx.answers` says which kinds the caller can answer, and `capabilities(ctx)` declares only those), `onInputComplete({ key })` (a `notifications/elicitation/complete` on the call's own POST stream; completions on the GET stream are ignored), `onProgress` (at most 10/s), `onLog` (**as built** ([#453](https://github.com/ian-pascoe/cloudpid/issues/453)): there is no such hook, since a discovery passes none and a function stub would not outlive its invocation; a call's server logs come back in its result as `logs`, see [_Telemetry_](#telemetry)), and `untilAborted()`, a pending callback that resolves on an abort and rejects if the caller dies, since RPC carries no `AbortSignal`. Either way the engine aborts the server request (Legacy `notifications/cancelled` and stream close; Modern stream close; through the bridge, a cancel of the child's request). A Modern question's `ResumeState` goes back to the Session as `input_required`, and the host keeps nothing; MCP tasks work the same way ([_Questions_](mcp-server-requests.md#questions)). A stub lives only as long as the invocation that made it, so the Session awaits the call for its whole length ([_RPC edges_](mcp.md#rpc-edges)). **As built** ([#452](https://github.com/ian-pascoe/cloudpid/issues/452)): `untilAborted` and `onProgress` pass Session → host → engine as they came. The engine asks the server for progress (a `progressToken`) only when the call has `onProgress`, passes at most 10 notices a second on (`progressTo` in `apps/mcp-worker/src/call-context.ts`; a dropped notice is followed by the next that passes), and each notice resets the call's timeout; a hook that throws or rejects fails nothing.
- **Additive fields from other areas:** stdio `request` results carry the bridge's `spawn`; an answer carries the `conn` shown on its card, and the host refuses one whose `conn` differs (`ServerChanged`, nothing sent) ([Elicitation in form and URL modes as durable requests](https://github.com/ian-pascoe/cloudpid/issues/388) D13, D15); `tasks/*` requests carry `server`, `tool` and the pinned `conn`, results carry `spawn` and the MCP sign-in id, `tasks/cancel` is allowed for a server switched off, and `ServerChanged` carries the name's current `conn` and `mcpServerIdentity` ([MCP tasks as durable long-running requests](https://github.com/ian-pascoe/cloudpid/issues/389) D4.3, D16). A `resources/read` with `watch: true` whose watch row could not be kept returns its content with the watch not started ([Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423) D3.2).
- **Pushes:** the Registry never calls out, so the main Worker (owner Settings saves, `addRepo`/`removeRepo`, a Repo Reload, an MCP sign-in's callback, sign-out or rebind, from the Registry's answer) and the Sessions (`settings_mcp_*`, watch ends) carry its changes to `apply`. A lost push heals at the next `windowOpened`, which passes the hash the host holds and is answered with the current one and `signInsRevision`, 0 until sign-ins exist (D6.3; [_From the Registry to the host_](mcp-configuration.md#from-the-registry-to-the-host), [_Tokens reach the host object_](mcp-sign-in.md#tokens-reach-the-host-object)).
- **Host → Registry** (same script; D6.4): `mcpServerSet({ environment, heldHash }) → { hash, signInsRevision, set?, revision? }`, which runs the Registry's 10-minute look at Repos' `.pi/mcp.json`; `signInsRevision() → number`, the revision of the MCP sign-ins alone, the counter `mcpServerSet` carries too; `mcpServerValues({ environment, server, conn })`, resolving `${NAME}` against Secrets then Variables (Variables only for a Repo's entries), never logged, and answering `{ status: "values", env, headers, missing }` (a name that resolved to nothing stays as written and is listed in `missing`), `{ status: "unknown_server" }` or `{ status: "server_changed", conn }`, with a fallback for a status this build does not know; and `mcpAccessToken` and `reportMcpAuth` ([_Tokens reach the host object_](mcp-sign-in.md#tokens-reach-the-host-object)).
- **For the UI,** through `RegistryRpcs` (D12.3; the UI itself is left for later, the map's "MCP status in the UI"): `mcpServers({ environment })` → the servers with status, tools and prompts, to which the main Worker adds Exposure with the pure resolver; `mcpServerLog({ environment, server, workspace? })` → the log ring plus the stderr tail from `bridge_status`, never starting a Container; `mcpReconnect` → `apply({ kind: "reload", servers })`. Sign-in controls stay the Registry's.
- **The Session side** (D13.3): a `McpHostClient` service with the four methods, used by `@cloudpid/extensions/mcp` and `@cloudpid/extensions/settings-mcp`; the live adapter is `apps/server/src/session/mcp-host.ts`, with an in-memory fake for tests. **As built** ([#452](https://github.com/ian-pascoe/cloudpid/issues/452)): `McpHostClient` is in `@cloudpid/extensions/mcp` with `requestStart`, `servers` and `request` (`apply` comes with `settings_mcp_*`), and never fails: a call that fails, or an answer this build cannot read, is `HostFailed` (`readMcpRequestStartResult`, `readMcpServersResult`, `readMcpHostRequestResult`, over one shared reader in `@cloudpid/mcp/host`), and a `request` whose RPC breaks is `HostLost`, a Session-side tag that never crosses the edge, which the tool answers as `host_lost`. Neither carries the cause to the model: the adapter logs it. Its live adapter is `apps/server/src/session/mcp-host.ts` (`mcpHostClient` over a `McpHostStub`, the host's methods as the client's shape over whatever stub reaches it, alchemy's Tag in the Session DO and a Promise stub in `session/host.fixture.ts`), since `session/mcp.ts` holds the Session's side of the `/mcp` endpoint; its fake is `packages/extensions/src/mcp.testing.ts`, for that package's own tests. The Session DO reaches the host through `McpHost`'s namespace, by `mcpHostName(environment)`. It calls `McpHost` through alchemy's Tag, which passes function and `RpcTarget` arguments as native stubs, turns a dead host into `RpcCallError`, and hands a returned `ReadableStream` to the caller as an Effect `Stream` ([Verify MCP host ↔ engine RPC on a deployed stage](https://github.com/ian-pascoe/cloudpid/issues/409) answer 5).
- **As built — `prompts/get`** ([#463](https://github.com/ian-pascoe/cloudpid/issues/463); `apps/server/src/mcp/request.ts` `promptGet`, `McpHostPromptGet` in `@cloudpid/mcp/types`): `request({ op: "prompts/get", server, params: { name, arguments? }, ctx })` is in `McpHostRequestInput` only, not in `McpHostRequest`, so the `mcp` extension's tool calls and task requests never take it. It is the owner's get at send (`ctx.origin: "owner"`; [_Getting a prompt at send_](mcp-in-a-session.md#getting-a-prompt-at-send)). The host answers `UnknownServer` for a server not in the set, `NotAllowed` for one switched off or `hidden`, or whose inventory does not list `params.name` (nothing is sent), which also expires the server's inventory so the next catalog read lists again (`relistNext`, `expireInventory`; so does a server's `NotFound` or `-32602` for the name), then resolves the server as a `tools/call` does (a sign-in's token, a stdio server in `ctx.workspace`) and sends `prompts/get` to the engine as a read (`mayHaveRun: false`: resent after a cut, as the core does). It is given `min(30 s, the entry's timeout)`, passes `ctx.answers` on, and answers `Completed { result }` with the server's `GetPromptResult` (a stream past 1 MiB, as for any result), or `CallFailed { error }`: a task-shaped answer is a `ProtocolViolation`. There is no feature flag: a host that predates it answers `HostUnsupported` (an `op` it does not know), which the Session refuses as `MCP_PROMPT_FAILED`. At discovery, `vetPrompt` (`inventory.ts`) bounds what is kept of each prompt: more than 16 arguments, an empty or repeated argument name or a name over 128 characters is "not offered" (a problem of `{ prompt, problem }`), `title` is cut at 120 characters, `description` at 1,000 and an argument's at 500, and only `name`, `title`, `description` and `arguments { name, title, description, required }` are kept.
- **As built — tasks** ([#455](https://github.com/ian-pascoe/cloudpid/issues/455); `apps/server/src/mcp/request.ts`): `request` also takes `tasks/get`, `tasks/update` and `tasks/cancel` (each with `taskId`, `tool` and the pinned `conn`), and answers `Task`, `TaskState`, `TaskAck` and `ServerChanged` besides `Completed`. The host checks `conn` before anything else and sends nothing on a mismatch; a `tasks/cancel` is the only request allowed for a server switched off. A `tasks/*` request is given 30 s, its own timeout and not the call's, and is spanned as `mcp.request` with `mcp.task`, a hash of the task id. The host passes `ctx.allowTask` to the engine only for an agent's or an App View's `tools/call` to an HTTP server, and always on a `tasks/*` request; for a stdio server the request is `HostUnsupported` until [#494](https://github.com/ian-pascoe/cloudpid/issues/494). The MCP sign-in id of the token used rides on `Task`, `TaskState` and `TaskAck` (`RequestAccess.signIn()`; [_The sign-in id_](mcp-sign-in.md)). `MCP_HOST_FEATURES` gains `"tasks"`.
- **As built — resume** ([#480](https://github.com/ian-pascoe/cloudpid/issues/480); `apps/server/src/mcp/request.ts`): `request` also takes `resume` (`{ tool, conn, resume, answers }`), and answers `InputRequired` (`{ requests, resume, conn, identity?, signIn?, spawn? }`) to a `tools/call` or a `resume` whose `ctx.answers.defer` is set; an engine's `input_required` for any other is `CallFailed` `ProtocolViolation`. The host checks the resume's `conn` first and answers `ServerChanged` with nothing sent on a mismatch, needs the tool still listed (`NotAllowed` otherwise) and a server not switched off, passes the `ResumeState` and the answers to the engine unread, keeps neither, and gives the resume the call's timeout and `mayHaveRun`. It is offered a task as a `tools/call` is. `MCP_HOST_FEATURES` gains `"resume"`. A Modern `resources/read`, which declares elicitation as a call does, never defers: the core answers its `input_required` rounds itself (`readResource`, as `callTool` does for a call that cannot defer), a deferral read as `cancel`, so a read always ends in its content or a failure. A resume with fewer answers than the round asked is `Unsupported`, never blamed on the server.

## The engine

- **`McpWorker`** (`apps/mcp-worker`, `@cloudpid/mcp-worker`): a plain async Worker, `workersDev: false`, no routes, no `nodejs_compat`. It exports `McpEngine`, a stateless `WorkerEntrypoint` running `@cloudpid/mcp`; `McpServer`, cloudpid's own `/mcp` ([_The handler_](mcp-endpoint.md#the-handler)); and a default that answers 404. It binds `MCP_BRIDGE` = `Cloudflare.WorkerEntrypoint(workspaces, "WorkspaceMcpBridge")`; `Server` binds `MCP_ENGINE` and `MCP_SERVER` through Outputs. Deploy order is Workspaces → Browsers / CodemodeSandboxes / McpWorker → Server (E1).
- **Interface** (`McpEngineMethods` in `@cloudpid/mcp/types`; D1): `discover(target, prior, hooks)`, `request(target, prior, req, hooks)` (`req.op` is `tools/call`, a list, or, as of [#466](https://github.com/ian-pascoe/cloudpid/issues/466), `resources/read { uri }`, which answers the server's `ReadResourceResult` as a value and, as of [#471](https://github.com/ian-pascoe/cloudpid/issues/471), `sha256`, and `resources/list_page` and `resources/templates/list_page { cursor? }`, one page each as `{ resources | resourceTemplates, nextCursor? }`, or, as of [#463](https://github.com/ian-pascoe/cloudpid/issues/463), `prompts/get { name, arguments, ctx }`, which answers the server's `GetPromptResult` as a value), `listen(target, prior, filter, hooks)` (an event stream of newline-delimited JSON), and `control(target | workspace, "bridge_status" | "bridge_stop" | "session_delete")`. Each returns its result plus `state: { era?, session? }` (null means drop), which the host stores. `target` carries `conn`, the name and the timeout, plus the URL and resolved headers for HTTP, or `workspace`, `start` and the resolved `env` for stdio.
- **Hooks** besides the Session's: `auth(stale)`, through which the host asks the Registry's `mcpAccessToken`, so tokens never reach a Session, a Workspace DO or a Container; and `opened()`, called when response headers arrive, so the host keeps the core's outbound queue of 5 across engine calls. Every hook is optional: a call no caller's invocation holds (the host's background discovery) passes none, since a function stub lives only as long as the invocation that made it ([#409](https://github.com/ian-pascoe/cloudpid/issues/409) answer 2).
- **Built so far** ([#447](https://github.com/ian-pascoe/cloudpid/issues/447)): `discover` and `request` for HTTP targets, with `tools/call` and the list `op`s; the `McpServer` entrypoint and the `MCP_SERVER` binding ([#451](https://github.com/ian-pascoe/cloudpid/issues/451)); stdio targets and `MCP_BRIDGE` ([#460](https://github.com/ian-pascoe/cloudpid/issues/460); [_The stdio bridge_](#the-stdio-bridge)); `listen` and `control` come with [#448](https://github.com/ian-pascoe/cloudpid/issues/448). An `op` this engine does not know fails as `Unsupported`, sending nothing.
- **Stateless:** each call rebuilds the SDK client with `connect(target, deps)` from `prior` and the hooks, and keeps nothing between calls. One `ManagedRuntime` per isolate holds the byte budget, the validator cache and `Telemetry` (D13.2).
- **Aborts:** each call that has one races `untilAborted()` (a call without it runs to its own bounds), which resolves when the caller aborts and rejects when it dies; either way the work is interrupted, which aborts the server request (a Legacy server gets `notifications/cancelled`), and the call fails as a `Cut`: `mayHaveRun: true` for a `tools/call`, `false` for `discover` and the lists, which run nothing.
- **`-32020`:** a `tools/call` whose headers the server rejects lists the server's tools again and is sent once more with the fresh definition. The server refused the first before running it, so the call runs at most once. The result, completed or failed, carries the fresh `tools` and their `problems`, compiled as discovery compiles them, for the host's catalog; a `tools/list` request's result carries its tools' `problems` too, so no definition reaches the catalog unchecked.
- **`ctx.waitUntil`:** the engine holds each call's work under `this.ctx.waitUntil(…)` as well as returning it. Without it, a dead host's call is cancelled silently with its fetches, and a Legacy server or the bridge is never told; with it, `untilAborted()` rejects at once and the engine sends its cancel ([#409](https://github.com/ian-pascoe/cloudpid/issues/409) answer 2).
- **Load caps** (D7.3, D8): ≤8 requests in flight per HTTP server, ≤4 per (stdio server, Workspace), ≤32 per host object; requests over a cap wait FIFO, and the wait counts toward their timeout. The outbound queue of 5 serves calls first; background work takes at most 3 of its slots. The Workers limit of six connections waiting for headers applies to the engine's own `fetch`es only: RPC (Session → host, host → engine) neither counts toward it nor queues behind it ([Verify MCP host ↔ engine RPC on a deployed stage](https://github.com/ian-pascoe/cloudpid/issues/409) answer 7). **As built** ([#449](https://github.com/ian-pascoe/cloudpid/issues/449); `limits.ts`, `McpLoadCaps`): the per-server cap of 8 and the host's 32 bound requests in flight; the queue of 5 bounds the host's engine calls, kept by the owner (#449 review) though RPC needs no connection slot, so that calls are served before background work: background work takes at most 3 slots, and a freed slot goes to a call waiting before any background work. They compose in one order, server then host then the queue, so no holder of a later slot waits for an earlier one. Each is first come first served (a freed slot goes straight to the oldest waiter, and a newcomer never takes a slot while anyone waits ahead of it), and a server's cap lives only while a request holds or waits for it, so a server that left the set leaves nothing behind. A discovery takes one of the 3 discovery slots, then one request in flight on its server and one background engine call; `request` ([#452](https://github.com/ian-pascoe/cloudpid/issues/452)) takes the same caps, its engine call as a call. The queue counts whole engine calls; `opened()` is not used yet.
- **Memory** (D9.1): per `McpWorker` isolate, one large slot for a single body over 4 MiB (up to 16 MiB) and an 8 MiB pool for bodies of 4 MiB or less: 24 MiB of counted bytes in flight, and at most 28 MiB while a deadlock is being broken (below); waiting is backpressure upstream (peak about 3 × 28 MiB plus ~20 MiB of SDK, about 104 MiB, under 128 MB). Each call holds one lease, grown as its `fetch`es count bytes and given back when the call ends however it ends (a defect included), or for a large result once its stream is read or cancelled, or once the stream has gone unread for 60 s (each pull renews it; the stream then errors and lets its bytes go, and the next call that asks the budget, or the timer of one waiting on it, takes the lease back); a Legacy GET stream is capped per event instead. A call that waits keeps what it holds counted, a call moving to the large slot its pool bytes too, until it gets the slot. Calls holding pool bytes can wait on each other, so when every one of them is waiting for the pool, the oldest waiter is let in over budget, and its later charges too, until it ends or moves to the large slot: one call at a time, so the pool overshoots by at most 4 MiB, and nobody overshoots while any holder still runs. The large slot needs no such rule, since its holder is charged nothing more. A release (the call's end, an abort, a timeout) gives its bytes back and drops its waiter at once. The budget is plain Promises, not an Effect `Semaphore`: a stateless isolate's waiter must be let in by the releasing call itself, and an Effect wake-up scheduled on a timer belongs to an invocation that may already have ended.
- **Large results** (D9.2): a result over 1 MiB passes engine → host → Session as a byte `ReadableStream` that the engine produces on pull; the host returns it unchanged, unread and never as an Effect `Stream` ([_RPC edges_](mcp.md#rpc-edges)). The engine scrubs the access-token echo and validates `structuredContent` before serializing; the Session takes one slot per isolate to decode a result over 4 MiB, and spills large ones to the Workspace ([_Calls and results_](mcp-in-a-session.md#calls-and-results)). As built ([#458](https://github.com/ian-pascoe/cloudpid/issues/458)): the Session reads at most 32 MiB of a stream; the slot is one per isolate and is held until the result is cut to its head and its value, not only while it is read; a read that is quiet for 30 s is a lost stream; Stop ends a wait for the slot at once, and the wait ends by itself after 45 s (`MCP_STREAM_SLOT_WAIT_MS`), under the 60 s the engine holds a stream unread (`MCP_STREAM_HOLD_MS`, one constant for both), as a cut the tool ran in (`engine_lost`). The peak of one 16 MiB text result is its read and parse, about 50 MB of JS heap, which is why two must not overlap ([_Calls and results_](mcp-in-a-session.md#calls-and-results)). The host does the same for the one large read it makes itself, an App's HTML (≤12 MiB of JSON, `MCP_APP_READ_BYTES`): one streamed answer decoded at a time in the host object (the slot covers the decode, not the engine round, and a wait for it is bounded by 30 s, under `MCP_STREAM_HOLD_MS`), with the reads of one page shared ([#466](https://github.com/ian-pascoe/cloudpid/issues/466); [_Declaring and reading Apps_](mcp-apps.md#declaring-and-reading-apps)).
- **Validation and compiling:** output validation runs in the engine (D9.3; the rule is [The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D17's: `structuredOutput: valid | invalid` with the first errors). TypeBox compiles in the engine only, at discovery and wherever the engine lists tools again (a `-32020` refresh, a `tools/list` request), so no definition reaches the host's catalog unchecked, through its interpreted fallback, cached by schema hash (2,000 entries), yielding between schemas (a Worker's clock stands still while it computes, so it cannot measure ~20 ms); nothing compiles at module scope. A `tools/call` whose schema is not cached (after a restart or a deploy) compiles it then.

## Discovery and the MCP inventory

- **What discovery does** (D7): the cached era (or a probe), connect, `tools/list` and `prompts/list` within their bounds, record the resources capability, compile schemas, store, and recompute the versions. It is single-flight per `conn`, ≤3 at once per object and ≤2 stdio per Workspace, and the version bumps only when content changes. **As built** ([#449](https://github.com/ian-pascoe/cloudpid/issues/449)): HTTP servers only, through the engine's `discover` with the `conn`'s era row as `prior` and its `${NAME}` values from `mcpServerValues`; the engine compiles and checks the tools, the host bounds them, stores the inventory and status, and recomputes the versions. A discovery passes the engine no hooks: it runs as a fiber in the host's runtime, often past the invocation that started it, and an `untilAborted()` from that invocation would cut it about 72 s later ([#409](https://github.com/ian-pascoe/cloudpid/issues/409) answer 2). The RPC itself is the object's pending I/O, which keeps it in memory for up to 15 minutes ([Durable Object lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/), "Pending operations prevent eviction"); that is the documented behaviour, not yet verified on a deployed stage, where #409's 72 s also falls inside the 70–140 s idle eviction. A discovery the host interrupts (a set change, a reload, a destroy) is dropped unread, its status put back, and the engine runs it to its own bounds: it runs nothing on the server, so no cancel crosses (a cancel keyed by a call id would reach an arbitrary isolate of the stateless engine), though an interrupted Legacy discovery leaves the `Mcp-Session-Id` it opened on the server until the server expires it. The host waits at most 300 s for the engine (the slowest discovery's own bounds, a Legacy server whose era row is in doubt: three connects and two list walks, 3 × 15 + 2 × 120 = 285 s, and 15 s of slack), and no discovery holds one of the 3 slots past 360 s, counted from when it took the slot: one older is given up at the next demand. A failure on the host's side (the engine out of reach or silent, a discovery past its deadline) is not the server's: its state and failures stay as they were, and it is held back 30 s.
- **The era probe and cache:** the probe runs at first discovery; its outcomes, the cache's lifetime and what drops it are in [_Protocol eras_](mcp.md#protocol-eras). Beyond those: 5xx or a network error makes the server `unavailable`; a cross-origin redirect, a non-`insufficient_scope` 403 or a 2xx that is not JSON-RPC makes it `failed`; 202 or an empty stream runs to the probe's timeout; 401 and 403 `insufficient_scope` follow [_Requests and Legacy sessions_](#requests-and-legacy-sessions) ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D2). `mcp_eras` rows are fed to the engine as `prior`, and `reload` drops them as a `conn` change does.
- **Bounds and problems:** per server ≤500 tools and ≤1 MiB of declarations (in list order; the rest dropped with a problem), descriptions cut at 4,000 characters, `instructions` ≤16 KiB, ≤100 prompts and ≤64 KiB of prompt metadata; a schema TypeBox rejects, an invalid `x-mcp-header`, or `execution.taskSupport: "required"` makes a per-tool problem (which of these still registers the tool: [_Exposure_](mcp-in-a-session.md#exposure); prompt problems: [_The `/` menu and the catalog_](mcp-in-a-session.md#the--menu-and-the-catalog)).
- **Set changes, per name** (D7.1):
  - **a new `conn`:** an HTTP server is discovered at once if the object was used in the last 24 h, else at first demand; a stdio one at first demand of a caller with a Workspace. A kept inventory for that `conn` is served at once.
  - **a changed or removed `conn`:** abort its calls (`ServerChanged`), a best-effort Legacy `DELETE`, `bridge_stop` with `start: false`, close streams, end its Resource watches ("server changed"), then rediscover. A kept MCP sign-in for (source, name, URL) applies again at once ([The agent's changes to MCP servers](https://github.com/ian-pascoe/cloudpid/issues/391) D8).
  - **switched off or `hidden`:** close the connection and streams, end watches, keep the inventory.
  - **only keys outside `conn`** (`description`, `timeout`, `enabled`, `sampling`, `exposure`, `toolExposure`): a version bump, with no reconnect or re-probe.
- **Other triggers** (D7.2): first use; `list_changed` refreshes that one list; TTL (Modern `ttlMs` floored at 1 min and capped at 24 h, Legacy and a Modern server without one 10 min, counted from the host's clock when it stores the inventory), checked on read, serving the stale list while it refreshes; `reload` (`settings_mcp_reload`, `mcpReconnect`) drops eras and Legacy sessions, then rediscovers HTTP servers at once; an MCP sign-in change (`signed_in`, `replaced`, `rebound`, pushed for a server) rediscovers that server's HTTP entry at once, with no Container, when it is not working (`sign_in`, `rejected`, `unavailable`, `not_discovered`, and `failed` or `unknown` a minute after the last try; the `sign_in` trigger skips any backoff's hold, and a discovery of that server already running is interrupted and started again), and a pull that finds the sign-ins revision moved without a push asks only the servers at `sign_in` or `rejected`; `signed_out` follows [_Sign-out_](mcp-sign-in.md#sign-out).
- **States** (D7.4):
  - `connecting`: one older than 120 s at wake returns to its previous state with no backoff.
  - `sign_in`: waits for an MCP sign-in change; calls fail fast with no network call, and a discovery at a reload or a set change makes none either while the Registry still says `required`.
  - `unavailable`: demand-driven backoff of 30 s, 1, 2, 5, then 10 min; a call still tries at once.
  - `failed`: no automatic retry; a set change, reload, sign-in change or call retries it, at most once a minute per server. An inventory it already has is kept.
  - **The full list** (`MCP_SERVER_STATES` in `@cloudpid/mcp/types`): `not_discovered` (in the set, never asked yet), `connecting`, `connected` (discovered; current or refreshing), `sign_in`, `rejected` (a second 401 with a fresh token), `unavailable`, `failed`, `skipped` (its definition cannot be used yet: a `${NAME}` that resolves to nothing, looked at again after a minute) and `disabled` (switched off, or `hidden` by its own `exposure`; its inventory kept). The fallback member is `unknown`: a state a newer build stored or sent reads as it, and it reads as `failed` ([_Deploys_](mcp.md#deploys)). `settings_mcp_*` reports `connected`, `needs_sign_in`, `failed` or `connecting` ([_Results_](mcp-configuration.md#results)).
- **The first request's wait:** a server with an inventory is never waited for. `requestStart` waits ≤10 s (`waitFor`, `waitMs`) only for servers with none yet whose Exposure can yield `direct` tools, and the wait ends for a server at `sign_in`, `unavailable` or `failed` (as built, at any state but `connecting`); the rest discover in the background. Only a caller with no `known` version waits: a Session's first request, before it has built tools ([MCP tools in a Session](https://github.com/ian-pascoe/cloudpid/issues/381) D7).
- **Stdio discovery** runs in the calling agent's own Workspace Container (a subagent's Subagent Workspace included), never `build:<env>`; the inventory is per Environment by `conn`, so every Workspace's Sessions share it (D4).
- **Who may start a Container** (D4.1, D11.3): only a `workspace` a live caller supplied. `requestStart` finding no inventory for a stdio `conn` (any Exposure) and `request` (calls, prompt gets, the agent's reads, Attached resource reads, and `ui/html { uri }`, which reads in the Workspace the request names and so may start its Container; an App's read beside or after its call uses the call's Workspace) may; `ui/html { hash }` reads only the host's own storage and never does; `servers({ waitMs })`, completions (`not_running`), previews, gap re-reads, listens, Settings and composer reads never do, and every background request uses `start: false`. TTL refreshes and `list_changed` use only a running process.
- **Stdio rediscovery is narrow** (D4.2): no inventory yet; a set change or reload; `list_changed` from any process on any stream; TTL from a running process; `-32602` for an unknown tool. When two Workspaces' processes of one stdio server list different tools, the latest discovery wins (a known limit). **As built** ([#460](https://github.com/ian-pascoe/cloudpid/issues/460)): a changed `conn` is met as _no inventory yet_, a reload as a TTL that ran out (a server with no inventory is _no inventory yet_), and TTL and `unavailable` refreshes use `start: false` (see _As built — the host_ under [_The stdio bridge_](#the-stdio-bridge)); `list_changed` and `-32602` are not built.

## Requests and Legacy sessions

- **One connection** per HTTP server, or per (stdio server, Workspace).
- **Legacy sessions** ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D5, D15): a row per connection holds `{ sessionId, protocolVersion, serverInfo, capabilities, instructions, initializedAt }`. On wake the engine rebuilds the transport with `sessionId` and `protocolVersion`, so the SDK skips `initialize`; the resumed client has no capabilities, so the core serves them from the row and runs with `enforceStrictCapabilities: false`. The GET stream is not resumed: the span without it is a gap ([ADR-0032](../adr/0032-a-resource-watch-is-held-while-its-conversation-runs-and-checked-by-re-reading-after-every-gap.md)). A 404 on a known session drops it, initializes fresh and resends once, `tools/call` included (the request never reached the server); a second 404 is `failed`. On a Modern server a 404 is an era drop instead. A session whose declared capabilities differ from what the entry now asks (a `sampling` change) is re-initialized at its next use, with `conn` and the inventory unchanged ([Sampling](https://github.com/ian-pascoe/cloudpid/issues/387) D2.4).
- **Remote Legacy SSE resume:** decided as kept, with the server's `retry` clamped to 0.5–10 s, and the request aborted after 2 resumes fail in a row; not built yet ([#542](https://github.com/ian-pascoe/cloudpid/issues/542)). Every connection, Legacy included, uses `maxRetries: 0`, so a Legacy request stream that ends without its answer is a `Cut` ([_Packages and objects_](mcp.md#packages-and-objects)).
- **List cache ([#471](https://github.com/ian-pascoe/cloudpid/issues/471); `apps/server/src/mcp/list-cache.ts`, `resources.ts`):** `McpHost.request` answers `resources/list` and `resources/templates/list` one page at a time and `resources/read` through the engine's `resources/read`, with the Session's `ctx` (a Legacy question on a read takes `ctx.answers` and `onInput` as a call's). The host keeps a Modern server's page in memory for its `ttlMs` (capped at 24 h; `cacheScope` read as `private`, which the key's auth context makes safe), under a key of the connection, the Workspace, a SHA-256 of the URL, the access token and the resolved headers (a stdio server's command, arguments, environment and directory), the method and the cursor. A Legacy page, a read, a streamed page (over 1 MiB, passed on unread) and an entry over 4 MiB are never kept. The bounds are 4 MiB an entry, 4 MiB in one host object's cache, and 8 MiB in the isolate: each host object builds its own cache, and every cache charges one isolate-wide budget, which drops the least recently used entry of any cache when it is passed. Each entry holds the era and `probedAt` it was made under, so a re-initialize or another protocol version never serves it, and a definition change (the `conn` changes) and a removed server drop it. A stdio process's end drops its pages when an engine round of that server next sees a new spawn id, so until then pages from the ended process can be served, for at most their `ttlMs`; a resource `list_changed` does not invalidate the cache yet (it waits on the listens, [#478](https://github.com/ian-pascoe/cloudpid/issues/478)). The cache is a speed-up only: an isolate that restarts asks the server again. A list's page is asked of the engine as the new `resources/list_page` and `resources/templates/list_page` ops, so an engine from before them answers `Unsupported`, which the Session reads as a failed list. A read of a `ui://` resource that is an App's carries `app` (the engine's `resources/read`, and the `x-cloudpid-app-read` header the core's tap strips): it alone is bounded by `MCP_APP_READ_BYTES`; any other read has 16 MiB.
- **Timeouts** ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D15):

  | Request                                               | Timeout                                                                                                                                   |
  | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
  | probe or `initialize`                                 | 15 s                                                                                                                                      |
  | through the bridge (Container start, spawn and probe) | 60 s                                                                                                                                      |
  | a list                                                | 30 s a page, 120 s a walk                                                                                                                 |
  | `tools/call`                                          | the entry's `timeout` (default 60 s), reset on progress, enforced in the host; the Session's RPC wait is capped at the timeout plus slack |
  | `resources/read`, `prompts/get`                       | 30 s, or the entry's lower `timeout`                                                                                                      |
  | `completion/complete`                                 | 5 s                                                                                                                                       |
  | listen ack                                            | 10 s                                                                                                                                      |
  | `tasks/*`                                             | 30 s each                                                                                                                                 |

  A call's timeout pauses while a Legacy question on it waits for the owner ([_Questions_](mcp-server-requests.md#questions)).

- **Byte limits** (D16), counted in the `fetch` wrapper over the raw body or the whole SSE stream as bytes arrive; a `Content-Length` over the limit aborts before reading: 16 MiB for `tools/call`, `tasks/get`, `resources/read`, `prompts/get` and each list page; 1 MiB for `completion/complete`, `server/discover`, `initialize` and each event on a listen or GET stream. A `tools/call` over the limit is an error result, never truncated: "over 16 MiB and dropped; the tool may have run" (`details.error: "too_large"`).
- **Tokens and 401/403 at the connection** ([Signing in to remote MCP servers](https://github.com/ian-pascoe/cloudpid/issues/390) D1.9, D1.10, D6, D7.2): before connecting an OAuth-capable HTTP server the host asks `mcpAccessToken`; `unavailable` makes the server `unavailable` with no tools and no network call, and so does `required` for a server that is already `sign_in` or `rejected`; any other `required` connects without a token (a server that needs no sign-in has none), and a 401 then makes it `sign_in`. A 401 at `initialize` or `server/discover` without a token makes it `sign_in`, with no retry. A 401 with a token asks again with `stale` and retries once; a second one is reported `rejected`, tokens kept. 403 `insufficient_scope` fails the call and reports `step_up`. A 401 on an entry with an `Authorization` header is `failed`, never `sign_in`. **As built (#454):** the token goes in the discovery call's target `headers` (a background call has no `auth` hook); the retry is one more engine call with the token the Registry hands back for `stale` (none when it is the same token); `required` for a server that is not already `sign_in` or `rejected` connects with no token, since a public server has no sign-in; `step_up` is `sign_in`, `rejected` is `rejected`, `refresh_failing` is `unavailable`; an entry whose own `Authorization` header is set is never given a token and never reports; a token is only sent to a URL within its sign-in's resource. A discovery from a sign-in change has the trigger `sign_in` (due as _Other triggers_ says); a transition is reported to the Registry once, with the challenge of the 401 or 403. The request path's `auth(stale)` is `engineAuth` over the same cache: `McpHost.request` passes it to the engine for a server with a token, and reports what the call answered by the same rules ([#452](https://github.com/ian-pascoe/cloudpid/issues/452); [_Tokens reach the host object_](mcp-sign-in.md#tokens-reach-the-host-object)). **A server that signs in on its own** ([#464](https://github.com/ian-pascoe/cloudpid/issues/464); [_Client Credentials_](mcp-sign-in.md#client-credentials)) is asked the same way, with outcomes of its own: it never connects without a token, and no token (the Registry's `failed`), a 401 that a renewed token does not cure, and a 403 `insufficient_scope` all make it `failed` with a problem, never `sign_in`, `rejected` or `step_up`, and nothing is reported to the Registry. Its target declares the OAuth Client Credentials extension (`extensions`). The request path does the same: no token, and the engine's `SignInRequired` and `StepUpRequired` after the one retry with a renewed token, fail the call as `Unreachable` with the problem, never as a sign-in the agent could ask for, and nothing is reported. The token cache, resource binding, `redirect: "manual"` and `[REDACTED]` are in [_Tokens reach the host object_](mcp-sign-in.md#tokens-reach-the-host-object); what a sign-out closes is in [_Sign-out_](mcp-sign-in.md#sign-out).
- **Listens** ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D12): at most one `resources/subscribe` set or `subscriptions/listen` per server, carrying the list-change flags the host wants (it never opens one for prompts alone); a filter change opens the new listen and closes the old once acknowledged, so two may be open. The core never reconnects a listen or GET stream: every end is `remote`, a gap the host handles by reopening and gap-checking at the next `requestStart` of a watching conversation ([ADR-0032](../adr/0032-a-resource-watch-is-held-while-its-conversation-runs-and-checked-by-re-reading-after-every-gap.md); holding rules in [_Resource watches_](mcp-in-a-session.md#resource-watches)).
- **Outbound requests** go through the guarded `fetch` and the queue of 5. `clientInfo` is `{ name: "cloudpid", version: <deploy> }`. `traceparent`/`tracestate` go in `_meta` only to cloudpid's own bridge, never to remote servers; `baggage` is never sent.

## The stdio bridge

- **Why a bridge:** a Container port reached through `getTcpPort(p).fetch` carries a long-lived stream with no platform time limit, and the Container and its processes survive a Durable Object restart; `exec` with `pty` breaks JSON-RPC framing, and no existing bridge (supergateway, either mcp-proxy) does lazy shared children with server→client forwarding ([Can a Cloudflare Container carry a long-lived stdio MCP stream?](https://github.com/ian-pascoe/cloudpid/issues/376); proven in [A stdio MCP server reached as Streamable HTTP through a Container bridge](https://github.com/ian-pascoe/cloudpid/issues/383)).
- **The bridge:** one small Node script in the sandbox image (`apps/sandbox-image`), started by the image's supervisor at each Container start, listening on `0.0.0.0` at a fixed `MCP_BRIDGE_PORT` outside the Container preview ports. It keeps nothing across a stop and needs nothing restored. **As built** (#441; the values are `@cloudpid/sandbox-image/mcp-bridge`'s, which the script repeats and a test keeps equal): `apps/sandbox-image/image/cloudpid-mcp-bridge.ts`, a dependency-free TypeScript file that Node runs by stripping its types, copied to `/usr/local/share/cloudpid/mcp-bridge.ts`; it imports no MCP SDK and nothing of cloudpid's at runtime (its type imports are erased by type stripping; the import rule, [`mcp.md`](mcp.md#packages-and-objects)), and its shared constants and wire types are in `@cloudpid/sandbox-image/mcp-bridge`, which the engine and the Workspaces Worker import, since the script itself is copied into the image alone. `MCP_BRIDGE_PORT` is 17781. The supervisor runs it with the Node the image's base `mise.toml` installs (`mise which node`, run against that file so it needs no Workspace config), only when the launch's environment has `CLOUDPID_MCP_BRIDGE_TOKEN` (the bridge exits without one), its lines going where computerd's do; the supervisor then unsets the token, so computerd and its commands never see it (D5.2); it does not restart a bridge that exits, so a dead bridge is mended by `container_restart`. A request is `POST /mcp` (or `GET /mcp` with a Legacy session) and names its server in `x-cloudpid-stdio-config`, the base64url of its config's JSON; the key is the SHA-256 of the config's canonical form (`mcpBridgeKey`). A child gets only `PATH` and `HOME` from the bridge, plus the config's `env`: never the token. Children lead their own process groups, so stopping one stops what a launcher (`npx`, `uvx`) started.
- **Bridge token** (D5.2): the Workspace DO mints a 256-bit token at each Container launch, keeps it in the launch record, hands it to the bridge as `CLOUDPID_MCP_BRIDGE_TOKEN`, and adds it as `Authorization: Bearer` on every forward; the bridge checks it on every request. The engine and the host never see it. It is defence in depth: the agent is root in the Container. **As built** (#448): `ContainerLaunch` (`apps/server/src/workspace/launch.ts`) mints it (256 random bits, as hex) in `LaunchRecord.bridgeToken` and sets `CLOUDPID_MCP_BRIDGE_TOKEN` in the launch's environment, in the retry from the image after a refused snapshot too; computer's restart is a launch, so it mints another and replaces it in the record (making the record when there was none). A reconnect to the running Container asks for the token it launched with, since computer relaunches a Container whose environment differs; one launched before tokens were kept is asked for none, runs no bridge, and gets one at its next launch (`container_restart`). No line the launch logs carries it.
- **Children** ([A stdio MCP server reached as Streamable HTTP through a Container bridge](https://github.com/ian-pascoe/cloudpid/issues/383) decision 7): a request names its server by its config (`command`, `args`, `env`, `cwd`) in a header; the key is the config's hash, so a changed config is a new server. A Legacy `initialize` without a session spawns (replacing a live child of that key) and answers `Mcp-Session-Id` = the spawn; a stale session gets 404. A Modern request goes to its key's child, spawned if none. Children are shared by every caller, lazily spawned, and forgotten at every stop.
- **Eras at the bridge** ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D4): the engine passes the host's cached era as `x-cloudpid-era`; the bridge probes a child on stdin with `server/discover` once per spawn unless the hint names an era, and an exit, any other error or 15 s of silence means Legacy (the child is respawned and sent `initialize`). It presents the child at its own era: for Modern it answers the engine's `server/discover` with the child's result; for Legacy it answers 400 with no Modern error. For a Modern child, bodies pass verbatim with ids rewritten and `Mcp-*` headers stripped, request-scoped progress and logs go out on the POST's SSE, a closed POST becomes `notifications/cancelled` on stdin, `subscriptions/listen` streams back and every open listen ends `remote` when the child exits, and a request the child sends goes to the stderr tail; `Mcp-Session-Id` is used only for Legacy children. The hint is `x-cloudpid-era: legacy|modern`. A probed child that answers Legacy is stopped and the verdict kept for its key until a Legacy `initialize` spawns it again or a hint of `modern` overrides it; a sessionless request that is not `initialize` for a Legacy key is 400 (`-32600`) without spawning. `DELETE` is 405: a shared child is not ended by one caller (the control call stops it).
- **Messages:** request ids are rewritten to the bridge's own, so callers never collide on a shared child. Server→client messages go to the stream of the request their progress token names, else the newest request in flight, else the GET stream, else wait for one. A caller that disconnects cancels its request (`notifications/cancelled`). A Legacy child's server→client requests (sampling, elicitation, roots) travel on the call's own SSE stream, and their answers come back as POSTs (202).
- **Responses and control** (D5.3, [Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423) D1.2): every response carries `x-cloudpid-spawn` (the spawn id) and `x-cloudpid-bridge: <level>`. `GET /_bridge/status` lists children, spawn ids, exits and each stderr tail (≤64 KiB); `POST /_bridge/stop { key }` stops one. Neither control call ever spawns a child. The bridge reports a child's exit, which ends that process's Resource watches ("server process ended"). `GET /_bridge/health` answers readiness for the Workspace DO's poll (`200 { "status": "ok" }`; D5.1 only implies the poll). **As built:** every call, the control ones too, needs the token (401 otherwise, still with `x-cloudpid-bridge`); `x-cloudpid-spawn` is on every response about a child, a stale session's 404 and a Modern request's 400 included (the live child's, when there is one) and absent from health, status, stop and a refusal; status lists live children and the last exit of each key that has none (`{ level, children: [{ key, spawnId, command, args, cwd?, pid?, era, state, startedAt, inFlight, listens, getStream, queued, exit?: { code, signal, reason?, error?, at }, stderrTail }] }`, never a server's `env`; the tail is the last 64 KiB in bytes, cut on a UTF-8 character); `POST /_bridge/stop { key }` answers `{ stopped }` once the process group is gone (SIGTERM, SIGKILL after 2 s). **A child that exits ends the streams of its requests and listens with no answer** (never a JSON-RPC error), which the engine reads as `Cut`; the status then names why (D5.4). A spawn that fails (`ENOENT`) is such an exit, with `error: "spawn failed: …"`.
- **`WorkspaceMcpBridge`** (D5.1): a new entrypoint of the Workspaces Worker, `mcpBridge(workspace, request, { start, use }) → Response`, for `ws:*` objects only; it answers 404 `no_workspace` when the Workspace DO has no record of itself. A stopped Container with `start: false` answers 503 with `x-cloudpid-container: stopped`; with `start: true` it starts the Container as a command does (runs `true` on its container backend, `writes: false`, single-flight), then polls `/_bridge/health` every 250 ms for up to 15 s, inside the 60 s bridge timeout. **As built** (#448; `apps/server/src/workspace/mcp-bridge.ts`, which the Workspace DO's `mcpBridge(request, options)` serves and the entrypoint in `worker.ts` hands to):
  - **No record:** a Workspace has a record of itself when a Session has used it (every call it makes to the Workspace counts: its readying starts with `skillSetHash`, then the Secrets and Skills writes, and none needs a file operation, so an Environment with no Repos and no Skills is a Workspace too), when it was prepared as a spare, or when computer has indexed its mounts (`_vfs_mounts` has a row). A destroyed one's storage is wiped, marks included. A name that is not `ws:<id>` (a Build's object) is `no_workspace` too, and no Container is started for either. So `no_workspace` means "never used, or destroyed". **Precondition:** a Session's readying is lazy, so before `requestStart`, or any `McpHost` call that may reach the bridge, the Session awaits a call to its calling Workspace (`noteSessionActivity`, for one) so the Workspace has marked itself; that is what makes `no_workspace` mean destroyed, as the host reads it (D11.2). A Subagent Workspace deleted while its Session's heartbeat still runs can answer as one that exists until its object resets (a known gap, `spare.ts`).
  - **The poll** runs after a start this request made (or joined), and for a Container found running whose launch is younger than the poll's time (a command or `container_restart` has only just started it, and its bridge may not be up), unless its bridge has answered or failed already. Any other Container found running is not polled, so a status check with `start: false` never waits for a bridge. A request that arrives in the middle of a poll shares it, and each attempt takes no longer than the interval. It reads the launch's token again at each attempt, since the launch is recorded after the platform has started the Container. A poll that fails (15 s, counted in attempts) is remembered for that launch: later requests answer `bridge_unreachable` at once until a new launch has a token of its own (`container_restart`). After a poll that succeeded, a bridge that exits fails fast.
  - **Refusals** are JSON `{ error, message }`, built in one place, with `cache-control: no-store`; their codes and the options are `@cloudpid/sandbox-image/mcp-bridge`'s (`McpBridgeRefusal`, `McpBridgeOptions`): 404 `no_workspace`; 503 `stopped` with `x-cloudpid-container: stopped`; 502 `start_failed` (the Container did not run `true`); 502 `bridge_unreachable` (the health never answered, nothing answers the forward, the bridge answered 401 to the launch's token, or the launch kept none), whose message says `container_restart` starts a new bridge; and the fallback 502 `bridge_failed` for anything unforeseen, which is also what a caller reads a code it does not know as (`mcpBridgeRefusalCode`). Any other status is the bridge's own, passed on with its headers and body.
  - **Holds:** a touch or hold the idle stop cannot record only shortens the idle time, and the request goes on. The response body is passed on chunk by chunk, and the hold ends when it ends, fails or is cancelled. A cancel of a quiet stream reaches the Workspace DO when the platform tells it, at the stream's next chunk at the latest; the hold cap bounds what is left.
- **Uses and holds:** `use: true` (calls, prompt gets, reads, completions, discovery, MCP task polls) is `IdleStop.touch()`, then `hold({ writes: true })` until the response body ends, fails or is cancelled (a stdio server may write the disk); never `noteActivity`. `use: false` (the GET stream, listens, subscribe and unsubscribe, bridge control) neither touches nor holds. An open session, an idle child, a stream and the server's own messages are not uses, so a stdio server never keeps the Container awake between requests, and its state across an idle stop is lost. A background MCP task's polls are requests, so they do keep it, within the Hold cap ([MCP tasks as durable long-running requests](https://github.com/ian-pascoe/cloudpid/issues/389) D4.4).
- **Idle stop and the Hold cap:** an idle stop never cuts a call, since the call holds the Container. A call in a Run is covered by the Run's heartbeat (activity), so the Hold cap cuts it only after an hour with no activity; a Legacy stdio question waiting on the owner (≤10 min) stays under it, and a stdio MCP task in the background lives within it, with **Keep the Container** to extend it ([_MCP tasks_](mcp-server-requests.md#mcp-tasks); [`container.md`](container.md) → Idle stop, Hold cap). `container_restart`, a resize, the memory guard, an OOM kill and a held stop can cut a call; a deploy does not. The memory guard's `--avoid` list spares the bridge (its process is named `cloudpid-mcp-bridge`; [`container.md`](container.md) → Memory guard): stopping it would cut every stdio server at once, where the guard's choice, the largest process, is a server that grew.
- **Roots:** only bridge connections declare `roots`, offering the Repos of the Workspace whose Container runs the server ([_Roots_](mcp-in-a-session.md#roots)).
- **As built — the engine** ([#460](https://github.com/ian-pascoe/cloudpid/issues/460); `apps/mcp-worker/src/bridge.ts`): `McpEngineTarget` is `http | stdio`; a stdio target (`kind: "stdio"`, `workspace` `ws:<id>`, `command`, `args`, `env` resolved, `cwd`, `start`, `roots`) is connected at one fixed URL through a `fetch` that hands each request to `MCP_BRIDGE.mcpBridge(workspace, request, { start, use })`, carrying the child's config in `x-cloudpid-config` and the era row's hint in `x-cloudpid-era`. A POST is a use and may start the Container when the target says `start`; the Legacy GET stream is neither. Connects, probes and `initialize` take up to 60 s (`connectTimeoutMs`). Every response must carry `x-cloudpid-bridge`: one below `MCP_BRIDGE_MIN_LEVEL` (1), or with none, fails the call as `Unsupported` ("this Container runs an older bridge; restart it"), which the host reads as `failed`. A refusal of `WorkspaceMcpBridge` is thrown as the core's failure, which its tap passes through: `no_workspace` → `Unreachable` with status 404 ("The Workspace no longer exists"), `stopped` → `Unreachable` with `stopped: true`, `start_failed` and `bridge_unreachable` → `Unreachable` with no status (never reached the server), `bridge_failed` and a code this build does not know → `Unreachable` 502. The results gain an optional `spawn`, the last `x-cloudpid-spawn` heard. Roots are declared only on a stdio target's connection (`McpDeps.roots`; an empty list still declares `roots`), never with `listChanged`: a Workspace keeps the Environment's Repos from when it was made, so they do not change under a running server.
- **As built — the host:** a stdio server is discovered **only on demand**, by a `requestStart` whose `caller.workspace` names the caller's Workspace (`isDue`, `startDue`'s `workspace`), in that Workspace's Container, which the discovery may start (`start: true`; no other caller does). The server's target is built as an HTTP one's is (`targetOf`, with the `workspace`): its `env` through `mcpServerValues`, which for a stdio server in a Workspace also answers `repos` (the Workspace's own, from the Registry's record of it; a Repo's entry gets only its Repo), which become the Roots (`file:///workspace/<directory>`, named by slug). A stdio server's state is its status's like any other (`skipped` only for a `${NAME}` that resolves to nothing). A stdio server's discovery is a discovery like any other, with these differences: **only one with no inventory (never discovered, or dropped by a reload) may start a Container** (`start: true`); a TTL refresh or an `unavailable` retry of a server that has an inventory uses `start: false` (`discoverOne`'s `mayStart`), and when the Container is not running (`Unreachable` with `stopped`, the bridge's `stopped` refusal, or the 404 of a Workspace that is gone) it is skipped quietly: the status and inventory are kept and the next try is a minute later, never a failure (any other failure of the refresh, a bridge that does not answer in a running Container included, counts as one and keeps the inventory; the skip does reset an `unavailable` server's backoff to that minute, while the Container stays stopped, and tells the `McpProcessEnded` handler of a gone Workspace every time, so a handler must be idempotent). A `failed` server with no inventory is tried again by a live demand at most once a minute, with `start: true` (accepted: a server that keeps failing may start a stopped Container once a minute while the caller keeps asking). **A reload** keeps the inventory of each stdio server that has one, so its tools stay served and built calls still find them: it is expired (`ttlUntil` 0) and its hold cleared (`nextRetryAt`, and the failures of a `failed` one), all in one synchronous write, and nothing is started. The next live demand that names a Workspace refreshes it with `start: false`; if the Container is stopped that is the quiet skip above and the old tools stay served. A stdio server with no inventory goes back to never discovered (`not_discovered`), for that demand to discover, starting the Container if it must. **A set change** needs nothing of its own: an entry whose definition did not change keeps its `conn` and inventory, and a changed one is a new `conn` with no inventory, discovered at first demand. No more than two stdio discoveries run for one Workspace (`MAX_STDIO_DISCOVERIES_PER_WORKSPACE`, `McpDiscovery.workspaceSlots`, on top of the host's 3 slots), and a call takes one of the 4 per (server, Workspace). Left for later: `list_changed` and `-32602` rediscovery of a stdio server, which need a running process to ask.
- **Cold starts:** time to a stdio server's `initialize` answer was 2.6–6.2 s cold on `cpu-1`, 0.6–0.95 s warm, and 0.8–1.1 s from caches a Snapshot kept, plus the Container's own start when stopped. The npm and uv caches are on the Container's disk, so only a Workspace's first call downloads; an unpinned `npx -y` asks the registry at every start. No preinstall; warming the caches in a Build is left for later (the map's "Fast stdio cold starts").
- **Secrets in a stdio server's `env`** are readable by the agent's commands through `/proc/<pid>/environ`: accepted, as a Secret already reaches commands as `$PI_SECRET_*` and output redaction applies.

## Failures and cuts

- **A stream that ends without its answer** fails its request at once as `Cut { mayHaveRun: true }`, never waiting for a timeout (the `fetch` tap aborts the request's signal, since the SDK drops `onRequestStreamEnd`).
- **Naming a stdio cut** (D5.4): from the bridge's status, checked with `start: false`: "Container stopped", "stdio server exited (code/signal)" with the last 2 KiB of stderr, or "cut". **As built** ([#460](https://github.com/ian-pascoe/cloudpid/issues/460)): the engine asks `GET /_bridge/status` (5 s, `start: false`, `use: false`) for a cut of any step, including a `tools/call`'s failure that comes back as a result, and renames only the message (the cut's `mayHaveRun` stays). The stderr tail the bridge keeps is scrubbed of the call's Secrets **whole, before** its last 2 KiB are taken (so a Secret that straddles the start of the quote is found), and a quote cut inside a line starts at the next line (kept as it is when no line follows the cut, as with one long last line).
- **Retries** ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D14, D15): after a cut, read-only requests (`*/list`, `resources/read`, `prompts/get`, `server/discover`, `tasks/get`) and `tasks/update`/`tasks/cancel` once, after a re-initialize where needed; `completion/complete` never; `tools/call` never, in either era: the agent gets "cut before its answer arrived; it may or may not have run". 408, 429 and 5xx retry read-only requests once after 1 s (honouring `Retry-After` up to 10 s). `-32020` (a header the server rejects) refreshes `tools/list` and retries once. A `tools/call` is sent again only when the server refused it before it ran: a Legacy 404, a Modern era drop, or a Legacy `-32042` ([_Elicitation requests_](mcp-server-requests.md#elicitation-requests)).
- **Lost ends** (D6.2 as amended by [Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423)): a dead host makes the Session report a cut with `details.cut: "host_lost"` (also for `Network connection lost.`, whichever end lost it), and its live Legacy questions expire. A dead Session makes its callbacks reject, so the engine aborts the server request and the result is dropped; the `mcp` tool is `replay: "safe"` with memo markers, so the Session's rerun, finding `mcp.sent` and no wait to resume, settles the call "may have partially run" ([_The waiting-question record_](mcp-server-requests.md#the-waiting-question-record)). A real cut between host and engine is `Cut { mayHaveRun: true, lost: "engine" }` (the host sets `lost` when the engine's RPC breaks, [#458](https://github.com/ian-pascoe/cloudpid/issues/458)), which the Session shows with `details.cut: "engine_lost"`, as it does a result stream that breaks while it reads it; any other `Cut` is shown without one; a cut listen is a gap.
- **Learned at the next contact, with no push** (D11.2): a destroyed Workspace (404 `no_workspace`), a `container_restart` or a resize (a changed spawn id, a 404, or a listen ending `remote`).
- **An old bridge:** an `x-cloudpid-bridge` level below the engine's minimum makes the server `failed` ("this Container runs an older bridge; restart it"); the owner restarts the Container, and the server is tried again by the next demand after a minute.

## Deploys

The deploy strategy (deferred code updates, `max_delay` 300 s), the rule that every MCP edge only gains, and each edge's gate are in [_Deploys_](mcp.md#deploys) and [`workers.md`](../development/workers.md#deploys-and-durable-object-code-updates). What the host and the Sessions do with calls in flight ([Deploys under deferred Durable Object code updates](https://github.com/ian-pascoe/cloudpid/issues/423) D3–D5):

- **A replaced host** (a code update reached it mid-call) still returns its results. Its writes for a call (era, Legacy session, inventory, status, App HTML) are best-effort: a refused write never turns a result into an error, a result never claims what was not kept, and what is lost heals as after a restart (a 404 → initialize, discovery reruns, versions are content hashes). At any failed storage operation, reads included (never matching the error's text), it stops background work (as built: a write `requestStart` or `servers` makes is best-effort, and a read they cannot make answers `HostFailed`): no new discovery or refresh, and its listens close; the new instance reopens and gap-checks at the next `requestStart` of a watching conversation. While both run, the caps count per instance and a listen may be held twice until its swap.
- **As built** ([#467](https://github.com/ian-pascoe/cloudpid/issues/467); `apps/server/src/mcp/{discovery,host,request,app-reads,app-store}.ts`):
  - **One switch stops background work.** `halt` (`discovery.ts`) sets it, and every place that meets a failed storage operation calls it, a read included, never reading the error: the best-effort writes of a call (`attemptOrHalt`: the rows the engine changed, an App's page), the writes of a request start, a reload and a discovery (`writeOrHalt`, or the discovery's own fiber dying), the server logs a call could not keep, a Registry pull whose storage failed, an App read that dies of a storage failure, and every method that answers `HostFailed` for what it cannot read or keep (`orHalt`: `requestStart`, `servers`, `serverLog`, `request`, and `apply`'s set, destroy, reload and sign-in changes). A Registry that cannot answer a pull is no storage failure and halts nothing. Once set, no discovery or refresh starts (`startDue`) and no call starts the read of an App's page (`startCallRead`); a mount's own `ui/html` read, a live caller's demand, still answers. A discovery already running is left to end, and halts at its own first refused operation.
  - **Cache upkeep is best-effort:** noting that a View mounted a page (`touchApp`, which decides the eviction order) is a write apart from the read (`readApp`), so a page the host read is served even when the note is refused. A page whose keeping was refused is returned to the mount that read it and never named as kept (`AppOutcome` `unkept`), and its call's `Completed` has no `app`.
  - **Not built yet:** the listens and the watch row of a `resources/read` with `watch: true` (D3.2, D3.3) come with Resource watches ([#478](https://github.com/ian-pascoe/cloudpid/issues/478)), which close at `halt` and answer a refused watch row with the content and the watch not started. The no-answer for a question a replaced Session cannot store (D4.2) is [#480](https://github.com/ian-pascoe/cloudpid/issues/480)'s, and the best-effort `tasks/cancel` (D4.3) [#488](https://github.com/ian-pascoe/cloudpid/issues/488)'s.
- **A replaced Session** keeps the call's invocation, so the call runs to its end within its timeout; its result is dropped, and the new instance settles it through pi-durable's recovery ("may have partially run"; never retried for `tools/call`). Nothing hands the result over and nothing cancels the call. A question reaching it gets the no-answer for its kind, and an MCP task it cannot record gets a best-effort `tasks/cancel` ([_The waiting-question record_](mcp-server-requests.md#the-waiting-question-record)).
- **An `McpWorker` deploy cuts nothing:** calls in flight finish on the engine version they started on (15 min observed), and new calls reach the new version.
- **A reset outside a deploy** (a runtime update, an eviction): engine calls whose host died see `untilAborted()` reject and abort; listens end, and the span until they reopen is a gap; Legacy rows are reused; stdio children survive; token, value and validator caches are asked for again; a `connecting` status older than 120 s returns to its previous state; live Legacy questions die ([ADR-0037](../adr/0037-a-modern-mcp-servers-question-is-answered-with-a-new-request-and-a-legacy-ones-lives-only-as-long-as-its-call.md)).

## Telemetry

- **Spans** (D12.1): in the host `mcp.request_start`, `mcp.request`, `mcp.discover`, `mcp.listen`, `mcp.gap_check` and `mcp.registry`; in the engine `mcp.engine.*` children (HTTP status, retries, era drop, re-initialize, bytes). How Workers tracing joins them, and what background work records instead, is in [_Testing and tracing_](mcp.md#testing-and-tracing). Spans never record argument or result values, header values, tokens, resolved `${NAME}` values or full URIs (scheme and host only). `tasks/get` spans are emitted only on a status change or an error and counted otherwise, with an 8-hex hash standing in for the `taskId`; as built ([#455](https://github.com/ian-pascoe/cloudpid/issues/455)) every one is emitted, the hash set before the request is sent, until the follower ([#488](https://github.com/ian-pascoe/cloudpid/issues/488)) can tell the host the status it last saw.
- **Server logs** (D12.2): `notifications/message` reaches the host through `onLog`: `warning` and above becomes a span event (`data` cut to 2 KiB and redacted), and everything goes to a ring of the last 50 per server; never to the model (levels: [_Server logging_](mcp-in-a-session.md#server-logging)).
- **As built** ([#453](https://github.com/ian-pascoe/cloudpid/issues/453); `apps/server/src/mcp/{logs,log-store,status}.ts`, `apps/mcp-worker/src/{logs,calls}.ts`, `packages/mcp/src/{log,connection}.ts`):
  - **Logs ride in the result, not in a hook.** The core asks every server that declares `logging` for `warning` (Legacy: `logging/setLevel` after an `initialize` that opens a session the host keeps, and never for a server that keeps none, in a discovery or a call, since it forgets the level at once; a refusal is ignored. Modern: `_meta` `logLevel` on every list and call) and hears `notifications/message` through `McpDeps.onLog`; with no `onLog`, it asks for none. The engine keeps the call's last 50 as `McpLogEntry` (`at`, `level`, `logger?`, `data`) and returns them as `logs` on `McpEngineDiscovered`, `McpEngineCompleted` and `McpEngineFailed` (gain-only: absent when none came, ignored by a host that does not know it). So a background discovery, which passes no hooks, gets its logs with no callback stub, and the host's `request` ([#452](https://github.com/ian-pascoe/cloudpid/issues/452)) reads `result.logs` the same way, through `recordLogs`. `data` is JSON text, scrubbed (next bullet) and then cut to 2 KiB, in that order so no value is cut in half. A server that answers in plain JSON (a stateless Legacy one) has no stream to log on, so none come.
  - **What the engine scrubs** (`apps/mcp-worker/src/scrub.ts`), from a call's logs, errors and results, a discovery's answer, the tools listed again after a `-32020` and a `tools/list` or `prompts/list` result: every token the call sent; every Secret value the host substituted into the target (`McpEngineTarget.redact`, from `mcpServerValues`' `redact`: the Secrets only, never a Variable, from any header; empty for an entry that references none, absent from a host older than the field); and what the target's credential headers hold, which finds a credential pasted into a header instead of referenced as `${NAME}` (`secretsOf`): the credential after the scheme of `authorization` and `proxy-authorization` (`Bearer x` gives `x`) and a `Basic` one's password, the value of each `name=value` part of `cookie`, and, for any other header whose name has `key`, `token`, `secret`, `auth`, `session`, `passwd`, `password`, `credential` or `signature` in it (a looser match than the names [_Approval_](mcp-configuration.md) refuses as literals, covering `API_KEY`, `APIKEY`, `ACCESS_KEY` and `PRIVATE_KEY` by `key`), its value and the value of each `name=value` part. A header like `X-Org: acme` or `Accept: application/json` is no credential and scrubs nothing. Each value is at least 4 characters, and is found as it is, JSON-escaped, and encoded for a URL path (`encodeURIComponent`) and a query (`URLSearchParams`).
    - **Only string values** are rewritten (`scrubValues` walks the JSON and changes strings, with the same forms of a value): never a key, a number, the shape, or the engine's own fields (`state`, `kind`, `era`, `protocolVersion`, times and ids), so a Secret that is `1759` or `2025` cannot break a number, a date or the rows the host stores, or make a `tools/call` result fail as not MCP.
    - **A name or a key is never rewritten** (a call is made by a tool's name, and the prompt cache keys on it): a tool or prompt whose name, or any key of its declaration (its schema's property names), holds a scrubbed value is **left out**, with a problem that says only its place in the list (`tool #3`) and never the value. A tool's goes in `problems` (`toolsHash`); a prompt's in `promptProblems` on `McpEngineDiscovered` and `McpEngineCompleted` (gain-only; the host keeps it as an `McpInventoryProblem.prompt`, so a prompts-only change never moves the tools' version). One routine (`vetListed`) does this for a discovery, the tools listed again after a `-32020` and a `tools/list` or `prompts/list` result; what stays has its descriptions, schemas, instructions, problems, `serverInfo`, errors and logs scrubbed in place.
    - **It catches accidents**, as `workspace/redact.ts` says of itself: a server that echoes a prefix or a suffix of a value, or the value cut or re-encoded another way, is not caught.
  - **The ring** is `mcp_logs` (migration 4), per `conn`, the last 50, written in the host's discovery and `request` after the result is stored (`recordLogs`); it goes with the `conn`'s status when that is pruned, and a wipe drops it. `warning` and above are also span events `mcp.log` (`level`, `logger`, `data`) on the span that heard them, and the span counts them (`mcp.logs`, `mcp.log_warnings`). The Workers tracer keeps an event only as `event.mcp.log`, the milliseconds since the span began, so the data itself is read from the ring.
  - **Spans:** `mcp.request_start` (`mcp.servers`, `mcp.window_opened`, `mcp.known`), `mcp.servers`, `mcp.server_log`, `mcp.apply` (`mcp.apply_kind`), `mcp.registry` and `mcp.discover` (`server`, `mcp.outcome`, `mcp.era`, `mcp.protocol_version`, `mcp.tools`, `mcp.prompts`, `mcp.problems`, `mcp.state`, `mcp.failures`, `mcp.logs`). The engine's `mcp.engine.discover` and `mcp.engine.request` carry `mcp.server` (the name), `mcp.server.origin` (scheme and host), `mcp.http.responses`, `mcp.http.retries`, `mcp.http.status` (the last), `mcp.era_drops`, `mcp.reinitializes` (the core's `McpConnection.stats()`), `mcp.bytes` (response bytes read) and `mcp.logs`; no attribute is a header, a token, a URL's path or query, an argument, a result or a log's text. `mcp.request`, `mcp.listen` and `mcp.gap_check` come with the code that makes those requests.
  - **The causing trace:** a discovery goes on after the invocation that started it, under whatever context the runtime gives it, so `mcp.discover` records `mcp.cause_trace_id`, the trace ID of the span current when it was started (`currentTraceId` in `@cloudpid/telemetry`: the runtime's own trace ID from the span's `spanContext()`, else Effect's).
  - **For the UI:** `RegistryRpcs` `mcpServers({ environment })`, `mcpServerLog({ environment, server, workspace? })` and `mcpReconnect({ environment, servers? })` (`McpStatus`, `apps/server/src/mcp/status.ts`, `@cloudpid/protocol`'s `mcp-status.ts`). The Registry says which servers an Environment has first (`mcpServerNames`, read-only), so an Environment with none never wakes its host and a name the set does not hold never reaches it. `mcpServers` asks the host for `tools`, `prompts` and `status`, and answers each server with its state, error, counts, problems, tools with Exposure (`resolveExposure` over the entry's `exposure` and `toolExposure`, and over the `tools.offered` of the Environment's Settings in force, its Overrides over Global's, which a Session resolves alike, matched against each tool's model-facing name; so a tool the Session offers directly shows `direct`; the Registry's `getSettingsOverrides` gives them, and a tool name or `exposure` this build does not know reads as `unknown`, `readMcpExposure`), prompts and status, and no entry, URL or hash. `mcpServerLog` answers the ring through the host's `serverLog`; `mcpReconnect` is `apply({ kind: "reload", servers })` for the names the Environment has. Each answer union has a fallback: a host that fails, answers `HostFailed` or `HostUnsupported`, or answers with a tag or shape this build cannot read, is `Unavailable`, never carrying the cause, and a state this build does not know reads as `unknown`, a problem. The stderr tail of a stdio server, and the status UI itself, come later.
  - **A known limit of the spans:** the Workers tracer keeps a span event only as `event.<name>`, the milliseconds since the span began, so the `mcp.log` events show that a log came and when, never its level, logger or data; those are in the ring (`mcpServerLog`). `recordLogs` (`apps/server/src/mcp/logs.ts`) is called by the host's discovery and its `request` ([#452](https://github.com/ian-pascoe/cloudpid/issues/452)) with `result.logs`.
