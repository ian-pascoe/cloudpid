# Agent changes

[ADR-0019](../adr/0019-the-agent-manages-its-environments-and-settings.md) lets the agent manage its Environments; an **Agent change** (GLOSSARY.md) is one change it makes, recorded with its reason. The `environment` extension (`@cloudpid/extensions/environment`) has the first tools, deferred as any later extension's are.

- **The Scope is named, never assumed** ([ADR-0027](../adr/0027-settings-at-two-scopes-with-explicit-overrides.md) → _The agent names the Scope_). Every `environment_*` tool but `environment_list` and `environment_create` takes a **required** `id`, and no tool falls back to the Session's own Environment, so a request meant for Global cannot land in one Environment by default. `*` (Global) is taken only by `environment_get` and the tools that keep something there (those named with the variable tools below); `environment_rename`, `environment_repo_add`, `environment_repo_remove`, `environment_rebuild`, `environment_delete` and `environment_setting_reset` act on one Environment's record or Override, and refuse it. The id of the Session's own Environment is the one `environment_list` marks "(this Session's)"; the system prompt does not name it (a section added there would break the prompt cache), so the tool descriptions point to `environment_list`. A call without `id` fails to decode, before any tool code runs; a call recorded before this rule (no `id`) that an eviction cut off is rerun only for a `replay: safe` tool, and then fails the same way with the missing `id` as its error result, changing nothing, while the model, which sees the new schema, calls again with an `id`.
- **`environment_list()`:** each Environment's id, name, Repos and Build, marking the Session's own. **`environment_get({ id })`:** the Environment's name and Repos, every Container setting in force (size, size limit `maxInstance`, idle time, Container-only paths, variables, Setup and Start Scripts, Toolchains, Spare Workspace), each marked as its own ("overridden here") or "inherited from Global" ([ADR-0027](../adr/0027-settings-at-two-scopes-with-explicit-overrides.md); see [_Container settings_](container.md)), its own variables, the variables kept Global that it does not override and the names of those it does (an Environment's own of the name wins), the names of the Secrets kept for it and of those kept Global that it does not override, each with whether it reaches the Build (never a value), its own Skills (name, description, when saved), the Skills kept Global that it does not override and the names of those it does, and its Build, with the last 1,000 characters of the last failed Build's reason. `id` is required: no Environment is assumed, the Session's own included (`environment_list` marks it); an unknown one is refused, pointing to `environment_list`. **`environment_get({ id: "*" })`** shows the Container settings at Global (its variables among them), each with the Environments that override it (`overriddenIn`), so a change there does not reach them, then the names of the Secrets kept Global and the Skills kept Global; `environment_list` ends with how many variables are kept Global.
- **`environment_variable_set({ id, name, value, reason })`, `environment_variable_unset({ id, name, reason })`:** one variable, by the owner's save's rules (`variableNameProblem`, at most 50 variables, values of at most 4,096 characters); a refusal says why and saves nothing. The `reason` (1 to 500 characters) is required. Unsetting a variable that is not set, or setting the value it has, says so and records nothing. Each result says the change applies at each Workspace's next Container start, adds for the Session's own Environment that `container_restart` applies it now, and says when the change asked for a new Build. Both run alone (sequential), and are not replayed: a rerun after an eviction would record the change again (`replay: unsafe`). Both also take `id: "*"` ([ADR-0023](../adr/0023-variables-for-every-environment.md)), the variables kept Global: the same refusals (a value or reason that holds a Secret the Session holds, anything shaped like a GitHub token, the GitHub App's key or a Secret Reference placeholder; a name the owner's rules refuse; a save that would give any Environment more than 50 variables with its own), and a result that names the Environments whose own variable of the name overrides it and those for which a new Build was asked (each Environment that wants a Build and does not override the name gets a new key). Besides the Container setting tools below (and `environment_container_size_limit_set`), only `environment_get`, `environment_secret_build`, `environment_secret_delete`, `environment_skill_save`, `environment_skill_install`, `environment_skill_update` and `environment_skill_remove` take `*`; the rest (an Environment's record, its Repos, its Build, and `environment_setting_reset`) refuse it, saying what it names.
- **Container settings, one tool each** (the rest of the Container settings the Environment's Container, Setup and Limits sections save; each takes a required `id` and a required `reason`, runs alone and is not replayed, like the variable tools, and is applied, recorded, handed to the Session's own Workspace and followed by the Builds' upkeep as they are). Each also takes `id: "*"`: the setting is then changed at Global, as the variables are, and the result names the Environments that override it (it does not reach them) and those for which a new Build was asked. With an Environment's `id` the value becomes its **Override** (GLOSSARY.md), one equal to Global's too, which a later change at Global does not reach; `environment_setting_reset` makes the field inherit Global's again:
  - **`environment_container_resize({ id, size, reason })`:** the Environment's `instance`. A `size` above the Environment's size limit (`maxInstance`, read first) is refused naming the limit and pointing to `environment_container_size_limit_set` (which waits for the owner's Approval: see _Approval_); the Registry checks it again as the owner's save does. The description lists the sizes with their resources, by memory, and says that this changes the next Container of every Workspace of the Environment (a Container that runs keeps its size) while `container_resize` changes only the current Workspace's Container until its idle stop and no Environment.
  - **`environment_idle_time_set({ id, minutes, reason })`:** `idleMinutes`, 1 to 1,440 (the schema leaves the range to the Registry, so a 0 is refused with the owner's save's message, `idleMinutes: …`). The result names the memory cost of the idle time at the Environment's size (`describeIdleCost`: `containerRates`' memory price, a minute and a whole idle stretch).
  - **`environment_setup_script_set({ id, script, reason })`, `environment_start_script_set({ id, script, reason })`:** the whole bash text (`scriptProblem`: at most 64 KiB of UTF-8, no NUL; empty removes the script). The descriptions say when each runs (Setup: once per content on each Container, after a snapshot restore too when the content is new, and in Builds, so a changed one makes a new Build; Start: at every Container start, restored ones too, and a service must detach) and that a step of one Repo is better in the Repo's own `.cloudpid/setup.sh` or `.cloudpid/start.sh` (ADR-0020). A result says whether a new Build was asked for; it does not echo the text.
  - **`environment_toolchains_set({ id, mise_toml, reason })`:** the text of a `mise.toml` (`toolchainsProblem`: at most 16 KiB of UTF-8, no NUL; empty: the image's base Toolchains). mise reads it, not the save.
  - **`environment_ignore_set({ id, patterns, reason })`:** the whole list of extra Container-only paths (at most 50, each checked by `ignorePatternProblem` as the owner's save checks it: `ignore.0: …`). The result warns that the next Container of each Workspace starts without the Workspace's Snapshot, since a Snapshot is tied to the list (see [_Snapshots_](container.md)), and so from the Environment's Build once there is one for the list, else from the image.
  - **`environment_spare_workspace_set({ id, enabled, reason })`** ([#323](https://github.com/ian-pascoe/cloudpid/issues/323)): `spareWorkspace`. The description weighs new Sessions that start without waiting for the clones and the Setup Scripts against the Container time each spare takes to prepare (see [_Spare Workspace_](workspace.md)). It is no Limit, so it waits for no Approval. After it the Session runs the spares' upkeep for the Environment (`spareUpkeep`, as the main Worker does after the owner's save), which removes the spare when it is off and makes one when it is on and the Environment had a Session lately; the result says so, and that no Container restarts and no Build is asked for.
  - **`environment_setting_reset({ id, setting, reason })`:** takes an Environment's Override of one setting (`instance`, `maxInstance`, `idleMinutes`, `ignore`, `setupScript`, `startScript`, `toolchains`, `spareWorkspace`; its own variables are taken back with `environment_variable_unset`) back, so it inherits Global's value again, and each later change of it there. It refuses `id: "*"` (Global inherits nothing: its value is changed with the setting's own tool at `*`). A field the Environment does not override says so and records nothing, so the tool is `replay: "safe"`. A reset the owner's save would refuse (a size that would then be above the size limit) is refused with its message. Resetting `maxInstance` changes a Limit, so it waits for the owner's Approval (see _Approval_).
  - A value the Registry refuses is reported as `Nothing was saved: <the owner's message>`, and nothing is recorded. The script, Toolchains and pattern tools refuse text that holds a held Secret's value, anything shaped like a GitHub token or the GitHub App's key, as the variable tools do. Each change's field is the setting's name (`instance`, `idleMinutes`, `setupScript`, `startScript`, `toolchains`, `ignore`, `spareWorkspace`); the Registry's change and revert are the same for all of them, so each is reverted from the Agent changes section like a variable.
- **`environment_create({ name, repos?, reason })`:** makes an Environment with the default Container settings and `repos` (each `owner/repo` or a plain `https` URL, parsed as the owner's `addRepo` parses one, cloned into the repo's own directory name), by the owner's name rules (1 to 80 characters after trimming, free whatever the case; the refusals say what the owner's do). The result gives its id, which the agent passes as `id` to the other tools to set it up, and says that the new Environment is not the Session's own and that the agent cannot start a Session in it (the owner can, from the New session composer or the Environment's Workspaces section: see [_Settings page_](client-and-protocol.md)). The spare Workspace and the Build upkeep run as after the owner's `createEnvironment`. **`environment_rename({ id, name, reason })`:** as `renameEnvironment`; a name the Environment has already changes and records nothing. **`environment_repo_add({ id, url, name?, reason })`, `environment_repo_remove({ id, name, reason })`:** as `addRepo` and `removeRepo` (`name` on an add is the directory, the repo's own by default; a directory held at the same address changes nothing, at another is refused; a directory that is not held is refused on a remove). Only the Environment's record and its spare Workspace change (the spare is made again if the Environment had a Session lately: see [_Spare Workspace_](workspace.md); and the Build upkeep runs): no Workspace a Session has, the Session's own included, gets a clone or loses one, and the result says so and that a new Workspace gets the change. **`environment_rebuild({ id, reason, proposed? })`:** without `proposed`, asks for a Build now as the owner's _Rebuild_ does (`Builds.rebuild`: the same refusal for an Environment with nothing to build), records the request once the Build is under way, and says so (`Builds.rebuild` answers `asked` or `underway`: when a Build of the wanted key is under way already, the owner's Rebuild leaves it alone and the tool answers that it is under way, asking for and recording nothing); `environment_get` shows its state and, when it fails, the end of its reason. All five take a `reason`, run alone, refuse a name, URL or reason that holds a Secret the Session holds, anything shaped like a GitHub token or the GitHub App's key, and are recorded as Agent changes and in the Run's Notification. The first four are not replayed; `environment_rebuild` is (`replay: "safe"`), for its Test Builds, and keeps a mark in the call's memo before it asks for a Build of the saved settings, so a rerun after an eviction asks for nothing again and says so.
- **Test Builds** (`environment_rebuild` with `proposed`; GLOSSARY.md → Test Build): `proposed` holds any of `repos` (the full list, each `{ url, name? }` as `environment_repo_add` takes one), `variables` (the full map), `setup_script`, `toolchains` and `ignore` (the full list): the inputs to a Build's key, each replacing the saved one. Start Scripts, size and idle time are not part of a Build and are not accepted (the parameters refuse other fields). Each value is refused, building nothing, when it holds a Secret the Session holds, anything shaped like a GitHub token or the GitHub App's key, and is checked as the saving tools check it (see [_Builds_](container.md) → _Test Builds_ for the rest). The Session asks for the Test Build by the call's task (`startTestBuild`), then waits for it in rounds the way `browser_handoff` waits: each round (`testBuildRound`, `apps/server/src/session/environment-lifecycle.ts`) asks the Test Build object every 5 s for at most 25 s, so no round depends on outliving an eviction. The call keeps in its memo that it asked, so a call an eviction cut off reruns and waits for the same Test Build without asking (or checking the proposal) again, and says it is gone if another Test Build has taken its place since it ended. Stop cancels the wait and the Test Build (`cancelTestBuild`); a wait that fails (five rounds in a row that could not reach the object) ends the call and leaves the Test Build to end on its own. It answers success with the time taken and which setting tools save each proposed field (it saves nothing itself), or an error with the failing step and the end of its output (redacted as a Build's failure reason is), or that it was stopped. A Test Build is not an Agent change: nothing is saved, recorded in the history or put in the Run's Notification. A second Test Build of the Environment while one runs is refused, saying so. The tool card's summary names the fields it tries (`Test Build of setup_script, toolchains`). Out of scope: saving the fields on success, and Test Builds the owner starts from the Settings page.
- **Values are plain.** A value that holds the value of a Secret the Session holds (`secret_ask`'s or the Environment's), or the GitHub App's private key (`CLOUDPID_GITHUB_APP_PRIVATE_KEY`, which the main Worker is bound to), as written or in any encoding the Session's redaction knows, or anything shaped like a GitHub token (`ghs_…`, `ghp_…`, `gho_…`, `ghu_…`, `ghr_…`, `github_pat_…`: the Session never sees the tokens the Workspaces mint), is refused, and nothing is saved or recorded (checked once the Session's Secrets are refreshed, so one the owner has just kept counts); so is a `reason` that holds one, since it is kept as written. The refusal points to keeping it as a Secret for the Environment. The tools are not wrapped to resolve Secret References, and the secrets extension's `beforeTool` hook lets their calls through: so every text the tools keep (a `value`, a script, the Toolchains, a pattern, a `reason`) that holds a placeholder (an unescaped double-brace reference, held or not, such as one a message was scrubbed to) is refused too, by the same check as a Secret's value (`holdsSecret`), saying what was saved would hold the reference's text, not the Secret, and pointing to keeping the value as a Secret for the Environment.
- **`environment_secret_build({ id, name, build, reason })`:** marks a Secret kept for the Environment as reaching the Build (`build: true`: it is `$PI_SECRET_<NAME>` in the Environment's Setup Scripts and part of the Build's key), or takes the mark off, as the owner's switch (`setEnvironmentSecretBuild`) does. `id: "*"` addresses a Secret kept Global. Only a Secret already kept can be marked (the owner keeps one in `secret_ask`'s form, see [_Secrets_](agent-capabilities.md#secrets)): there is no tool that keeps one or reads one, so the agent cannot set a value this way. A name not kept in that scope is refused, pointing to `secret_ask`; a Secret that has the mark records nothing. The Registry's `agentMarkSecretBuild` applies and records it in one transaction, then the Session runs the Builds' upkeep (each Environment's, for `*`). Root only, sequential and not replayed, like the other `environment_*` tools; a `reason` that holds a held Secret is refused.
- **`environment_skill_install({ id, source, skills?, reason })`** ([ADR-0026](../adr/0026-skills-kept-by-cloudpid-and-fetched-from-github.md), [_The Environment's own Skills_](workspace.md) → _Installing from GitHub_; `environment-skills.ts`): installs Skills from a GitHub source the Registry fetches as the GitHub App, pinned to a commit and kept with their Skill source. The result names what was installed (with the repo, ref and short commit), what was kept already, and what the checks refused with why; or, for a source that holds several Skills with none named, lists them and installs nothing, so the agent asks the user and calls again. It takes `id: "*"`: the Skills are then kept Global, which waits for the owner's Approval (see _Approval_), so the tool is `replay: "safe"`; each Environment's Workspaces (its spares too) serve them at their next readying, and the Session's own Workspace at once unless its Environment keeps its own Skill of every name installed (the result says which Environments' own Skills hide each). A rerun of an install for an Environment's own Skills runs it again: the Skills kept already come back unchanged, and a ref that moved is installed at its new commit. It also refuses Secrets in the source, the reason or the names as the other tools do. After it, for the Session's own Environment, the Session hands its Workspace the new Skill set at once; like the save it records one Agent change for each Skill kept, with the tool name `environment_skill_install`, and runs no Build's upkeep. Root only and sequential.
- **`environment_skill_update({ id, names?, overwrite?, reason })`** ([ADR-0026](../adr/0026-skills-kept-by-cloudpid-and-fetched-from-github.md), [_The Environment's own Skills_](workspace.md) → _Installing from GitHub_ → _Update_; `environment-skill-update.ts`): moves installed Skills to the latest commit of the ref each was installed from. The Registry fetches it as the GitHub App (`agentUpdateSkills`), never a Session or a Container. Without `names` it updates every Skill marked **update available**, and says so when there is none. A **modified** Skill is refused, and named in the result, unless `overwrite` is true; a Skill whose folder is unchanged at the new commit records nothing and says so; the others are updated when some are refused. Each Skill moved is one Agent change (`environment_skill_update`, the files and Skill source before and after), which the owner reverts in the Agent changes section; the Session hands its own Workspace the new set at once and the result says so as the install's does, and the Notification of the Run's end lists it. `environment_get` shows each Skill's **modified** and **update available** marks. Root only, deferred, sequential and `replay: "safe"` (a rerun finds the Skills at the new commit and records nothing again); a `reason` is required and refused, with the names, when it holds a Secret. **With `id: "*"`** the Skills kept Global are updated, which waits for the owner's Approval (_Approval_): the Registry first answers what each Skill would take (`previewSkillUpdates`: the new files, folder hash and the time the Skill was saved), the preview also checks the caps a save does (the 100 Skills and 8 MB of each Environment's merged set) and leaves out, saying why, a Skill that would pass them; the card shows each Skill as the install's does (its description and files, 16,000 characters of files for each Skill, with the same warning for what it could not show), marks a Skill whose edits the update would replace, and names the Skills left out; and on Approve the update is made at exactly the commits and folder hashes shown, and only for a Skill still last saved when the card was made (`changed-since` otherwise, nothing applied). One request shows at most `MAX_APPROVED_SKILLS` (10) Skills, as an install's does: a preview of more is refused before any Skill's files are read, and the agent names fewer with `names`; the Registry refuses an update for `*` that carries no pins, as it refuses a save, removal or install that carries no `expected` or `pin`. A rerun after an eviction does not read GitHub again to decide whether to ask: it waits for the request already made or takes its answer, and applies it at the pins that request holds.
- **`environment_skill_save({ id, path, reason })`, `environment_skill_remove({ id, name, reason })`** ([ADR-0026](../adr/0026-skills-kept-by-cloudpid-and-fetched-from-github.md); `packages/extensions/src/environment-skills.ts`): the save reads a Skill's folder from the Workspace through the call's environment (a folder the agent wrote, such as `/workspace/.cloudpid/tmp/<name>`, or one `npx skills add <source> --copy` made): every file below it but `.git` and `node_modules`, at most 500, refused when the path is not under `/workspace`, when it or a file in it is Container-only (the environment's `containerOnly`, so the save never reads through the Container what the Workspace does not hold), when it is missing or not a folder, holds a symbolic link, or holds a file that is binary, over 1.5 MiB (`MAX_FILE_BYTES`), over 4 MiB together (`MAX_SKILL_BYTES`) or looks like a credential (each problem a line). Each file's text and the `reason` are then refused when they hold a Secret the Session holds, anything shaped like a GitHub token or the GitHub App's key, or a Secret Reference's placeholder, as the other tools' values are. The Registry's `agentSaveSkill` checks the Skill ([_The Environment's own Skills_](workspace.md)) and saves it in place of one of its name, recording the change in the same transaction; the same files record nothing and say so. `environment_skill_remove` removes a Skill the Environment keeps (`agentRemoveSkill`); one it does not keep is refused, pointing to `environment_get`, and the Skills kept Global cannot be removed this way. After either (and after a save of the files kept already), for the Session's own Environment, the Session hands its Workspace the new Skill set at once; each result says where the Skill is served (`/workspace/.agents/skills/<name>`, read-only, over the Skill of the name kept Global, if any), whether this Session's Workspace has the change now or at its next readying, that the Environment's other Workspaces and its spare get it at their next readying, and that the skills list in the system prompt changes at the next Context Window. No Build's upkeep runs. The change's field is `skills.<name>`, its values before and after `{ files: { <path>: <content hash> } }` (null for no Skill); `skillChangeFiles { environment, change }` answers the texts. Root only and sequential, like the other `environment_*` tools. **With `id: "*"`** the Skill is saved to (or removed from) those kept Global, which waits for the owner's Approval (see _Approval_), so both tools are `replay: "safe"` and the change is recorded under the scope `*` as approved; each Environment's Workspaces (its spares too) serve it at their next readying, and the Session's own Workspace at once unless its Environment keeps its own Skill of the name (the result says which). A save with an Environment's `id` of a name also kept Global makes the Environment's own copy, which hides the other there; it needs no Approval, and the result says it hides it. The remove with an Environment's `id` removes only its own Skill: one kept Global is not the Environment's, and `id: "*"` removes it.
- **Root only.** The `environment_*` tools are the root conversation's, as `secret_ask` is: `PARENT_ONLY_TOOL_PREFIXES` keeps every tool whose name starts with `environment_` out of a child's grant, named or inherited.
- **Applied** as the owner's save is: the Session calls the Registry DO's `changeEnvironment` (the Environment, the change as a field, `variables.<NAME>` or a setting's name, with its new value or null, and the author: Session, conversation, tool, reason), which checks and writes the Environment's Overrides as `updateEnvironmentSettings` does (a value is a `set` of the field, null a `reset`: the field then inherits Global's) and records the change in the same transaction, answering the values in force before and after, whether each was inherited, and whether the Build key changed (`buildKey`, with the image left out). A value the field has as its Override already, or a reset of a field that is inherited already, records nothing; a value equal to the one it inherits makes it an Override, and is recorded. Then, as after the owner's save, the Session runs the Builds' upkeep for that Environment (`buildUpkeep`, which keeps its spare current once a new Build is good), and, for the Session's own Environment, hands the new overrides to its own Workspace DO at once (`updateContainerSettings`; a failure is logged, and the next readying hands them): every setting in force, the Environment's Overrides over Global's with the variables merged by name (`workspaceOverrides`), not the Overrides alone. With the id `*` the change is to the Container settings at Global: the Session calls `changeGlobal` (any Container setting or `variables.<NAME>`, with `expected` for an approved one), which checks it as `updateGlobalContainerSettings` does (no Environment that inherits it may be left above its size limit or with more than 50 variables), writes the document and records the change under the scope `*` with the setting's name as the field, answering the values before and after, the settings before and after, the Environments that override the field and those that wanted a new Build, and whether the Session's own Environment overrides it; the Session runs the Builds' upkeep at Global (and the spares' upkeep of each Environment for the Spare Workspace setting) and hands its own Workspace the merged overrides, unless its Environment overrides the field (that Workspace has nothing new to take). Other Environments' Workspaces get the change at their next readying, as they get the owner's. A change to variables does not run again a Setup Script that already ran: a Setup Script records only its own hash, so a Workspace whose Container ran it keeps what it did; a new Build runs it with the new variables, and so does a Workspace that starts from one.
- **Kept** (Registry migration 17, `agent_changes`): each change with its time, actor (`agent`, or `owner` for a revert), Session, conversation, tool, reason, scope (the Environment's id, its Settings Overrides' changes included, or `settings` for the Global Settings: see _Settings changes_), field, and the values before and after (JSON, null for not set). A change to an Environment's Container setting or Settings Override records the value in force on each side and, apart, whether it was inherited from Global rather than the Environment's Override (`beforeInherited`, `afterInherited` in `AgentChange`; columns `before_inherited` and `after_inherited`, migration 25, null for not inherited), never null for inherited. Migration 26 marked the changes recorded before Global held Container settings: an Environment stored then only what differed from the defaults, so a value recorded for a Container setting that was the default (a size by its name then or now) was one it did not override, and is marked inherited; the values stay as recorded. Reverting a change whose value before was inherited is a reset (the field inherits Global's again, whatever Global's is now), made only while the field is still as the change left it, as any revert is; reverting a reset puts the Override back. A scope keeps its last 200; deleting an Environment deletes its own. A change the owner approved first is marked so (`approved`, migration 18: see _Approval_). Besides the Container settings, a change's `field` is `name` (the name before and after), `repos.<directory>` (the Repo's address before and after, null for none: an add is null→address, a remove address→null), `environment` (the creation: null before, the name and Repos after, in the new Environment's own history) or `build` (a Build asked for: null before, `asked for` after). Secrets are recorded by name only: `secrets.<NAME>` is a Secret the owner kept in a `secret_ask` form on the agent's request (`kept` after, and before where the scope kept one of the name already; the actor is `agent` with the tool `secret_ask` and a reason that says the owner chose to keep it on the agent's request, and the Session's Run Notification lists it), and `secrets.<NAME>.build` is its Build mark (a boolean before and after). The history of the Secrets, the Container settings and the Skills kept Global is the scope `*` (no Environment id can be `*`; Global's Agent changes section shows it, merged with the Settings' changes, those of the Skills with them, and `listAgentChanges` and `revertAgentChange` take it); its Container settings are recorded by the setting's name, and its variables as `variables.<NAME>`, with both values in full, and reverted like an Environment's own (the document is written back, refused as the owner's save would be, and the Builds' upkeep runs at Global, with the spares' for the Spare Workspace setting). No value is in any record. The Registry DO records them in the same transaction as the change (`agentCreateEnvironment`, `agentRenameEnvironment`, `agentAddRepo`, `agentRemoveRepo`, `recordRebuild`; the Session runs the upkeep and, for a rebuild, asks the Builds first and records after, so a refused request records nothing). `listAgentChanges { environment }` lists them newest first, each with the revert that undid it (`revertedBy`), leaving out those the owner dismissed: `dismissAgentChange { environment, change }` marks one so (`dismissed`, migration 20), without reverting it or deleting its record (it still counts toward the 200, and a revert of it still finds it), and refuses a change the scope does not have. `revertAgentChange { environment, change }` writes the value before back and records that as the owner's change (`reverts`); it is refused, saying what the field is now, when the field no longer has the value the change gave it, for a change reverted already (the agent may have given the field that value again since), and for an owner's change (a revert is not undone). The revert of a rename puts the name back (refused if another Environment has it now), of an add takes the Repo out, of a remove puts it back at the end of the list; the main Worker then also keeps the spare current for a Repo. A Secret kept has no revert either (the history holds no value to bring back: the owner deletes the Secret itself), nor does one the agent deleted with the owner's Approval (`kept` before, null after: the owner keeps it again), but a Build mark does, and its revert runs the Builds' upkeep. The revert of a Skill's change writes its files before back (a new Skill is removed, a removed one comes back, as the owner's change, with no Build's upkeep), refused when the Skill no longer has the files the change gave it, or when bringing it back would put more than 100 Skills or 8 MB in a set (in the scope `*`, in any Environment's set); it is the owner's own action in the Agent changes section, so it waits for no Approval, and the agent has no revert tool; Workspaces get it at their next readying. The creation of an Environment and a Build asked for have no revert (deleting an Environment needs the owner's Approval: `environment_delete`), and the Agent changes section shows no _Revert_ for them. The main Worker then runs the Builds' upkeep, as after the owner's save. The Agent changes section of the Environment's Scope lists them, with its Skills' (see [_Environments from the UI_](workspace.md) and [_Settings page_](client-and-protocol.md)).
- **Transcript and Notification:** each change's result carries `details.agentChange` (the change's id, the Environment, the field, the values before and after), which its card shows in full. The Session keeps the Run's changes (tool, Environment name, field) in its key-value storage, and when the owner's Run that made at least one ends it sends one `notice` listing them, besides the usual `finished` or `failed` (see [_Notifications_](client-and-protocol.md)).

## Settings changes

The `settings` extension (`@cloudpid/extensions/settings`) gives the agent the Settings the owner edits at `/settings`, as deferred tools of the root conversation only (`PARENT_ONLY_TOOL_PREFIXES` has `settings_`). The Settings have two Scopes ([ADR-0027](../adr/0027-settings-at-two-scopes-with-explicit-overrides.md), [_Settings_](overview.md#settings)): Global, and each Environment's Overrides over it. Every `settings_*` tool takes a **required** `scope`: `*` for Global, or an Environment's id (as `environment_list` shows it), so where a change lands is the agent's decision, recorded in the Agent change; there is no default, and an id no Environment has is refused. A change at Global is an Agent change of the scope `settings`; one at an Environment is an Agent change of the Environment, under its id, beside its Container settings' changes. Both are kept and reverted as an Environment's are.

- **`settings_get({ scope })`:** the settings in force at the Scope (the models and roles, the thinking level, compaction, the offered tools, the branch summary prompt, the spend limit and the extension options), each with where its value comes from: at Global, the default or Global, with the Environments that override the field; at an Environment, its Override or inherited from Global. It also gives the saved overrides that no longer resolve and names the Session's own Environment, whose settings its requests run with. It is read-only and safe to replay. It shows the spend limit, the subagent depth and the Subagent Workspace limit, and says they are Limits the agent changes only with the owner's Approval. It shows the Instructions whole (their lines and bytes of UTF-8, then the text in an `<instructions>` block; Global's at an Environment, which has none of its own yet), and that `settings_instructions_set` changes them with the owner's Approval.
- **Changing tools** (each takes a required `scope` and a required `reason` of 1 to 500 characters, runs alone and is not replayed, like the Environment tools): **`settings_model_set({ scope, model?, thinking_level?, reason })`** (the default model and thinking level; a model the settings do not support is refused, the description lists the supported ones, and a Session's own pick is kept, which the result says), **`settings_role_set({ scope, role, model, hint?, reason })`** (`small`, `medium`, `large` or `xlarge`; the Role is one field, `roles.<role>`, its model and hint together: a hint left out keeps the Role's hint in force at the Scope), **`settings_tool_offer({ scope, pattern, reason })`** and **`settings_tool_defer({ scope, pattern, reason })`** (add to or take from the Scope's `tools.offered`, one name or pattern with `*`, saving the list whole; a pattern that is already so says so), **`settings_compaction_set({ scope, enabled?, reserve_tokens?, keep_recent_tokens?, background_tokens?, reason })`** (at least one; each is its own field), **`settings_branch_summary_set({ scope, skip_prompt, reason })`** and **`settings_extension_set({ scope, extension, key, value, reason })`** (`extensions.<extension>.<key>`; `null` takes the option away at Global, and resets the Environment's Override of it). A tool that sets several fields makes one write and one Agent change for each field that differs. At an Environment a set is an Override even when it equals the Global value (it pins it, and is recorded); only an Override that already has the value is left alone. Each result names the Scope and says whether this Session's next request uses the change: a change at another Environment does not reach it, nor does a change at Global to a field its Environment overrides.
- **`settings_reset({ scope, field, reason })`** (in the `approval-tools` extension, since a Limit's reset waits for Approval): at an Environment, removes its Override of `field`, which then inherits Global; at `*`, puts Global's `field` back to its default. `field` is one of the Override fields (`model`, `thinkingLevel`, `roles.<role>`, `compaction.<setting>`, `tools.offered`, `spendLimit.perSession`, `branchSummary.skipPrompt`, `extensions.<extension>.<key>`); a field that inherits already, or is at its default, changes nothing and says so. A Limit's reset waits for the owner's Approval (see _Approval_), so the tool is `replay: "safe"`. It refuses `instructions`, asking nothing, and points to `settings_instructions_set` with an empty text, which asks the owner: clearing the Instructions steers every conversation as much as writing them.
- **Limits are not here.** The spend limit, the subagent depth and the Subagent Workspace limit change only through the tools that wait for the owner's Approval (`settings_spend_limit_set`, `settings_subagent_depth_set`, `settings_subagent_workspaces_set`: see _Approval_), and `settings_extension_set` refuses `subagents.maxSubagentDepth` and `subagents.maxSubagentWorkspaces`, naming the tool for each. It also refuses a subagents toolset option (`baseToolset`, `readToolset`, `modifyToolset`) that is not a list of strings, since the extension ignores all its options when one is malformed.
- **Applied** as the owner's save is: the Session calls the Registry DO's `changeSettings` (the Environment, absent for Global; the fields, each a dotted settings path with its new value or a reset, and the author), which merges them into the saved overrides (Global's) or the Environment's Overrides (`changeSettingsOverrides`, as `updateSettingsOverrides` does), decodes them strictly with the owner's schema, and writes the document or the Environment's row and the records in one transaction. An invalid value is refused with the owner's own message, and nothing is written or recorded; a field that already holds the value is left out and says so; saved overrides that no longer resolve are dropped by the write, which the result reports. The Session then reads the settings again at once and rewrites the active branch's agent, so the same Run's next request uses the new default (unless the Session picked its own model or thinking level), and other Sessions read it when they next admit input.
- **Plain values.** The reason and the texts that are free-form (role hints, offered patterns, option values) are refused when they hold the value of a Secret the Session holds, anything shaped like a GitHub token, the GitHub App's key, or a Secret Reference's placeholder (held or not; an escaped one is plain text), as the Environment tools refuse: the tools resolve no reference, so the Settings would hold the reference's text, not the Secret. The refusal says so.
- **Kept and reverted:** the records are the `agent_changes` table's, with scope `settings` (Global) or the Environment's id, and the dotted path as the field (`model`, `roles.small`, `tools.offered`, `compaction.enabled`, `branchSummary.skipPrompt`, `instructions`, `extensions.<name>.<key>`; a Global change recorded before Roles were one field may name `roles.small.model`); the last 200 of each scope are kept. `before` and `after` are the field's values in force at the Scope. At an Environment a change also says whether the field was inherited before it (`beforeInherited`: it had no Override, so `before` is the value it inherited) and after it (`afterInherited`: a reset), in columns `before_inherited` and `after_inherited` (migration 25). An Environment's are listed and reverted with its other changes (`listAgentChanges`, `revertAgentChange { environment, change }`): the revert sets the Override back to `before`, or resets the field when it was inherited before, and is refused, saying what the field is now, when the field is not as the change left it (another value, or overridden since a reset, or reset since a set). Global's are listed and reverted as follows. `listSettingsChanges` lists them newest first, with the revert that undid each (`revertedBy`), leaving out those `dismissSettingsChange { change }` dismissed (as `dismissAgentChange` does). `revertSettingsChange { change }` writes the value before back (taking the override away when it was not set) and records the owner's change; it is refused, saying what the field is now, when the field has changed since, for a change reverted already and for an owner's change. The Agent changes section of their Scope on the Settings page lists them (at Global merged by time with those of the scope `*`, `listAgentChanges`), with the setting, its values before and after in full (the Instructions' as a line diff with a few lines around each change, the rest folded, as a Setup Script's; the transcript's card shows them so too), who and when, the Session that made it (while it is listed), the reason, _Revert_ and _Dismiss_; a revert loads the Settings again, and a section's unsaved draft stays.
- **Transcript and Notification:** a result carries `details.agentChanges` (each change's id, scope, field and the values before and after; at an Environment also the Environment, `{ id, name }`, which titles the card with its name, and both `beforeInherited` and `afterInherited` as booleans), which its card shows; the Run's end notice lists each as the tool and the field (`settings_model_set model`), with the Environment's name for a change at an Environment.

## Approval

An Agent change that changes a Limit, that changes the Skills kept Global, that changes the Instructions, or that no revert can undo, waits for the owner's **Approval** (GLOSSARY.md; [ADR-0019](../adr/0019-the-agent-manages-its-environments-and-settings.md)). The `approval-tools` extension (`@cloudpid/extensions/approval-tools`, over the requests of `@cloudpid/extensions/approvals`) has the tools, deferred and the root conversation's only (their names start with `settings_` or `environment_`, so `PARENT_ONLY_TOOL_PREFIXES` keeps them from children). Each takes a required `reason` (1 to 500 characters) and runs alone:

- **`settings_spend_limit_set({ scope, per_session, reason })`:** `spendLimit.perSession`, US dollars above 0, or null for no limit (at an Environment, an Override of no limit).
- **`settings_subagent_depth_set({ scope, depth, reason })`:** `extensions.subagents.maxSubagentDepth`, at least 1 (the default, 2, is the root's children and theirs).
- **`settings_subagent_workspaces_set({ scope, limit, reason })`:** `extensions.subagents.maxSubagentWorkspaces`, the Subagent Workspace limit: how many Subagent Workspaces one Session may have at once, at least 0 (default 1; see [_Subagents_](agent-capabilities.md#subagents)). Subagent Workspaces that exist stay when it is lowered.
- **`settings_reset({ scope, field, reason })`** of a Limit's field: an Environment's Override of it removed, so it inherits Global's (which may be higher), or Global's back to its default.
- **`settings_instructions_set({ scope, text, reason })`** ([ADR-0027](../adr/0027-settings-at-two-scopes-with-explicit-overrides.md); [_Instructions_](workspace.md)): the whole Instructions, Markdown, replacing them (an empty text removes them). They steer every conversation unasked, a stronger target for a prompt-injected agent than the Skills kept Global, so every change waits. `scope` is required as for every `settings_*` tool, and only `*` is taken for now: an Environment's id is refused, asking nothing, since Environment Instructions come with [#352](https://github.com/ian-pascoe/cloudpid/issues/352). Refused without asking: a text over 64 KiB of UTF-8 (naming its size), and a text or reason that holds a Secret the Session holds, a GitHub credential or a Secret Reference's placeholder, as the other tools' values are; a text the Instructions have already asks nothing and records nothing. The card's _Now_ and _After_ are the two texts as written ("None" for none), and `expected` is the text now: Approve sets them (`changeSettings` with `expected`) only while they are still that text, else `changed-since` and nothing is saved. The change is recorded as approved under the scope `settings` with the field `instructions` and both texts whole, shown as a line diff and reverted as any Settings change (the owner's Revert needs no Approval). The result says the change applies from each conversation's next Context Window, and that a context that has begun keeps the Instructions it started with.
- The three Limits wait at either Scope (ADR-0027): the card's target is the Global Settings or the Environment's Settings, and at an Environment the value now says whether it is inherited; the change is made only while the field still has that value and is still inherited or overridden as the owner saw it.
- **`environment_container_size_limit_set({ id, size, reason })`:** an Environment's `maxInstance`, or with `id: "*"` the one at Global (refused by the Registry when an Environment that inherits it would be left with a size above its limit, naming it). A limit below the size in force is refused without asking, pointing to `environment_container_resize`. An Environment that inherits its limit is asked about even for the size it inherits: the change makes it the Environment's own.
- **`environment_setting_reset({ id, setting: "maxInstance", reason })`:** takes an Environment's own size limit back, so it inherits Global's. The card shows the limit now (its own) and Global's; Approve resets it only while the limit in force is still the one shown. An Environment that does not override its limit is told so without asking, and a reset that would leave its size above Global's limit is refused without asking.
- **`environment_delete({ id, reason })`:** deletes an Environment as the owner's delete does (`removals`, `apps/server/src/registry/removal.ts`, which the main Worker's `deleteEnvironment` runs too): its Workspaces with their Sessions (archived ones too) and what was not pushed in them, its spare Workspace, its Build and Test Build objects, then its record with its kept Secrets and Agent changes. The default Environment and the Session's own are refused without asking.
- **`environment_secret_delete({ id, name, reason })`:** deletes a Secret kept for an Environment (`id: "*"`: at Global) as the owner's delete does, then runs the Builds' upkeep it touches. A name not kept in that scope is refused without asking.
- **`environment_skill_save({ id: "*", path, reason })`, `environment_skill_remove({ id: "*", name, reason })`, `environment_skill_install({ id: "*", source, skills?, reason })`, `environment_skill_update({ id: "*", names?, overwrite?, reason })`** (`packages/extensions/src/environment-skills-global.ts` and `environment-skill-update.ts`, which asks through the same `Approvals`, with wording of its own: what must still hold is the Skill, not a setting): the Skill steers every future Session, so a change to those kept Global waits. The save checks the folder as it does for an Environment (and the Registry's `agentPreviewSkill` the Skill, in each Environment's merged set) before it asks, and asks nothing when the same files are kept already. The card's _Now_ is the Skill as kept (its description and the paths of its files, or "not kept") and _After_ the description and the files' texts, as written and scrolling. The card shows at most 16,000 characters in all, since a Skill may be 4 MiB, and says so plainly when it cuts: a warning above and below the files names how many characters and files are not shown and that Approve saves that part unreviewed, and each file cut or left out says so where it is. The tool's description and, after an approved save of a Skill that was cut, its result tell the agent to keep a Skill at Global small enough to review in full. `expected` holds the digest of the folder and when the Skill was saved (a removal's, only when it was saved): Approve saves only while the folder still has that digest and the kept Skill still has that save time (`agentSaveSkill` and `agentRemoveSkill` take it as `expected` and answer `changed-since` otherwise). **The install** reads the repo first (the Registry's `agentPreviewSkillInstall`: the source fetched as `environment_skill_install` fetches it, each Skill checked as a save is, in each Environment's merged set) and asks nothing when every Skill is kept with the same files and Skill source already or refused, saying so. Otherwise one request shows every Skill it would keep, each as the save's card shows a Skill (its description and files, with the same 16,000-character limit and the same warnings, per Skill), and at most 10 Skills (`MAX_APPROVED_SKILLS`): more are refused without asking, the agent naming up to 10 and calling again. The Registry also refuses a preview whose Skills are more than 8 MiB together (`MAX_SKILL_SET_BYTES`, `previewSizeProblem`): no set could keep them at once, and the preview goes to the Session in one Durable Object call, so ten Skills of 4 MiB never make one past its 32 MiB. The Registry applies the count's bound itself, before it reads any Skill's files, so `skills: ["*"]` over a large repo is refused before anything is read or sent to the Session. `expected` holds the commit shown, how much the cards cut, and for each Skill shown its folder, a digest of its files and when the Skill of its name was last saved. Approve installs by reading exactly the folders the pin names at that commit, not at the branch's head now and not choosing again by name (`pin` of `agentInstallSkills`; a Skill the card did not show, such as another folder the same name resolves to, or an internal one a name reaches, is never read), and a Skill is kept only if its name and the digest of its files are the ones shown, and only while the Skill of its name was last saved then. Each Skill the card showed has a result: kept, kept already, or reported with why (its folder is gone or its files changed; one saved again is reported as not installed, the others are), recorded under the scope `*` as approved with its Skill source. The Registry also refuses an `agentInstallSkills`, `agentSaveSkill` or `agentRemoveSkill` for the scope `*` that carries no `pin` or `expected`, as a second guard. A rerun that holds the request or its answer reads nothing first (the repo may have moved, or GitHub be unreachable): it waits for the same request, or takes its answer, and installs what that pinned; if the Skills are kept already it says the install was approved and done, with the Skills the first call left out as refused. The Skills kept already and the ones the checks refused are listed in the result, each name once. **The update** (`environment_skill_update`, [_Installing from GitHub_](workspace.md) → _Update_) is asked as the install is: the Registry's `previewSkillUpdates` first, then one request that shows each Skill (the card of a save: the description, and the files with the same 16,000 characters and warnings per Skill, with a warning on a Skill whose edits the update replaces) at the commit and folder it would take, for at most 10 Skills and 8 MiB of files (`previewSizeProblem`, as an install's); `expected` holds the pins (commit, folder hash and when the Skill was saved), how much the cards cut, and the Skills left out with why; a rerun that holds the request or its answer reads nothing, and a Skill already at the approved commit and files counts as updated, whatever was saved or moved since. An Environment's own Skill needs no Approval, and neither does the owner's removal, install, update or revert in the Skills and Agent changes sections. A rerun after an eviction of a change that was approved and went through says it was approved and done already; one of an own Skill's save or removal (no request to find) says it may be done already.

The request and its answer:

- **Asked only when needed.** A tool first refuses what it would refuse anyway (a `reason` that holds a Secret the Session holds, anything shaped like a GitHub token or the GitHub App's key, an unknown Environment, the cases above) and asks nothing for a value the target has already, recording nothing. A rerun whose call asked already (`askedBefore`) goes on to its request whatever it finds, since it may have made the change itself before the eviction: an approved change the target has already is reported as approved, with nothing more changed.
- **The request** is durable and modelled on `secret_ask`'s: kept in the Session DO's storage (`approval-requests`) under the asking call's task id, it holds the tool, the target (an Environment by name, or the Settings), the change, the value before and after as the owner reads them, and the agent's reason. For a delete, _before_ says what is deleted: an Environment's Workspaces and Sessions by count (and its kept Secrets), or a Secret's name and whether it reaches the Build. The request also keeps, never sent to a client, the target's value as the owner was shown it (`expected`).
- **Delivery.** The Session sends the waiting requests to every client (`approval_requests`, after `hello` on every connect, an empty list too, and to every client whenever they change), and pushes an `input` Notification once for each new request, in the background, naming the change, its target and the agent's reason (`Approval needed: Size limit, Environment "Default" (…)`).
- **The card.** The web app shows a card for each request under the Secret forms (`apps/web/src/chat/approval-card.tsx`): the change, its target and tool, the value now and after, the agent's reason, an optional reason for a Decline, and **Approve** and **Decline**. The card is bounded so that a request of any size cannot push its buttons off the page (a `*` Skill install shows up to 10 Skills, about 160,000 characters): it is a column capped at the area's height, in which the header, the agent's reason (short, with a scroll of its own), the reason input and the buttons keep their size, and only the values _Now_ and _After_ scroll in the room left, a value of several lines shown as written in fixed-width text. A lone card shrinks to the area's height, so in portrait (a phone at 390×844, or 390×660 with a browser's toolbars) Approve and Decline are in view without scrolling. With several cards each keeps its own height and the area scrolls to reach them. The area that holds the waiting Browser Handoffs, Secret forms and Approval cards above the composer (`waiting-requests.tsx`, on the Session page and the Subagent page) is bounded the same way: at most 60% of the viewport's height with its own scroll, and no height when nothing waits, so the thread and the composer stay usable with several waiting. On a short viewport (under 32rem tall, as a phone in landscape) the area may take 72% of the height, the card is laid out tighter (the reason input beside the buttons) and keeps a height in which _Now_ and _After_ can be read, so the area, squeezed between the Session header and the composer, scrolls to reach the buttons. `approval_answer { request, approve, reason? }` answers it (the reason, at most 500 characters, is sent with a Decline only); an answer to a request that no longer waits (answered on another device, or its call ended) is refused.
- **Waiting.** The call waits with no deadline of its own. The tools are `replay: "safe"`: the request and the answer are in storage, so a call an eviction cut off reruns and waits for the same request (the one the owner sees, not one made of what the rerun read again), or takes the answer given meanwhile. Stop withdraws the request. A request whose call is gone is withdrawn once the Session is idle (`onIdle`), and an answer no call took is dropped then.
- **Approve** makes the change against what the owner saw. The Registry applies a Limit only while its field still has the value the request showed (`changeSettings` and `changeEnvironment` take it as `expected`, checked in the same transaction; otherwise they answer `changed-since`, nothing is saved or recorded, and the result asks the agent to ask again with the value as it is now); a delete of an Environment is made only while it would take no more Workspaces, Sessions or kept Secrets than the card counted (`expected` holds the counts; fewer is a delete an eviction cut off, which the rerun finishes), and a kept Secret is deleted only while its value and Build mark are those the owner saw (its `updatedAt`, checked by `agentDeleteSecret` in the delete's transaction). An applied change is an Agent change marked approved (`approved`, Registry migration 18; `approved: true` in `AgentChange`), kept, listed, reverted (a Limit) and put in the Run's Notification as any other; the Agent changes section and the tool's card say it was approved. A kept Secret deleted is recorded by name in its scope's history (`secrets.<NAME>`, `kept` before and null after), with no revert: the history holds no value, and the owner keeps it again. An Environment's history is deleted with it, so its delete is recorded nowhere but the call's card (field `deleted`, `DELETED_FIELD`) and the Run's Notification.
- **Decline** changes nothing; the result says so with the owner's reason, if any, and tells the agent not to ask again for the same change unless the owner wants it.
