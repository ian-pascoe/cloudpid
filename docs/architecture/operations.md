# Operations

- **Infra:** alchemy `2.0.0-beta.84` with `@effect/platform-node`. Workers and DOs are written in alchemy's Effect form, or as plain classes through Worker `bindings` where a mixin such as `withWorkspace` requires it. Containers use `schedulingPolicy: "durable_object"`.
- **Stages:** `alchemy dev` (workerd and local Docker, stage `dev_$USER`) and a single `prod` stage with `Cloudflare.state()`. GitHub Actions runs `bun run check` and deploys `prod` on push to `main`. Each pull request from this repository gets a preview stage `pr-<number>` once `check` passes, with its URL in a PR comment, destroyed, its Container application included, when the pull request is closed.
- **Access:** every stage's main Worker sits behind a Cloudflare Access application (declared on the Worker's `access` prop) with one policy, allow the owner's email. `prod` is served on `pi.ianpascoe.dev` (`ianpascoe.dev` zone, Access team `spirit-led-software`) and not on `workers.dev`; other stages stay on `workers.dev`.
- **CI credentials:** a second stack, `infra/github.ts` (`cloudpid-github`, stage `ci`), creates the scoped deploy API tokens and the GitHub environments `production` (deployments from `main` only) and `preview` (pull request previews, any branch) with their secrets and variables. See [`docs/development/infra.md`](../development/infra.md) → _CI credentials_.
- **Telemetry:**
  - **Traces.** `@cloudpid/telemetry` adapts pi-telemetry's `TelemetryContext` to an Effect `Tracer` (`effectTelemetry`), and that tracer to Workers' custom spans (`tracing` from `cloudflare:workers`, `workersTracer`), so every Effect span and every pi span is a span in the Worker's trace, among the runtime's own for fetches, bindings and RPC. Every Worker of the stack sets `observability: { enabled, logs, traces }` (`WORKER_OBSERVABILITY`; head sampling left at the default of 1, as this is one owner's agent). Workers has no way to name a span's parent, only the async context, so a span keeps the context it started in and its descendants run in it. alchemy's `Cloudflare.Telemetry()` makes a tracer per event and cannot serve the Session DO's long-lived runtime, so the Session builds its own once per object; OTLP export to a third party was not needed, since Workers Observability keeps traces (7 days) and is queryable without a new secret. Billing for traces starts on 1 December 2026.
  - **Spans.** `session.connect`, `session.message`, `session.close` and `session.alarm` are the object's invocations; `session.run` runs from a submission's admission to its settling, with the Run's requests and tool calls started under it, so they join the trace of the invocation that submitted it (the Run goes on after the message's reply, and the trace shows it); `session.resume` covers resuming interrupted work after an eviction, so a resumed Run's spans are in the alarm's or the first message's trace instead, and a Run an eviction cut off has no `session.run` end. `pi.ai.request` (provider, API, model, reasoning level, stop reason, token counts, cost, first chunk) is made at the `Models` seam, so it covers generations, compaction summaries, subagents and the title call; `pi.tool.<name>` (conversation, task and call IDs, whether it errored) wraps every tool, including a `codemode` script's nested calls. A failed request records how it failed (`retryable`, `context_overflow` or `other`, by pi-ai's own classifiers), not the provider's text, and a span carries only the events pi raises (a short dotted name): Effect's logger turns every log made inside a span into an event named by its message, which the Workers tracer leaves out. Prompts, tool arguments and results are never recorded. These are made at the seams the Session owns, since the pi-durable 1.3.0 Harness emitted no spans of its own. pi-durable 1.4.0 has `HarnessOptions.telemetry` (admission, task phase and report spans; its requests' `pi.ai.request` come from pi-ai, through the request's `telemetry` option, formerly `telemetryContext`), which is not passed yet: `effectTelemetry` is the adapter to pass, and the wrappers are then taken out. It maps pi's span links (`SpanOptions.links`, `addLink`) to Effect span links when they name a span it gave out; Workers tracing has no links, so they stay in Effect.
  - **Usage.** `pi.usage` is pi-durable's ledger per conversation; the Session's total is shown in its header (`watch_usage`, see [_Client and protocol_](client-and-protocol.md)). The title calls have no conversation, so their usage is kept in the Session's storage (`title-usage`) and added to the total.
  - **Container cost.** Each Workspace DO keeps what its Containers have cost (`ContainerUsageLedger`, `apps/server/src/workspace/container-usage.ts`; storage key `cloudpid:container-usage`), shown in the header of every Session in the Workspace (Sessions that share one each show all of it; a Session's figure adds its Subagent Workspaces', each read from its own Workspace DO, brought to the latest reading at its own rates and summed, so it grows at the rates of the Containers that still run: `sumContainerUsage`, `apps/server/src/session/container-cost.ts`; a deleted subagent's Workspace takes its usage with it), at Cloudflare's list prices (`CONTAINER_PRICES`, `@cloudpid/config`; the plan's monthly allowance is the account's and is not taken off). The figures are Cloudflare's usage analytics (the GraphQL Analytics API's `containersUsageAdaptiveGroups`, the dataset behind the dashboard's estimate, which counts real CPU time, the micro VM and egress), filtered by the label every launch carries (`cloudpid-ws=<object id>`, set by `ContainerLaunch`; workerd allows label names of at most 16 bytes and values of at most 64; computer does not compare labels, so adding them relaunches nothing). They trail by minutes, so they are asked up to 5 minutes ago, at most once a minute, in the background of a read (the read answers with what it holds); usage over an hour old is settled (asked once and added to a kept sum, in windows of at most a day, back at most 30 days) and the hour since is asked again at each refresh. After what they cover, and throughout when the deployment has no analytics token (`CLOUDPID_ANALYTICS_TOKEN`, with `CLOUDFLARE_ACCOUNT_ID`; `alchemy dev`, local deploys without it) or they fail (one warning per run of failures), the cost is estimated from what the Workspace saw: each launch is a run from its launch record's `launchedAt` to its stop (the idle stop, a restart, a Build's stop, the removal) or, for a Container gone on its own, its last sighting (a use, written at most every 30 s); memory and disk are priced for every second of a run on its size (`INSTANCE_RESOURCES`), and CPU as every vCPU at full use while a command ran (the idle stop's `begin`/`end`), as the Workspace cannot see a Container's CPU. The run time shown is the Workspace's own count. A Container that was running when the labels were introduced is unlabelled until its next launch, so the analytics miss it. The cost is not held to the spend limit.
  - **Spend limit** ([ADR-0010](../adr/0010-telemetry-at-the-seams-the-session-owns.md)). `spendLimit.perSession` (USD; off by default, because what a Session is worth depends on the work and the proxy's own key limits bound a runaway) is enforced at the Session's `Models`, as secret scrubbing and the image limit are: a request made when the Session has spent the limit is refused before it reaches the proxy, and ends as an error message ("This Session is out of budget: …") that the Harness ends the Run with, `unanswered` for `model_error` with that text, which the owner's failed-Run push carries. This replaces the `beforeRequest` hook the plan named: pi-durable 1.3.0's hook can only rewrite messages, and one that throws is reported and skipped, so it cannot stop a request; the seam also covers compaction and summaries, which the hook would not. The check runs at each request: those under way when the limit is crossed finish, so a Session overshoots by what they cost (one request per live conversation), and a refused request costs nothing. Subagents share the Session's limit: their requests go through the same `Models` and are held to it (a child's turn ends `failed` for `model_error`, and so does the root's next request), and the total they are held to is the Session's. The text avoids pi-ai's retry markers (`out of budget` is its own non-retryable marker). The title call counts toward the spend but is not refused: it costs a few tokens, and a refused one would leave the Session unnamed. A limit raised or cleared in the settings applies to the next request and a Run continues with a new prompt. If the ledger cannot be read, the request goes through and a warning is logged.
