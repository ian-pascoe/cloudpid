# MCP: configuration and the agent's changes

An Environment's Sessions reach the MCP servers of its **MCP server set**: Global's entries, the Environment's own, and each Repo's `.pi/mcp.json` as it is on the Repo's default branch, in one namespace ([ADR-0027](../adr/0027-settings-at-two-scopes-with-explicit-overrides.md), [ADR-0029](../adr/0029-repo-mcp-servers-run-as-its-scripts-do.md)). `packages/config` resolves the set purely; the Registry keeps it and hands it to the Environment's `McpHost`; the agent changes the owner's entries through the `settings_mcp_*` tools, some of them only with the owner's Approval ([ADR-0019](../adr/0019-the-agent-manages-its-environments-and-settings.md)). What a new set does to connections and discovery is in [_Discovery and the MCP inventory_](mcp-connections.md#discovery-and-the-mcp-inventory); when a Session's tools follow it, in [_The prompt cache and the `mcp_servers` section_](mcp-in-a-session.md#the-prompt-cache-and-the-mcp_servers-section).

## Entries

- **Where they live:** a typed top-level `mcp` root in `Settings` (`packages/config`), `mcp.servers` keyed by the server's name, at both Scopes ([MCP server configuration](https://github.com/ian-pascoe/cloudpid/issues/380) D1). Nothing else sits under `mcp`, and `servers` defaults to none, so `mcp: {}` reads: pi's `autoEnableCodemode` gets no key ([MCP tools in a Session](https://github.com/ian-pascoe/cloudpid/issues/381) D8). `extensions.mcp.*` is read by nothing, and `settings_extension_set` refuses `extension: "mcp"`. **Across a deploy:** a Worker still running the old code decodes the settings with unknown keys refused, so it drops an `mcp` root with a "dropped" problem on a lenient read and refuses a strict save of the whole document. The Settings page's section (#459) writes `mcp` now, and the `settings_mcp_*` tools (#484) are yet to come: a save that reaches a Registry still on the old code is refused, loudly and with its message, and the owner saves again, so the window is harmless ([_Deploys_](mcp.md#deploys)).
- **Two kinds of entry:** a **full entry** (it has `command`, `url` or `type`) is an MCP server definition plus `enabled`, `exposure` and `toolExposure`, and must define a server (`command` or `url`), so `type` alone makes an entry full, and it then fails to decode; an **MCP server adjustment** holds only `enabled`, `exposure` and `toolExposure`, adjusting a server defined in a lower layer.
- **Schema** (pi's `mcpServers` shape, [MCP server configuration](https://github.com/ian-pascoe/cloudpid/issues/380) D6):
  - `type`: `stdio` | `http` | `streamable-http`, inferred from `command`/`url` when absent. `sse` is refused, naming Streamable HTTP; `type` must fit the entry (`stdio` with a `command`, `http` or `streamable-http` with a `url`), and an entry has one of the two, with only its own transport's keys.
  - stdio: `command`, `args`, `env`, `cwd`. `command` is spawned without a shell, resolved by the OS against `PATH` and `cwd`; `~` is never expanded (refused in Settings, skipped in a Repo file).
  - HTTP: `url`, `headers`.
  - `enabled` (default `true`); `exposure` (`codemode` by default; `direct`, `deferred`, `hidden`; pi's `codemode-deferred` is read as `codemode`); `toolExposure` (the server's own tool names, as pi's entries spell them, or `*` patterns → an Exposure, first pattern wins).
  - `timeout` in seconds (default 60): the bound on a `tools/call`, a lower bound than 30 s on a `prompts/get`, and (capped at 10 min) an MCP task's inline window ([_MCP tasks_](mcp-server-requests.md#mcp-tasks)); `description`.
  - `oauth`: `clientId`, `clientSecret`, `privateKey`, `keyId`, `scope`, `clientName`, `clientRegistration`, `authServerMetadataUrl`, `issuer`, `grantType`; `callbackPort`/`callbackUrl` accepted and ignored with a hint that the redirect URI is cloudpid's own. The URI depends on the stage's app origin, which `@cloudpid/config` does not know, so `mcpEntryHints` gives a typed hint (`oauth-callback-ignored`, with the keys), carried by a Repo file's read (`hints`) and the resolved set (`hints`); the Settings page's Sign-in disclosure ([_Settings_](mcp-sign-in.md#settings)) adds the URI where it shows it. Its rules are in [_The `oauth` fields_](mcp-sign-in.md#the-oauth-fields) ([Signing in to remote MCP servers](https://github.com/ian-pascoe/cloudpid/issues/390) D3). Here: `oauth` on a stdio entry or beside an `Authorization` header is refused in Settings and skips the entry in a Repo file; in Settings `clientSecret` and `privateKey` are each exactly one `${NAME}`, never a literal (a Repo file may hold literals, being public already).
  - `sampling`: `ask` (default) | `allow` | `off` ([Sampling](https://github.com/ian-pascoe/cloudpid/issues/387) D2; see [_Sampling requests_](mcp-server-requests.md#sampling-requests)). In a Repo file `allow` is read as `ask`, with the problem "copy it into the Settings to allow it".
  - Elicitation, MCP tasks and MCP Apps have no per-server key (a per-server `tasks: false` is left for later).
  - `${NAME}` (never bare `$NAME`) only in `env` and `headers` values (and `oauth`'s two secrets). `${…}` anywhere else (`command`, `args`, `cwd`, `url`, the other `oauth` fields) is refused, and so is a `${…}` that is not a `${NAME}`. pi's `!command` values (an `env` or `headers` value starting with `!`) are refused in Settings and skip the whole entry in a Repo file. pi's `auth` is refused in Settings and skips the entry, with a problem, in a Repo file. Unknown keys: refused in Settings, the entry skipped with a problem in a Repo file. Every rule a Repo file shares with the Settings is one rule, one decode.
- **Names:** `^[A-Za-z0-9_-]+$`, at most 64 characters. Names that differ only in case or in `-`/`_` clash across every layer, since tool names lowercase the server part and map `-` to `_` ([MCP tools in a Session](https://github.com/ian-pascoe/cloudpid/issues/381) D6).
- **What is the definition:** every key but `enabled`, `exposure` and `toolExposure` (GLOSSARY → MCP server definition): `type`, `command`, `args`, `cwd`, `url`, `env`, `headers`, `oauth.*`, `timeout`, `description`, `sampling`. An adjustment can never carry one of them, so a different `sampling` or `timeout` per Environment takes an Environment's own full entry.
- **Directories** ([MCP server configuration](https://github.com/ian-pascoe/cloudpid/issues/380) D5): a Settings stdio entry runs in the Session's default directory (`/workspace/<repo>` with one Repo, else `/workspace`) and may give an absolute `cwd` (a relative one is refused). A Repo entry's `cwd` is relative only, normalized against `/workspace/<repo>` (its default) and kept inside it; otherwise the entry is skipped with a problem. A Repo's stdio entry is read with its `cwd` absolute, `/workspace/<repo>[/<cwd>]`, whether it gave one or not. A stdio server always runs in the calling agent's own Workspace Container, against its files, wherever its entry came from.
- **Bounds** ([MCP server configuration](https://github.com/ian-pascoe/cloudpid/issues/380) D10): 50 servers per Scope and per Repo file; an entry ≤ 16 KiB as written, measured without `enabled` and `exposure` (so switching a server off is always possible); `env` and `headers` ≤ 64 keys each; `toolExposure` ≤ 200 keys; a description ≤ 1 KiB; a Repo file ≤ 64 KiB. Settings refuse them on save; a Repo file over any of them (a 51st server, a name over 64 characters, an entry over its bounds) is skipped whole with a problem. An Environment's adjustments are not servers and do not count toward its 50: they are bounded by the servers they adjust, and counting them would stop an Environment with 50 servers of its own from switching one of Global's off. The count is of one layer's own full entries: the settings an Environment resolves to also hold Global's, so the bound is checked on the layer (`mcpLayerProblems`), not on the merged settings.

## Scopes, adjustments and the set

- **Environment over Global** (pi's rules, [MCP server configuration](https://github.com/ian-pascoe/cloudpid/issues/380) D2): an Environment's full entry replaces Global's of that name whole; its adjustment applies over the server it adjusts (`{ ...base, ...value }`). An Environment can switch a Global server off, never delete it. Global holds no adjustments: it has no lower layer to adjust.
- **Overrides:** an Environment's full entry is one Override field, `mcp.servers.<name>`; each key of its adjustment is an Override field of its own, `mcp.servers.<name>.enabled`, `.exposure` and `.toolExposure` (the map whole), each with its own Reset; resetting the last key removes the adjustment. `fieldDepth`, `settingsFieldPath` and `overrideFieldPath` become entry-aware for these paths. An Environment holds either its own entry or an adjustment for a name, never both.
- **Orphans:** an adjustment with no base is refused on save; one whose base disappears later (Global removed it, a Repo dropped it) is a problem with Reset.
- **Order** ([MCP server configuration](https://github.com/ian-pascoe/cloudpid/issues/380) D4): the owner's entries resolve first (an Environment's full entry over Global's); a Repo's full entries only add servers; adjustments then apply, a Repo's first and the Environment's last, so the Environment has the last word.
- **Shadowing:** a Repo entry under an owner's name (or a case or `-`/`_` twin of it) is **shadowed**: an info mark, plus "differs from your entry" when the normalized entries differ. It is never a problem and no provenance is stored. Two Repos defining one name is a problem; the first Repo in the Environment's Repo order wins.
- **A Repo's adjustments only switch off:** `enabled: false`, `exposure: "hidden"` and `hidden` values in `toolExposure`; any other adjustment is skipped, whole, with a problem. A Repo's `hidden` tools are put ahead of the server's own `toolExposure` keys (the first pattern wins), so an adjustment can hide more and never less.
- **An adjustment stays inside the entry bound:** adjustments apply key by key, and a key that would make the merged entry (its base with the adjustment over it) larger than 16 KiB is dropped alone (only `toolExposure` can, for the bound is measured without `enabled` and `exposure`, and a key that does not grow the entry is never refused), as a problem on that Override field (`mcp.servers.<name>.<key>`, with its Reset); the other keys, `enabled` among them, stand. The Settings and the set apply it alike (`applyMcpAdjustmentSteps`), so a Global entry that grew after an adjustment was saved, or a hidden-pattern list that does not fit beside a large entry, reads the same on both. The Settings cannot see a Repo's files, so there only an adjustment over a Global base is fitted; the set fits every one, a Repo's base included.
- **Several Repos:** the Repo layer is the union of every Repo's file, in the Environment's Repo order. Every Session of the Environment, at the Workspace root or in a Repo, sees the same set.
- **The resolver:** `resolveMcpServerSet(global, environmentOverrides, repoLayers)` in `@cloudpid/config` takes the Global document, the Environment's Overrides and each Repo's file as read (directory, slug, path and text), and returns the resolved entries, each with its source (`global`, `environment`, or `repo` with the Repo's directory, slug and path), the problems, and the orphaned adjustments. Each owner's layer is read as the Settings read it, by one function (`readMcpLayer`) that both call, so the two cannot differ: an entry that no longer decodes is skipped with a problem (it does not count toward the 50, nor make its twin a clash), and an adjustment stands key by key, each key being an Override field of its own. An Environment's own name that is the case or `-`/`_` twin of one of Global's wins, with a problem on Global's; the lenient read of an Environment's Overrides leaves Global's twin out of its settings the same way (a save refuses the clash). Beside it, also pure: the Exposure resolver (a tool's server `exposure`, then `toolExposure` with exact names over patterns and the first matching pattern winning, then a `tools.offered` match lifting `codemode` or `deferred` to `direct`, never `hidden`), shared by the Session, the Settings page, `settings_mcp_*` and the MCP status UI once it exists; `conn` and `mcpServerIdentity` ([_Storage_](mcp-connections.md#storage)).
- **What `hidden` means:** a `hidden` tool is unreachable: never registered in a Session, never in a subagent's ceiling, never callable from its server's App Views. A `hidden` server (its own `exposure`) also offers no MCP prompts and no resources. A switched-off or `hidden` server's connection and streams are closed and its Resource watches ended, its inventory kept. Nothing but the owner's Settings, or an approved agent change, makes either reachable again ([_Approval_](#approval)).

## A Repo's `.pi/mcp.json`

- **Which copy:** the Repo root's `.pi/mcp.json` on its **default branch**, read by the Registry through `RepoReader` as the GitHub App ([ADR-0029](../adr/0029-repo-mcp-servers-run-as-its-scripts-do.md)), its blob SHA telling a change, and cached per Environment in the Registry. Never a working tree: an edit on a branch changes the set only once it is merged.
- **When it is read:** on `addRepo`; when `McpHost` asks for the set (`mcpServerSet`) and the last look is over 10 minutes old; when a Build notices that the default branch moved; on Reload (the Settings page's, or `settings_mcp_reload`). Reads are throttled to one per (Environment, Repo) per 30 s, shared by the scheduled looks and the agent's reload; the owner's Reload bypasses the throttle.
- **GitHub Repos only** (as Skills, [ADR-0026](../adr/0026-skills-kept-by-cloudpid-and-fetched-from-github.md)): a non-GitHub Repo's file is not read (an info line on the page). A private GitHub repo the App cannot read is a problem asking the owner to install the App.
- **Failures,** by what GitHub answered ([MCP server configuration](https://github.com/ian-pascoe/cloudpid/issues/380) D7):
  - file 404 with the Repo readable: the Repo's servers go, with no problem;
  - Repo unreadable (repo 404 or lost access, rate limit, 5xx, network): the last good copy is kept, marked with the error and its age; a problem after 24 h of failed looks; dropped only by the owner's Reload or by removing the Repo;
  - read, but unparseable, without an `mcpServers` object, or over 64 KiB: the Repo's servers go, with a problem, and no old copy is kept.
- **Run ungated, without Secrets:** a Repo's servers run without the owner's OK, as its `.cloudpid/start.sh` does. Their `${NAME}` reads the Environment's Variables only; an entry naming a Secret is skipped with the problem "a Repo's server gets no Secrets — copy it to this Environment's Settings". The owner's copy (the page's _Copy to this Environment_ / _Copy to Global_, or an approved `settings_mcp_add` with `from_repo`) is the owner's entry from then on, resolves Secrets, stays as copied rather than following the Repo's commits, and needs its own MCP sign-in (an MCP sign-in is kept per source, name and URL, [ADR-0034](../adr/0034-an-mcp-sign-in-belongs-to-one-mcp-server-is-kept-global-in-the-registry-and-only-the-owner-makes-one.md)). A stored token is only ever sent to the resource it was obtained for, so a Repo entry naming any URL cannot collect the owner's token for another.
- **No tool writes it:** the agent edits `.pi/mcp.json` as any file, on a branch and in a pull request; git is its history and its revert, and such an edit is not an Agent change.

## `${NAME}` values

- **Resolution:** at use, per Environment, never in the Registry's copy of the set. An owner's entry (Global's or the Environment's) resolves `${NAME}` against the Environment's Secrets (its own, then Global's), then its Variables (its own, then Global's); a Repo's entry against Variables only. A Global entry therefore resolves differently in each Environment, and each Environment's `McpHost` connects to it on its own.
- **Where values go:** `McpHost` asks the Registry's `mcpServerValues({ environment, server, conn })` for the resolved `env` and `headers`, keeps them in memory only (asked again at the first use 60 s after the last answer, served stale while refreshing), and hands them to the engine with each call, with the Secret values among them as `redact`, which the engine scrubs from what it hands back; the bridge passes a stdio server's `env` to its process. Resolved values never enter a hash, a span, a log line, a Settings read, the Registry's set or a Session; Secrets are redacted wherever they could surface. A stdio server's `env` is readable by the agent's own commands through `/proc` in the same Container, which is accepted.
- **Checks:** the owner's form checks each `${NAME}` on save against the Scope's Variable and Secret names: at an Environment an unknown name is refused; at Global it is a hint, and a problem on the page of each Environment where it does not resolve. Left to implementation: whether a server with an unresolved name is then `skipped` or connects without the value. `settings_mcp_list` marks each name `secret`, `variable` or `missing`. The Settings page does both (_As built_ below): the form's check, and on each Environment's page a problem on the row of a server that reads a name that Environment lacks.
- **No Secret References:** a Secret Reference placeholder is never resolved in an entry or in MCP tool arguments ([_Calls and results_](mcp-in-a-session.md#calls-and-results)); `${NAME}` is the only way a Secret reaches an MCP server.

## The Settings page's "MCP servers" section

The section `mcp` (`/settings/:scope/mcp`) at each Scope ([MCP server configuration](https://github.com/ian-pascoe/cloudpid/issues/380) D9):

- **List:** one list by name, each row with its transport and target, an enabled switch, an Exposure select, the description (replaced by a problem when it has one), a source badge, and inherited/overridden marks with Reset on `enabled`, `exposure` and `toolExposure`. At Global each row shows "Overridden in N environments". A row whose latest change is the agent's, neither reverted nor dismissed, says "Changed by the agent · 5 min ago", linking to the change. Sign-in state and controls on HTTP rows are in [_Settings_](mcp-sign-in.md#settings); connection state and logs are left for later (the MCP status UI).
- **At an Environment:** _Add_ makes an Environment-own full entry; a row's switch and select write an adjustment (so "off at Global, on in one Environment" is a Global entry with `enabled: false` plus that Environment's `enabled` adjustment). Above the list, each Repo's file: its path, last read time, error, and **Reload**. Repo rows are read-only (view as JSON), with the switch-off adjustments and _Copy to this Environment_ / _Copy to Global_.
- **Add/Edit form:** stdio (command, args list, `cwd`) or HTTP (`url`); `env` and `headers` rows hinting `${NAME}` with the Scope's Variable and Secret names (values never shown), with the agent's credential-shaped-literal patterns ([_Approval_](#approval)) as warnings; timeout, description, enabled, Exposure, "Model use: Ask / Allow / Off" (`sampling`, [Sampling](https://github.com/ian-pascoe/cloudpid/issues/387) X4), a "Sign-in (OAuth)" disclosure with the `oauth` fields; `toolExposure` as pattern → Exposure rows, free-typed until the server has been discovered, then with tool-name suggestions; a raw-JSON tab.
- **Import:** "Paste pi `mcpServers` JSON" lists each entry with its problems before saving; a name already present asks _Replace_ or _Skip_; a top-level `autoEnableCodemode` is ignored with a hint.
- **Warnings:** the section warns when a server has `codemode` Exposure while `tools.offered` lacks `codemode` at that Scope ([MCP tools in a Session](https://github.com/ian-pascoe/cloudpid/issues/381) D8).
- **Problems:** each entry's problems show on its row, naming the source (Global, this Environment, or Repo `<name>` and path); a file's problems show on its Repo's row. An Environment's page shows the problems of its whole set; Global's shows only Global's own. Problems never reach a prompt section, a Session notice or a Notification; the agent reads them in `settings_mcp_list`.

### As built

The section is `apps/web/src/settings/mcp*.ts(x)`: `mcp-model.ts` (the rows and warnings, pure), `mcp-form.ts` (the form's fields and their checks), `mcp-import.ts`, `mcp-write.ts` (what each action writes), `mcp-state.ts` (atoms), and the components `mcp.tsx`, `mcp-form-panel.tsx`, `mcp-import-panel.tsx` and `mcp-parts.tsx` (the list of messages, the one select of an Exposure and of "Model use", and the line that says an Environment's names are not loaded). The form's drafts and the logic that moves them (`newMcpForm`, `mcpFormShowing`, `toolsDraftOf`) are in `mcp-form.ts`.

- **The rows are resolved in the browser,** by `resolveMcpServerSet` over the two documents the page already reads: Global's saved overrides (`getSettings`) and the Environment's Overrides (`getSettingsOverrides`), so the page and the Registry read one rule. Its Repo layers are the Registry's last good reads of each Repo's file (`mcpRepoFiles`, below), taken by the same `mcpRepoLayersOf` rule as the Registry's (a file with a copy held: `read`, or `unreadable` with its last copy kept). The list is by name; a row's source badge reads `Global` (at Global), `From Global`, `This environment`, or `This environment · replaces Global's`.
- **Marks:** at an Environment a Global server shows its three keys (`Enabled`, `Exposure`, `Tool exposure (n)`) each as _Inherited_, or _Overridden_ with a _Reset to Global_ that resets that Override field only. An Environment's own server has no marks (the switch and select write the key inside its entry). At Global the row says "Overridden in N environments", counting an Environment once whether it holds the entry or any adjustment key.
- **Writes act at once,** as Secrets do, and are made from the document as the Registry has it when the owner acts. At Global: the Global document whole with the entry's key set (`updateSettings`). At an Environment: a patch of its Overrides (`updateSettingsOverrides`): the adjustment key `mcp.servers.<name>.enabled|exposure|toolExposure` for a Global server (an Override even when equal to Global's), the key inside the entry for its own, one Override `mcp.servers.<name>` for an Add, an Edit or an import (which replaces an adjustment of that name), and `reset` for a Reset or a Remove. A change from a row's switch or select carries what the row showed it to be of (`target`: the Scope's own entry, or an adjustment of a Global server); if the Registry no longer holds that (the own entry was removed meanwhile, or an own entry now stands where the row showed an adjustment, or the Global server an adjustment is of is gone), it fails with a message and writes nothing, instead of adjusting Global's server of the same name. A server that is gone when the owner acts fails the same way.
- **The form, the import and the tool exposure editor open above the list,** not in a dialog (the editor's Save is held when its server is no longer one of Global's here); their drafts are kept per Scope while the app is open. A Global server at an Environment has no Edit: _Tool exposure…_ edits its adjustment whole, _Use its own copy…_ opens the form with Global's entry as this Environment's own (dropping its adjustments, as an own entry replaces them), and _Edit at Global_ links to Global's section. Removing Global's server leaves an Environment's adjustment of it as an orphan (a problem with Reset).
- **The form** writes pi's key order and no default: `enabled` only when off, `exposure` but `codemode`, `sampling` but `ask`, no empty `env`, `headers` or `toolExposure`. It keeps the keys it has no field for (`oauth`, `type`) as they were and says so; the JSON tab edits the whole entry, and a switch between the tabs reads one into the other. It is checked as the Registry checks it (`decodeMcpServerValue`, the name rules, a twin of any layer's name). Tool names are suggested from the Environment's `mcpServers` answer once the server has been discovered; at Global there is no host, so they are free-typed.
- **`${NAME}`:** the hints list the Scope's Secret names (its own and Global's) and Variable names (in force), never a value; an Environment's form refuses a name that is neither, and its row shows one as a problem, so a Global server whose name an Environment lacks says so on that Environment's page, naming the source of the entry (`Global: headers.Authorization reads ${NAME}, …`). At Global it is a hint. At an Environment Save and Import are held until the Scope's Secret and Variable names are loaded (the form says why), and blocked, with the error and _Try again_, when loading them failed, since a name checked against none would be missed; Global's are not held. **Credential-shaped literals** are `mcpCredentialLiterals` in `@cloudpid/config`, one check for the form, the import and the agent's tools, and a warning on the page, never a refusal.
- **The import** accepts pi's `{ "mcpServers": … }` and nothing else. Each entry is checked as the form checks it; one with a problem is never imported. A name the Scope's own layer has asks _Replace_ or _Skip_ (_Skip_ until chosen); at an Environment Global's name is no conflict, since the entry replaces Global's there, and the entry says so. A 51st server is a problem on the entry. `autoEnableCodemode` is ignored with a hint linking to the offered tools, and any other top-level key with a line saying so.
- **Problems** come from the set (an adjustment with no server, a twin-name clash) and from what the Registry's lenient read left out of each document, which `getSettings` and `getSettingsOverrides` give structured as `mcpProblems` (always, an empty list for none, so that the page reads the `problem` text only where the field is absent: an older Registry) (`@cloudpid/config`'s `McpSettingsProblem`: the layer it is in (a string, `global` or `environment`; a layer a later build adds is shown under its own name, not as Global's), the server's name, the keys below the entry, the words, and the Override fields whose Reset clears it). Those are an entry that no longer decodes ("is not used and is forgotten by the next save"), an adjustment key held over the entry bound once applied over the Global server it adjusts (the lenient read drops that key, and the next save at that Environment forgets it, as its row says; its Reset removes it at once), and a Global server left out of an Environment's view for the twin name of its own entry (Global's, not a forgotten Override of the Environment's). Each names its source. One that names a shown server is on its row, in place of the description, with its Reset; the rest are under _Problems_, an orphan with its Reset. Against an older Registry that gives only the `problem` text, the page reads the `mcp.servers.*` lines of it, as before; that fallback cannot tell whose layer a twin line is in, so it shows it as the Environment's.
- **Known limits:** the Registry takes no revision, so a change is made by reading the document as it is and writing it back: `updateSettings` takes the Global document whole, and `updateSettingsOverrides` a `set` and a `reset`, with no compare-and-set. Another change (the agent's, or the owner's in another tab) that lands between the page's read and its write can be lost by a Global write, which puts back the whole document it read; an Environment's patch touches only its own fields and loses nothing of other fields, but can overwrite the same field. This is the window every Settings section has; it is not closed here, and a Registry compare-and-set would be a change of its own. What the page does guard is its own row: a change aimed at an entry or an adjustment that is no longer there fails and writes nothing (above).
- **The warning** counts the enabled servers with `codemode` Exposure, since a server that is off reaches no one, against `tools.offered` in force at the Scope.
- **Status chips** are at an Environment only (Global has no host), from `mcpServers`, asked again every few seconds while the page is visible and after each save: `Connected · n tools`, `Connecting`, `Needs sign-in`, `Sign-in rejected`, `Unavailable`, `Failed: <error>`, `Skipped`, `Off`, `Not checked`, and `Unknown state` for a state this build does not know. An `Unavailable` or `NoEnvironment` answer shows no chips, with one line for the first.
- **Repo files** (an Environment's page; [#468](https://github.com/ian-pascoe/cloudpid/issues/468)):
  - **Reads:** the Registry keeps one row per (Environment, Repo) in `mcp_repo_files` (migration 31: the blob SHA, the text it read, `checked_at`, `ok_at` and the last error), deleted with the Repo or the Environment. `RepoReader.file(repo, ref, path) → { sha, size } | null` (the Contents API; `null` is the file's 404 with the Repo readable) tells a missing file from an unreadable Repo and an oversize file before its text is downloaded; the text is then read at that SHA. `headTree` was not used: it is truncated on big Repos and carries no size.
  - **The page** asks `mcpRepoFiles({ environment })` (a tagged answer: `Unavailable` and `NoEnvironment` as for `mcpServers`, and an older Registry has no such RPC, so the page shows the Repo rows it can) and writes `mcpReloadRepoFiles({ environment, repo? })`. A file's `state` is `never`, `read`, `absent`, `oversize`, `unreadable`, `not_github` or `unknown` (a state this build does not know), with the blob, the copy held, when it was read and looked at, and the error and since when; its `problem` text is computed by the Registry, not by the page: the 24-hour rule for an `unreadable` Repo whose last copy is kept, the oversize words, and an `unreadable` Repo with no copy to keep. A file that does not parse shows its problem from the copy's own read.
  - **Reload** reads the Repo again at once, **bypassing the 30 s throttle** (the owner asked), and drops the kept copy when the read fails; the Registry then runs a push in the background (`mcp.sync`). A Reload of one Repo is aimed by directory name; with none, every Repo of the Environment.
  - **Repo rows** are read-only: _View as JSON_ shows the entry as written, with the switch and Exposure writing the adjustment (`enabled`, `exposure` or `toolExposure`, any of them marks the row adjusted) on the Environment, by the same writes as a Global server's. A Repo's server whose `${NAME}` names a Secret shows the problem on the row (the host skips it, "Needs ${NAME}"); `${NAME}` values themselves are never shown.
  - **Copy** _opens the form_ with the Repo's entry as an Environment's own (or, for _Copy to Global_, sets Global's panel and moves to it), with `cwd` made absolute; it is not a one-click write, so that the form's checks and its `${NAME}` hints apply, and the owner saves it. A copy needs the entry as last read; a Repo whose file is `absent`, `oversize`, `not_github` or never read has none.
  - **Looks** are made by `mcp-repo-look.ts` (`lookAtMcpRepo`; one look per Repo at a time, a second joins it; a row is not written for a Repo removed in the meantime) for four reasons: `due` (the host's pull, and a Repo never looked at, which `sessionSettings` looks at once so that its servers count and wake the host), `moved` (`addRepo`, and `recordBuild` when a Repo's commit changed, which the main Worker's build upkeep follows with an `mcp.sync`; a Build seen through a Session is healed by the next pull), and `reload`. `due` and `moved` are throttled to one read per 30 s, and `due` to one per 10 minutes.
- **Left to their tickets:** the Sign-in (OAuth) disclosure and a row's sign-in state ([#469](https://github.com/ian-pascoe/cloudpid/issues/469)); and "Changed by the agent · 5 min ago", which reads the `mcp.servers.*` records of `settings_mcp_*` (#484), none of which exist yet, so the row has no such line.

## From the Registry to the host

- **What the Registry keeps:** the Repo layer cache and its looks, and per Environment the hash and revision its host was last handed, a counter of the revisions given out, and the deleted Environments whose host is yet to be wiped (a document, `mcp-handed`). The set itself is computed on demand from the layers (`mcpServerSetOf`, over `resolveMcpServerSet`; pure, in `apps/server/src/registry/mcp-set.ts`), never stored: a hash of the whole (SHA-256 over the entries' names and hashes in order) and per entry its own hash (over the name, source and entry in force), `conn` and `mcpServerIdentity`, all with `${NAME}` unresolved, so no Secret enters a hash. `McpHost` keys connections, inventories and eras by `conn`, not by the per-entry hash ([The Environment's MCP host object](https://github.com/ian-pascoe/cloudpid/issues/382) D3.1). A save at either Scope, a Repo look that changed a blob, `addRepo` and `removeRepo` change what it computes ([MCP server configuration](https://github.com/ian-pascoe/cloudpid/issues/380) D11).
- **Pushes:** a changed hash reaches the Environment's `McpHost` as `apply({ kind: "set" })`. The Registry never calls out, so the caller carries it: the main Worker for the owner's saves, `addRepo`/`removeRepo` and Reload, the Session for `settings_mcp_*` ([The Environment's MCP host object](https://github.com/ian-pascoe/cloudpid/issues/382) D6.3). After such a change the main Worker asks the Registry `mcpPending({ environment? })` (every Environment after a save at Global), which answers `{ pushes, wipes }`: the sets whose hash differs from what the host was last handed, and the deleted Environments whose host is to be wiped. It calls `apply` on each host's RPC stub, and tells the Registry `mcpPushed({ environment, hash, revision })` once the host took the set (`mcpDestroyed({ environment })` once it was wiped, which `mcpPending` lists as `wipes`, each with a revision from the same counter), so a push that failed is made again by the next, and a push never fails the save. Every set handed out, pushed or answered to a pull, has a `revision` from one counter that only rises; the host refuses a set whose revision is below the one it holds (`Stale`) and `mcpPushed` ignores one below the one recorded, so a push that arrives after a later pull, or two pushes out of order, never bring back an older set. **Destroy** is deferred the same way, since the Registry never calls out: its `deleteEnvironment` moves the Environment from handed to the list to wipe, with a revision above every set handed out so far, only if its host was ever handed a set (a host never woken holds nothing), and the main Worker sends `apply({ kind: "destroy", revision })`. `mcpPending` lists every wipe still owed at every sync, whatever Environment the sync is for, so a wipe that was lost is retried by any save, `addRepo`/`removeRepo` or the owner's next delete; the owner's delete endpoint runs a sync, and a delete a Session's `removals()` runs has no host binding, so it waits for the next sync of any kind. The host keeps `revision` as the floor of what may fill it again: a push or pull answered after the wipe, under an older revision, is `Stale`, while a newer set (an Environment made again) is kept. The Session → Registry edge of the `settings_mcp_*` tools has no version gate: across a deploy it fails loudly and heals ([_Deploys_](mcp.md#deploys)).
- **Pulls:** the host asks `mcpServerSet({ environment, heldHash }) → { hash, signInsRevision, set?, revision? }` (which runs the 10-minute Repo look) when a Session's Context Window opens (`requestStart` with `windowOpened`, a flag set on its first request), passing the hash it holds, so a lost push heals there; the answer's `signInsRevision` is the revision of the MCP sign-ins (0 until they exist), which `signInsRevision()` answers alone. The answer carries a new `revision` for the hash, noted as handed to the host whether the host holds that set or not, and the set only when its hash is not `heldHash` (a host that holds none holds the empty set). A later change is so pushed to the host even when no push of the earlier set was answered, and a push the host applied whose `mcpPushed` was lost is not forgotten; the host keeps the revision (and stores the empty set under it when it held none), so a push handed out before the pull is refused as `Stale`. An Environment the Registry does not list gets neither revision nor set. The host does not pull when it starts: what it holds is in its storage, it is woken only by a push or a `requestStart`, and a pull there is what heals a push that never came.
- **Empty sets:** `McpHost` is never woken for an Environment without MCP servers: `sessionSettings` carries `mcp: { servers: n }`, a Session with `n = 0` and no Resource watches skips `requestStart`, and an empty set is pushed only to an Environment whose host was last handed a non-empty set (`shouldPushMcpSet`: the hash differs from what the host was handed, and none handed is the empty set). A host that is pushed the empty set stores it, like any set.
- **Effects:** editing `description`, `timeout`, `sampling`, `enabled`, `exposure` or `toolExposure` bumps the MCP inventory's version without reconnecting; any change to `conn`'s inputs closes that server's connection and rediscovers it ([_Discovery and the MCP inventory_](mcp-connections.md#discovery-and-the-mcp-inventory)). The Session's tools follow from its next request; its `mcp_servers` section stays as it is for the Context Window, with a notice ([_The prompt cache and the `mcp_servers` section_](mcp-in-a-session.md#the-prompt-cache-and-the-mcp_servers-section)).

## The agent's changes

The agent changes MCP servers through ten `settings_mcp_*` tools in the static `settings_mcp` extension (`@cloudpid/extensions/settings-mcp`, reaching the host through `McpHostClient`), not in the `mcp` extension, which is rebuilt whenever the inventory changes ([The agent's changes to MCP servers](https://github.com/ian-pascoe/cloudpid/issues/391) D1). They follow [_Settings changes_](agent-changes.md#settings-changes): a required `scope` (`*` or an Environment's id), a required `reason` (1 to 500 characters) on every changing tool, `changeSettings` with the entry-aware paths, records in `agent_changes`, a revert. Asking follows [_Approval_](agent-changes.md#approval).

### The tools

- **`settings_mcp_list({ scope })`, `settings_mcp_get({ scope, name })`:** read-only (see [_Lists_](#lists)).
- **`settings_mcp_add({ scope, name, entry? | from_repo?, reason })`:** exactly one of `entry` (a server in pi's shape, decoded strictly with the owner's schema, and defining a server: an adjustment-only entry is refused) and `from_repo` ([_Copying a Repo's server_](#copying-a-repos-server)). Always asks.
- **`settings_mcp_update({ scope, name, set, reason })`:** `set` takes definition keys only. A top-level key replaces its value and `null` removes it; `env`, `headers` and `oauth` merge key by key, `null` removing one key; `args` is replaced whole. `enabled`, `exposure` and `toolExposure` are refused, naming their tools. Always asks.
- **`settings_mcp_remove`, `settings_mcp_enable`, `settings_mcp_disable` (`{ scope, name, reason }`).**
- **`settings_mcp_exposure_set({ scope, name, exposure, reason })`.**
- **`settings_mcp_tool_exposure_set({ scope, name, tool, exposure | null, before?, reason })`:** `tool` is the server's tool name, a `*` pattern, or a model-facing `mcp__…` name mapped back through the inventory (refused when it maps to none); `null` removes the key. First match wins, as in pi: `before` names an existing pattern key to insert ahead of, or moves an existing key; without it a new pattern goes last and an existing key keeps its place; exact names ignore `before`, since they beat patterns. The result resolves the server's known tools before and after, giving `decides` (the tools this key now decides) and `shadowed_by` (an earlier key that wins), with the fix spelled out. A key that matches no current tool is kept with a warning (stressed for a `hidden` key, which then hides nothing); for an undiscovered server it says "not checked".
- **`settings_mcp_reload({ scope })`:** an Environment's id only. Reads each Repo's file again (throttled as in [_A Repo's `.pi/mcp.json`_](#a-repos-pimcpjson)), and the Environment's `McpHost` drops its eras and Legacy sessions and rediscovers its HTTP servers at once ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D3, [The Environment's MCP host object](https://github.com/ian-pascoe/cloudpid/issues/382) D7.2). It reports per Repo its directory, slug, path, outcome (`changed`, `unchanged`, `absent`, `unreadable` with the last good copy kept, `invalid`, `not_github`, `recent`), blob, read time, and error with since when; for the set, the servers added, removed and changed and the problems added and cleared. It is not an Agent change: no reason, record or Notification line. Only the owner's Reload drops a last good copy.
- **Existing tools:** `settings_reset` takes `mcp.servers.<name>.enabled|exposure|toolExposure` only at an Environment and only where they are adjustment keys; it refuses `mcp.servers.<name>` (pointing to `settings_mcp_remove`), any `mcp.*` field at `*`, and a key of the Environment's own full entry (pointing to the enable, disable and Exposure tools). `settings_get` shows one line, "MCP servers: N at this Scope; `settings_mcp_list` shows them". `settings_tool_offer` of an `mcp__*` pattern never lifts `hidden`.
- **No rename, no probe, no sign-in:** a rename is an add (approved) plus a remove, so an MCP sign-in never follows a new name without the owner's yes. There is no tool that tries a server without saving it: the agent tests by hand in its Container (running the command, the MCP Inspector's CLI, or `curl` of an `initialize` with a held Secret's placeholder), which `settings_mcp_add`'s description suggests. No tool signs in or out, confirms an issuer or touches a client grant ([_MCP sign-ins_](mcp-sign-in.md#mcp-sign-ins)).
- **How they run:** root only (`settings_` is in `PARENT_ONLY_TOOL_PREFIXES`) and deferred, each with a value for scripts as the other `settings_*` tools give. `list`, `get` and `reload` are read-only, parallel and `replay: "safe"`. `disable` is sequential and `replay: "unsafe"`, as the ordinary `settings_*` tools are. `add`, `update`, `enable`, `exposure_set`, `tool_exposure_set` and `remove` may ask, so they are sequential and `replay: "safe"`, as `settings_reset` is.

### Scopes and layers

`name` means the server in force in that Scope's set (an owner's entry over a Repo's) ([The agent's changes to MCP servers](https://github.com/ian-pascoe/cloudpid/issues/391) D2):

- **On/off and Exposure:** at `*` they edit the key inside Global's entry. At an Environment they write that Environment's adjustment key (an Override even when equal to Global's) for a Global or Repo server, and the key inside the entry for its own server.
- **`add`:** at `*`, refused for a name Global has, allowed (with `entry`) for a name only in Repos, which it shadows. At an Environment, allowed over Global's server (its own replaces Global's there, and the card says so) and over a Repo's (shadowing it); refused for its own server (use `update`) and while it holds an adjustment for the name (clear it with `settings_reset` first).
- **`update` and `remove`:** only where the server is defined: at `*` for Global's, at an Environment for its own. A Global server at an Environment is refused, pointing to `*`, to `add`, or (for `remove`) to `disable`; a Repo server is refused, pointing to the Repo's file or a copy. Removing an Environment's own server falls back to Global's or un-shadows a Repo's, and the result says which.
- **A Repo-only name at `*`:** every tool refuses, naming the Environments that have it ("give one's id, or copy it").
- **Orphaned adjustments** are refused by the changing tools, pointing to `settings_reset`.
- **`disable` at `*`** on a Global server reaches every Environment but those whose own entry or `enabled` adjustment overrides it; the result names them.

### Approval

- **The line** ([The agent's changes to MCP servers](https://github.com/ian-pascoe/cloudpid/issues/391) D4, E1): a change to an MCP server definition waits for the owner's Approval: adding a server, copying a Repo's, or changing any key but `enabled`, `exposure` and `toolExposure` (an Environment's own entry shadowing Global's, a copy and a rename's add are adds). So does **widening**: any change that could make a switched-off server, or a hidden tool, reachable in some Environment's set:
  - switching a server on;
  - a server's Exposure leaving `hidden`;
  - removing a `hidden` `toolExposure` key, loosening one, or moving one so it matches fewer tools;
  - adding a non-`hidden` key on a `hidden` server, or a non-`hidden` key ahead of a `hidden` pattern;
  - a `settings_mcp_remove` or `settings_reset` that falls back to an on or un-hidden state.
- **Ordinary:** switching off, hiding, moves among `codemode`, `deferred` and `direct`, and removes that do not widen. Un-shadowing a Repo's switched-on entry is not widening. Enabling an entry whose `headers` name a Secret waits as widening, though where the Secret goes was settled when the definition was written.
- **The check:** by name, for each Environment the change reaches, with the pure resolvers (`resolveMcpServerSet` before and after, then `checkMcpWidening` over the server's two entries in `@cloudpid/config`, which lists why it widens). An exact name is told from a pattern by matching; two patterns are taken to overlap. The Registry has no inventory, so tool-level checks are conservative at the pattern level: it asks whenever the `hidden` keys shrink or a non-`hidden` key could now win. The card names the tools affected from the Session's own Environment's inventory when it has one.
- **What it protects** (said in the tools' descriptions): Secrets the Session never holds (a Global entry resolves `${NAME}` against every Environment's Secrets, and `scope: <B>` writes into B); the channel (headers are sent from `McpHost`, which neither the Session's redaction nor the Container sees); persistence (a URL keeps receiving every later call's arguments; a revert does not recall what leaked); the prompt (`description`, and the `instructions` a new server brings); the owner's MCP sign-ins. Not Secrets the Session already holds.
- **Values before asking:** every text the tools keep (name, command, args, `cwd`, url, `env` and `headers` values, `oauth` fields, description, `toolExposure` keys, reason) is refused when it holds a held Secret's value, a GitHub-token shape, the GitHub App's key or a Secret Reference placeholder, checked before decoding so no refusal echoes a value. **Credential-shaped literals** are refused too, copies included: literal text outside `${…}` in the `Authorization`, `Proxy-Authorization`, `Cookie`, `X-API-Key` and `Api-Key` headers (after an optional scheme word), and in `env`/`headers` keys ending `TOKEN`, `SECRET`, `PASSWORD`, `PASSWD`, `API_KEY`, `APIKEY`, `ACCESS_KEY` or `PRIVATE_KEY` (ignoring case and `-`/`_`); the refusal says to keep it as a Secret and write `${NAME}`.
- **`${NAME}` before asking:** at an Environment each name must resolve there (its Secrets and Global's, then its Variables and Global's), or it is refused. The refusal says what was not found where and points to `secret_ask` with `keep: "environment"` or `"all"`, to the owner for another Environment's Secrets, or to `environment_variable_set` for a value that is not secret. At `*` an unknown name is a card note listing the Environments where it is missing.
- **Refusals, in order** (nothing asked or recorded): parameters that fail to decode; a reason failing the plain-value check; an unknown scope (and `reload` or `from_repo` at `*`); the name and layer rules above (incl. a case or `-`/`_` clash with an owner's name, an adjusted name, `from_repo` problems); the plain-value check of every text; credential-shaped literals; the strict decode of the resulting entry; the bounds (incl. a 51st server); "already so"; an unknown `${NAME}` at an Environment; then widening decides whether to ask.
- **The card:** one per call, for one server and any number of its fields. Its target is "the Global Settings" or the Environment's Settings, and its change `MCP server "linear": add`, `edit`, `copy from Repo api`, `switch on` or `exposure`. A new optional `notes` block on the approval request (at most 12 lines of 200 characters, above _Now_/_After_, never scrolled away) says: **Runs** (command and directory, in each Workspace's Container) or **Connects** (from cloudpid, not the Container, to the URL); **Sends** (each `${NAME}` as Secret or Variable and where it goes; a Variable marked "plain: the agent can change it"; at Global, the Environments missing it); **Reaches** (this Environment's Sessions, or every Environment but those overriding it); **Replaces/shadows**; **Sign-in** (uses your MCP sign-in, or needs its own); **Prompt** (when `description` changes); **Model use** ("may use your models without asking" when `sampling` widens to `allow`, [Sampling](https://github.com/ian-pascoe/cloudpid/issues/387) D2.2); **Copy** (Repo, path, commit, read age, `cwd` made absolute); for widening, the tools it makes reachable. _Now_/_After_ show the entry as kept, pretty JSON in pi's key order, `${NAME}` unresolved, "None" for none. The `input` Notification reads `Approval needed: MCP server linear, Environment "Default"`. A decline returns "Nothing changed", the owner's reason, and not to ask again unless the user wants it.
- **Applying:** `expected` is `{ value: the entry in force at the Scope (or null), inherited?, after }`. Approve applies exactly `after` through `changeSettings`, only while value and inherited state are as shown; otherwise `changed-since` and nothing is saved. The Registry checks again in its transaction: the Environment exists, `changed-since`, the strict decode, the bounds, a name clash added meanwhile, `${NAME}` at an Environment; the Session re-runs the plain-value check on `after` first. A rerun after an eviction waits for the same request and applies the `after` it holds.
- **Itself an MCP server:** pointing a server at cloudpid's own MCP endpoint is not refused; it takes this Approval and a service token kept as an Environment Secret ([_Self-use_](mcp-endpoint.md#self-use)).

### Records and revert

- **Records** (`agent_changes`; scope `settings` for Global, the Environment's id otherwise): `add`, `update`, `remove` and a copy are one record each, field `mcp.servers.<name>`, `before`/`after` the entry in force at the Scope in its stored form (or null), with `beforeInherited`/`afterInherited` at an Environment (an add over Global's records Global's entry as an inherited `before`). On/off and the Exposure tools record `mcp.servers.<name>.enabled|exposure|toolExposure` with the key's value in force (`toolExposure` as the whole map), whether the key lives in a full entry or an adjustment; "inherited" means the Environment has no adjustment key. A rename is two records; a copy is an add record (`approved: true`), its provenance kept in the card, result and `details`, not the record. No Secret value is ever recorded (an owner-written literal is recorded as `before` when the agent edits that entry). The Run's Notification lists each, e.g. `settings_mcp_add mcp.servers.linear (Environment "Default")`.
- **Revert:** the owner's Revert never waits for Approval, widening or not. Reverting an add removes the entry, a remove puts it back, an edit restores the old definition, a copy removes the owner's copy (the Repo's entry runs again, without Secrets). A whole-entry change is reverted only while the Scope's entry is still `after` (same JSON and inherited state), a key change only while the key is; a revert is also refused as the owner's save would be (a 51st server, a name clash added since). A revert that puts an old URL back changes `conn`, so `McpHost` reconnects, reusing a kept inventory, and a kept MCP sign-in for (source, name, old URL) applies again at once.
- **A Repo's file** has no record and no revert here: git has both.

### Results

- **Each changing result** says what changed at which Scope (before/after lines); whether it reaches this Session (yes at its own Environment; at Global unless its Environment overrides the name; never at another Environment); and when: its tools follow from this Session's next request once discovered, the `mcp_servers` section stays as it is for this Context Window (a notice says so), and other Sessions get it at their next request. The Exposure tools' results give the effective Exposure from the resolver and name any `tools.offered` pattern that lifts a tool to `direct`.
- **Status wait:** after an applied `add`, `update` or `enable` that reaches the Session's own Environment, the tool asks `McpHost.servers` with the calling `workspace` and `waitMs: 10000`, and reports `connected` (N tools and how they reach the model), `needs_sign_in`, `failed` (at most 300 characters of error) or `connecting`. A stdio server is discovered only in the Session's own Workspace Container while it runs: no Container is started ("not discovered: the first call starts the Container") and no other Environment's host is woken ("not checked"). The change is applied, recorded and sent as a running update before the wait; Stop interrupts the wait and the change stands (still to verify in pi-durable: a cancelled call keeps its last running details). A rerun after an eviction finds the change made and reports the status with `waitMs: 0`.
- **Sign-in:** a server that needs one says "linear needs the user to sign in: load `mcp_sign_in_ask` with tool_search and ask"; the agent may ask in the same Run, since the set change bumps the inventory version and `mcp` is rebuilt with `mcp_sign_in_ask` ([_Sign-in requests_](mcp-sign-in.md#sign-in-requests)). A copy's result says it is the owner's server now, needs its own MCP sign-in and no longer follows the Repo's commits; a remove's says its sign-in stays, listed as unused, until the user signs out.
- **Details:** `details.agentChanges` keeps its shape (with `approval`), plus `details.mcp: { server, status, tools, error }` for the status chip; the structured output is the existing change output plus `server_status`.

### Lists

- **`settings_mcp_list({ scope })` at an Environment** shows its whole set: per server its name and tool prefix; its source (`global`, `environment`, or `repo` with the Repo's directory, slug and path); `replaces_global`; `shadowed` (the Repo entries it shadows, and whether they differ); transport and target; `enabled`, `exposure` and a `toolExposure` count, each with where it comes from; description; `reads` (each `${NAME}` as `secret`, `variable` or `missing`, and where it is used); the `settings_reset` fields the Environment holds; inventory state (`connected`, `connecting`, `needs_sign_in`, `failed`, `disabled`, `skipped`, `not_discovered`), tool, `direct`, prompt and resource counts, discovered time and error; `sign_in: { status, issuer_host, scopes, client_kind } | null`; problems with their source. Then each Repo's read state (blob, read time, error and since when, problem), orphaned adjustments, and warnings (such as `codemode` not offered while a server has `codemode` Exposure). **At `*`** it shows Global's entries only, with the inventory fields null and `overridden_in`/`adjusted_in` added.
- **`settings_mcp_get({ scope, name })`** adds the layers as written (Global's entry, the Environment's entry or adjustment, each Repo's, shadowed ones included), the resolved entry, up to 500 tools (cut with a flag), each with its model-facing name, title, effective Exposure and what decided it, hints and problems; the `toolExposure` keys that match nothing; the server's `instructions` (cut at 4 KiB) and prompt names; the negotiated protocol version ([The MCP core](https://github.com/ian-pascoe/cloudpid/issues/394) D3); `sampling`; and per-server counts such as forms declined for asking a credential ([Elicitation](https://github.com/ian-pascoe/cloudpid/issues/388) D8.4).
- **Neither** shows a resolved `${NAME}` value or a hash, and neither connects, discovers or wakes a Container: they read the Registry and `McpHost.servers` only. Their results are redacted as every result is.

### Copying a Repo's server

`settings_mcp_add({ scope: <Environment id>, name, from_repo: <the Repo's directory name in that Environment>, reason })`, at an Environment only ([The agent's changes to MCP servers](https://github.com/ian-pascoe/cloudpid/issues/391) D11):

- It copies the Repo's full entry as written (`${NAME}` kept) from the Registry's last good read, never a fresh GitHub read, with `cwd` rewritten to an absolute `/workspace/<dir>[/<cwd>]`.
- Refused before asking: an adjustment, a missing name, anything Settings refuse (`~`, `!command`, `auth`, unknown keys), a literal `clientSecret`/`privateKey` or a credential-shaped literal (the agent then uses `entry`). A `${NAME}` naming a Secret is the point of copying, not a problem.
- Afterwards the Repo's entry shows as shadowed and the copy stays as copied. A copy to Global is two steps: copy to an Environment, then `add` at `*` with an `entry` whose `cwd` is explicit. The owner's page _Copy to Global_ is one step.

### In the UI

- **Agent changes rows:** "MCP server linear", "MCP server linear · on/off", "· exposure", "· tool exposure". A whole entry renders as a folded JSON line diff (pi's key order, `${NAME}` as written; an add all `+`, a remove all `−`), `toolExposure` as one `pattern → exposure` line per key, `enabled` as on/off. Inherited marks ("Global's entry (inherited)") show on every Settings change, not only MCP ones. _Revert_ shows on every agent MCP change not yet reverted (approved ones and copies included), "Reverted" after.
