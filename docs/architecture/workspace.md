# Workspace and execution

[ADR-0016](../adr/0016-environments-and-a-container-per-workspace.md) replaced the Machines of [ADR-0015](../adr/0015-workspaces-are-worktrees-on-a-shared-machine.md). An **Environment** (GLOSSARY.md) is what the owner sets up once: a name, its Repos and its Container settings. A **Workspace** is what Sessions work in: a Workspace DO of its own (`ws:<id>`; the DO class and the `WORKSPACES` binding keep their names), its own Container, and its own full clone of each of its Environment's Repos, all on one branch. A new Session gets a new Workspace unless it is started in one that exists. A Session works in its Workspace, and its subagents in it too unless one has a **Subagent Workspace** (GLOSSARY.md; [ADR-0021](../adr/0021-subagents-in-workspaces-of-their-own.md)), a Workspace of the Session's Environment that the Registry lists as the Session's: so a Session has one Workspace, and one more for each of those, each conversation's tools using its own (see [_Subagents_](agent-capabilities.md#subagents)). Deleting the Session removes its Subagent Workspaces. Where these documents say a Workspace's file tree, Container, settings or snapshot, it means that one Workspace's. Machines, their worktrees and their Sessions were not carried over: the Registry's migration 11 reset them (see [_Client and protocol_](client-and-protocol.md) → Registry migrations).

## Filesystem and tools

- The workspace root is `/workspace`, with one directory per Repo of the Workspace: its clone. A Session's `cwd` defaults to its Workspace's directory (`workspaceDirectory`: `/workspace/<repo>` when the Workspace has exactly one Repo, else `/workspace`). `/workspace/.cloudpid/uploads/<session-id>/` holds the Session's Attachments (see [_Client and protocol_](client-and-protocol.md) → Attachments); like `.agents`, it is a hidden directory beside the repos.
- `ComputerExecutionEnv` (`packages/computer-env`) implements pi-durable's `ExecutionEnv` over the Workspace DO's RPC stub, and must pass `registerEnvConformance`. Its `listFiles` walks one directory at a time (one `fs.find` of the directory's own entries each) and filters as it goes, so a directory it skips (an excluded name, what git ignores, `.git`) is never walked; a directory holding `.git` below the listed one is a work tree of its own, whose ignore rules apply from there in place of those above it, also when the listed directory is in no work tree.
- `write` and `edit` are pi-durable's own tools, `read` is pi-durable's wrapped so that every image it returns fits the conversation (see _Images `read` returns_ below), and `bash` is pi-durable's tool with one more argument, `backend` (`@cloudpid/extensions/coding-tools`, see _Backends_). `ls`, `find`, and `grep` are thin tools over the Workspace DO's search operations (`readdir`, `find`, `grep` in `@cloudpid/computer-env`'s host, over computer's `fs.readdir`, `fs.find`, and `fs.grep`; `@cloudpid/extensions/files`), so on the Workspace's own paths they never start the container. Their parameters and output follow local pi's; `find` and `grep` skip `node_modules` and `.git` below the searched path, since the Workspace's file system has no `.gitignore` handling, and a search from above `/workspace/.agents/skills` or `/workspace/.cloudpid` skips them too.
- **Container-only paths** ([ADR-0018](../adr/0018-file-tools-reach-container-only-paths-through-the-container.md), GLOSSARY.md): a model tool's file operation on a path only the Container has (outside `/workspace`, or matching the launch's Container-only patterns inside it) runs on the Container, starting it if it is stopped. The Session's `env` and file search ask for it (`reachContainer` on each `EnvRequest`; `lookupEnv`, the composer, Skill and Prompt template discovery, Attachments and the readying never do). The Workspace DO decides by pattern alone, never by whether the file exists (`isContainerOnly`, `container-paths.ts`), with the patterns of the launch that runs now or of the next one (`ContainerLaunch.ignore`); every launch's list ends with `!/.cloudpid` and `!/.cloudpid/**` (`withHarnessKept`), so the harness's own directory is always synced. computer reaches a Container only through commands, so each operation is a bash script the Workspace DO runs there as any command (`ContainerFiles`, `container-files.ts`; 5 minutes at most), its failures named as the Container's (`… (on the Container)`). Bytes cross through stage files in `/workspace/.cloudpid/tmp` (`xfer-<uuid>`), which computer pushes before the command and pulls after it. `read` (and a binary reader) copies the whole file over when it opens it and reads the copy as the Workspace DO's own reader, since pi-durable's line scan needs every byte; a file over 32 MB (`MAX_CONTAINER_FILE_BYTES`) is refused with a pointer to `bash`. `edit`'s read records the file's SHA-256, and the write after it replaces the file (a temp file beside it with its mode, moved over it) only while it still has that hash, else fails with "read it again". `find` and `grep` rooted in a Container-only path run `find` (its `-path` as a superset of the glob, filtered exactly in the Workspace DO, at most 20,000 lines) and `rg --json --no-ignore --hidden`. `ls` of a synced directory adds the Container-only entries the Container has there, marked `(container-only)`, only while it runs: a listing does not start it. Operations the tools do not use on such paths (rename, remove, truncate, watch, listings for the composer) fail as `not_supported`, pointing at `bash`. computer's `createPiTools` is not used ([ADR-0008](../adr/0008-pi-durable-tools-over-computer-tools.md)). The coding tools' `coding_tools` prompt section (fixed text, one line per tool the request offers) tells the model to read files with `read` rather than `cat`/`sed -n` in `bash`, to change them with `edit`/`write` rather than python, node or `sed -i` scripts, to search with `grep`/`find`/`ls`, and to leave `bash`'s `backend` unset so the Container starts only for what needs it.
  - **Images `read` returns** (`@cloudpid/extensions/images`, [#91](https://github.com/ian-pascoe/cloudpid/issues/91)). A tool result is one conversation entry, one row of the Session DO's SQLite, which Cloudflare caps at 2 MB; a write over it fails the commit and so the Session. So every image `read` returns is at most 750,000 base64 characters (`MAX_IMAGE_CHARACTERS`, about 560 KB, the bound the browser's screenshots keep too), or the model's own `inputLimits.images.resize.maxBytes` when smaller; its width and height stay the model's (2000 × 2000 by default). The Session gives pi-durable's `read` an image processor over the Server Worker's Cloudflare Images binding (`IMAGES`), not Photon, whose WebAssembly memory would grow in the Session DO's 128 MB isolate and never shrink. `read` offers PNG, JPEG, GIF and WebP, the formats every provider takes inline and the binding takes as input; pi-durable's `read` also finds BMP, which the binding does not take, so a BMP is left out with a note to convert it to PNG first. An image that already fits passes through untouched, with no call to the binding: its size comes from its header (PNG's IHDR, GIF's screen, WebP's VP8/VP8L/VP8X chunk, JPEG's SOF segment; ported from pi-durable, `NOTICE.md`), and only an image whose header cannot be read is measured with the binding's `info`, so an outage or a used-up quota never drops an image that fits. Otherwise the binding scales it down to the model's width and height and re-encodes it (JPEG stays JPEG, anything else becomes WebP, which keeps transparency), at quality 80, then 60 when a little over (at least 60% of the output fitting), then smaller, both sides shrinking by the square root of the share that fits with a 10% margin and at least a quarter at a time, at most 6 outputs per image (`MAX_IMAGE_ATTEMPTS`), from one copy of the file's bytes. Images bills each unique transformation (a source and its size: format and quality do not count; `info` is free; 5,000 a month on the Free plan, after which it answers error 9422). The result says what was done: pi-durable's notes say it was converted or resized, with the factor that maps coordinates back; one only re-encoded at its size and format says "Re-encoded at quality 60 to fit…", and an animated GIF or WebP made a still (the output's `anim: false`) says only its first frame is shown. An image that cannot be made to fit, that the binding cannot decode, or that the binding refuses (quota, outage) is left out: the result is an error whose message names the image and why, and the Session goes on. pi-durable reads an image whole into the Session DO before preparing it, so an image file over 20 MB (`MAX_IMAGE_FILE_BYTES`, the Images binding's input limit) is refused before any of it is read, with a note to read a smaller copy. `alchemy dev` and the workerd tests use miniflare's local emulation of the binding (sharp, which honours the size and format but not the quality); the workerd test reads a 3 MB PNG of noise through a Session and checks that the stored image is within the bound and the Session answers on.
  - **Images of one tool result.** The bound is per image, but one result can carry several: a `codemode` script can `image()` many (pi-codemode allows 16 Mi characters of output; a script gets no images from a schema-less tool such as `read`, but can build its own), and a browser run can take several screenshots. So every tool result's images, a call's own and a nested one's, are held to 1,500,000 base64 characters in all (`MAX_RESULT_IMAGE_CHARACTERS`, two images at the bound, leaving room for the result's text and details): they are kept in order until the next would go over, and that one and every image after it become a note saying it was left out and why (`ResultImages`, an `afterTool` hook, which runs before pi-durable stores a result entry or a nested call's result). Code mode stores a script's result in its run's document before the hooks run, so the Session's sandbox holds the script's output to the same budget first (`remoteSandbox`, `apps/server/src/session/codemode.ts`).
- A Session is bound to one Workspace, recorded in the Registry with the Workspace's Environment when the Session is created and never changed. The Session DO asks the Registry for it once and keeps it (`workspace-placement` in its key-value storage); `HarnessOptions.env` builds a `ComputerExecutionEnv` on that Workspace's DO (`workspaceObjectName`: `ws:<id>`) for each call, in the conversation's own `cwd`, else the Workspace's directory. A Session the Registry does not list works at the root of `ws:unlisted`, which is never readied, and is asked about again. A Repo's directory is a name (`REPO_NAME` in `packages/protocol`: letters, digits, `.`, `_`, `-`, never leading with a dot or dash), so a Workspace's directory cannot be a path.
- **Environments from the UI:** the Environments page (`/environments`) lists the Environments (`listEnvironments`), each as a card with its Repos and its Workspaces. An Environment has a fixed id (`EnvironmentId`: `default`, or eight hex digits for one the owner makes) and a **name**, 1 to 80 characters after trimming, unique among Environments whatever the case (the Registry compares names folded with `toLowerCase`, as the web app does; a `COLLATE NOCASE` unique index backs it for ASCII), which can be changed (`renameEnvironment`). `default` (named Default, with no Repos) is made by the migration and cannot be deleted, so a new Session always has an Environment to start in. `createEnvironment` makes one with a name and no Repos. A card's ⋯ menu has _Edit…_ (a dialog with the name, the Container's size, idle time and extra Container-only paths, and the Environment's variables (a `NAME=value` line each, checked as they are typed), Setup Script and Start Script: `getEnvironmentSettings`/`updateEnvironmentSettings`; it shows the settings in force, its Overrides over the Container settings at Global, with the Environment's own variables only, and saves the fields it changed as `set` and the variables taken out as `reset`, so a field left alone keeps inheriting Global's (see [_Container settings_](container.md); the page that shows which fields are inherited and resets them comes with [#350](https://github.com/ian-pascoe/cloudpid/issues/350)); it says they apply at a Workspace's next Container start, that the variables are plain, and that a service a Start Script starts must detach) and _Delete…_ (`deleteEnvironment`; not offered for `default`, which the Registry also refuses). Deleting asks the owner to type the name, then removes each of the Environment's Workspaces as _Remove_ does, then its spare Workspace (its record, then its Workspace DO: see _Spare Workspace_), then its Build object and its Test Build object, then its record and the Secrets kept for it, which the Registry deletes only while no Workspace, spare or not, is made from it: one made meanwhile is removed the same way and the sweep runs again (three rounds at most); a failure partway leaves what is not yet removed listed, to try again. Once the record is gone the Build object (and the Test Build object) is wiped once more, since a Build upkeep that asked it for a Build meanwhile made it anew; an upkeep that asks a spare to prepare or a Build object for a Build after that finds the record gone and wipes the object again itself. Each Workspace row shows its branch and has _New session here_, _Restart container…_ and _Remove…_. A Subagent Workspace's row is marked with its subagent's ID and links to its Session, and has no _New session here_; its _Remove…_ names what it has not pushed (`workspaceWork`, read when the dialog opens as a report reads it: by its Workspace DO while its Container is stopped) and deletes the subagent with it (see [_Subagents_](agent-capabilities.md#subagents)). A Session's delete confirmation names each of its Subagent Workspaces that holds unpushed work. **Remove** (`removeWorkspace`) asks the owner to type the branch, then deletes every Session bound to the Workspace, archived ones too, each as `deleteSession` does, then the Workspace DO (`destroy`: its Container, its files with what was not committed or pushed, its settings and snapshot record; the saved disk itself expires on its own), then its record, which the Registry deletes only while no Session is bound to it: a Session started meanwhile is deleted the same way and the sweep runs again (three rounds at most). The branches pushed from it stay on the remotes. **Restart container** (GLOSSARY.md → Container restart) asks for a confirm, then the Workspace DO forgets its Snapshot and stops its Container if it runs (`restartContainer`): the files and Sessions stay, commands running in the Container end, and the next command launches a Container from the Environment's Build when there is a usable one, else from the image, which installs the Toolchains, runs the Setup Scripts and is snapshotted again; what only the Container's disk held (its Container-only paths: dependency directories, build output, caches) is gone. A Workspace the Registry does not list is refused by both. **Global** (a section above the cards): a _Variables_ form with a `NAME=value` line each (checked as it is typed, with the Edit dialog's rules; `getGlobalContainerSettings`/`updateGlobalContainerSettings`, asked again every few seconds while the page is visible, since the agent changes them too; a save sends the names added or changed as `set` and those taken out as `reset`, so the other Container settings at Global stay as they are), then the Secrets kept Global, then the line of the Skills kept Global (below), then the Agent changes of the scope `*` of its Container settings and Secrets (those of its Skills are on the Skills page). Each card has a _Variables_ line naming its own variables and "Also from Global" those it gets, and the Edit dialog's variables field counts the inherited ones in its limit of 50 and names those it gets and those it overrides. **Secrets** (see [_Secrets_](agent-capabilities.md#secrets)): each card has a [_Secrets_](agent-capabilities.md#secrets) section, and the section above the cards keeps those at Global, with a note that a value that is not secret belongs in the variables. Each lists its Secrets by name, with whether each reaches the Build (a switch: `setEnvironmentSecretBuild`), _Replace_ (which puts the name in the form, for the value to be typed again) and a delete that asks for a confirm (`deleteEnvironmentSecret`); a card also names the Secrets it gets from Global. The form takes a name and a value of one or more lines, masked where the browser can (`setEnvironmentSecret`; a new Secret's build flag is in the form, and a name the section keeps replaces that value, keeping its flag), checks both as they are typed, and empties once the Registry has the value. A value is never shown again. **Agent changes** (see [_Agent changes_](agent-changes.md)): each card lists what the agent changed in the Environment's settings, Repos, variables and Secrets, newest first (`listAgentChanges`, asked again every few seconds while the page is visible), each with the setting, its value before and after in full (a Setup or Start Script's or the Toolchains' as a line diff with a few lines around each change, the rest folded; a list of paths a line each), who made it and when (with a link to the Session that made it while it is listed), the agent's reason, and _Revert_ (`revertAgentChange`) while it is the agent's and not reverted yet; a refused revert says what the field is now. Each also has _Dismiss_ (`dismissAgentChange`), which takes it off the list and keeps what it changed. **Skills** (ADR-0026): the Skills page manages them (see [_Client and protocol_](client-and-protocol.md) → Skills page, and _Installing from GitHub_ below). Each card has one line of its Skills, "N skills · Manage" (`skillCountText`: those its Workspaces serve, its own and those it gets from Global, saying how many it gets), whose _Manage_ links to the Skills page's Installed tab filtered to it (`/skills?tab=installed&environment=<id>`); the section at Global has the same line for the Skills kept Global, linking to `environment=*`. The Agent changes of Skills are listed on the Skills page, not here.
- **Repos from the UI:** an Environment's card lists its Repos and adds one (`addRepo`) from an address: `parseRepoSource` (`packages/protocol`, which the UI uses as the owner types) accepts `owner/repo` (GitHub) or an `https` URL of a dotted, non-numeric host whose path is plain segments, and refuses credentials, ports, queries, fragments, escapes, `..`, other schemes and private-looking hosts. The directory defaults to the repo's name, and the form has an optional field to name it (`RepoName`'s rule, checked as it is typed); one another Repo of the Environment has is refused, the refusal shows under the form, and the owner names this one. Each Repo row has _Remove_ (`removeRepo`). Both change only the Environment's record, and after the answer its spare Workspace, which no longer has the Environment's Repos and is made again (see _Spare Workspace_): nothing is cloned or deleted in a Workspace a Session has. A Workspace takes the Environment's Repos (name and address) when it is made and keeps them, so a Repo added later reaches new Workspaces only, and one removed stays in the Workspaces that have it.
- **Workspaces** ([ADR-0016](../adr/0016-environments-and-a-container-per-workspace.md)): `createSession` with `workspace: "new"` (the default) takes the Environment's spare Workspace when it has a current one (see _Spare Workspace_, below), or else registers a Workspace with the Session, in one transaction: an id of eight hex digits (`WorkspaceId`); its Environment (`environment`, `default` when none is named; one that does not exist is refused) and that Environment's Repos then; its branch, `cloudpid/<id>` or one the owner names (`branch`, a name git takes: `BranchName`, other than `cloudpid/spare`); and the branch it starts from (`base`, else each Repo's default branch). A branch another Workspace of the Environment is on is refused, naming that Workspace, so the owner starts the Session in it instead. `workspace: <id>` starts a Session in one that exists, which brings its Environment (naming another is refused, as are `branch` and `base`). Deleting a Session leaves its Workspace and what the Session did in it, until the owner removes the Workspace; archiving leaves it too. The clones are not made when the Workspace is: the Session DO readies its Workspace when the Session first uses its files or environment (`readyPlacement`, `apps/server/src/session/workspace.ts`),. Readying (`prepareWorkspace`, `apps/server/src/workspace/prepare.ts`) asks the Registry for the Workspace's set-up (`getWorkspaceSetup`: its Repos, branch and base, and its Environment's Container settings), hands the settings to the Workspace DO (`updateContainerSettings`) when they differ from those it holds (the Workspaces Worker cannot bind the Registry), then asks the Workspace's files whether each Repo's `/workspace/<repo>/.git` is there, without the Container. For the Repos that lack one it runs `prepareWorkspaceScript` (`@cloudpid/sandbox-image/workspaces`) on the Container under the Workspace's lock (`flock`), 15 minutes at most: a full clone of each into `/workspace/.cloudpid/tmp/clone-<repo>` (`GIT_ALLOW_PROTOCOL=https`, with git's hooks off and `SKIP_REFERENCE_REPOS=1`, so a Repo's own checkout hooks do not run before its Setup Script does), on the Workspace's branch: tracked from `origin` when the remote has it, else made from `origin/<base>` or the remote's default branch, else an orphan branch in an empty repo; then it is moved into place and runs `mise install` if it declares Toolchains. A Repo that cannot be cloned is reported with git's output, and the others are still made. Each new clone then has its Setup Script run if it is due (`repoSetupScript`; one that fails is only logged, and due again at the next Container start), then its Start Script if it has one (`repoStartScript`), since the Container already runs and its bootstrap did not see the clone: the clone script leaves a flag for each clone it made in `/tmp/cloudpid-start-due/workspace/`, which the run takes under the clone's lock, so of two Sessions that made it at once only one starts its services; one that fails is only logged too. A readying that succeeded holds for 60 s (`WORKSPACE_CHECKED_FOR`); one that failed fails the call and is tried again at the next, so a clone that failed or was deleted is made again from its branch. The composer's lookups (`catalog` and `files`) only read files, so they never ready the Workspace or wait for it (`lookupEnv`): until the clones are there they find only what the Workspace holds, its Skill set (by default empty). Workspaces share nothing but their Repos' remotes: each has its own files, Container, Toolchains, processes and ports.
- **Carried files:** a Fork or Clone in a new Workspace (see [_Session tree_](client-and-protocol.md)) starts from the source Workspace's files as they are. After the Registry has registered the new Workspace and the new Session is filled, the source's Workspace DO runs `carryWorkspaceScript` (`@cloudpid/sandbox-image/workspaces`) on its Container under the Workspace's lock, 15 minutes at most: for each Repo it has a clone of with a commit, its HEAD (commits not pushed included) is pushed to `origin` as the new branch, and its uncommitted Changes (untracked files that are not ignored included), read through an index of its own so the clone is left as it was, as a commit on HEAD to `refs/cloudpid/carry/<branch>` (`carryRef`). It is refused before anything is pushed when a remote has the branch already, and a push that fails takes back what was pushed. The new Workspace's readying then clones the branch as any, and `prepareWorkspaceScript` applies the carried commit's diff to the work tree, uncommitted still, and deletes the ref; a carry that does not apply fails that Repo's clone (made again at the next readying) and stays on the remote for the owner. The switch of a spare taken for it does the same.
- **Spare Workspace** ([ADR-0016](../adr/0016-environments-and-a-container-per-workspace.md); a spare starts its first Container from its Environment's Build as any new Workspace does: see [_Builds_](container.md)): each Environment that had a Session lately keeps one Workspace made ahead, so a new Session does not wait for the clones, the Setup Scripts and the first Container start. Its record is marked spare (`spare`, Registry migration 12) and is on the placeholder branch `cloudpid/spare` (`SPARE_BRANCH`, `@cloudpid/protocol`, which a new Workspace's own branch may not be: `ownBranchProblem`), so the Environment-and-branch index allows one per Environment; it records the Environment's Repos when it is made, as any Workspace does, and the Environment's last good Build then (its snapshot id, `spare_build`, Registry migration 15), which it is prepared from. `listWorkspaces` and `getWorkspace` leave it out, so the UI never shows it and no Session can name it (`workspace: <id>`). **Taken:** `createSession` with a new Workspace takes the spare when its Repos (names and addresses, in any order) are the Environment's: in the same transaction it stops being spare and gets the branch (`cloudpid/<its id>` by default, or the owner's, with the usual refusal of a branch another Workspace is on, which leaves the spare) and the base, and is listed from then, made at that time. A spare whose Repos differ is stale: it is not taken, and the Session gets a new Workspace. A spare made from another Build than the Environment's last good one is stale too, but a Session still takes it (its clones are there) until the upkeep removes it. A Subagent Workspace takes the spare as a new Session's Workspace does (`createSubagentWorkspace`), but no upkeep runs behind it (`sessionSubagentWorkspaces` only keeps the Build current), so a burst of subagents does not prepare a spare after each. **Only for an Environment that had a Session lately** ([#322](https://github.com/ian-pascoe/cloudpid/issues/322)): the upkeep makes a spare, after a take or a new Build alike, only for an Environment that had a Session in the last 3 days (`SPARE_REFILL_WINDOW_MS`, `apps/server/src/registry/store.ts`), measured from the latest `updated_at` of its Sessions, which a Session's creation and each change of its status set (a deleted Session counts no more). Past that window the Environment keeps at most the spare it has: one made from an older Build stays and is still taken, not remade; one whose Repos are no longer the Environment's is removed, as no Session can take it, and not replaced; and an Environment without one gets none. A new Environment so gets its first spare after its first Session, and an Environment used again gets one after the Session that finds none. Each spare prepared runs a Container for a minute or two and takes a Snapshot, which an Environment nobody uses does not need. **Turned off** ([#323](https://github.com/ian-pascoe/cloudpid/issues/323)): an Environment's Container setting `spareWorkspace` (on by default; its Override, else Global's: see [_Container settings_](container.md)), read leniently as every reader of the settings does, keeps it from any spare: the upkeep lists the spare it has as stale, current or not, so it is removed with its Snapshot as any stale spare is, and registers none, so a new Session's Workspace is made when the Session is created and waits for the clones and the Setup Scripts at its readying, as the first Workspace after a Build does. A Session created before the upkeep removed the spare still takes it. Turned on again, the next upkeep makes one, under the window above. The main Worker runs that upkeep after the owner's save (below); after an Agent change to the setting (`environment_spare_workspace_set`) the Session runs it (see [_Agent changes_](agent-changes.md)). **Replenished:** after a Session is created in a new Workspace (taken or made), after `createEnvironment`, `addRepo` and `removeRepo`, after the Builds' upkeep records a new last good Build (`buildUpkeep`), after the owner's save of the Environment's Container settings (`updateEnvironmentSettings`) and the revert of an Agent change to its Spare Workspace setting, after a change of the Spare Workspace setting at Global (the owner's save, an Agent change or its revert: each Environment's), and behind `listSessions` (each Environment, until a run in that isolate finds nothing to do, so a fresh deploy gets spares too, and again after an upkeep of one Environment failed), the main Worker keeps the Environment's spare current after the answer, in `waitUntil` (`spareUpkeep`, `apps/server/src/registry/rpc.ts`). One Registry call (`upkeepSpares`) says what to do, so an upkeep with nothing to do costs that call: it lists the stale spares and registers a spare, with a fresh id, for each Environment that keeps one, had a Session lately and has none. Each stale spare's record is forgotten (`forgetSpare`, which keeps a record a Session took meanwhile, whose Workspace DO is then left alone), then its Workspace DO is wiped (`destroy`, then `reset`), and a second call registers their replacements; each spare registered is asked to prepare itself (`prepareSpare`), and one whose record was forgotten meanwhile (its Environment deleted, or gone stale) has its Workspace DO wiped again, since the request made it anew. What fails is logged and left: a stale spare not forgotten is removed at a later upkeep, one forgotten whose wipe failed is left to its idle stop, and a spare that was not prepared is readied by the Session that takes it, as any new Workspace. **Prepared:** the main Worker's `waitUntil` lasts about 30 s after the answer, far less than a clone, so the spare's Workspace DO does the work (`apps/server/src/workspace/spare.ts`): `prepareSpare` stores the set-up (Repos, branch, the Environment's Container settings and its last good Build; the Environment's Secrets it carries are kept sealed apart, as a readying's are: see [_Secrets_](agent-capabilities.md#secrets)) and sets the DO's alarm for now, and answers. The DO has one alarm, which the idle stop uses too: it begins a preparation that waits (without waiting for it to end), then runs the idle stop's check, and the idle stop never sets it later than a preparation that waits. The preparation holds the Container from the idle stop as a command does and runs `prepareWorkspace` over the DO's own files and Container (`preparationHost` with the DO itself as the Workspace stub): the settings are handed over, the Repos cloned on `cloudpid/spare` from each one's default branch, and their Setup and Start Scripts run; then one empty command runs on the Container, so a spare of no Repos has had its bootstrap (Toolchains, the Environment's Setup Script) too. Then the Container is snapshotted and stopped as at an idle stop (`IdleStop.stop`; a command that runs or arrives during the snapshot keeps it), unless the spare was taken meanwhile (see below). A preparation that fails is logged and leaves the spare as it is; one cut off by an eviction is begun again at the DO's next alarm (the idle stop's, which the hold armed), three times at most. **Readied once taken:** the readying (`prepareWorkspace`) reads each clone's `.git/HEAD` from the Workspace's files, without the Container, and gives the clones on `cloudpid/spare` to `prepareWorkspaceScript` with the missing ones. The script switches such a clone under the Workspace's lock, then the clone's own (so a Setup or Start Script of the spare's that still runs is waited for), with git's hooks off and `SKIP_REFERENCE_REPOS=1`: it fetches `origin`, checks out the Workspace's branch as a clone does (tracked from `origin` when the remote has it, else made from `origin/<base>`, else from the remote's default branch, `origin/HEAD`, else unborn in an empty repo), keeping what the spare's Setup Script changed in tracked files unless the checkout cannot (then it is discarded), and deletes `cloudpid/spare`. A switch that moved the commit removes the clone's Setup Script record, so the script is due again, flags the clone for its Start Script and runs `mise install` if it declares Toolchains, as for a new clone; the readying then runs both scripts as for a new clone. A spare taken while it is still being prepared ends on the Workspace's branch: a readying that finds a clone not there yet waits for the spare's clone under the Workspace's lock and then finds it on `cloudpid/spare` and switches it, and the spare's own Setup and Start Scripts take the clone's lock, as the switch does. A spare taken midway is not stopped under its Session: the preparation reaches its own Workspace DO through a handle of its own, and any call of the DO's from outside (a command, a file operation, a readying's `containerSettings` or `updateContainerSettings`, a Skills or Prompt templates lookup: `SparePreparation.noteUse`) marks the spare taken, so the preparation ends without the stop, logs so, and leaves the Container to the idle stop as for any Workspace. The mark is kept in the object's storage (`cloudpid:spare-used`) and never undone: a preparation that has not begun (a request the upkeep sends again after the take, or one an eviction cut off) is dropped, logged, instead of readying, and stopping, a Workspace a Session works in. **Removed:** a stale spare by the upkeep, as above, and an Environment's spare when the Environment is deleted (see _Environments from the UI_). Not verified on a deployed stage: the Workspace DO running commands on its own Container through itself (checked in workerd, which has no Container), the preparation's snapshot and stop, and how much of a new Session's wait a spare takes away.
- Skills: cloudpid ships none (ADR-0026). The Skill set a Workspace holds is empty until it is handed another (below), the Skills of its Environment: its own and those kept Global. The set is mounted read-only at `/workspace/.agents/skills`, and a write there fails with `EROFS`; `find` and `grep` from above the mount skip it. The `SkillSet` schema and the empty set (`EMPTY_SKILL_SET`) are in `apps/server/src/workspace/skill-set-schema.ts`, which imports nothing of computer, so the Registry loads it too. Repo-local `.agents/skills` are discovered too: the `skills` prompt section (`@cloudpid/extensions/skills`) lists the skills in `.agents/skills` of the conversation's `cwd` and of each directory above it up to `/workspace`, nearest first, as local pi lists them (name, description, path of `SKILL.md`, which the agent loads with `read`; `disable-model-invocation` skills are left out of the list). Discovery reads files and never starts the Container. Prompt templates in `.agents/prompts` are found the same way, for the composer (see [_Client and protocol_](client-and-protocol.md) → Slash commands).
  - **Read once per context:** like `project_context`'s (see _Project instructions_), the `skills` section's text is read once per Context Window and then shown as it was (`PromptInput.shown`; `frozenSection` in `@cloudpid/effect-durable`, which the `project_context` section uses too), whatever the Skills say later: a Skill can change during a Session ([ADR-0026](../adr/0026-skills-kept-by-cloudpid-and-fetched-from-github.md)), and pi-durable sends a changed section as a patch, which a provider without mid-conversation system messages (Anthropic's, as the Session's models are configured) folds into the system prompt, the head of the cache prefix. A Skill added, edited or removed mid-context reaches the list at the next Handoff or Session (a Fork or Clone: at its first Handoff).
    - A first read that finds no Skills is kept too, as an empty section that adds nothing to the prompt's text (an absent section cannot be told from one never read, and a Skill saved later would be added as a patch). A read that fails, or a request without an environment, keeps nothing: the next request reads again, and a Skill found then is added as a patch.
    - A Handoff starts a context without the section, and the next request lists the Skills as they are then; a new Session reads them as well. A compaction (`/compact`, an Emergency Rollover) that keeps an earlier system entry keeps the text too, and otherwise the Skills are read again. A Fork or Clone keeps the source's text until its own first Handoff.
    - Expansion at submit (`/skill:name`, `$name` links; see [_Client and protocol_](client-and-protocol.md) → Slash commands) does not use this list: it asks the Workspace for its Skills when the message is admitted, so it resolves against the Skills as they are now.
  - **Cost of a read:** discovery runs where the files are: `ComputerExecutionEnv.discoverSkills` is one call to the Workspace DO's `skills(cwd)`, which walks the directories from `cwd` up in process (`discoverSkills`, `@cloudpid/extensions/skills-discovery`) and takes the Skills of the set the Workspace holds from memory, parsed once per hash (the mount is read-only and holds exactly that set, so it is what a walk of the mount finds; a test compares the two, after a hand-over and an eviction too). A read is therefore one RPC whatever the number of skills, with no listing and no read of the mounted ones. The repo's own skills are listed and read at each read of the section (the first request of a Context Window) and at each expansion at submit, but next to the storage and capped at 100; they are not kept between reads, since the agent edits them. An environment without `discoverSkills` (a test's) is walked through its file operations, as before.
  - **The Skill set** ([ADR-0026](../adr/0026-skills-kept-by-cloudpid-and-fetched-from-github.md)): the Workspace DO keeps the Skill set its mount serves in its own storage (`apps/server/src/workspace/skill-set.ts`), each file under a key of its own as its UTF-8 bytes (a string past Latin-1 would be serialized at two bytes a character, and a value may hold 2 MB; a set kept before as strings is still read), with the set's content hash; with none kept it is the empty set (`EMPTY_SKILL_SET`, the hash of no file), which is kept as nothing. A Workspace whose mount computer copied from another set before (it records the set's hash as the mount's version) is copied again, empty, at its next index. `updateSkills(set)` (files by path under the mount, and a hash) replaces it and answers `{ ok: true }`, or `{ ok: false, message }` with nothing changed: a set with the hash held does nothing, and one that is not a set, has a path that is not one a walk of the mount lists (an empty, `.` or `..` segment, a `\`), or names a file and a directory is refused before anything is kept. Otherwise the set is kept and the mount copied anew at once, as computer copies a mount whose version changed (the mount's root cleared, then every file written), so the Workspace's files, discovery and the Worker Shell lose what the new set lacks. computer checks a mount's version only at a Workspace's first index, so it is patched with `Workspace.remount()`, which checks it again (`patches/@cloudflare__computer@0.8.0.patch`). The copy runs inside `blockConcurrencyWhile`, and computer's file system is synchronous SQLite: no other call of the Workspace DO runs during it, so each (a read, a listing, a write refused with `EROFS`, one of the Worker Shell's file calls) sees the whole old set or the whole new one; a Worker Shell command that makes several calls can see the old set in some and the new one in others. computer leaves a mount it failed to write cleared and writable, so when the new set cannot be written the set held before is kept and copied again within the same block, and the hand-over is refused. `skillSetHash()` answers the hash held, so a set is handed over only when its hash differs. A Workspace is handed its Environment's Skill set (_The Environment's own Skills_, below) at each readying: the Session asks its Workspace DO for `skillSetHash()` and passes it to `getWorkspaceSetup`, which answers the set (`skills`) only when the Environment's differs, and `prepareWorkspace` hands it over with `updateSkills` before any script runs (a refusal is logged, `The Workspace refused its Environment's Skill set: …`, and the readying goes on with the set held). A spare gets it with its set-up: `prepareSpare` takes the set apart from the set-up it stores and hands it over at once. After the agent saves or removes a Skill, the Session hands its own Workspace the new set at once (`workspaceSkillSet`, then `updateSkills`); the Environment's other Workspaces get it at their next readying, and the spare when the upkeep next prepares one. A Container that runs during a hand-over gets the new set through computer's sync, as any change to the files, but not at once: under `alchemy dev` (no bind mount) the first command after a hand-over that replaced a set of 48 files with one of 3 still saw 46 of the old ones beside the new ones, and the next command saw exactly the new set. Where the bootstrap bind-mounted the directory read-only (a deployed Container, see below), whether the sync can change it is not verified; the Container has the new set at its next start at the latest.
  - **The Environment's own Skills** ([ADR-0026](../adr/0026-skills-kept-by-cloudpid-and-fetched-from-github.md)): the Registry keeps Skills for an Environment (Registry migration 22: `skills`, one row per Skill with its name, description, files by path with each file's content hash, and when it was saved; `skill_files`, each content once by its SHA-256, so a row stays under the 2 MB a row may hold). An Environment's Skill set is its own Skills over those kept Global, layer by layer, the nearest first (`mergeSkills`, `apps/server/src/registry/skills.ts`): a Skill of its own replaces the Skill of the same name kept Global whole, never file by file (`skillLayers`, which gives `[own, *]`; the scope `*` is `GLOBAL_SCOPE`, no Environment id can be `*`, and the same `skills` and `skill_files` tables keep them under that scope, so no migration). An Environment's own Skill of a name hides the one kept Global, in that Environment only. The set's hash is the SHA-256 of its files' paths and content hashes, so an Environment with none of its own and none kept Global serves the empty set, under the hash `EMPTY_SKILL_SET_HASH` that a new Workspace holds already: its Workspaces are handed nothing and their mount is empty. A Skill is checked when it is saved (`checkSkill`): a `SKILL.md` whose frontmatter `name` follows the Agent Skills rules (1 to 64 lowercase letters, digits and hyphens, not starting or ending with a hyphen, no `--`; `skillNameProblem`) and is the folder's own name, and a `description` of 1 to 1,024 characters; paths a walk of the mount lists; the checks (`packages/extensions/src/skill-checks.ts`: text only, at most 1.5 MiB a file (`MAX_FILE_BYTES`) and 4 MiB a Skill (`MAX_SKILL_BYTES`), nothing that looks like a credential or a local path); and at most 100 Skills (`MAX_SKILLS`) and 8 MiB of UTF-8 (`MAX_SKILL_SET_BYTES`: the set goes to a Workspace in one Durable Object call) in the merged set, every layer counted; a Skill saved at Global is checked against the merged set of each Environment (an Environment's own Skill of the name replaces the one saved) and against the set of an Environment keeping none of its own Skills (a new one, or one that removes its override, serves the Skills kept Global alone), and is refused naming the first set it would push over a limit; a revert that brings a Skill back is checked against both too. Taking a Skill out is refused only where it would serve in its place the Skill kept Global that it hid (an Environment's own over one kept Global) and that set would pass a limit: the agent's removal, the owner's _Remove_ and a revert of a save (`refusedToTakeOut`) all say so and remove nothing. A content no Skill and no kept Agent change refers to is deleted when the changes are pruned to the last 200 and when a Skill or an Environment is deleted (`dropUnreferencedSkillFiles`). Skills are not part of a Build's key: a change to them asks for no Build.
  - **Installing from GitHub** ([ADR-0026](../adr/0026-skills-kept-by-cloudpid-and-fetched-from-github.md); `apps/server/src/github/skill-fetch.ts`, `skill-source.ts`, `skill-paths.ts`, `contents.ts`; `apps/server/src/registry/skill-install.ts`): the Registry fetches Skills from a GitHub source and keeps them as the Environment's own (or, for `*`, the Skills kept Global), each with its **Skill source** (GLOSSARY.md: the repo, the Skill's folder in it, the ref named, and the commit). The fetch runs in the main Worker, in the Registry DO, as the GitHub App with a read-only `contents` token (the owner's installation, else the app owner's; ADR-0025): no token is handed to a Session DO or a Container, and neither the agent nor the page reaches GitHub itself. A Session asks the Registry (`agentInstallSkills`), the page asks it too (`installEnvironmentSkills`).
    - **Sources** (`parseSkillSource`): `owner/repo`, `owner/repo@skill`, and a `github.com` URL, `https://github.com/owner/repo` or `…/tree/<ref>[/<path>]` (the first segment after `tree/` is the ref, as in the `skills` CLI, so a branch name that holds a `/` is written with `%2F`: `…/tree/feature%2Ffoo/skills`; the ref and the folder are decoded). Anything else (GitLab, other hosts, well-known indexes, a local path) is refused with the forms that work, and so is a ref with an empty, `.` or `..` segment, a repo named `.` or `..`, and a `.` or `..` segment in the folder: the Registry's request carries the installation's token, and a URL parser resolves those segments (escaped or not) to another endpoint (`contents.ts` refuses them again before it builds a path); `npx skills add <source> --copy` in a Container and `environment_skill_save` stay the way to those.
    - **Pinning:** the ref named (else the repo's default branch) is resolved to a commit with one call (`GET /repos/{owner}/{repo}/commits/{ref}`), then the recursive tree and each blob are read at that commit, so the Skills of one install come from one commit. The Skill source records the ref as named (null for the default branch) and the full commit. A tree GitHub truncates, a rate limit, a repo it cannot read (not found, or private without the App installed: the two cannot be told apart), and GitHub's refusals are each reported in words; a 401 refreshes the token once (`github/request.ts`, which `workspace/github-pulls.ts` asks through too: the headers, the owner's token else the app owner's, the one retry, and what a rate limit looks like). Each request to GitHub waits at most 15 seconds.
    - **Finding Skills** (`findSkillMdPaths`, ported from the `skills` CLI 1.7.4, MIT, Vercel; the notice is kept in `skill-paths.ts`): the repo's root `SKILL.md` and then each of the CLI's priority folders in turn (`skills/`, `skills/.curated`, `skills/.experimental`, `skills/.system`, `.agents/skills`, `.claude/skills` and the other agents' skill folders), a Skill directly in one or one or two folders below it, never below another Skill; when none of them holds a Skill, every `SKILL.md` at most six segments deep. The folders `node_modules`, `.git`, `dist`, `build` and `__pycache__` are skipped in the priority folders only, as the CLI does. A source with a path (`…/tree/<ref>/<path>`) looks under that folder only. A Skill takes its folder's files (a root-level Skill only its `SKILL.md`, as the CLI does) but not `metadata.json`, `.git`, `__pycache__` or `__pypackages__`. A Skill whose frontmatter has `metadata.internal: true` is left out of the list and of `["*"]`, and is installed when named. Names match the `SKILL.md` name, the folder name or its slug; two Skills of one name keep the first found. Blobs are read only for the Skills chosen, six at a time; a Skill over 4 MiB or a file over 1.5 MiB is refused before it is read. Limits the code enforces: at most 200 `SKILL.md` files are read for a listing (`MAX_SKILL_CANDIDATES`; a repo with more answers `too_many`, asking for a folder with a tree URL or the Skills by name), at most 500 files in a Skill's folder (`MAX_SKILL_FILES`, as `environment_skill_save`'s), and 15 seconds for each GitHub request and for a skills.sh search.
    - **What is asked and kept:** with no Skill named, a repo that holds one Skill installs it, and one that holds several answers the list (name, description, folder) and installs nothing; `skills: ["*"]` installs every Skill it lists, and names install those. Each Skill is then kept as a save keeps it, with the same checks (`checkSkill`, the set's 100 Skills and 8 MB) and its own transaction, so one the checks refuse is reported and the others are installed. The same files from the same source record nothing (`unchanged`); the same files from a new commit are kept again with the new source. A save over a Skill that has a Skill source, by the agent from a Workspace folder, keeps its source and marks the Skill **modified** (_Updates_ below), and a save with a source replaces it and clears the mark. The source is part of what an Agent change records (`SkillChangeValue.source`), so a revert puts it back with the files. The agent's install records one Agent change for each Skill kept (`environment_skill_install`); the owner's, from the page, is the owner's save and records none, as the owner's removal does.
    - **Registry migration 23** adds `skills.source` (JSON `{ repo, path, ref, commit }`, null for a Skill with none), add-only.
    - **Updates and the two marks** (`apps/server/src/registry/skill-updates.ts`; Registry migration 24 adds `skills.modified`, `skills.folder_hash` and `skills.update_available`, add-only). A Skill with a Skill source is **modified** once a save without a source (the agent's `environment_skill_save`, to an Environment or to `*`) has replaced its files: the save keeps the source and sets the mark, and a save with a source (an install or an update) clears it. The mark is part of what an Agent change records (`SkillChangeValue.modified`), so a revert puts back the files, the source and the mark together. A Skill is **update available** when the daily check found its folder changed at the head of its ref; an update, an install and a save with a source clear it, and a revert to another commit leaves it unmarked with the hash forgotten (what the ref has done since is not known: the next check records the hash from the tree at that commit and marks it if the ref has moved). The mark is never a reason to apply anything.
      - **The folder hash** (`folderHashOf`, `github/skill-paths.ts`) is the SHA-256 of the sorted `relative path NUL git blob SHA` lines of the files an install keeps (`skillFilesIn`: not `metadata.json`, `.git`, `__pycache__`, and only `SKILL.md` for a Skill at the repo's root). It is not the folder's git tree SHA, which ADR-0026 names: a tree SHA also moves for the files an install leaves out and, for a root-level Skill, at every commit that touches the repo, so it would mark Skills whose installed files are the same. It is computed from the recursive tree alone, with no blob read, and recorded in `skills.folder_hash` at install and at update. A Skill kept before it was recorded gets it lazily, at the first check, from the tree at the commit it was installed at (one more tree request for each repo and commit, then never again); a revert to another commit forgets it.
      - **The daily check** (`checkSkillUpdates`, `runDailySkillCheck`) runs in the Registry DO, started by `buildUpkeep` (`Registry.checkSkillUpdates`) in the run that finds no Build to ask for or wait on, the one that then rests an hour (`BUILD_QUIET_MS`), which is where the Builds' daily look at the Repos' default branches is made too, so it needs no alarm of its own and is asked for at most hourly. It runs at most once a day, whoever asks: the Registry document `skill-update-check` records the last run and is claimed before any request, so an upkeep in another isolate or an eviction does not repeat it; after a rate limit the run is due again in an hour. It reads every Skill with a Skill source in every scope (the Environments' and `*`), groups them by repo and ref and makes one Trees request for each (`RepoReader.headTree`: the ref's head tree in one request, the default branch's as `HEAD`), however many scopes hold Skills of it. For each Skill it compares the folder's hash at the ref's head with the recorded one and sets or clears **update available**. A Skill pinned to a tag shows an update only if the tag moves; a ref that is a full commit SHA never moves and is not looked at. It applies nothing and sends no notification. A rate limit stops the run and an error that is not GitHub's answer ends it (the Registry logs it); both are due again in an hour. A repo GitHub cannot read, a truncated tree, a folder that is gone, or an installed commit GitHub no longer has (a force-push) is logged by repo or Skill and leaves its marks as they were, the others being compared.
      - **Update** (`updateSkills`): each named Skill (without names, every Skill marked update available in the scope) is fetched again at the latest commit of its recorded ref (`fetchSkillsAt`: one commit and one tree for each repo and ref, the blobs of the Skills asked for only, the checks of an install) and kept in place of itself with the new Skill source, folder hash and no mark, in its own transaction. A Skill whose folder at the new commit has the same files records nothing (`unchanged`) and loses its update available mark. A modified Skill is refused, and named, unless `overwrite` is set. A Skill with no Skill source, one not kept, one that GitHub cannot be asked for, or whose files fail the checks, is reported and the others go on. An agent's update records an Agent change for each Skill moved, with the files and source before and after (and the mark), so the user's revert brings back the earlier commit and any edits an overwrite replaced. The owner's update from the page (`updateEnvironmentSkills`, for an Environment or `*`) is the owner's save: no Agent change, no Approval, no revert, as the owner's remove and install are.
    - **`skill_search({ query, limit? })`** (`packages/extensions/src/skill-search-tool.ts`): asks `https://skills.sh/api/search?q=…&limit=…` through the web extension's guarded transport and answers each result's id (`owner/repo/skill`), source (`owner/repo`, what `environment_skill_install` takes) and install count. It records nothing and installing does not depend on it; a query under 2 characters, an unreachable or slow skills.sh and an answer that is not the API's are each reported plainly. A Session tool, deferred by default (not in `tools.offered`), run in the Session DO, and root conversation only (`PARENT_ONLY_TOOLS`). The Installed tab's search calls the main Worker (`searchSkills`: skills.sh answers no cross-origin request), which makes the same request.
    - **The Skill directory** (`apps/server/src/registry/skill-directory.ts`, `skill-badges.ts`; GLOSSARY.md → Skill directory): the Skills page's lists and search of skills.sh, asked by the main Worker (skills.sh answers no cross-origin request). Both APIs are undocumented, and skills.sh's `robots.txt` disallows `/api/` for crawlers (an accepted risk: ADR-0026), so the Worker asks little and nothing scrapes skills.sh's HTML pages.
      - **`listSkillDirectory { view, page }`** (`all-time`, `trending` or `hot`, page from 0): `https://skills.sh/api/skills/{view}/{page}`, no auth, 200 rows a page, answering `{ skills, total, hasMore }`. A row is `{ source, skillId, name, installs }`, `installs` being the count of the list (all time; the last 24 hours on Trending; today on Hot) (skills.sh's `weeklyInstalls` sparkline and `isOfficial` are left out); Hot rows also carry `installsYesterday` and `change`. A row that is not a Skill with a source, ID and install count is left out. A page is kept in the Worker's Cache API (`caches.default`, key the request URL, `Cache-Control: max-age=3600`) about an hour: the answers are public and expendable, so they need no migration or sweep as a Durable Object's SQLite would (a Durable Object has no Cache API, so the Worker, not the Registry DO, asks), and `fetch`'s `cf.cacheTtl` could be neither seen nor tested. It is per data centre, which is fine for one owner; on a `workers.dev` hostname (the previews) cache puts are no-ops, so a preview asks skills.sh on every load. Only an answer that read as one is put, so a failure is never kept; a cache that cannot be read or written is skipped.
      - **`searchSkillDirectory { query }`**: `/api/search?q=…&limit=200` (at most 200 results, fuzzy), not cached, with the same query checks as `skill_search` (2 to 200 characters).
      - **Failure:** each fails with a `SkillDirectoryError { message }` (unreachable, timed out, an answer other than 2xx, or one that is not the API's shape), which the page shows plainly.
      - **Badges** (`installedIn`, `withInstalled`): the answer is joined with what the Registry keeps on every request, never cached, so an install shows at once (`installedSkills`: every Skill with a Skill source, in any scope). A Skill counts as installed when a kept copy's Skill source repo is the row's source (GitHub's names ignore case) and the row's Skill ID names the copy as an install resolves it (`skill-fetch.ts`): by the copy's SKILL.md name, else by the name of its folder (compared lower case, words joined by hyphens; skills.sh's `skillId` is the SKILL.md name, which is not always the folder's). A caller that knows the folder (a repo's listing) matches the path exactly instead (`{ repo, path }`), so the repo page and the Skill page reuse the same join. The badge says whether the Skills kept Global hold it (`global`), the ids of the Environments that keep it as their own (`environments`), and whether any copy is marked update available.
      - **A repo's Skills** (`listRepoSkills { owner, repo, ref? }`; `apps/server/src/registry/skill-repo.ts`, `listRepoSkills` in `github/skill-fetch.ts`): every Skill GitHub has in the repo at the ref (a branch, tag or commit; the default branch's head when absent), for the repo page. It is not a skills.sh call: the main Worker reads the repo as the GitHub App with a read-only (contents) token, through the same `RepoReader` and the same walk an install uses (`findSkillMdPaths`, so a Skill is found where an install would find it, and one the repo marks `metadata.internal` is left out as an install leaves it out), so a private repo the app can read is listed and a repo skills.sh does not index is too. It resolves the ref to a commit and lists that commit's tree (two requests, always: they say the repo is readable now), then reads each `SKILL.md` (at most 200; the rest are counted in `omitted`; a cold listing of such a repo is about 200 blob reads and 400 Cache API calls in one request) for its name and description (`readSkillMd`, the one an install uses). Each answer is `{ repo, ref, commit, skills: [{ name, description, path, skillId, installs?, installed? }], unreadable, internal, omitted }` (`internal` counts the Skills the repo marks `metadata.internal`, left out; `omitted` counts `SKILL.md` files past the 200 that were not read, any of which may be a Skill); `skillId` is what a Skill's page URL calls it (its folder's name, or its name for a Skill at the repo's root: `skillIdOf`), `unreadable` lists `SKILL.md` files that are not Skills (no name or description, or too large), and a repo with no Skills answers an empty list.
        - **Cached by blob SHA, in the Worker's Cache API** (the same place and for the same reasons as the leaderboards: the data is expendable and read-through, so it needs no table, migration or sweep in the Registry's SQLite, and a Durable Object has no Cache API, which is why the Worker, which holds the GitHub App's key as the draft's branches need, lists). A blob's SHA names its content for ever, so what is read of a `SKILL.md` (name, description, the internal mark, or why it is no Skill; not the file) is put once under `<repo, blob SHA>` (30 days' `max-age`, a version in the key) and a later listing, at any ref or commit, reads from GitHub only the `SKILL.md` files that changed. A cache that cannot be read or written costs a read of the blob. The commit and tree are not cached, so a repo the app has lost access to is not served from a cache.
        - **Installs and badges are joined after,** on every request: installs from one skills.sh search of `owner/repo` (blank for a Skill it does not return, for one whose ID another Skill of the repo shares, and when skills.sh does not answer: it is fuzzy, so some of a big repo's Skills may be blank), and badges matched exactly by `{ repo, path }` (`installedIn`), so a copy installed from another folder of the repo with the same name is not this Skill. Those the directory knows by installs come first, the rest in the walk's order.
        - **Installing the page's picks** is by folder, not name: `installEnvironmentSkills { folders }` (the owner's install only; the agent's `environment_skill_install` is unchanged) reads exactly those folders (`fetchSkills`' `folders`, as an approved install does), whatever the repo's other Skills are called, so two folders that declare one name, a name that is another folder's, and a repo of more than 200 `SKILL.md` files all install the Skill that was checked, and the Skill source kept records that folder so the badge by `{ repo, path }` lands on the row. A name that two checked folders share keeps the first, as the Environment keeps a Skill by name, and says why for the second.
      - **A Skill's page** (`viewSkill { owner, repo, skill, path?, ref? }`; `viewSkill` in `github/skill-fetch.ts`, `SkillRepos.view` in `registry/skill-repo.ts`): one Skill as GitHub has it at the ref's head, for `/skills/:owner/:repo/:skill`, through the same `SkillRepos` seam, reader, walk and `SkillRepoError` as the listing. With `path` it is exactly the Skill in that folder (`skillMdIn`, whatever it is called and even when the repo marks it `metadata.internal`, as an install of the folder takes it); without, `skill` is a name found by the rules an install by name uses: the same `SKILL.md` files are read (those in a folder named so alone when there are any, else the walk's, more than 200 of which fail `too_many`, as an install refuses them; each read once, by blob from the cache) and the same test (`isNamedSkill`, shared with `fetchSkills`: the name its SKILL.md gives, in any case or as `slug` writes it, or its folder's name) picks it; internal Skills are found too. Where an install takes the first Skill that answers to the name, the page tells them all: a name that means several Skills answers `{ status: "ambiguous", candidates }` (their names, descriptions and folders), and `path` picks one. It answers `{ status: "found", skill: { repo, ref, commit, name, description, path, skillId, skillMd, skillMdFile, files: [{ path, size? }], refused?, installs?, installed? } }`: the commit and tree (two requests), the `SKILL.md` text (one blob, besides those read to find a name; the other files are not read) and the files an install takes of the folder (`skillFilesIn`, so what an install leaves out, such as `.git` and `metadata.json`, is not listed, and a Skill at the repo's root is its `SKILL.md` alone); `refused` is why an install would refuse the Skill for its size (`sizeProblems`: too many files or bytes, which an install checks before it reads any), while what a file holds is only checked by the install. Installs and badges are joined as for the listing (`joinSkillView`). `skillMdFile` is the SKILL.md's name as GitHub has it (`skill.md` in any case), which the page links. A Skill the repo does not hold fails `SkillRepoError` with kind `no_skill`; a name asked of a repo with more than 200 SKILL.md files, none in a folder named so, fails with `too_many`; the other kinds are the listing's.
        - **Failure:** a `SkillRepoError { kind, message }`: `not_found` (GitHub has no such repo, or it is private and the app cannot read it; GitHub answers both with a 404, so they cannot be told apart, and the message says which installation to check), `bad_ref` (the ref is not found but the default branch is, which one more request tells), `invalid` (an owner, repo or ref that cannot be GitHub's: refused before any request, by the install's source checks), `rate_limited`, `refused` (the app's token), `truncated` (the repo is larger than one tree listing holds), `failed`, and, for a Skill's page only, `no_skill` (the repo is readable but holds no such Skill) and `too_many` (a name asked of a repo with more SKILL.md files than can be read to find it). A Skill's page reads the same repo at the same ref through the same seam and error; the owner's page needs no GitHub.
      - **An owner's repos** (`listOwnerRepos { owner }`; `apps/server/src/registry/skill-owner.ts`): the repos of a GitHub user or organization that the Skill directory lists Skills of, for the owner page. skills.sh has no owner listing, so the Registry asks `searchSkillDirectory`'s search (`/api/search?q=<owner>&limit=200`: fuzzy, at most 200 results, not cached, with the same query checks) and keeps the results whose source is `owner/repo` of that owner (the owner's case does not matter; forks and look-alikes the fuzzy search also returns, and sources that are not `owner/repo`, are left out), grouped by repo (case-insensitive, spelt as skills.sh spells it) into `{ repo, skills, installs }`: the Skills found in the repo, each counted once by ID, and their installs added up, the most installed repo first. It is an undercount for a prolific owner: `capped` is set when skills.sh answered 200 entries, the most a search holds (counted before entries that are not Skills are dropped: `SKILL_SEARCH_LIMIT`), and the page says so (it says the list may be incomplete even when it did not). An owner the search finds nothing of (or one whose name is under 2 characters, which is not searched for) answers an empty list, which the page shows as "not in the Skill directory"; a failed search is the Skill directory's `SkillDirectoryError`. It asks no GitHub and joins no badges: each repo's page lists what GitHub has, with badges.
    - **On the Skills page's Installed tab** (`apps/web/src/skills-installed.tsx`; see [_Client and protocol_](client-and-protocol.md) → Skills page), each Environment's section has its Skills (`listEnvironmentSkills`, asked again every few seconds while the page is visible, each with its name, description and when it was saved), the Skills it gets from Global ("Also from Global") and those of its own that override one ("Overrides the Global one"), as the Environments page does for variables, a _Remove_ that asks for a confirm (`removeEnvironmentSkill`: not an Agent change, as an owner's save is not, and it waits for no Approval; its Workspaces stop serving it at their next readying, and the Skill of the name kept Global, if any, is served again), and its Skills' Agent changes with _Revert_ and _Dismiss_ as the Environments page lists the others, each file a change added, removed or changed shown as a line diff (`skillChangeFiles`, asked when the row shows). A Skill with no Skill source (one the agent wrote or saved) opens a read-only viewer of the files the Registry keeps, `SKILL.md` first (`environmentSkillFiles`: the files kept for a Skill of a scope, with their texts, by path; refused for a Skill the scope does not keep). The section at Global lists the Skills kept Global the same way (`listEnvironmentSkills`, `removeEnvironmentSkill`, `environmentSkillFiles` and `installEnvironmentSkills` take the scope `*`; an Agent change's files, and _Revert_, take it too). The agent saves (`environment_skill_save`) and installs (`environment_skill_install`) them, at Global only with the owner's Approval; the page's install is the owner's own, with none. Each section has "Add skills from GitHub": a source input (the Add button installs it; a source that holds several Skills lists them with a checklist, and "Install n selected" installs the ticked), and a skills.sh search whose results each have an Add. Each listed Skill that has a Skill source shows it, linked to GitHub at its commit (`skillSourceUrl`). The section at Global has the same form ("Add skills from GitHub at Global"): `installEnvironmentSkills` takes the scope `*`, and the owner's install there is the owner's own save, with no Approval and no Agent change, as the owner's removal is. The same checks apply, in each Environment's merged set. Each listed Skill also shows a **modified** mark (the agent edited it after it was installed) and an **update available** mark (the daily check found its folder changed at its Skill source), and has an Update action (`updateEnvironmentSkills`), in an Environment's section and in "Global". Its confirm says the update is the owner's own change, not an Agent change, so it has no revert; for a modified Skill it also says the update replaces the agent's edits, and only then is `overwrite` sent. The result of the update (updated, already up to date, refused) is shown in the dialog. An Agent change of a Skill shows "(modified since installed)" after its Skill source when it marks it.
  - **The Container's copy:** computer's sync refuses a Container write under the mount (it is recorded as skipped) but leaves it on the Container, so the Container's copy would drift until it restarts. The bootstrap (see [_Container and Toolchains_](container.md)) therefore bind-mounts `/workspace/.agents/skills` over itself read-only (only where the Container has a real mount: not under `alchemy dev`, `CONTAINER_FUSE=false`), and a write there fails with `EROFS` on the Container too. It is best effort: where the Container cannot mount (`alchemy dev`'s, without FUSE), or when a deploy replaces the skills in a running Container, the directory stays ordinary and a write there succeeds locally, never reaches the Workspace and is gone when the Container restarts. Only the mount itself is protected: `mv /workspace/.agents …` on the Container takes the mount along, and the Workspace then holds the moved copy as ordinary files next to the real mount. Checked deployed: `touch`, `>>`, `rm -rf` under the mount fail with `EROFS` on the Container, which comes back read-only after a restart (`kill 1`), and the Worker Shell's and the Container's `sha256sum` of a skill agree.
  - **Files already at the mount:** computer clears a mount's root the first time it indexes it, so what a Workspace had at `/workspace/.agents/skills` before the mount existed would be deleted. The Workspace DO moves it to `/workspace/.agents/skills.pre-mount` (`-2`, `-3` if taken) before the first index and logs a warning; nothing is moved when the directory is absent or empty, nor once the mount has been indexed (computer records it). Older Workspaces may still hold a `/workspace/.agents/skills.pre-bundle` directory: it is what this move was named while Skills were bundled, and it is left as it is. Every Workspace opened since the mount was introduced has indexed it, so nothing is moved for it: only a Workspace not opened since then can have files set aside. The move is only logged (a warning in the Workspace DO's logs); nothing in the UI or the agent's context says so, but `ls /workspace/.agents` shows the directory. Skills of a Workspace's own belong in a repo's `.agents/skills`, or in `.agents/skills` of the repo directory the agent works in.
- **Project instructions** (`@cloudpid/extensions/agents-md`): the Workspace's `AGENTS.md` files are put in front of the model as local pi and codex put them there. A directory's instructions file is the first of `AGENTS.override.md`, `AGENTS.md`, `AGENTS.MD`, `CLAUDE.md`, `CLAUDE.MD` it holds (pi's list; an empty one counts as none), cut to 64 KiB and 1,000 lines with a note to `read` the rest; the instructions for a directory are those of `/workspace`, of each directory between, and of the directory itself, the farthest first (a directory outside `/workspace` has only its own). Finding them reads files only, next to them: `ComputerExecutionEnv.discoverInstructions(directory)` is one call to the Workspace DO's `instructions(directory)` (`discoverInstructions`, `@cloudpid/extensions/agents-md-discovery`, a module of its own so the Workspaces Worker does not load the harness); an environment without it is walked through `readTextFile`.
  - **The `project_context` section** holds the instructions of the conversation's `cwd`, each as `<project_instructions path="…">` in pi's format. Its text is read once per context and then shown as it was (`PromptInput.shown`), whatever the files say later: pi-durable sends a changed section as a patch, which a provider without mid-conversation system messages (Anthropic's, as the Session's models are configured) folds into the system prompt, the head of the cache prefix. A Handoff starts a context without it, and the next request reads the files again; a compaction that keeps an earlier system entry keeps the text too.
  - **`read`, `edit` and `write`** (wrapped; the extension sits before `secrets`, so a path's Secret references are resolved when it looks) add to their result the instructions for the touched file's directory that the context does not show yet, or shows with other text ("these replace them"), as Claude Code does for the `CLAUDE.md` files below its working directory. A tool result is the end of the context and is committed with the text, so nothing a request sent changes in a later one. An edit or write of an instructions file the context showed gets a one-line note that its new text applies instead of the file again; a `read` of one adds nothing for it. One result gets at most 128 KiB and 2,500 lines of instructions (the rest waits for a later call), and the three tools' output limits are raised by as much, since pi-durable keeps only the head of a result over its limits (`read` bounds its own text to the defaults). A failed call, a script's (nested) call, whose result goes to the script, and a lookup that fails add nothing.
  - **What the context shows** is a conversation document (`cloudpid.agents-md`): each file's path and a hash of the text shown. A `beforeRequest` hook makes it what the request holds (the section's blocks and the `details.agentsMd` of the results), so after a Handoff or a compaction took a result out, its instructions are added again at the next touch; the wraps check and update it in one commit, so parallel calls add a file once.

## Backends

| Backend      | Runs                                                                    | Use                                                                            |
| ------------ | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Worker Shell | just-bash in a Dynamic Worker, with `createGitClient()` providing `git` | Text and file commands: `cat`, `grep`, `sed`, `jq`, and read-only `git status` |
| Container    | Real Linux through computerd and FUSE at `/workspace`                   | Anything needing a real binary: `npm`, `node`, test runners, `gh`              |

`bash` chooses a backend per call: an explicit `backend` argument (`worker` or `container`) always wins, and without one the command decides (`routeCommand`, `packages/extensions/src/bash-routing.ts`). The Worker Shell cannot run ELF binaries, has no network, and has no credentials, so a command that needs any of those goes to the Container; a command that is not understood goes there too, since the Container runs anything and starts only when a command is sent to it. The Container is the costly part of a Session (billed while it runs, seconds to start), so the Worker Shell gets every command it can run: a program the router does not know is asked of the Worker Shell, and a command the Worker Shell turns out not to run is rerun on the Container when running it twice cannot write twice (both below). The tool description tells the model what each backend can do, that routing is automatic, that the Container is costly and that `backend` overrides it; an environment that cannot reach the Container answers a `container` call with an error.

- **Programs the router does not know:** a program in neither `WORKER_SHELL_COMMANDS`/`WORKER_SHELL_BUILTINS` nor `CONTAINER_PROGRAMS` (the real binaries the model runs most, which go straight to the Container) is asked of the Worker Shell before the command runs (`resolveRoute`: one `command -v` script, `probeScript`, for every such program in the command), and the command goes to the Container when one is missing. The script ends with a line of its own, and an answer without it (cut short, or a probe that failed) is not kept: its command goes to the Container this once. The answers are kept for the `bash` tool's life (one per Session DO isolate): every Worker Shell runs computer's shell at the version the Workspaces Worker deployed, and a Workspace DO still on older code that lacks a program fails the command, which then falls back as below.
- **Fallback:** a command routed to the Worker Shell has its output held back until it ends. When its stderr shows the Worker Shell could not run it as the Container would (`workerShellCannot`: `command not found`, an option its version of a program rejects, `not supported`, a syntax error, the git pack limit's message; on stdout, where `2>&1` puts them, only the shell's own `command not found` and syntax error, since a file the command prints may hold any line) and the command writes no file (`BashRoute.writes`: no output redirect but to `/dev/null` or a descriptor, no `rm`/`mkdir`/`cp`/`mv`/`tee` and the like, no `sed -i` (`-i.bak` and clusters included), `sort -o`, `find -delete`, no `awk` program that may redirect or comes from a file, no program the router does not know), it runs again on the Container, the Worker Shell's output is dropped, and an info diagnostic tells the model why. A command that writes is left with the Worker Shell's answer, since running it twice could write twice; so is one whose error a `2>/dev/null` hid, or a pipe changed (`2>&1 | grep x`). A Worker Shell command that never started (`spawn_error`) runs on the Container too, when it writes no file (computer may have started it before failing).

- **Container-only paths:** a command whose path words name a Container-only path goes to the Container up front: before a command routed to the Worker Shell runs, its argument words, redirect targets, `--opt=value` values and the literal start of each glob are resolved against its `cwd` (following a `cd` earlier in the command; `~` is the Container's `/root`) and sent in one call to the Workspace DO (`ComputerExecutionEnv.containerOnly`), which answers by the launch's patterns as for the file tools. False positives (`grep node_modules package.json`) are accepted: they cost a start, not a wrong answer. A Worker Shell run whose error says a Container-only path has no such file reruns on the Container as a fallback does, when it writes no file.
- **Reading the command:** the command is read the way bash reads it (quotes, pipelines and lists, subshells, `$(…)` and backticks, heredocs, `env`/`time`/`timeout`/`xargs`/`find -exec`/`bash -c` wrappers), so a program named in a string or a heredoc body does not count and one inside a substitution does. Every simple command must be one the Worker Shell runs, or the whole call goes to the Container (one call, one backend, except that a fallback runs the whole call again on the Container). `case` is read too: its word, `in` and patterns are not commands, its clauses' commands are. `./script`, `/usr/bin/x`, `bash script.sh`, `source`, a command named by `$VAR`, `select`, `coproc`, process substitution (computer 0.6.0's shell does not parse it, though just-bash 3.6 does), and a command that does not parse go to the Container.
- **Worker Shell commands:** `@cloudflare/computer`'s just-bash core (`cat`, `grep`, `rg`, `sed`, `awk`, `find`, `sort`, `tar`, …, no `curl`, `python`, `node`, `yq`, `sqlite3`), `jq` (an optional computer module the Workspace DO adds), the shell built-ins, and `git`. `WORKER_SHELL_COMMANDS` is that list; a workerd test runs each name through the real Worker Shell.
- **git:** `git` on the Worker Shell is isomorphic-git behind `createGitClient()` (the Workspace DO passes it), not real git, and its output is not always git's. Only a small read-only set stays there, each form checked against real git's output in the workerd test: bare `git status`, `git log --oneline` (with `-n`/`-N`), `git rev-parse` (`HEAD`, `--abbrev-ref HEAD`, `--show-toplevel`), bare `git ls-files`, and `git branch` (bare or `--show-current`). Everything else goes to the Container: every subcommand that writes the index or a ref (`add`, `rm`, `commit`, `tag`, `branch <name>`, `init`, `remote`, …), `diff` and `show` (the client's patches are not git's), plain `log` (another date format), `cat-file` (broken), `clone`, `fetch`, `pull`, `push` (no network or credentials on the Worker Shell), `config`, and what rewrites the working tree (`checkout`, `switch`, `reset`, `merge`, `stash`, `clean`), as does any option or argument not listed (`git status --short`, `git log --graph`). The Worker Shell's git has no default identity (it was removed: a commit there needs `GIT_AUTHOR_*`/`GIT_COMMITTER_*` in the command, and the router sends every commit to the Container, whose identity is `CLOUDPID_GIT_NAME`/`CLOUDPID_GIT_EMAIL`).

The Workspace DO registers both backends on its one Workspace, as `worker-shell` and `container-shell`, so both see the same `/workspace`: computer pushes the DO's changes to the Container before a Container command and pulls its changes back after it. `ComputerExecutionEnv.onBackend()` selects one. computerd runs commands with `/bin/sh -c`, which is dash on Ubuntu, so a Container command is wrapped in `exec bash -c '…'` to keep `bash` bash. The Container starts on the first command sent to it, which waits for it (a message the owner sends starts nothing, so a turn that runs no command costs no Container time): about 2 s after a restore, 10–30 s from the image on Cloudflare (4 s under `alchemy dev`).

The Worker Shell returns a command's output once, when it exits: `onOutput` gets all of stdout, then all of stderr, attributed but not interleaved in arrival order. The Container streams output as it comes, so its tests must check streaming, which the Worker Shell's cannot.

## Concurrency

Sessions in one Workspace share its file tree, Container, processes and ports, as local pi sessions share a directory. Each new Session gets a new Workspace by default, with clones, a branch and a Container of its own ([ADR-0016](../adr/0016-environments-and-a-container-per-workspace.md), which supersedes [ADR-0015](../adr/0015-workspaces-are-worktrees-on-a-shared-machine.md)); starting a Session in an existing Workspace shares it. Subagents share their parent's Workspace.

## Git

- Clone and push with mise-installed `git` and `gh` in the Container (`conda:git` from conda-forge, since mise has no git in its registry otherwise; `gh` from aqua).
- Authentication comes from cloudpid's GitHub App ([ADR-0025](../adr/0025-github-access-through-a-github-app.md), GLOSSARY.md → GitHub App): a public app, registered under the owner's account and installed there and on each organization whose repos the agent works on (all repositories), whose ID and private key are the deploy-time secrets `CLOUDPID_GITHUB_APP_ID` and `CLOUDPID_GITHUB_APP_PRIVATE_KEY` (`Config.Redacted`, bound to the Workspaces Worker and the main Worker as secrets; a key that is not an RSA PEM fails the deploy). `pnpm --filter @cloudpid/infra run github-app:setup` registers it through GitHub's manifest flow and writes both into the GitHub environments and `~/.config/cloudpid/dev.env`. Anyone can install a public app, but an installation of a stranger's only gives cloudpid that stranger's repos.
  - Each Workspace DO mints its own GitHub tokens from it (`GitHubApp`, `apps/server/src/github/app.ts`): it lists the installations (`GET /app/installations`, kept five minutes, so one made later is found within them) and the account that owns the app (`GET /app`), signs a JWT with the key (RS256, GitHub's PKCS#1 key wrapped as PKCS#8), and keeps a token per installation, by its account's login, until less than 45 minutes are left of its hour, minting another when something asks then; nothing runs on a timer. A call about one repo (the Diff pane's, the draft's Start from menu, whose main Worker mints read-only ones) uses the token of the installation on the repo's owner, else the app owner's, which reads any public repo. When a mint fails, the installation's last token is handed out until it expires, and the failure is told again without asking GitHub for a minute, doubling to 15. The key never reaches the Container.
  - Each Container command gets the current tokens, minted at its start (the bootstrap gets them at its start, for it and its scripts, a repo's Setup or Start Script taking its repo as its working directory): every installation's as `CLOUDPID_GITHUB_TOKENS` (`login=token` words), and as `GH_TOKEN` and `GITHUB_TOKEN`, which is all `gh` needs, the token of the account that owns the repos its working directory covers, by their remotes, when they have one owner (`githubAccountOf`), else the token of the account that owns the app. A command that has none runs without, its stderr saying why first; one that lacks some accounts' is told which, and one with no `GH_TOKEN` which accounts git still has a token for. The bootstrap also points git's credential helper for `https://github.com` at the token for the repo's owner (`useHttpPath`, so git hands it the path), else `$GITHUB_TOKEN`, read when git asks, so no host but github.com is offered one and no file holds one (the helper is in the Container's `~/.gitconfig`, not in `/workspace`). An Environment may so hold repos of several accounts. A process keeps the tokens it started with: one running longer than 45 minutes that then reaches GitHub (a long script that pushes at its end) may find it expired.
  - Every token minted that has not expired is taken out of output and searched for before a snapshot; none is logged. The Workspace DO keeps them in its storage until they expire (`cloudpid:github-tokens`), since its Container, and a command holding one, can outlive the instance that minted it.
  - Pushes, pull requests and comments come from the app's bot (`cloudpid[bot]`). A token of an app is not a user: `gh api user`, `gh repo fork`, `gh repo create` under the owner's account, gists and stars fail with "Resource not accessible by integration". For those the owner can keep a token of their own as a Secret at Global, which a command uses by setting `GH_TOKEN` to its `PI_SECRET_` variable.
  - Only the accounts the app is installed on are reachable with credentials; public repos elsewhere still clone. Webhooks are off until the GitHub triggers need them (behind Access, they will need a bypass for their path).
- Commits are by `CLOUDPID_GIT_NAME` / `CLOUDPID_GIT_EMAIL` (deploy-time variables; defaults `cloudpid` and the owner's email), set as the Container's global git identity unless one is already set. A repo's own `user.name` and `user.email` win.
- The harness keeps hidden refs of its own under `refs/cloudpid/*`: the bases and pull request heads Comparisons fetch, and the Run diff's saved trees (`refs/cloudpid/runs/<session>/{start,end}`, written by the Workspace DO, or by a script on the Container for a repo that needs the Container's git, on a private copy of the index; the objects stay loose until the owner's `git gc`). It never writes `refs/heads`, `refs/remotes`, `FETCH_HEAD`, the index or the tree for them (see [_Diffs and review_](diffs-and-review.md)).
