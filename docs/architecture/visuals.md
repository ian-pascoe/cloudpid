# Visuals

A **Visual** is a page the agent writes and shows the owner inline in a conversation (a chart, a diagram, an explainer, a mockup), on desktop and phone: the Session keeps it as it was shown, outside History, so it shows the same after a reload, on another device, in a Fork or Clone and in an archived Session, and it runs in the App sandbox, display only, unable to call tools or tell the model anything. Visuals are first-party and kept apart from MCP Apps, sharing only the App sandbox and the frame's components ([ADR-0046](../adr/0046-visuals-are-first-party-and-kept-apart-from-mcp-apps-sharing-only-the-app-sandbox-and-the-frames-components.md)), and run at one origin per Session with no connections and resources only from cdnjs and Google Fonts ([ADR-0045](../adr/0045-visuals-run-in-the-app-sandbox-one-origin-per-session-with-no-connections-and-resources-only-from-cdnjs-and-google-fonts.md)). The idea is T3 Code's `html_render`, which shows an agent's finished HTML page inline in its thread; before Visuals, the agent's HTML could not be seen in cloudpid at all.

- **Done for v1:** a Visual shows inline where its call is, fits its content, follows the theme live, looks the same after a reload, on another device, in a Fork or Clone and archived, cannot reach cloudpid, can be checked by the agent before it is shown, can pop out into a Visual Pane, and is written by `/export` and `session_transcript` as "Visual: <title> — <summary> (not rendered)". Desktop-only or client-cached Visuals were rejected: cloudpid is always on and used from a phone.
- **Out of scope:** general apps and mini-apps that drive the Session (that is MCP Apps' job, and would double the surface), owner editing, versions, sharing and downloads.
- **Display only:** scripts run, and the host channel carries only the style variables and theme, the page's size, link opens and Escape. Nothing a page shows can steer the model or act: an App View's calls skip Approval and hooks, and a Visual's page may be an injected agent's. App messages are left out for now; they could be added later over the same channel.
- **Owner controls:** none in v1, and no Setting. The owner's Instructions can steer the agent; a later off switch would be an extension option, not an `enabled` option now, which is speculative and which the agent could flip.

## Tools

- **Where they live:** the `visuals` extension (`packages/extensions/src/visuals/`) defines `visual_show` and `visual_check` and hands each shown page to the Session's `VisualRecorder`, which keeps it in `apps/server/src/session/visuals-store.ts` ([_The copy_](#the-copy)); `packages/protocol/src/visuals.ts` holds the types, the socket messages, the CDN list, the library table, the style-variable table and the shim; the Browsers Worker's `BrowserHost.checkVisual` runs the check ([_The check_](#the-check)).
- **Who calls them:** every conversation, the root and each subagent, and `codemode` scripts, as nested calls (a script is the natural place to build a chart from data); a child has them when its grant does, by the usual rules ([_Subagents_](agent-capabilities.md#subagents)). A child shows a Visual only when asked to, and says so in its report. Root-only was rejected: the child would hand the page up to be sent twice, with no safety gain.
- **`visual_show({ path | html, title, summary })`:** shows a page in the call's card. Exactly one of `path` (a file in the calling conversation's Workspace) or `html`; a `title` of at most 200 characters; a required `summary` of at most 300, which is the frame's accessible description and stands for the page wherever it is not rendered: Details, `/export`, `session_transcript` and the evicted card (an optional one would be missing exactly there, and restating the page in the reply would duplicate the chat). It never depends on `visual_check`, and every call shows a new Visual ([_The copy_](#the-copy) → Revisions).
  - **Text result:** `Shown "<title>". Don't restate it.`, then any warnings.
  - **Value** (for scripts): `{ id, title, bytes, source_path, supersedes, warnings }`, where `id` is the Visual's id, its call's id (`callId`), and `supersedes` is the id of the earlier Visual from the same file in the conversation that now shows collapsed, if any.
  - **Fails** only when nothing faithful can show: no source or both; a file that is missing, unreadable, not a regular file (or, every link resolved, under `/dev`, `/proc` or `/sys`) or not UTF-8; an empty page; a file over 2 MiB by its size, before it is read, or a page over 2 MiB after inlining, as soon as it passes it, or local files read that come to over 2 MiB in all, left out or not; viewport-height units (`vh`, `svh`, `lvh`, `dvh`) in the page's own CSS; a bad `title` or `summary`, measured with its Secrets replaced; the Session's Secrets unreadable, so the page cannot be checked for them (retryable). Failing on every defect was rejected: one bad image would cost the whole page.
  - **Warns** on: a local asset that is missing or too large; a host not on the list ([_Network and isolation_](#network-and-isolation)); `fetch`, XHR, `WebSocket` or `EventSource` in a script; an `<iframe>` or a `<form>`; `touch-action`, `overscroll-behavior` or a non-passive touch listener; Secrets replaced; a fragment wrapped into a document.
- **`visual_check({ path | html, width?, theme?, top? })`:** read-only. It renders the page in a throwaway context of the Session's Browser Run browser with the theme, shim and CSP a frame gives it, and returns a JPEG screenshot with what it measured and saw: the content height, whether the screenshot was clipped, the growth probe's finding, console messages, CSP violations and failed loads. `width` defaults to 736 px, the thread's column (`max-w-3xl` less `px-4`, one constant tested against the layout), about 360 for a phone; `theme` to `light`; `top` is where the 3,000 px screenshot starts. A browser that is unavailable fails the call ("not checked"); a Browsers Worker that predates `checkVisual` fails it as "unavailable"; a partial result warns, a page that stops responding among them ([_The check_](#the-check)). It is a tool of its own because Browser Run is the only real browser: `browser` cannot read the Workspace or apply the theme, shim and CSP, and a `check` mode of `visual_show` would have parameters that mean nothing for showing.
- **No rate limit:** the model sets the pace, and storage is bounded ([_The copy_](#the-copy) → Bounds).
- **As built ([#658](https://github.com/ian-pascoe/cloudpid/issues/658), [#661](https://github.com/ian-pascoe/cloudpid/issues/661); `packages/extensions/src/visuals/`):** A copy the Session cannot keep fails the call (unlike an App record, the copy is the point). The preparation is regex-based (a speed bump; the CSP is the boundary) and strips `preconnect`, `dns-prefetch`, `prerender` and `prefetch` links, not `preload`. `visual_check` takes `path` or `html` through the same preparation (the preparation needs no title or summary of a page that is only rendered, and `prepareForCall` in `tool.ts` is the one place both tools read the Workspace, redact and refuse a page they cannot tell clean of the Session's Secrets), so it fails on the same defects and gives the same warnings, then asks the Session's browser host for the check (`check.ts`). `width` is 200 to 2,000 px, `top` an integer from 0 to 100,000. Its value is `VisualChecked` (`packages/protocol/src/visuals.ts`: sizes, whether it was clipped, `grows`, the console (a check cut off before it measured the height gives `content_height` null), violations and failed loads, and the warnings of the show and of the check); the screenshot is an image part of the result and never a value. It is `replay: "safe"`: a rerun after an eviction is the same read.

## Guidance

- **Deferred:** both tools are deferred by default ([_Tool discovery_](agent-capabilities.md#tool-discovery)). Offering them would put about 1.5k tokens of description on every request.
- **The `visuals` section:** a static system prompt section of two lines, shown whenever either tool is granted, loaded or not, and frozen per Context Window: it says when to show a Visual and how to load the tools. It holds nothing that changes, so the provider's prompt cache keeps hitting; the rules are not in it, since conversations that never load the tools would pay for them.
- **The description:** the page rules, layout, style variables and libraries live in `visual_show`'s static description, and `visual_check`'s points at it.
- **Page rules:** one HTML document, its scripts and styles inline or from the list; no viewport-height units; no network calls, forms or frames; never ask the owner for credentials; `alt` on images, titles in SVGs, real text, and `prefers-reduced-motion` respected; `touch-action` and touch listeners only where a gesture needs them. Prefer `path`, at the scratch path ([_The copy_](#the-copy)), for anything that will be revised: after a compaction an inline page is recoverable only through `context_history`. Check with `visual_check` first, and check `dark` too when the page sets its own colors.
- **Layout:** the frame is the thread's width (736 px on a desktop, about 360 on a phone) and fits its height to the content, so a long explainer is one tall page, not a scroll box ([_The frame_](#the-frame) → Height).
- **Style variables:** the ext-apps spec's names that cloudpid already maps for App Views (`TOKENS` and `CONSTANTS`, in one table in `packages/protocol/src/style-variables.ts`, which `apps/web/src/sandbox-frame/host-context.ts` reads); names are only ever added. The client reads their values live, so a Visual follows the theme as it changes. `visual_check`'s light and dark values are a shared table that a drift test holds to `apps/web/src/styles.css`. cloudpid's own token names were rejected (a redesign could rename them under stored Visuals), and so was generating the table (a drift test is the repo's pattern).
- **Libraries:** the description names eight pinned cdnjs files, each pin avoiding a trap found by testing each library under this CSP in Chrome (left to `visual_check`, every trap would cost a check, one Visual at a time):
  - Mermaid `mermaid/11.17.2/mermaid.esm.min.mjs` (its chunks load from the same directory);
  - Chart.js `Chart.js/4.6.1/chart.umd.min.js`;
  - ECharts `echarts/6.1.0/echarts.min.js`;
  - D3 `d3/7.9.2/d3.min.js`;
  - Cytoscape `cytoscape/3.34.4/cytoscape.umd.min.js`;
  - KaTeX `KaTeX/0.19.1/katex.min.js` with `katex.min.css`;
  - highlight.js `highlight.js/11.11.2/highlight.min.js`;
  - three.js `three.js/0.187.0/three.module.min.js`, through an import map (it loads `three.core.js` beside it).
- **Known failures,** named in the description: Vega, Vega-Lite and vega-embed (they need eval); D3's `csvParse` and `tsvParse` (embed JSON, or parse in the page's own code); the full Plotly build (use `plotly-strict.min.js`, with no map traces); map tiles (no live maps); Chart.js's ESM build (it imports a chunk cdnjs does not serve); and "latest": every URL names a version.
- **Freshness:** pins do not change, so staying current is not a goal. The table is one constant in the static description, bumped by a deliberate deploy. A unit test holds every URL to an exact version; an opt-in test (`VISUAL_LIBS_CHECK=1`), run when bumping, fetches each pin and scans it for eval. A network check in CI was rejected as flaky.

## The copy

- **Sources:** `visual_show` takes exactly one of `path` or `html`, and the Session keeps the page as shown, outside History; the client loads only that copy. `path` makes check, fix, show cheap, and the agent has often just written the file; inline-only would re-send the page with each check and the show, and path-only would make a one-off need a scratch write. The copy is never a live link to the file: Workspaces are shared, mutable and removable.
- **The scratch path:** `/workspace/.cloudpid/tmp/visuals/<distinctive-name>.html`, absolute. It sits beside the Repos, is always synced (`withHarnessKept`), is on both backends and in every Subagent Workspace, and search skips it. A relative `.cloudpid/` was rejected, since a one-Repo cwd would put it in the Repo's committed `.cloudpid/`, and so was a folder per Session, since the agent does not know its Session's ID and a collision is harmless once the page is shown.
- **Inlining** (a `path` source, at show time): local images (PNG, JPEG, WebP, GIF, SVG; at most 1 MiB each, by its size before it is read; a device or other non-regular file is never read), stylesheets and single-file scripts, relative to the file or absolute, become part of the page. A file the page names many times is read, and warned of, once; what is kept of it is what it became in the page, never its bytes, and a stylesheet or script that is not UTF-8 is left out with a warning. A module graph is reported, not resolved. So pages work offline and stay faithful, and multi-file pages, self-bundled libraries and visual-explainer's kit work, which inlining images alone would not allow.
- **Secrets:** the copy, its title and its summary are redacted of the Session's held Secrets before images are inlined, and a replaced value is a warning, not a failure: the agent cannot see the value to remove it. An SVG is redacted as text before it is inlined; a binary image that holds a Secret's bytes is left out, under the same warning. Values never enter durable state, so a show whose Secrets cannot be read fails rather than keep an unchecked copy.
- **Bounds:**
  - a page is at most 2 MiB of UTF-8 after inlining, which holds two screenshots and is well under the 32 MiB socket message (T3 Code's 10 MiB an image and 25 MiB a page were rejected: a Visual lives in Session storage and travels over the socket);
  - each Session keeps at most 32 MiB of Visuals, in a bound of their own, apart from App records', with at most 1000 Visuals kept and 2000 stubs;
  - past a bound the least recently mounted Visual becomes a stub, never the one just written; answering `visual_page` with a page marks that Visual the most recently mounted, as `mcp_app_mount` does for an App record;
  - an evicted Visual's card shows its title, summary, source, time and size, with Open file for a `path` source.
- **The record** holds the `callId`, the conversation, the parent call (the `codemode` script's, for a nested call), the title, the summary, the source (`path`, or inline), the redacted page with its assets inlined, its size in bytes, the warnings given at the show, and the time. The origin is computed from the Session, never stored ([_Network and isolation_](#network-and-isolation)).
- **The store:** `visuals-store.ts`, in the Session's storage, built on a chunked-record primitive extracted from the App record store (`mcp-apps-store.ts`; [_App records_](mcp-apps.md#app-records)). A kind of App record was rejected: every App reader would branch on the kind, and Visuals would evict App data within one bound. Sharing the `mcp_app_*` messages was rejected too: a Visual's page lives in the Session, not in `McpHost`.
- **Revisions:** every show is a new Visual. An earlier Visual from the same file in the same conversation shows collapsed, "A newer version is below", with Reopen, worked out from the transcript; `supersedes` in the result names it. Replacing a Visual by its ID was rejected: an earlier card would then show what was not shown at the time, and a Fork would be ambiguous.
- **As built ([#658](https://github.com/ian-pascoe/cloudpid/issues/658)):** the Secrets are replaced in the extension's preparation, which counts them for the warning, and not again in the store; `supersedes` is worked out by the store when it keeps the copy (the latest earlier entry of the conversation from the same path), and the card's collapse from the transcript (`apps/web/src/visual/visuals.ts`). So the store's `supersedes` (in the call's value) can name a Visual on a branch since abandoned, which the transcript no longer shows; the card follows the transcript, and collapses only for a later Visual of the same file on the branch shown.

## Socket messages

Additive; old tabs skip messages they do not know.

- **Session → client:** `visuals { conversationId, visuals }`, per conversation on `watch`, as `mcp_apps` is ([_Socket messages_](mcp-apps.md#socket-messages)).
- **Client → Session:** `visual_page { id, callId }`, answered through the socket's `id`/`result` reply with the page, `evicted` or `none`.
- **`hello.visuals`:** a Session says it keeps Visuals. A client shows a `visual_show` call to a Session that does not say so as an ordinary tool card.
- **Client → Session:** `visual_file { id, callId }`, for Open file ([_The frame_](#the-frame) → The card), answered with the file's text as it is now, or `missing`, `too_large`, `not_text` or `none`. The path is the record's, never one the client sends, and the file is read from the Workspace of the conversation that showed it through the lookup environment, which never starts the Container (as a Result Spill's preview is).

## The frame

- **Components:** `apps/web/src/visual/` renders Visuals; `apps/web/src/sandbox-frame/` takes what App Views and Visuals share out of `apps/web/src/app-view/`: `frame-url`, the frame-protocol half of the bridge, the style variables, `open-link`, `focus` and `places` (keys `app:` and `visual:`). Both `app-view/` and `visual/` import it; importing from `app-view/` was rejected, since shared code should not live inside one feature. Visuals need no teardown.
- **The shim:** the web client injects it into the page at mount, and it is never stored, so a fix to it reaches every stored Visual. It speaks a subset of the ext-apps frame protocol: initialize, size, host context (the style variables and theme), open link, and Escape. The size is the root's height at `max-content`, as ext-apps' own apps measure it, so the frame shrinks to a page shorter than it. The sandbox Worker does not change, so a preview stage can test Visuals end to end; a shim served by the sandbox, which only `prod` deploys, could be tried only after a merge.
- **Sandbox flags:** the client passes the flags and the CSP. The inner frame is `allow-scripts allow-same-origin` with `referrerPolicy="no-referrer"`: no forms, pop-ups, downloads or clipboard, none of which display needs (T3 Code's pop-ups and downloads were rejected as open doors for no gain). A frame is never delegated `local-network`, `loopback-network` or `cross-origin-isolated`.
- **Origin and CSP:** one origin per Session on the App sandbox, sent the fixed policy through the proxy's existing `?csp=` ([_Network and isolation_](#network-and-isolation); [_The App sandbox_](mcp-apps.md#the-app-sandbox)). Under `alchemy dev`, Visuals share the one local sandbox origin with App Views (dev only).
- **Height:** the frame fits its content from 160 px up to 20,000 px, then scrolls inside and offers Pop out; the height is remembered per device. So an ordinary page gets no nested scroll; a 640 px cap was rejected, since long explainers would become scroll boxes. `visual_show` fails on viewport-height units rather than rewriting them (brittle) or letting the cap absorb them (a looping page would grow to 20,000 px), and a runtime guard freezes a frame whose height grows after 3 consecutive host resizes.
- **Scrolling:** the shim forces `html, body { overscroll-behavior: auto !important }`, so a scroll that reaches the frame's end chains to the chat; `touch-action` and touch listeners are left to the page, with a warning at the show and guidance (stripping them would break legitimate gestures). Whether touch scrolling over a cross-origin frame chains to the page is confirmed for Chrome Android only, and no primary source settles it for iOS Safari. If the iPhone does not chain, a tap-to-interact overlay is added on iOS and iPadOS WebKit only: a pan scrolls the chat, a tap activates the frame, and a sticky Done chip, focus leaving or scrolling away puts the overlay back. That keeps the frame's fit; a height cap was rejected, since scroll boxes still trap at their ends, and so was forwarding touches, which has no fling.
- **Lazy mounting:** frames mount near the viewport and unmount far from it, never while focused. There is no generation rule: a Visual is a fixed copy and never goes stale, so App Views' rule has nothing to protect; only a superseded Visual collapses.
- **Start:** a page that does not complete its handshake within 10 s shows "Visual couldn't start" with Retry, as App Views do.
- **The card:** a Visual shows in its call's card, outside the card's disclosure, under the chrome "Visual · <title>"; a `codemode` script's Visuals show in the strip under the script's card, and a subagent's in its thread. The call's place keeps the turn's narrative: above the final reply would need a moving anchor and lose order, and a Pane by default would take over a phone's screen. While the call streams, the card shows its progress. Its actions:
  - **Collapse** and **Reopen**;
  - **Pop out** to a Visual Pane, and **Show here** to bring it back;
  - **Copy HTML**: the redacted copy, without the shim;
  - **Open file**, for a `path` source, which opens the file as it is now;
  - **Details**: the source, size, time, warnings, origin and summary, and that the page was written by the agent.

  A standalone tab was rejected (a `blob:` URL takes the app's origin, and the sandbox holds no HTML), and so was a re-check by the owner (the check is the agent's tool).

- **The Visual Pane:** Pop out moves a Visual to a Visual Pane, one per Visual, at full size (a sheet on a phone), and the card says where it is shown, through the shared places. The Pane is `visual:<callId>` in the page's URL and the Session layout, as an App Pane is `app:<callId>`, and it ranks with the App Pane, over a Subagent Pane or page and the card; Show here closes it, and the place below mounts the Visual again. A card, a `codemode` strip's and a subagent's thread all offer both.
- **Links:** a link the page opens goes through the same confirmation as an App View's `ui/open-link` ([_The bridge_](mcp-apps.md#the-bridge)): nothing opens before the owner chooses.
- **Accessibility:** the frame's `title` is "Visual: <title>", and the summary is its accessible description; a mount never takes focus, and Tab moves in and out natively. The shim posts an Escape the page did not handle, and focus returns to the card, which App Views cannot do; the card acts on it only while that frame has the focus, so a page cannot pull the focus from elsewhere. Full conformance is not the aim, since nobody would verify it; the description asks for `alt`, SVG titles, real text and `prefers-reduced-motion`.
- **As built ([#658](https://github.com/ian-pascoe/cloudpid/issues/658); `apps/web/src/visual/`):**
  - Pop out, Show here and the Visual Pane are [#660](https://github.com/ian-pascoe/cloudpid/issues/660)'s (`visual-pane.tsx`, `panes.ts`, `pane-area.tsx`).
  - The Escape is the notification `cloudpid/notifications/escape` (`VISUAL_ESCAPE`): ext-apps has none. The frame protocol takes it through a `notifications` option, and names its subject in the 10 s failure ("The Visual did not start within 10 seconds").
  - Collapse and Reopen are kept on the device with the App Views' choices, by call.
  - A frame mounts within 1,200 px of the viewport and unmounts past 3,600 px, so a card at the edge does not flicker; the height guard counts any growth that answers a host resize within 200 ms (a frame or two), whatever its amount, since a script sized by its frame may climb in proportion as well as by a fixed step; a page that loads in stages a few hundred milliseconds apart is spared, and measuring at `max-content` already stops a CSS percentage from looping.
  - Copy HTML is offered once the page has loaded; Open file shows the file's text in a dialog (`visual_file`).
  - A link the page opens offers Open and Dismiss; the Browser Pane is an App View's choice.
  - **The Visual Pane ([#660](https://github.com/ian-pascoe/cloudpid/issues/660); `visual-pane.tsx`):** its tab is "Visual" with the title once the Session's Visuals list the call, and `visual:<callId>` is accepted up to 512 characters. The Pane claims the `visual-pane` place and loads the page by its call (`visual_page`), not through the Session's list, so a link to a Visual of a thread the page has not watched opens it, and one the Session does not have says "This Visual is not in this Session."; an evicted one shows its card's summary with Open file and claims nothing. The page fits its content, as in the card, and the Pane scrolls it; the Pane does not remember a height, which is the card's, in another width. Its header has Show here, Copy HTML, Open file and Details; Escape from the page returns the focus to the Pane, and Escape in the Pane's own chrome to the chat, as in an App Pane. A Visual has no teardown, so Pop out and Show here swap the frame at once; a collapsed card has no Pop out, since the card is the Visual's way in.

## Network and isolation

- **The policy:** `connect-src`, `form-action` and `frame-src` are `'none'`, and there is no `blob:` or eval. Resources load only inline, as `data:`, or from the list. It blocks ordinary requests and keeps a page as it was when shown: an open network would let pages change after the fact, and a CSP the agent declares would be whatever an injected agent wants.
- **The list:** `cdnjs.cloudflare.com`, `fonts.googleapis.com` and `fonts.gstatic.com`, fixed by cloudpid. No Setting sets it and no Repo does: the agent can edit a Repo's files, and the safety of a host rests on facts a Settings page cannot show; any later Setting would be an Override behind Approval. Neither host offers a third party read-back of its requests, publishing to cdnjs is reviewed, and cdnjs carries eval-free builds of the libraries Visuals need. jsDelivr is left out: its public stats API gives daily hits per file of any package, and it serves an attacker's published script at once, so it would be the remaining channel once the channels below close, and removing it then would break every Visual that used it.
- **The origin:** one per Session, from a hash of the Session's ID kept apart from MCP servers' hashes, on the App sandbox with no Worker change. It is a site of its own: the page holds no cookie of cloudpid's, reads no storage of the app's or any App's, cannot loosen the header CSP, and only the app may frame it (`frame-ancestors`). Sessions do not share page storage, which one origin per Environment would. An opaque-origin `srcdoc` frame on cloudpid's page (T3 Code's) was rejected: it is never better on any browser, shares the app's process on desktop Firefox, and `localStorage` throws in it.
- **Process isolation:** the wording everywhere is "its own site; its own process only on desktop Chrome and Firefox". On iOS (Safari and Chrome alike) the page shares the app's process, and on Chrome Android it gets one of its own only by heuristic.
- **Known limits,** shared with App Views:
  - **Channels no CSP governs.** A determined page can still signal out: WebRTC in every browser (CSP's `webrtc` directive ships in no browser), `preconnect` and `dns-prefetch`, and Chrome's `rel=prerender`; each reached an outside host under this policy in Chrome 150. So the promise is: a Visual cannot reach cloudpid or any App's storage, its ordinary requests reach only cdnjs and Google Fonts, and what the owner types into it is not private to cloudpid. That is accepted because an injected agent already has a stronger path: `secret_ask` shows the owner cloudpid's own form, and `web_fetch` sends a value anywhere public.
  - **Spectre on iOS.** A Spectre-class page could read the app page's memory there: the transcript, socket data, and a Live View or Owner-tab link while one is open. Accepted, with no `SharedArrayBuffer`, coarse timers and lazy mounting; no inline Visuals on iOS would fail the feature's purpose.
  - **Cookies across the sandbox's site.** Every App View's and Visual's origin is a subdomain of `ianpascoe.app`, one site, so a page can set a `Domain=ianpascoe.app` cookie that another Session's Visual or any App View then sends and reads ([ADR-0031](../adr/0031-app-views-run-in-a-secretless-sandbox-on-a-domain-of-their-own.md)). Accepted as for App Views: the sandbox reads and sets no cookie and holds no secret, so all such a cookie carries is what one page chose to leave for another.
  - **`Connection-Allowlist`** (Chrome and Edge 152+) closes WebRTC and the hints, but it is Chromium-only, its inheritance by the proxy's inner frame is untested, and a mistake breaks App Views without warning. Adding it on the proxy page is a follow-up for the App sandbox, which protects App Views too.
- **Speed bumps, not a boundary:** static resource-hint links are stripped when the page is prepared, and the shim deletes the WebRTC constructors before the page's scripts run. A fresh `about:blank` realm and script-inserted links bypass both; about ten lines of code, they stop generic payloads. A `MutationObserver` was rejected: it races, and implies a boundary.
- **Provenance:** the card's chrome reads "Visual · <title>" and Details "written by the agent"; the guidance tells the agent never to ask for credentials in a Visual. Focus banners were rejected, since every click focuses the frame.
- **The rules:** neither cloudpid's pages nor the sandbox become cross-origin isolated (COOP and COEP), and no frame is delegated `cross-origin-isolated`, `local-network` or `loopback-network`, which would give a framed page `SharedArrayBuffer`, precise timers or the owner's local network. The list and the CSP apply to every stored Visual when it mounts, so tightening either later breaks the stored Visuals that relied on it; loosening is one header.

## The check

`BrowserHost.checkVisual` (`apps/browser`), on the host's own CDP socket (`openCdpSocket`), never on a conversation's tab or an Owner tab ([_Browser_](browser.md)).

- **The context:** a browser context with `disposeOnDetach` (it ends with the socket that made it, so a dropped socket takes it too), a target in it, and the viewport (`width`, with `mobile` false: a mobile viewport lays a page with no viewport meta out at 980 px) and color scheme (`theme`) emulated.
- **The page:** `Fetch` fulfils `https://visual.invalid/` with the page and the real CSP header, built by the same `buildCsp` as the sandbox's; requests to the list's hosts pass, and every other request `Fetch` sees fails. That is not everything the page can do: the channels no CSP governs and `Fetch` does not see (WebRTC, `dns-prefetch`, `preconnect`, `rel=prerender`) are the known limits of [_Network and isolation_](#network-and-isolation), and the check's prelude and the stripped hints are the same speed bumps as the frame's. Every document but the page's fails too, in any frame, top-level navigations included: a page that sets `location = "https://cdnjs…"` would otherwise leave the CSP and the `sandbox` directive behind, since only the page's own response carries them. A relative URL resolves against `https://visual.invalid/` and fails in the check, where in a frame it resolves against the sandbox's origin: a page that used one (it should not, a Visual being one document) looks broken in the check only. A real header on an https origin matches the frame. The check adds `sandbox allow-scripts allow-same-origin` to the header, the frame's flags, on top of `buildCsp`'s output and not in `buildCsp`, so App Views and the sandbox Worker do not change ([ADR-0046](../adr/0046-visuals-are-first-party-and-kept-apart-from-mcp-apps-sharing-only-the-app-sandbox-and-the-frames-components.md)): without it a pop-up, a new target `Fetch` on the page does not see, reaches the network. `Page.setDocumentContent` with a `<meta>` CSP is kept as the fallback, which the spike showed is not needed: it lands on an opaque origin, where `localStorage` throws, and a meta cannot carry `sandbox`, so it would need a pop-up guard of its own ([_Risks_](risks-and-spikes.md)).
- **Measuring:** it waits for the load, the fonts and two frames (at most 10 s), measures the layout, runs the growth probe, and collects console messages (`Runtime.consoleAPICalled`), CSP violations (`Log.entryAdded` of source `security` and `Audits.issueAdded`, each of which saw every kind the spike made; neither is a console message or an exception; the check drops the `sandbox` directive's own `Log.entryAdded` warning, "an iframe with both allow-scripts and allow-same-origin can remove its sandbox", rather than report it as the page's) and failed loads (`Network.loadingFailed`, which a CSP-blocked script or image has, with `blockedReason: csp`, and a blocked `fetch` or `eval` does not).
- **The screenshot:** JPEG at quality 80, clipped to 3,000 px from `top`; over 750,000 base64 characters (the bound the transcript holds images to: [_Filesystem and tools_](workspace.md#filesystem-and-tools)) it is retaken at quality 60, then with the clip halved.
- **Bounds:** the context is disposed in a `finally`. One check runs at a time per Session, and a check takes at most 20 s in all from when it runs: resolving the browser, opening the socket (a connection that opens after the bound is closed), the page and the dispose are all inside it (cold or warm, a result took about 1.5 to 1.8 s in the spike). The host holds at most 4 checks per Session, the one that runs and those queued behind it; one more fails at once as busy ("visual_check is busy"), so a script that calls the tool in a loop cannot pile up work in the object. What the page says is bounded as it is heard: each list keeps its first 50 and counts the rest, and each text is cut at 500 characters before it is kept. Each check is noted as a use of the browser, as a `browser` run is, for the idle close.
- **Cost:** the screenshot's tokens count at `Models`, as any input's; browser time does not, as with `browser`, and a context starts no new browser instance. A ledger of browser time was rejected: `browser` has none either.
- **Failures:** a browser that is unavailable, or does not answer before the page is asked to load, fails the call ("not checked"); a check cut off by its bound once the page is loading (the page stopped responding: its main thread is hung, say by a script that never returns) is not a failure but a partial result, which warns and holds what the check had by then (the console, violations and failed loads it heard, and any measurement or screenshot it had); and a Browsers Worker without `checkVisual` makes the tool fail as "unavailable", which `BrowserError` says in a field of its own (`unavailable`), not in its text.
- **Page text reaches the model.** What a page logs, the addresses it fails to load and the violations it causes are the page's own words, and they are in the result the model reads, so a page can write what it likes there. The tool result quotes each (JSON-quoted, on one line, so a newline or a quote cannot start a line or a section of the check's own), labels the sections "the page's own text", and never puts page text in the telemetry. The guidance says to read them as findings, not as instructions.
- **Probed, in part:** the spike ran the context, the fulfilled page, the CSP and its events, the screenshots, the times and the cleanup on a deployed non-prod stage, over `openCdpSocket`; its numbers, what it did not run (the growth probe, the 10 s wait, the retake ladder as a ladder, WebRTC and the resource hints) and what it found ([_Risks_](risks-and-spikes.md), #657) are not repeated here. The violation events were seen with the `sandbox` directive on the header. No check ran through the real `checkVisual` until #661, which confirmed the events and the directive on a deployed stage (_As built_, below); the spike no longer gates the design.

- **As built ([#661](https://github.com/ian-pascoe/cloudpid/issues/661); `apps/browser/src/visual-check.ts`, `BrowserHost.checkVisual`):**
  - **The browser:** the host resolves the Session's browser, starting one when none runs (`cold_start` in the telemetry says it did, or that Browser Run had lost it), opens a socket of its own to it (`openCdpSocket`) and closes it when done. A second check of a Session waits for the first (`CheckQueue`, `apps/browser/src/check-queue.ts`: at most 4 held, `VISUAL_CHECK_MAX_PENDING`, then "visual_check is busy"), and the 20 s in all (`VISUAL_CHECK_MS`) start when a check does and cover resolving the browser and opening the socket (`within`), the check and its dispose (which has 3 s of the 20: the check's own bound is the 20 s less those, 17 s). The wait in the queue is not in the 20 s: at most 3 checks are ahead of one, so a call waits for at most 60 s. The Session notes the browser as used before the call and after it, as `browser` does.
  - **The header:** `visualCheckPolicy()` (`packages/protocol/src/visuals.ts`) is `buildCsp` over `VISUAL_CSP` and then the `sandbox` directive. `buildCsp` is `packages/protocol/src/csp.ts`'s, which the sandbox's `csp.ts` calls with the stage's own hosts: the browser host cannot depend on `apps/app-sandbox`, which depends on the server, which depends on the browser host. `frame-ancestors` is `'none'`: the page is the top-level document. A test in `apps/app-sandbox` holds the header to what the sandbox gives a frame.
  - **The prelude:** the shim answers only a host above its window, so at the top level it does nothing; the check runs `visualCheckPrelude(theme)` first in the page's `<head>` instead: `color-scheme` and `data-theme` on `<html>`, the style variables a frame is told (the light and dark values of `TOKENS`, `TOKEN_VALUES` in `packages/protocol/src/style-variables.ts`, which `apps/web/src/sandbox-frame/style-values.test.ts` holds to `styles.css`) and no WebRTC constructors. `prefers-color-scheme` is emulated as well, for the page's own media queries.
  - **The growth probe:** the viewport starts at 160 px, the frame's own start, and follows the page as the frame does (`apps/web/src/visual/height.ts`): measure at `max-content`, resize to the fitted height, measure again. A page whose fitted height grows after each of 3 resizes in a row `grows`, and the result says so with the heights it reported; a page over 20,000 px does not, as the fit is capped. The screenshot is taken at the viewport the probe ended on.
  - **What it reports:** console messages and uncaught errors (`error`, the text starting `uncaught:` to tell it from `console.error`), at most 50 of each list and 500 characters each, kept that way as they are heard (`Capped`: the first 50, a count of the rest, and each text cut before it is joined, so a page that logs in a loop costs a count), with a warning for the rest; CSP violations as one line each: every `Audits.issueAdded` of a CSP issue (`<directive> blocked <url>`, `eval` or `inline`) and every `Log.entryAdded` of source `security` that no issue covers, matched by the address the line quotes, since the log's own `url` is the page's. The pop-up the `sandbox` directive blocks is one of the latter ("Blocked opening … in a new window because the request was made in a sandboxed frame"). Failed loads leave out the favicon and cancelled requests.
  - **Partial results warn:** the page not finished loading in 10 s (measured as it was), a screenshot that fails, `top` past the end of the page, a screenshot over the bound at every rung of the ladder, and a page that stops responding (the check's bound passed after the page was asked to load: the result holds what it heard, with whatever it had measured or shot, and the height is not measured when it had none). A browser that cannot be reached, or does not answer before the page is asked to load, fails the call: "Not checked: …". A Browsers Worker from before the method answers Workers RPC's `The RPC receiver does not implement the method "checkVisual"`, which the Session's `remoteBrowserHost` turns into a `BrowserError` with `unavailable` set (only that message: a `TypeError` inside a current host's `checkVisual` is a failure of the check), and the tool says `visual_check is unavailable`.
  - **Navigations:** every `Document` request but `https://visual.invalid/` fails, in any frame, as the header's `sandbox` and CSP would otherwise be left behind by a page that navigates.
  - **Confirmed on a deployed stage** (`dev_ian_v661`, destroyed after; Browser Run's `HeadlessChrome/152.0.0.0`; the real `checkVisual` in the `BrowserHost` object, through a throwaway route that is not merged):
    - _The pop-up._ A page that called `window.open` to an address on the stage's own Worker, which counted the requests it got, got `null` back and a `Log.entryAdded` (`security`, error) saying the pop-up was blocked, in three checks; the Worker saw no request. The same page with the `sandbox` directive left off (a throwaway switch) did open it: the Worker saw a request from `HeadlessChrome/152.0.0.0`.
    - _The events._ The page's five blocks, a `fetch` (`connect-src`), `eval`, an image, a script and a `prefetch` link (`default-src`), each arrived as an `Audits.issueAdded` of a `ContentSecurityPolicyIssue` (the `eval` with no URL and the kind `kEvalViolation`); all but `eval` as a `Log.entryAdded` of source `security` too, whose `url` is the page's and whose text quotes the blocked address, and a blocked `fetch` also as one of source `javascript`. The image, the script and the link have a `Network.loadingFailed` with `blockedReason: csp`; the `fetch` and `eval` have none. The page ran on `https://visual.invalid`, `localStorage` worked, and d3 loaded from cdnjs.
    - _The directive's own warning_ arrived as a `Log.entryAdded` of source `security`, level `warning`, "An iframe which has both allow-scripts and allow-same-origin for its sandbox attribute can escape its sandboxing." (not the spike's wording: the first version of the filter missed it, which the stage showed), and the check drops it.
    - _Nothing left behind:_ after each check, and after the one that timed out (the `sandbox`-less control), `Target.getBrowserContexts` listed no context and `Target.getTargets` only the browser's own blank page.
    - _Not run:_ the retake ladder and the 10 s load wait against Browser Run (both unit-tested on the scripted transport), two checks at once, and a check against a browser the idle close ended.

## Fork and Clone

- **The copies:** a page of `ExportPage` gains `visuals?`, and `importEntries` an optional trailing fourth argument, at every hop: the Registry's `fillSession` call and `SessionObjects` (`registry/rpc.ts`, `worker-init.ts`), `SessionMethods` (`Session.ts`), the host (`host.ts`) and `sessionForks` (`fork-host.ts`), with `fork.ts`'s `fillSession` and `exportPage` where they are made; `sessionForks` is handed the Session's store (`SessionVisualsService`) as `visuals`, and calls its `copiesFor` for a page and `adopt` for an import. A page carries the Visuals of the calls its entries hold, and of the calls nested in them, fitted to `MAX_COPY_PAGE_SIZE` as App records are ([_App records_](mcp-apps.md#app-records)): after the entry, its App records and its question records, the records whole while they fit and the rest as stubs (everything the card shows, without the page), so one entry's calls (a `codemode` script that showed many) are never split from their copies. A call's copy is its record while it is kept, and its stub when it is evicted or its parts cannot be read. A copy takes only the calls of the path it copies, and `adopt` keeps them as the root conversation's, bounded by the Session's own bounds, in one write of the index.
- **Across builds:** `VisualCopy` is a union with a `{ kind: string }` fallback that is skipped, and records change only additively, with no format version (the repo's rule for records). `ExportPage` is a plain RPC value that is never decoded, so every mismatch between the builds of the source and the target degrades to "no longer kept". `adopt` reads each copy by its shape: a kind it does not know, or one that is not the shape of its kind, is skipped; a record that is not a `VisualRecord` this build reads, or whose page is over this build's 2 MiB (its size counted again from the page, not taken from the record), is kept as the stub its card fields make, if it has them, and otherwise skipped. A source before Visuals sends none and a target before them ignores the argument. A skipped copy leaves no entry, so the card of a successful `visual_show` call that the conversation's `visuals` list (once it has come) does not hold is built from the result's `details.visual` as "no longer kept": title, summary, source and size, with no time and no Open file. And a failure to keep the copies (the storage refusing a write) drops the page's Visuals, with a warning in the log, and the Fork is still made.

## Lifecycle

- **Streaming:** while the call streams, the card shows its progress, and the frame mounts once the copy exists. A partially streamed `html` argument is never rendered: a partial render would flicker.
- **Subagents:** a subagent's Visual renders in its thread, wherever that is open. A closed subagent card has no badge for it: a badge would need counts per conversation outside `watch`.
- **Deletion:** deleting the Session takes its store with it. `subagent_delete` does what it does for App records, which is nothing: they go when they are evicted. A child's History is not deleted either.
- **Archiving:** an archived Session shows its Visuals and keeps serving them.
- **Branch moves:** a move unmounts the Visuals it drops without a guard, since there is no teardown. The records of abandoned branches stay.
- **Compaction and Rollover** do not touch the store; an inline page is still recoverable through `context_history`.
- **Notifications:** a Visual sends no Web Push or Notification.
- **Export and transcript:** `/export` and `session_transcript` write a Visual as "Visual: <title> — <summary> (not rendered)"; `session_transcript` adds a link to its Visual Pane ([_Transcripts_](mcp-endpoint.md#transcripts)).
  - **As built ([#658](https://github.com/ian-pascoe/cloudpid/issues/658)):** both read the title and summary from the result's `details.visual`, so a call that failed writes none; the link to the Visual Pane, `/sessions/<id>?pane=visual:<callId>` after the line, is added when the result names its call and the Session knows its ID ([#660](https://github.com/ian-pascoe/cloudpid/issues/660); `renderTranscript`'s `session` option).
- **Local agents and imports:** out of scope. `/mcp` drives Sessions, not their tools, and a Session import carries no Visuals: converting an imported HTML file would guess what the conversation showed.

## Telemetry

The existing `pi.tool.visual_show` and `pi.tool.visual_check` spans ([ADR-0010](../adr/0010-telemetry-at-the-seams-the-session-owns.md); [_Operations_](operations.md) → Telemetry) gain counts and fixed values only; no new spans.

- **`visual_show`:** the source kind, bytes, inlined counts, Secrets replaced, evictions, and the kinds of warning and failure.
- **`visual_check`:** width, theme, cold start, outcome, counts, content height, screenshot bytes, and whether it was clipped.
- **Never:** page text, title, summary, path, console text or hosts; a host is content the page chose.
- **As built ([#658](https://github.com/ian-pascoe/cloudpid/issues/658)):** a tool cannot see the `pi.tool` span its call runs in, so each Session keeps its running calls' spans by `callId` (`tool-span.ts` in `effect-durable`; [_Operations_](operations.md) → Telemetry), and `visual_show` adds its counts there through `annotateToolSpan`.

## Testing

Following [`AGENTS.md`](../../AGENTS.md)'s conventions; a Playwright runner was rejected, since one feature does not justify a browser runner.

- **Node unit tests:** the protocol types; the shim's served text, run in a fake window; the preparation of a show and of a check; `visual-check.test.ts`, on a scripted `CdpTransport`; the view hash (the Session's origin); the page fitting in `fork.ts`; the library table (exact-version URLs), and its opt-in fetch and eval scan (`VISUAL_LIBS_CHECK=1`, `packages/extensions/src/visuals/libraries.test.ts`).
- **Workerd tests:** `call-records` (the extracted primitive), the App store's tests as its regression, and `visuals.workerd.test.ts`: the socket messages, a Fork across builds, and a recording tracer for the spans.
- **Web component tests:** the card, the frame, the height, lazy mounting and the places; the `styles.css` drift test of the style-variable values; the 736 px constant against the layout.
- **Real browsers:** the spike, done ([_The check_](#the-check)); S4's deployed-stage confirmation of the events and the directive, done; and a hand checklist on a preview stage, on desktop Chrome, Safari and Firefox, iPhone Safari and Android Chrome, which adds touch scrolling over a frame on the phones (the iPhone's result decides S5) and wheel chaining on desktop Firefox and Safari.

## Slices

Each slice ships alone and degrades safely; one big change was rejected, since the refactors and the check carry different risks.

- **S0a:** extract the chunked-record primitive from the App record store; the App store's tests are its regression.
- **S0b:** move the shared frame code from `apps/web/src/app-view/` into `apps/web/src/sandbox-frame/`; App View tests move with it.
- **Spike:** the check on Browser Run, done: it settled the design, with the header's `sandbox` directive added ([_Risks_](risks-and-spikes.md); #657).
- **S1:** `visual_show` end to end: the extension, the store, the socket messages, the shim and the card.
- **S2:** Fork and Clone copies, in parallel with S3.
- **S3:** the Visual Pane, in parallel with S2.
- **S4:** `visual_check`, after S1 (the spike is done): done in [#661](https://github.com/ian-pascoe/cloudpid/issues/661), which confirmed the violation events and the `sandbox` directive on a deployed stage, through the real `checkVisual` ([_The check_](#the-check)).
- **S5:** the tap-to-interact overlay, only if the iPhone check fails.
- **Not a slice:** `Connection-Allowlist` on the proxy page is a separate App sandbox follow-up ([#664](https://github.com/ian-pascoe/cloudpid/issues/664); [_Network and isolation_](#network-and-isolation)).
